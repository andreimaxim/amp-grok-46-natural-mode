**Block.** Do not drop the `processed?` guard. The job never serializes the generated `Mail::Message`, and Active Job has no serializer for it. Removing the raise lets enqueue succeed after the mailer has already run, then silently rebuilds a different message in the worker from the original class/action/args.

### What `processed?` means

[`ActionMailer::MessageDelivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb) is a lazy `Delegator`. Construction stores `@mailer_class`, `@action`, `@args` and leaves `@processed_mailer` / `@mail_message` nil ([22–31](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L22-L31)).

`processed?` is true once either is set ([48–50](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L48-L50)). That happens when `#message` / `__getobj__` loads the delegate, any delegated `Mail::Message` method forces load, or `#deliver_now` / `#deliver_now!` call `processed_mailer`. That is when templates, callbacks, and `mail(...)` run. Until then there is no `Mail::Message`.

### What is actually serialized

Unprocessed enqueue ([150–152](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L150-L152)):

```ruby
@mailer_class.delivery_job.set(options).perform_later(
  @mailer_class.name, @action.to_s, delivery_method.to_s, args: @args)
```

[`MailDeliveryJob#perform`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L21-L29) constantizes the mailer, optionally applies `params`, **re-invokes the mailer action**, then calls `deliver_now` / `deliver_now!` on that fresh object. The generated `Mail::Message` is never a job argument.

Active Job serializes primitives, Hash/Array/Range, a few time types, and GlobalID ([arguments.rb 39–43, 57–91](file:///home/user/workspace/repo/activejob/lib/active_job/arguments.rb#L39-L91)). There is no `Mail::Message` serializer under `activejob/lib/active_job/serializers/`. Passing one would raise `ActiveJob::SerializationError`. The author’s premise is inverted.

### Laziness, `deliver_later` vs `deliver_later!`, queues, custom jobs

- **Laziness is the feature.** Comments and the guide say typical usage leaves the object unloaded and calls `deliver_later` ([26–27](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L26-L27); [action_mailer_basics.md ~216–218, 302–307](file:///home/user/workspace/repo/guides/source/action_mailer_basics.md)).
- **`deliver_later` vs `deliver_later!`** only changes the third argument: `"deliver_now"` vs `"deliver_now!"` ([77–78](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L77-L78), [104–105](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L104-L105)). Both share `enqueue_delivery`. The bang skips `perform_deliveries` / `raise_delivery_errors` *in the worker*. Both would leak the same silent-loss path.
- **Queue selection** is `delivery_job.set(options)` plus `queue_as { arguments.first.constantize.deliver_later_queue_name }` ([mail_delivery_job.rb 13–16](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L13-L16)). Dropping `processed?` does not change queues; it only lets a processed object reach the same enqueue.
- **Custom `delivery_job`** still receives class name, action, delivery method, and `args:` — not a `Mail::Message` ([150–152](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L150-L152); [test 99–110](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L99-L110)). Workaround 3 in the current error is “write a job that *does* take the message.”

### Parameterized mailers: worse than the claim

[`Parameterized::MessageDelivery#enqueue_delivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/parameterized.rb#L144-L151): if processed, it calls `super`; otherwise it passes `params: @params`. If the parent stops raising, a processed parameterized delivery enqueues **without `params:`**. The job then does `mailer.constantize` rather than `.with(params)` ([mail_delivery_job.rb 22](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L22)). Headers/body that came from `params` disappear.

`deliver_all_later` already bypasses `enqueue_delivery` and always serializes `params:` + `args:` without processing ([action_mailer.rb 88–102](file:///home/user/workspace/repo/actionmailer/lib/action_mailer.rb#L88-L102); [test 163–178](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L163-L178)). That is consistent with “arguments only.”

### Observable behavior after mutating headers/body

```ruby
mail = Notifier.welcome(user)
mail.message.to = "other@example.com"
mail.deliver_later
```

Today: `RuntimeError` ([test 133–138](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L133-L138)). After the diff: enqueue succeeds with `["Notifier", "welcome", "deliver_now", args: [user]]`. The worker runs `Notifier.welcome(user)` again. The `to=` is discarded. Same for subject, body, attachments. Even read-only `mail.message` (or delegated `mail.subject`) is enough to set `processed?`.

### Serialization failures vs the no-prior-access path

**No prior access must keep working:** `processed?` is false; job args are class/action/`deliver_now`/`args` (and `params` when parameterized). Tests: [59–71](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L59-L71), [265–273](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L265-L273); [parameterized_test.rb 47–55](file:///home/user/workspace/repo/actionmailer/test/parameterized_test.rb#L47-L55). The diff does not change this path.

**Args still fail the same way:** unpersisted records still raise `ActiveJob::SerializationError` at enqueue. GID lookup failures at perform are delegated via `rescue_from ActiveJob::DeserializationError` ([mail_delivery_job.rb 18, 32–47](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L18-L47); [test 250–263](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L250-L263)). None of that involves `Mail::Message`. After processing, enqueue would “succeed” and then lose work, which is worse than a serialization error.

### Claim vs tests

Covered today: enqueue args for both delivery methods, delay/priority/queue/custom job, **raise if `message` was accessed** ([133–138](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L133-L138)), parameterized params on the unprocessed path, `deliver_all_later` does not process, deserialization errors.

Not covered, and the claim needs all of them if it were true: job payload containing a `Mail::Message`; header/body mutations surviving `deliver_later`; parameterized `deliver_later` after `message`; `deliver_later!` after access; a custom job that accepts a message; Active Job serializing `Mail::Message`. The existing raise test encodes the current invariant. There is no replacement assertion that a processed message is delivered as mutated.

### Smallest viable direction

Keep the `processed?` raise. If the product goal is “allow inspect/mutate then `deliver_later`,” that needs a new delivery path: serialize the generated email (e.g. encoded RFC822), teach `MailDeliveryJob` to deliver that object instead of re-calling the mailer action, and decide what happens to `deliver` callbacks, `rescue_from`, parameterized `params`, and request/I18n state. Tests would need mutation survival, parameterized processed enqueue, `deliver_later!`, and serialization errors. That is a feature, not a one-line deletion. Workarounds remain those in the current error: don’t touch the message, mutate only inside the mailer action, or enqueue a custom job that owns the `Mail::Message`.
