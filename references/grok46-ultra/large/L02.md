`#none` is a Null Object for relations. It stays a `Relation` so callers can keep chaining. Emptiness is an instance flag plus a dummy predicate, not `[]`.

```ruby
def none
  spawn.none!
end

def none! # :nodoc:
  unless @none
    where!("1=0")
    @none = true
  end
  self
end
```

`null_relation?` is `@none`. A new relation starts with `@none = false`. Clone/`spawn` keep the flag: `initialize_copy` dups `@values` and `reset`s load state, and does not touch `@none`.

### Chainability

`#none` is `spawn.none!`, so the original relation is unchanged. Later `where` / `order` / `limit` / `joins` also `spawn`, so they clone the flag. The result is still a null relation.

`Merger` copies it in one direction:

```ruby
relation.none! if other.null_relation?
```

`Post.where(...).merge(Post.none)` becomes none. `Post.none.merge(Post.where(...))` is already none from the clone, so it stays none even though `other` is not a null relation.

`#or` is the chaining exception:

```ruby
def or(other)
  if @none
    other.spawn          # drop the null relation
  else
    spawn.or!(other)     # keep receiver; OR in other's where (including 1=0)
  end
end
```

`Post.none.or(Post.where(id: 1))` is `Post.where(id: 1)` and will query. `Post.where(id: 1).or(Post.none)` builds `(id = 1) OR (1=0)` and will query. `#and` has no `@none` special case; it keeps the flag and the `1=0` predicate.

`unscope(:where)` / `except(:where)` / `rewhere` / `invert_where` change `@values` / `where_clause` only. They do not clear `@none`. `User.none.unscope(:where)` still short-circuits as empty. `invert_where` turns `1=0` into `NOT (1=0)` in SQL, but load still returns `[]` because the flag remains.

The `1=0` string is not an equality on a column, so `where_values_hash` / `scope_for_create` ignore it. `Developer.none.where(salary: 100_000).where_values_hash` is `{ "salary" => 100_000 }`.

The same flag is how empty `in_order_of` values, unboundable uniqueness checks, and `has_many` on a new owner without a foreign key become null relations (`none!`).

### `@none` vs `where_clause.contradiction?` on load

Two different empty-load exits in `exec_main_query`:

```text
exec_queries
  skip_query_cache_if_necessary
    exec_main_query
      if @none            → []  (or FutureResult.wrap([]) if async)
      skip_query_cache_if_necessary
        if where_clause.contradiction? → [].freeze
        elsif eager_loading?
          apply_join_dependency
            if relation.null_relation? → [].freeze
            else SELECT
        else SELECT
```

`@none` wins first and skips Arel, the contradiction walk, and join-dependency construction.

`contradiction?` is only:

- `Arel::Nodes::In` with an empty array (`where(id: [])`)
- `Arel::Nodes::Equality` whose right side is unboundable

`where!("1=0")` is a SQL literal. It is **not** a contradiction. A hand-written `where("1=0")` without `#none` still runs `SELECT ... WHERE (1=0)`. `#none` needs the flag for the cheap path; the literal is what `to_sql` and subquery compilation show (`WHERE (1=0)`).

Eager load has a third check: after `apply_join_dependency`, the rewritten relation can be `null_relation?` even if the outer object was not obviously empty at the start of the method.

`load_async` calls `exec_main_query` directly (still checks out a connection). With `@none` it gets `FutureResult.wrap([])` and never hits the inner cache wrapper.

### Calculations and `exists?` / `include?`

`calculate` returns before `perform_calculation`:

| operation | ungrouped | grouped |
|---|---|---|
| `count`, `sum` | `0` | `{}` |
| `average`, `minimum`, `maximum` | `nil` | `{}` |

Async wraps that in `Promise::Complete`. `pluck` / `ids` return `[]`. `pick` is `limit(1).pluck(...).first` → `nil`. `size` goes through `count(:all)` so it is `0`.

`empty?` / `none?` return true; `any?` / `one?` / `many?` return false. `none?` / `any?` / `one?` with a block or argument still return on `@none` **before** `super`, so they do not load records to run the predicate.

`exists?` is `return false if @none` before constructing the exists relation, including `exists?(id)` / `exists?(false)` / extra conditions.

`include?` does not read `@none` itself:

```ruby
if loaded? || offset_value || limit_value || having_clause.any?
  records.include?(record)   # load → exec_main_query @none → []
else
  exists?(pk hash)           # false via @none
end
```

Either way, no SQL.

### `delete_all` / `update_all`

Both return `0` on `@none` and do not compile a DELETE/UPDATE. `delete(id)` goes through `where(pk).delete_all`; `touch_all` goes through `update_all`. `destroy_all` loads `records` (empty) and iterates nothing.

### Query-cache skip state

`skip_query_cache` is a `SINGLE_VALUE_METHODS` entry on `@values`, independent of `@none`. `skip_query_cache_if_necessary` is `model.uncached(&block)` when that value is set.

`@none` exits in `exists?`, `calculate`, `pluck`, `delete_all`, and `update_all` happen **before** that wrapper, so a null relation never consults or writes the query cache.

`exec_queries` wraps the whole load in the wrapper, then `exec_main_query` returns `[]` on `@none` *inside* that wrapper and *outside* its own inner wrapper. If `skip_query_cache!` was set, you still enter `uncached`, but the block issues no SQL. `values_for_queries` already drops `:skip_query_cache`, so the flag is not part of query identity.

### Operations that can still execute SQL after further scoping

The rdoc line that later chaining “will not fire any query” is the common `where`/`load`/`count` path, not a total ban.

SQL still happens when:

1. **`#or`** — null left-hand side is replaced by `other.spawn`; null right-hand side is OR-ed as `1=0` onto a live relation. Both query.
2. **None used as a subquery / bind value** — `Comment.where(post_id: Post.none)` goes through `PredicateBuilder::RelationHandler`, which does `attribute.in(value.arel)`. The outer SELECT runs (`WHERE post_id IN (SELECT ... WHERE (1=0))`). Composite-key association values `pluck` the inner relation first; that pluck is `@none`-short-circuited, but a non-composite subquery is not.
3. **Inserts ignore `@none`** — `create` / `create!` / `insert_all` / `upsert_all` have no guard. `scope_for_create` does not pick up `1=0`, so `User.none.create!` inserts.
4. **`cache_version` / `compute_cache_key`** — no `@none` check. Unloaded `compute_cache_version` runs `COUNT(*)` / `MAX(timestamp)` with the `1=0` predicate.
5. **`to_sql` / `explain`** — `to_sql` compiles Arel on a connection (includes `WHERE (1=0)`). `explain.count` etc. usually collect no adapter queries because `count` short-circuits; `explain` on a load that already short-circuited is empty collection, not a table scan.

`in_batches` / `find_each` do not check `@none` up front, but the first `pick`/`pluck`/`records` does, so they do not query.

`find` / `first!` / `take!` on none still raise `RecordNotFound` after the empty load; no SELECT, but not a quiet empty array.
