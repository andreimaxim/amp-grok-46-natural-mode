`ActiveJob::Exceptions.retry_on` is a `rescue_from` wrapper. On perform it matches one handler (bottom-to-top, then superclass, via `klass === exception`, then `exception.cause`), increments a per-declaration counter, and either reenqueues or exhausts. Exhaustion with a block swallows the error; without a block the original exception is re-raised after `after_discard`.

### Control flow

```text
perform_now
  executions += 1
  _perform_job → perform callbacks → perform(*)
rescue Exception => exception
  rescue_with_handler(exception)          # Rescuable
    find_rescue_handler: reverse_each, klass === exception
    else walk exception.cause (cycle-guarded)
    handler.call(exception)               # retry_on block
      executions = executions_for(exceptions)   # increment per-declaration counter
      if attempts == :unlimited || executions < attempts
        report to error reporter if report: true
        retry_job(wait:, queue:, priority:, error:)
          instrument enqueue_retry
          enqueue (set wait/queue/priority, enqueue callbacks)
          restore scheduled_at/queue_name/priority
      else  # exhausted
        instrument retry_stopped
        yield job, error   # if block given; does not re-raise
        run_after_discard_procs(error)
        raise error        # only if no block
  if unhandled
    run_after_discard_procs(exception)
    raise                  # original exception
```

```diagram
┌─────────────┐  raise   ┌──────────────────┐
│ perform_now │─────────▶│ rescue_with_     │
└─────────────┘          │ handler          │
                         └────────┬─────────┘
                    match?        │
              ┌───────────────────┼───────────────────┐
              │ yes               │ no                │
              ▼                   ▼                   │
     ┌────────────────┐   ┌──────────────┐            │
     │ retry_on block │   │ after_discard│            │
     └───────┬────────┘   │ then re-raise│            │
             │            └──────────────┘            │
     executions < attempts                            │
     or :unlimited?                                   │
        │ yes              │ no                       │
        ▼                  ▼                          │
 ┌──────────────┐   ┌─────────────┐                   │
 │ report?      │   │ retry_stopped│                  │
 │ retry_job    │   │ after_discard│                  │
 │ enqueue_retry│   │ raise unless │                  │
 └──────────────┘   │ block given  │                  │
                    └─────────────┘
```

### Exception matching and handler lookup

`retry_on` registers through `rescue_from(*exceptions)` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 66–91). Each listed class becomes its own `[class_name, handler]` entry, appended in declaration order ([rescuable.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb) 59–83). The handler Proc is shared.

Lookup ([rescuable.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb) 140–152): `rescue_handlers.reverse_each.detect { klass === exception }`. Later declarations win; subclass handlers are appended after parent ones, so they win too. That is the documented “bottom to top, and up the class hierarchy” ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 26–27). Docs say `is_a?`; the code uses `===` (equivalent for Exception classes; custom `===` matchers also work — [rescuable_test.rb](file:///home/user/workspace/repo/activesupport/test/rescuable_test.rb) 148–151).

If nothing matches, Rescuable walks `exception.cause` with a cycle guard ([rescuable.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb) 100–117, [rescuable_test.rb](file:///home/user/workspace/repo/activesupport/test/rescuable_test.rb) 165–178). Active Job tests do not cover cause fallback; it still applies because `retry_on` is `rescue_from`.

Subclass vs superclass: `AfterDiscardRetryJob` declares `retry_on AfterDiscardError` then `retry_on ChildAfterDiscardError`. A child exception hits only the later, more specific handler, so `after_discard` runs once ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 423–428, [after_discard_retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/after_discard_retry_job.rb) 18–19).

### Counters: grouped vs separate declarations

Two counters:

- `executions` — global, `+= 1` at the start of every `perform_now` ([execution.rb](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb) 47–48). Serialized on the job ([core.rb](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb) 37–44, 111, 126, 167).
- `exception_executions[exceptions.to_s]` — per `retry_on` declaration. `executions_for` increments that key and returns it ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 204–212). The key is the `*exceptions` array’s `to_s`, closed over by the handler.

One declaration with several classes shares one counter. `retry_on FirstRetryableErrorOfTwo, SecondRetryableErrorOfTwo, attempts: 4` exhausts after 4 combined hits, even if the class changes ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 39–52). Separate `retry_on` calls get separate keys, so 4 `DefaultsError` + 3 `FirstRetryableErrorOfTwo` both stay under their limits ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 54–71). Delay math uses the per-declaration counter, not global `executions` ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 307–332).

If `exception_executions` is nil (AJ 5.2 payloads), `executions_for` falls back to global `executions` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 207–211, [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 364–385).

`attempts` includes the original run (default 5). After 4 retries the 5th `executions_for` is 5; `5 < 5` is false, so that failure exhausts. Raising 4 times then succeeding on the 5th is success ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 26–34); a 5th raise re-raises ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 73–78).

### `attempts: :unlimited`

Condition is `attempts == :unlimited || executions < attempts` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 77). Unlimited never takes the else branch. `UnlimitedRetryError` raised 9 times then succeeding on the 10th works ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 355–361, [retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb) 45).

### Wait: numeric, proc arity, `:polynomially_longer`, jitter

Declaration rejects unknown wait types ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 67–73, [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 447–465).

`determine_delay` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 180–197):

- Integer / Float / Duration: `to_f + jitter`. Default wait is `3.seconds`. Hour wait and `4.5` are tested ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 107–132).
- Proc: `arity == 2 || arity < -1` → `call(executions, error)`, else `call(executions)`. Jitter is not applied to proc results.
  - one-arg: `->(executions) { executions * 2 }` → 2, 4, 6, 8 ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 257–270)
  - optional one-arg (`arity -1`): `->(executions = 0)` still one-arg ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 273–284)
  - two-arg: `->(executions, error) { error.retry_after + executions }` → 11, 12 ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 287–298)
- `:polynomially_longer`: `executions**4 + jitter(executions**4) + 2` → ~3s, ~18s, ~83s, ~258s ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 185–189, [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 135–157). Docs at 32–33 match this formula.

Jitter ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 181–182, 199–202): omitted `jitter:` uses `self.class.retry_jitter` (framework default `0.0` at [exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 11; new apps `0.15` from 6.1 defaults). `jitter: nil` or `0` → `0.0`, no randomness ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 238–254). Formula is `Kernel.rand * delay * jitter`. Negative jitter shortens wait ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 221–235).

### `report: true`

Only on the retry path, before `retry_job`: `ActiveSupport.error_reporter.report(error, source: "application.active_job")` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 78). Exhaustion does not report. Test: `ReportedError` raised then retried is reported ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 396–399, [retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb) 46). Default `handled: true`, `severity: :warning` on `ErrorReporter#report`.

### Exhaustion block

`block_given?` / `yield self, error` refer to the block passed to `retry_on`, captured by the handler Proc ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 80–89).

- With block: `instrument :retry_stopped` wraps the yield; then `after_discard`; **does not re-raise**. `CustomCatchError` is swallowed and JobBuffer records custom handling ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 98–101).
- Without block: `retry_stopped` with no block, `after_discard`, then `raise error` (same object). `DefaultsError` 6 times is rescued by the test ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 73–78).

Unhandled exceptions skip retry_on entirely: `after_discard` then bare `raise` ([execution.rb](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb) 51–56, [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 406–411).

### Instrumentation

Retry: `instrument :enqueue_retry, { error:, wait: }` around enqueue ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 169–173).

- Notification: `enqueue_retry.active_job` ([instrumentation_test.rb](file:///home/user/workspace/repo/activejob/test/cases/instrumentation_test.rb) 27–29)
- Structured: `active_job.retry_scheduled` with job_class, job_id, executions, wait_seconds, exception_* ([structured_event_subscriber.rb](file:///home/user/workspace/repo/activejob/lib/active_job/structured_event_subscriber.rb) 111–124)
- Log: `Retrying … after N attempts in X seconds, due to a Klass` ([log_subscriber.rb](file:///home/user/workspace/repo/activejob/lib/active_job/log_subscriber.rb) 99–108, [logging_test.rb](file:///home/user/workspace/repo/activejob/test/cases/logging_test.rb) 292–297)

Because `enqueue` runs inside that, `around_enqueue` also emits `enqueue.active_job` or `enqueue_at.active_job`.

Exhaustion: `retry_stopped.active_job` / structured `active_job.retry_stopped` / log `Stopped retrying …` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 82–87, [instrumentation_test.rb](file:///home/user/workspace/repo/activejob/test/cases/instrumentation_test.rb) 31–33, [logging_test.rb](file:///home/user/workspace/repo/activejob/test/cases/logging_test.rb) 316–331). Emitted both with and without an exhaustion block.

### Queue / priority overrides

`retry_on` passes `queue:` and `priority:` into `retry_job` → `enqueue` → `set` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 79, [core.rb](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb) 180–184). `set` applies `wait` as `scheduled_at`, `queue` via `queue_name_from_part`, `priority` as `to_i` when present.

`retry_job` snapshots `scheduled_at`, `queue_name`, `priority`, enqueues, then restores them in `ensure` so the in-memory instance is unchanged; the serialized/enqueued copy keeps the overrides ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 169–173).

`retry_on HeavyError, queue: :low`: first perform logs `(default)`, retry logs `(low)` ([retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb) 47, [logging_test.rb](file:///home/user/workspace/repo/activejob/test/cases/logging_test.rb) 300–307). No exception test asserts `priority:` on `retry_on`; it uses the same `set` path.

### Callbacks

- Each attempt: `before_perform` / `around_perform` / `perform`. `after_perform` does not run if `perform` raised (`skip_after_callbacks_if_terminated: true` on perform callbacks).
- Reenqueue: full enqueue callback chain (`before_enqueue`, `around_enqueue`, `after_enqueue`). `RetriesJob` shows a `before_enqueue` failure is itself `retry_on`-able on the same job object ([retries_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/retries_job.rb), [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 387–393).
- `after_discard`: exhaustion (block or re-raise), `discard_on`, and unhandled errors. Not on a successful retry ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb) 406–444). If an `after_discard` proc raises, that exception is raised and the original `raise error` is skipped ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb) 214–223).

### Does the original exception escape?

| Path | Escapes? |
|---|---|
| Retry (attempts remaining / unlimited) | No. Handler swallows; `perform_now` returns the exception object ([execution.rb](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb) 51–53, [rescuable.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb) 107–109). |
| Exhaustion with block | No. Block runs; no `raise`. |
| Exhaustion without block | Yes. `raise error` after `retry_stopped` and `after_discard`. |
| No matching handler | Yes. `after_discard` then bare `raise`. |
