## Product shaping brief: clearer cross-adapter `insert_all` / `insert_all!` around `unique_by:` and `returning:`

This is a **behavior-change** brief for an existing bulk-insert capability. It describes the user-visible contract people should be able to rely on. It is not an implementation design. Current-behavior claims below are from this revision’s public API, capability predicates, and bulk-insert tests—not from an assumption that PostgreSQL, SQLite, MySQL, and MariaDB agree.

**Evidence inspected:** public `insert_all` / `insert_all!` contract; option validation and unique-index resolution; adapter predicates for skip-duplicates, conflict-target selection, and returning rows; bulk-insert tests covering skip vs bang, `unique_by`, `returning`, composite keys, empty input, mismatched keys, casting/serialization, and timestamps (mostly via the sibling upsert path). SQL generation and adapter internals were used only to establish what a caller can observe, not as a proposed solution.

---

### Problem frame

A developer bulk-inserts hashes with `ActiveRecord::Relation#insert_all` (skip duplicates) or `#insert_all!` (fail on duplicates), optionally naming a uniqueness target (`unique_by:`) and asking which values come back (`returning:`).

They are trying to write one call that is safe to run against PostgreSQL, SQLite, MySQL, and MariaDB: skip or reject the intended duplicates, leave existing rows unchanged, and—when the database can—get back inserted keys or chosen columns.

Today that is painful because the same options do not mean the same thing on every database, and the public contract overstates uniformity:

- `unique_by:` is documented as PostgreSQL/SQLite-only, but the skip form’s *default* uniqueness target is easy to misread as “primary key” on every adapter.
- On PostgreSQL/SQLite, skip without `unique_by:` ignores a row that collides with *any* unique index. On MySQL/MariaDB the skip form also ignores any duplicate-key collision, but **cannot** narrow that to one index; passing `unique_by:` raises.
- The bang form’s docs say `unique_by:` checks uniqueness “according to just one unique index.” In this revision, bang still raises on **any** unique violation. `unique_by:` is accepted on PostgreSQL/SQLite (including invalid names) and rejected on MySQL/MariaDB, without changing which conflict fails the statement.
- `returning:` is documented for PostgreSQL, SQLite, and MariaDB. MySQL rejects an explicit `returning:` value. MariaDB only returns rows when the server is new enough (≥ 10.5 in this revision). Default return columns are the table’s primary-key columns when returning is supported; otherwise the result has no columns.
- Composite-primary-key tables expose a further split: skip without `unique_by:` raises on PostgreSQL/SQLite (“no unique index found for” the model’s primary-key name) but succeeds on MySQL/MariaDB. Bang does not require `unique_by:` on any of these adapters.
- Skip and bang differ in atomicity: skip can keep the non-conflicting rows from the same call; bang is documented to insert **no** rows from that call if any row is not unique.

The desired progress is a contract a developer can predict from the adapter in front of them: which collisions are skipped vs raised, when `unique_by:` / `returning:` are legal, what the result contains, and whether a failed bang call left rows behind.

---

### Desired observable outcomes

1. **Adapter capability is visible in the call, not only after reading SQL.** On an adapter that cannot skip duplicates, select a conflict target, or return inserted rows, an explicit unsupported option fails with a clear argument error naming the adapter and the option. A supported default does not require the caller to pass the option.

2. **Skip (`insert_all`) never updates an existing row.** A skipped duplicate leaves the stored attributes unchanged. It is not a quiet upsert.

3. **Skip’s default conflict set is “any unique constraint on the table,” on every adapter that can skip.** Duplicate primary keys, duplicate named unique indexes, and duplicate composite unique indexes are all skipped unless the caller narrows the target. Non-conflicting rows in the same call are inserted.

4. **On adapters that can name a conflict target (PostgreSQL, SQLite), `unique_by:` narrows skip behavior to that unique index only.** Collisions on that index are skipped. Collisions on any other unique index raise `ActiveRecord::RecordNotUnique`. The target may be an index name, a single unique column, a composite unique column list (order-insensitive), or a unique expression index identified by name.

5. **On adapters that cannot name a conflict target (MySQL, MariaDB), `unique_by:` is not silently ignored.** Passing it raises. Skip still ignores duplicates on every unique key the database enforces.

6. **Invalid `unique_by:` fails before any row is written** when the option is meaningful (skip on PostgreSQL/SQLite): missing index, non-unique index, or column list that is not a unique index → argument error (“no unique index found…”). This should also hold if bang is defined to honor `unique_by:`; today bang does not validate the target.

7. **Bang (`insert_all!`) is all-or-nothing for uniqueness.** If any supplied row violates a unique constraint the statement enforces, the caller gets `ActiveRecord::RecordNotUnique` and **no row from that call remains inserted**. Existing rows are unchanged.

8. **Bang does not require a unique index or `unique_by:`** to insert new rows, including on composite-primary-key tables.

9. **Composite primary keys are first-class, but skip-on-conflict-target adapters still need an explicit target today.** PostgreSQL/SQLite skip without `unique_by:` raises when the model primary-key name does not match a unique index (the Cart fixture: model key `id`, table key `shop_id, id`). Skip with `unique_by:` matching the composite key succeeds. MySQL/MariaDB skip and bang succeed without `unique_by:`.

10. **`returning:` is opt-in only where the adapter can return inserted rows** (PostgreSQL, SQLite, MariaDB ≥ 10.5). Default: primary-key column(s) of successfully inserted rows. `returning: false` and `returning: []` insert the rows and return a result with no columns. A column list returns those columns. A wrapped SQL expression returns the expression’s result (including aliases). Attribute aliases are returned under the name the caller asked for.

11. **MySQL (and MariaDB too old to return rows) reject an explicit `returning:` value** and, when the option is omitted, return a result with no columns. Inserts still happen.

12. **Empty input is a no-op.** `insert_all([])` and `insert_all!([])` return an empty result and do not change the table.

13. **Every hash in the batch must have the same keys.** Extra or missing keys raise an argument error that names the extra/missing keys. No rows are inserted.

14. **Values are type-cast and serialized like a normal persist**, even though models are not instantiated and callbacks/validations do not run. Enums, serialized columns, and custom coders match `create` / `create!` for the same value. Unknown attributes raise `ActiveRecord::UnknownAttributeError`.

15. **Timestamp fill can be overridden per call.** If recording timestamps is on (model default or `record_timestamps: true`), omitted timestamp columns are filled. Caller-supplied timestamp values win. `record_timestamps: false` leaves omitted timestamps unset. *(Documented on `insert_all`; this revision’s tests exercise the override mainly through upsert.)*

16. **Skip vs bang atomicity is part of the product, not an accident of SQL.** Skip may persist a subset of the batch. Bang may persist none of it. Neither form updates skipped/failed existing rows.

---

### Non-goals

- Changing `upsert_all` / `upsert` beyond what is needed to keep skip “not a secret upsert.”
- Instantiating models, running validations, or firing callbacks on bulk insert.
- Prescribing SQL, conflict-clause shape, adapter internals, schema-cache wiring, or a rollout plan.
- Making MySQL/MariaDB grow `unique_by:` or making MySQL grow `returning:` in this brief.
- Flattening all four databases into one behavior where this revision’s capabilities differ.
- Redefining relation scoping, `create_with`, STI, or has-many-through rejection except as unchanged surroundings.

---

### Open questions

These are unsettled by this revision; they should not be treated as requirements until product intent is chosen.

1. **Bang + `unique_by:`.** Docs say bang checks only the named unique index. Implementation accepts the option on PostgreSQL/SQLite, does not resolve or validate it, and still raises on any unique violation. Should bang honor `unique_by:`, reject it as meaningless, or keep today’s “accepted but inert” behavior?

2. **Invalid `unique_by:` on bang.** Skip raises “no unique index found.” Bang currently does not. Should invalid targets fail the same way on both forms?

3. **Default skip target vs primary key.** Docs say “every unique index.” PostgreSQL/SQLite skip without `unique_by:` matches that when the primary key is not also selected as a named target. Composite-key models that expose a single-column `primary_key` raise instead. Should skip infer the **table** primary key, keep requiring `unique_by:`, or treat “no unique index found for id” as the intended composite-key error?

4. **Within-batch duplicate hashes on skip.** Two rows in one call with the same identifier: this revision keeps the **first** row’s attributes (the test name says “last”). Is first-wins the contract, or should last-wins match upsert-on-MySQL?

5. **`returning` after skip.** Docs say return values for **successfully inserted** rows. Tests cover returning mainly on bang and on skip with aliases. Should skipped rows ever appear in the result? What should a composite primary key return by default?

6. **`record_timestamps` on `insert_all` specifically.** Documented; tests are upsert-centric. Confirm insert-only fill/override is in scope for the same examples.

7. **MariaDB version split.** Is “MariaDB returns rows only when new enough, MySQL never” the lasting product surface, or should callers see one MySQL-family answer?

8. **Empty `returning:` vs `false`.** Both yield a no-column result today. Keep them equivalent?

9. **Partial unique indexes.** ISBN uniqueness applies only when `published_on` is present. Is “conflict target honors the index predicate” required, or only a PostgreSQL/SQLite artifact?

### Acceptance examples

Required unless marked illustrative. “Book” has a primary key `id`, a unique composite index on `[author_id, name]`, a partial unique index on `isbn` when `published_on` is set, and—where the adapter supports expression indexes—a unique index on `lower(external_id)`. “Cart” is a composite-primary-key table (`shop_id`, `id`) whose model primary key is `id`.

#### Adapter matrix (where supported)

| Observation | PostgreSQL | SQLite | MySQL | MariaDB |
|---|---|---|---|---|
| Skip duplicates | yes | yes | yes (any unique key) | yes (any unique key) |
| `unique_by:` | yes | yes | argument error | argument error |
| Bang without `unique_by:` | yes | yes | yes | yes |
| Default `returning` (omit option) | primary key columns | primary key columns | no columns | primary key columns if server ≥ 10.5; else no columns |
| Explicit `returning:` | honored | honored | argument error | honored if ≥ 10.5; else argument error |

#### Skip: default conflict target

**When** a Book with `id: 1` already exists  
**And** the caller `insert_all`s `{ id: 1, name: "Agile Web Development with Rails" }` with no `unique_by:`  
**Then** count is unchanged, the existing book is unchanged, and no exception is raised  
**On** PostgreSQL, SQLite, MySQL, MariaDB (skip supported).

**When** two new books share `author_id` and `name` but have no ids (or distinct ids)  
**And** the caller `insert_all`s both with no `unique_by:`  
**Then** exactly one row is inserted  
**On** all four adapters.

**When** an existing book has `format: "EXPECTED"` and unique `[author_id, name]`  
**And** skip inserts `{ format: "UNEXPECTED", author_id: same, name: same }`  
**Then** count is unchanged and `format` is still `"EXPECTED"` (skip is not upsert)  
**On** all four adapters.

**When** one skip call contains `{ id: 111, name: "expected_new_name" }` then `{ id: 111, name: "unexpected_new_name" }`  
**Then** the stored name is `"expected_new_name"` (first row kept)  
**On** adapters that skip. *(Open question if last-wins is desired.)*

#### Skip: named, composite, and expression `unique_by:` (PostgreSQL, SQLite only)

**When** `unique_by:` is `:isbn`, `%i[author_id name]`, `:index_books_on_isbn`, or `:id`  
**And** the row does not collide on that target  
**Then** the row is inserted.

**When** `id: 1` already exists  
**And** skip uses `unique_by: :index_books_on_author_id_and_name` with `{ id: 1, name: "Agile Web Development with Rails" }`  
**Then** `RecordNotUnique` is raised (collision is not on the named target).

**When** a book exists with `external_id: "abc"`  
**And** skip uses `unique_by: :index_books_on_lower_external_id` with `{ external_id: "ABC" }`  
**Then** count is unchanged  
**On** PostgreSQL/SQLite with expression indexes.

**When** `unique_by:` is the composite columns in reverse order (`[:name, :author_id]`)  
**Then** the composite unique index is still found and the insert proceeds as with the canonical order.

**When** MySQL or MariaDB is given any `unique_by:`  
**Then** argument error: the adapter does not support `:unique_by`.

#### Invalid or non-unique `unique_by:`

**When** skip on PostgreSQL/SQLite gets `unique_by: :cats`, `%i[author_id isbn]`, or `:author_id` (not unique)  
**Then** argument error matching “No unique index found”, and no row is inserted.

**When** bang on PostgreSQL/SQLite gets the same invalid `unique_by:`  
**Then** today the call is **not** rejected for a missing index *(open question 2)*.  
**When** bang on MySQL/MariaDB gets any `unique_by:`  
**Then** argument error: adapter does not support `:unique_by`.

#### Composite primary keys

**When** PostgreSQL/SQLite skip `Cart.insert_all [{ id:, shop_id:, title: }]` **without** `unique_by:`  
**Then** argument error: no unique index found for `id`.

**When** the same skip uses `unique_by: [:shop_id, :id]`  
**Then** the cart is inserted.

**When** bang `Cart.insert_all!` without `unique_by:`  
**Then** the cart is inserted on PostgreSQL, SQLite, MySQL, and MariaDB.

**When** MySQL/MariaDB skip Cart without `unique_by:`  
**Then** the cart is inserted (no conflict-target requirement).

#### Bang uniqueness and atomicity

**When** bang inserts several books and one collides with an existing unique value (e.g. existing `id` or `[author_id, name]`)  
**Then** `RecordNotUnique` is raised and **no row from that call** is present afterwards  
**On** all four adapters.

**When** bang on PostgreSQL/SQLite is passed `unique_by: :isbn` for a new ISBN  
**Then** the row is inserted (option is accepted).

**When** a partial unique ISBN already exists (`published_on` present)  
**And** bang inserts the same ISBN with `published_on` set, even with `unique_by: :isbn`  
**Then** `RecordNotUnique` is raised.

#### `returning:`

**When** returning is supported and the caller omits `returning:`  
**Then** the result is an `ActiveRecord::Result` whose columns are the primary-key column(s) (Books: `id`).

**When** `returning: false` or `returning: []`  
**Then** the row is inserted and the result has no columns  
**On** PostgreSQL, SQLite, MariaDB ≥ 10.5.

**When** `returning: [:id, :name]`  
**Then** result rows include those columns for successfully inserted records (`name` is `"Rework"` in the fixture case).

**When** `returning:` is a wrapped SQL expression `UPPER(name) as name`  
**Then** the result’s `name` is `"REWORK"`.

**When** an attribute alias is returned (`returning: :title` while inserting `title:`)  
**Then** the result includes the alias name `title`.

**When** MySQL (or MariaDB < 10.5) is given an explicit `returning:` value  
**Then** argument error: the adapter does not support `:returning`.  
**When** those adapters omit `returning:`  
**Then** insert succeeds and the result has no columns.

#### Empty input, mismatched keys, casting, timestamps

**When** `insert_all([])` or `insert_all!([])`  
**Then** the result is empty and table count is unchanged.

**When** hashes in one call differ in keys (extra `isbn` on one row, or missing `isbn` on the next)  
**Then** argument error: all objects must have the same keys, naming extra/missing keys; no rows inserted.

**When** bang/skip persist a serialized column or enum with the same Ruby value as `create!`  
**Then** the stored/loaded value matches `create!` (no double-encoding through a non-idempotent coder; arrays/enums round-trip).

**When** `insert_all!` is given an unknown attribute  
**Then** `ActiveRecord::UnknownAttributeError`.

**When** `record_timestamps:` is true/false opposite the model setting  
**Then** omitted timestamp columns are filled only when the call says to record timestamps; explicit timestamp attributes in the hash are kept. *(Confirm on insert_all, not only upsert—open question 6.)*

#### Unchanged surroundings (counterexamples)

**When** the caller uses `create_with` or a scoped association (`author.books.insert_all!`)  
**Then** scope/default attributes are applied; an explicit `author_id` on the hash does not override the association’s owner in this revision’s association-precedence test.

**When** the association is has-many-through  
**Then** argument error; bulk insert is refused.

These counterexamples are out of `unique_by:` / `returning:` scope except as “do not break.”

---

### Steering evidence

**Success looks like:** a developer can choose skip vs bang, know whether `unique_by:` and `returning:` are legal on the current database, and predict (a) which rows exist after the call, (b) whether existing rows were mutated, (c) whether a uniqueness error rolled back the whole batch, and (d) which columns are in the result—without reading adapter SQL.

**Investigate / do not ship as “clearer” if:**

- Skip on any advertised adapter updates an existing row’s non-key attributes.
- Bang uniqueness failure leaves any row from that call persisted.
- MySQL/MariaDB accept `unique_by:` and then skip a *different* collision set than PostgreSQL/SQLite with the same option.
- PostgreSQL/SQLite skip with a named `unique_by:` also silently skips collisions on other unique indexes.
- Explicit `returning:` on MySQL succeeds but returns columns (lying about support) or is ignored without error while the caller expected keys.
- Empty input or mismatched keys still writes a partial batch.
- Casting/serialization for insert diverges from `create` for the same value.

**Reconsider the problem framing if:** the real pain is upsert-vs-insert confusion, composite-primary-key modeling, or MariaDB version support—not `unique_by:` / `returning:` predictability. In that case stop widening this contract and split that work.

---

**Hypothesis, labeled:** the valuable product change is a **predictable per-adapter contract** (clear errors where unsupported, skip = any unique key unless `unique_by:` narrows it, bang = atomic fail, returning only where supported), not identical behavior on every database.

Please correct the problem frame, the bang+`unique_by:` intent, the composite-key skip error, and first-vs-last within-batch skip if those should differ from this revision’s baseline.
