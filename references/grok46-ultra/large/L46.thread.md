## Current behavior

Yes. Rails currently chooses the content and key paths **independently**:

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")
  content_path = root.join("config/credentials.yml.enc") if !content_path.exist?

  key_path = root.join("config/credentials/#{Rails.env}.key")
  key_path = root.join("config/master.key") if !key_path.exist?

  { content_path: content_path, key_path: key_path }
end
```

Source: [`Rails::Application::Configuration#credentials_defaults`](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L678-L690). These defaults initialize `config.credentials` during configuration construction ([lines 78–81](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L78-L81)).

Therefore, if:

- `config/credentials/<env>.yml.enc` exists,
- `config/credentials/<env>.key` does not, and
- `config/master.key` exists,

Rails selects:

```text
content_path = config/credentials/<env>.yml.enc
key_path     = config/master.key
```

That is already the proposed behavior. The configuration guide explicitly documents both independent fallbacks ([content path and key path](https://github.com/rails/rails/blob/main/guides/source/configuring.md#L325-L343)).

Consequently, Rails does **not** enforce basename pairing. It simply asks `ActiveSupport::EncryptedConfiguration` to decrypt the selected content with the selected key. If that key did not encrypt the file, decryption fails with `ActiveSupport::MessageEncryptor::InvalidMessage`.

## History and intended model

The method’s substantive behavior originated in [PR #33521, “Add support for multi environment credentials”](https://github.com/rails/rails/pull/33521), merged for Rails 6.0 in September 2018. Its stated behavior was:

- Prefer `config/credentials/<environment>.yml.enc`.
- Fall back to global `config/credentials.yml.enc`.
- Generate `config/credentials/<environment>.yml.enc` and `<environment>.key` through `credentials:edit --environment`.
- Allow both paths to be overridden.

The design discussion is particularly relevant:

- DHH described env credentials as **separate stores**, with no merge into global credentials, and initially proposed env content with either an env key or an environment key variable.
- Earlier in the discussion, the PR author explicitly considered using `config/master.key`/`RAILS_MASTER_KEY` for env content.
- The final implementation used one `RAILS_MASTER_KEY` environment-variable name for all stores while giving file keys environment-specific paths.
- The unchanged independent fallback logic has remained the effective method behavior since that Rails 6 addition; later work primarily taught credentials commands to respect configured path overrides.

The original credentials work, [PR #30067](https://github.com/rails/rails/pull/30067), framed credentials as encrypted API keys, passwords, and integration secrets, initially oriented toward production. Its discussion identified the security concern with placing all environments under one master key: anyone holding that key can decrypt production credentials.

The later multi-environment design addresses that concern by making separate env files and separate env key files the **normal generated layout**, so access can be segmented by environment. But Rails does not cryptographically or structurally require one key file per content filename; using one master key for several encrypted files remains supported.

## PR-review conclusion

A PR whose stated change is only “use `config/master.key` when env content exists but the env key does not” is redundant with current Rails. Changing the code to make that dependency more explicit could be a refactor or add missing matrix coverage, but it would not introduce new behavior.

Conversely, changing Rails to require env-content/env-key pairing would be a behavioral and compatibility change: it would reject a currently documented and historically supported setup where an environment-specific encrypted file is encrypted using the global master key.
