## Action Mailer queue targeting — product shaping brief

This is a **behavior-change** brief (with a reliability/testing outcome), not an implementation design. Source/test evidence is separated from the proposal. Claims about current behavior are grounded in this revision; proposed behavior is labeled as such.

The same brief was sent to [the parent thread](https://ampcode.com/threads/T-01a06130-c887-765b-8c03-b8a9325c590a).

### Part 1 — This revision’s observable contract (evidence)

What teams can already observe when they enqueue mail later and when they drain or assert those jobs.

#### Defaults and configuration

- Every mailer carries two class-level settings: the delivery job (default `ActionMailer::MailDeliveryJob`) and the later-delivery queue name (default `:mailers`). [actionmailer/lib/action_mailer/queued_delivery.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/queued_delivery.rb#L7-L9)
- Docs present `deliver_later_queue_name` as the queue used **with the default delivery job**. A custom delivery job is documented as controlling the queue instead. [actionmailer/lib/action_mailer/base.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/base.rb#L472-L476), [actionmailer/lib/action_mailer/message_delivery.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L68-L75)
- App-wide, `config.action_mailer.deliver_later_queue_name` is assigned onto the mailer. Rails 6.1 defaults set it to `nil`. Without `load_defaults`, the observed value is `:mailers`. [railties/lib/rails/application/configuration.rb](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L211-L217), [railties/test/application/configuration_test.rb](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L1450-L1484)
- Product docs: `nil` means “use Active Job’s default queue”; a custom job’s queue is used instead of this setting; the job adapter must actually process that queue or deliveries can be silently ignored. [guides/source/configuring.md](file:///home/user/workspace/repo/guides/source/configuring.md#L3086-L3108)

#### How `deliver_later` chooses a queue

- `deliver_later` / `deliver_later!` pass wait, wait_until, **queue**, and priority through to the mailer’s delivery job. [actionmailer/lib/action_mailer/message_delivery.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L77-L153)
- With the default job, the queue is read from **that mailer’s** `deliver_later_queue_name` at enqueue time. [actionmailer/lib/action_mailer/mail_delivery_job.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L14-L17)
- A mailer-level name is inherited, but a subclass can change it without changing the parent. Observed: `DelayedMailer` uses `:delayed_mailers` while `ActionMailer::Base` stays `:mailers`; assigning `:throttled_mailers` on the subclass still leaves Base at `:mailers`. [actionmailer/test/mailers/delayed_mailer.rb](file:///home/user/workspace/repo/actionmailer/test/mailers/delayed_mailer.rb#L5-L6), [actionmailer/test/message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L94-L130)
- An explicit `queue:` on the call **overrides** the mailer’s name for that delivery. Observed: `deliver_later(queue: :another_queue)` lands on `"another_queue"` even when the mailer is `:delayed_mailers`. The same override applies to `deliver_all_later`. [actionmailer/test/message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L113-L116), [actionmailer/test/message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L197-L204)
- Symbol and string names both enqueue. Tests assert the **string** form (`"delayed_mailers"`, `"throttled_mailers"`, `"another_queue"`).
- `nil` as the mailer queue name is a supported setting (6.1+ default). Enqueue still succeeds; Active Job treats a nil/blank part as its default queue name (`"default"` unless the app changed it). [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L339-L347), [activejob/lib/active_job/queue_name.rb](file:///home/user/workspace/repo/activejob/lib/active_job/queue_name.rb#L47-L50), [activejob/test/cases/queue_naming_test.rb](file:///home/user/workspace/repo/activejob/test/cases/queue_naming_test.rb#L41-L47)

[activejob/lib/active_job/queue_name.rb](file:///home/user/workspace/repo/activejob/lib/active_job/queue_name.rb#L47-L65), [activejob/test/cases/queue_naming_test.rb](file:///home/user/workspace/repo/activejob/test/cases/queue_naming_test.rb#L75-L84)

#### Custom delivery jobs

- Assigning `delivery_job` changes which job is enqueued. [actionmailer/test/message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L100-L108)
- A job that declares its own queue is observed as using **that** queue, not the mailer’s `deliver_later_queue_name`. Fixture: `CustomQueueDeliveryJob` / `CustomQueueDeliveryMailer`. [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L33-L50), [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L428-L434)
- Docs say the custom job “controls the queue name.” Observable nuance: `deliver_later` still forwards `queue:` into the job’s `set(...)`, so a **per-call** queue can still override a custom job. There is **no** Action Mailer test that asserts that combination.

#### How tests target and drain those queues

- `deliver_enqueued_emails` performs enqueued **mail delivery jobs only**. Optional `queue:` limits to one queue; optional `at:` limits to jobs due by that time. [actionmailer/lib/action_mailer/test_helper.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/test_helper.rb#L190-L223)
- “Is this a mail job?” is “is this class assigned as some loaded mailer’s `delivery_job`?” Custom jobs are included. [actionmailer/lib/action_mailer/test_helper.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/test_helper.rb#L249-L252), [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L604-L612)
- Queue filter, multiple mailers: draining `CustomQueueMailer`’s queue delivers that mailer’s later delivery and **leaves** `TestHelperMailer`’s delivery enqueued. [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L616-L627)
- Scheduled filter: `at: 1.hour.from_now` delivers the immediate mail and not `wait: 2.hours`. [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L630-L640)
- Asserting a specific later email, if no queue is given, takes the queue from a **fresh instance of that mailer’s delivery job** (so custom job queues and `nil` mailer names are discovered). Any explicit or discovered name is compared as a string. Symbol vs string is treated as the same name (`queue: :mailers` matches a string mailer name). [actionmailer/lib/action_mailer/test_helper.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/test_helper.rb#L148-L164), [actionmailer/test/test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L339-L430)
- Drain/assert filters compare `queue.to_s` to the job’s stored queue name. [activejob/lib/active_job/test_helper.rb](file:///home/user/workspace/repo/activejob/lib/active_job/test_helper.rb#L694-L696), [activejob/lib/active_job/queue_adapters/test_adapter.rb](file:///home/user/workspace/repo/activejob/lib/active_job/queue_adapters/test_adapter.rb#L68-L72)
- **Gap:** there is a test that asserting still works when a queue name prefix is configured, but **no** test that `deliver_enqueued_emails(queue: ...)` matches after prefixing or other adapter normalization. A filter of `:mailers` would not match an enqueued `"prefix_mailers"`.

#### Contract in one list

| Stimulus | Observable queue |
|---|---|
| No per-call `queue:`, default job | That mailer’s `deliver_later_queue_name`, inherited unless overridden |
| Mailer name is `nil` | Active Job default queue (`"default"` unless changed) |
| Mailer name is symbol or string | Same name, stored/compared as string (`:mailers` ↔ `"mailers"`) |
| Prefix configured | Prefixed string is what gets enqueued |
| `deliver_later(queue: ...)` | That call’s name wins over the mailer’s name |
| Custom `delivery_job` with its own queue | That job’s queue, unless the call also passes `queue:` |
| Parameterized mail | Same as the mailer’s job/queue; params are payload |
| `deliver_enqueued_emails` without `queue:` | All matching mail jobs (any queue), subject to `at:` |
| `deliver_enqueued_emails(queue:)` | Only mail jobs whose **stored** name equals `queue.to_s` |

### Part 2 — Product shaping brief (proposal)

#### Problem frame

**Actor:** An app team that sends mail later and tests that behavior.

**Situation:** They split mail across queues (priority, tenancy, internal vs external), sometimes override the queue on one call, sometimes use a custom delivery job, and they need tests to drain or assert **the same** queues production will use.

**Pain today:** Queue identity is assembled from several knobs (app default, per-mailer name, per-call override, custom job, symbol vs string vs `nil`, inheritance, schedule, Active Job prefix, adapter stringification). Enqueue and test helpers do not always share one obvious name. A filter or assertion can miss work that was enqueued, or drain the wrong mailer’s work. In production, a name the adapter does not process can be silently ignored.

**Desired progress:** Teams can predict which queue a later delivery uses, aim a test drain/assertion at that same queue, and tell apart “this mailer” vs “that mailer” vs “not yet due.”

#### Desired outcome

When this work succeeds, a team can:

1. **Direct** later delivery to a queue using the mailer default, a subclass override, a per-call override, or a custom delivery job, and observe a single resulting queue identity.
2. **Drain** later deliveries in tests for all mail jobs, or only one queue, or only jobs due by a time, including parameterized mail and custom jobs.
3. **Trust agreement:** the name they configured or passed is the name tests filter on, after the same symbol/string/`nil`/prefix/adapter normalization used at enqueue.
4. **Keep isolation:** draining one mailer’s queue does not deliver another mailer’s later work.

This is **not** a new mail product. It is making the existing later-delivery and test-drain path **predictable and mutually consistent**.

#### Appetite

**Hypothesis (not supplied by a product owner):** small batch. Preserve the existing knobs; make their observable identity consistent between enqueue and test. Do not add a new routing model, dashboard, or adapter.

#### Scope

In:

- Predictable targeting for `deliver_later` / `deliver_later!` (and the same options on bulk later delivery).
- Predictable test drain via `deliver_enqueued_emails` (`queue:`, `at:`).
- Agreement for multiple mailers, parameterized mail, scheduled mail, custom delivery jobs, symbol/string/`nil` names, inheritance, and adapter/prefix normalization of names.
- Related test assertions that already claim “this email was enqueued on this queue,” to the extent they must not contradict the drain.

Out, except as needed for the above: changing when mail is rendered, `deliver_now`, adapter internals beyond name identity, new queue backends, worker topology.

#### Non-goals

- Redesigning Active Job queues or how adapters store jobs.
- Changing email content, callbacks, or error handling.
- Requiring teams to drop custom delivery jobs or per-mailer names.
- Inventing a second, mail-only queue namespace.
- Exhaustive catalogs of every adapter’s name rules beyond “the name tests use is the name that was enqueued after normalization.”

#### Risks

- **Silent miss:** tests drain/assert `:mailers` while production enqueued `"prefix_mailers"` (or the reverse). Mail looks “unsent” in tests or is never processed in production.
- **Over-drain:** a loose filter delivers another mailer’s later work.
- **Compatibility:** apps that depend on today’s symbol/string/`nil`/prefix behavior break if identity rules change without a clear default-version story.
- **Custom jobs:** jobs that do not follow the default job’s “ask the mailer for its queue” pattern remain easy to mis-target if docs and tests disagree about whether `queue:` still wins.
- **Wrong framing:** if the real pain is “workers are not subscribed to that queue,” tightening test names will not fix production.

**Steering:** If teams still cannot point to one name that both enqueue and drain use, or if fixing tests increases false passes against production adapters, reconsider the framing. If the pain is only undocumented precedence, documentation may be enough.

#### Acceptance examples (proposed observable behavior)

Required cases. Product-facing; not test code.

**1. Multiple mailers (core)**  
Given Customer mail goes to an external queue and Employee mail to an internal queue, when the team drains only the external queue, they observe the customer mail sent and the employee mail still waiting.

**2. Per-call override**  
Given a mailer whose default later queue is `delayed_mailers`, when one call passes `queue: another_queue`, that delivery is observed on `another_queue`. A drain of `delayed_mailers` does not send it; a drain of `another_queue` does.

**3. Inheritance**  
Given a subclass sets its own later-queue name, parent mailers keep the previous name. Draining the subclass queue does not send parent later deliveries.

**4. Symbol, string, and nil**  
- `:mailers` and `"mailers"` are the same queue for enqueue, drain, and assert.  
- `nil` means Active Job’s default queue, not a queue literally named `"nil"` or `""`. A drain/assert aimed at that default queue hits those jobs. A drain aimed at `"mailers"` does not.

**5. Custom delivery job**  
Given a mailer whose job declares `delivery_job_queue`, later delivery is observed there (not on the mailer’s `deliver_later_queue_name` if that differs). Draining mail jobs still sends it. **Boundary:** if the call also passes `queue:`, that call’s name is what enqueue and drain share. **Open if disputed:** whether that override is required; today `set(options)` does apply, but Action Mailer does not assert it.

**6. Parameterized mailers**  
Given `InvoiceMailer.with(account: account).receipt.deliver_later` on the same mailer queue as a non-parameterized call, a drain of that queue sends both. Params do not create a second queue. A custom job on that mailer still applies.

**7. Scheduled delivery**  
Given one immediate later delivery and one `wait: 2.hours` on the same queue, draining with “due by one hour from now” sends only the immediate mail. A later drain of the same queue sends the rest. Schedule does not change queue identity.

**8. Queue filters**  
Given mixed mail jobs and non-mail jobs, `deliver_enqueued_emails` without a queue sends all **mail** jobs (any mailer queue) and not unrelated jobs. With `queue:`, only that mailer queue is sent.

**9. Adapters that normalize queue names**  
Given an adapter that stringifies, prefixes, or otherwise normalizes names, the name the team uses to drain or assert is the **normalized** name that was actually enqueued. Example: prefix `prefix` and mailer name `:mailers` enqueue as `prefix_mailers`; draining `queue: :mailers` without that prefix does **not** send them; draining the prefixed name does. Symbol vs string after normalization still matches.

**Counterexample (must not happen):** Customer mail enqueued on the external queue is left unsent because the drain used a different spelling of the same queue (`:external` vs `"external"`, or prefixed vs unprefixed) while production workers are subscribed to the enqueued spelling — or the reverse, tests pass on an unprefixed name that production never processes.

#### Open questions

1. Must per-call `queue:` override a custom job’s own queue? Current enqueue path does; docs emphasize the job “controls the queue”; no Action Mailer example covers both.
2. Is prefix/adapter normalization in scope for Action Mailer helpers, or only “helpers must use the same name Active Job already stored”?
3. Should 6.1 `nil` → default queue remain the compatibility story, or do teams now want an explicit visible name?
