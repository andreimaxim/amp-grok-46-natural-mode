`#strict_loading!` is an instance flag plus a mode. It does not load anything. It only changes what happens the next time an association on that record (or a record it infects) would run a lazy query.

```ruby
def strict_loading!(value = true, mode: :all)
  unless [:all, :n_plus_one_only].include?(mode)
    raise ArgumentError, "The :mode option must be one of [:all, :n_plus_one_only] but #{mode.inspect} was provided."
  end
  @strict_loading_mode = mode
  @strict_loading = value
end
```

Defined in [`activerecord/lib/active_record/core.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb). Tests live in [`activerecord/test/cases/strict_loading_test.rb`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb).

On `init_internals`, a new record copies class defaults: `@strict_loading = klass.strict_loading_by_default` (false) and `@strict_loading_mode = klass.strict_loading_mode` (`:all`). `strict_loading?` is only the flag. `strict_loading_n_plus_one_only?` / `strict_loading_all?` look only at mode, even if the flag is off. That is how mode is copied onto children.

### Two modes

Both set `@strict_loading = true`. They differ at `find_target`.

Gate in `Association#violates_strict_loading?`:

```ruby
def violates_strict_loading?
  return unless find_target?
  return if @skip_strict_loading
  return unless owner.validation_context.nil?
  return reflection.strict_loading? if reflection.options.key?(:strict_loading)
  owner.strict_loading? && !owner.strict_loading_n_plus_one_only?
end
```

Then `find_target` reports:

```ruby
if violates_strict_loading?
  Base.strict_loading_violation!(owner: owner.class, reflection: reflection)
end
```

**`:all` (default)** — any unloaded association whose `find_target?` is true is a violation. Singular and collection both raise.

**`:n_plus_one_only`** — the owner may lazy-load anything (`violates_strict_loading?` is false). Protection is applied by infecting children in `set_strict_loading`:

```ruby
def set_strict_loading(record)
  if owner.strict_loading_n_plus_one_only? && reflection.macro == :has_many
    record.strict_loading!                    # enable, mode defaults to :all
  else
    record.strict_loading!(false, mode: owner.strict_loading_mode)
  end
end
```

Called from `Association#find_target` after each lazy-loaded row, and from `AssociationRelation#exec_queries` after scoped collection queries (`first`, `limit`, …).

| Association just loaded | Child after `set_strict_loading` |
|---|---|
| `has_many` (HABTM is `has_many :through`, so `macro == :has_many`) | flag **on**, mode **`:all`** |
| `belongs_to` / `has_one` | flag **off**, mode copied (`:n_plus_one_only`) |

So `:n_plus_one_only` allows `parent.children` and `parent.parent`, but a record that arrived through a `has_many` cannot lazy-load **its** associations. That is the N+1 in `parent.children.each { |c| c.something }`.

A `belongs_to` child keeps the mode with the flag off. When **it** later loads a `has_many`, those grandchildren still get `strict_loading!`. That is how `developer.ship.parts` marks parts even though `ship` itself is not strict-loading.

### Where the error (or log) is raised

`ActiveRecord::Base.strict_loading_violation!` in [`core.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb):

```ruby
def self.strict_loading_violation!(owner:, reflection:)
  case ActiveRecord.action_on_strict_loading_violation
  when :raise
    message = reflection.strict_loading_violation_message(owner)
    raise ActiveRecord::StrictLoadingViolationError.new(message)
  when :log
    ActiveSupport::Notifications.instrument("strict_loading_violation.active_record",
      owner: owner, reflection: reflection)
  end
end
```

Default is `:raise` ([`activerecord/lib/active_record.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record.rb)).

Message from `Reflection#strict_loading_violation_message`:

```
`Developer` is marked for strict_loading. The AuditLog association named `:audit_logs` cannot be lazily loaded.
```

Polymorphic: `The polymorphic association named `:looter` cannot be lazily loaded.`

`:log` instruments the notification. `LogSubscriber#strict_loading_violation` writes that message at debug; `StructuredEventSubscriber` emits `active_record.strict_loading_violation` with `owner`, `class`, `name`. Tests: `test_strict_loading_violation_raises_by_default`, `test_strict_loading_violation_can_log_instead_of_raise`, `test_strict_loading_violation_on_polymorphic_relation`.

Call sites:

1. `Association#find_target` — normal lazy load (`to_a`, singular reader, `load_target`)
2. `CollectionProxy#pluck` — explicit, because `pluck` never hits `find_target`

`find_target?` is the other half of the gate. No query ⇒ no violation:

- already `loaded?` (preload / eager load / previous load)
- new owner without a FK (`belongs_to` uses `foreign_key_present?`)
- `@skip_strict_loading` (concat on a new record, some writer paths)
- `owner.validation_context` is not `nil` (validation)

Collections add a second force-path. `CollectionAssociation#find_from_target?`:

```ruby
loaded? ||
  (owner.strict_loading? && owner.strict_loading_all?) ||
  reflection.strict_loading? ||
  owner.new_record? ||
  target.any? { |record| record.new_record? || record.changed? }
```

In **`:all`**, `first` / `last` / `inspect` on an unloaded `has_many` go through `load_target` → `find_target` → violation. That is why `dev.audit_logs.first` raises (`test_raises_on_unloaded_relation_methods_if_strict_loading`). In **`:n_plus_one_only`**, that clause is false, so `developer.projects.first` runs a `LIMIT` query via `AssociationRelation` and does **not** mark the whole collection loaded (`test_strict_loading_n_plus_one_only_mode_does_not_eager_load_child_associations`).

### How state reaches association objects and child records

```text
record.strict_loading!(value, mode:)
  sets @strict_loading, @strict_loading_mode
        │
        ▼
record.association(:name)          # Associations#association
  Association / CollectionProxy
        │
        ▼
reader / to_a / first / pluck
        │
        ├─ already loaded?  → return target, no check
        │
        ├─ violates_strict_loading?  → strict_loading_violation!
        │
        └─ find_target
             for each row: set_inverse_instance; set_strict_loading(record)
```

Relation-level `Model.strict_loading` is a different entry: it sets `strict_loading_value` on the relation. After `exec_queries`:

```ruby
records.each { |record| record.strict_loading!(strict_loading_value) } unless strict_loading_value.nil?
```

Preload/eager-load cascade that same value onto associated records:

- `Relation#preload_associations` passes `StrictLoadingScope` when `strict_loading_value` is true
- `Preloader::Association#cascade_strict_loading` / `ThroughAssociation#through_scope` merge `scope.strict_loading`
- `JoinDependency#construct_model` calls `m.strict_loading! if strict_loading_value` and again if the join node’s reflection scope is `strict_loading`

Association option `strict_loading: true/false` on the reflection **wins** over the owner flag (`violates_strict_loading?` returns `reflection.strict_loading?` when the key is present). That is `strict_loading_mentor` vs `strict_loading_off_mentor` on `Developer`.

#### 4. `has_many :through` and middle records

`Developer has_many :firms, through: :contracts`.


Same with `projects_extended_by_name`.

Through a `belongs_to`, then a `has_many`, then **that** collection’s association (`test_strict_loading_n_plus_one_only_mode_with_belongs_to`):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)

developer.ship.parts.to_a          # OK
assert_not developer.ship.strict_loading?          # belongs_to child: flag off, mode kept
assert developer.ship.parts.all?(&:strict_loading?) # has_many of that child: flag on, :all

developer.ship.parts.first.trinkets.to_a
## StrictLoadingViolationError
```

Call tree for that last line:

```text
developer.strict_loading!(mode: :n_plus_one_only)
developer.ship
  violates_strict_loading? → false (n_plus_one_only)
  set_strict_loading(ship) → ship.strict_loading!(false, mode: :n_plus_one_only)
developer.ship.parts.to_a
  ship.strict_loading? is false → no violation
  set_strict_loading(part) → part.strict_loading!   # because ship.strict_loading_n_plus_one_only? && has_many
part.trinkets.to_a
  part is :all → StrictLoadingViolationError
```

The documented example in `strict_loading!` is the same shape: `user.comments.to_a` is allowed; `user.comments.first.ratings.to_a` is not.

#### 7. Disabling on an instance

```ruby
developer.strict_loading!          # enable
developer.audit_logs.to_a          # raises
developer.strict_loading!(false)   # @strict_loading = false; returns false
developer.audit_logs.to_a          # OK
```

`test_strict_loading!`. Relation form: `Developer.strict_loading(false)` against `strict_loading_by_default` (`test_strict_loading_by_default`). Association form: `strict_loading: false` on the reflection (`test_strict_loading_can_be_turned_off_on_an_association_in_a_model_with_strict_loading_on`).

`strict_loading!(false)` still writes `@strict_loading_mode` (default `:all` unless you pass `mode:`). Turning the flag off is enough for `violates_strict_loading?` on that record.

#### 8. Invalid mode

Not covered by `strict_loading_test.rb`; enforced in `strict_loading!`:

```ruby
developer.strict_loading!(mode: :n_plus_one)  # or :none, "all", nil, …
## ArgumentError:
##   The :mode option must be one of [:all, :n_plus_one_only] but :n_plus_one was provided.
```

Only `:all` and `:n_plus_one_only` are legal.

### Contrast

```text
:all
  owner lazy-loads anything unloaded → violation
  children of a strict_loading relation/preload also get strict_loading!

:n_plus_one_only
  owner lazy-loads anything → allowed
  has_many children → strict_loading! (:all) → THEIR lazy loads violate
  belongs_to/has_one children → flag off, mode kept → their has_many children then get :all
```

That is the whole mechanism: a boolean on the record, a mode that changes the violation predicate, infection of loaded targets via `set_strict_loading`, and a single reporter that either raises `ActiveRecord::StrictLoadingViolationError` or instruments `strict_loading_violation.active_record`.
