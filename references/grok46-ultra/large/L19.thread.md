### Proposed optimization / claim
Remove `ExtendedDeterministicQueries`’ expansion of deterministic equality values for:

- configured `previous:` encryption schemes, and
- plaintext values when `support_unencrypted_data` is enabled.

The author’s claim is that equality queries need only the ciphertext generated by the current scheme.

No literal patch diff was supplied. The described change is to stop `EncryptedQuery.process_arguments` from expanding a value into:

```ruby
[value, AdditionalValue(previous_type), ...]
```

and instead bind only the current scheme’s serialized ciphertext. That removes the effective SQL `IN (current_ciphertext, old_ciphertext..., plaintext...)` behavior.

- `activerecord/test/models/book_encrypted.rb`

### Review finding
**Reject; do not merge.** The claim is false. Expansion is what makes queries locate rows stored with an old deterministic key/scheme or in plaintext. Deserialization can still read those rows—current decrypt, then `previous:`, then plaintext—but `where`/`find_by` cannot discover them without query expansion. Thus the proposed change creates the misleading state where `find(id).name` works but `find_by(name: value)` returns `nil`.

The review also notes that expansion already no-ops when there are no previous types: no `previous:` configuration and unencrypted-data support disabled. So the change does not optimize that case; it removes the mixed-storage compatibility contract.

Observed failures after disabling expansion were reported at `extended_deterministic_queries_test.rb` lines **12, 29, 71, and 83**; the source was restored afterward.

### Assumptions / edge cases the child must check
- `previous:` rotation must use `deterministic: { fixed: false }`; default `fixed: true` writes with the oldest scheme and can hide the regression.
- Plaintext fallback is controlled by `scheme.support_unencrypted_data?`, including per-attribute opt-in/out, not merely the global configuration.
- `downcase` and encrypted `ignore_case` queries may still work with only current serialization; that does **not** validate removal of old-scheme/plaintext expansion.

## Assistant

**Reject. Do not merge.** The claim is false at this revision: a deterministic equality predicate is not “current ciphertext only.” `previous:` and `support_unencrypted_data` expansion is the query-side mixed-storage contract. Removing it leaves reads working and lookups empty.

### Query compatibility ≠ read/decryption compatibility

Two independent paths:

1. **Read/decrypt** (`EncryptedAttributeType#deserialize`): current decrypt → `previous_types` → plaintext fallback when `scheme.support_unencrypted_data?`. `find(id).email` still works for old ciphertext and plaintext.
2. **Query** (`EncryptedQuery.process_arguments`): if `previous_types` is non-empty, expand the bound value into `IN (plaintext_or_current, AdditionalValue(previous_type)...)`. `where`/`find_by`/`exists?` match rows stored under an old scheme or as plaintext.

The proposed change only touches path 2. Path 1 is unchanged. That is the misleading state: `EncryptedBook.find(id).name #=> "Dune"` while `EncryptedBook.find_by(name: "Dune") #=> nil`.

Expansion already no-ops when `type.previous_types.empty?` (no `previous:` and unencrypted support off). The change does not optimize that case; it deletes the compatibility branch.

Caveats that can hide the bug:

- Default `deterministic: true` is `fixed: true` and **writes/serializes with the oldest scheme**. A `previous:` test that omits `fixed: false` can pass because query serialize already uses the old ciphertext. Use `deterministic: { fixed: false }`.
- `support_unencrypted_data?` is `scheme.support_unencrypted_data?` (per-attribute override, else global), not the global flag alone.
- `CoreQueries#find_by` expands **before** `ActiveRecord::Base` statement-cache. An expanded Array is `StatementCache.unsupported_value?`, so SQL is `IN (...)`. Bind-only-current caches `WHERE name = ?` to the current ciphertext; later plaintext/`previous:` lookups reuse that statement.
- `ignore_case` predicates query the downcased encrypted `name` column. `original_name` / `preserve_original_encrypted` is a **read** path.
- `downcase:` / `ignore_case:` current-scheme lookups can succeed without expansion (serialize already downcases). That does **not** validate dropping old-scheme/plaintext expansion.

Existing tests at this revision (`extended_deterministic_queries_test.rb` + `encryption_schemes_test.rb`): 27 runs, 0 failures **with** expansion. Failures below were observed with a temporary prepend that made `additional_values_for` return `[]`, then removed.
