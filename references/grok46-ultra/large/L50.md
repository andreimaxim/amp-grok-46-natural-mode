This is **maintenance** work with a discovery gate: generate and destroy are reported to handle existing-file collisions inconsistently, but it is not established that those differences are unintentional. The brief does not propose implementation, architecture, or tests.

### Problem frame

**Actors:** application developers; engine/plugin maintainers running generators from an engine’s `bin/rails`; people running generate/destroy non-interactively (CI, pipes, scripts).

**Situation:** they run `bin/rails generate` or `bin/rails destroy` for a named generator. The generator would create, overwrite, or remove files under the current app or engine root. At least one target file already exists, with either the same content the generator would write or different (hand-edited) content.

**Pain today (reported, not confirmed as a defect):** generate and destroy do not present one collision story. Generate may say `identical`, `skip`, `force`, or `conflict` and ask `Overwrite …?`. Destroy removes matching paths without that same check. `--force` / `--skip` are advertised on both commands’ help, but destroy’s job is removal, not overwrite. After the operator skips a collision, destroy can still remove the file they just chose to keep. In a mountable engine, the colliding path is namespaced and rooted at the engine, so it is easy to think the command touched a different tree than it did.

**Desired progress:** from the CLI alone, an operator can predict—for the same generator, same name, same existing file—what generate and destroy will print and whether that file remains, in both an application and an engine, including when they pass `--force` / `--skip`, answer a prompt, or run with no TTY.

### Users and pain

- **Regenerating in an app:** they already have the file. They need to know whether generate will leave it, overwrite it, or ask, and whether a later destroy will delete a file they refused to overwrite.
- **Working in an engine:** they expect files to land under the engine destination root (namespaced in a mountable engine), not the dummy app or host app, and they expect destroy to aim at that same root.
- **Automating:** they cannot answer `Overwrite …?`. They need a non-interactive outcome that does not depend on hidden stdin EOF behavior.
- **Mistyping a generator:** they need the same “unknown generator” failure from generate and destroy, pointing at help for the command they ran.

### Desired observable CLI behavior

A single collision policy, visible in status text, prompts, exit, and the file on disk:

1. **Same generator identity.** `generate X` and `destroy X` resolve X the same way (short name, `rails:` prefix, nested `foo:bar` name, configured fallbacks). If X cannot be resolved, both commands fail without writing or deleting, with a “Could not find generator” message. Destroy must not send the operator only to generate help.
2. **Same destination.** For an application, both commands use the application root. For an engine’s `bin/rails`, both use that engine’s root, including when the engine is nested inside a host app. A mountable engine’s colliding path is the namespaced engine path, not the un-namespaced host path.
3. **Generate vs an existing file whose content already matches** what the generator would write: generate reports the file as identical and does not change it.
4. **Generate vs an existing file whose content differs:**
   - `--force`: overwrite; status indicates force.
   - `--skip`: leave the file; status indicates skip.
   - Interactive, no flag: report conflict, then ask whether to overwrite, with yes / no / all / quit (and help). Yes overwrites that file; no leaves it; all overwrites this and later conflicts in the same run; quit aborts and does not continue applying later files.
5. **Destroy vs an existing file** must follow the same skip/force/quit answers the operator already gave for that file in this workflow. In particular, a file left in place because generate skipped it (flag or “no”) is not then deleted by a following destroy of the same generator and name, unless the operator explicitly forces destruction of that path.
6. **Flags in help match behavior.** If destroy help lists `--force` as “overwrite files that already exist” and `--skip` as “skip files that already exist,” those flags must mean something a destroy user can observe. If destroy is not in the overwrite business, help must not advertise generate’s overwrite flags as if they applied unchanged.
7. **Non-interactive stdin** has a documented, stable outcome: it does not silently treat EOF as “yes, overwrite” unless that is confirmed as the intended policy.

Help already states the generate-side flags (`-f` overwrite, `-s` skip, `-p` pretend, `-q` quiet). That is the public contract generate is judged against.

### Non-goals

- New generators, new file kinds, or changing *what* a successful first-time generate writes.
- Redesigning diff/merge (`d` / `m`) beyond the yes/no/all/quit collision answers.
- Class-name / constant reservation checks, except where they abort generate before any file collision can occur.
- Dummy-app generation while creating a plugin, except as it affects later generate/destroy inside that engine.
- Implementation, internals, or specific tests.

### Acceptance examples

Required cases, not illustrations. “The file” means the path that generator would create for the given name under the current destination root.

**Identical content, generate then destroy**  
Given an application file that already matches what `bin/rails generate model Account` would write.  
When the operator runs that generate again with no flags.  
They see an `identical` status for that file, and the file is unchanged.  
When they then run `bin/rails destroy model Account`.  
If the file is still the generated artifact (not a skipped custom file), destroy removes it and reports `remove`.  
Counterexample: destroy must not report `conflict` / `Overwrite` for a file that generate just called identical.

**Differing content, generate with no flags (interactive)**  
Given the same path with hand-edited content.  
When they generate again with a TTY.  
They see `conflict` and `Overwrite <path>? (enter "h" for help) [Ynaqdhm]`.
- `Y` or `yes`: file becomes generated content.
- `n` or `no`: file stays hand-edited.
- `a` or `all`: this file and later conflicts in the run are overwritten without further prompts.
- `q` or `quit`: they see `Aborting...`, the process exits, this file is not overwritten, and later files in the run are not applied.

**`--force` on differing content**  
Given hand-edited content.  
When they generate with `--force`.  
There is no overwrite prompt; status indicates `force`; the file becomes generated content.

**`--skip` on differing content**  
Given hand-edited content.  
When they generate with `--skip`.  
Status indicates `skip`; the file stays hand-edited.

**`--skip` on identical content**  
Given content that already matches.  
When they generate with `--skip`.  
They still see `identical` (not `skip`), and the file is unchanged.

**Non-interactive stdin**  
Given differing content, generate, no `--force`/`--skip`, stdin not a TTY (EOF / empty pipe).  
When the command runs.  
The outcome is one stable policy: either it refuses to overwrite and leaves the file, or it overwrites, and that policy is the same for application and engine generate.  
Open: today’s path treats EOF as yes/overwrite. Whether that is intended is not decided here.

**Nested engine destination root**  
Given a mountable engine nested in a host app, current directory the engine, using the engine’s `bin/rails`.  
When they generate a controller that collides with a file already in the engine’s namespaced path.  
Collision status and any overwrite prompt name the engine path (e.g. under `app/controllers/<engine>/…`), not the host app’s un-namespaced path and not the dummy app unless that is the engine root.  
When they destroy the same generator and name from the same engine `bin/rails`.  
Removal is attempted on that same engine path, not a different tree.

**Namespaced generator resolution**  
Given generators reachable as `model`, `rails:model`, or a nested name such as `foobar:foobar`, and fallbacks (e.g. a missing group that is configured to fall back to another).  
When generate and destroy are given the same name.  
They invoke the same generator. A fallback that makes generate succeed must make destroy succeed with that same generator.

**Missing generator**  
When they run `bin/rails generate unknown` or `bin/rails destroy unknown`.  
Both print that the generator could not be found, exit unsuccessfully, and change no files.  
If a close name exists, a “Did you mean?” suggestion may appear.  
Help pointed to is help for the command they ran.

**Destroy after a skipped collision**  
Given a hand-edited file.  
When they generate with `--skip`, or answer `n` to overwrite.  
The file remains hand-edited.  
When they immediately `bin/rails destroy` the same generator and name, without `--force`.  
The skipped file is still there. Destroy does not treat “this path is the generated path” as license to delete a file generate was told not to touch.  
If they pass an explicit force-to-destroy (once that flag’s destroy meaning is settled), they can remove it.

**Engine vs application parity**  
Each example above, repeated with the engine’s `bin/rails` and the engine destination root, yields the same status words, prompts, skip/force outcomes, and missing-generator failure; only the colliding path is the engine’s.

### Current behavior the brief is grounded in (observed, not requirements)

Inspected: generate/destroy commands, generator invoke and lookup/fallbacks, Thor create/revoke and overwrite prompt, migration collision messages, Railties generator lookup tests, engine namespacing integration tests, mountable-engine generate/destroy scaffold tests.

Observed:

- Generate runs generators in create mode; destroy runs the same generator in remove mode. Both pass the command root (application root, or the engine root when the command is an engine’s).
- On create, an existing file with the same bytes is `identical`; a different file is `force`, `skip`, or `conflict` then `Overwrite …? [Ynaqdhm]`. Yes/empty overwrite; no skips; all overwrites the rest; quit prints `Aborting...` and exits; EOF currently overwrites.
- On remove, an existing path is `remove`d if present; a missing path still reports `remove`. `--force`/`--skip` are not applied as create-collision answers. Help for both commands still lists those flags as overwrite/skip.
- Generate replaces process args for third-party generators; destroy does not. Whether any in-tree generator depends on that is unverified.
- Unknown generator: “Could not find generator ‘…’.” plus generate help, then exit. Lookup covers `name`, `rails:name`, `name:name`, nested `a:b:c`, and configured fallbacks.
- Mountable engines namespace models/controllers/helpers; non-mountable engines do not. Destroy of a scaffold inside a mountable engine removes the namespaced files. Engine generator config can inherit or override the host’s generator config; that does not itself define file-collision policy.
- Migrations: a second generate with different content errors unless `--force` or `--skip`; identical is `identical`; destroy removes without that error. This is a stricter collision path than ordinary files.

None of the above is adopted as the desired policy except where an acceptance example restates it.

### Ambiguities — evidence needed before treating differences as bugs

1. **Is destroy supposed to share generate’s collision prompt at all?** Destroy’s public description is “Remove code generated by `bin/rails generate`.” Removing is not overwriting. Evidence: user-facing destroy docs, help text, and whether operators complain about destroy deleting customized files vs failing to delete them.
2. **After `--skip` or overwrite `n`, should a later destroy leave the file?** The acceptance example above assumes yes. Evidence: real operator expectation; whether skip means “this file is not owned by the generator anymore.”
3. **EOF as overwrite:** is non-interactive generate without `--force`/`--skip` intended to overwrite? Evidence: documented CI recipes; whether scripts rely on that.
4. **Shared help copy:** is listing overwrite/skip on `destroy --help` intentional, and if so what should those flags do on destroy? Evidence: whether anyone documents `destroy --skip`.
5. **Missing-generator help always names generate.** Intentional reuse vs copy-paste. Evidence: whether destroy-only users are expected to use generate help as the generator catalog.
6. **Generate-only process-arg replace.** Intentional because only generate shells out to libraries that read process args, or an accidental split. Evidence: a generator whose destroy path visibly mis-parses args.
7. **Migration error vs ordinary file prompt.** Intentional stricter migrations, or another inconsistency. Evidence: migration docs vs ordinary generator help.
8. **Class/constant collision** aborts generate and is skipped on destroy. In or out of scope for “existing file” collisions?
9. **App vs engine:** observed namespacing and destination-root differences look intentional. File-collision *policy* is not separately specified for engines. Evidence: an engine-only collision report that differs from the app once the path is held constant.

Until those are answered, do not treat “generate prompts, destroy deletes” as a confirmed defect. It may be the intended split between create and remove.

### Steering evidence

- **Success:** for each acceptance example, a person at the CLI can say what was printed and whether the file remained, and application vs engine differ only by destination path/namespacing.
- **Investigate further (without changing the outcome):** generate and destroy disagree on skip-then-destroy, on `--force`/`--skip` meaning, or on missing-generator help, *and* docs/help claim they should agree.
- **Wrong framing:** operators are only confused about engine namespacing (which file was the target), not about generate vs destroy policy. Then this is a destination/help problem, not collision-policy maintenance.
- **Stop:** evidence shows destroy is deliberately “always remove the generated path” and generate is deliberately “ask before clobbering.” Then the remaining work is help/docs honesty (don’t advertise overwrite on destroy; warn that skip does not protect against later destroy), not unifying the two commands.

### Open questions

See ambiguities 1–9. The ones that change the outcome are 1, 2, and 3: destroy’s relationship to generate’s skip/force/prompt, skip-then-destroy, and non-interactive EOF.
