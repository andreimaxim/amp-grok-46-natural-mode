## Current behavior

[`RunnerCommand#perform`](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/runner/runner_command.rb#L24-L65) replaces global `ARGV` with only the arguments following the code/file:

```ruby
def perform(code_or_file = nil, *command_argv)
  # boot application...
  ARGV.replace(command_argv)

  # eval stdin, load a file, or eval inline code
end
```

It **does not restore `ARGV` itself**. This applies to all three execution modes: stdin, file, and inline code.

However, normal programmatic dispatch through [`Rails::Command.invoke`](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L55-L76) wraps command execution in [`with_argv`](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L140-L146):

```ruby
def with_argv(argv)
  original_argv = ARGV.dup
  ARGV.replace(argv)
  yield
ensure
  ARGV.replace(original_argv)
end
```

Therefore:

```ruby
Rails::Command.invoke("runner", args)
```

restores the caller’s `ARGV`, including when runner code raises, because restoration occurs in `with_argv`’s `ensure`.

The behavior is explicitly covered by the command tests: commands receive invocation arguments, while mutations made during invocation do not escape ([`base_test.rb` lines 116–140](https://github.com/rails/rails/blob/main/railties/test/command/base_test.rb#L116-L140)).

## Direct `perform` calls

Calling the command class directly bypasses `with_argv`:

```ruby
Rails::Command::RunnerCommand.perform("runner", args, config)
```

Such a call can leave `ARGV` replaced after it returns. But `perform` is the lower-level Thor/Rails command entry point; the public in-process dispatch path is `Rails::Command.invoke`.

Consequently, adding save/restore inside `RunnerCommand#perform` would:

- be **redundant for normal CLI and `Rails::Command.invoke` execution**;
- protect direct low-level calls to `RunnerCommand.perform`;
- change the current layering, where invocation-level global-state isolation belongs to `Rails::Command.invoke`;
- potentially be inconsistent unless every command that mutates process globals receives similar protection.

If the PR’s stated bug occurs through `Rails::Command.invoke`, runner-level restoration should not be necessary; that suggests the embedding code bypasses `invoke`, uses an older Rails version, or follows a path not covered by `with_argv`.

## History of runner’s `ARGV.replace`

1. **November 2016 — file arguments restored**

   Commit [`5aea0952`](https://github.com/rails/rails/commit/5aea0952e7cb445e614652e3cd9aba71a836eed0) added:

   ```ruby
   def perform(code_or_file = nil, *file_argv)
     # ...
     if File.exist?(code_or_file)
       ARGV.replace(file_argv)
       Kernel.load code_or_file
     end
   end
   ```

   Its purpose was to restore the historical behavior where:

   ```console
   rails runner some_file.rb a b
   ```

   exposes `["a", "b"]` to the loaded file.

2. **March 2017 — applied to inline code too**

   Issue [#28515](https://github.com/rails/rails/issues/28515) reported that Rails 5.1 gave inline runner code:

   ```ruby
   ["puts ARGV.inspect", "x"]
   ```

   instead of `["x"]`.

   Commit [`a06a643e`](https://github.com/rails/rails/commit/a06a643e0572b8c983738c068ae637d020188c97) moved `ARGV.replace(command_argv)` before the file/code branch, so both files and inline code receive only their trailing arguments. Neither historical change attempted restoration afterward.

3. **February 2020 — restoration added at invoke level**

   PR [#38495](https://github.com/rails/rails/pull/38495), commit [`8ec7a2b7`](https://github.com/rails/rails/commit/8ec7a2b7aaa31527686b05e0640d125299933782), isolated `ARGV` around `Rails::Command.invoke`. Its explicit rationale was:

   > Any `ARGV` mutations done by a command will not affect code that executes after `Rails::Command.invoke`.

4. **March 2021 — invocation arguments populate `ARGV`**

   Commit [`ddcfde22`](https://github.com/rails/rails/commit/ddcfde2226217c0d65bd83a5d8dd25d7d3244f86) changed invoke-level setup from clearing `ARGV` to populating it with the supplied arguments while retaining restoration afterward. This reconciled consistent CLI/programmatic behavior with isolation between invocations.

## Related issues and PRs

The directly relevant upstream discussions are:

- [#28515](https://github.com/rails/rails/issues/28515): runner code saw its own source string in `ARGV`; fixed by moving `ARGV.replace` before both execution branches.
- [#38463](https://github.com/rails/rails/pull/38463): commands accidentally depended on prior process `ARGV`; discussion proposed isolating it centrally.
- [#38495](https://github.com/rails/rails/pull/38495): implemented invocation-level isolation specifically for CLI and library/in-process use.
- [#40994](https://github.com/rails/rails/pull/40994): populated `ARGV` for app templates after isolation exposed compatibility needs.
- The 2021 follow-up commit [`ddcfde22`](https://github.com/rails/rails/commit/ddcfde2226217c0d65bd83a5d8dd25d7d3244f86) generalized population to every `Rails::Command.invoke`.

I did not find a distinct upstream issue specifically alleging that **runner leaks `ARGV` when embedded through `Rails::Command.invoke`**. Upstream’s central isolation work already defines that use case as protected.

It only materially fixes callers invoking `RunnerCommand.perform` directly. The PR should demonstrate that direct invocation is intended/supported, or provide a reproduction showing how the normal `Rails::Command.invoke` ensure is bypassed or insufficient.

`ensure` runs on normal return, exceptions, and `exit` (`SystemExit`), including runner’s `exit 1` on syntax errors, NameError, missing `.rb`, and missing operand. Nested `invoke` stacks this. Isolation is tested in [railties/test/command/base_test.rb](file:///home/user/workspace/repo/railties/test/command/base_test.rb) (`ARGV is isolated`), not in `runner_test.rb`.

A leak exists only if a caller bypasses `invoke` and hits `RunnerCommand.perform` directly. That is not the public embedding API. `generate` does the same unrestored `ARGV.replace` and relies on the same invoke-level restore.

### Path-by-path

| Path | During run | After `invoke` | `$0` | Proposed ensure |
|---|---|---|---|---|
| Inline code | `command_argv` | original | unchanged | redundant |
| Ruby filename | `command_argv` | original | set to expanded path, **never restored** | restores ARGV only |
| stdin `-` | `command_argv` | original | unchanged | redundant |
| SyntaxError / NameError / missing `*.rb` | already replaced, then `exit 1` | restored by `with_argv` | n/a | redundant |
| Missing operand | help + `exit 1` **before** `ARGV.replace` | unchanged | n/a | not involved |
| Nested `invoke("runner", …)` | inner `command_argv` while running | outer ARGV after inner ensure | file run still clobbers `$0` | still redundant for ARGV |
| `--skip-executor` / `-w` | executor wraps eval/load only | same | same | no interaction |
| Args beginning with `-` | passed through as `command_argv` | original | n/a | does not change parsing |

Executor wrapping starts after `ARGV.replace` and does not touch ARGV. Dash-prefixed arguments are a Thor-parsing concern; the patch would not break `test_should_set_argv_when_running_code`.

### Compatibility risk

- Harmless on CLI and on `Rails::Command.invoke` (outer ensure already wins).
- Behavior change for unsupported direct `RunnerCommand.perform`: today ARGV remains `command_argv` after return; after the patch it snaps back.
- Identity is fine: `ARGV.dup` + `ARGV.replace` mutates the same global array. Do not rebind `ARGV`.
- False sense of isolation: file execution still assigns `$0 = expanded_file_path` (`$PROGRAM_NAME` is the same object). ARGV-only restore is incomplete if the goal is embedding hygiene.
- Wrong layer: duplicating `with_argv` inside one command makes runner special versus `generate` / `console`.

### Missing tests

[railties/test/commands/runner_test.rb](file:///home/user/workspace/repo/railties/test/commands/runner_test.rb) never inspects ARGV. The application runner tests only assert ARGV **during** a forked `bin/rails` run. There is no in-process test that snapshots ARGV, `invoke`s runner, and asserts ARGV afterward — including error/`exit 1`, nested invoke, `$0` after a file run, or dash-prefixed args post-invoke.

A patch that claims an embedding leak should fail those tests before the fix. Through `invoke`, they already pass without touching `RunnerCommand`.

### More precise change

Do **not** add save/restore inside `perform` unless a reproduction shows `Rails::Command.invoke("runner", …)` leaving ARGV dirty.

If the goal is in-process embedding hygiene: keep isolation in `with_argv`, document that embedders must call `invoke` not `perform`, and if process globals matter restore `$0`/`$PROGRAM_NAME` around the file branch with in-process tests. ARGV-only `ensure` is the wrong shape.
