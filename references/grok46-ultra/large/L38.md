## Behavior-preservation verification for Action Mailbox incineration

Oracle for a refactor of `Incineratable`, `IncinerationJob`, and `Incineration`: jobs actually enqueued (class, wait, queue) and database-visible / destructive outcomes. The internal split among those three types is not the contract.

### Current contract (this revision)

Three collaborating pieces:

1. `ActionMailbox::InboundEmail::Incineratable` — schedule on a committed processed-status change
2. `ActionMailbox::IncinerationJob` — delayed execution
3. `ActionMailbox::InboundEmail::Incineratable::Incineration` — destroy only if due and processed

`InboundEmail` includes `Incineratable` and defines `processed?` as delivered, failed, or bounced.

```
status bang (delivered! / failed! / bounced!)
  → UPDATE + COMMIT
    → after_update_commit :incinerate_later
         if ActionMailbox.incinerate && status_previously_changed? && processed?
      → IncinerationJob.set(wait: incinerate_after).perform_later(email)
           queue ActionMailbox.queues[:incineration]

later, job.perform(email)
  → email.incinerate
    → Incineration#run
      → destroy! iff due? && processed?
           due? := updated_at < ActionMailbox.incinerate_after.ago.end_of_day
```

Defaults: `ActionMailbox.incinerate = true`, `incinerate_after = 30.days` ([actionmailbox/lib/action_mailbox.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox.rb) lines 22–23; engine [actionmailbox/lib/action_mailbox/engine.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/engine.rb) lines 17–18, 34–35). Engine queue default is `:action_mailbox_incineration`; `load_defaults "6.1"+` sets it to `nil` ([railties/lib/rails/application/configuration.rb](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb) line 212).

Existing coverage is thin: [actionmailbox/test/unit/inbound_email/incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb) (three terminal statuses + `incinerate = false`) and [actionmailbox/test/jobs/incineration_job_test.rb](file:///home/user/workspace/repo/actionmailbox/test/jobs/incineration_job_test.rb) (missing record). Several invariants below are **source-established, not test-established**.

#### Invariants (must survive a refactor)

**I1. `processed?` is exactly the three terminal statuses.**  
`delivered? || failed? || bounced?` ([inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb) 41–43). Pending and processing are not processed. Guide: [guides/source/action_mailbox_basics.md](file:///home/user/workspace/repo/guides/source/action_mailbox_basics.md) 506–508. Mailbox processing writes those terminals ([base.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/base.rb) 124–130; [state_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/mailbox/state_test.rb) 34–50).

**I2. Scheduling happens only after a committed status change into a processed status, and only when `ActionMailbox.incinerate` is truthy.**  
`after_update_commit` with `ActionMailbox.incinerate && status_previously_changed? && processed?` ([incineratable.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable.rb) line 10). **I7. Destroy uses live state at perform time, not an enqueue-time snapshot.**

### Time control rules

Use `freeze_time` (or `travel_to` a known UTC instant) for every age/schedule test. The dummy app does not set `config.time_zone`, so `end_of_day` is UTC.

Do not treat `travel ActionMailbox.incinerate_after` as proof of the age formula. Compute the cutoff explicitly:

```ruby
cutoff = ActionMailbox.incinerate_after.ago.end_of_day
## due iff inbound_email.updated_at < cutoff
```

Pick `updated_at` values on both sides of that cutoff, including equality (not due). Prefer `update_columns(updated_at: ...)` so you do not fire extra update-commit scheduling.

#### 1. Transitions into each terminal processed status (I1, I3, I5)

For each of `delivered!`, `failed!`, `bounced!` under `freeze_time`:

```ruby
assert_enqueued_with job: ActionMailbox::IncinerationJob,
                     args: [inbound_email],
                     at: Time.current + ActionMailbox.incinerate_after,
                     queue: ActionMailbox.queues[:incineration] do
  inbound_email.public_send(status_bang)
end
```

Then `travel ActionMailbox.incinerate_after` and `perform_enqueued_jobs only: ActionMailbox::IncinerationJob`. Assert `InboundEmail` count −1 and the id is gone.

Negative: `processing!` from pending, and remaining pending, enqueue nothing.

#### 2. Repeated updates (I2)

- `delivered!` then `delivered!` again → exactly one job.
- Non-status `touch` / `update!(updated_at: ...)` on an already-delivered row → no additional job.
- `delivered!` then `failed!` → second job (status changed and still processed).
- `delivered!` then `pending!` → no additional job (`processed?` false).
- `create_inbound_email_from_source(..., status: :delivered)` → no job (`after_update_commit` only).

Assert with `assert_enqueued_jobs 1, only: ActionMailbox::IncinerationJob` / `assert_no_enqueued_jobs`.

#### 3. `ActionMailbox.incinerate = false` (I4)

Restore with `Object#with` or ensure:

```ruby
ActionMailbox.with(incinerate: false) do
  assert_no_enqueued_jobs only: ActionMailbox::IncinerationJob do
    email.delivered!
  end
end
```

Also: schedule while true, then set false, perform the already-enqueued job after travel → record **is** destroyed. Direct `email.incinerate` after making it due still destroys. The flag must not be read inside `Incineration#run`.

#### 4. Scheduling delay and queue (I5)

- Default: wait `30.days`, queue `ActionMailbox.queues[:incineration]` (nil under 6.1+ defaults → Active Job default queue; `:action_mailbox_incineration` if that config is set).
- Stub `ActionMailbox.incinerate_after = 14.days` → `at: 14.days.from_now`.
- Stub `ActionMailbox.queues[:incineration] = :another_queue` → `queue: "another_queue"` (or the string Active Job stores).

Do not assert wait via performing early; assert the job’s scheduled time.

#### 5. Record / config changed after scheduling (I7)

Schedule via `delivered!`, then before perform:

| Mutation after enqueue | After travel + perform | Assert |
|---|---|---|
| `update_columns(updated_at: Time.current)` (now) | not due | row remains |
| `pending!` or `processing!` | not processed | row remains |
| stay delivered, no extra writes | due | row gone |
| `ActionMailbox.incinerate_after = 90.days` | due? uses new duration | row remains if no longer due |
| `ActionMailbox.incinerate = false` | flag ignored at perform | row gone |

#### 6. Age boundary: `updated_at`, `ago`, `end_of_day` (I8)

Unit-test `Incineration.new(email).run` (or `#incinerate`) with time frozen. Do not go through the job wait.

Let `horizon = ActionMailbox.incinerate_after`.

- `updated_at = horizon.ago.end_of_day - 1.second` and processed → destroyed.
- `updated_at = horizon.ago.end_of_day` (equality) → **not** destroyed (`<`, not `<=`).
- `updated_at = horizon.ago.end_of_day + 1.second` → not destroyed.
- `updated_at = horizon.ago` (same clock time, earlier than `end_of_day` on a typical midday freeze) → destroyed. This is why `travel 30.days` currently works, and it is the behavior to keep.
- Same calendar day as `horizon.ago` but later than `horizon.ago` clock time, still before `end_of_day` → destroyed. Proves the cutoff is `end_of_day`, not the duration alone.
- Next calendar day after `horizon.ago.to_date` → not destroyed.

Use a processed email; `update_columns` for `updated_at`. Assert `assert_difference` / `assert_no_difference` on `InboundEmail.count`, then `reload` / `exists?`.

#### 7. Unprocessed records (I9)

For `:pending` and `:processing`, even with `updated_at` far in the past:

- no `IncinerationJob` on create/update that does not enter a processed status
- `email.incinerate` / `Incineration.new(email).run` / `IncinerationJob.perform_now(email)` does not destroy

#### 8. Already-deleted records (I10)

Keep [incineration_job_test.rb](file:///home/user/workspace/repo/actionmailbox/test/jobs/incineration_job_test.rb) 8–16. Also cover the scheduled path: `delivered!`, `destroy!`, `travel`, `perform_enqueued_jobs` → `assert_nothing_raised`, no leftover failures. Both `ActiveRecord::RecordNotFound` (if perform receives a stale instance) and GlobalID `DeserializationError::RecordNotFound` (serialized GID) must be discarded.

#### 9. Attachment and record destruction (I11)

On a successful due+processed incineration:

```ruby
blob = inbound_email.raw_email.blob
attachment_id = inbound_email.raw_email_attachment.id

assert_difference -> { ActionMailbox::InboundEmail.count }, -1 do
  inbound_email.incinerate
end

assert_not ActionMailbox::InboundEmail.exists?(inbound_email.id)
assert_not ActiveStorage::Attachment.exists?(attachment_id)
assert_enqueued_with job: ActiveStorage::PurgeJob, args: [blob]
## or perform PurgeJob and refute blob.service.exist?(blob.key)
```

`destroy!` must raise if destroy validations fail; happy path is a hard delete. Do not require synchronous blob IO if the app uses `purge_later`; requiring the PurgeJob (or performed purge) is the observable contract.

Do not bang status in isolation. Drive a real mailbox, then incinerate.

```ruby

inbound_email = create_inbound_email_from_mail(to: "replies@example.com", subject: "x")
```

### What “pass” means after the refactor

A refactor preserves behavior if:

1. Every I1–I12 assertion above still holds with the same database and job-queue observables.
2. Existing `incineration_test.rb` and `incineration_job_test.rb` still pass without weakening them.
3. Mailbox `state_test` terminals still schedule incineration as a side effect of `delivered!` / `failed!` / `bounced!`.

It may change whether `Incineration` exists, how `due?` is factored, or whether the callback is a lambda. It may not change the age formula, the processed set, the scheduling gates, discard-on-missing, or destroy+purge outcomes.

Gap to close relative to this revision: queue name, repeated updates, create-already-processed, perform-time recheck, `end_of_day` boundary including equality, unprocessed destroy refusal, attachment/blob destruction, and `incinerate=false` not affecting already-queued jobs. Those are current source behavior and must be locked before structural change.
