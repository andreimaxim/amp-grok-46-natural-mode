`after_commit` does not run when a row is written. It runs later, and only if three things are still true at the outer callback boundary: the record was enrolled on that transaction, `trigger_transactional_callbacks?` selected this in-memory instance, and the `on:` action filter matches the flags that instance still holds.

### Registration

`after_commit` / `after_rollback` / `after_create_commit` / `after_update_commit` / `after_destroy_commit` / `after_save_commit` all land on the `:commit` or `:rollback` callback chain. `on:` is rewritten into an `if:` proc that calls `transaction_include_any_action?`. Only `:create`, `:update`, and `:destroy` are legal (`ACTIONS`); `:save` and the string `"create"` raise.

```ruby
## activerecord/lib/active_record/transactions.rb
def after_commit(*args, &block)
  set_options_for_callbacks!(:after, args)
  set_callback(:commit, :after, *args, &block)
end

## on: [:create, :update] becomes:
options[:if] = [
  -> { transaction_include_any_action?(fire_on) },
  *options[:if]
]
```

`transaction_include_any_action?` is exclusive per instance:

- `:create` — `persisted? && @_new_record_before_last_commit`
- `:update` — `!(@_new_record_before_last_commit || destroyed?) && _trigger_update_callback`
- `:destroy` — `_trigger_destroy_callback`

`after_save_commit` is `on: [:create, :update]`, so it fires when either of those two is true.

Same filter name is deduplicated (`after_commit :foo` plus `after_create_commit :foo` keeps one). `on:` on a single `after_commit` is the way to attach several actions without that collapse.

Action flags are written during persistence, not at callback time:

- create path leaves `@_new_record_before_last_commit` true (captured in `remember_transaction_record_state` from the pre-transaction `@new_record`)
- `_update_record` sets `@_trigger_update_callback`
- `destroy` sets `@_trigger_destroy_callback ||= persisted? && destroy_row > 0`

`trigger_transactional_callbacks?` is the gate for “this instance is a candidate at all”:

```ruby
(@_new_record_before_last_commit || _trigger_update_callback) && persisted? ||
  _trigger_destroy_callback && destroyed?
```

Failed saves never set those flags, so they produce neither commit nor rollback callbacks (`test_dont_call_any_callbacks_after_transaction_commits_for_invalid_record`).

### Enrollment

`save` / `save!` / `destroy` wrap work in `with_transaction_returning_status`. That method always enrolls before the persistence body:

```ruby
ensure_finalize = !connection.transaction_open?
implicit_persistence_transaction(connection) do
  add_to_transaction(ensure_finalize || has_transactional_callbacks?)
  remember_transaction_record_state
  status = yield
  raise ActiveRecord::Rollback unless status
end
```

`add_transaction_record` appends onto `current_transaction`. Strong enrollment (`ensure_finalize: true`) goes on `@records`; otherwise a `WeakMap`. A bare `save!` opens its own transaction, so that implicit transaction *is* the outer boundary.

### Nested transactions vs savepoints

```
connection.transaction
  if !requires_new && current_transaction.joinable?
    yield current_transaction.user_transaction   # JOIN, no new stack frame
  else
    within_new_transaction                       # RealTransaction / RestartParent / Savepoint
  end
rescue ActiveRecord::Rollback
  # swallowed
```

`TransactionManager#begin_transaction` sets `run_commit_callbacks = !current_transaction.joinable?`. The outermost real transaction therefore has `run_commit_callbacks: true`. A `requires_new` child under a joinable parent has it `false`.

```
commit_transaction:
  before_commit_records          # no-op unless run_commit_callbacks
  pop stack
  SQL COMMIT or RELEASE SAVEPOINT
  commit_records
    if run_commit_callbacks
      record.committed! + after_commit callbacks
    else
      re-enroll records on parent
      append_callbacks onto parent

rollback_transaction:
  SQL ROLLBACK or ROLLBACK TO SAVEPOINT
  pop stack
  rollback_records               # always: rolledback! + after_rollback
```

Savepoint `full_rollback?` is `false`, so instance state restores only to that savepoint, not to the start of the outer transaction.

Joined inner `Rollback` is swallowed and does **not** roll back the parent (`Nested transactions` docs; both “Kotori” and “Nemu” persist). `requires_new: true` creates a savepoint so inner `Rollback` reverts only that savepoint.

### Callback execution at the outer boundary

Record `after_commit` runs only from `commit_records` when `@run_commit_callbacks` is true — i.e. after the real `COMMIT`, not after `RELEASE SAVEPOINT`. Inner joined blocks never even have their own transaction object.

Order (`CallbackOrderTest`):

- `before_commit` always runs in definition order, before SQL commit.
- `after_commit` / `after_rollback`: with `run_after_transaction_callbacks_in_order_defined` (Rails 7.1+ `load_defaults`) they run in definition order; gem default `false` runs them reversed. `prepend: true` still prepends.
- An error in one record’s `after_commit` stops the rest of that chain (`test_after_commit_chain_not_called_on_errors`) and does not un-commit the SQL.

### The six cases

#### 1. Create then update of the same instance in one transaction

`remember_transaction_record_state` writes `@_new_record_before_last_commit` from the original `@new_record` and does not clear it on the later update. `:create` is therefore true and `:update` is false (`_new_record_before_last_commit` short-circuits the update branch).

Observable at outer commit: unfiltered `after_commit`, `after_create_commit` / `on: :create`, `after_save_commit`. Not observable: `on: :update`, `after_update_commit`.

`ReplyWithCallbacks` plus `save_on_after_create` (`test_only_call_after_commit_on_create_and_doesnt_leaky`) is this pattern: extra saves inside the same transaction still yield only `:commit_on_create`.

A save *inside* `after_create_commit` is a new transaction. `committed!` has already set `@_committed_already_called`, so the next `remember_transaction_record_state` forces `@_new_record_before_last_commit = false` and the second history entry is `:commit_on_update` (`test_save_in_after_create_commit_wont_invoke_extra_after_create_commit`).

#### 2. Record saved only in an inner joined transaction

The inner `transaction` call is a join: no stack frame, no savepoint. `save!` enrolls on the already-current (outer) transaction. Inner block exit does nothing to callbacks. Outer `COMMIT` runs them.

If the inner joined block raises `ActiveRecord::Rollback`, that exception is swallowed and the outer transaction still commits the inner writes. No `after_rollback` from that inner raise.

#### 3. Rollback of an inner `requires_new` block, rescued by the outer block

`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint`:

```ruby
Topic.transaction do
  @first.save!
  Topic.transaction(requires_new: true) do
    second.save!
    raise ActiveRecord::Rollback
  end
end
## @first: 1 after_commit, 0 after_rollback
## second: 0 after_commit, 1 after_rollback
```

Inner savepoint rolls back immediately (`rollback_records`, `full_rollback?: false`). Inner `Rollback` is swallowed, so the outer block commits. `second` is not re-enrolled. Transaction-object `after_rollback` on the inner transaction also runs at inner rollback (`test_transaction_after_rollback_callback`).

#### 4. Outer rollback after an inner savepoint release

Inner `requires_new` that *returns* does `RELEASE SAVEPOINT`, then `commit_records` with `run_commit_callbacks: false` re-enrolls those records (and any transaction-object `after_commit` blocks) on the parent. No record `after_commit` yet (`test_only_call_after_commit_on_top_level_transactions`, `test_transaction_after_commit_callback`).

If the outer transaction then rolls back, those re-enrolled records get `after_rollback` with the action filters they still hold (`on: :create` / `:update` / `:destroy` as appropriate). Inner savepoint release does not “lock in” commit callbacks.

#### 5. Destroy of a newly-created record

Destroy of a never-persisted instance: `@_trigger_destroy_callback` stays false (`persisted? && destroy_row > 0` is false). No commit or rollback callbacks (`test_no_after_commit_on_destroy_after_transaction_commits_for_destroyed_new_record`).

Create then destroy in one transaction, same instance: after destroy, `persisted?` is false and `destroyed?` is true, so `:create` is false and `:destroy` is true. Observable: `after_destroy_commit` / `on: :destroy`, unfiltered `after_commit`/`after_rollback`. Not observable: `on: :create`, `after_save_commit`.

A rolled-back destroy of a persisted row fires `:rollback_on_destroy` (`test_only_call_after_rollback_on_destroy_after_transaction_rollsback_for_destroyed_record`).

#### 6. Multiple in-memory instances of the same database row

Enrollment is per object (`uniq(&:__id__)`), but the candidate map is keyed by `ActiveRecord::Core#==` / `#hash` (class + id). Only one instance runs callbacks.

`prepare_instances_to_run_callbacks_on`:

- skip instances with `!trigger_transactional_callbacks?`
- if `run_commit_callbacks_on_first_saved_instances_in_transaction` (gem default `true`): keep the first
- Rails 7.1+ `load_defaults` sets that flag `false`: last save wins, except a later non-destroyed instance cannot replace an already-destroyed candidate
- if an earlier candidate was created in this transaction, `_new_record_before_last_commit` is copied onto the winner so the later instance still runs **create** filters

`CallbacksOnMultipleInstancesInATransactionTest` (last-saved, the 7.1 default):

| Same-row sequence in one txn | Observable filter | History |
|---|---|---|
| create `"A"` then other instance update `"B"` | create, not update | `Created (title = "B")` |
| update `"two"` then update `"three"` | update | `Updated (title = "three")` |
| update then destroy | destroy | `Destroyed (title = "two")` |
| destroy then original instance update | destroy (destroy candidate is sticky) | `Destroyed (title = "one")` |

Old first-saved config: create+update reports `Created (title = "A")`; update+destroy reports `Updated (title = "two")` — the later destroy is skipped.

Two distinct new records that override `object_id` still both run callbacks, because uniqueness uses `__id__` (`test_saving_two_records_that_override_object_id_should_run_after_commit_callbacks_for_both`).

### Filter cheat sheet at the outer boundary

| What happened on that instance | `after_commit` | `on: :create` | `on: :update` | `on: :destroy` | `after_save_commit` | matching `after_rollback on:` if rolled back |
|---|---|---|---|---|---|---|
| create only | yes | yes | no | no | yes | `:create` |
| update only (previously persisted) | yes | no | yes | no | yes | `:update` |
| create then update, same instance | yes | yes | no | no | yes | `:create` |
| create then destroy, same instance | yes | no | no | yes | no | `:destroy` |
| destroy never-persisted new record | no | no | no | no | no | none |
| inner joined save, outer commits | yes, at outer | per flags above | | | | |
| inner `requires_new` rolled back | no | | | | | inner `after_rollback` immediately |
| inner `requires_new` released, outer rolls back | no | | | | | outer `after_rollback` with those flags |
