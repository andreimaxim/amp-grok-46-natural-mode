`Array#extract_options!` is in [activesupport/lib/active_support/core_ext/array/extract_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/array/extract_options.rb). It peels a trailing options hash off a splat so a method can take positionals plus an options hash.

```ruby
def extract_options!
  if last.is_a?(Hash) && last.extractable_options?
    pop
  else
    {}
  end
end
```

### Trailing-only rule

It inspects **only** `last`. No scan, no walk from the front, no earlier elements.

Both predicates must hold: `is_a?(Hash)` is the type gate; `extractable_options?` is the opt-in. If either fails, the array is unchanged and a new empty Hash is returned.

That is a trailing-options protocol, not “any Hash in the argument list.” `options(1, { a: :b }, 2)` keeps `{ a: :b }` positional. Only `options(1, 2, a: :b)` extracts.

### `Hash#extractable_options?`: `Hash` vs subclasses

On `Hash` itself:

```ruby
def extractable_options?
  instance_of?(Hash)
end
```

`instance_of?(Hash)` is strict: only a **plain** `Hash`, not a subclass. `is_a?(Hash)` would have been true for every Hash subclass; that is deliberately not this gate.

- `{ a: :b }` → extractable
- `HashSubclass.new` with `HashSubclass < Hash` and no override → **not** extractable
- `ActiveSupport::HashWithIndifferentAccess` / `OrderedOptions` / `OrderedHash` → extractable only because they override and return `true`

[extract_options_test.rb](file:///home/user/workspace/repo/activesupport/test/core_ext/array/extract_options_test.rb) locks this: `test_extract_options_doesnt_extract_hash_subclasses` puts a `HashSubclass` last, gets `{}` back, and the array still holds the subclass instance.

Reason: many domain objects inherit from Hash. Treating every subclass as “the options hash” would steal a positional Hash that happened to be last. Default is conservative; extraction is an explicit contract.

### Subclass opt-in

A Hash subclass opts in by overriding:

```ruby
def extractable_options?
  true
end
```

Framework classes that do this: `HashWithIndifferentAccess`, `OrderedOptions`, `OrderedHash`. A user subclass can do the same (`ExtractableHashSubclass` in the tests). Opt-in is per-class via the method, not a registry.

`extractable_options?` is only consulted after `last.is_a?(Hash)`. A non-Hash that defined the method is never asked.

### Receiver mutation

On success it `pop`s. The receiver loses its last element; the popped object is returned (same object, not a copy).

```ruby
array = [1, { a: :b }]
opts  = array.extract_options!  # => { a: :b }
array                           # => [1]
```

On failure it does **not** mutate. Last element stays.

```ruby
hash = HashSubclass.new
hash[:foo] = 1
array = [hash]
array.extract_options!  # => {}
array                   # => [hash]
```

Empty array and “last is not an extractable Hash” are both no-ops on the receiver.

### Return value when nothing qualifies

Always a **new empty Hash** `{}`, never `nil`, never the last element.

Misses: empty array, no trailing Hash, trailing Hash subclass that did not opt in, trailing non-Hash.

Callers can unconditionally merge/read (`options[:foo]`, `options.reverse_merge(...)`) without a nil check. That empty Hash is a fresh object, not shared with the receiver.

### Why an earlier hash stays positional

The method never looks past `last`.

```
args = [1, { a: :b }, 2]
         ^ positional  ^ last is 2, not a Hash → no extract
```

```
args = [{ a: :b }, { c: :d }]
         ^ stays     ^ extracted (plain Hash, last)
```

That matches the calling convention it was built for: `method(*positionals, **options)` / `method(a, b, key: val)`, where the options hash is the **final** argument. An earlier Hash is data, not the method’s options.

The `is_a?(Hash)` + `extractable_options?` pair then says: even when last *is* a Hash, it is options only if it is a plain Hash or a subclass that opted into being treated as one.

Whole contract: last element, extractable Hash or else `{}`, mutate only on extract. No scanning, no subclass-by-default, no nil.
