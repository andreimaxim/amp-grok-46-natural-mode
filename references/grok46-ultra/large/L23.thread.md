## Product shaping brief: clearer cross-adapter `insert_all` / `insert_all!` around `unique_by:` and `returning:`

This is a **behavior-change** brief for an existing bulk-insert capability. It describes the user-visible contract people should be able to rely on. It is not an implementation design. Current-behavior claims below are from this revision’s public API, capability predicates, and bulk-insert tests—not from an assumption that PostgreSQL, SQLite, MySQL, and MariaDB agree.

### Problem frame

A developer bulk-inserts hashes with `ActiveRecord::Relation#insert_all` (skip duplicates) or `#insert_all!` (fail on duplicates), optionally naming a uniqueness target (`unique_by:`) and asking which values come back (`returning:`).

They are trying to write one call that is safe to run against PostgreSQL, SQLite, MySQL, and MariaDB: skip or reject the intended duplicates, leave existing rows unchanged, and—when the database can—get back inserted keys or chosen columns.

Today that is painful because the same options do not mean the same thing on every database, and the public contract overstates uniformity:

- `unique_by:` is documented as PostgreSQL/SQLite-only, but the skip form’s *default* uniqueness target is easy to misread as “primary key” on every adapter.
- On PostgreSQL/SQLite, skip without `unique_by:` ignores a row that collides with *any* unique index. On MySQL/MariaDB the skip form also ignores any duplicate-key collision, but **cannot** narrow that to one index; passing `unique_by:` raises.
- The bang form’s docs say `unique_by:` checks uniqueness “according to just one unique index.” In this revision, bang still raises on **any** unique violation. `unique_by:` is accepted on PostgreSQL/SQLite (including invalid names) and rejected on MySQL/MariaDB, without changing which conflict fails the statement.
- `returning:` is documented for PostgreSQL, SQLite, and MariaDB. MySQL rejects an explicit `returning:` value. MariaDB only returns rows when the server is new enough (≥ 10.5 in this revision). Default return columns are the table’s primary-key columns when returning is supported; otherwise the result has no columns.
- Composite-primary-key tables expose a further split: skip without `unique_by:` raises on PostgreSQL/SQLite (“no unique index found for” the model’s primary-key name) but succeeds on MySQL/MariaDB. Bang does not require `unique_by:` on any of these adapters.
- Skip and bang differ in atomicity: skip can keep the non-conflicting rows from the same call; bang is documented to insert **no** rows from that call if any row is not unique.

The desired progress is a contract a developer can predict from the adapter in front of them: which collisions are skipped vs raised, when `unique_by:` / `returning:` are legal, what the result contains, and whether a failed bang call left rows behind.

### Desired observable outcomes

1. **Adapter capability is visible in the call, not only after reading SQL.** On an adapter that cannot skip duplicates, select a conflict target, or return inserted rows, an explicit unsupported option fails with a clear argument error naming the adapter and the option. 2. **Skip (`insert_all`) never updates an existing row.** A skipped duplicate leaves the stored attributes unchanged. It is not a quiet upsert.

3. **Skip’s default conflict set is “any unique constraint on the table,” on every adapter that can skip.** Duplicate primary keys, duplicate named unique indexes, and duplicate composite unique indexes are all skipped unless the caller narrows the target. 4. **On adapters that can name a conflict target (PostgreSQL, SQLite), `unique_by:` narrows skip behavior to that unique index only.** Collisions on that index are skipped. 5. **On adapters that cannot name a conflict target (MySQL, MariaDB), `unique_by:` is not silently ignored.** Passing it raises. Skip still ignores duplicates on every unique key the database enforces.

**When** a partial unique ISBN already exists (`published_on` present)  
**And** bang inserts the same ISBN with `published_on` set, even with `unique_by: :isbn`  
**Then** `RecordNotUnique` is raised.

#### `returning:`

**When** returning is supported and the caller omits `returning:`  
**Then** the result is an `ActiveRecord::Result` whose columns are the primary-key column(s) (Books: `id`).

**When** `returning: false` or `returning: []`  
**Then** the row is inserted and the result has no columns  
**On** PostgreSQL, SQLite, MariaDB ≥ 10.5.

**When** `returning: [:id, :name]`  
**Then** result rows include those columns for successfully inserted records (`name` is `"Rework"` in the fixture case).

**When** `returning:` is a wrapped SQL expression `UPPER(name) as name`  
**Then** the result’s `name` is `"REWORK"`.

**When** an attribute alias is returned (`returning: :title` while inserting `title:`)  
**Then** the result includes the alias name `title`.

**When** MySQL (or MariaDB < 10.5) is given an explicit `returning:` value  
**Then** argument error: the adapter does not support `:returning`.  
**When** those adapters omit `returning:`  
**Then** insert succeeds and the result has no columns.

#### Empty input, mismatched keys, casting, timestamps

**When** `insert_all([])` or `insert_all!([])`  
**Then** the result is empty and table count is unchanged.

**When** hashes in one call differ in keys (extra `isbn` on one row, or missing `isbn` on the next)  
**Then** argument error: all objects must have the same keys, naming extra/missing keys; no rows inserted.

**When** bang/skip persist a serialized column or enum with the same Ruby value as `create!`  
**Then** the stored/loaded value matches `create!` (no double-encoding through a non-idempotent coder; arrays/enums round-trip).

**When** `insert_all!` is given an unknown attribute  
**Then** `ActiveRecord::UnknownAttributeError`.

**When** `record_timestamps:` is true/false opposite the model setting  
**Then** omitted timestamp columns are filled only when the call says to record timestamps; explicit timestamp attributes in the hash are kept. *(Confirm on insert_all, not only upsert—open question 6.)*

#### Unchanged surroundings (counterexamples)

**When** the caller uses `create_with` or a scoped association (`author.books.insert_all!`)  
**Then** scope/default attributes are applied; an explicit `author_id` on the hash does not override the association’s owner in this revision’s association-precedence test.

**When** the association is has-many-through  
**Then** argument error; bulk insert is refused.

These counterexamples are out of `unique_by:` / `returning:` scope except as “do not break.”

---

### Steering evidence

**Success looks like:** a developer can choose skip vs bang, know whether `unique_by:` and `returning:` are legal on the current database, and predict (a) which rows exist after the call, (b) whether existing rows were mutated, (c) whether a uniqueness error rolled back the whole batch, and (d) which columns are in the result—without reading adapter SQL.

**Investigate / do not ship as “clearer” if:**

- Skip on any advertised adapter updates an existing row’s non-key attributes.
- Bang uniqueness failure leaves any row from that call persisted.
- MySQL/MariaDB accept `unique_by:` and then skip a *different* collision set than PostgreSQL/SQLite with the same option.
- PostgreSQL/SQLite skip with a named `unique_by:` also silently skips collisions on other unique indexes.
- Explicit `returning:` on MySQL succeeds but returns columns (lying about support) or is ignored without error while the caller expected keys.
- Empty input or mismatched keys still writes a partial batch.
- Casting/serialization for insert diverges from `create` for the same value.

**Reconsider the problem framing if:** the real pain is upsert-vs-insert confusion, composite-primary-key modeling, or MariaDB version support—not `unique_by:` / `returning:` predictability. In that case stop widening this contract and split that work.

---

**Hypothesis, labeled:** the valuable product change is a **predictable per-adapter contract** (clear errors where unsupported, skip = any unique key unless `unique_by:` narrows it, bang = atomic fail, returning only where supported), not identical behavior on every database.
