## Shaping brief: more predictable, accessible `button_to`

Working draft. Grounded in current helper, URL, CSRF, form, and test behavior. No implementation design.

**Evidence inspected:** `button_to` and related URL/method/token helpers in [`actionview/lib/action_view/helpers/navigation_helper.rb`](file:///home/user/workspace/repo/actionview/lib/action_view/helpers/navigation_helper.rb); URL conversion in [`actionview/lib/action_view/routing_url_for.rb`](file:///home/user/workspace/repo/actionview/lib/action_view/routing_url_for.rb); [`actionview/test/template/navigation_helper_test.rb`](file:///home/user/workspace/repo/actionview/test/template/navigation_helper_test.rb); guides for `button_to`, the Rails 7 upgrade, `button_to_generates_button_tag`, and Turbo confirm. Public docs still name this `ActionView::Helpers::UrlHelper#button_to`; the helper now lives on `NavigationHelper`.

Claims below are current observable behavior unless labeled **hypothesis** or **open**.

---

### Problem frame

Application authors use `button_to` when a control must cause a real request (sign in, save, delete, log out) and must not behave like a crawlable link. End users, including keyboard and assistive-technology users, then meet that control on the page.

Today the same helper can look like a labeled button, a rich HTML button, a GET navigation control, a POST/DELETE mutating control, a remote form, or a disabled control, depending on calling form. Argument meaning shifts between a string label and a block. Verb, authenticity token, form attributes, and “this will change data” signals land in different places. Authors cannot reliably predict what people will see, announce, or submit. People cannot reliably predict what activating the control will do.

Success: across the supported calling forms, authors can choose a label style, verb, remote-or-not, enabled-or-not, form extras, token policy, and destination, and both authors and end users can predict the resulting action without surprises around HTML safety, missing destinations, or CSRF.

---

### Actors

- **View author:** builds a one-control action in a template.
- **End user:** activates the control with pointer, keyboard, or assistive technology.
- **Assistive-technology user:** needs name, role, disabled state, and whether the action navigates vs changes data.
- **Security-conscious author:** needs mutating requests to carry an authenticity token unless they opted out, and untrusted label text not to run as HTML.
- **App maintainer on older defaults:** still has the legacy submit-control shape when `button_to_generates_button_tag` is false.

---

### Current observable baseline

#### Calling forms

- **String label:** `button_to(name, url, html_options)` — first argument is the visible name; second is the destination.
- **Block:** `button_to(url, html_options) { label }` — first argument is the destination; the block is the visible name. Documented example: `button_to [:make_happy, @user] do ... end`.
- **Nil name:** `button_to(nil, url)` uses the URL string as the visible name (`test_button_to_with_query_and_no_name`).
- **False destination:** `button_to("Hello", false)` and `button_to(false) { "Hello" }` emit a form with **no** destination attribute (`test_button_to_with_false_url`, `test_button_to_with_false_url_and_block`).
- **Nil destination** is not covered by a `button_to` test. URL conversion treats `nil` as “current page”, not as “omit destination”. **Hypothesis:** `button_to("Hello")` / `button_to("Hello", nil)` submits to the current page rather than matching `false`.

#### URL conversion

- String URLs pass through; path helpers become paths; query `&` is escaped in the destination (`test_button_to_with_query`, `test_button_to_with_html_safe_URL`).
- Models and `[parent, child]` arrays use the resource route. New records POST to the collection; persisted records PATCH to the member (`test_button_to_with_new_record_model`, `test_button_to_with_persisted_model`, nested variants). Rails 7 made this default explicit in the upgrade guide.

#### Method selection

- Default for a plain URL is POST.
- `method: :get` → form method GET; no authenticity token (`test_button_to_with_method_get`).
- `method: :delete` → form method POST plus a hidden `_method=delete` (`test_button_to_with_method_delete`). Same pattern for PATCH/PUT.
- Explicit `method:` wins over model-inferred PATCH/POST.

#### Authenticity token

Only on POST-method forms (POST/DELETE/PATCH/PUT), not GET.

| Stimulus | Observable result | Evidence |
|---|---|---|
| CSRF off / no `protect_against_forgery?` | No token field | `test_button_to_without_protect_against_forgery_method` |
| CSRF on, no option | Generated token field | `test_button_to_with_straight_url_and_request_forgery` |
| `authenticity_token: "token"` | That value | `test_button_to_with_authenticity_token` |
| `authenticity_token: true` | Generated token | `test_button_to_with_authenticity_token_true` |
| `authenticity_token: false` | No token even if CSRF on | `test_button_to_with_authenticity_token_false` |

#### Generated form attributes

- Form class defaults to `button_to`; `form_class:` replaces it; unsafe `form_class` is escaped.
- Nested `form:` values appear on the **form**. Computed method, destination, and `remote: true` (`data-remote` on the form) are applied after `form:` is merged, so nested method/destination do not stick. Nested `class` wins over `form_class` (`test_button_to_with_remote_and_form_options`).
- Remaining html options land on the **control** (`class`, `name`/`value`, `data-confirm`, `data-disable-with`, `disabled`).
- Extra `params:` become hidden fields; unpermitted strong params raise.

#### Block capture vs string label

- String name becomes control content. With current defaults, that is a `<button type="submit">`; with the legacy flag off and no block, a submit input whose value is the name (`test_button_to_generates_input_when_button_to_generates_button_tag_false`).
- A block always becomes a `<button type="submit">` whose inner HTML is the block result, including tags (`test_button_to_with_block`).
- `link_to` string names escape `<script>`; `button_to` has **no** equivalent test. **Hypothesis:** a string label is escaped; a block can keep markup that is already treated as safe.

#### Remote, disabled, HTML

- `remote: true` marks the **form**, not the control. `remote: false` is a normal form.
- `disabled: true` disables the **control** only; the form remains. `disabled: false` omits disabled.
- Guides: non-GET should be a real form control, not a link; Turbo confirm for `button_to` must be placed via nested `form:` data, while helper `data: { confirm: }` lands on the control. Authors can mark the wrong element.

### User problems (today)

1. **String vs block:** the first argument changes meaning, so authors mis-assign label and destination.
2. **GET vs POST vs DELETE:** GET looks like the same button but navigates without a token; DELETE looks like POST in the form and only differs by a hidden field people and AT do not see.
3. **`remote: true`:** remote-ness is on the form; confirm/disable hints often on the control. Without JS it still does a full submit. AT does not hear “remote”.
4. **Disabled:** the control is inert; the surrounding form is not, so the page can still look like an active action.
5. **Nested `form:`:** some extras stick, method/destination do not, class precedence is easy to get wrong.
6. **Explicit authenticity token:** `true` / omitted / string / `false` are easy to confuse; GET silently has no token.
7. **Nil vs false destination:** `false` omits destination; `nil` is believed to target the current page. Easy to ship a control that submits somewhere unintended.
8. **Unsafe HTML in labels:** string vs block likely differ; only form class and destinations are proven escaped. Authors can ship XSS or over-escaped names.

---

### Desired outcomes (externally observable)

1. **Predictable calling forms.** A string-label call and a block call with the same destination, verb, and options produce the same destination, verb, token policy, enabled state, and remote-or-not. Only the visible name (plain text vs rich content) differs.
2. **Predictable verbs.** GET, POST, and DELETE are distinguishable to the author from the call, and to the user as navigate vs change-data, without relying on hidden fields alone as the only cue.
3. **Predictable remote.** `remote: true` is visible as “this form may submit without a full navigation”; without the supporting environment it still submits to the same destination with the same verb and token rules.
4. **Predictable disabled.** `disabled: true` is announced and cannot be activated; `disabled: false` is a normal activatable control.
5. **Predictable nested form extras.** Extras intended for the form appear on the form; they do not silently override or get overridden in ways the author cannot see from the call.
6. **Predictable tokens.** POST/DELETE carry a token when CSRF is on unless the author opted out; GET does not; an explicit token is the one submitted.
7. **Predictable destinations.** `false` means no destination; a missing/nil destination does not silently alias `false` unless product later says it should.
8. **Safe names.** Untrusted string labels never run as HTML. Block content that the author marked as HTML can be rich. Both remain a named control.

Do **not** read these as prescriptions of tags, attributes, new options, or JS.

---

### Constraints

- Existing calling forms stay valid: string, block, model, nested array, path helper, `method:`, `remote:`, `disabled:`, `form:`, `form_class:`, `params:`, `authenticity_token:`.
- Non-GET mutating submits must not lose CSRF protection by default.
- Legacy apps with `button_to_generates_button_tag` false still exist.
- The basic submit path must work without JavaScript.
- Escaping untrusted names is a security constraint.
- Docs/upgrade notes already taught “persisted record ⇒ PATCH” and “Turbo confirm goes on the form”.

---

### Non-goals

- Redesigning `link_to` or general form builders.
- Inventing new helper options, markup recipes, or JavaScript adapters.
- Changing CSRF for the rest of Action View.
- Making GET `button_to` into a link, or DELETE into a GET.
- An exhaustive matrix of every HTML option.
- Test-suite design.

### Behavioral examples

Required unless marked illustrative.

**String label, POST (core).** Given a template `button_to "Sign in", sign_in_path`, when the page renders, the user sees a named activatable control that POSTs to the sign-in destination, with a token if CSRF is on.

**Block label.** Given `button_to(sign_in_path) { rich name }`, destination, verb, and token match the string form; the name may include the block’s markup.

**GET.** Given `method: :get`, activating navigates with GET to that destination and does **not** send an authenticity token.

**DELETE.** Given `method: :delete`, activating is a mutating request to that destination (not GET). CSRF-on behavior matches other non-GET calls. Counterexample: it must not be a crawlable link.

**Remote.** Given `remote: true` plus nested `form:` extras, the form is the remote surface and extras appear there; confirm-style data passed as control data stays on the control (today). Without JS, submit still hits the same destination.

**Disabled.** Given `disabled: true`, the user cannot activate it and AT reports it disabled. `disabled: false` matches an enabled control.

**Nested `form:`.** Given `form: { class: "custom-class", "data-type" => "json" }` and `remote: true`, those form extras are present on the form together with remote. Counterexample: nested method/destination do not replace the helper’s verb/destination (today).

**Explicit token.** CSRF on + string token ⇒ that value is submitted. `true` ⇒ generated token. `false` ⇒ no token. GET ⇒ no token regardless.

**False vs nil destination.** `false` ⇒ no destination attribute, both string and block. Nil/omitted destination: **open** — must not be documented as equivalent to `false` until decided.

**Unsafe HTML label.** String `"Malicious <script>content</script>"` ⇒ user sees the characters, script does not run. Block that yields a safe tag (e.g. a span) ⇒ that markup is the name. Unsafe `form_class` and `&` in destinations stay escaped.

**Illustrative — persisted model.** `button_to(persisted_record) { "Update" }` PATCHes the member URL unless `method:` overrides (upgrade-sensitive).

**Illustrative — nil name.** `button_to(nil, url)` names the control with the URL string.

### Compatibility risks

- Changing string/block argument meaning, default POST vs model PATCH, token presence, or which element receives `remote`/confirm/disabled would break templates and CSS/JS selectors.
- Forcing one control element would change legacy input-submit apps.
- Treating `nil` like `false` would retarget existing current-page submits.
- Escaping block output like string labels would flatten rich names; not escaping string labels would be XSS.
- GET token insertion or DELETE without method override would break clients and routes.

---

### Open product questions

1. Should omitted/`nil` destination match `false` (no destination), current page, or be an author error?
2. Must string and block names follow one escaping rule, or is “strings escaped, blocks may be rich” the intended contract?
3. Should remote/confirm/disable hints be one surface (always form or always control) for AT and JS adapters, or is today’s split acceptable if documented?
4. Is GET `button_to` first-class navigation, or a compatibility path that should feel different from POST/DELETE?
5. How obvious must DELETE/PATCH be to AT users beyond “it’s a button in a form”?
6. Should persisted-record default PATCH stay, given the Rails 7 surprise?
7. How much AT/visual difference is acceptable between legacy submit inputs and current buttons?
8. Is `authenticity_token: false` a supported public opt-out or a trap?

---

### Steering evidence (external, not tests)

**Success.** Authors using string and block forms for the same action get the same destination, verb, token policy, and enabled/remote state. Reviewers can say what activating will do. AT users get a name, disabled state, and navigate vs mutate. Untrusted string names do not execute. CSRF-on POST/DELETE still send a token unless opted out. GET still does not. `false` still omits destination.

**Investigate / do not ship.** String and block forms diverge on destination or verb. Disabled controls still submit. Remote-only behavior appears when JS is off. Tokens vanish on POST/DELETE or appear on GET. Nil destination is treated like `false` without a product decision. Unsafe string labels execute.

**Framing may be wrong if** authors are not confused by calling forms, and the real pain is styling, Turbo confirm placement, or docs still saying `UrlHelper` after the NavigationHelper move.

**Measurable signals (qualitative unless you already count these):** fewer “wrong verb / missing token / script in label / button did nothing” reports; authors can predict string vs block, GET vs DELETE, remote, disabled, `form:`, token, nil vs false, and HTML names from docs/examples alone; AT review of a typical delete/log-out control passes name + disabled + not-a-link; upgrade of a persisted-record `button_to` does not silently change verb.
