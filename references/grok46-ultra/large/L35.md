## Action Cable `stream_from` + `broadcast` (this checkout)

Revision: [`ace84a2f3e4138a823592864972adbfde084cfd0`](https://github.com/andreimaxim/rails-for-grok-large/commit/ace84a2f3e4138a823592864972adbfde084cfd0). Evidence is this tree’s implementation and tests.

### What you observe

`stream_from` attaches this channel instance to a named pubsub queue. `broadcast` encodes a payload and publishes it to that same name. Only subscribers who are already streaming that name receive the message; it is not stored.

Default (no callback): the client gets a WebSocket JSON envelope `{ identifier, message }` whose `message` is the decoded broadcast payload.

User callback: nothing is transmitted unless the callback itself calls `transmit`. The callback runs on the worker pool, not on the pubsub thread.

Confirmation: the client’s `confirm_subscription` is withheld until every `stream_from` pubsub subscribe succeeds, then sent once.

Subscribe:

```text
Subscriptions#add
  Channel#subscribe_to_channel
    subscribed  →  stream_from / stream_for / stream_or_reject_for
      String(broadcasting)
      defer_subscription_confirmation!
      handler = worker_pool_stream_handler(...)
      streams[broadcasting] = handler
      pubsub.subscribe(broadcasting, handler, success)
        success → ensure_confirmation_sent
    if rejected? → reject_subscription  (type: reject_subscription)
    else         → ensure_confirmation_sent
```

Broadcast:

```text
Server#broadcast(name, message, coder: ActiveSupport::JSON)
  broadcaster_for(String(name), coder:)
    Broadcaster#broadcast
      instrument "broadcast.action_cable"
      encoded = coder ? coder.encode(message) : message
      pubsub.broadcast(name, encoded)
        SubscriberMap#broadcast → each handler.call(encoded)
```

### Default handler vs user callback ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L160-L225))

`worker_pool_stream_handler` always builds an inner handler, then:

- **User callback or block present:** outer lambda is `connection.perform_work handler, :call, message` (L166–L169). That is `Socket#perform_work` → `Worker#async_invoke` on the thread pool ([socket.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L57-L59), [worker.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L52-L66)). Test: callback sets `Thread.current[:ran_callback]`; the test thread’s flag stays false ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L337-L376)).
- **No callback:** the inner handler is returned as-is (L170–L172). Test: `socket.perform_work` is not called; `{ foo: "bar" }` arrives as `message` ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L378-L387)).

`stream_handler` (L179–L184):

- User handler → `stream_decoder(user_handler, coder:)`.
- Else → `default_stream_handler`.

**Default** (L195–L197, L214–L224): `coder ||= ActiveSupport::JSON`, then decode, then `transmit message, via: "streamed from #{broadcasting}"`. The channel wraps that in `{ identifier:, message: }` ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L240-L248)); the socket JSON-encodes the envelope ([socket.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L45-L117)). So a JSON broadcast is decoded in the stream handler and re-encoded for the WebSocket. Comment at L192–L194 notes that double encode/decode is unoptimized.

**User callback:** `transmit` happens only if the callback calls it. Docs example does `transmit message` after inspecting the decoded hash (L57–L75).

### `coder: nil` vs `ActiveSupport::JSON` vs custom

Asymmetry: `coder:` means different things on subscribe vs broadcast, and on default vs callback.

**On `stream_from` (default `coder: nil`):**

| | `coder: nil` | `coder: ActiveSupport::JSON` (or other truthy coder) |
|---|---|---|
| **User callback** | `stream_decoder` returns the callback unchanged (L207–L208). Raw pubsub payload. | `coder.decode(message)` then `handler.(decoded)` (L201–L206). |
| **Default handler** | `coder ||= ActiveSupport::JSON` (L196). Still JSON-decodes, then transmits. | Uses that coder to decode, then transmits. |

There is no way to get a raw default retransmit without overriding `default_stream_handler`. `ChatChannel#pick_coder` maps `"none"` → `nil` and `"custom"` → `DummyEncoder` ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L26-L41)), but no test subscribes with those params.

**On `broadcast` (default `coder: ActiveSupport::JSON`)** ([broadcasting.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L35-L61)):

```ruby
encoded = coder ? coder.encode(message) : message
server.pubsub.broadcast broadcasting, encoded
```

Truthy coder encodes; `coder: nil` publishes the Ruby object as-is. `broadcaster_for` also does `String(broadcasting)` (L42–L43). Tests: name is a string ([broadcasting_test.rb](file:///home/user/workspace/repo/actioncable/test/server/broadcasting_test.rb#L17-L19)); `broadcast.action_cable` notification payload is `{ broadcasting, message, coder: ActiveSupport::JSON }` (L21–L38).

**Server-side custom encoding** is the `coder:` argument to `broadcast` / `broadcaster_for`, not the channel’s `stream_from` coder. The “custom encoder” test ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L356-L365)):

- `server.broadcast "test_room_1", { foo: "bar" }, coder: DummyEncoder`
- `DummyEncoder.encode` → `'{ "foo": "encoded" }'`
- Channel still subscribed with default JSON coder (`params[:coder]` nil → `ActiveSupport::JSON`)
- Handler JSON-decodes that string to `{ "foo" => "encoded" }` and transmits it
- Client `message` is `{ "foo" => "encoded" }`

So custom *broadcast* encoding is visible to the client only insofar as the *stream* coder can decode it.

### Stopped streams

`on_unsubscribe :stop_all_streams` ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L80-L82)).

- `stop_stream_from`: `streams.delete` then `pubsub.unsubscribe` that handler only (L123–L131). Another channel still streaming `"room_one"` stays subscribed ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L195-L219)).
- `stop_all_streams`: unsubscribe every stored handler and `clear` the hash (L141–L146). Same isolation: other channel instances keep their streams (L168–L193).
- `stop_stream_for` delegates to `stop_stream_from(broadcasting_for(model))` (L134–L136, test L235–L262).

If the name is not in `streams`, stop is a silent no-op.

### Rejected subscriptions

`stream_or_reject_for(nil)` calls `reject` ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L150-L156)). `reject` sets `@reject_subscription` ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L271-L273)). After `subscribed`, `subscribe_to_channel` calls `reject_subscription`: remove from connection subscriptions and transmit `{ identifier, type: "reject_subscription" }` (L204, L333–L342). `ensure_confirmation_sent` returns immediately if rejected (L253–L254), so no confirmation is sent. Test: last transmission is the rejection, not a confirm ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L122-L137)). Rejected channels also ignore later actions ([rejection_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/rejection_test.rb#L39-L55)).

### Decode / encode failures

No rescue in `stream_decoder` or `Broadcaster#broadcast`.

- **Encode failure** in `coder.encode` ([broadcasting.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L59)) propagates to the `broadcast` caller. Pubsub is not reached.
- **Decode failure** on the **default** handler runs on the pubsub callback thread (`SubscriberMap#invoke_callback` is a bare `callback.call message`, [subscriber_map.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/subscription_adapter/subscriber_map.rb#L73-L75)). Unrescued; that subscriber’s delivery fails. There is no test for this.
- **Decode / callback failure** on a **user** handler runs inside `Worker#invoke`, which logs the exception and calls `handle_exception` only if the *receiver* implements it ([worker.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L57-L66)). The receiver is the handler Proc (`handler.call`), so the error is logged and swallowed. No test for this either.

`DummyEncoder` always succeeds; tests never pass invalid JSON.

### String coercion of broadcasting names

Both sides coerce with `String(...)`:

- Subscribe/stop: [streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L93-L125)
- Broadcast: [server/broadcasting.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L43)

`stream_for` / `broadcast_to` first build a string via `serialize_broadcasting` (gid/to_param + `:`), then that string is what `stream_from` / `server.broadcast` use. Tests: symbol stream ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L74-L233)); broadcaster name ([broadcasting_test.rb](file:///home/user/workspace/repo/actioncable/test/server/broadcasting_test.rb#L17-L19)); `broadcast_to` object/array/string ([channel/broadcasting_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/broadcasting_test.rb#L15-L73)).

If one side used a symbol and the other forgot `String(...)`, Redis/inline maps would miss. This revision coerces both ends.
