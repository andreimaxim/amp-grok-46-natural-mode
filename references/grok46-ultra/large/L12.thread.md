### Security vs String compatibility

**Security (must preserve; XSS surface):**
1. Safe receiver + unsafe input via `<<`/`concat`/`+`/`insert`/`prepend`/`replace`/`[]=`/`bytesplice` HTML-escapes via `to_str` then `ERB::Util.unwrapped_html_escape`.
2. Safe receiver + `html_safe` input is inserted raw.
3. Unsafe receiver + any input is inserted raw. Result stays unsafe.
4. `safe_concat` on a safe receiver is raw `String#concat`. On an unsafe receiver it raises `SafeConcatError` and does not mutate.
5. `%` on a **safe** buffer escapes unsafe args (`explicit_html_escape_interpolated_argument` uses `unwrapped_html_escape(arg)` / `to_s`, not `to_str`). Safe args are raw. Result stays `SafeBuffer` and `html_safe?`.
6. `%` on an **unsafe** buffer does not escape; result is a new `SafeBuffer` with `html_safe? == false`.
7. Dirtied copies (`dup`/`clone`), `* n`, and `%` of an unsafe buffer remain unsafe (`initialize_copy` L75–77; `*` L116–123; `%` L133–136).
8. Bang transformers (`gsub!`, `sub!`, …) mark the receiver unsafe **before** mutating. Non-bang versions return a plain `String` via `to_str`.
9. Slice of a **safe** buffer stays a safe `SafeBuffer`. Slice of an **unsafe** buffer returns a plain `String` (`to_str[*]`, L46–48). `slice!` on unsafe leaves the receiver unsafe.

**String compatibility (must preserve, not XSS):** `SafeBuffer < String`; `concat`/`<<` return `self`; `+` is `dup.concat`; `%` and `*` return new objects; `concat(nil)` is a no-op; `<<` requires `to_str` (objects with only `to_s` raise); `%` casts via `to_s`; Numeric is `html_safe?`; YAML/`as_json`/`to_param` emit a normal String.
