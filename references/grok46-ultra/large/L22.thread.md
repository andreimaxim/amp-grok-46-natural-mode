3. Unsafe or impossible attempts fail before or instead of corrupting in-memory state, with a failure that matches the cause: dirty persisted attributes, missing row, writes prevented, lock clause the database will not honor, isolation the adapter or nesting will not honor.

4. Adapter differences stay visible: the same call is not required to succeed on every database. Unsupported lock SQL and unsupported isolation remain distinguishable from each other.

5. Existing default `with_lock { }` behavior (exclusive lock, joinable transaction, yield, commit/rollback) remains the baseline unless an example below explicitly changes it.

---

### Non-goals

- Changing optimistic locking, `Relation#lock` finder chaining, or schema/DDL lock options.
- Making every adapter accept every lock clause or isolation level.
- Prescribing a new method name, keyword list, positional vs keyword split, or deprecation plan.
- Changing how applications recover from `RecordNotFound`, deadlocks, or `StatementInvalid` beyond making those outcomes observable and distinct.
- Performance, lock-wait timeouts as a first-class setting, or multi-row lock APIs.

---

### Risks

- **Silent wrong lock.** If a custom clause is mistaken for a transaction option (or the reverse), the row may take `FOR UPDATE` or no lock while the author believes otherwise. That is worse than raising.
- **Adapter false confidence.** A clause that is a no-op on SQLite but real on PostgreSQL/MySQL can pass locally and fail or mean something else in production.
- **Nesting + isolation.** Authors who add `requires_new` and `isolation` together may expect a nested isolated lock; today that combination is invalid for `transaction`. A safer `with_lock` must not hide that.
- **Dirty-record `RuntimeError`.** Unnamed `RuntimeError` is easy to rescue accidentally (`rescue RuntimeError`) or miss (`rescue ActiveRecord::ActiveRecordError`). Whether that stays is open; changing it would be a compatibility break.
- **Write-prevention.** Locking is treated as a write. Relaxing that would let read-only roles take locks.
- **Missing row after lock wait.** Another session can delete the row; the author must see “gone,” not an empty object.

### Acceptance examples

Required cases. “Author” is the application code calling `with_lock`.

#### 1. Default lock

**Given** a persisted, clean `Person` on an adapter that accepts `FOR UPDATE`.
**When** the author calls `with_lock` with no lock argument and an empty block (or a block that only reads).
**Then** the block runs inside a transaction, the reload uses the default exclusive lock, and no error is raised.
**PostgreSQL observation:** the reload SQL includes `FOR UPDATE`.

#### 2. `false` (no row lock)

**Given** a persisted, clean record.
**When** the author asks `with_lock` to use lock `false`.
**Then** the block still runs in a transaction and the record is reloaded, but the reload does **not** request a row lock (`FOR UPDATE` / custom clause absent).
**Open:** locking tests never call `with_lock(false)`; this is the intended reading of `false` elsewhere in locking. If product intent is “`false` is invalid,” that would be a different outcome and must be chosen explicitly.

#### 3. Custom lock clause

**Given** a persisted, clean `Person` on PostgreSQL.
**When** the author passes `FOR SHARE NOWAIT` as the lock.
**Then** the reload SQL includes `FOR SHARE NOWAIT`, and the block runs while that lock is held.

**Counterexample — clause the database rejects:**
**Given** a custom fragment the adapter/database does not accept (guide: raw SQL the database does not support).
**When** the author uses that fragment with `with_lock`.
**Then** they observe `ActiveRecord::StatementInvalid`, not a successful lock and not `TransactionIsolationError`.

**Adapter note:** MySQL authors may use `LOCK IN SHARE MODE`; SQLite tests do not establish `FOR SHARE`. Success is per adapter, not universal.

#### 4. Dirty persisted record

**Given** a persisted `Person` with `first_name` changed in memory and not saved.
**When** the author calls `with_lock` (default or custom lock).
**Then** locking does not proceed; they see an error that locking unpersisted changes is unsupported and that `"first_name"` changed. In-memory changes are not silently discarded. A later save/reload choice remains theirs.
**Contrast:** the same record with no unsaved changes locks without that error.

#### 5. Commit

**Given** a persisted `Person`.
**When** the author `with_lock`s, sets `first_name` to `"fooman"`, and `save!`s, and the block returns normally.
**Then** a subsequent `reload` shows `"fooman"`.

#### 6. Exception rollback

**Given** a persisted `Person` whose `first_name` is `old`.
**When** the author `with_lock`s, saves `"fooman"`, then raises.
**Then** the exception is visible to the caller, and a subsequent `reload` shows `old`, not `"fooman"`.

#### 7. Yielding the transaction object

**Given** a persisted record (PostgreSQL tests pin this).
**When** the block takes one argument.
**Then** that argument is the current transaction, and the author can register callbacks such as `after_commit` on it. Work scheduled `after_commit` runs only if that transaction commits.

#### 8. `requires_new` and `joinable`

**Given** an already open joinable transaction.
**When** the author calls `with_lock` with `requires_new: true` and `joinable: false`.
**Then** the block’s transaction is not the outer one, and it is not joinable. Locking happens in that inner transaction.

#### 9. Isolation

**Given** PostgreSQL (or another adapter that can set isolation) and no conflicting open transaction.
**When** the author calls `with_lock` with `isolation: :read_uncommitted`.
**Then** the transaction in the block reports isolation `:read_uncommitted`.

**Counterexample — unsupported or invalid isolation:**
**When** the adapter cannot set isolation, the level is invalid, the call joins a transaction that already has a different isolation, or it requests isolation on a nested savepoint.
**Then** the author sees `ActiveRecord::TransactionIsolationError` (SQLite non-`:read_uncommitted` included). SQLite `:read_uncommitted` without shared-cache currently raises a different `StandardError`; whether that should stay distinct is open.

#### 10. Nesting

**Given** example 8’s outer + inner setup.
**When** the inner `with_lock` block runs.
**Then** inner commit/rollback semantics follow the inner transaction (`requires_new`), not by silently joining the outer one. Isolation still cannot be changed mid-nesting (example 9 counterexample).

**Open:** `with_lock` nested inside `with_lock` without `requires_new` is not tested; default `transaction` would join. Whether joining is desired for nested `with_lock` is unspecified.

#### 11. Missing row during reload

**Given** a persisted instance whose row is deleted before reload (another session, or deleted then `with_lock` on the stale object).
**When** the author calls `with_lock`.
**Then** they observe `ActiveRecord::RecordNotFound` and the block does not run as a successful locked update. If a wrapping transaction was opened, it does not commit work from that block.
**Open:** no locking test asserts this; it follows documented `reload` behavior.

#### 12. Write-prevention mode

**Given** `ActiveRecord::Base.while_preventing_writes`.
**When** the author calls `with_lock` with the default lock or a custom clause.
**Then** they observe `ActiveRecord::ReadOnlyError` and the lock query is not performed.

**Contrast:** outside write-prevention, or inside nested `while_preventing_writes(false)`, the same `with_lock` does not raise that error.

---

### Combined custom clause + transaction options (the actual gap)

**Given** a clean persisted row on PostgreSQL.
**When** the author wants both `FOR SHARE NOWAIT` (or equivalent) **and** `requires_new: true` / `joinable: false` / a supported isolation in one critical section.
**Then** both apply: the reload SQL has the custom clause, and the transaction has those options. Neither is dropped. A mistaken attempt that would apply the default lock while ignoring the clause (or pass the clause into `transaction` as an unknown option) is a **failure**, not a silent default lock.

This combined call is **not** in the current locking tests. It is the behavior that would make the feature “easier and safer”; the exact spelling of the call is left open.

---

### Steering evidence

**Success looks like:** Authors can lock with default, `false`, or custom SQL in the same movement as transaction options; commit/rollback/yield still match tests today; dirty, missing, and read-only cases stay loud; PostgreSQL vs MySQL vs SQLite still differ in the table above rather than pretending to be the same.

**Investigate / do not ship if:**

- A custom clause plus transaction options results in `FOR UPDATE` or no lock without an error.
- Unsupported lock SQL starts raising `TransactionIsolationError`, or unsupported isolation starts raising only `StatementInvalid`, so authors cannot tell what to change.
- Dirty records begin locking and dropping in-memory edits.
- Write-prevention allows locks.
- Default `with_lock { }` no longer exclusive-locks on adapters that used to.

**Reconsider the problem framing if:** The real incidents are “I did not know I must be in a transaction to lock,” or “SQLite is not PostgreSQL,” rather than mixing clause + options. Then docs and adapter errors matter more than a combined calling path.

### Open questions

1. Is `false` a supported “no lock, still transactional reload” mode for `with_lock`, or an accident of the lock argument?
2. Should lock-as-transaction-keyword (or the reverse) raise a locking-specific error, a keyword error, or be accepted? No current test.
3. Should the dirty-record failure stay a generic `RuntimeError`, or become a named Active Record error? Compatibility vs rescue safety.
4. Should SQLite shared-cache isolation failures use `TransactionIsolationError` like other isolation failures?
5. New (unpersisted) records: `lock!` skips reload today. In or out of scope?
6. Is joining an already-open transaction the default nested `with_lock` behavior we want to keep?
7. Any requirement to *document* per-adapter clause/isolation matrices, vs only failing clearly at runtime?
