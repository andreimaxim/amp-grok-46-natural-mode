**Request changes.** The proposed `credentials_defaults` patch is a no-op against current Rails, and the claim that environment credentials should *always* fall back to the global key is false.

### Verdict

Request changes. Do not merge a `credentials_defaults` change for this. Current Rails already selects content and key independently in [`credentials_defaults`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L683-L691):

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")
  content_path = root.join("config/credentials.yml.enc") if !content_path.exist?

  key_path = root.join("config/credentials/#{Rails.env}.key")
  key_path = root.join("config/master.key") if !key_path.exist?

  { content_path: content_path, key_path: key_path }
end
```

So `config/credentials/<env>.yml.enc` present + `config/credentials/<env>.key` absent already yields `key_path = config/master.key`. That is documented on [`Rails.application.credentials`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L589-L606) and in `config.credentials.content_path` / `key_path`. A patch that only encodes that case does not change boot behavior.

### Why “always fall back to the global key” is wrong

Key lookup is `ENV["RAILS_MASTER_KEY"]` first, then `config.credentials.key_path`, then missing-key handling. `master.key` is only the default *file* path, not a master key for every store.

| Situation | Actual key used |
|---|---|
| env.yml.enc + env.key | env.key (no master.key fallback) |
| env.yml.enc, no env.key, master.key present | master.key (already true) |
| env.yml.enc, no env.key, `RAILS_MASTER_KEY` set | env var, even if master.key exists |
| `config.credentials.key_path` set | that path; no automatic fallback |
| `credentials:edit --environment X` | **pairs** `config/credentials/X.yml.enc` + `X.key` and **creates** `X.key` if missing; does not fall back to master.key |
| env.yml.enc absent, env.key absent | global `credentials.yml.enc` + `master.key` |
| env.yml.enc absent, env.key present | current code uses **global content + env.key** (independent fallback; a real footgun the PR does not address) |

`credentials:show` / `fetch` follow `credentials_defaults`. `credentials:edit --environment` does not. Treating boot fallback as a global invariant would make the command lie.

`config.require_master_key` also does not mean “require `config/master.key`”. It is passed as `raise_if_missing_key` into `EncryptedFile`, so it requires `RAILS_MASTER_KEY` or whatever `key_path` was selected (`env.key` or `master.key`). Default is `false`. Guide text that only mentions `config/master.key` is already slightly wrong.

Invalid keys are not recovered by falling back further. Wrong `RAILS_MASTER_KEY` or wrong file key → `ActiveSupport::MessageEncryptor::InvalidMessage` (credentials command: “Perhaps you passed the wrong key?”). Missing key + `require_master_key` → boot abort. Missing key + `require_master_key` false → credentials read as empty / `secret_key_base` nil.

### Production vs development

- Development/test (`Rails.env.local?`): `secret_key_base` can come from `tmp/local_secret.txt` if credentials have no key. `credentials:edit --environment development|test` omits `secret_key_base`.
- Production: missing `secret_key_base` is an error. Env credentials without env.key will try `master.key` / `RAILS_MASTER_KEY`; a mismatched key fails decryption rather than falling back to global *content*.
- Env content does **not** merge with `config/credentials.yml.enc`. If `production.yml.enc` exists, global credentials are skipped even when the production key is missing.

### Security / compatibility

Independent key fallback is the documented Rails 6+ model (PR #33521), not a new guarantee this PR would add. Endorsing it as “always use the global key” is the security mistake:

- Per-env files exist so production secrets can use a different key than `master.key`. Falling back to `master.key` for `production.yml.enc` undoes that isolation whenever `production.key` is absent.
- `RAILS_MASTER_KEY` is one name for every store. For env credentials it must be the *env* key, not `config/master.key`. Using the global master key in that env var against `production.yml.enc` is a decrypt failure (or a silent success if the files were encrypted with the same key).
- Compatibility: pairing env content strictly with env.key (no master.key fallback) *would* break apps that encrypt `config/credentials/<env>.yml.enc` with `config/master.key`. Do not ship that without a deprecation. The proposed patch does not even do that; it restates current defaults.

Custom `content_path` / `key_path` must stay overrides. The PR must not fold those back to `master.key`.

### Missing tests (do not change `credentials_defaults` to “fix” these)

There is no matrix test for env content + missing env.key + present `master.key`. Existing coverage is only: env path with env.key, custom path pair, and `RAILS_MASTER_KEY` with `with_key: false`.

Needed, without changing production code:

1. env.yml.enc + env.key + master.key → env.key wins; mystery decrypts.
2. env.yml.enc, no env.key, master.key **same** as encrypting key → decrypts via master.key.
3. env.yml.enc, no env.key, master.key **different** → `InvalidMessage`, no second fallback.
4. env.yml.enc, no env.key, no master.key, `RAILS_MASTER_KEY=<env key>` → decrypts (already partly covered).

6. env.yml.enc, no keys, `require_master_key true` → abort; `false` → no abort.
7. no env.yml.enc → `credentials.yml.enc` + `master.key` (global content fallback).
8. custom `content_path`/`key_path` unchanged.
9. `credentials:edit --environment production` still creates `config/credentials/production.key` rather than reusing `master.key`.
10. production vs development `secret_key_base` when env credentials exist but the key does not.
