`reload` refreshes one Ruby object in place. It always issues a SELECT after busting the query cache, then copies internal state onto `self`. It never replaces the record. If the SELECT finds nothing, it raises and leaves that internal state untouched.

### Override chain

On a typical `ActiveRecord::Base` subclass, later `include`s sit in front ([`activerecord/lib/active_record/base.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/base.rb)):

```text
record.reload
  AutosaveAssociation#reload          # clear marked_for_destruction
    AttributeMethods::Dirty#reload    # super, then nil mutation trackers
      Persistence#reload              # query + in-place state swap
```

[`AutosaveAssociation#reload`](file:///home/user/workspace/repo/activerecord/lib/active_record/autosave_association.rb) runs first:

```ruby
def reload(options = nil)
  @marked_for_destruction = false
  @destroyed_by_association = nil
  super
end
```

[`Dirty#reload`](file:///home/user/workspace/repo/activerecord/lib/active_record/attribute_methods/dirty.rb) wraps Persistence and resets dirty bookkeeping only if `super` returns:

```ruby
def reload(*)
  super.tap do
    @mutations_before_last_save = nil
    @mutations_from_database = nil
  end
end
```

Optional extras: `Aggregations#reload` clears `@aggregation_cache` before `super`; Active Storage nils `@attachment_changes` after `super`.

### Persistence#reload

From [`activerecord/lib/active_record/persistence.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb):

```ruby
def reload(options = nil)
  self.class.connection_pool.clear_query_cache

  fresh_object = if apply_scoping?(options)
    _find_record((options || {}).merge(all_queries: true))
  else
    self.class.unscoped { _find_record(options) }
  end

  @association_cache = fresh_object.instance_variable_get(:@association_cache)
  @association_cache.each_value { |association| association.owner = self }
  @attributes = fresh_object.instance_variable_get(:@attributes)
  @new_record = false
  @previously_new_record = false
  self
end
```

```diagram
reload(options)
  ┌─ connection_pool.clear_query_cache
  ┌─ apply_scoping?(options)?
  │     yes → _find_record(options.merge(all_queries: true))
  │     no  → unscoped { _find_record(options) }
  │              find_by!(_in_memory_query_constraints_hash)
  │              missing → RecordNotFound  (self unchanged after cache clear)
  ├─ steal @association_cache from fresh_object
  ├─ rebind each association.owner = self
  ├─ steal @attributes from fresh_object
  ├─ @new_record = false; @previously_new_record = false
  └─ return self
        Dirty then nils both mutation trackers
```

`fresh_object` is a different Ruby object, built by the finder and discarded. Only its `@attributes` and `@association_cache` are copied. `reload` returns `self` (`object_id` unchanged). `@destroyed` is not cleared.

#### Query-cache clearing

The first statement is `self.class.connection_pool.clear_query_cache`. That is the pool-level store in [`connection_adapters/abstract/query_cache.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/query_cache.rb): increment `@query_cache_version` when a connection is pinned (transactional fixtures), then `query_cache.clear`.

A prior `find` under `QueryCache` would otherwise return the cached row. [`test_reload_via_querycache`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb) populates the cache, updates the row inside `uncached`, then `reload`s and asserts the DB value (`"Mary"`), not the cached one.

The SELECT that follows is a new query. `lock: true` goes through `base.lock(...).find_by!`, and locked SELECTs are not cached (`select_all` skips the cache when `arel.locked`).

#### Lookup: `_find_record` and query constraints

```ruby
def _find_record(options)
  all_queries = options ? options[:all_queries] : nil
  base = if all_queries
    self.class.all_queries_scope
  else
    self.class.all
  end
  base = base.preload(strict_loaded_associations)

  if options && options[:lock]
    base.lock(options[:lock]).find_by!(_in_memory_query_constraints_hash)
  else
    base.find_by!(_in_memory_query_constraints_hash)
  end
end
```

`find_by!` is `where(...).take!`, which raises `ActiveRecord::RecordNotFound` when no row matches.

The WHERE hash uses **in-memory** values, not `id_in_database`:

```ruby
def _in_memory_query_constraints_hash
  if self.class.query_constraints_list.nil?
    { @primary_key => id }
  else
    self.class.query_constraints_list.index_with { |column_name| attribute(column_name) }
  end
end
```

That is why [`test_find_via_reload`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb) works: `Post.new; post.id = 1; post.reload` loads id 1 and then sets `@new_record = false`. [`test_reload_uses_query_constraints_config`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb) asserts the SELECT includes every query-constraint column.

`strict_loaded_associations` preloads associations already in `@association_cache` whose owner is `strict_loading?` and not `strict_loading_n_plus_one_only?`. [`test_strict_loading_has_one_reload`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb) shows a strict-loading record can still read a preloaded `has_one` after reload because it was re-preloaded on the find. Without strict loading, associations are not queried during reload.

Custom SELECT extras die here: [`test_reload_removes_custom_selects`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb) — `Post.select("posts.*, 1 as wibble")` then `reload` drops `wibble` because the new find is a plain `all`/`all_queries_scope`, not the original relation.

#### Scoped versus unscoped, including `all_queries: true`

```ruby
def apply_scoping?(options)
  !(options && options[:unscoped]) &&
    (self.class.default_scopes?(all_queries: true) || self.class.global_current_scope)
end
```

`default_scopes?(all_queries: true)` is true only if some `default_scope` was declared with `all_queries: true` ([`Scoping::Default`](file:///home/user/workspace/repo/activerecord/lib/active_record/scoping/default.rb)). Ordinary default scopes do not trip this.

`global_current_scope` is set only by `Relation#scoping(all_queries: true)` ([`_scoping`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb)). `Model.where(...).scoping { }` without that flag sets `current_scope` only.

Two paths:

1. **Unscoped path** (default): `self.class.unscoped { _find_record(options) }`. `unscoped` with a block is `relation.scoping(&block)` — `current_scope` becomes an empty relation. `_find_record` then calls `self.class.all`, which returns that empty scope. Ordinary default scopes and non-`all_queries` `scoping` blocks do **not** appear in the SQL.

2. **Scoped path**: `_find_record(..., all_queries: true)` uses [`all_queries_scope`](file:///home/user/workspace/repo/activerecord/lib/active_record/scoping/named.rb):

```ruby
def all_queries_scope
  scope = if default_scopes?(all_queries: true)
    default_scoped(all_queries: true)
  else
    relation
  end
  if current_scope = global_current_scope
    scope = scope.merge!(current_scope)
  end
  scope
end
```

`build_default_scope(..., all_queries: true)` keeps only default scopes whose `all_queries` flag is true (`execute_scope?`). A mixed model therefore applies the `all_queries: true` firm scope on reload and skips the ordinary mentor scope ([`test_default_scope_with_all_queries_runs_on_reload_but_default_scope_without_all_queries_does_not`](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb)).

Tests that pin this:

| Test | SQL on reload |
|---|---|
| `test_default_scope_doesnt_run_on_reload` | no `mentor_id` |
| `test_default_scope_with_all_queries_runs_on_reload` | has `mentor_id` |
| `reload({ unscoped: true })` with all-queries default scope | no `mentor_id` |
| `where(salary: 80000).scoping` (no flag) | has `mentor_id`, no `salary` |
| `scoping(all_queries: true)` | has `mentor_id` and `salary` |
| `Author.where(organization_id: 1).scoping` | no `organization_id` |
| same with `all_queries: true` | has `organization_id` |

CHANGELOG notes the scoped path used to leak non-all-queries current scope into reload; `apply_scoping?` now keys off `global_current_scope` / all-queries default scopes only.

### Association cache: replace and rebind owner

After a successful find:

```ruby
@association_cache = fresh_object.instance_variable_get(:@association_cache)
@association_cache.each_value { |association| association.owner = self }
```

`fresh_object` is a new record. Its `@association_cache` is empty unless `_find_record` preloaded `strict_loaded_associations` (or `after_initialize` built an association, as `Publication` does).

So a previously loaded association on `self` is dropped. The cache hash and the `Association` objects inside it are the ones from `fresh_object`, not the old ones.

Those `Association` objects still have `owner` pointing at `fresh_object` (the discarded instance). The loop rebinds `association.owner = self` ([`Association` `attr_accessor :owner`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb)).

[`test_reload_sets_correct_owner_for_association_cache`](file:///home/user/workspace/repo/activerecord/test/cases/persistence/reload_association_cache_test.rb) is the regression: `Publication` `after_initialize` builds `editor_in_chief`, so reload’s `fresh_object` already has an association in cache. After reload, a transaction assigns `editors` / `editor_in_chief` and `save!`. `after_save_commit :touch_name` mutates `name` on whatever object the association thinks is owner. Without rebinding, that is the discarded `fresh_object` and `publication.name` stays `"Rails Way"`; with rebinding it becomes `"Rails Way (touched)"` on the original object.

Next read of a previously loaded association (when it was not re-preloaded) misses the cache and queries again, so DB changes to the association are visible. Reload of the parent does **not** itself SELECT the association unless strict-loading preload applied.

### Persistence flags and mutation trackers

Persistence then:

- `@new_record = false` — even if the receiver started as `Post.new` ([`test_find_via_reload`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb)).
- `@previously_new_record = false` — so `previously_new_record?` is false after reload.
- does **not** assign `@destroyed`.

Dirty runs after that success path and nils both trackers. Later reads reconstruct:

- `mutations_from_database` → new `AttributeMutationTracker` over the new `@attributes` (no unsaved changes).
- `mutations_before_last_save` → `ActiveModel::NullMutationTracker` (`changes` `{}`, `any_changes?` false).

[`test_reload_should_clear_changed_attributes`](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb): assign `catchphrase`, `changed?` true, `reload`, `changed?` false.

There is no dedicated `saved_changes`+`reload` test. The mechanism is the same nil → `NullMutationTracker`. After `Person.create!` / `update`, `saved_changes` is populated ([`dirty_test.rb`](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb) “saved_changes returns a hash…”). After `reload`, `saved_changes` is `{}` and `saved_changes?` is false. `changes_applied` (used by save) *moves* `mutations_from_database` into `mutations_before_last_save`; reload *drops* both.

Autosave: [`test_a_marked_for_destruction_record_should_not_be_be_marked_after_reload`](file:///home/user/workspace/repo/activerecord/test/cases/autosave_association_test.rb) — flag cleared on the same object.

### Observable edge cases

Same Ruby object in every success and failure path (`return self`, or raise before the ivar swap). Internal state is replaced only after `find_by!` succeeds.

#### 1. Unsaved local attribute change

```ruby
pirate = Pirate.create!(catchphrase: "shiver me timbers")
pirate.catchphrase = "*hic*"   # changed? == true
pirate.reload                  # SELECT; same object
## catchphrase back to "shiver me timbers"; changed? == false
```

Queries. Does not raise. Identity kept. `@attributes` replaced; Dirty trackers niled. In-memory edit is gone.

#### 2. `saved_changes` after a prior save, then reload

```ruby
person = Person.create!(first_name: "Sean")  # saved_changes? == true
person.reload
## saved_changes == {}; saved_changes? == false
```

Queries. Does not raise. Identity kept. Last-save mutation history is discarded, not snapshotted. Contrast save, which preserves it via `changes_applied`.

#### 3. Row hidden by a default scope vs explicit scoping

**Ordinary `default_scope` (no `all_queries`):** reload uses the unscoped path. The hidden row is still found. Queries, succeeds, same object, attributes replaced. [`test_default_scope_doesnt_run_on_reload`](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb).

**`default_scope ..., all_queries: true` that excludes the row:** reload uses `all_queries_scope`. `find_by!` raises `RecordNotFound`. Cache was already cleared; `@attributes`, association cache, dirty state, `@new_record` are unchanged. Identity kept. [`test_default_scope_with_all_queries_runs_on_reload`](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb).

**Escape hatches:** `reload(unscoped: true)` forces the unscoped path even with all-queries default scopes. `Model.where(...).scoping(all_queries: true) { record.reload }` merges that relation into the SELECT; a scope that excludes the row raises. The same `scoping` **without** `all_queries: true` does not affect reload.

#### 4. Deleted row

```ruby
deleted_post.reload  # SELECT, then raise RecordNotFound
```

Queries. Raises. [`test_delete_all` in `delete_all_test.rb`](file:///home/user/workspace/repo/activerecord/test/cases/relation/delete_all_test.rb). Identity kept. Because the raise happens in `_find_record`, Persistence never swaps `@attributes` / `@association_cache` and Dirty never nils trackers. In-memory attributes, `changed?`, `saved_changes`, and association cache remain as they were. `@destroyed` is whatever it already was (destroy/delete set it; a `DELETE` issued elsewhere does not).

#### 5. Already-loaded association whose database contents changed

```ruby
post.comments.load          # association cached on post
## ... comments table updated out of band ...
post.reload                 # SELECT posts only (unless strict-loading preload)
post.comments               # cache miss → SELECT comments (fresh rows)
```

Parent reload queries the parent row (and, under default strict loading, re-preloads those cached associations in the same `_find_record`). It does not raise if the parent still exists.

Identity:

- `post` is the same object.
- `@association_cache` is a **new** hash stolen from `fresh_object` (usually empty).
- Old `Association` proxy and old comment records are no longer referenced from `post`.
- Next `post.comments` builds a new association with `owner = post` (or uses a re-preloaded one whose `owner` was rebound) and loads new target records.

Association *contents* follow the database; association *object identity* does not survive reload. Owner rebinding exists so any associations that *were* copied off `fresh_object` operate on `self`, not on the discarded finder result.
