**Verdict: request changes.** The Cookies gate is wrong given how Rails actually configures `session_store`, and it does not implement the claimed behavior.

### Claim vs source

Proposed change in `Rails::Application::DefaultMiddlewareStack#build_stack`:

```diff
- middleware.use ::ActionDispatch::Cookies unless config.api_only
+ middleware.use ::ActionDispatch::Cookies if !config.api_only || config.session_store
```

Current assembly (unchanged except Cookies):

- Cookies: `unless config.api_only`
- Session: `if !config.api_only && config.session_store` (also applies `force_ssl` `secure` cookies)
- Flash / CSP / Permissions-Policy: `unless config.api_only`
- Flash is not real Rack middleware (`ActionDispatch::Flash.new(app)` returns `app`); it only prepends request methods

`config.session_store` is **not** “user opted into sessions”:

- `setup_default_session_store` (Finisher, before `:build_middleware_stack`) sets `:cookie_store` unless `session_store?` is already set. It does **not** skip `api_only`.
- Getter `config.session_store` returns `nil` for `:disabled`, else the resolved store class (truthy).
- `session_store?` is the raw `@session_store`, so `:disabled` is truthy there.

A default API-only app already has `config.session_store == ActionDispatch::Session::CookieStore`. The proposed condition is true for every API app that did not set `:disabled`.

I applied the patch locally, ran railties middleware tests, then reverted. `Rails::Command::MiddlewareTest#test_api_middleware_stack` failed: Cookies appeared in the default API stack. Session and Flash did not.

### Observable stack / request consequences

**Default full-stack:** no change. Order remains Callbacks → Cookies → Session::CookieStore → Flash → CSP → Head → …

**Default API-only (the actual regression):** Cookies is inserted after Callbacks, before Head. Session is still absent. `request.session` stays `Http::Session.disabled`; `reset_session` still works. `ActionController::API` still has no `cookies` helper, but `request.cookie_jar` exists via `RequestCookieMethods`. If anything touches the jar, `ActionDispatch::Cookies#call` can emit `Set-Cookie`. Every request pays Cookies middleware even when unused.

**API-only + `config.session_store :cookie_store`:** same as default API-only. Configuring the store still does **not** insert session middleware. The PR adds Cookies without Session — a half-stack that cannot persist a session cookie through Session, and is not what the API guide describes.

**API-only following the guide** (`session_store` + `middleware.use Cookies` + `middleware.use config.session_store, config.session_options`): user `use` appends after the default stack, so Session stays inside Cookies. After the PR, default Cookies is also present earlier (outside Head/ETag). Duplicate Cookies: inner write, outer `have_cookie_jar?` may write again unless the jar was already `commit!`’d by `Response#before_sending`. `commit_cookie_jar!` only freezes the jar; writing is Cookies middleware’s job.

**Manual Session without Cookies:** session stores call `request.cookie_jar[...] =`. Without Cookies#call, those mutations are not flushed. That is why the guide requires Cookies. The PR does not fix the documented “session_store alone is not enough” pitfall, because it still does not insert Session for API apps.

**Flash:** does not need Cookies; it needs an enabled session (`commit_flash` no-ops unless `session.enabled?`). The PR does not add Flash (correct).

**`config.session_store :disabled`:** getter is `nil`, so API-only still gets no Cookies. Full-stack still gets Cookies, no Session. That part of the predicate is fine.

**Initialization order:** `config.session_store` in `application.rb` / `config/initializers` is visible at stack build. `after_initialize` is too late. The PR does not change that.

**`force_ssl` secure session cookies:** still gated on `!config.api_only && config.session_store`. Unchanged.

### Test coverage and gaps

Covered today:

- Default full-stack and API stacks: `railties/test/commands/middleware_test.rb`. API list must not include Cookies/Session/Flash. **This PR fails that test.**
- Middleware order: Session depends on Cookies; Flash depends on Session (`test_middleware_dependencies`) — full-stack only.
- API `reset_session` without Flash: `session_test.rb`.
- Disabled sessions: writes 500, reads/reset 200.
- API-only + **manual** Cookies + Session + DatabaseSelector: `session uses default options if previous sessions exist` (only asserts 200, not stack membership).
- Active Storage `test_api_only_with_custom_session` adds Session **without** Cookies.

Gaps the PR does not fill: no assertion that API-only + `config.session_store :…` without `middleware.use` gets (or does not get) Cookies/Session; no duplicate-Cookies case; no API-only + `:disabled` stack list; no request-level `Set-Cookie` test for API session enablement.

### Compatibility

- Contradicts `guides/source/api_app.md` and the API generator comment: cookies/session/flash are opt-in.
- Breaks existing `test_api_middleware_stack`.
- Apps that already `middleware.use ActionDispatch::Cookies` get a second Cookies layer.
- Expands cookie surface on every API-only app without enabling sessions.

### Narrower alternative (only if the product intent is real)

Do **not** key off `config.session_store` while the default initializer still sets cookie_store for API apps.

If API apps should get a working session by setting `config.session_store` only:

1. Skip `setup_default_session_store` (or default it to `:disabled`) when `config.api_only`.
2. In `build_stack`, when `config.session_store` is truthy, insert **Cookies then Session** (same order as full-stack), including the `force_ssl` secure-cookie assignment, for both API and full-stack.
3. Leave Flash / CSP / MethodOverride / TempfileReaper behind `unless config.api_only`.
4. Update the API guide, `test_api_middleware_stack`, and add tests for: default API (no Cookies), API + `:cookie_store` (Cookies + Session, no Flash), API + `:disabled` (neither), and no duplicate when someone still `middleware.use Cookies`.

If the intent is only “don’t let people add Session without Cookies”, that is already documented; a one-line Cookies change without Session is the wrong fix. Keep requiring the explicit pair.

**Approve? No. Request changes.** The claimed predicate is false in this codebase, the patch regresses the default API stack (verified), and it never installs session middleware for API-only apps.
