## Active Storage download-link expiration — product shaping brief

This is a **behavior-change** brief with a documentation outcome: application developers should be able to predict when a download link still works. It is not an implementation plan. Current-revision evidence is in the first half; the shaped proposal is in the second. Hypotheses are labeled.

---

### Current observable behavior (this revision)

Evidence inspected: Active Storage routes, blob/service/controller comments, controller and model tests, the Active Storage and configuring guides, and the signed-identifier expiry rule used by Rails message verification. No live HTTP experiment was run. Claims below are what this revision’s source and tests already make observable.

#### Two independent clocks

Developers meet two different lifetimes:

1. **Application download link** — the Rails URL from `rails_storage_proxy_url` / `rails_storage_redirect_url` (and the default `url_for` / `rails_blob_*` helpers). Validity is the **signed blob identifier** in the path.
2. **Service URL** — the storage-provider URL from `ActiveStorage::Blob#url` (and the same on variants/previews). Validity is a **short-lived service grant**, default **5 minutes**, configured separately from (1).

Guides and controller comments state this split. Redirect mode uses both clocks: the Rails URL is checked first, then the client is sent to a service URL that has its own lifetime. Proxy mode uses only the application-link clock; the file is streamed from the app.

#### Permanent versus expiring signed blob identifiers

- `ActiveStorage::Blob#signed_id` with no expiry produces a **non-expiring** identifier. Tests treat it as usable later; comments and the guide call these URLs **hard to guess but permanent by default**.
- Passing `expires_in:` or `expires_at:` produces an expiring identifier. Model tests: a 1-minute `expires_in` or `expires_at: 1.minute.from_now` finds the blob immediately; after traveling **2 minutes**, `find_signed` returns `nil`.
- `rails_storage_proxy_url` and `rails_storage_redirect_url` put that identifier into the path. Per-URL `expires_in` / `expires_at` override the application default. If no per-URL expiry is passed, they use `config.active_storage.urls_expire_in`, which **defaults to unset/nil** (no expiry).
- When that default is set to 1 minute, a freshly generated proxy or redirect URL succeeds immediately and **404s after 2 minutes**.
- Attachments expose the same signed identifier as their blob. A custom `purpose` is honored only when lookup uses that purpose; download routes always look up with the blob-id purpose. A purpose-mismatched identifier is invalid for download. Legacy identifiers generated the old way still resolve.
- **Not tested at controllers:** representation (variant/preview) URLs using `expires_in` / `expires_at`. Routes apply the same signed-blob-id expiry as blob URLs; that inheritance is source-visible, not controller-test-visible.

#### Service URL expiry (`#url`)

- Private services: `#url` is short-lived and signed. Default lifetime **5 minutes**. Disk, S3, and GCS private URLs take that lifetime. Disk service URLs that are expired, tampered, or otherwise unverified **404**.
- Public services: `#url` is a **permanent public object URL**. S3/GCS public URLs do not use the expiry argument. Disk-as-public still issues a disk URL, but with **no expiry** on the encoded key. Tests show a public disk blob URL succeeds.
- Variants/previews use the same service-URL clock when asking the storage service for the derivative.

#### Proxy versus redirect, and cache headers

**Proxy** (file bytes from the app):

- Valid request: **200**, body is the file.
- Cache-Control: `max-age=3155695200, public, immutable` (~100 years, public, immutable). Comments: signed ids are permanent by design so intermediaries can cache.
- If the file is missing on download: **404** and `Cache-Control: no-cache`.
- If download raises: **500** and `Cache-Control: no-cache`.
- Controllers are publicly reachable; knowing the URL is enough. Authentication on the rest of the app does not apply.

**Redirect** (302 to the service URL):

- Valid request: redirect to a URL containing the filename; Cache-Control: `max-age=300, private` (5 minutes, private) — aligned with the default service-URL lifetime, not with signed-id permanence.
- Default helper resolution is redirect mode.

**Mismatch that developers actually hit:** a proxy URL can be given a 1-hour signed-id expiry while the response still says “cache publicly forever.” Origin will 404 after expiry; a CDN that honored `public, immutable` may keep serving. Redirect responses are private and short-lived, so they do not have that intermediary-outlives-expiry problem in the same way; the **service URL** they point at still dies on its own 5-minute (default) clock even if the Rails URL is permanent.

#### Tampered, expired, and missing identifiers

- Invalid / tampered signed blob id on proxy or redirect: **404**. Same for invalid variation keys on representation proxy/redirect.
- Expired signed id (duration or timestamp, per-URL or default): **404**.
- Soft lookup (`find_signed`) after expiry: `nil`. Bang lookup after expiry: invalid signature. Download controllers use the bang path and turn invalid signature into 404.
- Destroyed blob with a still-valid signed id: bang lookup raises record-not-found. **Not rescued in the blob-loading hook** (only invalid signature is). **No Active Storage controller test** for “valid id, blob gone.” Production Rails often maps that to 404; that mapping is not proven here.
- Disk service: invalid encoded key → 404; missing file → 404.

#### Public versus private services

This only changes the **service URL**, not whether the Rails download URL exists or expires.

- Private: service URL expires; redirect then depends on hitting the service before that grant dies.
- Public: service URL does not expire (cloud public URLs; disk public encodes no expiry). Anyone with that service URL keeps access until the object is removed or the bucket policy changes.
- The Rails proxy/redirect URL still uses the signed-blob-id clock in both cases.

#### Variants and previews

- Representation URLs carry a signed blob id **and** a signed variation key.
- Invalid blob id or invalid variation key → **404** (proxy and redirect, variants and previews).
- Valid representation proxy streams the derivative (200); valid representation redirect 302s to the derivative’s service URL, then the processed image is served.
- Variation keys are signed for integrity, **not** given their own expiry in tests. Expiry of a representation **application** URL, if any, is the blob signed-id’s expiry. Expiry of the **service** URL for the derivative is the 5-minute (default) service clock, unless the service is public.
- **Gap:** no representation controller test for `expires_in` / `expires_at` / default `urls_expire_in`.

#### Boundary timing

- Tests only cover **inside** vs **after**: 1-minute lifetime, assert success now, travel **2 minutes**, assert 404 / `nil`. They do not assert the exact expiry instant.
- Message verification treats a payload as expired when current UTC time is **greater than or equal to** the stored expiry. **Hypothesis from that rule, not from an Active Storage test:** at the exact expiry instant the identifier is already invalid (no inclusive “still valid at T”).
- `expires_in` is a duration from generation time; `expires_at` is an absolute time. Both are supported on signed ids and on the proxy/redirect helpers.
- Redirect cache `max-age=300` is the HTTP cache lifetime of the **302**, not a promise that the **Location** URL lives 300 seconds from first click. A client that follows a cached 302 late can land on an already-expired service URL.

#### What the published docs already say (and where they collide)

The guide tells developers that redirect/proxy URLs **never expire by default**, that `expires_in` limits how long they remain valid, that service URLs default to 5 minutes, and that expiry is **not** a substitute for authenticated access control. Controller comments still say signed ids are **permanent by design** so URLs can be cached — including on proxy, which then sends `public, immutable` forever. Those two stories are both present in this revision.

### Shaped proposal (behavioral, user-facing)

#### Problem frame

**Actor:** an application developer using Active Storage to give users (or other systems) a download or view link.

**Situation:** they generate a link with `signed_id`, `#url`, `rails_storage_proxy_url`, or `rails_storage_redirect_url`, sometimes with an expiry, sometimes relying on defaults, sometimes in front of a CDN, on a public or private service, for an original or a variant.

**Pain:** they cannot tell, from the APIs and docs together, **which clock** will make the link stop working, **when**, **what the user sees**, and **whether a cache may keep serving it anyway**. Permanent-by-default application URLs, 5-minute service grants, 100-year public proxy caching, 5-minute private redirect caching, and public-bucket permanence look like one “URL expiry” feature but are not.

**Why it matters:** developers ship links in emails, pages, APIs, and CDNs. If they believe `expires_in: 1.hour` means “the file is reachable for one hour and not after,” they can leak access (cached proxy), surprise users with 404s (expired signed id or expired service redirect), or keep a “temporary” public-service URL alive forever.

**Hypothesis (not supplied by a ticket):** the desired progress is **predictable lifetimes and failure appearance**, not a new serving mode and not replacing authenticated controllers.

#### Desired outcome

After this work, a developer who generates a download link can answer these without guessing:

1. Does this link expire? If yes, on which clock — application signed identifier, service grant, HTTP cache, or public-object permanence?
2. What happens if someone uses it **before**, **at**, and **after** that boundary?
3. What happens if the identifier is tampered with, meant for another purpose, or the file is gone?
4. Does proxy vs redirect change what the user receives and how long intermediaries may reuse it?
5. Does a public service change any of the above?
6. Do variants follow the same rules as originals?

Success is qualitative: a competent Rails developer can choose a helper and expiry options and correctly predict user-visible behavior for the cases below.

#### Appetite

**Hypothesis:** this is a **small batch**. The serving modes already exist. The work is making their clocks, defaults, and failures predictable — by clarifying behavior and, only if needed, removing contradictions that make “expires” mean something else under cache or public-service rules. It is not a rewrite of file serving or a new access-control product.

Out of appetite: authenticated/authorized file access (already a separate documented path), new CDN products, and changing how files are stored.

#### Scope

In:

- Application download links from `rails_storage_proxy_url` and `rails_storage_redirect_url` (and the default resolution that picks one of those).
- Direct signed blob identifiers via `ActiveStorage::Blob#signed_id` / attachment signed ids, including permanent vs `expires_in` / `expires_at` vs application default.
- Service URLs via `#url` on blobs and on variants/previews, including the 5-minute default and public vs private.
- User-visible results: 200 vs 302 vs 404 (and 500 when the file cannot be fetched for a non-missing error).
- Cache-Control on proxy vs redirect, and the implication for CDNs and browsers.
- Tampered, purpose-mismatched, expired, and missing-file cases.
- Variants/previews as first-class examples of the same clocks.
- Boundary timing: duration vs absolute time; behavior at/after the instant.

Out unless it falls out of making the above predictable:

- Direct-upload PUT URLs (they share the service-URL default but are an upload grant, not a download link).
- Replacing built-in controllers with authenticated ones (existing alternative; expiry is not that alternative).
- Changing storage providers or bucket policies.

#### Non-goals

- Making expiry equivalent to authentication or per-user authorization.
- Promising that a URL shared before expiry cannot be used by anyone who has it during its lifetime (the guide already warns this).
- Guaranteeing that a CDN will forget a proxy response the moment the signed identifier expires, unless the work explicitly takes that contradiction into scope as a behavior change.
- Exact-second clock synchronization across app servers and cloud providers as a product promise.
- Changing filename, content-type, or content-disposition rules.

#### Risks

- **Silent access after “expiry” (proxy + CDN).** If application URLs can expire but proxy responses remain `public, immutable` for ~100 years, developers who set `expires_in` may believe access has ended while caches still serve bytes. Treating that as acceptable “current behavior” leaves the original pain in place for CDN users.
- **Breaking permanence.** If defaults stop being permanent, existing emails, bookmarks, and `url_for(attachment)` links start 404ing. That is a compatibility cliff.
- **Two clocks remaining unexplained.** If only application-URL expiry is clarified, developers will still be surprised when a permanent redirect’s **Location** dies in 5 minutes, or when `#url` on a public service never dies.
- **Public buckets.** Documenting or changing only Rails URL expiry will not stop a leaked public service URL.
- **Exact-instant ambiguity.** If “valid for 1 minute” is not defined as inclusive or exclusive of the end instant, tests and developer intuition will disagree at T.
- **Variants.** If representation URLs are omitted, developers will copy blob examples and mis-predict derivative links.

#### Behavioral outcomes and acceptance examples

Required examples unless marked illustrative.

**1. Permanent application link (default)**

- Given no application-wide URL expiry and no per-link expiry, when a developer generates a proxy or redirect link, the signed identifier does not expire.
- When a user requests that link later, they still get the file (proxy: 200 with bytes; redirect: 302 toward the file), unless a **different** clock has ended (service grant for that request, missing file, public object removed).

**2. Per-link `expires_in` / `expires_at`**

- Given a proxy or redirect link with `expires_in: 1.minute` (or `expires_at` one minute from now), when the user requests it immediately, they get the file (200 or 302 as above).
- When they request the **same** URL after that lifetime has passed, they get **404**, not the file.

**3. Application-wide default expiry**

- Given the application default for controller URLs is 1 minute and the developer passes no per-link expiry, when the user requests a freshly generated proxy/redirect URL immediately, success; after the default lifetime, **404**.

**4. Signed identifier without going through a helper**

- Given `signed_id` with no expiry, lookup later still finds the blob.
- Given `signed_id(expires_in: 1.minute)` or `expires_at` one minute from now, lookup immediately finds the blob; after the lifetime, lookup does not find it.
- Counterexample: a signed id created for a **custom purpose** does not work as a download-link identifier.

**5. Tampered or invalid identifiers**

- When the user requests a proxy or redirect URL with a garbage or tampered signed blob id, they get **404**.
- When they request a variant/preview URL with an invalid variation key, they get **404**.

**6. Service URL clock (`#url`)**

- Private service: `#url` is usable immediately and is not a permanent publishing URL; after the service lifetime (default 5 minutes unless overridden), that **service** URL no longer serves the file (disk: 404). A **new** `#url` call issues a new grant.
- Public service: `#url` remains a lasting public locator; passing an expiry to `#url` does not make the public object stop being reachable.

**7. Redirect uses both clocks**

- Given a **permanent** redirect application URL and a private service, when the user hits the Rails URL, they receive **302** with `Cache-Control` private and max-age **300** (default).
- The **Location** they are sent to is a service URL on the service clock. Following it immediately works; following that same Location after the service lifetime does not.
- Given an **expiring** redirect application URL, after the signed identifier expires the Rails URL itself 404s — the user never gets a new service grant.

**8. Proxy cache versus identifier expiry**

- Given a default (non-expiring) proxy URL and a successful fetch, the response is **200** with `Cache-Control: max-age=3155695200, public, immutable`.
- Given an **expiring** proxy URL: origin 404s after expiry. **Open question / risk:** intermediaries that cached the earlier 200 may still have bytes. The desired outcome must pick one: either developers are told that proxy expiry does not retract cached copies, or “expires” on proxy is not considered done until cache instructions cannot outlive the identifier. That choice is the main product fork.

**9. Missing or unreadable file**

- Proxy, file not on the service: **404** and `Cache-Control: no-cache` (must not be stored as a forever-success).
- Proxy, unexpected download failure: **500** and `no-cache`.
- Disk service URL for a deleted blob: **404**.

**10. Variants**

- A valid variant/preview proxy URL returns the derivative bytes (200); a valid redirect URL 302s then serves the processed image.
- Invalid blob id or variation key: **404**.
- If the application URL is generated with expiry, the variant link must follow the **same signed-blob-id expiry** as an original (required for predictability; currently source-visible, not controller-tested).
- The derivative’s **service** URL follows public/private service rules, not a third clock.

**11. Boundary timing**

- `expires_in` counts from generation; `expires_at` is absolute.
- **Hypothesis to confirm:** at the exact expiry instant the identifier is already invalid (`>=` expiry). Acceptance should state that explicitly so “valid for 1 minute” is not read as inclusive of T+1:00.
- Tests that only sample T+0 and T+2 minutes are not enough to claim the instant.

**12. Expiry is not access control** (counterexample)

- Anyone who has a still-valid URL can use it, including if the rest of the app requires login. Expiry only ends that URL. Per-user rules remain the authenticated-controller path.

#### Steering evidence

**Success looks like:** a developer can read the public description of these APIs and correctly predict the examples above; shipping an expiring link no longer surprises them with a 5-minute service 404, a forever CDN copy, or a public URL that never dies.

**Investigate / do not call it done if:**

- Setting `expires_in` on a proxy URL still produces a response that intermediaries are told to keep forever, and CDN users still treat that as “access ended.”
- Default links start 404ing in the wild because permanence changed without an explicit compatibility decision.
- Variant links expire differently from original links.
- `#url` on public vs private services is still described as one “expiring URL” behavior.
- At-the-instant behavior disagrees with what developers are told.

**Reconsider the framing if:** the real pain is “random people can open /rails/active_storage/... URLs,” which is access control, not expiry predictability. Or if the real pain is only missing docs and current behavior is already the intended contract — then this is documentation, not a behavior change.

#### Open questions (material)

1. **Proxy expiry vs `public, immutable`:** is the desired product “origin 404s after expiry, caches may still serve” (document the trap) or “an expired proxy link must not remain cacheable beyond that lifetime”? This decides whether behavior must change.
2. **Keep permanent defaults?** Predictability does not require changing the nil/permanent default. Changing it is a separate compatibility decision.
3. **Exact instant:** confirm exclusive end (`>=` expiry ⇒ invalid) as the developer-facing rule.
4. **Valid signed id, blob deleted:** should the user-visible result be the same 404 as tampering/expiry? Today that path is not proven in Active Storage controller tests.
5. **Appetite for variant examples in the public contract:** treat them as required (recommended) or original-only?
