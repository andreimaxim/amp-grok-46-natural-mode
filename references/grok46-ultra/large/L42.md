`Rails::Application#config_for` is a thin env-slicer on top of `ActiveSupport::ConfigurationFile`. It does not cache. Path resolution, ERB/YAML parse, then `Hash#deep_symbolize_keys`, then `shared`/`env` selection, then a *shallow* `ActiveSupport::OrderedOptions` wrap of a Hash result.

### Pipeline

```text
config_for(name, env: Rails.env)
  resolve path
    Pathname → used as-is
    else "#{paths['config'].existent.first}/#{name}.yml"
  if !yaml.exist? → raise RuntimeError
  ActiveSupport::ConfigurationFile.parse(yaml)
    File.read
    if content includes "<%" → ERB.new(content).result  (no binding; TOPLEVEL)
      YAML.unsafe_load(rendered) || {}
    else
      YAML.unsafe_load_file(path) || {}
    rescue Psych::SyntaxError → ConfigurationFile::FormatError
  all_configs = parsed.deep_symbolize_keys
  config  = all_configs[env.to_sym]
  shared  = all_configs[:shared]
  if shared
    config = {} if config.nil? && shared.is_a?(Hash)
    if both Hash → config = shared.deep_merge(config)   # env wins
    elsif config.nil? → config = shared                 # non-hash shared (e.g. array)
    # else env value kept; shared ignored
  end
  config = OrderedOptions.new.update(config) if config.is_a?(Hash)
  config
```

### Path resolution — intentional

Non-Pathname: interpolate into the first existent `paths["config"]` entry (engine default `"config"`) plus `.yml`. Symbol/string both work via `to_s`. Pathname is used verbatim (`is_a?(Pathname)`, not pathname-like).

Tests: `"config_for uses the Pathname object if it is provided"`; missing-file test uses `config_for('custom')` and asserts `#{app_path}/config/custom.yml`.

### ERB — intentional, with incidental trigger

Contract (test `"config_for containing ERB tags should evaluate"`): `<%= 'custom key' %>` becomes `"custom key"`.

Mechanics in `ConfigurationFile#parse`:
- ERB only if the raw file contains the substring `"<%"`.
- `config_for` does not pass `context:`; `erb.result` with no binding.
- ERB filename is set to the YAML path (parser test: backtrace contains YAML path).
- After ERB, `YAML.unsafe_load` on the string; otherwise `YAML.unsafe_load_file` so Psych can name the file.
- `|| {}` turns Psych’s empty-document fallback (`false`) into `{}`.

Incidental: any `<%` in the file, including inside a YAML string, forces the ERB path. The NBSP warning in `#read` is unused by `config_for` tests.

### YAML load — intentional unsafe parse; FormatError is a contract

`unsafe_load` / `unsafe_load_file` (not `safe_load`). Tests rely on this: `foo: :from_shared` is a Ruby Symbol. Aliases and arbitrary classes are therefore loadable. Not called out in the `config_for` tests beyond YAML symbols.

Syntax errors: `Psych::SyntaxError` → `ActiveSupport::ConfigurationFile::FormatError` with `"YAML syntax error occurred while parsing"`. Tests: `"config_for with syntax error show a more descriptive exception"` and `ConfigurationFileTest#raises FormatError for malformed YAML`.

### `symbolize_names` / YAML patches — intentional post-parse symbolization

`config_for` never passes `symbolize_names` into YAML. It always does `ConfigurationFile.parse(yaml).deep_symbolize_keys`.

That is the whole compatibility story: gems that patch YAML and reject `symbolize_names` cannot break this path, because that option is not used.

Test `"config_for handles YAML patches (like safe_yaml) that disable the symbolize_names option"` stubs `YAML.load` and asserts `{ key: "value" }`. The stub target is stale: current parse calls `unsafe_load_file` / `unsafe_load`, not `load`. The assertion still holds because `deep_symbolize_keys` is what produces symbol keys. Treat the test *name* as the contract; the `YAML.load` stub as leftover mechanics.

`deep_symbolize_keys` walks hashes and arrays (`key.to_sym rescue key`). It runs on the *whole* document so both env names and `:shared` are symbols before lookup.

### `env:` — intentional

Keyword defaults to `Rails.env`. Lookup is `all_configs[env.to_sym]`, so `"production"` and `:production` match.

Test `"config_for allows overriding the environment"`: `config_for('custom', env: 'production')` while the process is not production → `"unicorn"`.

### `shared` and deep overrides — intentional, with a typed merge

Documented on the method and in [`guides/source/configuring.md`](file:///home/user/workspace/repo/guides/source/configuring.md).

| shared | env | result | test |
|---|---|---|---|
| Hash | Hash | `shared.deep_merge(env)` (env wins, nested hashes recurse, arrays replaced) | `"shared config is overridden"`; `"merges shared configuration deeply"` |
| Hash | missing/`nil` (including `test:` with no value) | treat env as `{}`, then deep_merge → shared | `"shared config is returned when environment is missing"`; OrderedOptions test `env: :test` |
| truthy non-Hash (array) | `nil` | env becomes shared as-is | `"works with only a shared root array"` |
| array | array | env kept, shared ignored | `"returns only the env array when shared is an array"` |
| absent | missing | `nil` | `"without the environment configured returns nil"` |

The `config = {} if config.nil? && shared.is_a?(Hash)` line exists so a missing env still deep-merges into a Hash (and later OrderedOptions) rather than returning shared by identity. For a non-Hash shared, the `elsif config.nil?` branch returns shared unchanged.

`Hash#deep_merge` only recurses into hashes (`deep_merge?` → `other.is_a?(Hash)`). Array values are replaced, not concatenated. That is why a shared array is dropped when the env key is also an array.

If env is a non-Hash (array/scalar) and shared is a Hash, neither merge branch runs; env is returned and shared is ignored. Only the array side of that is tested.

### Symbolized access / OrderedOptions — intentional at the *root Hash only*

If the selected value `is_a?(Hash)`, wrap with `ActiveSupport::OrderedOptions.new.update(config)`. Nested hashes stay plain `Hash` with symbol keys. Not recursive.

Consequences, all tested at the root:
- Method access: `config.some_key` — `"returns an ActiveSupport::OrderedOptions"`
- String or symbol `[]`: `"loads custom configuration from YAML accessible as symbol or string"` (`[:foo]` and `["foo"]`). This is OrderedOptions `#[]` / `#[]=` calling `key.to_sym`, not HashWithIndifferentAccess.
- Hash API: `"makes all hash methods available"` (`keys`, `values`, `to_h`, equality with a Hash)
- Nested access is symbol-only on inner hashes: `"loads nested custom configuration from YAML as symbol keys"` uses `[:foo][:bar][:baz]`

6.1 upgrade notes say string keys no longer work; that refers to *nested* hashes (and the old indifferent-access return). Root string keys still work via OrderedOptions. The configuring guide still shows `payment["merchant_id"]` at the root.

Incidental: `update` copies nested hashes by reference; they are not OrderedOptions. `assert_equal({ baz: 1, qux: 2 }, config[:foo][:bar])` would pass either way.

### Scalar and array roots — array is a contract; scalar is the same branch, untested

`"does not assume config is a hash"`: env root array → `["foo", "bar"]`, not OrderedOptions.

Any non-Hash env value takes that branch (return as parsed, after shared rules). A scalar env root would return the scalar. No test for a scalar document or scalar env value. A non-Hash *document* root would call `deep_symbolize_keys` on a non-Hash and raise; empty files never hit that because parse returns `{}`.

### Absent environment — intentional `nil` unless `shared`

No matching env key, no `shared`: `config` is `nil`, skip wrap, return `nil`. Test `"config_for without the environment configured returns nil"` (file has only `test:`, app is `development`).

With `shared`, see table above. Empty YAML key (`test:` → `nil`) is the same as a missing key.

### Empty file — intentional `nil`

`set_custom_config ""` → parse `|| {}` → `{}` → no `:development`, no `:shared` → `nil`. Test `"config_for with empty file returns nil"`.

The `{}` coercion is in `ConfigurationFile`, not `config_for`. Psych empty-file fallback is `false`; `false || {}` is `{}`. YAML `false`/`null` at the document root would also become `{}` and then `nil` from `config_for`. Untested; incidental.

### Missing file — intentional RuntimeError

Not `Errno::ENOENT`. Message: `"Could not load configuration. No such file - #{yaml}"` with the resolved Pathname. Test `"config_for raises an exception if the file does not exist"`. Existence is `Pathname#exist?` after path resolution; no `config/` dir would interpolate `nil` into the path and still raise this error. Untested.

### Intentional contracts vs incidental mechanics

**Contracts** (method docs, guides, and/or `configuration_test.rb`):
- Load `config/<name>.yml` or an explicit Pathname
- ERB then YAML
- `env:` (default `Rails.env`) selects a top-level key
- `shared` deep-merges under a Hash env; Hash env wins; missing Hash env falls back to shared; array env with array shared keeps env
- Hash result is `ActiveSupport::OrderedOptions` (method + string/symbol `[]` at the root)
- Nested keys are symbols
- Array env root is returned as an Array
- Missing env without shared → `nil`
- Empty file → `nil`
- Missing file → that RuntimeError
- Psych syntax → `ConfigurationFile::FormatError`
- Symbol keys even if YAML cannot take `symbolize_names`

**Incidental / untested consequences of the same code:**
- No caching
- `<%` substring, not a real ERB detect
- `unsafe_load` (Ruby symbols/classes/aliases)
- `YAML.load` stub in the patches test does not intercept current parse
- OrderedOptions wrap is shallow
- Scalar env roots; non-Hash document roots
- Psych empty/false/null document → `{}` → `nil`
- Shared Hash ignored when env is non-Hash
- Arrays never deep-merged
- `database_configuration`’s `shared` behavior is a separate algorithm
