## Maintenance brief: development route reload after an invalid route file

This is **maintenance** of the development reload contract at `Rails::Application::RoutesReloader` / `app.routes_reloader`, the registered route sets, external draw paths, and `config.file_watcher`. The routing DSL and successful-dispatch behavior are not the target. The work is to make reload, error, and recovery determinate so a developer is not left guessing whether previously drawn routes still answer requests and when a corrected file becomes the live draw.

No external ticket or reproduction was supplied. Current-behavior claims below are from this checkout’s source and tests. Where tests do not cover a case, that is left open rather than treated as a guarantee.

### Problem frame

**Actor.** A developer running a Rails app in development, with reloading enabled, editing `config/routes.rb` (or a mounted engine’s equivalent) or a file under an external draw directory (`config/routes/**/*.rb`).

**Situation.** They save a change that is not valid Ruby, or that raises while the file is loaded. They then hit the app, open `/rails/info/routes`, or generate a URL. Later they correct the file and hit the app again. The same loop can involve an application file and a mounted engine file at once, a deleted route file, or either value of `config.reload_classes_only_on_change`.

**Pain.** After the bad save it is not obvious from outside the reload machinery whether previously working application and engine routes still match, whether the next request will raise again / 404 / serve stale routes, whether correcting the file is enough by itself, or whether application and engine draws fail independently.

**Desired progress.** At that boundary, a failed draw is visible, the post-failure routing result is stable, and a corrected file takes effect on the next watcher-visible reload trigger — without a process restart or an unrelated extra save.

**Boot.** `app.routes_reloader` is a `RoutesReloader` built with `config.file_watcher` (default `ActiveSupport::FileUpdateChecker`; confirmed by “routes reloader uses configured file_watcher”). Each engine/application that has routes registers its `config/routes.rb` on `paths`, its route set on `route_sets`, and `config/routes` directories on `external_routes` and on route-set `draw_paths`. In local env the application route set is lazy; `execute_unless_loaded` is skipped at finish unless eager load. Loading tests: routes and `after_routes_loaded` run once on boot/first use.

**Successful change.** In development, a later request picks up edits to `config/routes.rb` or an external draw file: routes are added and removed, named helpers follow, engine and application draws share one reloader. Production in the same test does not pick up the change. `reload_routes!` always reloads.

**Failed first load.** Unit tests: `execute` that raises leaves `loaded` false; a waiting thread retries rather than proceeding as loaded. There is **no** application-level test that a syntax error in an already-live `config/routes.rb` leaves old routes matching, or that it does not.

**Inferred from source, not covered by tests (this is the pain).** `reload!` empties every registered route set, then loads every path. The file watcher records new mtimes before the load block runs. On exception the previous “loaded” flag is restored; the emptied sets are not restored. Once a reload cycle starts, `to_run` always runs a full routes `execute`. Whether a cycle starts depends on `config.reload_classes_only_on_change`:

- **true (default):** a cycle starts only if some registered reloader, including this one, reports `updated?`. After a failed reload the watcher has already consumed that mtime, so a repeat request with no further filesystem change may not run the routes reload again.
- **false:** a cycle starts on every request, so a still-invalid file is attempted again each time.

**Application + engine.** They share one reloader, one `paths` list, one `route_sets` list. Tests cover successful engine files and a boot-time missing application `config/routes.rb` when routes were declared in the application class. They do not cover one of two live files becoming invalid, or both changing in one request.

**Deleted files.** The default watcher treats a disappearing watched file as an update (watched-set size changes) and only loads paths still listed; loading a missing Ruby file raises. External draw files are not themselves loaded by the reloader; they are re-read when `draw :name` runs. A missing drawn file raises `ArgumentError` from the mapper. No test covers deleting a previously live routes file after boot.

**`config.file_watcher`.** Swap in `EventedFileUpdateChecker` (or another object with the same `updated?` / `execute` / `execute_if_updated` API) and the reloader’s updater is that class. Detection timing follows that watcher; the reload/error contract after detection is still `RoutesReloader`.

### Desired observable outcomes

1. **After a successful boot or successful reload, the live route sets are exactly the last successful draw** of the application plus mounted engines, including external draw files pulled in by `draw`.
2. **A load error in any one watched route file is visible on the request (or reload trigger) that first observes the change.** The developer can tell the draw failed; they are not left with silent stale success.
3. **Until a subsequent successful draw, it is determinate whether previously successful routes still match.** This brief does not pick last-good vs empty vs keep-raising. Maintenance succeeds when that answer is the same for application routes, mounted engine routes, and external draw files, and is stable across the next request with no further file change.
4. **A corrected file takes effect on the next reload trigger that can see the correction** — typically the next request after the save — without an unrelated file change or a process restart. That must hold for both `config.reload_classes_only_on_change` values and for both polling and evented `config.file_watcher`.
5. **Application and engine route files are one reload unit.** A change or failure in one is not an isolated engine-only or app-only reload. After recovery, both sides reflect the files on disk together.
6. **Deleting a watched route file is a change**, not a silent keep-forever. The next successful draw no longer includes what that file used to define; a delete that makes the remaining files unloadable is the same class of failure as invalid Ruby.

### Non-goals

- Changing the routing DSL, `draw` authoring rules, or production dispatch when reloading is disabled.
- Making production pick up route file edits.
- Redesigning class reloading, I18n reloading, or autoload, except insofar as `reload_classes_only_on_change` already gates whether a request starts a reload cycle.
- Prescribing how `RoutesReloader` stores state, how route sets are cleared, or how tests are written.
- New developer-facing UI beyond the existing exception page, routing error, and `/rails/info/routes`.

### Acceptance examples

Required cases for judging the maintenance, not a test plan.

**Initial boot.** Development app with valid application `config/routes.rb`, a mounted engine with its own `config/routes.rb`, and an external file under `config/routes` drawn from the application. First request uses those draws. `app.routes_reloader` is the application’s reloader and watches those paths/directories via `config.file_watcher`.

**Syntax/erroring reload.** After that success, the developer writes invalid Ruby into exactly one of: the application routes file, the engine routes file, or the external draw file. They then issue a request (or otherwise trigger the development reloader). They observe a load failure attributable to that file, not a quiet continue.

**The next request, file still invalid, nothing else saved.** With `config.reload_classes_only_on_change` true, and again with it false: the observable routing result is the same determinate post-failure condition as outcome 3. It must not flip between “old routes work,” “empty/404,” and “error” without another file event.

**Correction.** They restore valid Ruby that defines a different route than before. Next request (no restart, no mandatory extra file touch) serves the new draw and not the pre-error draw. Named helpers and `/rails/info/routes` agree with the corrected files. Holds for application, engine, and external draw corrections, and for both `reload_classes_only_on_change` values.

**Simultaneous application and engine changes.** In one interval before the next request, both the application and engine route files change to valid new content. One request later, both new draws are live. If instead one of the two files is invalid, the failure is visible and neither side is left on a privately updated draw that the other side did not jointly recover from; after both files are valid, one request recovers both.

**Deleted route files.** After a successful draw, the developer deletes a previously watched `config/routes.rb` or a drawn external file. The next request treats that as a change. If remaining files still form a valid draw, routes from the deleted file are gone. If remaining files cannot load (missing `draw` target, missing main file still on `paths`), the result matches the erroring-reload examples, and recreating a valid file recovers on the next request.

**`config.reload_classes_only_on_change`.** True: a routes-file mtime/dir change is enough to start the cycle; an unchanged routes tree is not rebuilt on every request. False: every request is willing to run the routes load again, so a still-bad file keeps failing and a just-corrected file can succeed without another distinct change source. Neither setting requires a process restart for a corrected file that the watcher can see.

**`config.file_watcher`.** Replacing the watcher class does not change the outcomes above once that watcher reports the same `updated?` / `execute` events. If the watcher cannot see a save, that is a watcher limitation, not a second routes contract.

### Open behavioral questions

These change the desired outcome if answered; they should not be filled in by implementation preference.

1. **Last good draw vs empty vs keep raising.** After a failed reload of an already successful draw, should requests keep matching the last successful application+engine draw, match nothing, or keep raising the load error until a successful draw? Source currently points at emptied sets plus a restored “loaded” flag; tests do not lock a product answer.
2. **Does “visible failure” mean only the first request after the bad save, or every request until correction?** Interacts with question 1 and with `reload_classes_only_on_change`.
3. **Partial success across route sets.** If an earlier path in `paths` loads and a later one raises, is any of that partial draw allowed to become the live application or engine set, or must all registered sets stay on the same generation (all last-good or all failed)?
4. **Non-request triggers.** Console, `reload_routes!`, and rake: same contract as the next HTTP request, or only request-wrapped reloading is in scope?
5. **Invalid Ruby vs routing DSL errors vs missing files.** One failure class, or missing files are allowed to mean “no routes from that source” without error when the path is no longer existent?
6. **Evented watcher lag.** If `EventedFileUpdateChecker` reports the save one request late, is that acceptable as long as the request after the report matches the examples?

### Evidence still to collect

Not observed in this checkout (no live app run):

- One development request after introducing a syntax error into an already-booted `config/routes.rb`, then a second request with the file still bad, then a third after correction — under both `reload_classes_only_on_change` values.
- The same sequence with only a mounted engine file bad, and with only an external draw file bad.
- Application and engine files saved in the same interval, one valid and one invalid, then both valid.
- Deleting `config/routes.rb` or a drawn `config/routes/*.rb` after boot.
- Repeating the error/correction pair with `config.file_watcher = ActiveSupport::EventedFileUpdateChecker`.
- What `/rails/info/routes` and URL helpers show in the emptied-vs-stale window (question 1).

Until those are collected, outcome 3 and questions 1–3 remain the unresolved core of the developer uncertainty this maintenance is meant to remove.

**Steering.** If after the work a developer still cannot tell whether old routes are live, or a corrected file does not take effect on the next watcher-visible request, the framing is not met. If the only remaining issues are production, DSL syntax, or class-reload performance, the framing is too wide and those should be left alone.
