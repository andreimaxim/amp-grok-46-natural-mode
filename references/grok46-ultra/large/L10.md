**Verdict: BLOCK.** Replacing `value.blank?` with `value.nil?` in `Hash#compact_blank!` does not preserve the Active Support API. Ruby `Hash#compact` drops only `nil`; `compact_blank!` drops every `blank?` value.

### Claim vs contract

At this revision (`ace84a2`), [`Hash#compact_blank!`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb) (lines 265–276) documents and implements `Object#blank?`:

```265:276:activesupport/lib/active_support/core_ext/enumerable.rb
  # Removes all blank values from the `Hash` in place and returns self.
  # Uses Object#blank? for determining if a value is blank.
  #
  # ```
  # h = { a: "", b: 1, c: nil, d: [], e: false, f: true }
  # h.compact_blank!
  # # => { b: 1, f: true }
  # ```
  def compact_blank!
    # use delete_if rather than reject! because it always returns self even if nothing changed
    delete_if { |_k, v| v.blank? }
  end
```

The same predicate is used by `Hash#compact_blank` (`reject { |_k, v| v.blank? }`, L258–263) and `Enumerable#compact_blank` (`reject(&:blank?)`, L190–208). Action Pack even documents the split: `Parameters#compact` removes `nil`; `Parameters#compact_blank` uses `blank?` ([`strong_parameters.rb`](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb) L1030–1053).

`blank?` itself is defined in [`object/blank.rb`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb). Observable treatment:

| Value | `blank?` | `nil?` | `compact` keeps | `compact_blank` keeps |
|---|---|---|---|---|
| `nil` | true (`NilClass#blank?` L69) | true | no | no |
| `false` | true (`FalseClass#blank?` L86) | false | **yes** | **no** |
| `""` | true (`String#blank?` L223) | false | **yes** | **no** |
| `" "` / other whitespace | true (`String#blank?`, `BLANK_RE`) | false | **yes** | **no** |
| `[]` | true (`Array#blank?` aliases `empty?` L180) | false | **yes** | **no** |
| `{}` | true (`Hash#blank?` aliases `empty?` L206) | false | **yes** | **no** |
| `0`, `1`, other numerics | false (`Numeric#blank?`) | false | yes | yes |
| `true` | false (`TrueClass#blank?` L103) | false | yes | yes |

The proposed `nil?` predicate would leave `false`, `""`, `" "`, `[]`, and `{}` in the hash. That breaks every documented example.

### Destructive return / identity

`Hash#compact_blank!` is not `Hash#compact!`:

- MRI `Hash#compact!` returns `self` if it deleted any `nil`, else `nil` (`{a: 1}.compact!` → `nil`).
- AS uses `delete_if` so it **always returns the same receiver**, even when nothing is blank (comment at enumerable.rb L274). `Array#compact_blank!` uses the same rationale.
- Contrast: `Parameters#compact_blank!` uses `reject!`, which can return `nil` when nothing changed.

The existing bang test asserts mutated contents, not `assert_same`. A `nil?` swap would still return `self` via `delete_if`; identity would not catch the semantic break. Content assertions would.
