### Problem frame

**Actor:** A Rails application or library author who stores settings in `ActiveSupport::OrderedOptions` or `ActiveSupport::InheritableOptions` (typical surfaces: `Rails.application.config`, railtie config hashes, encrypted configuration values) and later reads a setting that must actually be there.

Diagnosis is a search through assignment sites and parent/child option sets, not an answer at the point of the required read.

This matters because these objects are how Rails configuration is actually held (`config.active_record`, `config.action_mailer`, custom `config.x.*` hashes, encrypted credentials, and similar). Required reads happen late (boot, first use, credentials access). A generic “is blank” failure at that moment is expensive to map back to the write that caused it.

---

### Desired outcomes

These are externally observable claims. They do not name APIs, classes, or storage.

1. **Successful required reads stay successful and return the same values they return today.** If a bang read currently returns a value, it still returns that same value. Insertion order of names, mixed string/symbol assignment, `to_h` / iteration order, parent-then-child presentation, and child overrides of present values remain as they are.

2. **A required read that cannot be used fails in a way a person can understand.** The failure still happens for the cases that fail today (never assigned, `nil`, `false`, whitespace-only / empty strings, inherited blank, child override to blank). The person can tell from the failure that the required setting was not usable.

3. **A person can diagnose which situation caused the failure without reconstructing assignment history from scratch.** At the point of failure they can distinguish at least: never assigned vs assigned-but-unusable, and for inheritable sets, inherited unusable value vs local override that made a parent value unusable. They can tell `false` and whitespace apart from “missing” well enough to fix the right write.

4. **Quiet reads, `respond_to?`, `dig`, and Hash-like lookup do not become a second, incompatible configuration language.** Missing quiet readers still return `nil`. String and symbol assignment/lookup still resolve to the same stored name. `dig` still symbolizes the first identifier and walks nested values. `respond_to?` still reports the dynamic readers, writers, and bang names people already rely on.

5. **Inherited present values remain visible to required reads until a child actually overrides them.** A child that does not write a name still sees the parent’s present value on a required read. A child present override is what a required read returns.

---

### Non-goals

- Changing which present values a required read returns, or the Hash-like insertion / parent-then-child ordering of names.
- Making quiet reads raise, or making missing names stop returning `nil` on the non-bang path.
- Making `respond_to?` start returning false for unassigned names.
- Making `key?("string")` become true (current tests assert it is false).
- Replacing `OrderedOptions` as the holder of Rails config, credentials, or railtie settings.
- Broader configuration validation, schema, type checking, or a new settings product.
- Changing `blank?` / `presence` for Ruby objects in general.
- Teaching people a new way to assign or look up keys that already succeed.

---

### Compatibility boundaries

Preserve:

- Return values of successful `[]`, dynamic readers, `dig`, and bang reads (including `true`, `0`, non-blank strings, symbols, and other present objects).
- Symbol storage with string-or-symbol assignment and lookup for those successful paths.
- Insertion-order enumeration on `OrderedOptions`; parent keys then child-only keys, with child values winning, on `InheritableOptions`.
- Quiet missing reads returning `nil`.
- `respond_to?` being true for arbitrary reader, writer, and bang names.
- Child override of a present parent value remaining the value a required read returns.
- Failure still occurring for the unusable cases listed above (do not start treating `false` or whitespace as a successful required read).

Do not require:

- A particular exception class, message string, or backtrace shape beyond “a person can understand and diagnose the failure.” Today it is `KeyError` with `":name is blank"`; a compatible outcome may keep raising on the same stimuli while making the report more specific.
- `key?` with string arguments to change.
- Any new name, method, or object type in the public surface — this brief does not add any.

Hypothesis, labeled as such: callers may rescue `KeyError` and match `/is blank/`. Tightening diagnosis should not silently stop failing those stimuli; whether the exact class and substring must stay bit-identical is an open compatibility question (see below).

### Example journeys

Required cases unless marked illustrative.

#### 1. Required setting is present — unchanged success

A person assigns `host = "api.example.com"` (symbol, string, or writer; all equivalent today). They require it with a bang read. They observe `"api.example.com"`, the same object the quiet reader would return. Order of other names is unchanged.

Same journey with inherited config: parent has `host = "api.example.com"`, child does not write `host`. Bang read on the child returns `"api.example.com"`.

Same journey with override: parent has `host = "api.example.com"`, child writes `host = "staging.example.com"`. Bang read on the child returns `"staging.example.com"`.

#### 2. Required setting was never assigned

A person never writes `secret`. Quiet read is `nil`. Bang read fails. **After this work**, they can tell the name was never assigned (not that it was set to an empty string or `false`). They can go add the assignment rather than inspect values they never wrote.

#### 3. Required setting was assigned `nil`

A person writes `secret = nil` (or a child overrides a parent secret to `nil`). Quiet read is `nil`. Bang read fails. **After this work**, they can tell the name was assigned and the value is `nil`, and for a child they can tell it was a local override of a parent name when that is what happened.

#### 4. Required setting was assigned `false`

A person writes `allow_concurrency = false`. Quiet read is `false` (tests already treat this as a stored, falsey, non-missing value). Bang read fails today with `":allow_concurrency is blank"`. **After this work**, failure still occurs (compatibility: `false` is not a successful required read today), but they can tell the stored value is `false` rather than “missing” or “whitespace.” They do not waste time looking for an omitted assignment.

#### 5. Required setting was whitespace-only

A person writes `token = "   "` (or `"\t\n"`, or `"\u00a0"`). Quiet read returns that string. Bang read fails. **After this work**, they can tell the value is blank text rather than absent, so they look at ENV/YAML trimming rather than at a missing initializer.

#### 6. Counterexample — do not change successful present values

A person writes `timeout = 0` or `enabled = true`. Bang read continues to return `0` or `true`. These are successful required reads today and stay successful.

#### 7. Child override hides a good parent value

Parent has `foo = :bar`. Child writes `foo = nil` (or `false`, or `"  "`). Bang read on the child fails. **After this work**, they can tell the child overrode a parent name with an unusable value, rather than believing the parent never had `foo`.

#### 8. Illustrative: mixed string/symbol assignment does not shuffle order

Assign `one` via writer, `two` via symbol, `three` via string. Enumeration and `to_h` remain `one`, `two`, `three`. This journey exists only to pin the ordering compatibility boundary; it is not new product behavior.

### Acceptance evidence

Evidence that the outcome exists:

- A person who bang-reads a present setting still gets the identical value they get on today’s quiet/bang path, including inherited present values and present child overrides.
- Enumeration / `to_h` of mixed assignments still shows insertion order (and parent-then-child order with overrides).
- For each failing journey above (missing, `nil`, `false`, whitespace, inherited blank, child blank override), the required read still fails, and an observer who is not looking at assignment code can correctly say which of those situations it was.
- Quiet `missing`, `respond_to?(:anything)`, string/symbol lookup, and `dig` still behave as in the current tests.

Evidence that would contradict success:

- A bang read of a currently present value (`:bar`, `"ok"`, `true`, `0`, inherited present, present override) returns something else or raises.
- Order of names in `each` / `to_h` changes.
- `false` or `"   "` start succeeding as required reads.
- Missing quiet reads stop returning `nil`.
- Failures still occur but remain indistinguishable (same report for missing, `nil`, `false`, whitespace, and child override).
- A child with no own assignment stops seeing a present parent value on a required read.

Evidence that the problem framing is wrong (investigate, then revise or stop):

- People who use bang reads already get enough context from surrounding boot traces and do not use the error text at all.
- The real confusion is `false` being unusable as a required boolean, and clearer diagnosis without changing that rule still leaves them stuck.
- Callers depend on the exact `KeyError` / `is blank` pairing so thoroughly that any more specific report is treated as a breakage and they refuse the change.
- Required reads are rare next to quiet `nil` reads; the painful path is the silent missing reader, not the bang path.

Decisions those signals should trigger: continue if successful values and order hold and failed journeys become distinguishable; investigate if only the message changes but people still cannot tell missing from `false`; revise the outcome if `false`-as-failure is the actual product bug; stop if bang-read diagnosis is not where time is spent.

### Open questions

1. Must failed required reads keep raising `KeyError` with a message that includes `is blank`, because people rescue or match that today? Tests only assert `assert_raises(KeyError)` for `nil` and missing, not the message string ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L121-L125), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L134-L137)). Live behavior is `":name is blank"`. This brief treats “still fails on the same stimuli” as the compatibility floor and leaves bit-identical exception text as unresolved.

2. Is distinguishing `false` from missing enough, or do people also need `false` to become a successful required read (boolean flags)? Current behavior and this request’s “preserve successful return values” both keep `false` as a failure. If product intent is “required means assigned, including `false`,” that would be a different outcome and should replace journey 4.

3. How much inheritance context is enough: “this child overrode the name” versus naming the parent value that was hidden? The brief requires the person to tell override from inherited-blank from never-assigned; it does not require dumping the parent value.

4. Whitespace: is “blank text” enough, or must Unicode vs ASCII space be visible? Current `blank?` treats `"   "`, `"\t\n"`, and `"\u00a0"` the same. Distinguishing “blank text” from missing is the outcome; finer whitespace taxonomy is out of scope unless someone corrects this.
