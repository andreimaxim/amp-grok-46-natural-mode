## Temporary `ActiveSupport::Notifications.subscribed` observation — product shaping brief

This is a behavioral specification, not an implementation plan. It does not choose APIs, classes, data structures, algorithms, or code changes. Current-state claims are limited to this revision’s documentation and tests.

### Problem frame

**Actor:** Rails maintainers and application authors writing tests or short-lived diagnostics.

**Situation:** They need to see which notifications fire *while a specific piece of code runs*—a controller action, a query, a cache write, a failing instrumented block—then stop seeing them.

**Current pain:** Temporary observation already exists, but it is a second-class, easy-to-misuse path next to long-running `subscribe` / `unsubscribe`.

- The instrumentation docs present long-running `subscribe` as the main story. Temporary observation is a later API-comment section, absent from the user guide.
- Callers must bring their own callback and their own collector. The test suite itself repeats `events = []; callback = lambda { ... }; subscribed(callback, name) do ... end`.
- The API comments warn that subscribe/unsubscribe is for long-running listeners and “wipes some internal caches,” which discourages the exact test/diagnostic use.
- Matching, timestamps, nested events, payload mutation, and exceptions already have precise behavior, but a test author can still leak a listener, miss a nested child, or drop events from a raising block if they assemble observation by hand.

**Desired progress:** Temporary observation of matching events during a block should be the obvious, safe path for tests and diagnostics, with the same matching and event semantics people already rely on, and with no leftover listener afterward. Long-running `subscribe` / `unsubscribe` and existing callback arities stay as they are.

#### Matching

- A **string** pattern matches that event name only, not a similar name. During `subscribed(callback, "foo")`, instrumenting `"foo"` is observed and `"foofoo"` is not ([notifications.rb L172–L178](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L172-L178); [notifications_test.rb L226–L238](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L238)). Invalid pattern types are rejected (`ArgumentError`: pattern must be a String, Regexp, or empty) ([notifications.rb L306–L310](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L306-L310); [fanout.rb L91–L107](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L91-L107)).
- A **regexp** matches every name the pattern matches (`pattern === name`). Documented for `subscribe` ([notifications.rb L145–L151](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L145-L151); [guide L76–L81](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L76-L81)); implemented on the shared subscribe path ([fanout.rb L99–L103](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L99-L103), [L440–L448](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L440-L448)). There is **no** dedicated `subscribed(..., /regexp/)` test. Temporary regexp matching is evidenced through `capture_notifications(/post\./)` ([notification_assertions.rb L85–L87](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L85-L87); [notification_assertions_test.rb L92–L95](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L92-L95)) and through `subscribe(/\d/)` ([notifications_test.rb L444–L454](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L444-L454)).
- **No pattern** (`nil` / omitted) observes every event name during the block ([notifications.rb L152–L153](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L152-L153), [L332](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332); [notifications_test.rb L244–L256](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L256)).

#### Automatic unsubscription

`subscribed` installs the callback, runs the block, and always uninstalls afterward ([notifications.rb L155–L178](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L155-L178), [L332–L336](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L336)). After the block, the same event name is no longer delivered to that callback ([notifications_test.rb L239–L241](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L239-L241), [L257–L259](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L257-L259)). Docs warn this path is for occasional use because unsubscription clears internal caches ([notifications.rb L161–L163](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L161-L163)).

#### Timestamps

Default five-argument callbacks receive wall-clock `Time` for start and finish. `monotonic: true` receives monotonic `Float` instead ([notifications.rb L51–L71](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L51-L71), [L181–L190](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L181-L190); [guide L64–L73](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L64-L73); [notifications_test.rb L279–L313](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L313)). Default `monotonic:` is `false` ([notifications.rb L183–L184](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L183-L184), [L332](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332)).

#### Nested instrumentation and payload mutation

Nested `instrument` emits the **child before the parent**. After the inner block, only the child has been delivered; after the outer block, both have, parent last ([notifications_test.rb L486–L499](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L486-L499)). Mutations to the yielded payload, including nested hashes, are visible to subscribers ([notifications_test.rb L45–L51](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L51), [L76–L85](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L76-L85); instrumenter yields the same payload then finishes, [instrumenter.rb L81–L96](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/instrumenter.rb#L81-L96)). Guide: the notification is sent after the block, carrying the supplied payload ([guide L1078–L1087](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L1078-L1087)).

A nested *temporary* observer that is active only around `finish` of an already-started event does **not** receive that event; the outer temporary observer that was active at start and finish does ([notifications_test.rb L197–L221](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L221)).

#### Exceptions from the instrumented block

If the instrumented block raises, an event is still published, the payload gains `:exception` (`[class_name, message]`) and `:exception_object`, and the exception is re-raised ([notifications.rb L97–L107](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L97-L107); [guide L1068–L1076](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L1068-L1076); [instrumenter.rb L81–L96](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/instrumenter.rb#L81-L96); [notifications_test.rb L501–L514](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L501-L514)). `subscribed` uninstalls in `ensure` ([notifications.rb L332–L336](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L336)), so a raising block should not leave the temporary callback installed. **There is no dedicated test** that a raising block inside `subscribed` both delivers the annotated event and leaves no listener.

#### Callback arities (must be preserved)

A single-argument callback receives an `Event`. Otherwise the callback receives five arguments: `name, start, finish, id, payload` ([notifications.rb L38–L57](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L38-L157), [L278–L305](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L278-L305); [guide L31–L61](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L31-L61); arity selection [fanout.rb L368–L384](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L368-L384)). `subscribed` uses that same delivery ([notifications_test.rb L204–L208](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L204-L208) one-arg `Event`; [L279–L286](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L286) five-arg). Callables that respond to `call` are also accepted ([notifications.rb L112–L117](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L112-L117)).

#### Long-running `subscribe` / `unsubscribe` (must be preserved)

`subscribe` / `monotonic_subscribe` remain for process-lifetime listeners and return a subscriber that `unsubscribe` can remove by object or by name ([notifications.rb L191–L225](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L191-L225), [L312–L330](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L312-L330)). Unsubscribing by name does not remove unrelated listeners; regexp listeners keep other matching names ([notifications_test.rb L351–L394](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L351-L394)).

#### Test/diagnostic usage today

In-tree tests already wrap `subscribed` to collect events for a block ([notification_assertions.rb L85–L87](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L85-L87)), including string, regexp, and all-event capture ([notification_assertions_test.rb L83–L108](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L83-L108)). Other tests pass a lambda into `subscribed` for scoped probing. The instrumentation **guide does not document** `subscribed`.

### Maintainer / user pain

1. **Temporary observation is not the documented default for tests.** The guide teaches `subscribe` as if the listener lives for the process. A test author who follows the guide can leave a callback installed across examples.
2. **The scoped API is callback-first and collector-hostile.** `subscribe` takes a block; `subscribed` requires a prepared callable plus a second block for the work. Seeing “what fired during this call” means allocating an array and a lambda every time, which is why test helpers re-wrap it.
3. **The “use sparingly / cache wipe” warning fights the test use case.** Tests and one-off diagnostics are exactly short-lived. Maintainers are told the supported API is the wrong shape for them.
4. **Semantics are easy to get subtly wrong** when assembling observation by hand: exact vs regexp vs all; wall-clock vs monotonic; child-before-parent order; payload mutation; events from raising blocks; a nested observer that starts too late seeing nothing.

### Desired observable outcomes

These are claims about what a person can do or see. They are not a design.

1. **Block-scoped observation is the obvious path for tests and diagnostics.** A maintainer can say “while this code runs, show me matching notifications,” run the code, and inspect only those events.
2. **Observation ends when the block ends**, including when the block raises. Later instrumentation of the same names is not delivered to that observer. Other, long-running listeners are unaffected.
3. **Matching stays as today:** exact string, regexp, or every event.
4. **Timestamp choice stays as today:** wall-clock `Time` by default; monotonic `Float` when requested.
5. **Event content stays as today:** nested child-before-parent order; payload mutations (including nested hashes) visible; raising instrumented blocks still publish, annotate `:exception` / `:exception_object`, and re-raise.
6. **Callback shape stays as today:** one argument → `Event`; otherwise five arguments; `call`-able objects still work.
7. **Long-running `subscribe` / `unsubscribe` / `monotonic_subscribe` behave as they do now**, including unsubscribe-by-name vs regexp leftovers.
8. **Documentation treats temporary observation as a first-class test/diagnostic story**, with the same matching and exception facts the API comments already state, including regexp and all-event forms that `subscribed`’s own examples currently omit.

### Non-goals

- Changing long-running `subscribe`, `monotonic_subscribe`, or `unsubscribe`.
- Changing callback arities or `Event` vs five-argument delivery.
- Changing what counts as a match (string exactness, regexp `===`, nil = all).
- Changing wall-clock vs monotonic timestamp types or defaults.
- Changing nested emission order, payload mutation visibility, or exception payload keys.
- Making instrumentation a general-purpose message bus beyond current publish-after-block behavior.
- Prescribing performance work, cache policy, or new telemetry.
- Requiring every Rails hook in the guide to be re-documented.

### Compatibility constraints

- Existing one-arg and five-arg callbacks, including objects that implement `call`, must keep receiving the same shapes.
- Existing `subscribe` / `unsubscribe` / `monotonic_subscribe` call sites must keep their current observable behavior.
- String / regexp / omitted-pattern matching must not silently broaden or narrow.
- Default timestamps remain wall-clock `Time`; `monotonic: true` remains monotonic `Float`.
- Applications that mutate payloads inside `instrument` must still see those mutations in observers.
- A raising instrumented block must still publish, annotate, and re-raise.

### Representative examples

Required cases unless marked illustrative.

#### 1. Exact name, only during the block

A test instruments `"foo"`, `"foofoo"`, and `"foo"` inside `subscribed` for `"foo"`, then instruments `"foo"` again outside.

**Observes:** two `"foo"` events inside the block; not `"foofoo"`; nothing more after the block.

Grounded in [notifications_test.rb L226–L241](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L241).

#### 2. Regexp matching during the block

A diagnostic observes `/post\./` while the app instruments `"post.submitted"`.

**Observes:** that event. A name that does not match the regexp is omitted. After the block, further `"post.submitted"` events are not observed by this observer.

Grounded in [notification_assertions_test.rb L92–L95](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L92-L95) and [notifications_test.rb L444–L454](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L444-L454). *Open:* no direct `subscribed` regexp test.

#### 3. All events during the block

A diagnostic omits a pattern while `"foo"` and `"foofoo"` fire, then `"foo"` fires again afterward.

**Observes:** every name inside the block, in order; none after.

Grounded in [notifications_test.rb L244–L259](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L259).

#### 4. Wall-clock vs monotonic timestamps

Five-arg observer, default: `started` / `finished` are `Time`. Same observer with `monotonic: true`: both are `Float`. After the block, further events do not overwrite those captured classes.

Grounded in [notifications_test.rb L279–L313](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L313).

#### 5. Nested instrumentation and payload mutation

Outer `instrument("awesome", payload: "notifications")` wraps inner `instrument("wot", payload: "child")`. Separately, an instrumented block writes `payload[:my_key]` and `payload[:some_key][:key_two]`.

**Observes:** `"wot"` delivered first, then `"awesome"`; mutated keys visible to the observer, including nested hash values.

Grounded in [notifications_test.rb L45–L51](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L51), [L76–L85](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L76-L85), [L486–L499](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L486-L499).

#### 6. Nested temporary observers (boundary)

Outer `subscribed` starts an event handle, inner `subscribed` runs only around `finish`.

**Observes:** the outer observer receives the event; the inner one receives nothing.

Grounded in [notifications_test.rb L197–L221](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L221).

#### 7. Raising instrumented block

Inside temporary observation, `instrument` raises `RuntimeError "FAIL"`.

**Observes:** the exception still comes out to the caller; an event was still delivered; payload still has the original keys plus `:exception => ["RuntimeError", "FAIL"]` and `:exception_object` equal to the raised error; after rescue, further instrumentation is not delivered to the temporary observer.

Publish / annotate / re-raise is grounded in [notifications_test.rb L501–L514](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L501-L514). Cleanup after raise is implied by `ensure` ([notifications.rb L332–L336](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L336)), not by a dedicated `subscribed` test.

#### 8. Counterexample — long-running subscribe is untouched

A process-lifetime `subscribe("foo")` is already installed. A test uses temporary observation of `"foo"` and then returns.

**Observes:** the long-running listener still receives later `"foo"` events. Temporary observation must not be “fixed” in a way that unsubscribes by name and wipes that listener.

Grounded in unsubscribe-by-name vs leftover listeners ([notifications_test.rb L366–L372](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L366-L372)) and the preserve-`subscribe` constraint.

#### 9. Counterexample — arity is not collapsed (illustrative of the constraint)

A one-arg callback still receives `Event`. A five-arg callback still receives `name, start, finish, id, payload`. A usability improvement that only delivers `Event`, or that swaps argument order, is out of scope.

### Acceptance signals

**Success looks like:**

- A maintainer writing a test or a short diagnostic can observe matching events for one block of work without a leftover listener, without touching global `subscribe` / `unsubscribe`.
- Exact-name, regexp, and all-event scoping each work for that block-shaped use.
- Nested child-before-parent order, payload mutations, wall-clock vs monotonic timestamps, and raising-block publish/annotate/re-raise still match the examples above.
- Existing long-running subscribers keep receiving events after a temporary observation ends.
- One-arg and five-arg callbacks keep their current shapes.
- Someone following the instrumentation docs can find the temporary-observation story without reading only the `subscribed` method comment.

**Investigate / do not ship if:**

- Events from a temporary observation leak into later tests or later requests.
- A raising block is observed but the callback is still installed, or the event is dropped in order to “clean up.”
- Nested work reverses order or hides payload mutations.
- `subscribe` / `unsubscribe` callers report missing events or wiped regexp listeners.
- One-arg callbacks start receiving five arguments, or the reverse.

**Reconsider the problem framing if:**

- People still prefer hand-rolled `subscribe` + `unsubscribe` in tests because the scoped path is still awkward or still documented as “use sparingly.”
- The real pain was missing guide coverage only, and the API was already fine once discovered.
- The real pain was assertion helpers (`assert_notification` / `capture_notifications`) rather than `subscribed` itself.

### Open questions

- Is the primary user the author of Rails’ own tests, an application test author, or someone debugging production-like diagnostics? The in-tree helpers suggest tests; the API comments also describe one-off blocks.
- Should regexp temporary matching be treated as a required documented example of `subscribed`, given it is tested only through `capture_notifications` / `subscribe`?
- Must a raising *work* block (not only a raising `instrument` block) leave no listener? Implementation uses `ensure`; no test says so.
- Is “use sparingly because it wipes caches” still a user-facing warning for tests, or is that an internal performance note that currently undermines the desired story? This brief does not decide cache behavior.
