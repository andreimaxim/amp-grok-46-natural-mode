Observed conversion and update on mixed `:key`/`"key"` input. Drafting the shaping brief from that behavior, without an implementation design.

**Problem frame:** An application author ingests nested configuration or options through indifferent-access conversion or update. Today, a single source that contains both `:key` and `"key"` is collapsed to one entry; which value remains is unspecified; nested collisions can drop an entire inner hash; and nothing in the result shows that input was discarded. They cannot tell a bad mixed-key source from a successful ingest.

This is distinct from the intended product of indifferent access: treating `:timeout` and `"timeout"` as the same lookup key when overlaying YAML/JSON string keys onto Ruby symbol defaults.

---

### Current observable behavior

Evidence: public `update` contract (“only one of the values end up in the receiver, but which one is unspecified”) plus direct conversion/update of mixed, nested, and multi-hash inputs. The published guides only show the happy path (`{ a: 1 }.with_indifferent_access["a"] # => 1`). Tests exercise mixed *distinct* keys (`:a` and `"b"`), not colliding pairs.

**Conversion of one mixed hash** keeps a single string key. In these runs, the later pair in hash iteration order won; that order is not part of the public contract.

- `{ :key => "symbol-value", "key" => "string-value" }` → `{ "key" => "string-value" }`
- `{ "key" => "string-value", :key => "symbol-value" }` → `{ "key" => "symbol-value" }`

After conversion, `[:key]` and `["key"]` both return the survivor. The original hash is unchanged. Key count drops with no other signal (`5` pairs → `3` keys when two colliding pairs and one unique key are converted).

**Equal values still collapse.** `{ :key => "same", "key" => "same" }` → `{ "key" => "same" }`. There is no value loss, but the duplicate key form is gone and still unannounced.

**Non-string/symbol keys stay distinct.** `{ 1 => "int", "1" => "str", :"1" => "sym" }` → `{ 1 => "int", "1" => "sym" }`. `"1"` and `:"1"` collide; integer `1` does not.

**Nested collision at the outer key discards a whole subtree.**

```
{ :db => { :adapter => "postgres", "adapter" => "mysql" }, "db" => { host: "localhost" } }
→ { "db" => { "host" => "localhost" } }
```

The entire `:db` tree (including its own inner collision) is gone. Deep outer collision is the same: mixed `:env` / `"env"` left only the later `"env"` subtree.

**Hashes inside arrays collapse the same way.**

```
{ items: [ { :id => 1, "id" => 2 }, { "name" => "a", :name => "b" } ] }
→ { "items" => [ { "id" => 2 }, { "name" => "b" } ] }
```

**Update / merge of a regular hash that itself contains both forms** is the documented unspecified-winner case. `update({ :key => "from-symbol", "key" => "from-string" })` kept `"from-string"` in this run.

**Sequential multi-hash update is different:** later hash wins under ordinary overlay rules.

```
{}.update({ timeout: 5 }, { "timeout" => 10 })  →  { "timeout" => 10 }
```

That is specified merge order, not the unspecified same-hash collapse. Intentional overlay of string-key YAML onto symbol-key defaults behaves this way and is the useful indifferent-access case:

```
{ timeout: 30, retries: 0, pool: 5 }.merge({ "timeout" => 5, "retries" => 3 })
→ { "timeout" => 5, "retries" => 3, "pool" => 5 }
```

**Boundaries that are not this problem:** indifferent lookup when only one form exists; preserving non-colliding neighbors (`:b`, `"c"`); leaving the source hash unmutated.

---

### User pain

The author cannot distinguish “ingest succeeded” from “a colliding pair was dropped.” The surviving value can be the opposite of what they meant, and it can change if insertion order changes. Nested outer collisions look like a missing section, not a key clash. Debugging presents as “the wrong adapter/host/timeout is active” with no leftover sibling to inspect.

---

### Desired behavioral outcomes

Stated only as far as the request allows; the mechanism is an open product question.

1. **Detect discarded mixed-key input.** When conversion or update collapses `:key` and `"key"` from one source, the author can tell that data was discarded—not only that a single value remains.
2. **Nested and in-array collisions are visible too.** A clash inside a nested hash, or inside a hash in an array, is observable in the same sense as a top-level clash. An outer-key clash that drops a whole subtree is observable as discarded data, not as a quiet smaller tree.
3. **Intentional overlay stays overlay.** Merging a string-key hash and a symbol-key hash as two sources still means later-wins (or block) indifferent merge. That is not discarded data.
4. **No-collision ingest is unchanged.** Sources with only one form per logical key, plus non-string keys, keep today’s result.

### Examples

**Core (silent loss today).**  
Situation: one config hash has `timeout: 30` and `"timeout" => 5`.  
Action: convert or update through indifferent access.  
Today: `{ "timeout" => 5 }` (or `30`, unspecified); no signal.  
Desired: the author can tell a value was discarded. Whether ingest still returns a hash is open (error vs observation).

**Nested subtree drop.**  
Situation: `{ :db => { adapter: "postgres" }, "db" => { host: "localhost" } }`.  
Today: `{ "db" => { "host" => "localhost" } }`; postgres config is gone.  
Desired: discarded `db` data is detectable, including that a whole section disappeared.

**Nested inner collision.**  
Situation: `{ db: { :adapter => "postgres", "adapter" => "mysql" } }` with a unique outer key.  
Today: `{ "db" => { "adapter" => "mysql" } }` in this run.  
Desired: the inner clash is detectable even when the outer key did not collide.

**Array of hashes.**  
Situation: `items: [{ :id => 1, "id" => 2 }]`.  
Today: `[{ "id" => 2 }]`.  
Desired: same detectability as a top-level clash.

**Multi-hash overlay (counterexample — keep).**  
Situation: defaults `{ timeout: 30 }` then file `{ "timeout" => 5 }` as two hashes.  
Today and desired: `{ "timeout" => 5 }`. This is overlay, not undetectable discard.

**Multi-hash where one argument is itself mixed.**  
Situation: `update({ :key => "from-symbol", "key" => "from-string" })`.  
Today: one survivor, unspecified which.  
Desired: discarded member of that argument is detectable. Sequential update of two *separate* single-form hashes remains overlay.

**Equal values.**  
Situation: both forms hold `"same"`.  
Today: one key, no signal.  
Open whether this counts as discarded data (value-identical vs key-form loss).

**Non-collision (counterexample — keep).**  
`{ :a => 1, "b" => 2 }` still becomes `{ "a" => 1, "b" => 2 }` with no new signal.

### Compatibility constraints

- Indifferent lookup and two-source string/symbol overlay are existing public behavior and must remain available.
- Unspecified winner on same-hash `:key`/`"key"` is currently documented for `update`. Making collapse noisy or fatal by default would change apps that already ingest mixed hashes and happen to keep the value they want.
- Conversion does not mutate the source hash; that should stay true.
- Integer and other non-string/symbol keys must not start colliding with string keys (`1` vs `"1"`).
- A later hash in `update(h1, h2)` overwriting an earlier indifferent key is specified overlay, not the bug.

These bound the outcome: detection of same-source collapse must not be bought by breaking indifferent overlay or by changing no-collision results.

---

### Success signals

Success looks like: an author who feeds a mixed-key source can tell that something was discarded; nested and in-array cases are included; two-source YAML-over-Ruby overlay still produces the overlay result; no-collision hashes look as they do now.

**Investigate or stop if:**

- People only notice mixed keys in toy top-level hashes, while nested config still fails silently.
- Detection fires on intentional two-source overlay (`timeout:` then `"timeout"` from YAML), so normal config loading becomes unusable.
- Apps with no mixed keys see new failures or new required steps.
- Authors still cannot tell *which* logical key was involved (if key disclosure is later required).
- Teams ignore the signal because it is too noisy, or cannot use it because it is too expensive on large nested hashes.

**Framing is wrong if** the real incidents are almost all two-source overlays with surprising last-wins, not same-source `:key`+`"key"` pairs. Then the work would be about merge policy, not discarded-data detection.

---

### Open questions

**Opt-in behavior.** Is detection always on, off unless requested, or chosen per conversion/update? Always-on would surface collisions that today’s apps silently accept; opt-in would leave default ingest unable to see discarded data.

**Error versus observation.** Should mixed-key collapse refuse the ingest, or still return a hash and also report the loss? Error prevents running on ambiguous config; observation preserves today’s result shape so callers can log and continue. Equal-value pairs may deserve a different answer than disagreeing values.

**Key disclosure.** If anything is reported, does it name the logical key, nested path (`env.production.host`), both original key forms, both values, or only that “a collision occurred”? Disclosure helps debug nested subtree drops; it may leak config values.

**Performance.** Collision detection on every conversion of large nested option trees may be noticeable. Whether that cost is acceptable for default ingest, only for an opt-in path, or only above some size is unresolved. This brief does not choose a strategy.

**Also unresolved:** whether value-identical mixed keys count as discarded data; whether `merge`, `deep_merge`, constructors, and `update` must all be in the first outcome or only conversion + `update`.

---

This is a working shaping brief, not an implementation design: no API, flag, or error type is chosen. The product gap is undetectable same-source collapse; overlay of two single-form hashes is not that gap. The four named questions have to be settled before sketching a solution.
