## Product shaping brief: required configuration reads through `ActiveSupport::OrderedOptions`

This is a product-shaping brief, not an implementation design. It describes current observable behavior, the pain of required reads, desired outcomes, and how we would know the work succeeded. It does not propose classes, methods, storage, or implementation mechanics.

Evidence for current behavior comes from [activesupport/lib/active_support/ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb), [activesupport/test/ordered_options_test.rb](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb), [activesupport/lib/active_support/core_ext/object/blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb), and a live reproduction of bang-reader cases the tests do not cover (`false`, whitespace-only strings, inherited blank overrides).

---

### Problem frame

**Actor:** A Rails application or library author who stores settings in `ActiveSupport::OrderedOptions` or `ActiveSupport::InheritableOptions` (typical surfaces: `Rails.application.config`, railtie config hashes, encrypted configuration values) and later reads a setting that must actually be there.

**Situation:** Assignment and lookup already work as a Hash with dynamic accessors. When a setting is required, the person uses a bang read (documented as “raise when the value is blank”) so boot or runtime fails instead of silently continuing with `nil`.

**Current pain:** A failed required read is hard to understand and hard to diagnose. Every failing bang read raises the same `KeyError` with the same `":name is blank"` text, whether the name was never assigned, assigned `nil`, assigned `false`, assigned a whitespace-only string, inherited as blank from a parent, or overridden to blank on a child. Quiet reads of missing names return `nil`, and `respond_to?` affirms every name, so the person cannot tell from ordinary lookup whether a required setting was omitted or merely empty. The failure does not identify which of those cases occurred, and it does not point at inheritance versus a local override.

**Desired progress:** Required reads that succeed keep returning exactly the values they return today, in the same Hash-like order. Required reads that fail become understandable: the person can tell that a required setting was not usable and can distinguish the situation that caused the failure well enough to fix the configuration, including across parent/child option sets.

---

### Current observable behavior

#### Symbol and string assignment and lookup

`OrderedOptions` stores under symbol keys. Assigning with a string or a symbol, or with a dynamic writer, all land on the same symbol key. Lookup with `[]`, a dynamic reader, or `dig` accepts either a string or a symbol and returns the same value.

Documented and tested:

- `a[:allow_concurrency] = true` then `a[:allow_concurrency]` is true; later assigning `false` keeps size 1 and the lookup is false ([ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L11-L17), [ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L38-L44), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L11-L27)).
- `a["else_where"] = 56` then `a[:else_where]` is `56` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L24-L26)).
- Dynamic writers match: `a.else_where = 56` then `a.else_where` is `56` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L62-L77)).
- Unset lookup is `nil`: `a[:not_set]` and `a.not_set` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L14), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L65)).

`key?` does **not** treat strings and symbols as equivalent. After `object.one = ...`, `object[:two] = ...`, and `object["three"] = ...`, `key?(:one)`, `key?(:two)`, and `key?(:three)` are true, but `key?("one")`, `key?("two")`, and `key?("three")` are false ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L228-L239)). The same split holds for `InheritableOptions` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L243-L254)).

Iteration and `to_h` use insertion order of the symbol keys. Mixed symbol/string/writer assignment of `one`, `two`, `three` yields `{ one:, two:, three: }` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L29-L41), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L161-L168)).

#### Dynamic readers, writers, `respond_to?`, and `dig`

Any name is treated as a reader, writer, or bang reader. `respond_to?` is true for names that have never been assigned, including writers and bang names ([ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L48-L64), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L106-L111)): `assert_respond_to a, :blah`, `assert_respond_to a, :blah=`, and `a.method(:blah=).call(42)` then `a.method(:blah).call` returns `42`. Bang names also respond: `assert_respond_to a, :foo!` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L117)).

`dig` symbolizes only the first identifier. `a[:test_key] = 56` then `a.test_key`, `a["test_key"]`, `a.dig(:test_key)`, and `a.dig("test_key")` are all `56` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L43-L51)). Nested `a.dig(:test_key, 0, :a)` walks into the stored value; a missing nested step returns `nil` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L53-L59)).

#### Missing dynamic reader

A reader for a name that was never assigned returns `nil` and does not raise ([ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L26), [ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L55-L57), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L65)). This is the quiet path. It is what a person sees when they forget the bang on a required setting.

#### Bang readers when the value is missing or blank

A bang read returns the stored value when that value is present. Otherwise it raises `KeyError` with message `":#{name} is blank"` ([ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L28-L31), [ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L52-L54)). “Present” here is Active Support `presence`: the value is returned only if it is not blank; otherwise the error is raised ([blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L6-L9), [blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L56-L58)).

| Stimulus | Quiet reader | Bang reader | Test coverage |
| --- | --- | --- | --- |
| Name never assigned | `nil` | `KeyError: :name is blank` | Yes ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L124-L125)) |
| Assigned `nil` | `nil` | `KeyError: :name is blank` | Yes ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L121-L123)) |
| Assigned `false` | `false` | `KeyError: :name is blank` | Not in tests; live reproduction |
| Assigned `""`, `"   "`, `"\t\n"`, or `"\u00a0"` | that string | `KeyError: :name is blank` | Not in tests; live reproduction (`String#blank?` in [blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L180-L206)) |
| Assigned a present value (`true`, `0`, `:bar`, `"ok"`) | that value | that same value | Yes for `:bar` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L114-L119)); `true` / `0` / non-blank string confirmed live |

`false` is blank ([blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L75-L86)). `0` is not blank ([blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L209-L221)). Empty collections are blank; that path is unused in the tests.

Successful bang reads return the same object as the quiet reader: `assert_equal a.foo, a.foo!` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L119)).

The error text is always `":name is blank"`. It does not say the name was missing, was `nil`, was `false`, or was whitespace. It does not include the actual value.

#### Inherited values and child overrides (`InheritableOptions`)

A child built from a parent continues lookup in the parent. `parent[:foo] = true` then `child.foo` is true ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L79-L85)). A child assignment hides the parent for that name: `parent[:foo] = :bar`, `child[:foo] = :baz`, then `child.foo` is `:baz` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L87-L94)).

`to_h`, `keys`, `each`, and `to_a` present parent names first, then child-only names, with child values replacing parent values for overridden names ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L171-L178), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L257-L262), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L289-L310)). `overridden?(key)` is true only when the parent has the name **and** the child has its own assignment, including when the child assigned via a string key ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L265-L275)). A child assignment with no parent name is not an override ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L278-L286)).

Bang reads follow the same lookup:

- Present parent value: `InheritableOptions.new(foo: :bar)` then `a.foo!` equals `a.foo` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L129-L132)).
- Child sets the name to `nil`: bang raises `KeyError` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L134-L136)).
- Name absent from parent and child: bang raises `KeyError` ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L137)).

Live reproduction, not in tests:

- Present parent value, no child assignment: bang returns the parent value.
- Child overrides with a present value: bang returns the child value.
- Child overrides a present parent value with `nil`, `false`, or `"  "`: bang raises `KeyError: :name is blank` — same text as a missing name.
- Parent value is `false`, child does not override: bang raises that same `KeyError`.

A person cannot tell from the error whether the blank came from the parent, from a child override, or from the name never being assigned at all.

#### Feedback channels that exist today

- Quiet reader / `[]` / `dig`: value or `nil`. Cannot distinguish unset from `nil`.
- `key?` (symbol only): whether that symbol is an own key (and, on `InheritableOptions`, a parent key). String queries are always false in tests.
- `overridden?`: whether a child hid a parent name.
- Bang reader: either the present value or `KeyError` with a single message.
- `inspect` / `to_h` / `keys`: dump of contents, including inherited names on `InheritableOptions`. Useful after the fact; not what a failed bang read itself reports.

### User pain (restated as experience)

When boot or a library insists on a required setting via a bang read, failure looks the same in every unusable case. The person has to reconstruct by hand: Was the name never written? Was it written as `nil`? As `false` (a plausible boolean setting)? As spaces from YAML or ENV? Did a child override wipe a good parent value? The quiet reader will not tell them; `respond_to?` will not tell them; the error text will not tell them. Diagnosis is a search through assignment sites and parent/child option sets, not an answer at the point of the required read.

This matters because these objects are how Rails configuration is actually held (`config.active_record`, `config.action_mailer`, custom `config.x.*` hashes, encrypted credentials, and similar). Required reads happen late (boot, first use, credentials access). A generic “is blank” failure at that moment is expensive to map back to the write that caused it.

---

### Desired outcomes

These are externally observable claims. They do not name APIs, classes, or storage.

1. **Successful required reads stay successful and return the same values they return today.** If a bang read currently returns a value, it still returns that same value. Insertion order of names, mixed string/symbol assignment, `to_h` / iteration order, parent-then-child presentation, and child overrides of present values remain as they are.

2. **A required read that cannot be used fails in a way a person can understand.** The failure still happens for the cases that fail today (never assigned, `nil`, `false`, whitespace-only / empty strings, inherited blank, child override to blank). The person can tell from the failure that the required setting was not usable.

3. **A person can diagnose which situation caused the failure without reconstructing assignment history from scratch.** At the point of failure they can distinguish at least: never assigned vs assigned-but-unusable, and for inheritable sets, inherited unusable value vs local override that made a parent value unusable. They can tell `false` and whitespace apart from “missing” well enough to fix the right write.

4. **Quiet reads, `respond_to?`, `dig`, and Hash-like lookup do not become a second, incompatible configuration language.** Missing quiet readers still return `nil`. String and symbol assignment/lookup still resolve to the same stored name. `dig` still symbolizes the first identifier and walks nested values. `respond_to?` still reports the dynamic readers, writers, and bang names people already rely on.

5. **Inherited present values remain visible to required reads until a child actually overrides them.** A child that does not write a name still sees the parent’s present value on a required read. A child present override is what a required read returns.

---

### Non-goals

- Changing which present values a required read returns, or the Hash-like insertion / parent-then-child ordering of names.
- Making quiet reads raise, or making missing names stop returning `nil` on the non-bang path.
- Making `respond_to?` start returning false for unassigned names.
- Making `key?("string")` become true (current tests assert it is false).
- Replacing `OrderedOptions` as the holder of Rails config, credentials, or railtie settings.
- Broader configuration validation, schema, type checking, or a new settings product.
- Changing `blank?` / `presence` for Ruby objects in general.
- Teaching people a new way to assign or look up keys that already succeed.

---

### Compatibility boundaries

Preserve:

- Return values of successful `[]`, dynamic readers, `dig`, and bang reads (including `true`, `0`, non-blank strings, symbols, and other present objects).
- Symbol storage with string-or-symbol assignment and lookup for those successful paths.
- Insertion-order enumeration on `OrderedOptions`; parent keys then child-only keys, with child values winning, on `InheritableOptions`.
- Quiet missing reads returning `nil`.
- `respond_to?` being true for arbitrary reader, writer, and bang names.
- Child override of a present parent value remaining the value a required read returns.
- Failure still occurring for the unusable cases listed above (do not start treating `false` or whitespace as a successful required read).

Do not require:

- A particular exception class, message string, or backtrace shape beyond “a person can understand and diagnose the failure.” Today it is `KeyError` with `":name is blank"`; a compatible outcome may keep raising on the same stimuli while making the report more specific.
- `key?` with string arguments to change.
- Any new name, method, or object type in the public surface — this brief does not add any.

Hypothesis, labeled as such: callers may rescue `KeyError` and match `/is blank/`. Tightening diagnosis should not silently stop failing those stimuli; whether the exact class and substring must stay bit-identical is an open compatibility question (see below).

### Example journeys

Required cases unless marked illustrative.

#### 1. Required setting is present — unchanged success

A person assigns `host = "api.example.com"` (symbol, string, or writer; all equivalent today). They require it with a bang read. They observe `"api.example.com"`, the same object the quiet reader would return. Order of other names is unchanged.

Same journey with inherited config: parent has `host = "api.example.com"`, child does not write `host`. Bang read on the child returns `"api.example.com"`.

Same journey with override: parent has `host = "api.example.com"`, child writes `host = "staging.example.com"`. Bang read on the child returns `"staging.example.com"`.

#### 2. Required setting was never assigned

A person never writes `secret`. Quiet read is `nil`. Bang read fails. **After this work**, they can tell the name was never assigned (not that it was set to an empty string or `false`). They can go add the assignment rather than inspect values they never wrote.

#### 3. Required setting was assigned `nil`

A person writes `secret = nil` (or a child overrides a parent secret to `nil`). Quiet read is `nil`. Bang read fails. **After this work**, they can tell the name was assigned and the value is `nil`, and for a child they can tell it was a local override of a parent name when that is what happened.

#### 4. Required setting was assigned `false`

A person writes `allow_concurrency = false`. Quiet read is `false` (tests already treat this as a stored, falsey, non-missing value). Bang read fails today with `":allow_concurrency is blank"`. **After this work**, failure still occurs (compatibility: `false` is not a successful required read today), but they can tell the stored value is `false` rather than “missing” or “whitespace.” They do not waste time looking for an omitted assignment.

#### 5. Required setting was whitespace-only

A person writes `token = "   "` (or `"\t\n"`, or `"\u00a0"`). Quiet read returns that string. Bang read fails. **After this work**, they can tell the value is blank text rather than absent, so they look at ENV/YAML trimming rather than at a missing initializer.

#### 6. Counterexample — do not change successful present values

A person writes `timeout = 0` or `enabled = true`. Bang read continues to return `0` or `true`. These are successful required reads today and stay successful.

#### 7. Child override hides a good parent value

Parent has `foo = :bar`. Child writes `foo = nil` (or `false`, or `"  "`). Bang read on the child fails. **After this work**, they can tell the child overrode a parent name with an unusable value, rather than believing the parent never had `foo`.

#### 8. Illustrative: mixed string/symbol assignment does not shuffle order

Assign `one` via writer, `two` via symbol, `three` via string. Enumeration and `to_h` remain `one`, `two`, `three`. This journey exists only to pin the ordering compatibility boundary; it is not new product behavior.

### Acceptance evidence

Evidence that the outcome exists:

- A person who bang-reads a present setting still gets the identical value they get on today’s quiet/bang path, including inherited present values and present child overrides.
- Enumeration / `to_h` of mixed assignments still shows insertion order (and parent-then-child order with overrides).
- For each failing journey above (missing, `nil`, `false`, whitespace, inherited blank, child blank override), the required read still fails, and an observer who is not looking at assignment code can correctly say which of those situations it was.
- Quiet `missing`, `respond_to?(:anything)`, string/symbol lookup, and `dig` still behave as in the current tests.

Evidence that would contradict success:

- A bang read of a currently present value (`:bar`, `"ok"`, `true`, `0`, inherited present, present override) returns something else or raises.
- Order of names in `each` / `to_h` changes.
- `false` or `"   "` start succeeding as required reads.
- Missing quiet reads stop returning `nil`.
- Failures still occur but remain indistinguishable (same report for missing, `nil`, `false`, whitespace, and child override).
- A child with no own assignment stops seeing a present parent value on a required read.

Evidence that the problem framing is wrong (investigate, then revise or stop):

- People who use bang reads already get enough context from surrounding boot traces and do not use the error text at all.
- The real confusion is `false` being unusable as a required boolean, and clearer diagnosis without changing that rule still leaves them stuck.
- Callers depend on the exact `KeyError` / `is blank` pairing so thoroughly that any more specific report is treated as a breakage and they refuse the change.
- Required reads are rare next to quiet `nil` reads; the painful path is the silent missing reader, not the bang path.

Decisions those signals should trigger: continue if successful values and order hold and failed journeys become distinguishable; investigate if only the message changes but people still cannot tell missing from `false`; revise the outcome if `false`-as-failure is the actual product bug; stop if bang-read diagnosis is not where time is spent.

### Open questions

1. Must failed required reads keep raising `KeyError` with a message that includes `is blank`, because people rescue or match that today? Tests only assert `assert_raises(KeyError)` for `nil` and missing, not the message string ([test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L121-L125), [test](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L134-L137)). Live behavior is `":name is blank"`. This brief treats “still fails on the same stimuli” as the compatibility floor and leaves bit-identical exception text as unresolved.

2. Is distinguishing `false` from missing enough, or do people also need `false` to become a successful required read (boolean flags)? Current behavior and this request’s “preserve successful return values” both keep `false` as a failure. If product intent is “required means assigned, including `false`,” that would be a different outcome and should replace journey 4.

3. How much inheritance context is enough: “this child overrode the name” versus naming the parent value that was hidden? The brief requires the person to tell override from inherited-blank from never-assigned; it does not require dumping the parent value.

4. Whitespace: is “blank text” enough, or must Unicode vs ASCII space be visible? Current `blank?` treats `"   "`, `"\t\n"`, and `"\u00a0"` the same. Distinguishing “blank text” from missing is the outcome; finer whitespace taxonomy is out of scope unless someone corrects this.
