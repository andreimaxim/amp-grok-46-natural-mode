I have enough from the callback terminator, `performed?`, render/redirect, DoubleRenderError, and filter/logging tests to draft the brief without proposing a design.

## Shaping brief: clearer observability when an Action Controller callback chain stops because a callback performed a response

This is a **discovery** brief for maintainers, with a possible later **new capability** if they decide observers still cannot tell intentional halt from confusing control flow. It is not a commitment to change behavior, logs, notifications, or APIs.

Discovery basis: current `before_action` / `around_action` / `after_action` docs and tests, the process-action terminator that consults `performed?`, rendering and redirecting, `AbstractController::DoubleRenderError`, the existing halt hook/log/event, and the Action Controller overview plus instrumentation guide. Those establish today’s stimuli, outcomes, boundaries, and feedback channels. They do not by themselves prove that current signals are insufficient for every audience.

---

**Problem frame:** An application developer or maintainer is looking at a request whose controller action did not run, or that failed after a response was already prepared. They need to know whether a callback intentionally finished the request, whether inner work was skipped for another reason, or whether ordinary Ruby execution continued after a render/redirect and then collided with a second response. Today those cases do not share one readable story: a rendering or redirecting `before_action` can complete the request and emit a halt line, a non-yielding `around_action` can skip the action without that halt line, a conditional callback can simply never run, and a second render raises. That mix makes it easy to misread a successful short-circuit as a bug, or a continued-after-render bug as “the filter chain halted.”

**Hypothesis, not a user-supplied metric:** the pain is diagnostic, not missing HTTP behavior. The chain already stops when a before callback has performed a response. What is uneven is whether an external observer can tell *why*.

---

### Affected actors

- **Application developers** writing authentication, authorization, redirects, and wrapping callbacks, then debugging why an action, later before callback, or `after_action` did not run.
- **Operators / support** reading request logs or events for a 200, 302, 404, or empty-looking response and deciding whether that was intended.
- **Library and Rails maintainers** deciding whether a report is app control flow, framework halt policy, or a double-render mistake.
- **Instrumentation subscribers** that already see `process_action`, redirect, and halt events and must infer meaning from a small payload.

End users of the app are only indirectly affected: they already receive whatever response the callback or error handling produced.

---

### Current observable baseline

Established from the sources above:

1. **A before callback that renders, redirects, or otherwise leaves `performed?` true stops the rest of the process-action chain.** Remaining before/around work and the action do not run. After callbacks, including prepended ones, are skipped. The client gets that callback’s response (rendered body, redirect, or `head`).
2. **`performed?` means a response body is set or the response is committed.** That is the halt condition. Rendering, redirecting, `head`, and assigning a response all count. The public docs and the halt log phrase this as “renders or redirects,” which is narrower than the actual condition.
3. **Render and redirect do not return from ordinary Ruby.** Inside an action (or any callback that keeps running), a second `render`, `redirect_to`, or `head` raises `AbstractController::DoubleRenderError`. The error text itself tells the reader that neither render nor redirect terminates execution and that a `return` is needed to leave an action.
4. **A halt from a before callback is already externally visible**, when it happens:
   - HTTP response from that callback
   - info log: `Filter chain halted as :filter_name rendered or redirected`
   - notification `halted_callback.action_controller` with only `:filter`
   - structured event `action_controller.callback_halted` with that filter name
5. **That halt signal is tied to the before-callback terminator, not to every way inner work is skipped.** Tests pin the log for a redirecting before callback. They do not pin an equivalent line for a non-yielding around callback.
6. **A non-yielding around callback does not raise.** Earlier befores run; later befores, the action, and afters do not. Tests do not treat this as a performed-response halt and do not assert a particular response body.
7. **Exceptions in an around callback are errors, not halt-because-performed.** Raise before yield: action does not run. Raise after yield: action has already run. Guide text: `after_action` does not run if the request cycle raised; code after `yield` runs on exception only if the around callback uses `ensure`.
8. **Conditional callbacks (`only` / `except` / `if` / `unless`, and skips) either run or they don’t.** A skipped callback cannot halt. Combined options have documented precedence (`only` over `if`; `if` over `except`). Absence of a callback’s side effects is the only usual signal that it was skipped.
9. **Successful halt still does other request work that is not the action** (for example flash set in a redirecting before callback is still there on the next request). Halt means “action and remaining callbacks cancelled,” not “the request was abandoned.”

---

### Desired outcomes

These are outcomes maintainers would use to judge whether observability is clear enough. They do not require a particular log line, event, API, metric, or implementation.

1. **An observer can tell a performed-response halt from a completed action.** When a before callback renders or redirects, it is visible that the action did not run *because that callback already performed a response*, and that later callbacks were cancelled on purpose.
2. **An observer can tell a performed-response halt from a double-render failure.** Continuing after a render/redirect and attempting a second response remains a distinct failure, not a successful short-circuit.
3. **An observer can tell “inner chain never entered” from “inner chain halted after a response.”** A non-yielding around callback and a rendering before callback should not look like the same story unless maintainers later decide they should.
4. **An observer can tell “callback did not run” from “callback ran and halted.”** Conditional skip and performed-response halt remain different.
5. **Exceptions before and after yield remain errors**, not silent equivalents of halt-because-performed.
6. **Existing halt, redirect, and completion signals stay interpretable.** Any clearer story should not make today’s `Filter chain halted as … rendered or redirected` line, halt event, or `DoubleRenderError` message untrue.

---

### Explicit non-goals

- Changing when the chain stops, what `performed?` means, or whether after callbacks are skipped after halt.
- Making `render` / `redirect_to` / `head` return from an action, or removing `DoubleRenderError`.
- Requiring a new log, notification, structured event, public API, dashboard, or config flag.
- Making every skipped or conditional callback emit a signal.
- Redesigning `before_action` / `around_action` / `after_action` registration.
- Treating production performance or log volume as settled constraints (they are open questions).
- Fixing app-level “forgot to `return` after redirect” as if it were a framework halt bug.

---

### Behavioral examples

Required cases for agreement. “Observer” means anyone using today’s external channels (HTTP response, logs/events, exception). No new mechanism is implied.

#### 1. Rendering before callback (intentional halt)

**Situation:** A controller has a `before_action` that renders a body, then an action that would render something else, plus an `after_action` (and, as a boundary, a prepended `after_action`).

**When:** The action is requested.

**Observable result today:** The client receives the before callback’s body, not the action’s. The action did not run. Neither after callback ran. A halt log/event names that before callback and says it rendered or redirected.

**What clearer observability would mean:** That result is readable as “this callback finished the request,” not as “the action failed to run” or “after callbacks are broken.”

#### 2. Redirecting before callback (intentional halt)

**Situation:** A `before_action` redirects to another action; the original action and after callbacks exist.

**When:** The original action is requested.

**Observable result today:** Redirect response to the target URL. Original action and after callbacks do not run. Halt log/event names the redirecting callback. Following the redirect is a new request. Side effects such as flash from the halting callback can still be present on that next request.

**What clearer observability would mean:** The redirect is attributable to the callback that halted, and is not confused with the action having run or with `DoubleRenderError`.

#### 3. Non-yielding around callback (skip without performed-response halt)

**Situation:** A before callback, then an around callback that does not yield, then a later before, the action, and an after.

**When:** The action is requested.

**Observable result today:** No exception. The first before and the around callback run. Later before, action, and after do not. Tests do not expect the “Filter chain halted as … rendered or redirected” line.

**What clearer observability would mean:** An observer can see that the inner chain was not entered because the around callback did not yield, and can distinguish that from a before callback that rendered or redirected.

#### 4. Exception before yield (error, action never runs)

**Situation:** An around callback raises before yielding.

**When:** The wrapped action is requested.

**Observable result today:** That exception is raised. The action does not run. This is not a performed-response halt.

**What clearer observability would mean:** This remains classified as an error before the action, not as “filter chain halted as rendered or redirected.”

#### 5. Exception after yield (error, action already ran)

**Situation:** An around callback yields, then raises.

**When:** The wrapped action is requested.

**Observable result today:** The action has already run (and typically has rendered). The exception then propagates. After-yield code without `ensure` does not run if the action itself raised; `after_action` is not described as running on an exception in the request cycle.

**What clearer observability would mean:** This remains “action ran, then the around callback failed,” not a halt-because-performed and not the same as raising before yield.

#### 6. Conditional callbacks (never ran, so cannot halt)

**Situation:** A before callback is limited with `only`, `except`, `if`, or `unless`, or skipped. On a matching action it would render or redirect; on a non-matching action it would not run.

**When:** Both a matching and a non-matching action are requested.

**Observable result today:** On match, the callback runs and, if it performs a response, halt behaves as in examples 1–2. On non-match, the callback’s side effects are absent and the action runs. A false `if` means the callback does not run even if listed. Documented precedence: `only` wins over `if`; `if` wins over `except`.

**What clearer observability would mean:** “Did not run because of a condition” is not presented as a halt, and a halt still names a callback that actually ran.

#### 7. Action that attempts a second render (confusing control flow, not halt)

**Situation:** An action renders, then renders again (or renders then `head`). No before callback halted the chain.

**When:** That action is requested.

**Observable result today:** `AbstractController::DoubleRenderError`. Message states that render and redirect may be used at most once and that neither terminates execution. This is not the halt log.

**What clearer observability would mean:** This failure is still unmistakably “execution continued after a response was already performed,” the opposite of a clean callback halt.

**Related boundary, for contrast:** A before callback that renders *does* stop the action, so the action never gets a chance to double-render. Same `render` method, two different control-flow stories.

### External success signals (without prescribing a mechanism)

Signals that would show the framing is working—using whatever channels already exist or that maintainers later choose. None of these requires a new log, event, or API.

**Evidence of success**

- Given example 1 or 2, a developer who was not present for the code change can answer: which callback finished the request, that the action was cancelled because a response was already performed, and that after callbacks were skipped by policy.
- Given example 7, the same person can answer that this is continued execution after a response, not a halted filter chain.
- Given example 3, they do not cite a “rendered or redirected” halt as the explanation unless a response actually was performed.
- Given examples 4–5, they describe an exception around yield, including whether the action ran.
- Given example 6, they do not treat a non-matching `only`/`except`/`if` as a halt.
- Existing halt wording remains true for the before-callback performed-response case; `DoubleRenderError` remains true for a second response in continuing code.

**Evidence that would contradict success**

- People still cannot tell example 2 from example 7 without reading source.
- People treat example 3 as a performed-response halt, or treat example 1 as a missing action bug.
- Halt-related output says “rendered or redirected” in a case where nothing rendered or redirected, and readers trust that phrase.
- Exception-before-yield and halt-because-performed are filed as the same class of incident.

**Evidence the problem framing is wrong**

- Developers already get enough from the current halt line, redirect log, and `DoubleRenderError` message; confusion reports are actually about callback *order* or `only`/`if` precedence, not about halt vs continue.
- The real pain is that render/redirect do not return inside actions, and better halt telemetry would not reduce double-render mistakes.
- The real pain is only production volume or payload shape of the existing halt event, not missing distinction.

**Decisions those signals should trigger**

- Distinctions hold → the observability question is answered; any later change is optional.
- Halt vs double-render still collapse → keep this framing.
- Confusion is order/conditionals, not halt → revise the outcome toward documenting or exposing skip/order, not halt-because-performed.
- Confusion is only “render does not return” → stop treating halt observability as the problem; the established `DoubleRenderError` message already names that rule.

---

### Unresolved product questions

1. **Who is the primary reader?** App developer in development, operator in production, or framework maintainer? That choice changes how much detail is “clear enough” without implying a channel.
2. **Is the gap missing distinction, or a misleading existing phrase?** The halt line always says “rendered or redirected,” while halt actually follows `performed?`. Is that phrase the bug, or is silence in the around/conditional/exception cases the bug?
3. **Should a non-yielding around callback be the same *kind* of story as a rendering before callback?** Both prevent the action; only one is a performed-response terminator halt. Maintainers have not said whether observers should see them as siblings.
4. **Must conditional skip be observable at all?** Desired outcome 4 only says skip must not look like halt. It does not say skip needs its own signal.
5. **Does `head` / committed response / send-file-from-before deserve the same “intentional halt” story as render and redirect?** Behavior already matches; messaging may not.
6. **Development vs production.** Is a clearer story needed on every request, or only when someone is already investigating?
7. **Compatibility.** If today’s halt log string or `:filter`-only payload is a de facto contract, how much can wording change before that counts as a behavior change rather than clearer observability?
8. **Is this even a Rails change?** It may be enough to confirm current baseline in docs/examples. That remains a valid conclusion of this discovery.

---

No implementation is recommended. The question for maintainers is whether, for the examples above, an external observer can already tell intentional performed-response halt from skipped conditionals, non-yielding arounds, around exceptions, and double-render continuation—and, if not, what distinction would count as success without committing to a particular new signal.
