Reject appending before the strict check.

`Errors#add` is documented and implemented as raise *instead of* adding:

```ruby
error = Error.new(@base, attribute, type, **options)

if exception = options[:strict]
  exception = ActiveModel::StrictValidationFailed if exception == true
  raise exception, error.full_message
end

@errors.append(error)
error
```

The rdoc is explicit: `strict: true` raises `ActiveModel::StrictValidationFailed` (and `strict: SomeClass` raises that class) instead of adding the error, and afterward `person.errors.messages # => {}`. Same wording is in `validates!` / `:strict`. Appending first inverts that.

The exception class and message do not depend on the append. `Error` is already built before the `raise`, so `error.full_message` is available without mutating `@errors`. `strict: true` still maps to `ActiveModel::StrictValidationFailed`; any other truthy `options[:strict]` is still raised as-is with that string. Custom classes (`NameIsInvalid`, `CustomStrictValidationException` in `validations_test.rb`) still only receive the message string via `raise exception, error.full_message` — they never get the `ActiveModel::Error` object. After rescue, callers would not inspect a richer exception; they would only see a dirty collection.

That collection mutation is the problem, not a feature. On the strict path `@errors.append` currently never runs, so rescue leaves `errors` empty. Appending first would leave the error in `objects`/`messages`/`details` after `StrictValidationFailed` (or a custom class) is rescued. That mixes an exceptional, not-user-correctable failure into the same collection used for form errors, makes `added?`/`empty?` lie relative to the documented API, and forces every rescuer to `errors.clear`. `valid?` would re-run validators, but anything that reads `errors` between rescue and the next `valid?` would observe a recorded strict failure that was never supposed to be stored.

Non-strict `add` should stay unchanged: append, then return the `ActiveModel::Error`. That is already covered by `"add creates an error object and returns it"`. The strict tests in `validations_test.rb` (`test_strict_validation_in_validates`, `test_strict_validation_custom_exception`, `test_strict_validation_error_message`, etc.) only assert the exception class/message from `valid?`; they do not pin collection emptiness, but the public rdoc example does.

If the goal is inspect-after-rescue, put the `ActiveModel::Error` on the exception (or expose `full_message`, which is already the exception message). Do not record it on `@errors`.
