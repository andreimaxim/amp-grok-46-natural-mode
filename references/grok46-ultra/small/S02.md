**Reject this.** `deep_merge?` is the receiver-owned compatibility hook. `other_val.is_a?(DeepMergeable)` is not a substitute.

Current recursion in [`ActiveSupport::DeepMergeable#deep_merge!`](file:///home/user/workspace/repo/activesupport/lib/active_support/deep_mergeable.rb):

```ruby
if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
  this_val.deep_merge(other_val, &block)
elsif block_given?
  block.call(key, this_val, other_val)
else
  other_val
end
```

Default `deep_merge?` is `other.is_a?(self.class)`. The docs say classes may restrict or expand that domain. Overrides:

- [`Hash#deep_merge?`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/hash/deep_merge.rb) → `other.is_a?(Hash)` (narrower)
- [`ActionController::Parameters#deep_merge?`](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb) → `other.is_a?(ActiveSupport::DeepMergeable)` (wider)
- test `OmniWrapper` → `super || other.is_a?(OtherWrapper)`

The only production call of `deep_merge?` is this one. Dropping it makes those overrides dead.

**Custom classes.** [`activesupport/test/deep_mergeable_test.rb`](file:///home/user/workspace/repo/activesupport/test/deep_mergeable_test.rb) already covers the break:

- `"deep_merge does not deep merge non-subclass values by default"` — `Wrapper` vs `OtherWrapper` (`Wrapper.dup`). Both include `DeepMergeable`, so the new check recurses. Today `Wrapper#deep_merge?` is false, so the nested `OtherWrapper` **replaces** the nested `Wrapper`. After the change the nested result is a `Wrapper` from `this_val.deep_merge`. Assertion fails.
- `"deep_merge? can be overridden to allow deep merging of non-subclass values"` still recurses, but only because both sides happen to be DeepMergeable. The override is no longer what decides. Restrictions (`deep_merge?` → false for some DeepMergeable `other`) become impossible.
- Subclass merge (`Wrapper` / `SubWrapper`) still works under both checks; that is not evidence the change is safe.

**Block fallback.** Incompatible DeepMergeable pairs currently miss the first branch and hit `block.call` (or `other_val`). After the change they recurse and the block never runs for that key. Same-class block tests still pass and hide this.

**Mutation / return.** Recursion stays `this_val.deep_merge` (non-bang), so when recursion still happens, nested values are not mutated in place and `deep_merge!` still mutates only the receiver. What changes is **when** recursion happens: replacement by `other_val` becomes a left-typed dup merge. Nested class, object identity, and “`deep_merge!` does not mutate the underlying values” change for the Wrapper/OtherWrapper case.

**Hash / Parameters.** Nested `Hash` + non-Hash DeepMergeable (e.g. `Parameters`, custom wrapper): today `Hash#deep_merge?` is false. Afterward `Hash#merge!` is invoked with a non-Hash. That can `TypeError` (no implicit `to_hash`) or, for permitted Parameters, convert via `to_hash`. Nested Parameters + Hash is already allowed by Parameters’ override; that path is not a reason to delete the hook.

Suggested comment:

> Please don’t land this. Compatibility is owned by `this_val.deep_merge?(other_val)`, not by a symmetric `DeepMergeable` type check. The default is `other.is_a?(self.class)`; Hash narrows to Hash, Parameters widens to DeepMergeable, and the tests lock both “non-subclass replaces” and “override to expand”. This change drops that hook, skips the block for incompatible DeepMergeable pairs, and turns replacement into `this_val.deep_merge` (left-typed copy). Keep the `deep_merge?` call.
