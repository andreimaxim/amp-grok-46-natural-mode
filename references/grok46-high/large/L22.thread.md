## Product shaping brief: easier, safer `with_lock` when a custom lock clause and transaction options are both needed

This is a behavioral shaping brief, not an implementation design. It does not prescribe method signatures, argument order, internal control flow, or code changes. Where Rails source and tests do not establish a fact, the claim is labeled as a hypothesis or left open.

### Problem frame

**Actor:** An application maintainer using Active Record pessimistic locking on an already-loaded persisted record.

**Situation:** They need one action that (1) starts a transaction with specific wrapping options and (2) reloads the row under a chosen lock — default exclusive lock, no lock, or a database-specific clause — then runs work against that locked row.

**Current pain:** `with_lock` already combines those two jobs, but the combination is easy to get wrong and easy to observe inconsistently. Lock intent and transaction intent are supplied together in a mixed positional/options style. Adapters accept different clauses and isolation levels. Failures show up as several different errors, some only after a transaction has begun, and some only on some databases. A dirty in-memory record, a row that disappeared, or write-prevention mode each fail in their own way.

**Why it matters:** Locking plus transaction options is used to serialize updates, register after-commit work, and control whether the lock joins an outer transaction. If the lock clause is dropped, isolation is silently not applied, or the failure is an opaque database error, the application can lose isolation guarantees or ship adapter-specific production failures.

**Desired progress:** One obvious, safe way to request both the lock and the transaction options, with failures that are visible, distinguishable, and honest about adapter support — without changing the meaning of today’s successful default path.

- Inventing a new numeric reliability target.
- Changing write-prevention, `RecordNotFound`, or transaction commit/rollback meaning outside this use.
- Prescribing a new calling convention, keyword layout, or deprecation plan (those are later design choices).
- Expanding into query-cache, sharding, or multi-db routing beyond what write-prevention already implies.

### Risks

- **Silent weaker lock.** A custom clause that an adapter ignores (SQLite `FOR UPDATE` as a no-op in tests is a warning sign) could look successful while not serializing writers.
- **Error-type confusion.** Today lock-SQL failure, isolation failure, dirty-record failure, missing-row failure, and write-prevention failure are five different observations. Collapsing them would hide which request failed; splitting them further without need would make rescue logic harder.
- **Transaction already open.** Dirty-record and missing-row failures occur after `with_lock` has entered a transaction. Users who rescue and continue in an outer transaction may see rollback/join effects they did not associate with locking.
- **Nested isolation.** Users who pass `isolation:` on an inner `with_lock` will keep hitting `TransactionIsolationError`. Making that “easier” must not start allowing isolation changes on join/savepoint if the transaction API still forbids it.
- **Adapter documentation drift.** Examples that use `FOR SHARE NOWAIT` or `LOCK IN SHARE MODE` are not portable. A safer API that still accepts raw SQL will keep producing production-only `StatementInvalid` on the wrong database.
- **`false` as lock.** If `false` is easy to pass accidentally (e.g. a failed lookup of a clause), the application would run a transaction with **no** row lock. That is a safety hazard unless `false` remains an explicit, documented “no lock” choice.

### Acceptance examples

All are **required** cases for agreement on behavior, not an implementation test plan. “Observe” means what a caller or log/SQL watcher can see.

#### 1. Default lock

**Given** a persisted person with no unsaved changes.  
**When** they call `with_lock` with no lock argument and an empty block (or work that does not fail).  
**Then** the reload uses an exclusive row lock (`FOR UPDATE`), the block runs inside a transaction, and the transaction commits.

#### 2. No lock (`false`)

**Given** the same persisted person.  
**When** they call `with_lock` with lock `false`.  
**Then** a transaction still wraps the block, the person is reloaded, and the reload SQL has **no** lock clause.  
*Open: this is inferred from `lock!` / `reload`; not tested on `with_lock` itself.*

#### 3. Custom clause

**Given** the same persisted person and an adapter that accepts the clause.  
**When** they call `with_lock` with a custom clause (e.g. PostgreSQL `FOR SHARE NOWAIT`, MySQL `LOCK IN SHARE MODE`).  
**Then** that clause appears on the reload SQL, and the block runs inside the transaction.

**Counterexample — unsupported clause:**  
**Given** an adapter/database that rejects the clause.  
**When** they use that clause with `with_lock`.  
**Then** they observe `ActiveRecord::StatementInvalid` (database rejected the SQL), not a successful unlocked reload.

#### 4. Dirty persisted record

**Given** a persisted person whose `first_name` was changed in memory and not saved.  
**When** they call `with_lock`.  
**Then** locking is refused, the message names `first_name`, and they are told to save or reload. The in-memory change is not discarded by a successful locked reload.

#### 5. Commit

**Given** a persisted person.  
**When** `with_lock` changes `first_name` and saves, then the block ends normally.  
**Then** a later `reload` shows the new `first_name`.

#### 6. Exception rollback

**Given** a persisted person with original `first_name`.  
**When** `with_lock` saves a new `first_name` and then raises.  
**Then** after the error is handled, a later `reload` shows the original `first_name`.

#### 7. Yielding the transaction object

**Given** a persisted person.  
**When** the `with_lock` block takes the yielded argument.  
**Then** that argument is the current transaction, and after-commit / after-rollback callbacks can be registered on it.

#### 8. `requires_new` and `joinable`

**Given** an already open joinable transaction.  
**When** `with_lock` is used with `requires_new: true, joinable: false`.  
**Then** the block runs in a different, non-joinable current transaction, not the outer one.

#### 9. Isolation option

**Given** an adapter that supports the requested level (e.g. PostgreSQL `:read_uncommitted`).  
**When** `with_lock` is used with that `isolation:`.  
**Then** the current transaction reports that isolation level.

**Counterexample — joining with a different isolation:**  
**Given** an open transaction.  
**When** `with_lock` joins it and requests a different isolation.  
**Then** the user observes `TransactionIsolationError` (cannot set isolation when joining).

**Counterexample — nested/savepoint isolation:**  
**Given** an open transaction.  
**When** `with_lock` starts a nested transaction (`requires_new`) and also requests isolation.  
**Then** the user observes `TransactionIsolationError` (cannot set isolation in a nested transaction).

**Counterexample — adapter/level unsupported:**  
**Given** SQLite or another adapter that cannot set the requested isolation.  
**When** `with_lock` requests it.  
**Then** the user observes `TransactionIsolationError`, except SQLite `:read_uncommitted` without shared-cache, which currently raises a shared-cache `StandardError`. That split is current behavior; whether it should stay is open.

#### 10. Nesting

**Given** an outer `with_lock` (or outer transaction) already holding the row.  
**When** an inner `with_lock` runs without `requires_new`.  
**Then** it joins the outer transaction; work in the inner block is part of the outer commit/rollback. *(Joining is established for `transaction`; not specifically tested as `with_lock`/`with_lock`.)*

**When** the inner call uses `requires_new: true`.  
**Then** the inner work is a nested transaction relative to the outer one (same distinction as example 8). Isolation on that inner call still fails as in example 9.

#### 11. Missing row during reload

**Given** a persisted in-memory person whose row has been deleted by another connection/work.  
**When** they call `with_lock`.  
**Then** they observe `ActiveRecord::RecordNotFound`. The block does not run as a successful locked update, and any wrapping transaction started by this call does not commit new work.  
*Reload’s missing-row error is documented; `with_lock`-specific coverage is absent.*

#### 12. Write-prevention mode

**Given** `while_preventing_writes` is enabled.  
**When** they call `with_lock` with the default lock **or** a custom clause.  
**Then** they observe `ActiveRecord::ReadOnlyError` (`Lock query attempted while in readonly mode`).

**Nested disable:**  
**Given** write-prevention enabled, then inner `while_preventing_writes(false)`.  
**When** they call `with_lock` there.  
**Then** locking proceeds without `ReadOnlyError`.

### Steering evidence

**Would contradict success**

- Default `with_lock` no longer emits `FOR UPDATE` / no longer wraps a transaction.
- A custom clause is accepted as a transaction option or dropped when options are also present (combined request failed).
- `false` either locks anyway or is indistinguishable from the default exclusive lock.
- Dirty records are locked and silently lose in-memory changes, or fail with an unrelated database error.
- Successful blocks do not persist; exceptions do not roll back.
- The block no longer receives the transaction object.
- `requires_new` / `joinable` / supported isolation have no effect.
- Write-prevention allows lock queries.
- Missing-row reload succeeds or fails as something other than `RecordNotFound`.
- Unsupported lock SQL succeeds without locking, or unsupported isolation is ignored instead of raising.

**Would suggest the problem framing is wrong**

- Application authors never need a custom clause and transaction options on the same call; they always compose `transaction` + `lock!` themselves and do not hit confusion.
- Production incidents are almost entirely concurrent lock waits / deadlocks, which this API shape cannot make observable.
- The painful part is only documentation of adapter SQL, not the combined call.

**Decisions those should trigger**

- Contradictory default-path evidence → stop; the change is breaking core locking.
- Combined clause+options still ambiguous → investigate calling experience; do not declare success.
- Framing looks wrong (authors don’t combine the two) → stop or shrink to docs/examples only.
- Adapter honesty regressions (silent ignore) → revise; safety is the point.

### Open questions

1. Is `with_lock(false)` a supported public behavior, or only an accident of `lock!` / `reload`?
2. Should dirty-record refusal stay a generic `RuntimeError`, or is a dedicated error part of “safer”? (Current tests expect `RuntimeError` + changed-attribute message.)
3. Should missing-row and dirty-record failures be observable *before* a new transaction exists, or is “inside the wrapping transaction” acceptable?
4. Should SQLite’s shared-cache `StandardError` for `:read_uncommitted` stay different from `TransactionIsolationError`?
5. How much adapter-specific guidance is in scope vs. continuing to pass raw SQL through and let `StatementInvalid` speak?
6. Is nested `with_lock`/`with_lock` a behavior we must define beyond existing `transaction` join/savepoint rules?
7. Are unpersisted records in `with_lock` in scope? `lock!` currently no-ops reload for them.

---

**Problem frame (compact):** Maintainers need one safe action that both locks a persisted row (default, none, or custom SQL) and wraps work in a transaction with explicit join/isolation options. Today those intents can be combined, but adapter support and failure modes are uneven, and several important refusals are easy to miss.

**Behavioral outcome (compact):** Combined lock + transaction requests keep both intents; default lock, commit/rollback, yield, write-prevention, dirty-record refusal, and missing-row refusal stay observable; unsupported clauses and isolation fail in distinguishable, adapter-honest ways.

This brief is a proposed shared understanding from Rails’ current observable behavior plus the requested outcomes. It is not a confirmed product spec and not an implementation plan.
