`after_commit` is a **transaction-boundary** callback, not a persistence callback. A save or destroy only enrolls the record and stamps action flags. The `:commit` / `:rollback` chains run later. `on:` is evaluated against those flags at fire time, not against “the last `save`/`destroy` call.”

### Registration: `on:` becomes an `if:` predicate

[`after_commit`](activerecord/lib/active_record/transactions.rb) registers on the `:commit` chain. `after_create_commit` / `after_update_commit` / `after_destroy_commit` / `after_save_commit` are shortcuts that inject `on:`.

`set_options_for_callbacks!` rewrites `on:` into:

```ruby
options[:if] = [
  -> { transaction_include_any_action?(fire_on) },
  *options[:if]
]
```

Allowed actions are only `[:create, :destroy, :update]`. The predicate, evaluated at callback-run time:

```ruby
when :create  then persisted? && @_new_record_before_last_commit
when :update  then !(@_new_record_before_last_commit || destroyed?) && _trigger_update_callback
when :destroy then _trigger_destroy_callback
```

These three are mutually exclusive for a given instance at fire time. Create wins over update: if the instance was new when first enrolled, `:update` is suppressed even if `_trigger_update_callback` is later true.

Unfiltered `after_commit` / `after_rollback` still only run if the transaction invokes `committed!` / `rolledback!` with `should_run_callbacks: true`, which requires `trigger_transactional_callbacks?`. Failed saves never enroll (`test_dont_call_any_callbacks_after_transaction_commits_for_invalid_record`). Previous transactions’ flags are not reused.

### Enrollment

`save` / `save!` / `destroy` go through `with_transaction_returning_status`: join or open a txn, `add_to_transaction`, snapshot state, persist, rollback the persist txn if it returns falsey.

Action flags come from persistence:

- create: `remember_transaction_record_state` sets `@_new_record_before_last_commit` from the snapshot
- update: `_update_record` sets `@_trigger_update_callback`
- destroy: `@_trigger_destroy_callback ||= persisted? && destroy_row > 0`

The snapshot is taken once per instance per open txn (`@_start_transaction_state ||= ...`) and `level` increments on each nested persist. That is why create-then-update still sees “was new when the txn started.”

### Nested transactions: join vs `requires_new`

```ruby
if !requires_new && current_transaction.joinable?
  yield current_transaction.user_transaction   # no new stack frame
else
  within_new_transaction(...)
end
```

`run_commit_callbacks = !current_transaction.joinable?`:

| Situation | Stack object | `@run_commit_callbacks` |
|---|---|---|
| Outermost real txn | `RealTransaction` | **true** |
| Nested `requires_new` under a joinable parent | savepoint or restart-parent | **false** |
| Nested without `requires_new` | *none* — join | n/a |

A write marks the parent dirty, so a typical save-then-`requires_new` uses a **savepoint**. Both nested types have `full_rollback? == false`.

**Inner commit** (`@run_commit_callbacks == false`) does not fire model callbacks. It re-enrolls each record on the parent. **Inner rollback** *does* run `rollback_records` immediately. **Outer `RealTransaction` commit** is the only place model `after_commit` runs.

Evidence: `test_only_call_after_commit_on_top_level_transactions` — inner `requires_new` save leaves history empty until the outer block exits.

### Order and which `on:` filters fire

`before_commit` always runs in definition order. `after_commit` / `after_rollback` order depends on `ActiveRecord.run_after_transaction_callbacks_in_order_defined` (false in the gem; true for new apps):

- **true**: `[1, 2, "prepend 2", "prepend 1", 3, 4, "save", "create"]` on create; rollback `["rollback1", "rollback2"]`
- **false**: `[1, 2, "create", "save", 4, 3, "prepend 1", "prepend 2"]`; rollback `["rollback2", "rollback1"]`

| Final state | Fires | Does not fire |
|---|---|---|
| created (still persisted, was new) | unfiltered, `:create`, `:save` | `:update`, `:destroy` |
| updated (not new, not destroyed) | unfiltered, `:update`, `:save` | `:create`, `:destroy` |
| destroyed | unfiltered, `:destroy` | `:create`, `:update`, `:save` |
| new record destroyed without INSERT | nothing | all |

Same-filter-name `after_commit :do_something` plus `after_create_commit :do_something` **deduplicate**; `on: [:create, :update]` does not.

### Concrete scenarios

**Create then update of the same instance in one transaction.** Both persists enroll the same object. The snapshot keeps `new_record: true`, so `@_new_record_before_last_commit` stays true. `_trigger_update_callback` becomes true, but `:update` requires `!@_new_record_before_last_commit`. At outer commit, only create-side filters run. One `committed!`, not two.

**Record saved only in an inner joined transaction.** No inner transaction object exists. Enrollment is on the outer `RealTransaction`. Nothing runs at the inner `end`.

**Rollback of an inner `requires_new` block, swallowed by the outer block.** Inner is a savepoint. `after_rollback` runs on the inner record immediately. The outer record stays enrolled and gets `after_commit` when the outer commits. Evidence: `test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint` — outer commits 1 / rollbacks 0; inner commits 0 / rollbacks 1.

**Outer rollback after an inner savepoint release.** Inner commit re-enrolls the record on the parent without calling `committed!`. Outer rollback then runs `after_rollback` with the inner save’s flags. No `after_commit`.

**Destroy of a newly-created record.** Never persisted: `new_record.destroy` stamps no destroy trigger — no callbacks (`test_no_after_commit_on_destroy_after_transaction_commits_for_destroyed_new_record`). Created then destroyed in the same txn: `persisted?` is false so `:create` is false; only `:destroy` (and unfiltered) run.

**Multiple in-memory instances for the same row.** Equality is class+id, so they compete; only one instance’s callbacks run. `run_commit_callbacks_on_first_saved_instances_in_transaction` **true** (gem default): first triggering instance wins — create-then-other-instance-update fires `after_create_commit` on the creator. **false** (new apps): last instance wins, but a later non-destroyed instance cannot replace an earlier `destroyed?` candidate, and `@_new_record_before_last_commit` is copied onto the later instance so create-then-find-update fires `after_create_commit` on the updater with the updated attributes. Destroy followed by an update on another instance: destroy wins in both configurations.
