## Shaping brief: clearer observability when an Action Controller callback chain stops because a callback has performed a response

This is a discovery brief for Rails maintainers. It describes the problem and desired externally observable outcomes. It does not choose a log line, notification, API, or other implementation.

**Evidence inspected:** Action Controller / Abstract Controller callback registration and terminator; `performed?`; render, redirect, and `head`; `AbstractController::DoubleRenderError`; Active Support callback halt / after-skip / around-skip behavior; existing halt logging, notification, and structured event; filter, log-subscriber, and double-render tests; Action Controller overview guide. Claims below are from that evidence unless labeled as a hypothesis.

---

### Problem frame

**Actors:** application developers and operators debugging a request; Rails maintainers judging whether today’s halt story is clear enough.

**Situation:** A controller action is wrapped in `before_action`, `around_action`, and `after_action`. A callback may produce a response (render, redirect, `head`) and thereby stop later work. That is a supported, documented pattern (for example, redirecting an unauthenticated user).

**Pain today:** When the action body, later befores, afters, or around-after-yield work do not run, an observer often cannot tell whether that was:

1. an intentional halt because a callback already performed a response,
2. an around callback that never continued,
3. a callback that simply did not match (`only` / `except` / `if` / `unless` / `skip_*`),
4. an exception, or
5. an action that kept running after a first render/redirect and then failed with `DoubleRenderError`.

**Why it matters:** Halt-on-performed-response is legitimate control flow. Without a way to distinguish it from the other cases, people waste time treating auth redirects as missing callbacks, treating a silent around skip as a halt, or treating a second render as “the chain halted.”

**Hypothesis (request framing, not a measured incident):** today’s signals are easy to miss, easy to over-read, or too coarse to answer “did this request stop because a callback already answered?”

---

### Current observable baseline

What actually happens, independent of any new work:

- **`before_action` that renders or redirects (or otherwise becomes `performed?`):** that callback runs; later befores, the action, and afters (including prepended afters) do not. The client gets that callback’s body or redirect. Tests treat this as success, not an error.
- **`around_action` that never yields:** earlier befores run; the around runs; nested befores, the action, and afters do not. No exception. Tests assert this is silent success. This path is **not** the same as the before-callback terminator.
- **Exception before yield in `around_action`:** the action does not run; the exception is the external result. Exception after yield: the action did run; the exception still surfaces. Guide: afters do not run after an exception; around-after-yield can still run if the callback uses `ensure`.
- **Conditional callbacks:** unmatched `only`/`except` (and equivalent conditionals) simply do not run. That is not a halt. Matching before+after on one action still both run when nothing has performed a response.
- **Action that renders/redirects twice, or `head` after render:** `AbstractController::DoubleRenderError`. The error text states that render/redirect do **not** stop the rest of the action method; the caller must return. That is a different rule from callback-chain halt.
- **`performed?`:** Abstract Controller: response body is set. Action Controller: response body or committed response. Implicit render uses it so a callback-produced response is not overwritten.
- **Signals that already exist for before-callback halt:** a notification named `halted_callback.action_controller` carrying the filter; an info log of the form `Filter chain halted as :redirector rendered or redirected`; a structured event `action_controller.callback_halted` with the filter. The log wording always says “rendered or redirected.” Tests cover this for a redirecting before, not for render, `head`, around-without-yield, conditionals, exceptions, or double render.
- **Around-without-yield, conditionals, exceptions, and DoubleRenderError do not share that halt signal.** DoubleRenderError is an exception, not a halt notice.

So: halt-on-performed-response already has *some* before-callback breadcrumb, and it always claims render-or-redirect. Other ways the later chain never runs look different, or look like nothing.

---

### Desired outcomes

When work in this area succeeds, without prescribing how:

1. A person investigating a request can tell that later callbacks/action did not run **because a callback had already performed a response**, as distinct from “the callback never matched,” “an around never continued,” “an exception occurred,” or “the action tried to perform twice.”
2. Intentional performed-response halt remains a successful, supported way to finish a request (auth redirect, early `head`, etc.). The response the callback performed is still the response.
3. Accidental double performance in an action that kept running is still visibly a **second-response** failure, not a callback halt.
4. Maintainers can point to external evidence that answers “was this halt intentional performed-response, or confusing control flow?” rather than inferring only from missing side effects.

---

### Behavioral examples

Required cases for agreement. “Observable result” is what a client, log/trace consumer, or debugger can see today; desired distinction is what clearer observability would add, not a chosen mechanism.

#### 1. Rendering `before_action`

A before renders a body. Later befores, the action, and afters do not run. The client gets that body. Today this is a successful halt. Desired: an observer can attribute the skipped later work to “this before already performed a response,” not to a missing action or a skipped-by-condition after.

#### 2. Redirecting `before_action`

A before redirects. Same skip of action and afters. Client gets the redirect. Same halt signal wording as a render, if any signal appears. Desired: still recognizable as performed-response halt; not confused with the action having run and then redirected.

#### 3. Non-yielding `around_action`

An around runs and does not continue. Nested befores, action, and afters do not run. No exception. Today this does **not** use the before terminator and does not produce the halt breadcrumb. Desired: an observer can tell “the around never continued” from “a before already answered.” Whether a non-yielding around that also rendered should count as performed-response halt is an open question below.

#### 4. Exceptions before and after yield

Before yield: action does not run; exception is the result. After yield: action did run; exception still surfaces; afters do not. Desired: exception paths are not described as “filter chain halted as rendered or redirected.”

#### 5. Conditional callbacks

`only`/`except` (and similar) that do not match: the callback does not run; the action can still run. Matching before+after on the included action both run if nothing performed a response. Desired: “did not apply to this action” is not presented as a halt.

#### 6. Action that attempts a second render

Action renders, then renders again or calls `head`. `DoubleRenderError`. Desired: this remains “two performances in one action,” not “callback chain halted.” It also remains distinct from a before that rendered and correctly prevented the action from running.

---

### Explicit non-goals

- Changing whether a performed before skips the action and afters.
- Changing whether a non-yielding around skips nested work without raising.
- Changing DoubleRenderError, or making render/redirect implicitly return from the action method.
- Making unmatched conditionals into halts.
- Prescribing a particular log, notification, API, metric, dashboard, or docs-only fix.
