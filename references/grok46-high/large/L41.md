## Shaping brief: reliably targeting and testing `deliver_later` queues

This is a product brief, not a design. Current-contract claims are from source and tests. Proposed behavior is only what a mailer author or test author should be able to do and see.

---

### 1. This revision’s observable contract

**How a later-delivery queue is chosen**

- A mailer has a later-delivery queue name and a delivery job. Framework defaults are queue `:mailers` and job `ActionMailer::MailDeliveryJob`. A subclass keeps the parent’s values until it sets its own; setting a subclass does not change the parent.
- `deliver_later` / `deliver_later!` enqueue that mailer’s delivery job. An explicit `queue:` on that call is the queue for that enqueue only. `wait` / `wait_until` schedule it; `priority` is carried with the job. If the message was already built, enqueue is refused.
- Parameterized mail (`Mailer.with(...).action.deliver_later`) uses the same job, queue choice, and per-call options; the only extra visible payload is the params.
- With the default delivery job, the enqueued job’s queue is the mailer’s `deliver_later_queue_name`. A custom `delivery_job` owns the queue; the mailer’s `deliver_later_queue_name` is not what testers should expect unless that job itself reads it.
- `nil` as the mailer’s later-delivery queue name means “Active Job’s default queue” (normally `"default"`), not “no queue” and not the `:mailers` fallback.
- Symbols and strings are both accepted as configured or per-call names. After enqueue, the name testers and adapters see is a string. If an Active Job queue-name prefix is set, the visible name is the prefix plus the chosen name.

**How tests target those queues**

- `deliver_enqueued_emails` delivers only jobs that are some loaded mailer’s delivery job. With no `queue:`, it delivers all such jobs (subject to `at:`). With `queue:`, it delivers only jobs whose *visible* queue equals that filter after string conversion. `at:` delivers unscheduled jobs and jobs due at or before that time; later scheduled jobs stay enqueued.
- `assert_enqueued_email_with` matches one mailer action on that mailer’s delivery job. If the caller omits `queue:`, the expected queue is the one that job would actually use (including custom job queues, `nil` → default, and prefix). A passed `queue:` is compared as a string, so `:mailers` matches `"mailers"`.
- Several mailers may enqueue in one stretch of work. A queue filter is allowed to deliver or match one mailer’s jobs and leave the others enqueued.

### 3. Problem frame

**Actor:** A Rails team that sends mail in the background and tests that mail by queue.

**Situation:** Several mailers share an app. Some use the default later-delivery queue, some set their own name (symbol, string, or `nil`), some pass `queue:` on one call, some use a custom delivery job, some are parameterized, some are scheduled. Tests then try to deliver or assert “only this queue.”

**Pain today:** The name written on the mailer is not always the name tests and adapters use. Symbol vs string, `nil` vs `"default"`, a queue prefix, a custom job’s own queue, or a per-call override can make a filter miss in silence: the email stays enqueued, or an assertion looks at the wrong queue, while other mailers in the same example keep moving. Teams cannot tell whether later delivery is wrong or the test targeted the wrong name.

**Why it matters:** Silent misses make queue isolation untrustworthy. Teams either run every enqueued email (and couple unrelated mailers) or skip later-delivery tests.

---

### 4. Desired outcome

A developer can point at a later-delivery queue the same way they chose it—mailer default, per-call `queue:`, `nil`, symbol or string, custom job, parameterized or not—and then:

1. See that enqueue land on one stable, visible queue identity.
2. Deliver only that queue’s mail in a test, including when other mailers enqueued at the same time.
3. Leave scheduled-for-later mail undelivered when they ask for “due by now.”
4. Get a clear miss when they target a queue that had no mail, rather than a quiet no-op that looks like success.

Success is qualitative: “I named the queue the way I configured it, and only those emails ran or matched.”

---

### 5. Appetite

Small batch. Tighten targeting and test isolation around the existing later-delivery knobs. Do not add new delivery modes, new job types, or a new test framework. If the work cannot make “the name I configured is the name I filter with” true for the cases below without widening into Active Job’s global queue model, stop and shrink to docs-and-examples only.

---

### 6. Scope

In:

- Default later-delivery queue vs a mailer-level name vs a per-call `queue:`.
- Symbol, string, and `nil` names.
- Inheritance: subclass name does not change the parent; unset subclass follows the parent.
- Custom `delivery_job`, including a job that defines its own queue.
- Parameterized mail using the same queue rules.
- Several mailers in one test.
- `deliver_enqueued_emails` with queue filter and with time filter.
- Test helpers and adapters that stringify (and may prefix) queue names.

Out of appetite but must not get worse: production adapters that further rewrite names (case, intern, prefix). Testers should still be able to use the name they configured and have it match what that adapter stored, or see a clear mismatch.

---

### 7. Non-goals

- Changing when mail is sent in production, retry/error behavior, or `deliver_now`.
- Replacing Active Job or adding a mail-only queue adapter.
- New assertion DSLs, matchers, or a requirement to write specific tests.
- Making unloaded mailer classes visible to helpers.
- Redesigning parameterized mail or scheduled jobs beyond queue targeting.
- Forcing every app onto `:mailers` or onto `nil`; both remaining legal is required.

---

### 8. Risks

- **Silent filter miss (current pain).** A queue filter that stringifies or prefixes differently from enqueue looks like “no mail” while jobs sit on another name.
- **Wrong owner.** Filtering by the mailer’s `deliver_later_queue_name` while a custom job uses another queue delivers nothing or the wrong jobs.
- **Cross-mailer bleed.** A too-broad filter (or no filter) delivers unrelated mailers and hides regressions.
- **Time-filter bleed.** Treating scheduled mail as due, or dropping immediate mail when `at:` is set.
- **False framing.** If failures are really “mailer class not loaded” or “message was accessed before `deliver_later`,” queue naming work will not help. Reconsider if teams still miss after names consistently match.

### 9. Acceptance examples

Required unless marked illustrative.

**Several mailers, queue filter**

- *Situation:* Customer mail is configured for `:external_mailers`. Employee mail is configured for `:internal_mailers`. Both `deliver_later` in one test.
- *Action:* Deliver enqueued emails targeting the external queue only.
- *Observe:* Customer mail is sent. Employee mail is still waiting on the internal queue.

**Per-call override**

- *Situation:* A mailer’s default later-delivery queue is `:delayed_mailers`. One call uses `queue: :another_queue` (symbol).
- *Action:* Deliver or assert targeting `:another_queue` (or `"another_queue"`).
- *Observe:* Only the overridden call is on that queue. Other calls for that mailer stay on `"delayed_mailers"`.

**Symbol / string / nil**

- *Situation:* One app uses `:mailers`, another `"sample_mailer_queue_name"`, a 6.1-defaults app uses `nil`.
- *Action:* Enqueue with `deliver_later`, then assert or deliver using the name the team configured (symbol or string) or, for `nil`, the platform default queue.
- *Observe:* Match succeeds. `nil` is not treated as `:mailers`. `:mailers` and `"mailers"` are the same visible queue.

**Inheritance**

- *Situation:* A subclass sets `:throttled_mailers`. The parent still has the framework default.
- *Action:* Enqueue both.
- *Observe:* Subclass mail is on `"throttled_mailers"`. Parent mail is unchanged (`"mailers"`, or default queue if the parent’s name is `nil`).

**Custom delivery job**

- *Situation:* A mailer uses a custom delivery job. Another custom job declares its own queue (`:delivery_job_queue`).
- *Action:* Enqueue both; deliver all enqueued emails with no queue filter; assert the job-owned-queue mail without passing a queue.
- *Observe:* Both send. The job-owned queue is the visible queue, not the mailer’s `deliver_later_queue_name`, unless that job follows the mailer name.

**Parameterized mail**

- *Situation:* `ParamsMailer.with(inviter:, invitee:).invitation.deliver_later`, same queue rules as ordinary mail, possibly a custom job.
- *Action:* Target that mailer’s queue (or deliver all mail jobs).
- *Observe:* The parameterized email is sent or matched like a non-parameterized one on the same queue. Params do not create a second queue identity.

**Scheduled delivery**

- *Situation:* One `deliver_later` (due now) and one `deliver_later(wait: 2.hours)` from the same mailer.
- *Action:* Deliver enqueued emails due by one hour from now.
- *Observe:* Only the immediate email is sent. The two-hour email remains enqueued.

**Prefix / adapter normalization**

- *Situation:* Active Job prefix is `"prefix"`, or an adapter stores queues as strings only. Mailer name is `:mailers`.
- *Action:* Assert or deliver using the name the team uses in mailer config (`:mailers` or `"mailers"`).
- *Observe:* The email is found on the visible stored name (`"prefix_mailers"` or `"mailers"`). Targeting a name that cannot match the stored form fails clearly.
- *Open (see below):* whether the filter input is the configured name or the already-prefixed stored name. Either is acceptable if it is consistent and obvious.

**Counterexample: untouched message vs later delivery**

- *Situation:* Code reads the message, then calls `deliver_later`.
- *Observe:* Enqueue does not happen. This is out of scope to “fix”; queue targeting must not be blamed for it.

### 10. Steering evidence

**Success looks like:** In an example with two mailers, a scheduled send, and mixed symbol/string/`nil`/custom job, a developer names one queue and only that queue’s due mail is delivered or matched.

**Investigate / do not ship if:** A filter using the configured name silently delivers zero while jobs exist under a string, prefixed, or default-queue name.

**Reconsider the framing if:** After names match, teams still fail because mailer classes were not loaded, because they accessed the message before `deliver_later`, or because they expected `deliver_later_queue_name` to override a custom job’s queue.

**Stop if:** Making configured names match stored names requires changing production enqueue identity for existing apps (e.g. forcing `:mailers` where `nil` currently means `"default"`).

---

### 11. Open questions

1. When a prefix (or adapter rewrite) is on, should `deliver_enqueued_emails(queue: :mailers)` mean the configured name (framework applies the same rewrite) or the already-visible stored name (`"prefix_mailers"`)? Current assertions resolve the stored name; `deliver_enqueued_emails` is not shown with a prefix.
2. Should targeting “this mailer” without a queue name always follow the custom job’s queue, and never `deliver_later_queue_name`, when those differ? Current docs say the job owns the queue.
3. Is a clear error required when a queue filter matches no mail jobs but other mail jobs are enqueued, or is “delivered zero” enough?

No implementation is implied. The outcome is: the name a team uses to choose a later-delivery queue is the name they can use to test it, across the cases above.
