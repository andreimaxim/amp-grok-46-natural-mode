**Request changes.** Do not merge `middleware.use ::ActionDispatch::Cookies if !config.api_only || config.session_store`.

The claim is right that CookieStore/AbstractStore write through `request.cookie_jar` and only `ActionDispatch::Cookies#call` flushes `Set-Cookie`. The condition is wrong: it does not mean “user opted into sessions.”

**Assembly today** (`DefaultMiddlewareStack#build_stack`):

- Full-stack: Cookies → `config.session_store` (if truthy) → Flash (Flash is a no-op Rack layer; it only prepends request methods).
- API-only: all three omitted. Guide and generator say add Cookies/session/flash manually.
- Session middleware is still gated with `if !config.api_only && config.session_store`. This diff does not change that.

**Why `config.session_store` is the wrong gate**

`setup_default_session_store` runs before `:build_middleware_stack` and does **not** skip `api_only`. Unless the app set a store, it assigns `:cookie_store`. The getter then returns `ActionDispatch::Session::CookieStore` (truthy) for every default API app. `:disabled` is the only falsy case (`nil`).

So `!config.api_only || config.session_store` is true for **all default API-only apps**, not “whenever a session store is configured.”

**Observable consequences**

| App | Stack | Request |
|---|---|---|
| Default API-only | **Cookies added**; still no Session/Flash | Extra middleware on every request. `request.session` stays disabled (`Request#default_session`). Cookie jar can now emit `Set-Cookie` if anything touches it. Breaks exact `api middleware stack` test. |
| API + user `session_store` only | Cookies yes, Session still absent | Sessions still do not persist. Claim is not delivered. |
| API following the guide (`use Cookies` + `use session_store`) | **Duplicate Cookies**; Session still at the end via proxy `use` | Double jar flush. Order stays legal (default Cookies is outer). |
| API + `session_store :disabled` | No Cookies | Same as today. |
| Full-stack / full-stack + `:disabled` | Unchanged | Cookies stay; session middleware still omitted when disabled. |

`config.middleware.use` is replayed *after* the default stack (`MiddlewareStackProxy`), so auto-Cookies at the Callbacks slot plus a later `use Session` is valid order, but it is not what API apps do today.

**Tests**

Covered: exact full vs API stacks; Flash-before-Session-before-Cookies; API `reset_session`; full-stack `:disabled` writes 500; default store initializer; API apps that **manually** add Cookies+Session.

Gaps: no test that API + default store omits Cookies; no API + `session_store` without extra middleware; no duplicate-Cookies case; no initialization-order test (store set in an initializer vs `application.rb`). Isolation apps also force `config.session_store :cookie_store`, so they would not catch default-API leakage.

**Compatibility**

Breaking for every API-only app (new Cookies middleware; `rails middleware` changes). Conflicts with “cookies can be added back manually.” Duplicate Cookies for apps that already follow `guides/source/api_app.md`. Session options/`force_ssl` secure-cookie logic still skipped for API because session middleware is not installed.

**Narrower alternative** (only if we want auto-wiring at all): skip the default store for `api_only` in `setup_default_session_store`, then when `config.session_store` is truthy install **both** Cookies and the session store. Update the API guide so apps stop `use`ing Cookies themselves (otherwise duplicates). The one-liner alone cannot do that. Status quo is also fine: the documented two `middleware.use` lines already work.

Approve only if Cookies are **not** added to default API apps and session middleware is considered in the same change.
