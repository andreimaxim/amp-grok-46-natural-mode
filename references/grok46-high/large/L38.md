### Current contract (observed, not redesigned)

Three objects, two moments:

1. **Schedule** — `after_update_commit` on `InboundEmail` calls `IncinerationJob.schedule` when `ActionMailbox.incinerate && status_previously_changed? && processed?`.
2. **Execute** — the job deserializes the record and calls `inbound_email.incinerate` → `Incineration#run` → `destroy!` **only if** `due? && processed?`.

`processed?` is `delivered? || failed? || bounced?`. `pending` and `processing` are not processed. Mailbox `receive` reaches those terminals via `delivered!` / `failed!` / `bounced!` ([`base.rb` `track_status_of_inbound_email`](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/base.rb), [`state_test.rb`](file:///home/user/workspace/repo/actionmailbox/test/unit/mailbox/state_test.rb)).

`due?` is:

```ruby
updated_at < ActionMailbox.incinerate_after.ago.end_of_day
```

That is a **strict** `<` against end-of-day of `(now - incinerate_after)`, not `updated_at <= incinerate_after.ago`. Existing tests pass at exactly `travel 30.days` only because of `end_of_day` slack.

`incinerate = false` gates **scheduling only**. `Incineration#run` and the conductor `incinerate` path do not read the flag.

Missing records: `discard_on ActiveRecord::RecordNotFound, ActiveJob::DeserializationError::RecordNotFound`. The job test destroys first, then `perform_later` + `perform_enqueued_jobs` and asserts no raise.

Destruction is `destroy!`. `has_one_attached :raw_email` defaults `dependent: :purge_later`, so the attachment row is destroyed with the record and the blob is purged asynchronously.

**Do not freeze these (implementation accidents unless a refactor keeps the observable result):**

- Concern + command-object split, `after_update_commit` vs other commit hooks, `destroy!` vs `destroy` as long as a failed destroy still surfaces.
- `end_of_day` vs another equivalent “same calendar day still due at wait expiry” rule — preserve the **observable** cutoff (see age-boundary tests), not the method name.
- Dual `discard_on` exception classes — preserve “missing record is ignored, transient deserialize errors are not discarded.”
- Conductor calling `incinerate` directly; queue symbol `:action_mailbox_incineration` on pre-6.1 defaults.
- Create-as-already-processed does **not** schedule today (`after_update_commit` only). Untested; treat as current behavior to characterize, not a documented promise.
- `incinerate = false` does not stop an already-queued job or a direct `incinerate` call. Test characterizes this; do not “fix” it in a behavior-preserving refactor.

### Focused unit / job checks

#### 1. Terminal processed transitions (schedule + destroy)

Keep the three existing cases; make the enqueue assertion complete:

For each of `delivered!`, `bounced!`, `failed!` on a fixture created as `:processing`:

- `assert_enqueued_with job: ActionMailbox::IncinerationJob, args: [inbound_email], at: 30.days.from_now, queue: ActiveJob::Base.queue_name # or configured queue`
- `travel 30.days`
- `assert_difference -> { ActionMailbox::InboundEmail.count }, -1` around `perform_enqueued_jobs only: ActionMailbox::IncinerationJob`
- `assert_not ActionMailbox::InboundEmail.exists?(id)`

Also enqueue from real mailbox `receive` (integration-flavored unit): `SuccessfulMailbox` / `UnsuccessfulMailbox` / `BouncingMailbox` from [`state_test.rb`](file:///home/user/workspace/repo/actionmailbox/test/unit/mailbox/state_test.rb) should each enqueue one incineration job. That ties terminals to production status writes, not only bang methods.

#### 2. Repeated updates

| Update | Expect |
|---|---|
| `processing` → `delivered` | enqueue 1 |
| `delivered` then `update!(message_id: ...)` with status unchanged | enqueue 0 more (`status_previously_changed?` is false) |
| `delivered` → `failed` or `bounced` | enqueue **another** job (status changed and still processed) |
| `delivered` → `pending` or `processing` | enqueue 0 |
| `pending` → `processing` | enqueue 0 |
| second `delivered!` while already delivered | enqueue 0 (no previous change) |

Assert with `assert_enqueued_jobs 1, only: IncinerationJob` then `assert_no_enqueued_jobs` / `assert_enqueued_jobs 2` as appropriate.

#### 3. `ActionMailbox.incinerate = false`

- Existing: no enqueue on `delivered!`.
- Add: `failed!` / `bounced!` also enqueue nothing.
- Characterize (do not “fix”): with flag false, `inbound_email.incinerate` after making `due?` true still destroys if `processed?`. Flag is a scheduler switch, not a destructor switch.

#### 4. Scheduling delay and queue

- Default: `at: ActionMailbox.incinerate_after.from_now` with default 30.days.
- `ActionMailbox.with(incinerate_after: 14.days)` (or assign/restore): enqueue `at: 14.days.from_now`.
- Queue: `ActionMailbox.queues[:incineration] = :mailbox_gc` → `assert_enqueued_with queue: "mailbox_gc"` (or symbol form the test helper accepts).
- `queues[:incineration] = nil` → job uses Active Job default queue.
- `IncinerationJob.schedule(email)` without a status callback still uses `wait: incinerate_after`.

#### 5. Record changed after scheduling (staleness)

Schedule via `delivered!`, then before perform:

**A. `updated_at` bumped, still processed** (`touch` or non-status update). Travel to original `wait` expiry. `perform_enqueued_jobs`. Record **remains**. `due?` uses current `updated_at`, which is no longer `< incinerate_after.ago.end_of_day`.

Then travel until the new `updated_at` is due; a **newly** scheduled job (or a manual `incinerate`) should destroy. The original job is a single shot; it must not destroy early.

**B. Status moved to unprocessed** (`processing!` / `pending!`) after enqueue. At wait expiry, record **remains** (`processed?` false).

**C. Status moved to another processed terminal** (`delivered!` then `failed!`). Two jobs. Each execution re-reads status + `updated_at`. First job may no-op on due-ness because `failed!` bumped `updated_at`; later due job destroys. Assert final `count` and that no job raises.

#### 6. Age boundary: `updated_at`, `ago`, `end_of_day`

Drive `Incineration.new(email).run` directly (unit) **and** via the job (job test). Freeze a midday timestamp.

Let `cutoff = ActionMailbox.incinerate_after.ago.end_of_day`.

| `updated_at` | processed | `run` |
|---|---|---|
| `cutoff - 1.second` | yes | destroys |
| `cutoff` exactly | yes | **does not** destroy (`<` not `<=`) |
| `cutoff + 1.second` | yes | does not |
| `incinerate_after.ago` (midday, before end_of_day) | yes | **destroys** — this is why `travel 30.days` works today |
| `incinerate_after.ago.beginning_of_day` | yes | destroys |
| `incinerate_after.ago.end_of_day + 1.second` (next midnight) | yes | does not |

Also: `travel 30.days - 1.minute` after schedule — job is not yet runnable (`at:` still future); do not `perform` it early. After `travel 30.days`, job is runnable **and** `due?` is true for an untouched `updated_at`.

If `incinerate_after` is changed between enqueue and perform, `due?` uses the **current** config, not the wait used at enqueue. Characterize that.

#### 7. Unprocessed records

- `pending` / `processing`: `delivered!` path skipped; `assert_no_enqueued_jobs only: IncinerationJob`.
- Direct `Incineration.new(pending_email).run` with `updated_at` forced due: count unchanged.
- Job `perform_now` on a due but `processing` record: count unchanged, no raise.

#### 8. Already-deleted records

Keep `assert_nothing_raised` around enqueue+perform after `destroy!`.

Add:

- `perform_now` is not the missing-record path; deserialization happens on job load. Prefer `perform_later` + `perform_enqueued_jobs` as the current test does.
- A transient `ActiveJob::DeserializationError` that is **not** `::RecordNotFound` is **not** discarded (do not broaden `discard_on`). If too coupled to GlobalID, document as invariant and skip a brittle test.

#### 9. Attachment / record destruction

On a successful incineration after `travel 30.days`:

- `InboundEmail` row gone.
- `ActiveStorage::Attachment` for `raw_email` gone (`assert_not ActiveStorage::Attachment.exists?(id)`).
- `ActiveStorage::Blob` eventually purged: `assert_enqueued_with job: ActiveStorage::PurgeJob` (or `assert_difference` on blobs after `perform_enqueued_jobs` including purge). Do not require synchronous file delete in the incineration job itself — `purge_later` is the current contract.
- Failed/`due?` false path: attachment and blob **remain**.

Use `create_inbound_email_from_fixture("welcome.eml")` so a real blob exists ([`test_helper.rb`](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/test_helper.rb)).

### Integration-level observation (at least one)

Run a mailbox `receive` through to incineration, not only bang methods:

1. `freeze_time`.
2. `create_inbound_email_from_mail(...)` (status `:processing`).
3. `SuccessfulMailbox.receive inbound_email` → `delivered?`, exactly one `IncinerationJob` enqueued at `30.days.from_now`.
4. `travel 30.days`; `perform_enqueued_jobs only: IncinerationJob`.
5. Email row gone; `raw_email` attachment gone; purge job enqueued or blob gone after performing it.

Optional second observation: conductor `POST` incinerate ([`IncineratesController#create`](file:///home/user/workspace/repo/actionmailbox/app/controllers/rails/conductor/action_mailbox/incinerates_controller.rb)) on a due processed email destroys immediately with **no** extra job; on a fresh processed email it no-ops (`due?` false). This is the synchronous public path.
