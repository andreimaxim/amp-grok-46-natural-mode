## Conclusion

This leak is already handled when runner is entered through the supported API, `Rails::Command.invoke`.

- [`Rails::Command.invoke`](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L55-L69) wraps command dispatch in `with_argv(args)`.
- [`with_argv`](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L140-L146) snapshots `ARGV`, replaces it with invocation arguments, and restores the snapshot in `ensure`.
- [`RunnerCommand#perform`](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/runner/runner_command.rb#L24-L65) then replaces that temporary `ARGV` with `command_argv`, removing the code/file argument before user code executes.
- When `perform` returns or raises, the outer `with_argv` ensure restores the caller’s original `ARGV`.

Conceptually:

```ruby
# Rails::Command.invoke
saved = ARGV.dup
ARGV.replace(args)              # [code_or_file, *command_argv]
RunnerCommand.perform(...)
  ARGV.replace(command_argv)    # arguments visible to runner code
ensure
  ARGV.replace(saved)           # caller's ARGV restored
```

Therefore, adding another save/restore inside `RunnerCommand#perform` is redundant for `Rails::Command.invoke`. It only changes behavior for callers bypassing the command API and directly invoking `RunnerCommand.perform`.

## Upstream intent and history

This behavior is deliberate:

- [PR #38495, “Isolate ARGV in Rails::Command.invoke”](https://github.com/rails/rails/pull/38495) explicitly says mutations by commands must not affect code executing after an in-process `Rails::Command.invoke`.
- The resulting commit was `8ec7a2b7aaa31527686b05e0640d125299933782`.
- Rails later changed isolation from an empty temporary `ARGV` to one populated from invocation arguments. Commit `ddcfde2226217c0d65bd83a5d8dd25d7d3244f86` states that programmatic and CLI invocation should behave identically while **“ARGV will still be isolated between invocations.”**
- This contract is covered by tests:
  - [`ARGV is populated`](https://github.com/rails/rails/blob/main/railties/test/command/base_test.rb#L116-L124)
  - [`ARGV is isolated`](https://github.com/rails/rails/blob/main/railties/test/command/base_test.rb#L126-L140)

The runner-specific `ARGV.replace(command_argv)` also has intentional history:

- [Issue #28515](https://github.com/rails/rails/issues/28515) reported runner incorrectly exposing the code string in `ARGV`.
- [PR #28527](https://github.com/rails/rails/pull/28527) fixed it so runner code sees only trailing arguments.
- That landed as `a06a643e0572b8c983738c068ae637d020188c97`, merged by `36334bf989a6a3e3b7254804d6c7f6227e2a98e9`.

## Known issue status

I found no Rails issue or PR specifically reporting **runner leaking `ARGV` after an in-process `Rails::Command.invoke`**. The upstream isolation work already defines and tests the opposite behavior.

A direct `RunnerCommand.perform(...)` call can leave `ARGV` changed, but that is below the isolation boundary established by `Rails::Command.invoke`. A proposed inner `ensure` would be defensible only if Rails wants to make direct command-class invocation independently isolated; it should not be presented as fixing normal `Rails::Command.invoke` embedding.
