## Shaping brief: clearer `insert_all` / `insert_all!` behavior around `unique_by:` and `returning:`

This is a **behavior-change** brief. The desired progress is a contract people can predict per database, not a portable API that all adapters pretend to share. Evidence is this revision’s public docs, option validation, adapter capability predicates, and bulk-insert examples. Claims below are current-system facts unless labeled as a hypothesis or open question.

**Not in scope:** SQL generation, adapter internals, rollout, `upsert_all` except where it is needed to contrast skip vs raise.

---

### Problem frame

An application author bulk-inserts rows with `insert_all` (skip duplicates) or `insert_all!` (fail if not unique). They pass `unique_by:` to name the uniqueness rule and `returning:` to get values back for inserted rows.

Today those options do not mean the same thing on PostgreSQL, SQLite, MySQL, and MariaDB. A call that skips or returns rows on one database raises `ArgumentError` on another, or silently uses a different uniqueness rule. `insert_all!` documents `unique_by:` as “check just one unique index,” but the bang form still raises on any unique violation. Composite-primary-key models insert without `unique_by:` on MySQL/MariaDB and refuse on PostgreSQL/SQLite.

The pain is not missing bulk insert. It is writing one call, observing one database, and being wrong about the others — including whether duplicates were skipped, which index counted, whether any rows landed after a uniqueness error, and whether the result contains columns.

**Desired progress:** For each supported database, the author can tell in advance whether the call is allowed, which duplicates are skipped vs raised, what the result contains, and whether a failure leaves the table unchanged.

---

### Current baseline (adapter support)

Observed capability, not a design proposal:

| Database | Skip duplicates (`insert_all`) | Named conflict target (`unique_by:`) | Return inserted values (`returning:`) |
|---|---|---|---|
| PostgreSQL | yes | yes | yes |
| SQLite | yes | yes | yes |
| MySQL | yes | no | no |
| MariaDB | yes | no | yes on MariaDB ≥ 10.5; otherwise no |

Public contract today:

- Neither form instantiates models or runs callbacks/validations. Values still go through Active Record type casting and serialization.
- Input is an array of hashes that must share the same keys.
- Both forms return an `ActiveRecord::Result`.
- `insert_all` skips rows that collide with **every** unique index unless `unique_by:` narrows that (where supported).
- `insert_all!` raises `ActiveRecord::RecordNotUnique` if any row violates a unique index; **no rows from that call are inserted**.
- Default `returning:` is the primary key where returning is supported, and omitted where it is not.
- `unique_by:` may be a column, a column list, or a unique index name — PostgreSQL and SQLite only.
- `returning:` may be column names, `false`, or a known-safe SQL fragment — PostgreSQL, SQLite, and MariaDB (where returning exists) only.

---

### Behavioral outcomes

1. **Adapter honesty.** Asking for `unique_by:` or `returning:` on a database that does not support that option fails immediately with a clear error naming the adapter and the option. Omitting the option remains valid on that database.

2. **Skip vs bang.** `insert_all` never updates an existing colliding row. `insert_all!` never inserts a partial batch after a uniqueness failure.

3. **Default uniqueness (skip).** With no `unique_by:`, a duplicate against any unique index on the table is skipped. Existing row values stay as they were.

4. **Named uniqueness (skip, PostgreSQL and SQLite).** With `unique_by:`, only that unique index is the skip rule. A collision on a different unique index still raises `RecordNotUnique`.

5. **Bang uniqueness.** `insert_all!` raises on any unique-index violation, including when `unique_by:` is passed on databases that accept it. `unique_by:` on bang does not mean “only this index matters.”

6. **Returning.** Where supported, the result columns follow `returning:` (default primary key, selected columns, or a safe SQL expression). `returning: false` and `returning: []` insert successfully and return a result with no columns. Where unsupported, an explicit `returning:` value is an error; the default call still inserts and returns a result without those columns.

7. **Guards that do not depend on the database.** Empty input returns an empty result and inserts nothing. Mismatched hash keys raise `ArgumentError` and name missing/extra keys. Stored values match ordinary create for type casting and serialization. Timestamp fill follows the model setting unless `record_timestamps:` overrides it; an explicit timestamp in the hash is kept.

---

### Non-goals

- Changing `upsert_all` / `on_duplicate:` / `update_only:`.
- Making MySQL or MariaDB accept `unique_by:`, or making MySQL accept `returning:`.
- Prescribing SQL, ON CONFLICT vs ON DUPLICATE KEY, adapter internals, or a rollout plan.
- Instantiating models, running callbacks, or running validations on this path.
- A single portable call that hides adapter limits.

---

### Acceptance examples

Shared setup unless noted: `Book` has a primary key `id`, a unique index on `[author_id, name]`, a **partial** unique index on `isbn` that applies only when `published_on` is present, and — where expression indexes exist — a unique index on `lower(external_id)`. `Cart` uses a composite primary key `[shop_id, id]`.

#### A. Skip vs bang under the default uniqueness rule

**A1. Skip an existing primary-key collision (all adapters that can skip)**
- Situation: Book `id: 1` already exists.
- Action: `Book.insert_all [{ id: 1, name: "Agile Web Development with Rails" }]`
- Observe: book count unchanged; existing book unchanged.

**A2. Skip does not upsert (all adapters that can skip)**
- Situation: a book with `author_id: 8, name: "Refactoring", format: "EXPECTED"`.
- Action: `insert_all` a row with the same author/name and `format: "UNEXPECTED"`.
- Observe: count unchanged; `format` is still `"EXPECTED"`.

**A3. Same-batch duplicate identifiers, skip (all adapters that can skip)**
- Action: `insert_all [{ id: 111, name: "expected_new_name" }, { id: 111, name: "unexpected_new_name" }]`
- Observe: one row with `id: 111` and name `"expected_new_name"` (first payload kept; later duplicate skipped, not applied).

**A4. Same-batch duplicate on a non-id unique index, skip**
- Action: two hashes with `author_id: 8, name: "Refactoring"` and different or omitted ids.
- Observe: exactly one row inserted.

**A5. Bang on a uniqueness collision (all adapters)**
- Action: `insert_all!` including a row that collides with an existing unique index (e.g. existing `[author_id, name]`).
- Observe: `RecordNotUnique`; **no row from this call is present**. Contrast with skip, where non-colliding siblings in the same array would have been kept.

#### B. Named / composite / expression `unique_by:` (PostgreSQL, SQLite)

**B1. Skip only the named index**
- Action: `insert_all [{ id: 1, name: "Agile Web Development with Rails" }], unique_by: :index_books_on_author_id_and_name`
- Observe: `RecordNotUnique` because `id: 1` collides on the primary key, which is not the skip target.

**B2. Column, composite columns, index name, primary key**
- Action: four skip inserts with `unique_by: :isbn`, `unique_by: %i[author_id name]`, `unique_by: :index_books_on_isbn`, `unique_by: :id`.
- Observe: each inserts when it does not collide on that target.

**B3. Composite column order does not matter**
- Action: `unique_by: [:name, :author_id]` for an index on `[:author_id, :name]`.
- Observe: treated as that unique index, not as missing.

**B4. Expression unique index** (PostgreSQL, SQLite; not MySQL/MariaDB because they reject `unique_by:`)
- Situation: a book with `external_id: "abc"`.
- Action: `insert_all [{ external_id: "ABC" }], unique_by: :index_books_on_lower_external_id`
- Observe: skipped; count unchanged.

**B5. Partial unique index still partial**
- Situation: ISBN unique index applies only when `published_on` is set. Existing row has that ISBN and a published date.
- Action: bang insert with the same ISBN and a published date, `unique_by: :isbn`.
- Observe: `RecordNotUnique`.
- Boundary (open if we need a required example): same ISBN with `published_on` absent may not collide on that index.

#### C. Invalid or non-unique `unique_by:`

**C1. PostgreSQL / SQLite**
- Action: `insert_all` or `insert_all!` with `unique_by: :cats`, `unique_by: %i[author_id isbn]`, or `unique_by: :author_id` (no unique index).
- Observe: `ArgumentError` matching `No unique index` — before any insert. For bang, unsupported/invalid `unique_by:` still fails the option check on skip’s finder only when skip/upsert resolves the index; bang currently accepts `unique_by:` on these adapters without resolving it (**open question 1**). Skip form definitely raises `No unique index`.

**C2. MySQL / MariaDB**
- Action: any `insert_all` / `insert_all!` with `unique_by:` present.
- Observe: `ArgumentError` that the adapter does not support `:unique_by`. No insert.

#### D. Composite primary keys

**D1. PostgreSQL / SQLite, skip without `unique_by:`**
- Action: `Cart.insert_all [{ id: 2, shop_id: 1, title: "My cart" }]`
- Observe: `ArgumentError` / `No unique index found for id` (model primary-key setting does not match the composite key).

**D2. PostgreSQL / SQLite, skip with `unique_by: [:shop_id, :id]`**
- Observe: row inserted.

**D3. PostgreSQL / SQLite, bang without `unique_by:`**
- Action: `Cart.insert_all! [{ id: 2, shop_id: 1, title: "My cart" }]`
- Observe: insert succeeds; bang does not require a resolvable unique index.

**D4. MySQL / MariaDB**
- Action: `Cart.insert_all` / `insert_all!` without `unique_by:`.
- Observe: rows insert. `unique_by:` is not available (see C2).

#### E. `returning:`

Where returning is supported: PostgreSQL, SQLite, MariaDB ≥ 10.5.

**E1. Default**
- Action: `insert_all! [{ name: "Rework", author_id: 1 }]`
- Observe: result is `ActiveRecord::Result`; columns are the primary key (`id` for Book).

**E2. `returning: false` and `returning: []`**
- Observe: insert succeeds; result columns are empty.

**E3. Selected columns**
- Action: `returning: [:id, :name]`
- Observe: result includes `name` `"Rework"` for the inserted row.

**E4. SQL expression**
- Action: `returning: Arel.sql("UPPER(name) as name")`
- Observe: result `name` is `"REWORK"`. A raw string that is not marked known-safe is rejected.

**E5. MySQL (and MariaDB without returning)**
- Default call: insert succeeds; result does not include returned primary-key columns from this feature.
- Explicit `returning: :id` / `[:id, :name]` / SQL: `ArgumentError` that the adapter does not support `:returning`.

**E6. Attribute alias** (where returning exists)
- Action: insert with aliased attribute `title`, `returning: :title`.
- Observe: result columns include `"title"`.

#### F. Empty input and mismatched keys (all adapters)

**F1. Empty array**
- Action: `insert_all([])` and `insert_all!([])`
- Observe: empty result; table unchanged. Does not require skip/returning support.

**F2. Extra key**
- Action: hashes `{ name:, author_id: }` and `{ name:, author_id:, isbn: }`
- Observe: `ArgumentError` that all objects must have the same keys, mentioning extra `isbn`.

**F3. Missing key**
- Inverse of F2; error mentions missing `isbn`.

#### G. Type casting, serialization, timestamps

**G1. Casting/serialization match `create`**
- Action: insert a value that the model type-casts or serializes (array-like name where that type exists; serialized `content`; enum `status:`).
- Observe: persisted value equals the value from `create!` with the same input. String values on a custom coder are not double-encoded.

**G2. Timestamp override**
- Default: when the model records timestamps and the hash omits them, created/updated timestamps are set.
- `record_timestamps: false`: those columns are not auto-filled even if the model setting is on.
- `record_timestamps: true`: they are auto-filled even if the model setting is off.
- If the hash already includes `created_at` / `updated_at` / `updated_on`, that value is kept.

*(Timestamp examples in this revision are written against upsert; insert uses the same option and fill rule. Treat insert-specific confirmation as steering evidence, not a new requirement.)*

#### H. Atomicity difference, skip vs bang

**H1. Bang is all-or-nothing for uniqueness**
- Action: `insert_all!` of three rows where the third collides.
- Observe: exception; none of the three exist afterward.

**H2. Skip is per-row for uniqueness**
- Action: `insert_all` of a new unique row plus a colliding row.
- Observe: the new row exists; the colliding row does not replace existing data.

These two are required, not illustrative: they are the product distinction between the two methods.

---

### Steering evidence

**Success looks like:** An author can read adapter support once and predict allow vs refuse, skip vs raise, result columns, and leftover rows for the examples above — without assuming PostgreSQL behavior on MySQL/MariaDB.

**Investigate / do not ship if:**

- `insert_all` on a skip-capable adapter updates an existing colliding row.
- `insert_all!` uniqueness failure leaves some rows from that call in the table.
- MySQL/MariaDB accept `unique_by:` or MySQL accepts explicit `returning:`.
- PostgreSQL/SQLite `unique_by:` on skip ignores other unique indexes when it should still raise, or refuses a real unique index (including reversed composite columns or an expression index name).
- Empty input or mismatched keys start depending on the database.
- Serialized/cast values from insert diverge from `create`.

**Reconsider the framing if** the real demand is “make all four databases do the same thing” (a portability feature) rather than “make the existing differences obvious and stable.” That would be a different outcome: new capability on MySQL/MariaDB, not clearer behavior of what this revision already does.

---

### Open questions

1. **Bang + `unique_by:`.** Docs say bang can check just one unique index. Implementation accepts `unique_by:` on PostgreSQL/SQLite but still raises on any unique violation, and does not resolve the index the way skip does. Should the clarified contract keep today’s “accepted but not narrowing” behavior, or is that a defect against the documented meaning?

2. **Skip + invalid `unique_by:` on bang.** Should bang reject unknown/non-unique `unique_by:` with `No unique index` the same way skip does, or keep ignoring it after the adapter-support check?

3. **Partial unique indexes.** Is “collision only when the index predicate matches” a required skip/bang example, or only a boundary to mention?

4. **MariaDB versions below 10.5.** Treat as MySQL-like (no returning) without further product work?

5. **Default skip target on composite PK models.** Is “must pass `unique_by:` on PostgreSQL/SQLite, must not pass it on MySQL/MariaDB” the intended long-term contract, or only current behavior we should not paper over?

6. **Empty `insert_all([])`.** Behavior is adapter-independent; one example in this revision is gated on upsert support. Confirm empty input is required on every adapter.
