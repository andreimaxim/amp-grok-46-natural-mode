**Verdict: the claim is incorrect, and the patch is not safe at this revision.** Do not land it. Rewriting a signed cookie after a successful secret/digest rotation is the documented upgrade path, not an unnecessary write.

I applied the one-liner locally to `SignedKeyRotatingCookieJar#parse` only. Two existing rotation tests error immediately. The file is restored.

### Findings (by severity)

#### 1. High — rotation no longer upgrades the cookie; removing the rotator will invalidate it

The signed jar’s rewrite is intentional. Read path:

1. `SignedKeyRotatingCookieJar#parse` verifies with `on_rotation: -> { rotated = true }`, then `super(..., force_reserialize: rotated)` in [`cookies.rb`](actionpack/lib/action_dispatch/middleware/cookies.rb) (~644–646).
2. `SerializedCookieJars#parse` does `self[name] = { value: value }` when `force_reserialize || reserialize?(dumped)` (~600–608). That write goes through `commit` → `CookieJar#[]=` and lands in `@set_cookies`.
3. `Messages::Rotator#read_message` calls `on_rotation` only when the **primary** verifier fails and a **fallback** succeeds ([`rotator.rb`](activesupport/lib/active_support/messages/rotator.rb) 29–44). Current-key cookies are not rewritten today. Old-key cookies are.

`reserialize?` only covers serializer-format upgrades (hybrid marshal→JSON, JSON→MessagePack). It is false for a same-serializer secret/digest rotation, so `force_reserialize: rotated` is the **only** trigger that re-signs with the new key/digest.

That is the documented contract in [`guides/source/security.md`](guides/source/security.md) (~409–415): old SHA1 cookies are rewritten with the new digest on access so they stay valid after the rotator is removed.

Hard evidence: with `force_reserialize: false`, these tests error `ActiveSupport::MessageVerifier::InvalidSignature: invalid message string` because `@response.cookies["user_id"]` is nil:

- `test_signed_cookie_rotating_secret_and_digest` ([`cookies_test.rb:641`](actionpack/test/dispatch/cookies_test.rb)) — old SHA1 + old secret is readable, then asserts the Set-Cookie verifies with the **new** SHA256 + current secret.
- `test_rotating_signed_cookies_digest` ([`cookies_test.rb:1000`](actionpack/test/dispatch/cookies_test.rb)) — SHA1→SHA256 digest rotation, same rewrite assertion.

The patch does not “avoid unnecessary rewrites.” It disables the rewrite the rotator exists to perform.

#### 2. Medium — signed vs encrypted jars would diverge

The proposed diff touches only the signed jar. `EncryptedKeyRotatingCookieJar#parse` still passes `force_reserialize: rotated` (~694–696). Encrypted rotation tests (`test_encrypted_cookie_rotating_secret`, legacy HMAC-CBC upgrades) would keep rewriting; signed would not. Same `on_rotation` contract, two behaviors.

#### 3. Low — leftover `rotated` is unused

Leaving `rotated = false` and the `on_rotation` lambda produces `warning: assigned but unused variable - rotated` (observed under `bin/test`). If this were ever the desired behavior, the rotation callback would need to be removed too — which is another signal the rewrite is the point of that callback.

Serializer/digest upgrades are two different layers: the cookie verifier uses `NullSerializer`; payload format is applied *after* verification in `SerializedCookieJars`. Key rotation cannot be folded into `reserialize?`.

### Tests the proposed change would need (if pursued anyway)

Do not invert the existing rotation tests without also changing the security/upgrade guides. If the product decision really is “read old cookies but never upgrade them,” the patch is still incomplete. Needed:

1. Keep `test_signed_cookie_rotating_secret_and_digest` / `test_rotating_signed_cookies_digest` asserting **read** of the old cookie, but change the write assertion to `assert_nil @response.cookies["user_id"]` (no Set-Cookie).
2. A follow-up request that **removes** the rotator and shows the still-old cookie is now unreadable — that is the behavior this patch would ship, and it contradicts the current guides.
3. The same pair for encrypted cookies, or an explicit test that signed and encrypted rotation-write policy differ.
4. A current-signature control: request cookie == response (already true; worth pinning so “no rewrite” cannot regress the other way).
5. Tampered / expired: already covered; they must keep returning nil with no Set-Cookie.

I would not rewrite this patch. The one-line change fights the rotator, the tests, and the documented upgrade story. If the real pain is extra Set-Cookie traffic, that belongs in a different design (opt-in, or skip rewrite when the rotated config will remain forever), not a silent `false`.
