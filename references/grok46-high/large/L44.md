**Verdict: request changes.** The claim is wrong for the supported embedding path, and restoring ARGV in `RunnerCommand#perform` is the wrong fix.

### Claim vs implementation

`perform` does replace ARGV and never restores it:

```ruby
## railties/lib/rails/commands/runner/runner_command.rb
def perform(code_or_file = nil, *command_argv)
  ...
  ARGV.replace(command_argv)
  # eval / Kernel.load / stdin; $0 set only for files
end
```

That does **not** leak through normal in-process embedding. `Rails::Command.invoke` already snapshots and restores ARGV:

```ruby
## railties/lib/rails/command.rb
def invoke(...)
  with_argv(args) do
    command.perform(command_name, args, config)
  end
end

def with_argv(argv)
  original_argv = ARGV.dup
  ARGV.replace(argv)
  yield
ensure
  ARGV.replace(original_argv)
end
```

A nested/in-process `Rails::Command.invoke("runner", ...)` already restores the caller’s ARGV even if `perform` mutates it, including on `exit 1` (`SystemExit` still runs `ensure`). That is intentional (PR #38495 / later “ARGV is populated but isolated” work) and covered by `railties/test/command/base_test.rb` (`ARGV is populated`, `ARGV is isolated`).

The proposed

```ruby
old_argv = ARGV.dup
ARGV.replace(command_argv)
...
ensure
  ARGV.replace(old_argv)
```

is redundant there: the inner restore puts back `[code_or_file, *command_argv]`, then outer `with_argv` puts back the real caller ARGV.

A leak exists only if someone bypasses `invoke` and calls `RunnerCommand.perform` / Thor `dispatch` directly. That is below the isolation boundary Rails already chose. Generate/console do the same unrestored `ARGV.replace` and rely on `with_argv`.

### Edge cases vs `runner_test.rb`

Both `railties/test/commands/runner_test.rb` and `railties/test/application/runner_test.rb` drive `bin/rails runner` via the isolation helper (fork/`rails()`). They never observe ARGV after `perform` returns in-process. They do cover:

| Case | Behavior | ARGV restore relevant? |
|---|---|---|
| Inline code | `eval(code, TOPLEVEL_BINDING, __FILE__, __LINE__)` | During run, ARGV is `command_argv`. After CLI process, irrelevant. |
| Ruby filename | `File.exist?` then `Kernel.load`; `$0 = expanded_file_path` | ARGV set; **`$0`/`$PROGRAM_NAME` never restored** |
| stdin `-` | `eval($stdin.read, ...)`; `$0` unchanged | ARGV still replaced |
| SyntaxError / NameError / missing `*.rb` | message + `exit 1` | `ensure` would run, but `with_argv` already does |
| Executor | `ARGV.replace` happens **before** `conditional_executor`; `--skip-executor` / `-w` works | Restore-after-wrap would not change during-run ARGV |
| Args beginning with `-` | `test_should_set_argv_when_running_code` expects `--foo,a1,-b,a2,a3,--moo` | Proposed change does not affect this |
| Nested invoke | untested in runner tests; outer `with_argv` nests correctly | Inner restore unnecessary |

`$0`/`$PROGRAM_NAME` **is** a real in-process leak for the file path (`test_should_set_dollar_0_to_file` / `test_should_set_dollar_program_name_to_file` only assert the value *during* the script). The PR does not restore `$0`.

### Compatibility / missing tests

- Harmless double-restore if stacked on `with_argv`, but it paper-covers the wrong API and invites the same patch in generate/console.
- If someone *did* call `perform` directly and the script mutated ARGV intending that to stick, the new `ensure` would clobber it. CLI `bin/rails runner` exits, so this is not a user-facing CLI bug.
- No runner test asserts ARGV after in-process invoke. Adding the `ensure` without an invoke-level test would not prove the claimed embedding bug.

### More precise change

Do **not** restore ARGV inside `perform` as the fix for “embedding leaks runner arguments.”

If the goal is embedding hygiene:

1. Keep isolation at `Rails::Command.invoke` / `with_argv` (already the contract).
2. If file runner must be embeddable without leaking process identity, restore `$0`/`$PROGRAM_NAME` around `Kernel.load`, not ARGV.
3. Add an in-process test: `original = ARGV.dup; Rails::Command.invoke("runner", ["puts ARGV.inspect", "a"]); assert_equal original, ARGV` — this should already pass.
4. Optionally test nested invoke and `$0` restoration if you decide that is a supported contract.

**Request changes.** The ARGV leak claim is false for `Rails::Command.invoke`; the proposed `perform` `ensure` is redundant there, untested by `runner_test.rb`, and misses the actual file-path `$0` leak.
