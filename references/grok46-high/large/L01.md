## Verification strategy for `#touch`

Prove preservation only through `record.touch(...)` and public observations: return value, exception class/message, in-memory attributes, a reloaded row, dirty/saved-change APIs, lifecycle predicates, and callback ledgers. Do not compare private helpers (`_touch_row`, `_update_row`, `@_trigger_update_callback`, Dirty/Optimistic overrides).

On a successful persisted touch, read all of: return value; in-memory timestamps/extra names/`lock_version`; the DB row via `reload` or a second `find`; `changed?` / `changed` / `<attr>_changed?`; `saved_changes?` / `saved_changes`; callback flags; `persisted?` / `new_record?` / `destroyed?` / `readonly?`. SQL matching is allowed only to show whether a write happened.

### Record state

**Persisted.** Force `updated_at` into the past with `update_columns`, then `touch`. Expect a truthy return; timestamps advanced in memory and after reload; other columns unchanged; lifecycle predicates unchanged. Make the record invalid first: `touch` still succeeds (no validations).

**New.** `Model.new.touch` (with or without names) raises `ActiveRecord::ActiveRecordError` whose message includes `Cannot touch on a new or destroyed record object` and mentions `persisted?`, `new_record?`, or `destroyed?`. No INSERT/UPDATE; instance stays new; timestamps and callback ledgers unchanged. A different exception is not equivalent.

**Destroyed.** After both `destroy` and `delete`, `touch` raises the same error as the new-record case. Not `FrozenError` (that would mean the `persisted?`/`readonly?` guards moved after mutation). Row stays gone; ledgers empty.

**Readonly record.** `readonly!` then `touch` raises `ActiveRecord::ReadOnlyRecord` with `"#{Model} is marked as readonly"`. Timestamps and ledgers unchanged.

**Readonly attribute.** `touch(:born_at)` raises `ActiveRecord::ActiveRecordError` with `"born_at is marked as readonly"` before any UPDATE. Distinct from whole-record `ReadOnlyRecord`.

### Timestamps, custom names, aliases, explicit time

**Defaults.** No-arg `touch` updates `updated_at`/`updated_on` only. `created_at`/`created_on` change only when named.

**No timestamp columns.** `Car.first.touch` returns truthy, raises nothing, issues no UPDATE, still runs `after_touch`. That is not the no-row-updated path.

**Aliases.** On `Developer` (`updated_at` → `legacy_updated_at`), both the alias accessor and the real column show the new time; `saved_changes` keys are the real names (`legacy_updated_at`, `legacy_updated_on`). Passing alias or column name writes the same underlying attribute.

**Extra names.** `task.touch(:ending)` and `touch(:starting, :ending)` set those columns plus default update timestamps to the touch time; they are not left dirty. Reloaded row matches.

**Explicit `time:`.** Every touched attribute equals that exact time in memory and after reload. Omitting `time:` is near `Time.now` in the connection timezone (`assert_in_delta`), not a stale in-memory value.

### Optimistic locking

**Success.** `person.touch` increments `lock_version` in memory and DB, advances `updated_at`, leaves `changed?` false, and puts `"lock_version"` and `"updated_at"` in `saved_changes`. A second `find` + `touch` increments again.

**Stale / 0 rows under locking.** Update one instance; `touch` the other. Raises `ActiveRecord::StaleObjectError` (`error.record` is the stale instance). Stale `lock_version` is not left incremented; `saved_changes?` is false; winner’s row is untouched; `after_touch` and `after_commit` do not run.

`preserve_lock_version_on_touch` is a separate public mode (no bump, no stale raise). Default `touch` must still bump and stale-raise.

### Dirty tracking and saved changes

```ruby
developer.salary += 10_000
developer.touch
```

`salary` stays dirty and is not persisted (`reload` restores it). `saved_changes` keys are only the touched timestamps, not `salary`. After a clean `touch`, `changes` is empty, `saved_changes` holds old/new pairs, and touched attributes are not `<attr>_changed?`.

### Callbacks

Only `after_touch`, `after_commit`, and `after_rollback` run. `before_save` / `after_update` / validations stay silent.

- Successful implicit touch: `after_touch` once; `after_commit` on update once; no rollback.
- Nested `requires_new` transaction: `after_touch` at the call; `after_commit` only after the outermost commit.
- `touch` then `raise ActiveRecord::Rollback`: `after_touch` ran; `after_commit` did not; `after_rollback` on update ran; timestamps restored.
- `Model.no_touching { record.touch }`: no UPDATE, timestamps unchanged, `after_touch` does not run.

### No-row-updated (non-locking)

```ruby
topic = Topic.find(id)
Topic.where(id: topic.id).delete_all
result = topic.touch
```

Without locking: `touch` returns **`false`**, not `StaleObjectError`. In-memory timestamps match pre-touch (implicit transaction rolls back on a falsy status). Row stays gone. `after_touch` **does** run; `after_commit` / `after_rollback` on update do **not**; `saved_changes?` is false; unrelated dirt remains dirty.

With locking, the same 0-row UPDATE is `StaleObjectError` and `after_touch` does **not** run. Those two outcomes must not be swapped.

Empty-name touch on a model with no timestamp columns is not this case: truthy return, no UPDATE, `after_touch` runs, no `after_commit` on update.

If two implementations match on every observation above, the public `touch` contract is preserved. Divergence on any of them is a behavior change, even if private helpers look equivalent.
