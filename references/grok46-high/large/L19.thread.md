A deterministic equality predicate is not “current-scheme ciphertext only.” `ExtendedDeterministicQueries` exists to bind every stored form SQL can see. `EncryptedAttributeType#deserialize` can try current, then `previous:`, then plaintext. `WHERE`/`find_by` cannot. ### Query vs read

- **Read/decrypt:** `deserialize` → current decrypt → `previous_types` → plaintext if `support_unencrypted_data?`. `find(id)`, `reload`, and attribute readers keep working.
- **Query:** `where` / `exists?` / `Base.find_by` rewrite hash predicates to `[value, AdditionalValue(previous_type)...]`. Previous types include configured `previous:` schemes plus a `NullEncryptor` clean-text type when unencrypted data is supported. That is what makes `IN (current, old ciphertext, plaintext)` match mixed rows.

`downcase` / `ignore_case` encrypted rows already match via current `serialize` (both downcase before encrypt). They do not justify dropping expansion. Unencrypted rows and `previous:` rows do.

`ignore_case`’s `original_<column>` is a **read** path (`preserve_original_encrypted`). Queries hit `name`, not `original_name`.
