## Assistant

**Problem frame:** A Rails app or library author ingesting configuration, options, or params-like hashes needs both values from a source that used `:key` and `"key"` as distinct entries. Conversion or update through `ActiveSupport::HashWithIndifferentAccess` treats those as one key, keeps only one value, and does not say which. Nested and multi-hash ingestion can drop whole subtrees the same way. The author cannot tell that data was discarded, so mixed-key configuration cannot be ingested with confidence.

This is existing-system behavior, not a greenfield feature. Discovery used the public contract, the documented update note, the test suite’s assignment/merge examples, and direct conversion/update runs. Those establish stimulus, observable result, and the lack of a discard signal. They do not prescribe a fix.

---

**Current observable behavior**

Indifferent access is meant to treat `:foo` and `"foo"` as the same key (params-style). After conversion, keys are strings; lookup by either form returns the same stored value.

When a **regular** hash that already contains both `:key` and `"key"` is converted or `update`/`merge`d in:

- Exactly one value remains under that indifferent key.
- The public contract says **which value wins is unspecified**.
- Afterward, `size` is 1, both `:key` and `"key"` look up the survivor, and nothing reports that a second source entry existed.

Observed in this checkout (Ruby hash iteration order; **not** a promised winner):

- `{ :key => "symbol", "key" => "string" }` converts to `{ "key" => "string" }`.
- `{ "key" => "string", :key => "symbol" }` converts to `{ "key" => "symbol" }`.
- Sequential assignment is different and specified by write order: `h[:key] = "first"` then `h["key"] = "second"` leaves `"second"`.

An `update` block on a regular mixed-key hash is invoked once per source pair as each is written into the receiver. It does **not** present “this source had two keys that collide under indifferent access.” If the other hash is already indifferent, the collision has already happened before `update`.

There is no user-visible channel today that says a value was discarded.

---

**Behavioral outcome (desired)**

Someone ingesting mixed-key hashes can tell whether conversion or update dropped a value because `:key` and `"key"` were collapsed, instead of silently keeping one unspecified survivor.

Until the open questions below are answered, this is an outcome to steer toward, not a chosen policy (raise vs report vs opt-in, what to disclose, default vs compatible silence).

---

**Examples**

Required core — silent top-level discard:

- **Given** a regular hash `{ :timeout => 30, "timeout" => 5 }` (two entries, different values).
- **When** it is converted to indifferent access, or used as the argument to `update`/`merge`.
- **Then** the result has one `"timeout"`, lookups by `:timeout` and `"timeout"` agree, `size` is 1, and there is no indication that 30 or 5 was dropped. The documented winner is unspecified.

Required nested — subtree loss, not only a leaf:

- **Given**
  ```ruby
  {
    "database" => { adapter: "pg", "adapter" => "mysql", pool: { size: 5, "size" => 10 } },
    :database  => { adapter: "sqlite" }
  }
  ```
- **When** converted to indifferent access.
- **Then** the observed result is `{ "database" => { "adapter" => "sqlite" } }`. The first `database` hash, including `pool`, is gone. Nested mixed keys collapse the same way when they are the only collision.

Required multi-hash — two different collision sites:

- **Given** an indifferent receiver and `update`/`merge` of `{ :a => 1, "a" => 2 }` then `{ "b" => 3, :b => 4 }`.
- **When** both regular hashes are applied.
- **Then** the result has one `a` and one `b`. Across hashes, later-hash overwrite of the same indifferent key is ordinary merge. **Inside** each hash, mixed `:a`/`"a"` still has an unspecified survivor. The caller cannot tell an intra-hash collapse from a normal later-hash overwrite.

Boundary — sequential writes are not the ingestion bug:

- **Given** an indifferent hash.
- **When** the caller assigns `:key` then `"key"` (or `store` in that order).
- **Then** last write wins. That is observable assignment, not an unspecified intra-hash collapse.

Boundary — identical values still hide cardinality:

- **Given** `{ :k => "same", "k" => "same" }`.
- **When** converted.
- **Then** one entry remains. Even though the value matches, the caller cannot see that the source had two keys.

Counterexample — no mixed pair, no discard:

- **Given** `{ host: "db.internal" }` or `{ "host" => "db.internal" }` only.
- **When** converted or merged.
- **Then** the value is kept; either key form reads it. That convenience must remain.

Illustrative — update block is not a collision detector:

- **Given** `{ "k" => "old" }` (indifferent) updated with `{ :k => "from_sym", "k" => "from_str" }` and a block.
- **When** update runs.
- **Then** the block may run for each write against the same indifferent key, but the source is never described as “two colliding keys in one hash.”

---

**Compatibility constraints** (user-visible, not a design)

- Indifferent lookup (`:foo` and `"foo"` as one key) stays the reason this type exists, including params-style use.
- Today, mixed-key conversion/update does not raise and does not report discard. Callers may depend on “it just works” and on last-write sequential assignment.
- Changing default conversion to fail, or pinning a winner, would change existing ingestion. Any stricter detection is in tension with that silence.
- `merge` is non-mutating relative to the receiver; `update` mutates. Nested hashes become indifferent on the way in. Those external shapes stay in scope as the paths that collapse keys.
- Unspecified winner is part of the public update documentation for a regular hash with both `:key` and `"key"`.

---

**Steering evidence / success signals**

Success (once policy is chosen): a caller ingesting mixed-key configuration can detect that a value was discarded, or can rely on a stated, stable outcome instead of an unspecified survivor. Nested and multi-hash cases do not hide extra loss. Same-value collisions are not invisible if cardinality matters. Sequential last-write assignment still behaves as assignment.

Contradicts success: mixed-key conversion still yields one value, unspecified winner, no signal; nested collapse still drops subtrees unnoticed; detection only works at the top level; or ordinary single-form hashes (`:host` only) start failing or changing values.

Suggests the framing is wrong: real pain is only undocumented winner order, not undetectable discard; or operators already treat mixed keys as programmer error and only want a documented last-write rule; or the costly cases are deep config trees where any extra work on every conversion is unacceptable. That evidence should reopen the outcome (detect vs define vs leave unspecified) rather than assume a particular mechanism.

---

**Open questions** (do not resolve here)

1. **Opt-in vs default.** Should mixed-key detection or a defined winner be opt-in so current silent collapse remains the default, or should new behavior apply to all conversion/update? Who is allowed to choose (the converting caller vs a process-wide setting) is unset.

2. **Error vs observation.** On collision, should ingestion fail, or complete and only report that data was discarded? Failure protects config correctness; observation preserves “always get a hash back.”

3. **Key disclosure.** If anything is reported or raised, should it name the colliding key, both original forms (`:key` and `"key"`), both values, and nest path (`database.adapter`)? Disclosure helps debugging and may leak config in logs.

4. **Performance.** Conversion/update is on hot paths (params, options, nested config). Any collision work that is more than today’s single pass may be unacceptable if it applies to hashes with no mixed keys. Whether “no mixed keys” must stay as cheap as now is unset.

Also unset, and should stay unset until those four are answered: whether same-value collisions count; whether sequential assignment should be treated like intra-hash collapse; whether already-indifferent hashes (collapsed earlier) need a second signal.

---

This is the working behavioral specification: **undetectable mixed-key collapse during indifferent conversion/update**, with nested and multi-hash loss, compatibility with silent indifferent access, and those four questions left open. No API, structure, or algorithm is chosen.

If this framing is wrong—if the real need is only a documented winner, or a hard error by default—correct that before any design work.
