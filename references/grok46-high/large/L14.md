## Shaping brief: required configuration reads through OrderedOptions

This is a **behavior change**: keep successful required reads as they are, and make *failed* required reads easier to understand and diagnose. It is not a new configuration system and not a defect against an established contract—the bang reader already raises. The change is the quality of the failure, not the existence of a required-read path.

The same brief was sent to [the parent thread](https://ampcode.com/threads/T-01a06130-c887-765b-8c03-b8a9325c590a).

### Problem frame

A Rails maintainer or application author is reading a value that must be present—an API key, a host, a queue name—through `ActiveSupport::OrderedOptions` (Rails config, `config_for`, credentials-style objects). Today they can require a value by using the bang reader. When that fails, every failure looks the same, so they cannot tell whether the value was never set, was set to `nil`, was `false`, or was only whitespace. That slows diagnosis at boot and in inherited/env overrides. After this work, a failed required read should make the actual situation obvious, without changing successful returns or Hash-like ordering.

### User pain

Hypothesis from the request plus the behavior above, not a measured incident:

1. **Every required-read failure is identical.** Missing, `nil`, `false`, and whitespace all say `:foo is blank`. The reader cannot tell what to fix (unset env, explicit nil override, boolean flag, padded string).
2. **`false` is a real config value** (`allow_concurrency = false` is a first-class test case) but cannot be required with bang; it looks “blank.”
3. **The failure is thin.** The error does not identify the key or the options object the way `Hash#fetch` does, so nested or inherited config is harder to locate.
4. **Silent missing reads.** A missing non-bang reader returns `nil`, same as an explicit `nil`, so optional vs required confusion is easy.
5. **Inherited overrides hide origin.** A child can blank out a parent value; bang still says “is blank” with no hint that a local override, not the parent, is why.

### Desired outcomes

Stated as what a person can observe, not how it is built.

1. **A failed required read distinguishes the situation** enough to act: never set vs set-but-unusable (nil / blank string) vs a set boolean `false`, without the reader having to re-probe the object.
2. **A successful required read is unchanged:** if today’s bang returns a value, it still returns that same value (`"value"`, `0`, other present objects).
3. **Hash-like ordering is unchanged:** iterating keys/values after mixed string and symbol writes still yields symbols in insertion order (parent keys then child keys for inheritable copies).
4. **Everyday lookup stays interchangeable** for strings and symbols on `[]`, dynamic readers/writers, and the first argument to `dig`.
5. **Inheritance stays override-based:** a child still sees the parent until it writes; a child write, including a blanking write, is what a required read observes.
6. **Compatibility for non-required reads:** missing dynamic readers still return `nil`; `respond_to?` still accepts names that have never been assigned, unless a later confirmed outcome says otherwise.

### Compatibility boundaries

Must not change:

- Successful bang and non-bang return values for present objects, including `0` and non-blank strings
- Symbol storage / string-or-symbol read interchange for `[]`, `[]=`, dynamic accessors, and `dig`’s first key
- Insertion order of keys, and InheritableOptions’ parent-then-own key listing
- Child override winning over parent, including `nil` and blank overrides
- Non-bang missing read returning `nil` rather than raising

Must not expand into:

- A different configuration object or Rails config API
- Changing `EncryptedConfiguration#require` (nil-only nested require is a separate contract)
- Changing `key?`’s symbol-only answer unless that is later confirmed as part of diagnosis
- Performance, freezing, or Ractor shareability work

### Non-goals

- New classes, methods, storage, or other implementation mechanics
- Making missing *non-bang* reads raise
- Redefining `blank?` / `presence` globally
- Redesigning string vs symbol `key?` inconsistency as its own project
- Changing successful credentials / `config_for` return shapes

### Example journeys

Required unless noted. Actor: application author or Rails maintainer reading config.

**1. Present required value (core success — must stay).**  
Config has `api_key = "secret"`. They require it. They get `"secret"`, same as the non-bang read.

**2. Never set (core failure).**  
No `api_key` is assigned. They require it. They can tell the name was never set, not that a blank string was stored.

**3. Explicit nil (boundary).**  
They set `api_key = nil` (or a child overrides a parent key with `nil`). They require it. They can tell the name is set and empty, and in the child case that the child value is what failed—not that the parent was missing.

**4. Whitespace-only string (boundary).**  
They set `host = "   "`. Non-bang still returns `"   "`. A required read fails in a way that is recognizably “blank text,” not “missing key.”

**5. Boolean false (boundary / open).**  
They set `allow_concurrency = false`. Non-bang still returns `false`. Today a required read raises `:allow_concurrency is blank`. After this work, the failure (or success) must make it obvious that the stored value is `false`, not that the key is missing. Whether requiring `false` should succeed is an open question below.

**6. Inherited present value (core).**  
Parent has `foo = "parent"`; child does not override. Required read on the child returns `"parent"`.

**7. Child present override (core).**  
Child sets `foo = "child"`. Required read on the child returns `"child"`, not the parent.

**8. Ordering unchanged (counterexample to “rewrite storage”).**  
They assign with mixed strings and symbols. Each-ing the object still yields symbol keys in write order. A required-read change that scrambled order would be a failure of this brief.

**9. Optional read unchanged (counterexample).**  
They call the non-bang reader for a missing name. They still get `nil`, not an exception.

### Acceptance evidence

**Success looks like:** someone hitting a boot-time missing or blank setting can say what was wrong from the failure alone (unset vs nil vs blank text vs false) and then set or override the right place (parent vs child). Existing code that already bang-reads present values still gets the same objects back. Config dumps / iteration order still match today’s tests.

**Investigate / do not ship if:**

- A bang read that used to return a present value now raises or returns something else
- Key order in `each` / `to_h` / `keys` changes
- String and symbol reads of the same assignment diverge
- A child stops seeing an un-overridden parent value
- Non-bang missing reads start raising

**Reconsider the problem framing if:**

- People still cannot tell missing from blank after the failure text changes (wrong diagnosis of the pain)
- The real confusion is `EncryptedConfiguration#require` (“Missing key”) vs OrderedOptions bang (“is blank”), i.e. two required-read dialects, not OrderedOptions itself
- The real confusion is `false` being blank, and clearer messages without changing that rule still surprise boolean config authors

### Open questions

These would change the outcome if answered differently:

1. **Should a required read of `false` succeed?** Today it fails as blank. `false` is a documented, tested configuration value. Confirm whether “required” means “set, even if false” or “present in the `presence` sense.”
2. **How much distinction is enough?** Missing vs any-blank may be enough; or missing vs nil vs whitespace vs false may all need to be distinct.
3. **Are credentials bang readers in scope?** They are the documented public required-read. Improving OrderedOptions failures would change what `credentials.some_api_key!` shows. Confirm that is wanted.
4. **Must the exception remain `KeyError` with the same class, or may the class/message change as long as it still raises?** Compatibility for `rescue KeyError` is implied but not stated.

No implementation is proposed. Successful return values and Hash-like ordering are frozen; only the understandability of failed required reads is in play.
