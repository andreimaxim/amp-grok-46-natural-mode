## Maintenance brief: development route reload after an invalid route file

Kind of work: **maintenance** of the existing development route-reload contract. The named boundary is `Rails::Application::RoutesReloader` / `app.routes_reloader`, the application and engine route sets it reloads, external `draw` paths, and `config.file_watcher`. This is not a new routing capability and not a production behavior change.

Ticket-provided claim (not independently reproduced as a request-level bug): in development, editing one application or mounted-engine route file so it contains invalid Ruby can leave a developer unsure whether the previous routes are still usable and when a corrected file takes effect.

### Discovery (current behavior)

Inspected: `RoutesReloader`, `Application#routes_reloader` / `reload_routes!` / `reload_routes_unless_loaded`, engine registration of route files and `config/routes` directories, `Mapper#draw`, `FileUpdateChecker`, the finisher reloader hook, `reload_classes_only_on_change`, `LazyRouteSet`, and tests in `routes_reloader_test.rb`, `routing_test.rb`, `engine_test.rb`, and `loading_test.rb`.

Established from tests and source:

- Development enables reloading; production does not pick up live route-file edits on the next request.
- Application and engine `config/routes.rb` files, plus `config/routes/**/*.rb` as external draw directories, are registered on one application reloader. That reloader is built with `config.file_watcher` (default `ActiveSupport::FileUpdateChecker`).
- A successful development edit of `config/routes.rb` or an external draw file is visible on the next request (named helpers, direct URLs, and polymorphic mappings included). Explicit reload adds and removes routes.
- Local boot can defer drawing until the first request or helper use (`LazyRouteSet`). A failed first draw leaves routes unloaded; waiters retry rather than proceeding as if loaded.
- `Mapper#draw` raises if the named external file is missing, listing the searched directories.
- Default `config.reload_classes_only_on_change` is true: a reload cycle runs only when some registered watcher reports a change. When it is false, every request runs a reload cycle. During a cycle, routes are always redrawn, not only when the route files themselves changed (locale/class changes can also redraw routes).
- The file watcher treats a change in watched file count (including disappearance of a previously existing file) or a newer mtime as an update. Files under gem paths are not watched.

Inferred from source, **not** covered by a request-level test: a reload clears every registered route set before drawing files. If drawing then raises, that error can surface on the request that attempted the reload, but the previous routes are already gone. `reload!` restores its prior “loaded” flag even when drawing failed, and the watcher records the failed file’s timestamp before/during execute. After that, with `reload_classes_only_on_change` true and no further file change, a later request may not attempt another draw. Hypothesis: the developer then sees empty/missing routes (for example 404) rather than the old table and rather than the original syntax error. This is the core uncertainty; it is not proven at the HTTP boundary.

Not evidenced: simultaneous invalid application and engine files; deleting `config/routes.rb` or an external draw file after a successful boot; a full request after a syntax error then a correction, for both `reload_classes_only_on_change` values.

### Problem frame

Actor: a developer running a Rails app in development, editing the application’s route file, a mounted engine’s route file, or an external draw file, and probing the app with a browser, curl, console helpers, or `/rails/info/routes`.

They want a saved route-file change to become the live routing table on the next request, or a clear failure if the file cannot be drawn — without restarting the server.

Today, a successful valid edit does that. An invalid Ruby file does not have a request-level contract in the test suite. The developer cannot tell whether old routes still answer, whether the next request raises, whether routes have gone empty, or whether fixing the file is enough.

That matters because the usual development loop is “edit, refresh, see the new route or the error.” If that loop is silent, stale, or empty, they waste time restarting, reverting, or debugging the wrong layer.

### Desired observable outcomes

1. After a clean boot with valid files, the defined application, engine, and external-draw routes answer as written.
2. When a watched route file becomes invalid Ruby (or otherwise fails to draw), the next reload attempt fails visibly with that error. The previous routing table is not silently kept as if the bad edit never happened. The developer is not left with an unexplained empty table and no error.
3. After the file is corrected, the next request (or other established reload trigger) uses the corrected table without a server restart.
4. Application and mounted-engine files, and external draw files, follow the same contract. One bad file does not leave the others half-applied in an unexplained way.
5. Deleting a watched route file has a defined, visible result (error or a table that no longer includes that file’s routes) rather than an unexplained mix of old and missing routes.
6. `config.reload_classes_only_on_change` true vs false may differ in *when* a cycle runs, but not in the meaning of success, visible failure, or “corrected file now applies.”
7. Unchanged: production / reloading disabled does not apply live route-file edits. Valid reloads continue to add, remove, and replace routes and helpers. `config.file_watcher` remains the watcher used for these files.

### Non-goals

- New routing DSL, new reload APIs, or new developer-facing reload commands.
- Changing what a valid route file means, or production/eager-load routing.
- Choosing a particular watcher implementation beyond honoring `config.file_watcher`.
- Console-only, test-only, or Zeitwerk-only work except as it shows up through the same request/helper observations.
- Prescribing internal flags, data structures, or a test design.

### Acceptance examples

Required unless marked illustrative.

**Initial boot.** Given valid application routes, a mounted engine, and an external draw file, when the developer boots in development and issues the first request, they observe those routes (and development info/welcome routes where they apply). Helpers and polymorphic mappings match the files.

**Syntax / erroring reload.** Given that boot, when they save invalid Ruby in one watched file (application, engine, or external draw) and trigger the next reload, they observe the draw error. They do not observe the pre-edit table continuing to answer as though the save did not happen.

**Next request after the error, file still broken.** When they request again without fixing the file: if a reload cycle runs, they still see the error; if a cycle does not run, they must not see a silent resurrection of the old table. The open question below is whether this case must always re-raise or may 404 — it must not look like “old routes still work.”

**Correction.** When they save a valid file and send the next request, they observe the corrected table. No restart. Removed routes 404 / lose helpers; added and changed routes and mappings match the file.

**Simultaneous application and engine changes.** When both are valid, the next request shows both. When one is invalid, they see a visible draw failure, not a mix of new routes from the good file and old routes from the bad one.

**Deleted route files.** When they delete a watched `config/routes.rb` or an external file still referenced by `draw`, the next reload is a visible failure or a table that no longer contains that file’s routes. Deleting an unreferenced extra file under `config/routes` should not by itself keep serving that file’s old routes.

**`reload_classes_only_on_change` true.** Only a detected change (or another watcher that already causes a cycle) starts a cycle. After a failed draw, a later request with no further change must not restore the old table. After a correction, the next request applies it.

**`reload_classes_only_on_change` false.** Every request may redraw. Invalid files keep failing visibly; a correction is visible on the next request.

**Counterexample (must remain).** In production / reloading disabled, editing or breaking a route file does not change what the running process serves until restart.

### Steering evidence

- Contradicts success: after a bad save, old routes still answer; or after a correction, the next request still 404s / still raises the old error until restart; or one bad engine/app file leaves a mixed table; or production starts live-reloading.
- Suggests wrong framing: developers already get a clear error and a reliable correction on the next request in a real app (then the work is documentation, not contract maintenance); or the pain is only first-boot lazy load, not later edits.
- Decision: if request-level reproduction shows old routes surviving a failed draw, keep outcome 2 and investigate. If it shows a clear error and a working correction already, stop or narrow to the untested edges (delete, simultaneous files, both config flags). If it shows empty routes and no error after the first failed cycle, the framing is right and that silence is the gap.

### Open behavioral questions

1. After a failed reload, must every later request re-raise until the file is valid, or is a non-raising “routes missing” response acceptable if it cannot be mistaken for the old table?
2. Should `/rails/info/routes` and console URL helpers use the same rule as HTTP?
3. If application routes are valid and only the engine file is invalid, must the whole request fail, or may application routes still answer?
4. Is deleting `config/routes.rb` while routes were also declared in the application class still “do not reload those class-body routes” (existing engine example), or in scope?
5. Does a custom `config.file_watcher` that misses deletes or same-second writes change the contract, or must any configured watcher meet the same observable updates?
6. Are syntax errors, `NameError` inside the file, and `Mapper#draw` missing-file errors one contract or different?

### Evidence still to collect

- Request-level reproduction in development: valid boot → invalid `config/routes.rb` → request; same request again; then correction → request. Record status, body/error, and whether old paths still answer.
- Repeat for a mounted engine file and for `config/routes/*.rb` referenced with `draw`.
- Repeat with `reload_classes_only_on_change` true and false.
- Delete the route file (and delete an external draw file still referenced).
- Change application and engine files in one interval, including one invalid.
- Confirm production still ignores the same edits.
- Optional: `/rails/info/routes` and a console helper after the failed draw.

Do not treat source-level clear-then-load as the required design; it is only a clue that the silent-empty-table hypothesis is plausible. Downstream work should confirm or replace that hypothesis at the developer-visible boundary before changing anything.
