They set `api_key = nil` (or a child overrides a parent key with `nil`). They require it. They can tell the name is set and empty, and in the child case that the child value is what failed—not that the parent was missing.

**4. Whitespace-only string (boundary).**  
They set `host = "   "`. Non-bang still returns `"   "`. A required read fails in a way that is recognizably “blank text,” not “missing key.”

**5. Boolean false (boundary / open).**  
They set `allow_concurrency = false`. Non-bang still returns `false`. Today a required read raises `:allow_concurrency is blank`. After this work, the failure (or success) must make it obvious that the stored value is `false`, not that the key is missing. Whether requiring `false` should succeed is an open question below.

**6. Inherited present value (core).**  
Parent has `foo = "parent"`; child does not override. Required read on the child returns `"parent"`.

**7. Child present override (core).**  
Child sets `foo = "child"`. Required read on the child returns `"child"`, not the parent.

**8. Ordering unchanged (counterexample to “rewrite storage”).**  
They assign with mixed strings and symbols. Each-ing the object still yields symbol keys in write order. A required-read change that scrambled order would be a failure of this brief.

**9. Optional read unchanged (counterexample).**  
They call the non-bang reader for a missing name. They still get `nil`, not an exception.

### Acceptance evidence

**Success looks like:** someone hitting a boot-time missing or blank setting can say what was wrong from the failure alone (unset vs nil vs blank text vs false) and then set or override the right place (parent vs child). Existing code that already bang-reads present values still gets the same objects back. Config dumps / iteration order still match today’s tests.

**Investigate / do not ship if:**

- A bang read that used to return a present value now raises or returns something else
- Key order in `each` / `to_h` / `keys` changes
- String and symbol reads of the same assignment diverge
- A child stops seeing an un-overridden parent value
- Non-bang missing reads start raising

**Reconsider the problem framing if:**

- People still cannot tell missing from blank after the failure text changes (wrong diagnosis of the pain)
- The real confusion is `EncryptedConfiguration#require` (“Missing key”) vs OrderedOptions bang (“is blank”), i.e. two required-read dialects, not OrderedOptions itself
- The real confusion is `false` being blank, and clearer messages without changing that rule still surprise boolean config authors

### Open questions

These would change the outcome if answered differently:

1. **Should a required read of `false` succeed?** Today it fails as blank. `false` is a documented, tested configuration value. Confirm whether “required” means “set, even if false” or “present in the `presence` sense.”
2. **How much distinction is enough?** Missing vs any-blank may be enough; or missing vs nil vs whitespace vs false may all need to be distinct.
3. **Are credentials bang readers in scope?** They are the documented public required-read. Improving OrderedOptions failures would change what `credentials.some_api_key!` shows. Confirm that is wanted.
4. **Must the exception remain `KeyError` with the same class, or may the class/message change as long as it still raises?** Compatibility for `rescue KeyError` is implied but not stated.

No implementation is proposed. Successful return values and Hash-like ordering are frozen; only the understandability of failed required reads is in play.
