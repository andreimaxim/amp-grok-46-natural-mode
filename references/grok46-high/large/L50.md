**Problem frame:** App and engine authors use `bin/rails generate` and `bin/rails destroy` as inverse commands. When a target file already exists, generate and destroy do not give the same, predictable collision story, so people cannot tell whether a file will be kept, overwritten, or deleted.

This is a **maintenance / consistency** brief. The first job is to decide whether today’s generate/destroy differences are an intentional contract or accidental drift. Until that is settled, “make them consistent” is a hypothesis, not a requirement to change CLI behavior.

Evidence inspected: advertised generate/destroy help, command entry points, existing-file handling on create vs remove, generator lookup/fallbacks, Railties generator and engine integration coverage, and the command-line / generators / engines guides. Claims below are observed CLI behavior or labeled hypotheses.

---

**Users**

- An application developer regenerating or undoing models, controllers, scaffolds, and similar boilerplate.
- An engine/plugin author running the same commands from the engine’s `bin/rails`, writing into the engine tree (not the dummy app).
- Someone in CI or a script running generate/destroy with no TTY and closed or empty stdin.

**Pain today**

- Generate treats an existing file as a collision (identical / overwrite / skip / ask). Destroy removes a destination that exists, with no content check and no prompt.
- Help lists `--force` and `--skip` for both commands. Those flags change generate’s collision story; destroy still deletes existing destinations.
- Guides describe destroy as the opposite of generate: it should undo what generate did. Destroy after a skipped collision can delete a file generate never wrote.
- A missing generator fails the same way on both commands, but the message always tells the user to run `bin/rails generate --help`.
- Non-interactive generate that hits a differing existing file does not safely no-op; closed stdin is treated as “overwrite.”

---

**Current observable CLI behavior** (not yet “desired”)

Help for both commands advertises `--force` (overwrite existing files), `--skip` (skip existing files), `--pretend`, and `--quiet`.

**Generate** writes files. If the destination is missing: `create`. If it exists and the new content is the same: `identical`, file unchanged, no prompt. If it exists and the content differs: `--force` overwrites (`force`); `--skip` leaves it (`skip`); otherwise `conflict` and an overwrite prompt.

**Destroy** removes destination files that exist (`remove`) and still prints `remove` when they do not. It does not compare content and does not ask.

**Lookup** is shared: `model` prefers the Rails model generator; `test_unit:model` is explicit; configured fallbacks (for example a missing `shoulda:model` resolving to the test-unit model generator) apply to both; unknown names exit nonzero with `Could not find generator '…'` and optional “Did you mean?”, always pointing at `bin/rails generate --help`.

**Engine `bin/rails`** uses the engine root as the write/remove root. Isolated engines namespace generated paths (for example `app/models/blorgh/article.rb`). Nested dummy apps boot the command; they are not the destination root.

**Class-name** collisions (`The name 'Post' is either already used…`) are a separate generate-only gate, bypassed by `--force` or `--skip-collision-check`. **Migration name** collisions on generate error and tell the user to pass `--force` or `--skip`; they do not use the file overwrite prompt. Destroy of a matching migration still removes the existing file.

---

**Desired observable CLI behavior** (leading interpretation, pending intent)

One collision contract for application and engine generators, on both commands:

1. **Identical content, generate:** report identical; leave the file; do not prompt.
2. **Differing content, generate:** `--force` replaces; `--skip` leaves the file; interactive prompt otherwise; answers apply as below.
3. **Destroy** only removes files this generator run would have created and that generate actually wrote or overwrote. A file generate skipped, left identical, or never created stays. Destroy does not prompt to overwrite.
4. **`--force` / `--skip`** mean the same for existing files on generate in apps and engines. On destroy they do not become a second way to delete unrelated files.
5. **Missing generator:** both commands fail with the same not-found message and a help pointer that matches the command the user ran.
6. **Engine destination root:** collisions are judged in the engine tree when using the engine’s `bin/rails`, including namespaced paths, not against the dummy app.
7. **Non-interactive stdin** on a differing generate collision does not overwrite unless `--force` was passed.

If evidence shows destroy is *meant* to delete any matching destination, then (3) is wrong and the guides’ “undo generate” claim is the thing to correct—not the command.

---

**Non-goals**

- New generators, new flags, or new prompt letters.
- Changing how generator names, namespaces, or fallbacks are resolved, except the missing-generator help pointer in example 9.
- Redesigning class-name or migration-name collision policy, except where it would make generate/destroy file results diverge after `--force` / `--skip`.
- Changing template contents, dummy-app bootstrapping, or engine isolation rules.
- Implementation, architecture, or specific tests.

---

**Acceptance examples** (required unless marked)

Shared setup: a generator that would write `app/models/article.rb` (and the usual companions). The same examples apply to an isolated engine, with namespaced paths under the engine root.

1. **Identical content, generate**  
   File already matches what generate would write.  
   User runs `bin/rails generate model Article …` with no flags.  
   Output includes `identical` for that file; bytes unchanged; no overwrite prompt.

2. **Differing content, generate, no flags, interactive Yes**  
   File exists with different content. Prompt: `Overwrite …? … [Ynaqdhm]`. User answers `y`.  
   File is replaced with generated content; status indicates overwrite.

3. **Differing content, interactive No**  
   User answers `n`. File unchanged; status `skip`. Later files in the same run still prompt.

4. **Differing content, interactive All**  
   User answers `a` on the first differing file. That file and later differing files in this run are overwritten with no further prompts. Identical files stay `identical` and unprompted.

5. **Differing content, interactive Quit**  
   User answers `q`. Output includes `Aborting...`; process exits; that file is not overwritten. Files already handled in this run stay as they were after their own answers.

6. **`--force`, differing content, generate**  
   No prompt. File replaced. Status `force` (or equivalent overwrite status).

7. **`--skip`, differing content, generate**  
   No prompt. File unchanged. Status `skip`.

8. **Non-interactive stdin, differing content, generate, no `--force`**  
   Stdin is closed or empty (CI, piped `/dev/null`).  
   File is not overwritten. The run does not hang on a prompt. (Hypothesis: fail or skip; must not silently overwrite. Current behavior overwrites on EOF—this example is the proposed contract, not today’s.)

9. **Missing generator**  
   `bin/rails generate no_such_generator` and `bin/rails destroy no_such_generator` both exit nonzero, say the generator could not be found, and may suggest a close name. Help mentioned is `generate --help` or `destroy --help` matching the command used. No files change.

10. **Namespaced resolution**  
    `bin/rails generate model Article` and `bin/rails destroy model Article` use the Rails model generator. `bin/rails generate test_unit:model Account` uses the test-unit model generator. With a fallback from `shoulda` to `test_unit`, `shoulda:model` generate and destroy use the same resolved generator. Collision/removal then follows examples 1–8 and 11 for that generator’s files.

11. **Destroy after a skipped collision**  
    Pre-existing customized `app/models/article.rb`. User runs generate with `--skip` (or answers `n`). File unchanged.  
    User then runs `bin/rails destroy model Article`.  
    The customized file is still there. Destroy may remove files generate actually created in an earlier run, but not the skipped one.  
    (Today destroy deletes that destination if it exists. Whether that is intentional is open.)

12. **Nested engine destination root**  
    From an isolated engine’s `bin/rails`, generate would write `app/models/blorgh/article.rb` under the **engine** root. That path already exists with different content.  
    Same results as examples 1–8 and 11, relative to the engine tree. The dummy app is not the destination; a like-named file only in `test/dummy` is not the collision. Destroy after skip does not delete the engine file generate skipped.

13. **Counterexample — destroy is not an overwrite prompt**  
    Existing generated file, no `--force`/`--skip`. `bin/rails destroy model Article` does not ask `Overwrite …?`. It either removes files it is allowed to undo (desired) or, today, removes the destination without asking (current).

---

**Steering evidence**

- Reconsider “destroy undoes generate” if people routinely use destroy to wipe pre-existing files generate skipped or never wrote, and that is documented as supported.
- Reconsider “EOF must not overwrite” if documented CI practice is: non-interactive generate without `--skip` replaces colliding files.
- Reconsider engine-root collisions if engine authors are told to generate into the dummy app; observed command root is the engine root.
- Investigate rather than “fix” if generate/destroy differences are limited to status text while file outcomes already match a documented contract.

**Open questions (evidence needed before treating differences as bugs)**

1. Is destroy allowed to delete a destination generate skipped or left identical? Guides say undo generate; current remove-if-exists does more. Need: documented intent, changelog, or known workflows that depend on the aggressive delete.
2. Is EOF-as-overwrite on the generate prompt intentional (default Yes, including closed stdin) or an accident of the prompt? Need: a documented non-interactive recipe besides `--force`/`--skip`.
3. Should `--force`/`--skip` on destroy do anything to files? Help says they apply; destroy does not use them for existing-file decisions.
4. Should a missing generator on destroy point at destroy help, or is always-generate-help intentional?
5. Are migration collisions that error instead of prompting, and class-name collisions that only run on generate, in scope for “existing file” consistency, or separate contracts?
6. For interactive `q` after some files were already overwritten: is partial apply accepted, or must the whole run be all-or-nothing? Current prompt aborts without rolling back earlier answers.
7. Diff (`d`) and merge (`m`) are available on the generate prompt; they are not in the required example set. Confirm they stay out of scope.

No implementation is implied. The decision this brief is for: **which of the current generate vs destroy collision outcomes are the contract**, and therefore which examples are bugs rather than behavior to preserve.
