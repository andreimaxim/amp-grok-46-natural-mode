`#strict_loading!` is an instance switch. It stores two ivars and returns the boolean:

```ruby
def strict_loading!(value = true, mode: :all)
  unless [:all, :n_plus_one_only].include?(mode)
    raise ArgumentError, "The :mode option must be one of [:all, :n_plus_one_only] but #{mode.inspect} was provided."
  end
  @strict_loading_mode = mode
  @strict_loading = value
end
```

Source: [`activerecord/lib/active_record/core.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb). A new record copies class defaults in `init_internals`: `@strict_loading` from `klass.strict_loading_by_default` (false), `@strict_loading_mode` from `klass.strict_loading_mode` (`:all`). So `strict_loading_all?` is true on ordinary records even when strict loading is off; that only matters once `@strict_loading` is true.

A **relation** has a separate API (`Relation#strict_loading` / `#strict_loading!(value)`) that stores only a boolean. After the query, `Relation#exec_queries` calls `record.strict_loading!(strict_loading_value)` on each parent, which uses default mode `:all`. There is no relation-level `:n_plus_one_only`.

### `:all` vs `:n_plus_one_only`

The mode is not consulted when the association is already loaded. The gate is `Association#violates_strict_loading?`:

```ruby
def violates_strict_loading?
  return unless find_target?                         # already loaded → no
  return if @skip_strict_loading                     # writers skip
  return unless owner.validation_context.nil?        # validation skip
  return reflection.strict_loading? if reflection.options.key?(:strict_loading)
  owner.strict_loading? && !owner.strict_loading_n_plus_one_only?
end
```

| | `:all` (default) | `:n_plus_one_only` |
|---|---|---|
| Owner lazy-loads any unloaded association | **violation** | **allowed** |
| Child records from a `has_many` | not reached (load blocked) | `record.strict_loading!` → children are `:all` |
| Singular (`belongs_to` / `has_one`) children | not reached | `record.strict_loading!(false, mode: owner.strict_loading_mode)` — flag off, **mode copied** |
| Then a child lazy-loads its own association | n/a | **violation** (`:all` on the has_many child) |

That last row is the point of `:n_plus_one_only`: the parent may load each association once; walking parent → children → each child’s association is the N+1 that still errors.

`set_strict_loading` uses `reflection.macro == :has_many`. HABTM is implemented as `has_many :through`, so `Developer#projects` counts as `:has_many`.

```ruby
def set_strict_loading(record)
  if owner.strict_loading_n_plus_one_only? && reflection.macro == :has_many
    record.strict_loading!                              # on, mode :all
  else
    record.strict_loading!(false, mode: owner.strict_loading_mode)  # off, mode copied
  end
end
```

`strict_loading_n_plus_one_only?` looks only at `@strict_loading_mode`, not `@strict_loading`. A singular child can have `strict_loading? == false` and still `strict_loading_n_plus_one_only? == true`, so the *next* `has_many` still marks *its* children strict. That is how `developer.ship.parts` works below.

Called from `Association#find_target` after each cached SELECT, and from `AssociationRelation#exec_queries` after a scoped association query (`#first`, `#limit`, etc.).

### Where the error (or log) fires

```text
record.association reader
  CollectionAssociation#reader → CollectionProxy (does not load)
  SingularAssociation#reader   → reload → load_target
    Association#find_target
      violates_strict_loading? ──yes──▶ Base.strict_loading_violation!
      else SELECT, then set_strict_loading(record)
CollectionProxy#pluck
  same violates_strict_loading? check (pluck can skip find_target)
CollectionProxy#to_a / #records
  exec_queries → load_target → find_target (same gate)
```

`ActiveRecord::Base.strict_loading_violation!` in [`core.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb):

- `ActiveRecord.action_on_strict_loading_violation` default `:raise` → `ActiveRecord::StrictLoadingViolationError` with `reflection.strict_loading_violation_message(owner)`
- `:log` → `ActiveSupport::Notifications.instrument("strict_loading_violation.active_record", owner:, reflection:)` → debug log via `LogSubscriber`

The `owner:` passed in is `owner.class`, so the message is class-level: `` `Developer` is marked for strict_loading. The AuditLog association named `:audit_logs` cannot be lazily loaded. `` Polymorphic: “The polymorphic association named `:looter`…”. Tests: `test_strict_loading_violation_raises_by_default`, `test_strict_loading_violation_can_log_instead_of_raise`.

Writers (`<<`, `=`, and `load_target` inside `replace` / new-record `concat`) wrap with `skip_strict_loading`. `build` never calls `find_target`. Tests: `test_strict_loading_on_concat_is_ignored`, `_on_build_`, `_on_writer_`.

### Observable examples (`strict_loading_test.rb`)

#### 1. Lazy `has_many` (`:all`)

`test_strict_loading!`, `test_raises_if_strict_loading_and_lazy_loading`:

```ruby
developer = Developer.first
developer.strict_loading!          # true, mode :all
developer.audit_logs.to_a          # StrictLoadingViolationError
developer.audit_logs.first         # same
developer.audit_logs.pluck(:id)    # same
```

`:all` also makes `CollectionAssociation#find_from_target?` true, so `#first` loads the whole collection through `load_target`, then `find_target` raises. Relation form: `Developer.strict_loading.first` is the same instance flag.

#### 2. Lazy `belongs_to` (`:all`)

`test_raises_on_lazy_loading_a_belongs_to_relation_if_strict_loading_by_default` and `test_raises_on_lazy_loading_a_strict_loading_belongs_to_relation`:

```ruby
developer.mentor                   # owner strict_loading by default → error
developer.strict_loading_mentor    # belongs_to ..., strict_loading: true → error even if owner is not
```

Singular path: `reader` → `reload` → `find_target`. `belongs_to` `find_target?` also requires a present FK; a nil FK is not a violation. Per-association `strict_loading:` wins whenever the key is present. `strict_loading: false` on `strict_loading_off_mentor` allows the load even if the owner is strict.

#### 3. Preloaded association

`test_strict_loading_with_has_many`, `test_preload_audit_logs_are_strict_loading_with_pluck`:

```ruby
dev = Developer.preload(:audit_logs).first   # or includes, with owner strict
dev.audit_logs.to_a                          # ok — loaded? so find_target? is false
dev.audit_logs.pluck(:id)                    # ok
```

Parent `strict_loading` also cascades onto preloaded children. Preload passes `StrictLoadingScope` when the parent relation is strict; eager load / JOIN calls `m.strict_loading!` in `JoinDependency#construct_model`. `test_preload_audit_logs_are_strict_loading_because_parent_is_strict_loading`: `Developer.includes(:audit_logs).strict_loading.first` → parent and every `audit_log` are `strict_loading?`.

`reload` copies the fresh record’s `@association_cache` and, in `:all` mode, `_find_record` preloads currently strict-loaded associations (`test_strict_loading_has_one_reload`).

#### 4. `has_many :through` and middle records (`:all`)

`Developer` has `has_many :contracts`, `has_many :firms, through: :contracts`, `has_one :ship`. `test_strict_loading_with_has_many_through_cascade_down_to_middle_records`:

```ruby
dev = Developer.strict_loading.includes(:firms).first
dev.firms            # ok — preloaded
dev.firms.first.contracts.first  # error — Firm is strict (cascaded); :contracts not preloaded
dev.contracts.first  # error — through preloader used contracts internally with associate_by_default: false, so dev.contracts is still unloaded
dev.ship             # error — not in the includes list
```

The through preloader loads middle rows to stitch `firms`, but does not mark `dev.contracts` loaded. A later lazy load of the through association is a violation. Preloaded `firms` inherit strict loading, so *their* `contracts` also violate.

#### 5. Validation-time association access

`violates_strict_loading?` returns unless `owner.validation_context.nil?`. Core docs: “Strict loading is disabled during validation in order to let the record validate its association.”

```ruby
## test_strict_loading_is_ignored_in_validation_context
with_strict_loading_by_default(Developer) do
  AuditLogRequired.create!(developer_id: developer.id, message: "i am a message")
end

## test_strict_loading_with_reflection_is_ignored_in_validation_context
developer.required_audit_logs.build(message: "I am message")
developer.save!   # validation_context is :update, not nil
```

#### 6. Parent → children → each child’s association (`:n_plus_one_only`)

`test_strict_loading_n_plus_one_only_mode_with_has_many` (HABTM `projects`, treated as `has_many`):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)
developer.projects.to_a                         # ok
developer.projects.all?(&:strict_loading?)     # true — set_strict_loading used strict_loading!
developer.projects.detect { ... }.firm          # StrictLoadingViolationError — child is :all
```

`test_strict_loading_n_plus_one_only_mode_with_belongs_to` (actually `has_one :ship` then `has_many :parts`):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)
developer.ship.parts.to_a                       # ok
developer.ship.strict_loading?                  # false — singular child: strict_loading!(false, mode: :n_plus_one_only)
developer.ship.parts.all?(&:strict_loading?)   # true — mode traveled; has_many still enables children
developer.ship.parts.first.trinkets.to_a        # error
```

`test_strict_loading_n_plus_one_only_mode_does_not_eager_load_child_associations`: `#first` does **not** load the full collection (`find_from_target?` is false because `strict_loading_all?` is false). It runs a `LIMIT 1` AssociationRelation, which still `set_strict_loading`s that one child. The following `.firm` in that test does not raise because fixture projects have no `firm_id`, so belongs_to `find_target?` is false.

#### 7. Disabling on an instance

`test_strict_loading!`:

```ruby
developer.strict_loading!          # on
developer.audit_logs.to_a          # error
developer.strict_loading!(false)   # returns false; strict_loading? false
developer.audit_logs.to_a          # ok
```

Relation override: `Developer.strict_loading(false)` when the class is `strict_loading_by_default`.

#### 8. Invalid mode

Not covered by `strict_loading_test.rb`. Source only: any `mode` other than `:all` / `:n_plus_one_only` raises `ArgumentError` **before** ivars are assigned.

```ruby
developer.strict_loading!(mode: :bogus)
## ArgumentError: The :mode option must be one of [:all, :n_plus_one_only] but :bogus was provided.
```

**Mental model:** `@strict_loading` is “this record may not lazy-load,” except `:n_plus_one_only` which means “this record may lazy-load, but every `has_many` child is flipped to `:all` so the *next* hop cannot.” Preload/eager-load sets `loaded?` and skips the gate; through preload does not automatically load the middle association on the parent. Validation, association writers, and an explicit `strict_loading:` option are the other escapes. Reporting is `:raise` or `:log` via `ActiveRecord.action_on_strict_loading_violation`.
