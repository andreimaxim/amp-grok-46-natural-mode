## Product shaping brief: temporary `subscribed` observation

This is a behavioral specification for making **temporary** `ActiveSupport::Notifications.subscribed` observation easier to use in **tests and diagnostic tooling**. It is not an implementation plan. Current-state claims below are taken from this revision’s documentation and tests.

---

### Problem frame

**Actors.** Rails maintainers and application authors who write tests, query/count assertions, or short-lived diagnostic probes around instrumentation.

**Situation.** They need to watch notifications **only while a block of work runs**, then stop watching. Typical work: assert that a request fired N SQL events; capture `post.submitted` during a submit; sample duration of a nested instrumented section.

**Pain today.** Temporary observation exists, but it is a thin, easy-to-misuse wrapper around the long-running subscribe API.

- Callers must supply a **pre-built callback**. `subscribe` can take a block; `subscribed` cannot ([`notifications.rb` L332–L337](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L337) vs `subscribe` at [L312–L317](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L312-L317)).
- Docs treat temporary use as exceptional and warn that subscribe/unsubscribe **wipes internal caches** and hurts performance ([L155–L163](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L155-L163)). Test helpers still depend on it: `capture_notifications` ([`notification_assertions.rb` L85–L88](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L85-L88)), `assert_queries_count` ([`query_assertions.rb` L28](file:///home/user/workspace/repo/activerecord/lib/active_record/testing/query_assertions.rb#L28)).
- Matching, timestamp style, nested start/finish, payload mutation, and raising blocks are **real contracts**, but they are split across `subscribed` tests, general `subscribe` tests, and `instrument` tests. A tooling author has to assemble that picture.
- Nested or interleaved start/finish can **miss** an observer that was not active at finish ([`test_subscribed_interleaved_with_event`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L220)). That is surprising if “I subscribed around this work” is taken to mean “I see every event that overlaps this work.”

**Why it matters.** Tests and diagnostics are the main legitimate users of temporary observation. If that path stays awkward, people either leak long-running subscribers into tests, copy fragile subscribe/unsubscribe/`ensure` boilerplate, or write assertions that silently miss nested, mutated, or failing work.

**Desired progress.** Observing “what fired during this block” should be the natural, safe path for tests and diagnostics, without changing how process-lifetime subscribers work.

### Maintainer / user pain (working model)

1. **Scope is easy to get wrong.** People want “events caused by this block.” What they get is “events whose **finish** happens while this callback is subscribed,” plus name/regexp filtering. Nested `build_handle` work can finish inside a different window ([L197–L220](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L220)).

2. **The temporary API is less convenient than the permanent one.** Tests must allocate a lambda, choose arity, and choose `monotonic:` before they can watch anything. Helpers paper over this; ad-hoc diagnostics do not.

3. **Regexp matching is a first-class need in tooling** (`capture_notifications` [L85–L88](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L85-L88), [L91–L97](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L91-L97)) but is documented primarily on `subscribe`, not as a `subscribed` example.

4. **Raising work is a normal diagnostic case.** A failing instrumented block still emits an event with exception payload ([L502–L514](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L502-L514)). Temporary observers must still be removed. That combination (see the event, still raise, still unsubscribe) is easy to get wrong if people roll their own `subscribe`/`unsubscribe`.

5. **Performance warning vs. test reality.** Docs say use temporary subscription sparingly ([L161–L163](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L161-L163)), yet the test suite’s notification and query assertions are built on it. Maintainers lack a clear “this is the supported test/diagnostic path” story.

**Hypothesis (not a user-supplied metric):** the pain is **ergonomics and clarity of contract** for block-scoped observation, not missing matching power. Exact name, regexp, and all-events already exist.

### Desired observable outcomes

After the work, a test or diagnostic author can:

1. **Watch a bounded window.** While a block runs, matching notifications are delivered to their observer. After the block returns **or raises**, that observer receives nothing further from later `instrument` calls.

2. **Select events the same three ways they already can.** Exact string name; regexp; or every event (no pattern). Non-matches in the window are omitted.

3. **Keep timestamp meaning explicit.** Default five-arg timestamps remain wall-clock `Time`. `monotonic: true` still yields monotonic `Float` start/finish. One-arg `Event` observers keep working.

4. **See nested work in finish order.** An inner `instrument` that starts and finishes inside an outer `instrument` is observed as its own event, delivered before the outer event.

5. **See payload as it stands at publish.** Mutations applied to the payload object during the instrumented block are visible to the temporary observer, including nested hash updates.

6. **See failures without swallowing them.** If the instrumented block raises, the observer still receives the event (with `:exception` / `:exception_object` on the payload), the original exception still propagates, and the temporary observer is gone afterward.

7. **Leave process-lifetime subscribers alone.** Existing `subscribe` / `monotonic_subscribe` / `unsubscribe` behavior, including regexp subscribers and unsubscribe-by-name, remains the way to attach long-running listeners.

### Non-goals

- Changing long-running `subscribe`, `monotonic_subscribe`, or `unsubscribe`.
- Changing callback arities (one-arg `Event` vs five-arg tuple) or the rule that selects them.
- Changing Rails hook names, default payloads, or when `instrument` publishes.
- Making temporary observation the default for production, process-lifetime logging.
- Promising that an observer sees events that **started** before its window and **finished** after it (current tests say the opposite for interleaved handles).
- Inventing a numeric performance SLO. The cache-wipe warning ([L161–L163](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L161-L163)) stays a documented cost unless later work separately addresses it.
- Broader instrumentation redesign (async queues, silencing, Ractor snapshot protocol).

### Compatibility constraints (must preserve)

These are constraints, not solution choices:

- **Long-running subscribe/unsubscribe stay as they are.** String, regexp, or empty pattern; unsubscribe by subscriber object or by name; regexp subscribers remain subscribed to unmatched names when a single string is unsubscribed ([docs L191–L225](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L191-L225); [`UnsubscribeTest` L323–L375](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L323-L375)).
- **Callback arities stay as they are.** One required argument receives `Event`; otherwise five arguments `name, start, finish, id, payload` ([L43–L74](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L43-L74), [L278–L302](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L278-L302)).
- **`monotonic: false` (default) vs `monotonic: true`** keep their timestamp types ([L279–L312](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L312)).
- **Automatic unsubscription after the block**, including when the block raises (`ensure` at [L334–L336](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L334-L336)).
- **Invalid patterns still raise** `ArgumentError` (“pattern must be specified as a String, Regexp or empty”) ([L304–L310](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L304-L310); fanout [L107](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L107)).
- Existing test helpers that call `subscribed` (`capture_notifications`, query assertions) must keep working with the same call shape they use today.

### Representative examples

Required cases unless marked illustrative.

#### 1. Exact name, then silence (core)

A test watches `"foo"` around a block that instruments `"foo"`, `"foofoo"`, `"foo"`. The observer records `["foo", "foo"]`. After the block, another `"foo"` does not change that list.

Grounded in [`test_subscribed` L226–L241](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L241).

#### 2. All events (core)

The same block with **no pattern** records `["foo", "foofoo", "foo"]`. After the block, further instruments are not recorded.

Grounded in [`test_subscribed_all_messages` L244–L260](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L260).

#### 3. Regexp (core for tooling)

A diagnostic watches `/post\./` around work that instruments `"post.submitted"` and `"user.created"`. Only `"post.submitted"` is collected. This is what `capture_notifications(/post\./)` does today ([L91–L97](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L91-L97)).

#### 4. Wall-clock vs monotonic (core)

Five-arg callback, default options: `start` and `finish` are `Time`. Same callback with `monotonic: true`: both are `Float`. Instruments after the block do not invoke the callback.

Grounded in [L279–L312](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L312).

#### 5. Nested instrumentation (required)

```text
instrument "awesome"
  instrument "wot"
    # work
  # "wot" is observed here (inner finished)
## "awesome" is observed here (outer finished)
```

A temporary observer active for the whole outer block sees **both**, inner first.

Grounded in [`test_nested_events_can_be_instrumented` L486–L499](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L486-L499).

#### 6. Nested subscribed windows vs late finish (required boundary)

An outer `subscribed` starts a handle, an inner `subscribed` runs only around `handle.finish`, then the outer window ends. **Outer observer sees one event; inner observer sees none.**

This is current behavior ([L197–L220](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L220)). The desired outcome is to **keep this finish-time rule visible**, not to silently redefine “during the block” as overlap-with-start. If a future change redefined it, that would be a separate, explicit behavior change.

#### 7. Payload mutation (required)

Work does `instrument("foo") { |payload| payload[:my_key] = "success!" }`. The temporary observer’s payload has `my_key: "success!"`. Nested hash keys added in the block are likewise visible.

Grounded in [L45–L53](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L53), [L76–L84](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L76-L84), [L475–L480](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L475-L480).

#### 8. Raising instrumented block (required)

Work does `instrument("awesome") { raise "FAIL" }`. The caller still sees `RuntimeError`. The temporary observer still got one event whose payload includes the original keys plus `exception: ["RuntimeError", "FAIL"]` and `exception_object` equal to the raised error. A later `"awesome"` is not observed.

Grounded in [L502–L514](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L502-L514) plus `subscribed`’s `ensure` unsubscribe [L334–L336](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L334-L336). Combined `subscribed` + raising-block is **not** a dedicated test today; the two contracts are specified separately and must hold together.

#### 9. Raising *observer block* (required cleanup)

The `subscribed` block itself raises before any instrument. The temporary callback must not remain registered. (Follows from `ensure` at [L334–L336](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L334-L336); not given its own example in `SubscribedTest`.)

#### 10. Counterexample: long-running subscribe is unchanged (illustrative)

A process-lifetime `subscribe("render")` still receives every later `"render"` until `unsubscribe`. Temporary observation of `"sql.active_record"` during a test must not detach that subscriber or change its arity.

### Acceptance signals

**Success looks like**

- A maintainer can scope observation to a block using exact name, regexp, or all events, and show (in a test or a short diagnostic script) that events after the block are not received.
- Nested instrumented work in that block shows up inner-then-outer, with payloads as mutated at publish.
- A raising instrumented block still delivers the exception payload to the observer, still raises, and does not leave the observer attached.
- Existing `subscribe` / `unsubscribe` examples in docs and tests continue to behave as they do in this revision.
- One-arg and five-arg callbacks, and `monotonic: true` vs default, still produce the same argument shapes.

**Failure / investigate**

- Events leak after the block, including after a raised block.
- Regexp or all-event matching diverges from `subscribe` / `capture_notifications`.
- Nested events disappear, reorder, or lose in-block payload mutations.
- A raising instrumented block is observed **or** re-raised, but not both.
- Timestamp classes flip without `monotonic:` being set.
- Long-running subscribers stop firing, change arity, or require different unsubscribe rules.

**Wrong-problem signals (reconsider the framing)**

- Maintainers still copy `subscribe` + manual `unsubscribe` in tests because the temporary path cannot express regexp, all-events, or monotonic time.
- The only remaining complaints are production throughput of subscribe/unsubscribe cache invalidation — that is the documented long-running-vs-temporary tradeoff ([L161–L163](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L161-L163)), not test usability.
- People needed a **trace of in-flight (started-but-not-finished) work**, which current finish-time delivery cannot show ([L197–L220](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L220)). That would be a different outcome.
