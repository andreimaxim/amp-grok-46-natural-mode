## `ActiveRecord::Relation#none`

`#none` is a Null Object for relations: same type as a normal `Relation`, chainable, and empty without hitting the database on the usual read/count/bulk-write paths. It is **not** a subclass. Emptiness is a sticky ivar, `@none`, plus a SQL `WHERE (1=0)` clause that is *not* what most short circuits look at.

### Construction and chainability

```
none  → spawn.none!
none! → unless @none
          where!("1=0")
          @none = true
```

`spawn` is `clone` (or `model.all` when already in a scope execution). `initialize_copy` dups `@values` and `reset`s load state; it does **not** clear `@none`. So every later `where`/`order`/`limit`/`except`/`only`/`unscope`/`rewhere` keeps the flag.

`@none` is **not** in `@values`. `unscope(:where)` / `except(:where)` can drop the `1=0` predicate and still be a null relation. `null_relation?` is just `@none`.

Merger copies it the other way: `relation.none! if other.null_relation?`.

`#or` is the chain that *drops* nullness on the receiver:

```
if @none
  other.spawn          # empty OR x => x
else
  spawn.or!(other)     # x OR empty keeps x's predicates, plus 1=0 from other
end
```

`Post.none.or(Post.where(id: 1))` is a live query. That is intentional identity for OR.

`where_values_hash` ignores the SQL literal, so `Model.none.where_values_hash` is `{}`. A later hash `where` still shows up in the hash; `@none` stays true.

### Loading: `@none` vs `where_clause.contradiction?`

These are two different empty-query mechanisms.

`contradiction?` is only:

- `In` with an empty Array (`where(id: [])`)
- `Equality` whose bind is unboundable

`WHERE 1=0` is **not** a contradiction. A plain `where("1=0")` still hits the adapter. `#none` therefore sets both the ivar (Ruby short circuit) and the predicate (SQL shape / subquery fallback).

```
exec_queries
  skip_query_cache_if_necessary
    exec_main_query
      if @none → []  (or FutureResult.wrap([]) if async)
      skip_query_cache_if_necessary
        if where_clause.contradiction? → [].freeze
        elsif eager_loading?
          apply_join_dependency
            if relation.null_relation? → [].freeze
            else select_all
        else _query_by_sql
```

`@none` returns *before* the inner `skip_query_cache_if_necessary` and *before* `contradiction?`. Eager load has a second `null_relation?` check because join-dependency can spawn a new relation.

`load_async` calls `exec_main_query` directly (not via `exec_queries`), so the same `@none` return applies.

### Calculations, `exists?`, `include?`

All of these short-circuit on `@none` *before* building Arel or consulting the query cache:

| method | `@none` result |
|---|---|
| `calculate` count/sum | `0`, or `{}` if grouped |
| `calculate` avg/min/max | `nil`, or `{}` if grouped |
| async variants | `Promise::Complete` of the same |
| `pluck` / `ids` | `[]` |
| `exists?` | `false` (before `conditions` / `contradiction?`) |
| `empty?` / `none?` | `true` |
| `any?` / `one?` / `many?` | `false` |
| `size` | no direct check; unloaded goes through `count` |

`include?` / `member?` has no `@none` check of its own:

- wrong class → `false`
- loaded, or `offset`/`limit`/`having` → `records.include?` → `load` → `exec_main_query` → `[]`
- otherwise → `exists?(pk hash)` → `false` from `@none`

So `include?` never issues SQL on a null relation, but the empty answer is always via `exists?` or `records`, not a dedicated branch.

Fallback empty paths that *do* use `contradiction?` (`exists?` after constructing the EXISTS relation, `pluck` when not `@none`, `execute_simple_calculation` / grouped calculate) are irrelevant once `@none` is set.

### `delete_all` / `update_all`

Both `return 0 if @none` before compiling Arel or opening a connection. Tests assert zero queries.

Downstream:

- `delete(id)` → `where(pk => id).delete_all` (spawn keeps `@none`) → `0`
- `touch_all` / `update_counters` → `update_all` → `0`
- `destroy_all` does **not** check `@none`; it does `records.each(&:destroy)`. Load short-circuits to `[]`, so no DELETE either.

`delete_all` still runs the “invalid methods” check only after the `@none` return, so `Model.distinct.none.delete_all` is `0`, not `ActiveRecordError`.

### Query-cache skip state

`skip_query_cache!` sets `skip_query_cache_value` (a `SINGLE_VALUE_METHOD`, stored in `@values`, cloned with the relation). `skip_query_cache_if_necessary` is `model.uncached(&block)` vs `yield`.

`@none` short circuits **outside** that wrapper for `exists?`, `calculate`, `pluck`, and `exec_main_query`. Those paths never enter `uncached` and never talk to the connection, so they neither read nor write the query cache.

`load` / `exec_queries` is slightly different: the *outer* wrapper still runs. On a `none.skip_query_cache!` load you enter `uncached`, then `exec_main_query` returns `[]`. No SQL, no cache fill. Preload on empty records is a no-op. `load_async` skips that outer wrapper entirely.

`values_for_queries` already omits `:skip_query_cache` (with `:extending` and `:strict_loading`) from query identity; that is independent of `#none`.

`in_batches` always `skip_query_cache!` on the batch relation, then `pluck`/`pick`. Those see `@none` and return empty, so the loop breaks with no SQL. The skip flag is set but unused.

### Operations that can still execute SQL after further scoping

`#none` does not mean “this object can never cause SQL.” Reads and the bulk mutators above are guarded. These are not:

1. **`#or` on a null receiver** — returns `other.spawn`. `Post.none.or(Post.where(id: 1))` queries.

2. **Null relation as a subquery** — `PredicateBuilder::RelationHandler` builds `attribute.in(none_relation.arel)`. The inner Arel still has `WHERE (1=0)`, but the *outer* statement runs. `Comment.where(post_id: Post.none).count` is a real query (covered by `test_null_relation_in_where_condition`).

3. **Inserts / create** — no `@none` check. `scope_for_create` only hashes equality predicates, so `1=0` does not become a column. `none.create` / `insert_all` / `upsert_all` / `find_or_create_by` (find misses, then create) / `create_or_find_by` still talk to the database.

4. **Association queries under `none.scoping`** — current_scope clones `@none` for `Model.all` on that class, but `record.association` builds its own relation. `Comment.none.scoping { post.comments.count }` still queries (same as `where("1=0").scoping`).

5. **Lost `@none`, leftover or missing `1=0`** — a freshly constructed `Relation` starts `@none = false`. If some path copies only `@values` without the ivar, `WHERE 1=0` would be executed (`contradiction?` is false). Conversely, `unscope(:where)` keeps `@none`, so reads stay empty even though `to_sql` no longer has `1=0`. `invert_where` would produce `NOT (1=0)` in SQL and still not query, because the ivar remains.

`to_sql` / `explain` metadata always compile Arel (and `to_sql` includes `WHERE (1=0)`); that is compilation, not a server round-trip on the `#none` object itself.
