## Current behavior: two independent fallbacks

`Rails::Application::Configuration#credentials_defaults` chooses the two paths independently:

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")
  content_path = root.join("config/credentials.yml.enc") if !content_path.exist?

  key_path = root.join("config/credentials/#{Rails.env}.key")
  key_path = root.join("config/master.key") if !key_path.exist?

  { content_path: content_path, key_path: key_path }
end
```

Source: [`railties/lib/rails/application/configuration.rb#L683-L691`](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L683-L691)

Consequently:

| Environment content exists? | Environment key exists? | Selected content | Selected key |
|---|---|---|---|
| Yes | Yes | `credentials/<env>.yml.enc` | `credentials/<env>.key` |
| Yes | No | `credentials/<env>.yml.enc` | `master.key` |
| No | Yes | `credentials.yml.enc` | `credentials/<env>.key` |
| No | No | `credentials.yml.enc` | `master.key` |

`Rails::Application#credentials` passes that selected pair directly to `EncryptedConfiguration`:

```ruby
@credentials ||= encrypted(
  config.credentials.content_path,
  key_path: config.credentials.key_path
)
```

Source and API documentation: [`railties/lib/rails/application.rb#L589-L607`](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L589-L607). The docs explicitly describe the paths independently: environment content or global content if absent; environment key or `master.key` if absent. `RAILS_MASTER_KEY` takes precedence over either file key.

## Original intent: paired stores

Environment credentials were introduced by [PR #33521](https://github.com/rails/rails/pull/33521), merged as [`e0d3313`](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba). Its commit message and changelog describe:

- `config/credentials/production.yml.enc`
- decrypted by `RAILS_MASTER_KEY` **or** `config/credentials/production.key`
- the global pair remaining `config/credentials.yml.enc` and `config/master.key`

The original implementation actually selected the pair together, based solely on whether the environment-specific encrypted content existed:

```ruby
def default_credentials_key_path
  if credentials_available_for_current_env?
    File.join(root, "config", "credentials", "#{Rails.env}.key")
  else
    File.join(root, "config", "master.key")
  end
end
```

See the [introduction diff](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba).

DHH’s design statement in [PR #33521](https://github.com/rails/rails/pull/33521) was particularly clear:

> The key used to decrypt will be either `config/credentials/$environment.key` or `ENV["RAILS_#{Rails.env.upcase}_KEY"]`.

He also said the environment and global files were “separate files and separate stores of credentials,” with no merging. The final implementation standardized the environment variable as `RAILS_MASTER_KEY`, but retained the environment-specific file-key pairing.

Thus, historical intent supports these pairs:

- `config/credentials.yml.enc` ↔ `config/master.key`
- `config/credentials/<env>.yml.enc` ↔ `config/credentials/<env>.key`
- `RAILS_MASTER_KEY` may replace the file key for whichever content file was selected.

It does **not** clearly support silently mixing an environment content file with the global file key merely because the environment key is missing. The present independent fallback permits that combination, but this differs from the original paired implementation and rationale.

## Discussion and known wrong-key problems

- [Issue #41830](https://github.com/rails/rails/issues/41830) discusses environment-specific stores and reiterates that the application loads the environment file instead of the global file when present. One commenter observed that `master.key` is not normally the key for environment credentials, while `RAILS_MASTER_KEY` can supply the active key for either store.
- [Issue #46636](https://github.com/rails/rails/issues/46636) is a concrete user-facing wrong-key case: the reporter used `config/master.key`/its value for staging credentials and could not load them. The resolution was to deploy the value of `config/credentials/staging.key` as `RAILS_MASTER_KEY`; after switching keys, staging credentials worked.
- The environment-credentials PR itself has reports of `ActiveSupport::MessageEncryptor::InvalidMessage` / `OpenSSL::Cipher::CipherError` caused by environment content being opened with `master.key`; the remediation was to use/rename the corresponding environment key.
- Command tests verify that credential diffing returns raw encrypted content when an environment key is unavailable or decryption errors occur: [`credentials_test.rb#L282-L313`](https://github.com/rails/rails/blob/main/railties/test/commands/credentials_test.rb#L282-L313).

## PR-review conclusion

Rails **currently implements independent fallback**, so selecting `master.key` when `<env>.yml.enc` exists but `<env>.key` does not is already what `credentials_defaults` says to do.

However, the feature’s original implementation, generators, tests, commit documentation, and maintainer design discussion all treat environment content and environment key as a pair. A missing `<env>.key` ordinarily means the key should arrive through `RAILS_MASTER_KEY`; substituting `config/master.key` risks decrypting the environment file with an unrelated global key and producing `InvalidMessage`.

Therefore, if the proposed PR claims this mixed pairing is the intended semantic rather than merely preserving current behavior, that claim is weak. The stronger historical interpretation is **paired stores with `RAILS_MASTER_KEY` as the shared override mechanism**.

   A present but unrelated `master.key` suppresses `MissingKeyError` and instead causes `InvalidMessage`. With `require_master_key`, Rails therefore validates that *some* key exists, not that the selected store’s key exists. If both stores happen to share a key, the configuration silently works and masks the missing environment key.

2. **Global content + environment key**  
   A stale `config/credentials/<env>.key` can break an otherwise valid global credentials setup even though no environment ciphertext exists.

This is primarily a configuration-integrity and availability defect, **not a direct confidentiality vulnerability**: an unrelated key cannot decrypt the ciphertext. The security concern is silently eroding the intended key/store boundary and accepting a misconfigured deployment when keys happen to match.

The original merged implementation in [PR #33521 / commit `e0d3313`](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba) used the environment ciphertext’s existence as the single predicate for both paths. The independent checks appeared in [`1068945`](https://github.com/rails/rails/commit/1068945b8fc9324c795224ca8e16c45d9ff15f10), whose purpose was command/config integration, without rationale for changing store semantics.

## Correct fix

Yes: a tiny paired-store selection is the right implementation:

```ruby
content_path = root.join("config/credentials/#{Rails.env}.yml.enc")

if content_path.exist?
  key_path = root.join("config/credentials/#{Rails.env}.key")
else
  content_path = root.join("config/credentials.yml.enc")
  key_path = root.join("config/master.key")
end
```

Explicit `config.credentials.content_path` and `key_path` overrides remain independently configurable; only automatic discovery is paired.

Compatibility caveat: the guide currently documents independent fallbacks ([configuring.md](file:///home/user/workspace/repo/guides/source/configuring.md#L325-L342)), so applications may intentionally rely on environment ciphertext encrypted by `master.key`. Restoring pairing can break those applications unless they provide `RAILS_MASTER_KEY` or copy the key to the environment path. That warrants documentation/release-note handling and argues against an unannounced stable-series backport, but it does not make mixed automatic discovery coherent.

2. **Environment ciphertext absent, stray environment key present**
