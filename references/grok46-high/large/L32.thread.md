1. **String vs block.** Same destination, verb, token, remote, and disabled behavior; the supplied visible name is the name people and AT get. A block is for richer content, not a different submit contract.
2. **GET vs POST vs DELETE.** A person can predict read vs change. GET does not pretend to mutate. DELETE remains a mutating submit, not a GET link.
3. **`remote: true`.** Operable and named like the non-remote twin; destination, verb, token, and disabled behavior preserved.
4. **Disabled.** Cannot be activated; AT can tell it is unavailable.
5. **Nested `form:`.** Form attributes affect the form; control attributes affect the control. Authors should not be surprised that the same `data` key differs on the control vs under `form:`.
6. **Explicit token.** Mutating submits are protected unless the author opts out; GET stays token-free; an explicit value is honored.
7. **Nil URLs.** Missing vs omitted destinations must be explicit. Whether `nil` matches `false`, targets the current page, or is rejected is open.
8. **Unsafe labels.** A string label is shown as text; a block may include tags the author wrote.

### Constraints and non-goals

Keep `button_to` as a form-backed submit; preserve supported calling forms; do not break CSRF for ordinary POST/DELETE; honor persisted-model PATCH unless `method:` is passed.

Non-goals: prescribing markup, new options, JavaScript, internal helper changes, or tests; changing routing or CSRF generation; making `button_to` a general form builder.

### Behavioral examples

**Core — string, default POST.** A labeled `button_to` to a URL with no method renders a named submit that POSTs to that URL, with a token if protection is on.

**Core — block.** Same URL with a block: destination, verb, token, remote, and disabled match the string twin; block content is what the person sees.

**GET.** `method: :get` issues GET with no token and no override.

**DELETE.** `method: :delete` is a mutating DELETE submit, not a GET link, with a token when protection is on.

**Remote.** `remote: true` remains a named submit to the same destination and verb; the form is identifiable as remote.

**Disabled.** `true` cannot be activated; `false` can.

**Nested `form:`.** Extra form attributes (class, data) affect the form; label and disabled still affect the control.

**Explicit token.** String token is submitted as that value; `true` uses the generated token; `false` omits it.

**No destination (`false`).** Still a submit with no explicit destination, string or block.

**Nil URL (boundary).** Must not be an undocumented surprise — illustrative until the product question is answered.

**Unsafe string label (boundary).** `<script>alert(1)</script>` is shown as text, not run. A block with a span still shows that span.

**Counterexamples.** DELETE must not render as an ordinary followable link. Unpermitted strong params fail rather than emit hidden fields.

### Compatibility risks

Apps that scrape or style form class, remote marking, `_method`, or token fields; pre-7.0 “persisted model ⇒ POST”; older “string label ⇒ submit input”; confirmation data on the control instead of `form:`; any tightening of `nil` URL or unsafe-label handling.

### Open product questions

1. Should `nil` as the URL mean “no destination,” “current page,” or invalid?
2. Must string and block be indistinguishable except for visible content, including control type?
3. Should confirm/disable-with data always apply to the control people activate, or is “put this under `form:`” an accepted rule?
4. How strictly must GET stay a safe read?
5. For unsafe labels, is escaping enough, or should already-safe HTML in a string label be allowed (as `link_to` does)?
6. Is AT name/role/disabled exposure in scope, or is “real submit, not a fake link” the accessibility bar?

### External success signals

Authors get the same destination, verb, token, remote, and disabled behavior from a string or a block. Keyboard and screen-reader users can find the control, hear a name that matches the visible label, and activate it when it is not disabled. GET reads; POST/DELETE change data and are not followable as GET links. Unsafe string labels appear as text. `false` still means no destination; `nil` matches the decided rule.

Investigate if authors still cannot predict GET vs DELETE vs remote; if people cannot operate the control without a mouse; if disabled/remote controls are announced as links; or if ordinary POST/DELETE token and class behavior breaks. Stop if the remaining issue is a Turbo `form:` documentation gap rather than `button_to` itself.

Discovery limit: current behavior is from docs and HTML assertions, not from running pages with assistive technology.
