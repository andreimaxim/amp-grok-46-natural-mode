**Verdict: request changes.** Env ciphertext without an env key should not fall back to `config/master.key`.

There is no separate PR branch. That mixed fallback is already what [`credentials_defaults`](railties/lib/rails/application/configuration.rb) does: content and key are chosen independently. That is the bug, not intended pairing.

Environment credentials are separate stores. Automatic discovery should follow whether the env ciphertext exists:

- `config/credentials/<env>.yml.enc` ↔ `config/credentials/<env>.key`
- otherwise `config/credentials.yml.enc` ↔ `config/master.key`
- `ENV["RAILS_MASTER_KEY"]` is the shared override, tried before any key file

`credentials:edit --environment` still force-pairs env content + env key. `show`/`fetch` inherit the mixed defaults.

**Security / compatibility.** Mixing env content with `master.key` turns a missing env key into `InvalidMessage` instead of `MissingKeyError`. With `require_master_key`, Rails only proves *a* key exists. A leftover env key can also open global content with the wrong file. This is a config-integrity failure more than a confidentiality hole: the wrong key cannot decrypt. `RAILS_MASTER_KEY` already covers “no env key file.”

**Correct tiny diff:** pair both paths on env ciphertext existence. Explicit `content_path`/`key_path` overrides stay independent.

**Missing tests:** (1) env ciphertext, no env key, unrelated `master.key` → `key_path` stays the env key; `require_master_key` raises `MissingKeyError` for that path. (2) no env ciphertext, stray env key → global content still uses `master.key`.
