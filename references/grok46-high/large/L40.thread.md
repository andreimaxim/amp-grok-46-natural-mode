**Why it matters:** Wrong lifetime causes broken images/downloads, accidental long-lived sharing, or CDN/cache behavior that contradicts the expiry the developer thought they set. The security warning (expiry ≠ authorization) is easy to miss because expiry *looks* like a permission knob.

**Desired progress:** One teachable expiration story per kind of link, with boundaries a developer can predict without reading controller internals.

---

### Desired outcome

After this work, a developer can choose a link kind and state, in advance:

- whether it is permanent or time-limited;
- which clock they are setting (application identifier vs backend service URL);
- what a recipient, a CDN, and a later first-time requester will observe at “still valid,” “exactly at cutoff,” and “after cutoff”;
- that public and private storage differ only for **service** URLs;
- that proxy and redirect differ in **how bytes are delivered and cached**, not in how the signed application identifier is minted;
- that variants follow the same application-identifier and delivery-mode rules as original files;
- that expiry limits *this URL*, and is not access control.

Success is qualitative: developers can pick the right link for “stable public asset,” “short-lived share,” and “do not put this in a CDN as if it were permanent,” and get the lifetime they expected.

### Scope

In:

- Predictable lifetime of signed blob identifiers: permanent default, optional relative/absolute cutoff, optional app-wide application-URL default.
- Predictable lifetime of service URLs: private vs public.
- Predictable proxy vs redirect delivery, including cache headers and what a recipient can do with a copied URL.
- Tampered, expired, and invalid identifiers (including variation keys) failing closed in one client-visible way.
- Variants/previews using the same application-identifier expiry as the original blob they were minted with.
- Boundary timing: still valid before cutoff; unusable at/after cutoff, stated explicitly.
- Teaching the difference between “this URL stopped working” and “this person is allowed to see this file.”

Out (non-goals):

- Authenticated/authorized file access (already a separate, documented replacement of the public controllers).
- Encrypting identifiers, hiding blob ids, or rotating signing secrets as a product feature.
- Direct-upload PUT URL design, except to note they are a different, already short-lived clock.
- Changing storage providers, mirroring, or CDN productization.
- Distinct HTTP status for expired vs tampered vs missing file (unless predictability *requires* it; current 404 is a viable “unusable link” signal).
- New developer APIs, data model changes, or a unified “one URL to rule them all.”
- Making public backend objects expire, or making private service URLs permanent, as a silent default flip.

---

### Risks

- **Cache vs identifier skew (proxy):** forever public cache can outlive a short signed identifier. Tightening cache to match expiry can bust CDNs that today depend on immutable proxy responses. Leaving it invites “I expired it but the CDN still has it.”
- **Default permanence of application URLs:** existing emails, hotlinks, and CDN mappings assume they never die. Turning on an app-wide default later 404s those URLs.
- **Two knobs, similar names:** application-URL default vs service-URL default. Collapsing or renaming them in the *story* without a careful compatibility story will mis-set one clock or the other.
- **Public services:** developers who call `#url` expecting a 5-minute cap on a public bucket will keep publishing durable object URLs.
- **Identical 404s:** simpler for clients; harder to debug “expired” vs “typo” vs “purged file.”
- **Variants:** a non-expiring variation key next to an expiring blob identifier is easy to misunderstand; the blob identifier already gates the representation URL.
- **Expiry ≠ auth:** remaining the most likely framing failure. If teams use short links as their only control, this work can make them *more* confident without making files actually private.

### Behavioral outcomes and acceptance examples

Required examples unless marked illustrative.

#### 1. A signed identifier is permanent until the developer says otherwise

- **Permanent:** Developer mints a signed identifier with no cutoff. Days later, the same identifier still names that blob.
- **Relative cutoff:** Minted with a 1-minute lifetime. Used immediately → blob is found / download works. Used after 2 minutes → identifier is unusable (find returns nothing; download 404).
- **Absolute cutoff:** Same pattern with a cutoff time 1 minute from now.
- **Boundary:** At the cutoff instant the identifier is already unusable, not valid-through-the-instant. (Pin this; today’s Active Storage tests skip the exact instant.)
- **Counterexample:** Minting a cutoff does not delete the file. A newly minted identifier for the same blob still works.

#### 2. Application proxy/redirect URLs share that identifier clock

- **Default:** Proxy and redirect URLs with no cutoff keep working later. Redirect still 302s; proxy still returns bytes.
- **Per-URL cutoff:** Either helper with a 1-minute cutoff works immediately and 404s after 2 minutes, for both original files and variants.
- **App-wide default:** When the application default lifetime is 1 minute, URLs generated without a per-URL cutoff follow that 1-minute clock.
- **Invalid identifier:** Garbage signed id or invalid variation key → 404 for proxy and redirect, blobs and representations.

#### 3. Service URLs are a different clock, and public/private matters

- **Private:** `#url` stops working after the service lifetime (default 5 minutes) even if the application URL is still valid. Hitting a still-valid redirect URL after that mints a **new** service URL; the old service URL does not revive.
- **Public:** `#url` remains a durable object address; recipients can keep using it after 5 minutes.
- **Misuse (illustrative):** Putting a private `#url` into an email as if it were the stable application URL → recipients fail after the service lifetime.

#### 4. Proxy and redirect cache what their delivery mode implies — and that must not silently contradict expiry

- **Redirect, default:** Redirect response is privately cacheable for the service-URL lifetime (5 minutes today). It does not tell public CDNs to store the file forever.
- **Proxy, default permanent identifier:** Successful proxy response is publicly cacheable for a very long time (today ~100 years, immutable), which matches a permanent application URL.
- **Proxy + short identifier (the conflict to resolve in the outcome, not by prescribing a mechanism):** If a developer publishes a 1-minute proxy URL, then after that minute: a first-time requester gets 404. It must be explicit whether a CDN that already cached the bytes may keep serving them. Today it may. Predictability requires that this not be a surprise.
- **Proxy failure:** Missing/errored download is not stored as a success (`no-cache`, 404 or 500).

#### 5. Variants do not get a secret extra lifetime

- Representation URL minted with a 1-minute blob-identifier cutoff: works inside the window, 404 after, same as the original file.
- Invalid variation key: 404 even when the blob identifier is valid.
- Processed variant’s **service** URL follows the private/public service-URL rules above, independent of the application URL.

#### 6. Expiry is not authorization

- Anyone with a still-valid application URL can download through the built-in endpoints, even if the rest of the app requires login.
- After expiry, that URL 404s; a different still-valid URL for the same file still works.
- Developers who need “only this user” must put their own front door in front of the file. Short links do not substitute.

### Steering evidence

**Success looks like:** A developer can explain, without caveats that contradict production, how long each of the three link kinds lasts, what happens at cutoff, and which cache/public-private choice they just made. Support questions of the form “why did this image die in 5 minutes?” and “I expired it, why is it still on the CDN?” become rare or have a one-sentence answer that matches observed behavior.

**Investigate / reconsider the framing if:**
- Failures are actually authorization bugs (wrong person, not wrong lifetime).
- The real pain is only missing docs, and behavior is already consistent once the three clocks are named — then shrink to a documentation outcome.
- CDN operators reject any change to forever-proxy caching, and developers reject leaving the cache/expiry skew in place — then the outcome “predictable proxy + short expiry” is internally in conflict and must be split or dropped.
- Apps depend on exact-instant *inclusive* validity (`valid through expires_at`) and we documented the opposite.

**Stop if:** The work becomes a new access-control or link-shortening product, or proposes silently flipping default application URLs from permanent to expiring.
