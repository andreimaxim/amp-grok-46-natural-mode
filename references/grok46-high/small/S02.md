**Block this.** `deep_merge?` is the left-hand value’s compatibility policy, not a redundant type check.

Current contract in [`activesupport/lib/active_support/deep_mergeable.rb`](activesupport/lib/active_support/deep_mergeable.rb):

```ruby
if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
  this_val.deep_merge(other_val, &block)
elsif block_given?
  block.call(key, this_val, other_val)
else
  other_val
end
```

`deep_merge?` defaults to `other.is_a?(self.class)`. Docs say classes may restrict or expand that domain. Hash restricts to `Hash`; `ActionController::Parameters` expands to any `DeepMergeable`. The receiver (`this_val`) owns that call.

#### Custom classes

[`activesupport/test/deep_mergeable_test.rb`](activesupport/test/deep_mergeable_test.rb) already encodes this:

- `SubWrapper < Wrapper` → nested values **are** deep-merged.
- `OtherWrapper = Wrapper.dup` → both include `DeepMergeable`, but they are unrelated, so nested values are **replaced**, not recursed.
- `OmniWrapper` overrides `deep_merge?` to **expand** into `OtherWrapper`.

After the diff, Wrapper/OtherWrapper nested pairs would recurse because both are `DeepMergeable`. The “do not deep merge non-subclass values by default” test would fail, and a custom class could no longer **restrict** compatibility. Same bug for Hash vs `Parameters`: `Hash#deep_merge?` is `other.is_a?(Hash)`, so a nested Hash does not deep-merge nested Parameters today.

#### Block fallback

When `deep_merge?` is false, the conflict is a normal merge: the block runs, or the right-hand value wins. The proposed check skips that path for any two `DeepMergeable` objects, including pairs that deliberately reject each other.

#### Mutation / return

`deep_merge` is `dup.deep_merge!`; `deep_merge!` returns the includer’s `merge!` result; nested recursion uses non-bang `this_val.deep_merge(...)`, so nested values are not mutated in place. The diff does not change those mechanics when the recursive path is already taken. It changes *whether* that path is taken, so rejected pairs get a recursive merge instead of replacement.

Keep `this_val.deep_merge?(other_val)`. If it still looks redundant, add a regression for a custom class whose `deep_merge?` returns false for another `DeepMergeable`: block fallback, default replacement, `deep_merge` does not mutate, `deep_merge!` mutates the receiver and returns `merge!`’s result.
