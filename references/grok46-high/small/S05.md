The proposed reorder should be rejected. Strict `add` is documented and implemented as raise-instead-of-append, not append-then-raise.

`ActiveModel::Errors#add` builds the `ActiveModel::Error`, then if `options[:strict]` is set it maps `true` to `ActiveModel::StrictValidationFailed` (or uses the given exception class) and `raise`s with `error.full_message` **before** `@errors.append(error)`. Non-strict `add` then appends and returns that `Error`. The method docs state this explicitly: raise “instead of adding the error”, and after `add(..., strict: true)` they show `person.errors.messages # => {}`.

That contract is load-bearing:

- **Exception class and message.** `strict: true` must keep raising `ActiveModel::StrictValidationFailed` with the full message (`"Name is invalid"`, `"Title can't be blank"`). `strict: SomeException` must keep raising that class with the same message. Tests in `validations_test.rb` cover both (`test_strict_validation_in_validates`, `test_strict_validation_custom_exception`, `test_strict_validation_error_message`). A reproduction of the current method matches: `strict: true` → `ActiveModel::StrictValidationFailed: Name is invalid`; `strict: NameIsInvalid` → `NameIsInvalid: Name is invalid`.
- **Collection mutation.** After a rescued strict `add`, the collection must stay empty. Appending first would leave the error in `@errors` for anyone who rescues, so `errors.messages`, `errors.empty?`, and later `valid?` would all lie. That is a silent behavior change for every `validates ..., strict:` / `validates!` caller, not a convenience.
- **Normal `add` return.** Non-strict `add` must still append and return the `ActiveModel::Error` (`errors_test.rb`: `"add creates an error object and returns it"`). Strict `add` never returns; it raises. Do not change the non-strict path to make the strict path inspectable.
- **Custom strict exception classes.** Custom classes only get a string message, not the `Error` object. That is why “inspect after rescue” looks appealing, but stuffing the error into the collection couples exception handling to validation state. Rescuers of `TokenGenerationException` / `CustomStrictValidationException` would suddenly see a recorded error they were never meant to treat as a normal failure.

If callers need the `Error` after rescue, put it on the exception (or pass `full_message`, which they already get). Do not mutate `@errors` on the strict path. Built-in validators already forward `**options` into `errors.add` (e.g. `PresenceValidator`), so this method is the entire strict implementation; changing the order is a framework-wide contract break.
