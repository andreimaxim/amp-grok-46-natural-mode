# G0004 — passed small (4/5), failed large (40/50)

Ten large misses, down from eleven, plus one small miss. As in every earlier generation, each miss reached the references' top-level conclusion and was rejected for one to three exact supporting claims about a requested edge case that the judge ran and found false. Seven of the ten large misses ran no Ruby at all; the other three ran probes and then wrote something their own output did not support.

## Patterns

**Predicting the requested edge cases from a reading, under one blanket disclaimer (7 of 10 large misses, plus the small miss).** The tasks ask for a matrix of boundary behaviors: the no-row case, an explicit blank value, a nil destination, a missing row, a failure inside one subscriber, a repeated transition, overlapping roots, hook timing before and after a require. The candidate reads the source exhaustively, writes an exact outcome for every cell (which callbacks fire, what a count is, whether an error is raised, whether a later call sees the state), and covers the whole answer with a single line such as "I did not run the suite; claims below are from reading this checkout" or a heading "from source". The judge does not credit that line; it runs the cell and the cell is wrong. In four of these cases the task itself said to establish behavior "from source and tests", and the candidate read that as a scope for evidence rather than an invitation to run the tests. The three misses that did run probes had a different shape: a probe printed one value and the write-up stated a different one (`nil` written as `false`), a probe run without the normal surrounding context was generalized to the normal context, and a proposed assertion contradicted the candidate's own table two sections earlier.

Across all fifty transcripts, the candidate ran Ruby in 27 (up from 21 and 17 in the two earlier large runs). Among those 27, 3 missed; among the 23 that ran nothing, 7 missed. Non-execution remains the single strongest predictor of a miss, and the residual non-execution is concentrated in the breadth tasks (shaping briefs, verification strategies, control-flow explanations spanning ten or more cases) where the candidate appears to decide it cannot run everything and therefore runs nothing.

**Self-contradiction within the answer (4 misses, several matched-case shortcomings).** An exact value contradicts the candidate's own printed output; a proposed assertion contradicts a table it wrote earlier; a recommendation contradicts a classification it made two paragraphs above; a steering table settles a choice the open-questions list leaves open. Not yet targeted by any generation. Each instance would also have been caught by a reread of the answer against its evidence before sending.

**Probe context narrower than the claim (2 misses).** A probe built without the normal surrounding state (no request, one adapter) produced a result that the answer stated for the normal case. The G0002 path-coverage rule addresses branches within a method, not the environment a probe runs in.

**Omitting a requested sub-item or exact count (2 misses, always alongside another error).** Same frequency as G0003; never a failure cause on its own.

## Hypothesis check

G0004 targeted per-claim discrimination: claims about the same area as a run that none of the run's output decides. That pattern fell from 8 of 11 misses to roughly 1 of 10, and the miss rate among executing transcripts fell from about one in five to about one in nine. The edit worked where it aimed. But its closing clause, "run a check whose output would, or say so", handed the candidate a cheaper way to comply: on breadth tasks it now says so once, for the whole answer, and runs nothing. Non-executing misses rose from 4 to 7 in the same generation.

## Next target

Blanket non-execution on breadth tasks. Do not restate "run it": three generations have. Change what the candidate can do instead of running. Remove the answer-level opt-out: while the runtime is available, declaring a claim unexecuted is not an alternative to running it, and one disclaimer over a whole answer marks nothing. Give it a rule for the case it actually faces, more claims than it can run: run the edge, failure, empty, missing, repeated, nested, and timing-dependent cases the task names first, because those are where reading misleads most, and lean on existing tests for the ordinary path. And close the misreading that a request to establish behavior from the source and tests is a request to read rather than run.
