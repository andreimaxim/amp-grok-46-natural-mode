# G0003 — passed small (5/5), failed large (39/50)

Eleven misses, down from eighteen. As in every earlier generation, each miss reached the references' top-level conclusion (correct verdict, correct control flow, correct contract) and was rejected for one or two concrete supporting claims that the judge executed or read and found false. Nine of the eleven misses ran Ruby; the candidate now executes, but the executions do not cover the claims that failed.

## Patterns

**Claims outside the scope of what was run (8 of 11 misses).** The candidate runs an existing test file or a probe of its own, watches it pass or print, and then writes claims about the same area that no line of that output decides. Shapes it took:

- A probe printed one observable (a callback count, a query count, a return class) and the write-up asserts a neighboring observable it never printed (a timestamp changing, a value being stored in a cache, an exhaustion boundary).
- An existing test file passed, and the candidate states a number, order, or condition that none of its assertions make; in one case it misread a test's argument as the assertion.
- The write-up explains the mechanism behind an observed result ("because nil is stored", "the wrapper calls X which calls Y", "no new object is allocated") from a mental model, when the result itself was observed but the mechanism was not. One answer contradicted its own later paragraph.
- A guarded validation is described as if the guard did not exist: the candidate names the check but not the condition that decides whether it runs, so it predicts a raise where the code skips the check, or propagation where an outer rescue catches it.
- Proposed probes whose setup or assertion fails against the current checkout (two cases, down from about five): the candidate ran other probes in the same session but not the one it handed over.

The references' matching answers either print the exact value they then claim, or restrict the claim to what they printed. The G0003 rule ("run each such case before you write it down") is satisfied in the candidate's eyes once it has run something about the topic; it does not ask, claim by claim, whether the output would have differed had the claim been false.

**Leaving a decidable question open (2 misses, 2 matched-case shortcomings).** A shaping brief asks the user whether a combination "may already work" when the source it quoted settles it; an explanation stops at "no nil guard, no test covers it" for an explicitly requested edge that a one-line run resolves. Same frequency as in G0002.

**Omitting an explicitly requested sub-item (3 misses, always alongside another error).** A requested environment comparison left cursory, a requested count contract declined, requested behaviors inventoried but given no probe. Not on its own a failure cause in any case.

**Fabricated citation (one-off).** A commit SHA presented as verified evidence that does not exist in the history.

## Hypothesis check

G0003 targeted unexecuted oracles by removing the line-citation escape and naming proposed tests, coverage claims, and API names as claims. It worked where it aimed: misses that executed nothing fell from six to two, and handed-over oracles that fail against the checkout fell from about five to two. The candidate now runs probes in most cases. What remains is the distance between what a run showed and what the answer says: the candidate treats a run in the area as verification of every sentence about the area.

## Next target

Per-claim discrimination. Do not restate "run it": the candidate does run, and believes the rule is met. Make the check operational at the level of a single claim: a run verifies only what its output shows; a passing suite does not verify what no assertion states, a probe does not verify a value it did not print or the mechanism offered to explain it; for each concrete claim, name the printed output that would have been different if the claim were false, and if none exists, run one that would or mark the claim unexecuted.
