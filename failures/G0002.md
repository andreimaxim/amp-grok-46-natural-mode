# G0002 — passed small (4/5), failed large (32/50)

First generation to reach the large suite. Eighteen misses. As in G0000 and G0001, almost every miss reached the references' top-level conclusion (correct verdict, correct control-flow shape, correct contract) and was rejected for one or two concrete supporting claims that the judge executed and found false.

## Patterns

**Unexecuted expected outcomes and oracles (15 of 18 misses).** The candidate reads the implementation exhaustively — dozens of `sed`/`rg` calls per case — and then writes concrete claims it never ran, in a checkout whose test suite runs in seconds. Six misses ran no Ruby at all; the rest ran existing test files or unrelated probes, not the case they got wrong. The claims took several shapes, all of which the judge settled with one focused run:

- Expected values for a preservation or regression suite (return value, truthiness, whether a callback fires, dirty-tracking flags, in-memory state after rollback, an exact message string, the return shape for a collection input).
- Proposed assertions, probes, reproducers, and test templates handed to the user as oracles: one calls an API that does not exist, one asserts a query pattern the unrefactored baseline already produces, one template fails on one of the fixtures it says it covers, one "before/after" matrix never constructs the "before" case, one reproducer asserts a regression that current code does not prevent.
- Claims about what an existing test covers, or that a named fixture has a property (it does not).
- Outcomes of an interaction between two layers (middleware stacked twice, a subclass inheriting a queue proc, save on a clean record) stated from a mental model of the code rather than a run.

The references' matching answers in the same cases quote the output of the exact probe. The candidate's investigation volume is not the gap; execution is. The G0001 rule ("execute that exact case when a runtime is available, or cite the line that decides it") is satisfied in the candidate's eyes by citing lines, and its scope — "a concrete outcome for a specific input" — does not, to the candidate, cover a test it proposes, a coverage claim about an existing test, or an API name it writes into an assertion.

**One-path generalization (4 misses, 2 matched-case shortcomings).** Still present after G0002's edit, now mostly where the second path lives in a sibling method form, a subclass override, or an array-versus-hash input rather than a visible branch of the method read. Lower frequency than in G0001's small run; each instance would also have been caught by running the case.

**Leaving a decidable question open (2 misses, 1 matched-case shortcoming).** One verification strategy declared a boundary behavior "unproven" when the underlying layer's source and tests settle it; one shaping brief listed alternatives and asked the user to choose the central outcome, and did not say what evidence would resolve its open questions. One-off compared with the pattern above.

**Unsafe procedural advice (one-off).** A cleanup step recommended for the rejected-call case would remove a frame that was never pushed.

**Stale or imprecise citations (several matched cases).** Line ranges that miss the cited code. Never a failure cause; a symptom of the same read-don't-run habit.

## Hypothesis check

G0002 targeted path-complete general statements. The small suite improved 3→4 and the generalization pattern is now a minority of misses, so the edit helped where the alternative path is a visible branch. It did not remove the pattern where the other path is in a different class or method form, and it did nothing for the dominant pattern, which the G0001 edit was meant to address and only partly did.

## Next target

Unexecuted oracles. Do not restate "run it or cite the line": the candidate cites lines and believes it complied. Change the approach: when the runtime is available, citing the line is no longer an alternative to running the case, and the rule must name the things the candidate does not currently recognize as claims — proposed assertions and templates, coverage statements about existing tests, API and fixture names written into test code, expected values in a matrix — as things to be executed against the current checkout before they are written down.
