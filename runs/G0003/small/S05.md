**Reject this.** Strict `add` must raise *instead of* recording the error. Appending first breaks that contract.

Current `add` builds the `ActiveModel::Error`, then:

```341:352:activemodel/lib/active_model/errors.rb
    def add(attribute, type = :invalid, **options)
      attribute, type, options = normalize_arguments(attribute, type, **options)
      error = Error.new(@base, attribute, type, **options)

      if exception = options[:strict]
        exception = ActiveModel::StrictValidationFailed if exception == true
        raise exception, error.full_message
      end

      @errors.append(error)

      error
    end
```

The documented contract is explicit: `:strict` raises **instead of adding**, and the collection stays empty:

```321:331:activemodel/lib/active_model/errors.rb

    #   # => ActiveModel::StrictValidationFailed: Name is invalid

    #
    #   person.errors.messages # => {}
```

Same wording on `validates` / `validates!`: raise instead of adding. That is the whole point of strict validations — fail immediately, do not collect.

What this change would get wrong:

**Exception class and message stay the same, so this is not a bugfix.** `strict: true` still becomes `ActiveModel::StrictValidationFailed`; a class such as `NameIsInvalid` / `CustomStrictValidationException` is still raised with `error.full_message` (`"Name is invalid"`, `"Title can't be blank"`). Tests already cover that (`test_strict_validation_custom_exception`, `test_strict_validation_error_message`). Callers who rescue already have the message on the exception. They do not need the collection.

**Collection mutation is the contract break.** After `add(..., strict: true)` raises and is rescued, `errors` must remain unchanged: `messages == {}`, `empty? == true`. Appending first leaves the new `ActiveModel::Error` in `@errors`. Rescuers then see `added?`, `full_messages`, and `size` as if this were a normal validation failure. `valid?` already `errors.clear`s before running validators; a strict failure mid-run would then leave a half-built errors object behind the exception.

**Normal `add` return must not change.** Non-strict `add` appends and **returns the `ActiveModel::Error`** (see `test "add creates an error object and returns it"`). Strict `add` must not return at all. Moving `append` above the `raise` does not give callers a return value; it only smuggles state into the collection after `raise`. If someone needs the object after rescue, attach it to the exception — do not mutate `errors`.

**Custom strict classes do not justify this.** `raise exception, error.full_message` already works for any `StandardError` subclass. Custom classes are about the exception type, not about recording an `ActiveModel::Error`.

Please keep the raise-before-append order. The `Error` is constructed first only so the exception can carry `full_message`; that object is intentionally not inserted into `@errors`.
