**Don’t land this.** `deep_merge?` is the compatibility hook; `other_val.is_a?(DeepMergeable)` is not a substitute.

```41:47:activesupport/lib/active_support/deep_mergeable.rb
        if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
          this_val.deep_merge(other_val, &block)
        elsif block_given?
          block.call(key, this_val, other_val)
        else
          other_val
        end
```

`deep_merge?` is documented as the place classes “restrict or expand the domain of deep mergeable values.” Default is `other.is_a?(self.class)`. Hash tightens that to `other.is_a?(Hash)`; Parameters widens it to any `DeepMergeable`; `OmniWrapper` in the tests does the same. The proposed check never calls that method, so those overrides become dead code and the default sibling-class rule disappears.

That is already covered, and it would fail:

```89:91:activesupport/test/deep_mergeable_test.rb
    nested_value = Wrapper[@hash_1].deep_merge(OtherWrapper[@hash_2])[@nested_value_key]
    assert_equal OtherWrapper[@hash_2][@nested_value_key], nested_value
```

`OtherWrapper` is `Wrapper.dup`, so both are `DeepMergeable` but `Wrapper#deep_merge?` is false. Today the nested value is replaced with `other_val`. After this change it would recurse into `this_val.deep_merge(other_val)`.

Consequences of taking that path:

- **Block fallback.** Incompatible nested pairs currently hit `block.call(key, this_val, other_val)` (or `other_val` with no block). Recursing swallows that pair; the block only runs on leaves. The docs say the block is for non-`DeepMergeable` values, but the real gate is `deep_merge?`, including two DeepMergeable objects that the receiver refuses.
- **Return identity.** Replacement keeps `other_val` (here an `OtherWrapper`). Recursion returns `this_val.dup.deep_merge!(...)` — a new object of the receiver’s class. The assertion above is exactly that distinction.
- **Mutation.** Nested recursion still uses `deep_merge` (non-bang), so `deep_merge!` still does not mutate nested values when it *does* recurse. The change is which pairs recurse. For a custom `merge!` that assumes `other.underlying` (as `Wrapper` does), Hash-or-Parameters nested under a wrapper would go from replacement to `NoMethodError`.
- **Hash vs Parameters.** Hash will not deep-merge nested Parameters (`deep_merge?` → `is_a?(Hash)`). Parameters *will* deep-merge nested Hash. That asymmetry is owned by each override. `is_a?(DeepMergeable)` would make Hash recurse into Parameters and then `Hash#merge!`/`to_hash`, including `unpermitted` raises.

`this_val.is_a?(DeepMergeable)` is the right first check (responds to `deep_merge?` / `deep_merge`). The second check has to stay `this_val.deep_merge?(other_val)`. I ran `activesupport` `test/deep_mergeable_test.rb`: 10 runs, 10 assertions, all passing on current code.
