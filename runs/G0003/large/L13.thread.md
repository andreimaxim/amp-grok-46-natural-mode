## Assistant

**Problem frame:** A test author or diagnostic author needs to watch Active Support notifications only while a block of work runs. Today that job is possible, but it is assembled by hand on top of a long-running subscription API, so it is easy to observe the wrong events, keep listening too long, or misread nested, mutated, or failing work.

This is a draft of the shared understanding. The current-state facts below are from this revision’s docs and tests (unread as executed). The pain and desired outcomes are inferred from that API shape and from how test helpers already use it.

### Current behavior

Temporary observation is [`ActiveSupport::Notifications.subscribed`](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L337): install a callback, run a block, always remove that callback afterward. Docs present this as a sparingly used alternative to long-running subscribers because subscribe/unsubscribe clears internal caches ([docs](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L155-L190)). The instrumentation guide documents long-running [`subscribe`](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L42-L90), not temporary observation.

Matching is the same as `subscribe`: exact string, regexp, or no pattern (all events). Fanout rejects other pattern types ([fanout](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L85-L107)). Direct `subscribed` tests cover exact name and all-events ([`test_subscribed`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L242), [`test_subscribed_all_messages`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L257)). Regexp matching for a block-scoped observer is exercised through [`capture_notifications`](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L85-L88) ([test](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L83-L111)), not a dedicated `SubscribedTest` example.

After the block, that callback does not see later events of the same name ([`test_subscribed`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L242)). The method uses `ensure`, so unsubscription is intended even if the observation block raises; that raise path is not itself tested.

Timestamps: default five-argument callbacks receive wall-clock `Time` ([`test_timed_subscribed`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L295)). `monotonic: true` yields monotonic `Float` start/finish ([`test_monotonic_timed_subscribed`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L297-L313); [docs](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L181-L190)). Long-running `subscribe` / `monotonic_subscribe` use the same two domains ([tests](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L125-L161)).

Callback shape is inherited, not special-cased: a single-argument listener receives an `Event`; otherwise name, start, finish, id, payload ([docs](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L36-L72); [arity tests](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L106-L129); [arity detection](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/fanout.rb#L368-L384)). Test capture uses the one-argument form ([helper](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L87)).

Nested work and payload mutation are specified for instrumentation, not as `subscribed`-specific tests. Inner `instrument` finishes and is published before the outer event ([`test_nested_events_can_be_instrumented`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L487-L499)). The instrumented block may mutate the yielded payload; subscribers see the mutated hash ([payload tests](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L52), [L475-L479](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L475-L479)). A nested temporary subscriber does **not** see an event whose start happened before it subscribed, even if finish runs inside its block ([`test_subscribed_interleaved_with_event`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L223)).

If the instrumented block raises, the event is still published, the payload gains `:exception` (`[class_name, message]`) and `:exception_object`, and the exception still raises ([docs](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L95-L107); [`test_instrument_publishes_when_exception_is_raised`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L504-L513); [instrumenter](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/instrumenter.rb#L91-L92)).

Long-running `subscribe` / `unsubscribe` remain a separate path: keep listening until explicitly removed, including unsubscribing by subscriber object or by string name, with regexp subscribers only dropping the named event ([docs](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L192-L227); [unsubscribe tests](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L322-L372)).

**Usability gap (inferred):** a test or diagnostic author must supply both a collector callback and a work block, choose pattern and monotonic flag, and know which of the rules above apply. [`NotificationAssertions`](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb) already wraps this for assertions, which shows the job is common, but temporary observation itself is still documented as an exceptional, cache-wiping use of the long-running API.

### Desired observable outcomes

1. While a chosen block runs, the author can observe matching notifications and, when the block ends, observation has stopped—even if that block raises.
2. Matching is exact name, regexp, or all events, with the same meaning as today.
3. Events observed during that window have the same meaning long-running subscribers already see: nested instrumentation (inner published before outer), in-block payload mutation, and a published event with exception payload when the instrumented work raises (the original error still surfaces).
4. Five-argument observers can still choose wall-clock timestamps (default) or monotonic timestamps.
5. Long-running `subscribe` / `unsubscribe` and both callback arities keep their current behavior.

These are outcome claims, not an API or helper design.

### Non-goals and compatibility

- Do not change long-running `subscribe` / `unsubscribe` (including name-based unsubscribe and regexp exclusions).
- Do not change callback arities: one argument still means `Event`; otherwise name, start, finish, id, payload.
- Do not change when instrumentation publishes, nested finish order, payload mutation, or exception keys.
- Do not treat production-wide temporary subscription performance as in scope; the existing cache-clearing warning still applies to non-test use.
- Do not expand this into a new assertion catalog. Existing helpers may keep working; they are not the product being reshaped except as users of temporary observation.

### Representative examples

Required cases, not an exhaustive catalog.

**Exact name, then silence.** Subscribe temporarily to `"foo"`. During the block, `"foo"` is observed and `"foofoo"` is not. After the block, another `"foo"` is not observed. (Current: [`test_subscribed`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L242).)

**Regexp.** Observe `/post\./` for a block that instruments `"post.submitted"`. That event is observed; a non-matching name in the same block is not. (Current helper: [capture test](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L92-L98).)

**All events.** Omit the pattern. Every instrumented name during the block is observed; none after. (Current: [`test_subscribed_all_messages`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L257).)

**Wall-clock vs monotonic.** Default five-argument observation of `"foo"` yields `Time` start/finish. The same work with monotonic observation yields `Float`. Events after the block do not update those callbacks. (Current: [timed](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L295) / [monotonic](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L297-L313).)

**Nested instrumentation.** Temporary observation of all events around:

```text
instrument "outer" do
  instrument "inner" { ... }
end
```

The observer sees `"inner"` complete first, then `"outer"`, each with its own payload. (Current publish order: [`test_nested_events_can_be_instrumented`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L487-L499).)

**Nested observation boundary.** An event is started under an outer temporary observer, then finished inside an inner temporary observer of the same name. The outer observer records it; the inner one does not. (Current: [`test_subscribed_interleaved_with_event`](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L223).)

**Payload mutation.** The instrumented block writes into the yielded payload. The temporary observer’s event shows the mutated values, not the pre-block hash. (Current for subscribers: [L45-L52](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L52), [L475-L479](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L475-L479).)

**Instrumented block raises.** Temporary observation around `instrument("awesome") { raise "FAIL" }`: the error still raises; the observed event payload includes `exception: ["RuntimeError", "FAIL"]` and the exception object. (Current: [L504-L513](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L504-L513).)

**Observation block raises.** The work block passed to temporary observation raises before finishing. After that failure, later instruments are not delivered to that callback. (Intended by `ensure` in [`subscribed`](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L337); not a dedicated test.)

**Counterexample — leave long-running subscribers alone.** A process-lifetime `subscribe("render")` still receives `"render"` before, during, and after someone else’s temporary observation of `"sql.active_record"`. Unsubscribing that long-running subscriber still requires `unsubscribe`.

### Acceptance signals

**Success looks like:** a test or diagnostic author can watch a block of work, state a name / regexp / all-events filter, and afterward describe only those events—with nested order, mutated payloads, and exception payloads when the instrumented work failed—without leftover listening and without rewriting existing `subscribe` callbacks.

**Investigate the implementation of observation if:** events leak after the block; matching disagrees with `subscribe`; monotonic vs wall-clock types flip; nested inner/outer order changes; raising instrumented work is silent or loses `:exception` / `:exception_object`; or an observation-block raise leaves the callback installed.

**Reconsider the problem framing if:** authors are not actually blocked by temporary observation, and the real pain is assertion helpers, production cache cost, or confusion about `Event` vs five-argument callbacks. In that case stop treating `subscribed` usability as the outcome.

**Stop or reject the work if:** long-running `subscribe` / `unsubscribe` behavior or callback arities change in order to make the temporary path nicer.

### Open questions

- Is the intended user of this improvement the raw `subscribed` caller, the test assertion helpers that wrap it, or anyone writing short-lived diagnostics? The request names test and diagnostic tooling; it does not say which surface must feel better.
- Should temporary observation stay documented as “use sparingly” in apps, while becoming an ordinary tool in tests? That split is implied by the cache warning versus `capture_notifications`, not decided.
- The interleaved start/finish example is current behavior. Confirm it is required (an event belongs to observers present at start) rather than a quirk to hide.

If the pain is “too much bookkeeping to watch a block,” this draft is the outcome. If the pain is really leaky listeners, missing regexp docs, or assertion helpers, the outcomes above should be cut to that.
