**Problem frame:** A Rails developer requires a named value from `ActiveSupport::OrderedOptions` (or an `InheritableOptions` child of it) and uses the existing bang read to fail if it is not usable. Today that failure always looks like “this name is blank,” whether the name was never assigned, was assigned `nil` or `false`, or holds only whitespace. Inherited parent values and child overrides collapse into the same signal. The developer cannot tell what went wrong, while successful reads and Hash-like order must stay as they are.

**Hypothesis (correct me):** the work is only to make those existing required-read failures understandable. It is not a new required-read gesture, and it is not a change to which values already succeed.

**InheritableOptions.** A child keeps reading a parent name until it writes its own. A child write hides the parent for that name only; the parent is unchanged. `overridden?(:name)` is true only when the parent had the name and the child wrote it.

Bang on an inherited present value succeeds with that value. Bang on an inherited `false` or whitespace-only string fails with the same `":name is blank"`. After a child writes `nil` over a present parent, the child’s bang fails and the parent still holds the original value. A name on neither parent nor child fails the same way.

**Feedback channels today.** Ordinary miss → `nil`. Required miss/blank → `KeyError` whose text always says blank and does not carry the name as `KeyError#key`. `respond_to?` does not distinguish. Inspect/to_h show stored pairs but not “this bang failed because the child overrode the parent with nil.”

## What should change, and what must not

**Behavioral outcome.** Using the existing bang read, the developer still gets the current successful value when the required name is usable, and still gets a failure when it is not. On failure they can tell which name was required and which of these happened: never assigned; assigned `nil`; assigned `false`; assigned a whitespace-only string (or other blank). On an inheritable child they can tell whether the rejected value was inherited or written on the child. Successful readers, writers, `[]`, `dig`, order, and `respond_to?` stay as they are.

**Non-goals.** New names or gestures for required reads. Changing which values already succeed. Changing Hash-like insertion order or symbol-key iteration. Making ordinary (non-bang) readers raise. Making `respond_to?` report only assigned names. Broader config, credentials, or `Configurable` work.

**Compatibility boundaries.**

- If bang succeeds today, it still succeeds and returns that same value (`:bar`, `"ok"`, `true`, `0`, inherited present parent values, child overrides that are present).
- Ordinary `h.name` / `h[:name]` / `h["name"]` still return the stored value or `nil`.
- String and symbol still address the same stored name for `[]`, `[]=`, `dig`’s first argument, and dynamic accessors.
- Iteration and `to_h` still yield symbol keys in insertion order.
- Failure remains a `KeyError` (callers that rescue it keep working). Message and whether the error identifies the name may improve; the set of failing cases (`nil`, `false`, whitespace-only, missing, inherited blanks, child-nil override) stays failing.
- `respond_to?(:name)`, `respond_to?(:name=)`, and `respond_to?(:name!)` remain true.

## Journeys

Required unless marked illustrative.

1. **Present required value.** The developer sets `host = "api.example.com"` (symbol or string write, or `h.host = ...`) and reads `host!`. They get `"api.example.com"`, same as `host`.

2. **Never assigned.** They read `secret_key_base!` on an object that never had that name. They get a `KeyError` that names `secret_key_base` and that it was never assigned—not only that it is blank.

3. **Assigned `nil`.** They set `secret_key_base = nil` (or `[:secret_key_base] = nil`) and read `secret_key_base!`. They get a `KeyError` that names the name and that it is `nil`, distinct from journey 2.

4. **Assigned `false`.** They set `allow_concurrency = false` as in [test_usage](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L20-L22) and read `allow_concurrency!`. It still fails. They can tell the name is set to `false`, not missing. (Ordinary `allow_concurrency` still returns `false`.)

5. **Whitespace-only string.** They set `api_token = "   "` and read `api_token!`. It still fails. They can tell the name holds a blank string, not that it is unset.

6. **Inherited present value.** Parent has `foo = "parent"`. Child does not write `foo`. `child.foo!` returns `"parent"`.

7. **Child override.** Parent has `foo = :bar`. Child writes `foo = :baz`. `child.foo!` returns `:baz`. Parent `foo` is still `:bar`.

8. **Inherited unusable value.** Parent has `flag = false` or `token = "   "`. Child does not write that name. `child.flag!` / `child.token!` fail and show the unusable inherited value, not a missing child name.

9. **Child nil override.** Parent has `foo = "parent"`. Child writes `foo = nil`. `child.foo!` fails as assigned `nil` on the child. Parent `foo` is still `"parent"`.

10. **Illustrative, unchanged:** `dig("test_key")` after a symbol write still returns the value; a missing ordinary reader still returns `nil`; looping still yields `[:allow_concurrency, true]` then `[:else_where, 56]` after those two writes.

## What would count as done

A developer who only uses today’s bang read can, from the failure alone, answer: which name, missing vs `nil` vs `false` vs whitespace-only, and inherited vs written on this child. A present required read still returns the same object/value as now. A script that assigns by string and reads by symbol, iterates keys, or rescues `KeyError` still behaves. Ordinary misses still return `nil`.

**Reconsider the framing if:** people still cannot tell missing from blank after the change; successful bang results change; string/symbol lookup or insertion order changes; or the real pain is “`false` should count as a required value” (that would change which reads succeed, which this brief treats as out of bounds).

**Open questions**

- Must inherited-vs-child origin appear on every inheritable failure, or only when a parent name exists?
- Is naming `false` / whitespace on a still-failing bang enough, or do you want `false` to start succeeding? The latter would break the compatibility boundary above.

This is the current shared understanding, not a locked spec. If the actor, the missing-vs-blank split, or the `false`-still-fails rule is wrong, say so and the outcomes change.
