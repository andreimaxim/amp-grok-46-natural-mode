## Assistant

`retry_on` is a `rescue_from` wrapper. On each failure it increments a per-declaration counter, then either reenqueues the same job or treats the handler as exhausted. Matching uses Active Support’s rescue table, not a separate Active Job matcher.

```diagram
perform_now
  executions += 1
  perform callbacks → perform(*)
       │
       │ exception
       ▼
rescue_with_handler ── no match ──▶ after_discard → re-raise
       │
       │ first reverse match (klass === error)
       ▼
executions_for(declaration) += 1
       │
       ├── still retryable ──▶ report? → retry_job (enqueue_retry)
       │                         wait / queue / priority
       │                         enqueue callbacks → adapter
       │                         original exception swallowed
       │
       └── exhausted
             retry_stopped
             exhaustion block? ── yes ──▶ yield job, error → after_discard
                             └── no  ──▶ after_discard → raise error
```

### How a handler is installed

[`retry_on`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L66-L94) validates `wait` at definition time (`Integer`, `Float`, `ActiveSupport::Duration`, `Proc`, or `:polynomially_longer`), then registers one `rescue_from` handler per listed class. Those entries share a single block that closes over the full `exceptions` array from that declaration:

```66:94:activejob/lib/active_job/exceptions.rb
def retry_on(*exceptions, wait: 3.seconds, attempts: 5, queue: nil, priority: nil, jitter: JITTER_DEFAULT, report: false)
  # ...
  rescue_from(*exceptions) do |error|
    executions = executions_for(exceptions)
    if attempts == :unlimited || executions < attempts
      ActiveSupport.error_reporter.report(error, source: "application.active_job") if report
      retry_job wait: determine_delay(...), queue: queue, priority: priority, error: error
    else
      # exhaustion: block and/or re-raise
    end
  end
end
```

`rescue_from` appends `[klass.name, handler]` onto the inherited `rescue_handlers` array, so later declarations sit further right ([`rescuable.rb` L53–L72](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L53-L72)).

### Exception matching: bottom-to-top, then up the class

Job execution lands here:

```46:57:activejob/lib/active_job/execution.rb

deserialize_arguments_if_needed
_perform_job
rescue Exception => exception
  handled = rescue_with_handler(exception)
  return handled if handled
  run_after_discard_procs(exception)
  raise
end
```

Lookup is in [`find_rescue_handler`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L122-L135): `rescue_handlers.reverse_each.detect` with `klass === exception` (for an `Exception` class that is `is_a?`). First hit wins; later handlers are not run.

That produces:

- **Same class, later declaration wins.** Handlers are searched right-to-left.
- **Subclass vs superclass.** A child class matches both `ChildError` and `ParentError`. The most recently declared matching handler is used. [`AfterDiscardRetryJob`](file:///home/user/workspace/repo/activejob/test/jobs/after_discard_retry_job.rb#L16-L19) declares `retry_on AfterDiscardError` then `retry_on ChildAfterDiscardError`. Raising the child uses only the child handler; [`after_discard` runs once](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L423-L429).
- **Up the job class hierarchy.** `rescue_handlers` is a `class_attribute`. A subclass copies parent handlers and appends its own, so reverse search sees the subclass first, then the parent ([rescuable tests](file:///home/user/workspace/repo/activesupport/test/rescuable_test.rb#L153-L165)).
- **Cause chain.** If nothing matches, `rescue_with_handler` walks `exception.cause` ([`rescuable.rb` L90–L103](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L90-L103)). `exceptions_test.rb` does not cover that path.

Unhandled errors skip `retry_on` entirely, run `after_discard`, and re-raise ([`execution.rb` L53–L56](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L53-L56), [test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L409-L415)).

### Counters: one declaration vs several

Two counters exist:

| Counter | When it increases | Serialized? |
|---|---|---|
| [`executions`](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L47) | Every `perform_now`, including the first | yes |
| [`exception_executions[exceptions.to_s]`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L207-L214) | Only when that `retry_on` handler runs | yes ([`core.rb` L40–L44, L125–L126](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L40-L44)) |

[`executions_for`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L207-L214) increments **before** the `attempts` check. The key is `exceptions.to_s` of the **whole** declaration list, not the class that matched.

```207:214:activejob/lib/active_job/exceptions.rb
def executions_for(exceptions)
  if exception_executions
    exception_executions[exceptions.to_s] = (exception_executions[exceptions.to_s] || 0) + 1
  else
    executions  # pre-individual-counter payloads (AJ 5.2)
  end
end
```

So:

- `retry_on FirstRetryableErrorOfTwo, SecondRetryableErrorOfTwo, attempts: 4` shares one counter. Three `First*` then a `Second*` is execution 4 of that declaration; `4 < 4` is false, so the original `SecondRetryableErrorOfTwo` is raised ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L42-L56), [job](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L35)).
- Separate `retry_on` calls keep separate keys. Four `DefaultsError` (default 5 attempts) then three `FirstRetryableErrorOfTwo` (4 attempts) still succeed ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L58-L77)).
- Delay math uses this per-declaration count, not `job.executions` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L308-L332)).
- If `exception_executions` is `nil` (old payloads), the handler falls back to the global `executions` counter ([tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L368-L390)).

`attempts` counts the original run. Default is 5: four retries then success on the fifth ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L26-L35)); a sixth raise exhausts ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L79-L84)).

### `attempts: :unlimited`

The retry branch is `attempts == :unlimited || executions < attempts` ([L77](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L77)). `:unlimited` never takes the exhaustion path. [`UnlimitedRetryError`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L45) raised nine times then succeeded on the tenth ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L360-L366)).

### Wait proc: one argument vs two

Polynomial waits for executions 1..4 are `3 + j(1)`, `18 + j(16)`, `83 + j(81)`, `258 + j(256)` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L135-L158)). - Omitted → `self.class.retry_jitter` (class default `0.0` at [L11](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L11); new apps set `0.15` from Rails 6.1 defaults in [`configuration.rb`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L191)).

- Otherwise `Kernel.rand * delay * jitter`. Zero short-circuits; negative jitter still moves the wait ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L221-L236)).

The rdoc formula `((executions**4) + (Kernel.rand * (executions**4) * jitter)) + 2` ([L31](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L31)) matches the code.     run_after_discard_procs(error)
```80:90:activejob/lib/active_job/exceptions.rb
    raise error
  end
end
```

- With a block: `retry_stopped` wraps `yield job, error`, then `after_discard`. The exception is **not** re-raised unless the block/`after_discard` raises ([`CustomCatchError` test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L101-L104), [`after_discard` with block](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L417-L421)).
- Without a block: `retry_stopped`, then `after_discard`, then `raise error` (same object). Tests rescue `DefaultsError` / `ChildAfterDiscardError` ([L79–L84](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L79-L84), [L423–L429](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L423-L429)).

On a successful retry the original exception does **not** escape: the handler returns, `rescue_with_handler` returns the exception, and `perform_now` returns it ([`execution.rb` L53–L54](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L53-L54)).

### Reenqueue: wait, queue, priority

```168:175:activejob/lib/active_job/exceptions.rb
def retry_job(options = {})
  instrument :enqueue_retry, options.slice(:error, :wait) do
    scheduled_at, queue_name, priority = self.scheduled_at, self.queue_name, self.priority
    enqueue options
  ensure
    self.scheduled_at, self.queue_name, self.priority = scheduled_at, queue_name, priority
  end
end
```

`enqueue` → [`set`](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L175-L182): `wait` becomes `scheduled_at`, `queue` goes through `queue_name_from_part`, `priority` is `.to_i`. `nil` queue/priority leave the current values. The adapter serializes the mutated job; `ensure` restores the **in-memory executing** job so the current run does not keep the override.

[`retry_on HeavyError, queue: :low`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L47) is observed as perform from `default` then `low` ([`logging_test.rb`](file:///home/user/workspace/repo/activejob/test/cases/logging_test.rb#L297-L305)). `priority:` is the same `set` path; `exceptions_test.rb` does not assert it.

### Callbacks

Perform callbacks wrap `perform` only ([`_perform_job`](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L62-L66)). The exception leaves that chain, then `rescue_from` runs. `after_perform` therefore does not see a handled retry.

Retry enqueue runs the **enqueue** callback chain (`before`/`around`/`after_enqueue`). [`RetryJob`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L54-L58) uses `before_enqueue` to log `scheduled_at`. If `before_enqueue` raises, that new error is what `perform_now` rescues; [`RetriesJob`](file:///home/user/workspace/repo/activejob/test/jobs/retries_job.rb) `retry_on BeforeEnqueueError` covers retrying the same job object ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L392-L395)).

`after_discard` runs on exhaustion (block or re-raise) and on unhandled errors, not on a successful retry ([L85–L89](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L85-L89), [L55](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L55)).
