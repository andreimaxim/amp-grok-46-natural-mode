`isolate_namespace` is class-definition setup. It does not dispatch a request. It stamps the engine class, the namespace module, and the engine’s future route set so that later boot, route load, controller inheritance, and dispatch all see an isolated engine.

```text
Engine class body
  isolate_namespace(Mod)
    engine_name ← underscore(Mod.name).tr("/", "_")
    isolated    ← true
    config.default_scope ← { module: underscore(Mod.name) }
    Mod.railtie_namespace / table_name_prefix / use_relative_model_naming?
    Mod.railtie_helpers_paths / railtie_routes_url_helpers
        (only if Mod does not already respond)

Boot
  make_routes_lazy → RouteSet (LazyRouteSet in local env)
  add_routing_paths → reloader.paths / route_sets
  ActionController on_load → mounted_helpers + RoutesHelpers.with(app.routes)

Route load (eager at init, or lazy on first use)
  RouteSet#eval_block wraps draw in scope(module: "...")
  Mapping stores controller as "ns/foo", not "foo"
  mount → named route + define_mounted_helper + script_namer
  Application finisher → main_app helper

Controller class load (autoload may be first request)
  inherited → include Mod.railtie_routes_url_helpers
            → helpers_path = Mod.railtie_helpers_paths

Request
  Engine#call → build_request sets req.routes = engine.routes
  Journey uses already-compiled controller name
  URL helpers already included; mounted helpers proxy via SCRIPT_NAME
```

## `engine_name` and `isolated?`

[`engine_name` is an alias of `railtie_name`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L354-L356). [`railtie_name`](file:///home/user/workspace/repo/railties/lib/rails/railtie.rb#L178-L181) assigns when given an argument; otherwise it memoizes `generate_railtie_name(self.name)`. Isolation always assigns:

```250:252:railties/lib/rails/railtie.rb
        def generate_railtie_name(string)
          ActiveSupport::Inflector.underscore(string).tr("/", "_")
        end
```

So `isolate_namespace Bukkits` makes `Bukkits::Engine.engine_name == "bukkits"`, not `"bukkits_engine"`. The isolated-engine test asserts that, plus `Bukkits.railtie_namespace == Bukkits::Engine` ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L952-L953)). Nested `isolate_namespace Bukkits::Awesome` yields `"bukkits_awesome"` from the same formula.

`isolated` is a class `attr_accessor`; [`isolated?` aliases it](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L354-L355). The instance delegates `engine_name` and `isolated?` to the class ([line 437](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L437)). The flag is consulted at boot by [`prepend_helpers_path`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L664-L667): an isolated engine does not push `app/helpers` onto the application unless the engine *is* the application.

There is no Railties test that assigns `engine_name` around `isolate_namespace`. From the source: `isolate_namespace` always overwrites any earlier `engine_name`. A later `engine_name "..."` would change `railtie_name` (mount’s default `:as`, rake `namespace railtie_name`), but [`table_name_prefix` already closed over `name` at isolation time](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L392-L403).

Anonymous / unnamed namespace: `isolate_namespace` passes `mod.name` into `generate_railtie_name` and `Inflector.underscore` with no nil guard. There is no engine or integration test for `Module.new`. Nested named modules are tested; anonymous ones are not.

## Table-name prefix

If `mod` does not already `respond_to?(:table_name_prefix)`, isolation defines `#{engine_name}_`. On Active Record load it redefines that method to prepend `ActiveRecord::Base.table_name_prefix`:

```397:405:railties/lib/rails/engine.rb
            unless mod.respond_to?(:table_name_prefix)
              define_method(:table_name_prefix) { "#{name}_" }

              ActiveSupport.on_load(:active_record) do
                mod.singleton_class.redefine_method(:table_name_prefix) do
                  "#{ActiveRecord::Base.table_name_prefix}#{name}_"
                end
              end
            end
```

Active Record then uses the nearest parent that `respond_to?(:table_name_prefix)` ([`full_table_name_prefix`](file:///home/user/workspace/repo/activerecord/lib/active_record/model_schema.rb#L317-L318)). Tests:

- default prefix `"bukkits_"` ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L952))
- existing `Bukkits.table_name_prefix` is left alone → `"foo"` ([lines 1351–1366](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1351-L1366))
- `config.active_record.table_name_prefix = "ar_prefix_"` → `Bukkits::Post.table_name == "ar_prefix_bukkits_posts"` ([lines 1369–1393](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1369-L1393))

Relative model naming is the other half of the same module stamp: `use_relative_model_naming?` → true, so [`ActiveModel::Naming`](file:///home/user/workspace/repo/activemodel/lib/active_model/naming.rb#L282-L286) builds names without the engine prefix. That is why `polymorphic_path(Post.new)` inside the engine is `/bukkits/posts/1` and `form_for(Bukkits::Post.new)` emits `name="post[title]"` ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L831-L1032)).

## `railtie_routes_url_helpers` and controller lookup

Isolation defines, unless already present:

```415:417:railties/lib/rails/engine.rb

              define_method(:railtie_routes_url_helpers) { |include_path_helpers = true| railtie.routes.url_helpers(include_path_helpers) }

```

and `railtie_helpers_paths` → `railtie.helpers_paths`.

Those methods are not used at dispatch. They are used when a controller or mailer class is first inherited.

[`ActionController::Railtie`](file:///home/user/workspace/repo/actionpack/lib/action_controller/railtie.rb#L80-L82) on load:

- `include app.routes.mounted_helpers` (application `main_app` plus every mounted engine)
- `extend AbstractController::Railties::RoutesHelpers.with(app.routes)`
- `extend ActionController::Railties::Helpers`

[`RoutesHelpers.with`](file:///home/user/workspace/repo/actionpack/lib/abstract_controller/railties/routes_helpers.rb#L10-L20) on `inherited`:

```text
if klass.module_parents.detect { respond_to?(:railtie_routes_url_helpers) }
  include namespace.railtie_routes_url_helpers(...)
else
  include app.routes.url_helpers(...)
end
```

[`ActionController::Railties::Helpers`](file:///home/user/workspace/repo/actionpack/lib/action_controller/railties/helpers.rb#L8-L22) does the same walk for `railtie_helpers_paths` vs the application helper path.

So `Bukkits::FooController < ActionController::Base` includes `Bukkits::Engine.routes` helpers (`foo_path`) and engine helper files (`help_the_engine`). It does not include application helpers (`something`) or application named routes (`bar_path`). It still has `main_app` because mounted helpers come from the *application* route set. The isolated-engine test hits `/bukkits/from_app` → `"false"`, `/bukkits/foo/show` → `"/bukkits/foo"`, `/bukkits/routes_helpers_in_view` → `"/bukkits/foo, /bar"`, and asserts the mailer has `foo_url` but not `bar_url` ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L831-L973)). Action Mailer uses the same `RoutesHelpers` hook with `include_path_helpers = false` ([`action_mailer/railtie.rb`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/railtie.rb#L41-L43)).

Leading-slash controllers in an isolated draw escape the module prefix ([`add_controller_module`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L329-L339)). That is how an engine action can target application controllers without changing isolation.

## Route-set creation, default `routes`, custom `endpoint`

[`Engine#routes`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L552-L567) creates `@routes` with `config.route_set_class.new_with_config(config)` on first access. [`RouteSet.new_with_config`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/route_set.rb#L372-L386) copies `config.default_scope` onto the set.

[`Engine#endpoint`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L535-L537) is `self.class.endpoint || routes`. - default endpoint is the route set: mount engine, `GET /bukkits/foo` → `"foo"` ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L753-L776))
- custom `endpoint lambda { ... }` still puts `engine.routes` in `env["action_dispatch.routes"]` via [`build_request`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L779-L784) ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L810-L829))

[`routes?`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L706-L708) is just `@routes`. The unit test constructs an engine that leaves `@routes` nil and asserts `routes?` is false ([`railties/test/engine_test.rb`](file:///home/user/workspace/repo/railties/test/engine_test.rb#L6-L14)). ## Mount helpers and `main_app`

[`Mapper#mount`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L605-L667) defaults `:as` to [`app.railtie_name`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L701-L708) for a Rails engine — i.e. `engine_name`. Isolation therefore changes the default helper from `my_engine_engine` to `my_engine`.

For a Rails app it then [`define_generate_prefix`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L710-L739):

- builds a `script_namer` from the mount’s named route
- [`app.routes.define_mounted_helper(name, script_namer)`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/route_set.rb#L520-L541) on the *engine* route set
- extends the engine route set so `find_script_name` uses that prefix

[`define_main_app_helper`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb#L60-L62) does `app.routes.define_mounted_helper(:main_app)` on the *application* set, with no script namer.

Because every controller includes `app.routes.mounted_helpers`, an isolated engine action can call `main_app.bar_path`, and an application action can call `bukkits.foo_path`. SCRIPT_NAME is composed at helper-call time, not at `isolate_namespace` time. Evidence:

- engine `main_app.bar_path` with `SCRIPT_NAME=/foo` → `/foo/bar` ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1659-L1703))
- application `bukkits.bukkit_path` under the same SCRIPT_NAME → `/foo/bukkits/bukkit`
- Blog mounted at `/:user` (default `"anonymous"`) generates `/anonymous/blog/posts` from the app and `/john/blog/posts/1` from inside the engine; Metrics (also isolated) uses `blog.post_path(1)` → `/anonymous/blog/posts/1` ([`mounted_engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/mounted_engine_test.rb#L220-L268))
- engine mounted at `"/"` keeps `script_name` empty ([`engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1609-L1657))

`main_app` is not created by `isolate_namespace`. Isolation only makes it necessary: engine named routes no longer include the application’s.

## Lazy versus eager route loading

[`make_routes_lazy`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L616-L619) (before `:bootstrap_hook`) sets `config.route_set_class = LazyRouteSet` when `Rails.env.local?` (development/test, [`EnvironmentInquirer::LOCAL_ENVIRONMENTS`](file:///home/user/workspace/repo/activesupport/lib/active_support/environment_inquirer.rb#L14-L38)) and then instantiates `routes`.

[`set_routes_reloader_hook`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb#L160-L180) loads immediately when the application set is not a `LazyRouteSet` **or** `config.eager_load` is true. Otherwise the first use loads them.

[`LazyRouteSet`](file:///home/user/workspace/repo/railties/lib/rails/engine/lazy_route_set.rb) calls `Rails.application.reload_routes_unless_loaded` from `call`, `draw`, `recognize_path`, `url_helpers` (`ProxyUrlHelpers`), named-route `method_missing` (only `_path`/`_url`), and a separate [`MountedHelpers`](file:///home/user/workspace/repo/railties/lib/rails/engine/lazy_route_set.rb#L47-L74) that lazy-defines mount helpers but leaves `_path`/`_url` to the named-route module. [`reload_routes_unless_loaded`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L168-L170) is a no-op until the application is initialized.

[`lazy_route_set_test.rb`](file:///home/user/workspace/repo/railties/test/engine/lazy_route_set_test.rb) pins the externally visible split:

- engine `root_path` is not in `methods` until invoked, then `"/plugin/"`
- `GET /plugin/` loads on the request
- engine `url_for(controller: :posts, ...)` loads
- `mounted_helpers` does not define `:plugin_engine` until use; then `helpers.plugin_engine.posts_path` and `helpers.main_app.root_path`
- after an explicit reload, both `:main_app` and `:plugin_engine` are `method_defined?`
- a plain `RouteSet.new` still uses the shared `MountedHelpers` module with no lazy `method_missing`

Eager path: production, or `eager_load`, runs `execute_unless_loaded` during finish so the same helpers exist before the first request. Isolation does not change that policy; it only supplies `default_scope` and the module hooks that the eventually-loaded set and controllers use.

## Class setup versus request dispatch

| When | What isolation already did | What still happens later |
| --- | --- | --- |
| Engine class body | `engine_name`, `isolated?`, `default_scope`, module methods | no RouteSet, no mount helper, no dispatch |
| Boot | `prepend_helpers_path` skips isolated engine helpers; `make_routes_lazy` allocates the set (possibly `LazyRouteSet`) | routes file not necessarily loaded |
| Route load | `eval_block` applies `scope(module:)`; mappings store `"ns/controller"` | mount defines helpers and script namers |
| Controller/mailer class load | `inherited` includes engine url helpers and helper paths | autoload may defer this until first request |
| Request | Journey looks up the already-compiled controller; `Engine#call` sets `req.routes` and `engine_script_name` | URL helpers / mounted helpers may trigger lazy load, then generate with SCRIPT_NAME |

`isolate_namespace` never looks at the request. The externally visible routing effects — unprefixed engine routes pointing at namespaced controllers, `foo_path` instead of `bukkits_foo_path`, `main_app` / mount proxies, polymorphic names without the engine prefix, and `bukkits_*` tables — are those later phases reading the class-level stamps.
