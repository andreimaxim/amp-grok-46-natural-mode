## Current behavior

`credentials_defaults` chooses the content and key paths **independently**:

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")
  content_path = root.join("config/credentials.yml.enc") if !content_path.exist?

  key_path = root.join("config/credentials/#{Rails.env}.key")
  key_path = root.join("config/master.key") if !key_path.exist?

  { content_path: content_path, key_path: key_path }
end
```

Source: [`railties/lib/rails/application/configuration.rb` lines 683–690](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L683-L690).

Consequently:

| Env content exists | Env key exists | Selected content | Selected file key |
|---|---|---|---|
| No | No | `config/credentials.yml.enc` | `config/master.key` |
| No | Yes | `config/credentials.yml.enc` | `config/credentials/<env>.key` |
| Yes | No | `config/credentials/<env>.yml.enc` | `config/master.key` |
| Yes | Yes | `config/credentials/<env>.yml.enc` | `config/credentials/<env>.key` |

The third row is therefore already current Rails behavior: an environment-specific encrypted file can fall back to `config/master.key`. Conversely, the second row shows that this is not implemented as atomic content/key pair selection.

The public API documentation explicitly describes that independent behavior: environment content falls back when the content file is absent, while environment key falls back when the key file is absent ([`application.rb` lines 589–606](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L589-L606)).

## Actual key lookup and `RAILS_MASTER_KEY`

`Rails.application.credentials` passes the selected paths to `encrypted` ([lines 605–606](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L605-L606)). `encrypted` defaults its environment-key name to `RAILS_MASTER_KEY` and constructs `EncryptedConfiguration` with that key and the configured file path ([lines 624–630](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L624-L630)).

1. `ENV[env_key]`
2. the selected `key_path`
3. missing-key handling

def key

end

## History and stated intent

Environment-specific credentials were introduced by [PR #33521](https://github.com/rails/rails/pull/33521), merged as [`e0d3313`](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba).

The merged implementation originally selected the two paths **as a pair based on whether environment-specific content existed**:

```ruby
def default_credentials_key_path
  if credentials_available_for_current_env?
    ... "#{Rails.env}.key"
  else
    ... "master.key"
  end
end
```

Therefore, in the original implementation, once `config/credentials/<env>.yml.enc` existed, Rails selected `config/credentials/<env>.key` even if that key file was absent. It did **not** fall back independently to `master.key`.

Relevant discussion in the PR strongly supports conceptual pairing:

- The PR description says `credentials:edit --environment staging` creates both `staging.yml.enc` and `staging.key`.
- DHH described environment credentials as “separate files and separate stores of credentials,” with the environment file decrypted by its environment key.
- Kaspth characterized “multiple environments keyed separately from master.key” as the preferable security model.
- The merge commit/changelog said an environment file “can be decrypted by `ENV["RAILS_MASTER_KEY"]` or `config/credentials/production.key`,” not `config/master.key`.

The exception was always the shared environment override: the PR settled on `RAILS_MASTER_KEY` for all environments because only the current deployment’s key needs to be present.

## Was there a PR or issue requesting `master.key` fallback?

I found no Rails issue, PR, or discussion specifically proposing or justifying this case:

> `config/credentials/<env>.yml.enc` exists, `<env>.key` is missing, therefore use `config/master.key`.

The principal historical PR, [#33521](https://github.com/rails/rails/pull/33521), points the other way: environment content and environment key were originally selected together. The current independent fallback appears in today’s implementation and documentation, but the historical discussion does not establish it as the feature’s original design intent.

## Conclusion

There are two defensible readings:

- **Current Rails contract:** the paths are independently resolved, so falling back an environment content file to `config/master.key` is supported and documented.
- **Original feature intent:** environment content and its environment key were a pair; only `RAILS_MASTER_KEY` was intended as the universal deployment override.

Accordingly, a proposed change that introduces independent `master.key` fallback is not inventing behavior relative to current Rails `main`, but it would differ from PR #33521’s original paired-path implementation and its security rationale. If preserving the original pairing is the goal, selection should be based on the content file: environment content implies environment key, with only `RAILS_MASTER_KEY` allowed to override it.

## Timeline and change

### 1. PR #33521 originally selected content and key as a pair

Environment-specific credentials landed on **September 19, 2018** in [commit `e0d3313b` (“Support environment specific credentials file. (#33521)”)](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba).

Its implementation used one predicate—the existence of the environment-specific encrypted content—for both paths:

```ruby
def credentials_available_for_current_env?
  File.exist?("#{root}/config/credentials/#{Rails.env}.yml.enc")
end

def default_credentials_content_path
  if credentials_available_for_current_env?
    File.join(root, "config", "credentials", "#{Rails.env}.yml.enc")
  else
    File.join(root, "config", "credentials.yml.enc")
  end
end

def default_credentials_key_path
  if credentials_available_for_current_env?
    File.join(root, "config", "credentials", "#{Rails.env}.key")
  else
    File.join(root, "config", "master.key")
  end
end
```

See the original [configuration implementation](https://github.com/rails/rails/blob/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba/railties/lib/rails/application/configuration.rb#L279-L298).

Thus:

| Environment content exists? | Content path | Key path |
|---|---|---|
| Yes | `config/credentials/<env>.yml.enc` | `config/credentials/<env>.key` |
| No | `config/credentials.yml.enc` | `config/master.key` |

The environment-specific key did **not** need to exist for Rails to select it. This preserved the content/key pairing and let `RAILS_MASTER_KEY` take precedence over that selected key file.

### 2. Independent fallback was introduced by a refactor

The behavior changed in [commit `ddb6ed60` (“Refactor credentials configuration defaults”)](https://github.com/rails/rails/commit/ddb6ed60), which replaced the shared content-existence predicate with independent existence checks. The current implementation is:

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")
  content_path = root.join("config/credentials.yml.enc") if !content_path.exist?

  key_path = root.join("config/credentials/#{Rails.env}.key")
  key_path = root.join("config/master.key") if !key_path.exist?

  { content_path: content_path, key_path: key_path }
end
```

See [`credentials_defaults`](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L683-L691).

That creates a formerly impossible mixed pair:

```text
config/credentials/production.yml.enc
config/master.key
```

whenever `production.yml.enc` exists but `production.key` does not.

The apparent motivation was implementation cleanup: consolidating two default methods into a hash used to initialize credentials options. I found no accompanying compatibility rationale specifically arguing that an environment credential should fall back to `master.key`. In other words, the independent-key fallback appears to be an unintended semantic change introduced during refactoring, rather than a deliberately discussed feature.

## Original design discussion

The [PR #33521 conversation](https://github.com/rails/rails/pull/33521) strongly describes environment credentials as a separate content/key store:

- DHH specified that if `config/credentials/<environment>.yml.enc` exists, it should be loaded with `config/credentials/<environment>.key` or an environment variable, and Rails should not try the global credentials store.
- He explicitly said: **“These are separate files and separate stores of credentials.”**
- Later he summarized the accepted direction as: **“Look for an environment-specific credentials first, if not found, fall back to global credentials.”**
- The merged PR description likewise says `production.yml.enc` is decrypted by `RAILS_MASTER_KEY` or `config/credentials/production.key`.

That discussion supports pairing fallback at the **store** level, not choosing content and disk-key independently.

A later report, [issue #41830](https://github.com/rails/rails/issues/41830), noted the confusing distinction that `config/master.key` was not used for environment-specific credentials, while `RAILS_MASTER_KEY` was global. The discussion did not resolve that by proposing a disk-key fallback; it focused on command environment selection and avoiding production boot.

Related [PR #34789](https://github.com/rails/rails/pull/34789) changed credentials editing so it would not boot the full application environment. That was motivated by initializers trying to consume incomplete credentials, not by key-path fallback.

## Runtime behavior: wrong key versus missing key

`Rails.application.credentials` creates an `EncryptedConfiguration` with the selected paths, and passes `config.require_master_key` through as `raise_if_missing_key`:

- [`Rails::Application#credentials`](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L589-L607)
- [`Rails::Application#encrypted`](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L624-L630)
- [`EncryptedConfiguration#initialize`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_configuration.rb#L58-L63)

`EncryptedFile#key` checks:

1. `ENV["RAILS_MASTER_KEY"]`
2. the configured `key_path`
3. missing-key handling

See [`EncryptedFile#key`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L49-L61).

### Wrong key

If a key exists but does not match the ciphertext, `read` attempts decryption and `MessageEncryptor#decrypt_and_verify` raises:

```text
ActiveSupport::MessageEncryptor::InvalidMessage
```

See [`EncryptedFile#read`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L63-L77) and [`#decrypt`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L105-L115).

Therefore, under independent fallback, an unrelated `config/master.key` turns what would previously have been a clear missing-key condition into a wrong-key/invalid-message boot failure.

### Missing key

If neither the environment variable nor configured key file exists:

- With `config.require_master_key = true`, key lookup raises `ActiveSupport::EncryptedFile::MissingKeyError`, with instructions to supply the configured key file or environment variable.
- With it `false`, key lookup returns `nil`; `read` then raises `MissingContentError` rather than attempting decryption.

The exception definitions are in [`encrypted_file.rb`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L9-L28), and read behavior is at [lines 63–77](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L63-L77).

Credentials are lazy: merely constructing `Rails.application.credentials` does not decrypt them. The failure occurs when configuration is actually read—often during boot because `secret_key_base` or an initializer accesses credentials.

## `production.rb` and `require_master_key`

Historically, generated `config/environments/production.rb` included the commented opt-in:

```ruby
# Ensures that a master key has been made available in ENV["RAILS_MASTER_KEY"], in config/master.key,
# or in an environment key such as config/credentials/production.key.
# This key is used to decrypt credentials and other encrypted files.
# config.require_master_key = true
```

It is an opt-in, not intrinsically forced merely by running in production. Configuration itself initializes `require_master_key` to `false` at [`configuration.rb`](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L78-L80).

On current `main`, that commented setting is no longer present in the generated [`production.rb.tt`](https://github.com/rails/rails/blob/main/railties/lib/rails/generators/rails/app/templates/config/environments/production.rb.tt), but the setting remains supported and is still passed directly to `EncryptedConfiguration`.

## Conclusion

The historical evidence favors treating independent disk-key fallback as a regression:

- PR #33521 intentionally selected an environment-specific content/key **pair**.
- Its discussion called each pair a separate credential store.
- Independent fallback appeared later in a refactor, without discussion justifying mixed paths.
- The semantic effect is material: a missing environment key can silently select an unrelated `master.key`, changing a useful `MissingKeyError` into `InvalidMessage` during credential read or boot.

**Request changes.** Environment ciphertext should stay paired with the environment key. Independent fallback to `config/master.key` is the wrong contract.

The claimed patch is already the current [`credentials_defaults`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L683-L690): content and key are chosen by separate `exist?` checks. That mixed pair was not the original design. [PR #33521](https://github.com/rails/rails/pull/33521) selected both paths from one predicate — “does `config/credentials/<env>.yml.enc` exist?” — so env content implied `config/credentials/<env>.key` even when that key file was missing. Independent fallback arrived later in a refactor ([`ddb6ed60`](https://github.com/rails/rails/commit/ddb6ed60)), not as a discussed feature. `RAILS_MASTER_KEY` was always the universal override; `master.key` was not.

### What actually happens

[`Rails.application.credentials`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L589-L630) decrypts `config.credentials.content_path` with `ENV["RAILS_MASTER_KEY"]` first, then `config.credentials.key_path`. [`EncryptedFile#key`](file:///home/user/workspace/repo/activesupport/lib/active_support/encrypted_file.rb#L53-L127) never tries a second disk key. `config.require_master_key` only raises `MissingKeyError` when **both** the env var and the selected `key_path` are absent.

Independent selection produces these pairs:

| Env `.yml.enc` | Env `.key` | `master.key` | Runtime paths | Decrypt result |
|---|---|---|---|---|
| no | no | yes | global content + `master.key` | OK (intended global store) |
| no | yes | yes | global content + **env key** | `InvalidMessage` if keys differ |
| yes | no | yes | env content + **`master.key`** | `InvalidMessage` unless ciphertext was encrypted with master |
| yes | yes | * | env content + env key | OK |
| yes | no | no | env content + `master.key` (missing) | `MissingKeyError` only if `require_master_key`; else empty credentials |

The two mixed rows are the defect. Wrong-key is worse than missing-key: a present `master.key` makes `key?` true, so `require_master_key` never fires, and [`EncryptedConfiguration#read`](file:///home/user/workspace/repo/activesupport/lib/active_support/encrypted_configuration.rb#L115-L121) does not swallow `InvalidMessage`. Boot then fails with “couldn't decrypt,” not “missing `config/credentials/production.key`.”

`RAILS_MASTER_KEY` already covers the legitimate deploy case (env ciphertext, no env key file). That path is tested in [`railties/test/application/credentials_test.rb`](file:///home/user/workspace/repo/railties/test/application/credentials_test.rb#L31-L38). Disk `master.key` does not need to impersonate it.

### Commands vs runtime

[`credentials:edit --environment`](file:///home/user/workspace/repo/railties/lib/rails/commands/credentials/credentials_command.rb#L22-L25) always sets **both** `config/credentials/<env>.yml.enc` and `config/credentials/<env>.key` unless `config.credentials.*` is overridden. USAGE states the same: the env file is created “with the corresponding encryption key,” and only `ENV["RAILS_MASTER_KEY"]` outranks key files.

So the standard command cannot create env ciphertext encrypted with `master.key`. Runtime fallback to `master.key` would decrypt with a key the editor never used. `credentials:show` / `credentials:edit` with no `--environment` while `RAILS_ENV=production` would then follow `credentials_defaults` and could edit production ciphertext with `master.key` — a different key than `credentials:edit --environment production`. Custom `content_path` / `key_path` are already the supported escape hatch and are tested.

Development vs production does not change the pairing rule. Production is simply where env files are common and where `secret_key_base` is read from credentials, so the mixed-key `InvalidMessage` shows up as a boot failure. `require_master_key` defaults to `false` in all environments; it is not production-specific.

### Security / compatibility

This is not a confidentiality bypass: AES-GCM rejects the wrong key. It **is** an isolation and diagnostics bug. Env stores were designed as separate key material so a leaked `master.key` does not decrypt production credentials. Teaching runtime to try `master.key` against env ciphertext:

- turns a missing env key into a wrong-key failure whenever `master.key` exists
- lets a leftover env key poison global fallback (`credentials.yml.enc` + env key)
- widens blast radius if anyone actually encrypts env files with the global key

Restoring pairing is a compatibility change relative to **current** docs ([`application.rb`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L592-L602), [configuring.md](file:///home/user/workspace/repo/guides/source/configuring.md#L325-L340)), which already describe independent fallback. Apps that intentionally omit the env key and encrypt env files with `master.key` would need `config.credentials.key_path = "config/master.key"` or `RAILS_MASTER_KEY`. That is the correct migration, not silent fallback.
