This is a **behavior-change** shaping brief. The capability already exists; the work is a clearer, adapter-honest contract for `insert_all` / `insert_all!` around `unique_by:` and `returning:`. Evidence is this revision’s public API comments, option-validation behavior, adapter capability predicates, and bulk-insert tests — not a claim that every database already agrees.

**Problem frame:** An app developer bulk-inserts rows through Active Record, often against more than one database, and needs to know which rows land, which are skipped, when the whole batch is refused, and what comes back. Today that depends on the database in ways the shared method names hide: `unique_by:` is only a real conflict target on PostgreSQL and SQLite; `returning:` is only a real result on PostgreSQL, SQLite, and MariaDB 10.5+; MySQL can skip duplicates but cannot name the uniqueness rule. The skip form and the bang form also mean different things under a uniqueness clash, and `unique_by:` on the bang form is accepted where conflict targets exist even though it does not change which clash is fatal. The pain is writing one call, shipping it, and getting a skip, a hard error, an empty result, or a silent no-op depending on the adapter.

**Behavioral outcomes** (desired, grounded in this revision unless marked as an open question):

1. Callers can skip conflicting rows with `insert_all` on every adapter that can skip duplicates, and can demand an all-or-nothing insert with `insert_all!` on every adapter.
2. Where an option is not supported, the call fails before any row is written, with an error that names the option and the adapter.
3. Where `unique_by:` is supported, it names one uniqueness rule for the skip form; without it, any unique-index clash is a skip. Other unique-index clashes still fail.
4. Where `returning:` is supported, omitted `returning:` yields the primary key of successfully inserted rows; `returning: false` and `returning: []` yield no returned columns; selected attributes and a wrapped SQL expression yield those values. Where it is not supported, omitting it is fine and yields no returned columns; passing it is an error.
5. Values still go through Active Record type casting and serialization; models are not instantiated; callbacks and validations do not run.
6. Skip vs bang atomicity stays distinct: skip inserts the non-conflicting rows; bang inserts nothing if any row violates uniqueness.

**Non-goals:** Changing `upsert_all`. Inventing `unique_by:` or `returning:` on adapters that cannot do them. Making all four databases behave as one. Prescribing SQL, adapter internals, or a rollout. Adding callbacks, validations, or model instantiation to bulk insert.

**Acceptance examples**

Shared setup unless noted: a `Book` table with a primary key `id`, a unique index on `[author_id, name]`, a partial unique index on `isbn` that applies only when `published_on` is present, and — where the adapter has expression indexes — a unique expression index on `lower(external_id)`. A `Cart` table uses a composite primary key `[shop_id, id]`. “Supported” means the adapter’s capability predicates in this revision.

### Skip vs bang under the default conflict target

**PostgreSQL and SQLite**

- Given an existing book `id: 1`, when the caller `insert_all`s `{ id: 1, name: "Agile Web Development with Rails" }` with no `unique_by:`, the existing row is unchanged and count does not increase.
- Given two new hashes that share `author_id` and `name` but no `id`, when the caller `insert_all`s them with no `unique_by:`, exactly one row is inserted.
- Given a batch that includes a uniqueness clash, when the caller `insert_all!`s it, the caller observes `ActiveRecord::RecordNotUnique` and no row from that batch is inserted.

**MySQL and MariaDB** (skip duplicates supported; no conflict target)

- Same skip examples as above: an existing primary-key clash is skipped; two same-batch `[author_id, name]` clashes insert one row; existing non-key attributes are not overwritten (skip is not an update).
- `insert_all!` still raises `RecordNotUnique` on a uniqueness clash and inserts no rows.
- Passing `unique_by:` on either form raises `ArgumentError` that the adapter does not support `:unique_by`. No row is written.

### Named, composite, and expression `unique_by:` (PostgreSQL and SQLite only)

- When the caller `insert_all`s a new book with `unique_by: :isbn`, `unique_by: %i[author_id name]`, `unique_by: :index_books_on_isbn`, or `unique_by: :id`, a new row is inserted.
- Column order does not matter: `unique_by: [:name, :author_id]` matches the `[author_id, name]` unique index.
- Given an existing primary-key row, when the caller `insert_all`s that same `id` with `unique_by:` pointing at `[author_id, name]` (a different uniqueness rule), the caller observes `RecordNotUnique` rather than a skip.
- Where expression indexes exist, given a book with `external_id: "abc"`, when the caller `insert_all`s `{ external_id: "ABC" }` with `unique_by:` set to that expression index, count does not increase.

**MySQL and MariaDB:** any of those `unique_by:` values is an `ArgumentError`; the expression-index example is not available as a conflict target.

### Invalid or non-unique `unique_by:`

**PostgreSQL and SQLite:** `unique_by: :cats`, `unique_by: %i[author_id isbn]` (no such unique index), or `unique_by: :author_id` (not unique) raises `ArgumentError` matching “No unique index found”. No row is written.

**MySQL and MariaDB:** the same calls raise “does not support `:unique_by`”, not a missing-index error.

### Composite primary keys

**PostgreSQL and SQLite**

- `Cart.insert_all([{ id: 1, shop_id: 1, title: "My cart" }], unique_by: [:shop_id, :id])` inserts the row.
- `Cart.insert_all([{ id: 2, shop_id: 1, title: "My cart" }])` with no `unique_by:` raises `ArgumentError` matching “No unique index found for id”.
- `Cart.insert_all!([{ id: 2, shop_id: 1, title: "My cart" }])` with no `unique_by:` inserts the row. The bang form does not require a named unique index.

**MySQL and MariaDB:** `Cart.insert_all` and `Cart.insert_all!` without `unique_by:` both insert. There is no “name the composite key” option.

### `returning:`

**PostgreSQL, SQLite, and MariaDB ≥ 10.5**

- `insert_all!` of one book with `returning:` omitted returns an `ActiveRecord::Result` whose columns are the primary key (`id` for `Book`).
- `returning: false` and `returning: []` return a result with no columns. The row is still inserted.
- `returning: [:id, :name]` returns those attributes for successfully inserted rows.
- `returning: Arel.sql("UPPER(name) as name")` returns the computed value (`REWORK` for name `"Rework"`).
- A raw SQL string that is not wrapped as known-safe SQL is refused with `ArgumentError` before insert.

**MySQL (and MariaDB < 10.5):** omitting `returning:` inserts and returns a result with no returned columns. Passing `returning:` (including `false`, columns, or an expression) raises `ArgumentError` that the adapter does not support `:returning`.

### Empty input, mismatched keys, unknown attributes

All four adapters:

- `insert_all([])` and `insert_all!([])` return an empty result and write no rows.
- Two hashes with different keys raise `ArgumentError` that all objects must have the same keys, naming the extra or missing key (for example extra `"isbn"`). No row is written.
- An unknown attribute raises `ActiveRecord::UnknownAttributeError`.

### Type casting / serialization

Where `returning:` is supported: inserting a value that `create!` would cast/serialize (for example a non-string `name`) stores the same persisted value as `create!`. Where `returning:` is not supported, the stored value still matches `create!`; only the returned result shape differs.

### Timestamp override

On all adapters that can insert:

- If the model records timestamps, omitted timestamp attributes are filled in on insert.
- `record_timestamps: false` leaves omitted timestamps unset.
- `record_timestamps: true` fills them even if the model would not.
- An explicit timestamp in the hash is kept and not overwritten.

### Atomicity: skip vs bang

All adapters that can skip duplicates:

- Skip: a batch of one new row and one conflicting row inserts the new row, leaves the existing row’s other attributes unchanged, and does not raise.
- Bang: the same batch raises `RecordNotUnique` and inserts neither row.
- Skip with two hashes that share the same identifier in one batch keeps the first hash’s values, not the second.

On PostgreSQL/SQLite, skip plus `unique_by:` still raises — and inserts nothing for the clashing row — when the clash is on a uniqueness rule other than the one named.

### Bang form and `unique_by:` (current, easy to misread)

**PostgreSQL and SQLite:** `insert_all!(..., unique_by: :isbn)` of a non-conflicting row succeeds. A row that clashes on `isbn` still raises `RecordNotUnique`. `unique_by:` does not narrow which uniqueness rule is fatal; any unique-index clash still fails the whole batch.

**MySQL and MariaDB:** `insert_all!(..., unique_by: :isbn)` is refused as unsupported, even though the bang form would not use a conflict target.

**Steering evidence**

- Treat the outcome as failing if a skip call updates existing attributes, if a bang clash leaves some rows inserted, if MySQL/MariaDB accept `unique_by:`, if MySQL accepts `returning:`, or if PostgreSQL/SQLite silently ignore an invalid `unique_by:`.
- Reconsider the framing if the real pain is “make MySQL name a conflict target” or “make bang `unique_by:` actually select one index.” Those are different products than an honest cross-adapter contract.
- Continue if callers can predict, per adapter, skip vs raise, returned columns, and which uniqueness rule applies, without reading SQL.

**Open questions**

- Should bang `unique_by:` stay accepted on PostgreSQL/SQLite for API symmetry, or be rejected as meaningless because it does not change which clash is fatal?
- Should skip without `unique_by:` on a composite-primary-key model use the full composite key automatically on PostgreSQL/SQLite, matching MySQL’s “just insert” path?
- Is first-in-batch kept on same-identifier skip the intended rule, or should that stay an accident of this revision?
- For MariaDB 10.5+, is returning primary keys by default the intended MariaDB behavior, or should MariaDB match MySQL’s empty result unless `returning:` is explicit?
- Should a wrapped SQL `returning:` expression remain part of the supported contract, or only attribute lists?

This draft treats this revision’s adapter-specific behavior as the baseline to *clarify*, not a mandate to unify databases. Correct the problem frame, any example that should not be required, or any open question that is actually already decided.
