**Block.** The claim is wrong for this revision, and the diff is not a bang counterpart to `#attach`. It changes when the record is persisted, what exception is raised, what is returned, and how many times callbacks run.

`#attach!` is documented to call `#attach` and raise only if the record was **meant to be saved** and that save failed ([many.rb](file:///home/user/workspace/repo/activestorage/lib/active_storage/attached/many.rb#L51-L67)). `#attach` saves immediately only when `record.persisted? && !record.changed?`; otherwise it stages pending attachments. `changed?` is attribute dirty state, not attachment changes: assigning highlights leaves `changed? == false` and `changed_for_autosave? == true` ([dirty.rb](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L286-L288), [model.rb](file:///home/user/workspace/repo/activestorage/lib/active_storage/attached/model.rb#L313-L314)). I confirmed that with a runtime probe.

```51:67:activestorage/lib/active_storage/attached/many.rb
    def attach(*attachables)
      record.public_send("#{name}=", blobs + attachables.flatten)
      if record.persisted? && !record.changed?
        return if !record.save
      end
      record.public_send("#{name}")
    end

    def attach!(*attachables)
      attach(*attachables) || raise(ActiveRecord::RecordNotSaved.new("Failed to save the record", record))
    end
```

`Attached::One` is the same contract ([one.rb](file:///home/user/workspace/repo/activestorage/lib/active_storage/attached/one.rb#L64-L80)). Changing only Many would split the API.

## What the current code actually does

`#attach` returns `nil` only when it attempted `record.save` and that save returned false. Otherwise it returns the `Attached::Many` proxy, which is always truthy. So current `#attach!` raises only on that failed immediate save.

Existing tests already cover the validation-failure path the PR claims is broken:

- persisted, unchanged, invalid `#attach` returns `nil` ([many_test.rb](file:///home/user/workspace/repo/activestorage/test/models/attached/many_test.rb#L811-L818))
- persisted, unchanged, invalid `#attach!` raises `ActiveRecord::RecordNotSaved` ([many_test.rb](file:///home/user/workspace/repo/activestorage/test/models/attached/many_test.rb#L820-L827), same for One at [one_test.rb](file:///home/user/workspace/repo/activestorage/test/models/attached/one_test.rb#L148-L155))

I ran those tests: 6 runs, 9 assertions, 0 failures. A probe on this checkout printed:

- invalid `#attach!` → `ActiveRecord::RecordNotSaved` / `"Failed to save the record"`
- `record.save!` on the same record → `ActiveRecord::RecordInvalid` / `"Validation failed: Name can't be blank"`

Validation failures on the immediate-save path already raise. They do not raise `RecordInvalid`, and they should not start calling `save!` unconditionally.

## Concrete regressions from `attach; record.save!`

**New records.** Current `#attach!` does not persist. Probe: `User.new(...).highlights.attach!(blob)` → `persisted? == false`, pending `attachment_changes`. Proposed `save!` would insert the user (or raise if invalid). That contradicts `#attach` and the changed/new-record tests at [many_test.rb](file:///home/user/workspace/repo/activestorage/test/models/attached/many_test.rb#L836-L841).

**Changed records.** `@user.name = "Tina"; @user.highlights.attach!(blob)` currently leaves attachments unpersisted and keeps the name change pending (probe: `persisted attachments? == false`, `will_save_change_to_name? == true`). Proposed `save!` would persist the name **and** the files together. `#attach` defers exactly to avoid writing unrelated dirty attributes.

**Successful immediate save.** For a persisted, unchanged, valid record, `#attach` already calls `record.save` (after_save writes attachments, after_commit uploads, [model.rb](file:///home/user/workspace/repo/activestorage/lib/active_storage/attached/model.rb#L243-L273)). Then `save!` runs a second time: extra `after_save` / `after_commit`, extra `updated_at` bump. Probe: current `#attach!` extra `after_save` count `1`; `attach` then `save!` count `2`.

**Return value.** Current success returns the `Attached::Many` proxy (same as `#attach`, [many_test.rb](file:///home/user/workspace/repo/activestorage/test/models/attached/many_test.rb#L805-L809)). `save!` returns `true` ([persistence.rb](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L391-L393)). Callers using the return value as the attachment proxy break.

**Exception class/message.** Failed validations on `save!` raise `RecordInvalid` via `raise_validation_error` ([validations.rb](file:///home/user/workspace/repo/activerecord/lib/active_record/validations.rb#L53-L55), [validations.rb](file:///home/user/workspace/repo/activerecord/lib/active_record/validations.rb#L86-L88)). Current `#attach!` raises `RecordNotSaved` with `"Failed to save the record"`. The existing Many/One tests would fail. `RecordNotSaved` is the callback-abort path, not the validation path ([errors.rb](file:///home/user/workspace/repo/activerecord/lib/active_record/errors.rb#L166-L174)).

**Empty / nested arrays / duplicates.** These are handled by `#attach` (`flatten`, `blobs + attachables`, `compact_blank` / `CreateMany`). Nested arrays already work (probe: 2 files). Duplicate existing blob does not create a second row (probe: count stayed 1). The proposed extra `save!` does not fix those cases; on the success path it only double-saves.

**Pending changes.** A second `save!` after a successful `#attach` runs with `attachment_changes` already cleared by `after_commit`. It does not “make save more consistent”; it persists the whole record again.

## Missing tests (current and proposed)

`#attach!` is only tested for persisted + unchanged + invalid, and only `assert_raises(RecordNotSaved)` with no message or `#record` check. There are no tests that `#attach!`:

- does not persist new records
- does not persist dirty records
- returns the proxy on success, not `true`
- does not double-save / double-callback
- stays aligned with `Attached::One`

Those gaps are why this diff looks plausible and is still wrong.

## Smallest corrected direction

Keep the save-or-defer rule. Do **not** always call `record.save!`.

If the only desired change is “raise like `save!` on the immediate-save path”:

- assign as `#attach` does
- call `record.save!` **only** when `record.persisted? && !record.changed?`
- return `record.public_send("#{name}")`
- update Many **and** One together
- change the invalid-record tests to `RecordInvalid` (and add a `RecordNotSaved` case only if callback abort matters)
- add tests for new records, dirty records, success return value, and no double save

If the goal is just “validation failures raise on the path that already saves,” current `#attach!` already does that. No code change.
