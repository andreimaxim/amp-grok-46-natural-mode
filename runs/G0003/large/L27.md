**Reject.** The rewrite after a successful signed-cookie rotation is the upgrade path, not an extra write. Hard-coding `force_reserialize: false` leaves cookies on retired secrets/digests. Current-key cookies already skip that rewrite.

I ran the signed-cookie and verifier suites at this revision (15 cookie tests, 30 verifier tests; all passed). The proposed line is not in the tree; this is a review of that diff against current code.

## Findings

### 1. High — rotation rewrite is required; the patch breaks the signed-jar upgrade contract

[`SignedKeyRotatingCookieJar#parse`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L643-L646) verifies with `on_rotation`, then asks [`SerializedCookieJars#parse`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L600-L608) to reassign when `rotated` is true:

```643:646:actionpack/lib/action_dispatch/middleware/cookies.rb
        def parse(name, signed_message, purpose: nil)
          rotated = false
          data = @verifier.verified(signed_message, purpose: purpose, on_rotation: -> { rotated = true })
          super(name, data, force_reserialize: rotated)
```

That assignment is `self[name] = { value: value }`, which goes through signed [`commit`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L648-L651) and re-signs with the **current** secret and digest. Middleware then emits `Set-Cookie`.

That is the observed contract today:

- [`test_signed_cookie_rotating_secret_and_digest`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L641-L657) plants a SHA1 message from an old raw secret, reads it, and asserts `@response.cookies["user_id"]` verifies with the **new** derived key and SHA256.
- [`test_rotating_signed_cookies_digest`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L1000-L1013) does the same for digest-only rotation.

With `force_reserialize: false`, those reads still return `45`, but there is no `Set-Cookie`. The next request still carries the old signature. Removing the rotation later invalidates every such cookie.

`on_rotation` only runs after the primary verifier fails and a fallback succeeds ([`Messages::Rotator#read_message`](file:///home/user/workspace/repo/activesupport/lib/active_support/messages/rotator.rb#L29-L47); [`on_rotation is called on successful rotation`](file:///home/user/workspace/repo/activesupport/test/messages/message_rotator_tests.rb#L42-L45)). It does **not** fire for a current signature ([`on_rotation is not called when no rotation is necessary`](file:///home/user/workspace/repo/activesupport/test/messages/message_rotator_tests.rb#L59-L62)). So “unnecessary rewrite after key rotation” is already false for cookies that are already on the new key.

Default marshal cookies never take the other rewrite path: [`reserialize?`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L594-L597) is false for `:marshal`. After this patch, old-secret + marshal cookies never upgrade.

### 2. High — “safely” is wrong for retiring a key; signed vs encrypted would diverge

The verifier is built from the current key, then old secrets/digests are stacked with [`rotate`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L633-L639). Rails treats those fallbacks as temporary. The rewrite is how a cookie leaves the fallback.

[`EncryptedKeyRotatingCookieJar#parse`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L694-L696) still passes `force_reserialize: rotated`. Encrypted cookies would keep upgrading; signed cookies would not. [`test_encrypted_cookie_rotating_secret`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L1113-L1134) would still pass. That split is not a safe rotation story.

### 3. Medium — serializer upgrades are a different switch; this patch does not isolate them

Payload format is **not** the MessageVerifier serializer (`NullSerializer`). It is [`SerializedCookieJars`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L568-L614). Format migration is `reserialize?(dumped)`, independent of `rotated`.

Still true after the patch:

- hybrid Marshal → JSON still rewrites ([`test_signed_cookie_using_hybrid_serializer_can_migrate_marshal_dumped_value_to_json`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L731-L745))
- JSON already on hybrid does not ([`test_signed_cookie_using_hybrid_serializer_can_read_from_json_dumped_value`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L748-L762), `assert_nil @response.cookies["user_id"]`)
- marshal reading JSON does not rewrite ([`test_signed_cookie_using_marshal_serializer_can_read_from_json_dumped_value`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L715-L728))
- message_pack still migrates JSON ([`test_signed_cookie_using_message_pack_serializer_can_migrate_json_dumped_value_to_message_pack`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L780-L793))

So the patch does not “stop extra serialization.” It only disables **key/digest** upgrade, and only on the signed jar.

### 4. Low — expiry and tamper already skip writes; this line is not what protects them

Expired metadata throws `:invalid_message_content` before `on_rotation` ([`extract_from_metadata_envelope`](file:///home/user/workspace/repo/activesupport/lib/active_support/messages/metadata.rb#L80-L85)). `verified` swallows that and returns nil ([`MessageVerifier#verified`](file:///home/user/workspace/repo/activesupport/lib/active_support/message_verifier.rb#L225-L233)). `SerializedCookieJars#parse` then no-ops on nil.

Ran and passing:

- [`test_signed_cookie_with_expires_set_relatively`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L1466-L1476) — readable at +1h, `nil` at +3h
- [`test_tampered_with_signed_cookie`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L658-L667) — `nil` on a swapped payload
- [`test_legacy_signed_cookie_is_treated_as_nil_by_signed_cookie_jar_if_tampered`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L970-L975) — unsigned `user_id=45` stays `nil`, no `Set-Cookie`
- [`test_tampered_cookies`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L954-L958) — bad signature does not raise
- verifier metadata tests: expired `:expires_at` / `:expires_in` decode to nil

A current SHA1/SHA256 signature already does not rewrite ([`test_signed_cookie_using_default_digest`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L615-L625), [`test_signed_cookie_using_custom_digest`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L627-L639)).

## What the current path actually does

```text
cookies.signed[:name]
  AbstractCookieJar#[]
    parse(purpose: "cookie.name")     # retry without purpose if nil
      MessageVerifier#verified(..., on_rotation)
        primary secret+digest         # current cookie: rotated=false
        else fallback rotate(...)     # old secret/digest: on_rotation, rotated=true
      SerializedCookieJars#parse
        nil / tamper / expiry → return
        force_reserialize || reserialize? → self[name] = { value: }
          dump with payload serializer
          verifier.generate with current key + purpose/expiry metadata
          CookieJar#[]= → @set_cookies
  Cookies#call → cookie_jar.write(response)
```

## Tests this change would need (and why they should fail)

Do not land this without replacing the rotation contract. If someone still wants “never rewrite on rotation,” these are the cases that must be explicit — they currently contradict the patch:

1. **Old secret** — keep [`test_signed_cookie_rotating_secret_and_digest`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L641-L657). Today it requires `@response.cookies["user_id"]` to verify with the new SHA256 key. Under the patch this assertion must fail unless the test is weakened to “read succeeds, no `Set-Cookie`,” which is a behavior change, not a cleanup.
2. **Old digest, same key** — same for [`test_rotating_signed_cookies_digest`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L1000-L1013).
3. **Current signature** — read a cookie already signed with the active secret/digest while rotations are configured; assert **no** `Set-Cookie`. This is already how `on_rotation` works; it does not need `force_reserialize: false`.
4. **Expired metadata** — old-secret cookie with `expires_in` in the past; assert `nil` and no `Set-Cookie` (rotator does not call `on_rotation` on `:invalid_message_content`).
5. **Tamper** — keep the existing tamper tests; they must still return `nil` and not write.
6. **Serializer-only** — hybrid/message_pack migration tests must still rewrite; marshal-reading-JSON must not. Those paths must not be confused with key rotation.
7. **Retire the fallback** — after one successful read of an old-secret cookie, drop `cookies_rotations` and read again. Current code still works because of the rewrite. The patch would start returning `nil`. That is the safety test the claim needs and does not have.

[`test_cookie_with_hash_value_not_modified_by_rotation`](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L1137-L1146) only checks the loaded Hash. It would still pass under the patch and is not coverage for upgrade.

If the real pain is rewrite side effects (`self[name] = { value: value }` drops `expires` / `httponly` / `domain` on the HTTP cookie), fix option preservation on upgrade. Do not disable `force_reserialize: rotated`.
