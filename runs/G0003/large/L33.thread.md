Useful ActiveModel::Dirty context:

- Dirty maintains two timelines: **unsaved/current mutations** and **mutations from the most recent save** (`previous_changes` / `saved_change_to_*?`).
- `changes_applied` is the post-persistence transition: it accepts the current changes as applied, clears the current dirty state, and preserves them as the last-save changes. In a plain ActiveModel object, call it after the backing save succeeds; Active Record normally does this as part of persistence.
- `restore_attributes` reverts specified (or, by default, all) **currently dirty attributes** to their original tracked values and removes those pending changes. It is an in-memory rollback of unsaved changes, not a database reload or rollback.
- `clear_changes_information` only discards Dirty bookkeeping—both current changes and last-save/previous-change information. It **does not restore attribute values**.

So an explanation should emphasize that these are not interchangeable: `changes_applied` commits the Dirty lifecycle after a successful save; `restore_attributes` restores values; `clear_changes_information` merely forgets tracking history.

## Assistant

Dirty keeps two timelines. Current unsaved work lives in `@mutations_from_database`. The last accepted save lives in `@mutations_before_last_save`. [`changes_applied`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L272-L278) promotes the first into the second. [`restore_attributes`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L320-L322) writes old values back and drops those current changes. [`clear_changes_information`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L325-L329) drops both timelines and leaves attribute values alone.

### Two trackers, one public API

[`mutations_from_database`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L387-L393) picks the tracker from whether the object has `@attributes`:

```text
mutations_from_database
  @attributes defined?  → AttributeMutationTracker(@attributes)
  else                  → ForcedMutationTracker(self)
mutations_before_last_save
  @mutations_before_last_save || NullMutationTracker
```

Plain Dirty (the `DirtyModel` in [`dirty_test.rb`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L7-L43)) uses `ForcedMutationTracker`. `ActiveModel::Attributes` uses `AttributeMutationTracker`. Generated methods are only dispatch:

| Method | Reads |
|---|---|
| `changed?` / `changes` / `*_changed?` / `*_change` / `*_was` | current tracker |
| `previous_changes` / `*_previously_changed?` / `*_previous_change` / `*_previously_was` | last-save tracker |
| `*_will_change!` | `force_change` on the current tracker |

Until something is saved, the last-save tracker is [`NullMutationTracker`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute_mutation_tracker.rb#L168-L188): `changed?` is false, `changes` is `{}`, `original_value` is `nil`. That is why `*_previously_was` is `nil` on a fresh object even when `*_was` already returns the live value.

### What the three methods actually do

[`changes_applied`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L272-L278) is the post-persist step. It returns `nil`.

```text
changes_applied
  if no @attributes
    mutations_from_database.finalize_changes   # snapshot [from, to]
  @mutations_before_last_save = mutations_from_database
  forget_attribute_assignments                 # only if @attributes
  @mutations_from_database = nil
```

`ForcedMutationTracker#finalize_changes` freezes the `[from, to]` pairs before later edits can change live readers ([`attribute_mutation_tracker.rb`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute_mutation_tracker.rb#L146-L148)). `AttributeMutationTracker` skips that because it already holds the pre-forget `AttributeSet`. [`forget_attribute_assignments`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L395-L397) rebuilds `@attributes` via `forgetting_assignment`, which drops “assigned from original” so the next tracker starts clean. Active Record calls this after create/update ([`activerecord/.../dirty.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/attribute_methods/dirty.rb#L231-L241)).

[`restore_attributes`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L320-L322) defaults to `changed` (currently dirty names) and returns that array. Each name goes through [`restore_attribute!`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L414-L420):

```text
restore_attribute!(name)
  return unless attribute_changed?(name)
  public_send("#{name}=", attribute_was(name))
  clear_attribute_change(name)
```

Unchanged names are skipped. The setter may call `*_will_change!` again; `ForcedMutationTracker#force_change` does not overwrite an original that is already recorded ([`force_change`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute_mutation_tracker.rb#L141-L143)). Then `forget_change` removes the name from current dirty state. `previous_changes` is not touched.

[`clear_changes_information`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L325-L329) returns `nil`. It sets both tracker ivars to `nil` (last-save then becomes `NullMutationTracker` on next read) and forgets assignments. Attribute values stay where they are. That is the `reload!` helper in the module docs, not rollback.

### Walkthrough: in-place, apply, second edit, restore

This is the `ForcedMutationTracker` path: no `@attributes`, so in-place mutation is invisible unless `*_will_change!` runs first. That is the contract in the module docs ([`dirty.rb`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L110-L122)) and the test at [`dirty_test.rb:94-101`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L94-L101).

Start with `name = +"Yam"`, `color = "Red"`.

**1. In-place replace without `name_will_change!`**

`name.replace("Hadad")` mutates the string. Dirty does not see it.

- `changed?` → `false`; `changed` → `[]`; `changes` → `{}`
- `previous_changes` → `{}`
- `name` → `"Hadad"`; `name_changed?` → `false`; `name_change` → `nil`; `name_was` → `"Hadad"` (live value; the tracker has no original)
- `name_previously_changed?` → `false`; `name_previously_was` → `nil`

**2. `name_will_change!`, then in-place append**

[`attribute_will_change!`](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L409-L411) clones the current value into `forced_changes` ([`clone_value`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute_mutation_tracker.rb#L158-L164)). Right after `name_will_change!`, before further mutation:

- `changed?` → `true`; `changes` → `{ "name" => ["Hadad", "Hadad"] }`
- `name_was` → `"Hadad"`

Then `name << "!!"`:

- `name` → `"Hadad!!"`
- `name_change` / `changes["name"]` → `["Hadad", "Hadad!!"]`
- `name_was` still `"Hadad"` (the clone, not the mutated string)
- `previous_changes` still `{}`

The clone is why `*_will_change!` must run *before* mutation. After `replace`/`<<`, cloning would snapshot the already-mutated value.

With `ActiveModel::Attributes`, the same `name.replace("Hadad")` *is* dirty without `*_will_change!` ([`attributes_dirty_test.rb:89-96`](file:///home/user/workspace/repo/activemodel/test/cases/attributes_dirty_test.rb#L89-L96)). `Attribute#changed_in_place?` compares `original_value_for_database` to the live value ([`attribute.rb:66-71`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute.rb#L66-L71)). `changes` becomes `{ "name" => ["Yam", "Hadad"] }`.

**3. `changes_applied` (via `save`)**

Returns `nil`. Current tracker is stored as last-save; a new empty current tracker is created lazily.

- `changed?` → `false`; `changes` → `{}`
- `previous_changes` → `{ "name" => ["Hadad", "Hadad!!"] }`
- `name` still `"Hadad!!"` (values are not rewritten)
- `name_changed?` → `false`; `name_change` → `nil`; `name_was` → `"Hadad!!"`
- `name_previously_changed?` → `true`; `name_previous_change` → `["Hadad", "Hadad!!"]`; `name_previously_was` → `"Hadad"`
- `color_previously_changed?` → `false`; `color_previous_change` → `nil`

Covered by [`dirty_test.rb:123-137`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L123-L137) and [`:151-155`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L151-L155).

**4. Second edit:** `name = "Bob"`, `color = "White"`

- `changed?` → `true`; `changed` → `["color", "name"]` (forced-tracker key order)
- `changes` → `{ "color" => ["Red", "White"], "name" => ["Hadad!!", "Bob"] }`
- `previous_changes` still `{ "name" => ["Hadad", "Hadad!!"] }` — new edits do not rewrite last-save ([`dirty_test.rb:140-147`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L140-L147))
- `name_was` → `"Hadad!!"`; `color_was` → `"Red"`
- `name_previously_was` → `"Hadad"`; `name_previous_change` unchanged

Repeated assigns keep the first original: `name = "A"; name = "B"` yields `name_change == [original, "B"]` ([`dirty_test.rb:175-187`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L175-L187)). `force_change` refuses to replace an existing original.

**5. `restore_attributes(["name"])` — color omitted**

Returns `["name"]`. Only `name` is reassigned to `name_was` and forgotten.

- `name` → `"Hadad!!"`; `name_changed?` → `false`; `name_change` → `nil`; `name_was` → `"Hadad!!"`
- `color` still `"White"`; `color_changed?` → `true`; `color_change` → `["Red", "White"]`
- `changed?` → `true`; `changes` → `{ "color" => ["Red", "White"] }`
- `previous_changes` still `{ "name" => ["Hadad", "Hadad!!"] }`

This is [`dirty_test.rb:225-236`](file:///home/user/workspace/repo/activemodel/test/cases/dirty_test.rb#L225-L236). An omitted dirty attribute stays dirty. Passing an already-clean name is a no-op inside `restore_attribute!`.

**6. `restore_attributes` with no args**

Restores remaining dirty names (`["color"]`). Returns that list.

- `changed?` → `false`; `changes` → `{}`

### Return values and `*_was` quirks worth treating as part of the contract

| Call | Return |
|---|---|
| `changes_applied` | `nil` |
| `restore_attributes(names)` | `names` (default: current `changed`) |
| `clear_changes_information` | `nil` |
| `*_change` / `*_previous_change` when not dirty | `nil` |
| `changes` / `previous_changes` when empty | `{}` (`HashWithIndifferentAccess` once a real tracker has served `changes`; `NullMutationTracker#changes` is a plain `{}`) |

`*_was` on an unchanged attribute is the live value (`ForcedMutationTracker#original_value` falls through to `_read_attribute`; [`attribute_mutation_tracker.rb:133-139`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute_mutation_tracker.rb#L133-L139)). `*_previously_was` on `NullMutationTracker` is always `nil`.

On `ForcedMutationTracker`, last-save `original_value` for an attribute that was *not* in that save also reads the live object. After a later `color = "White"`, `color_previously_was` can become `"White"` even though `color` was never in `previous_changes`. `AttributeMutationTracker` does not do that: it keeps the old `AttributeSet`, so `color_previously_was` stays `"Red"` while `color` is `"White"`.

The three methods are not interchangeable: `changes_applied` commits the dirty lifecycle after a successful save; `restore_attributes` restores values for selected current changes; `clear_changes_information` only forgets tracking.
