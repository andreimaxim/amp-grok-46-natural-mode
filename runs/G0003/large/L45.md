**Request changes.** The claim is right that session stores need `ActionDispatch::Cookies`, but this one-line condition does not implement that, and it would put Cookies on every default API-only app.

The proposed swap in [`default_middleware_stack.rb`](file:///home/user/workspace/repo/railties/lib/rails/application/default_middleware_stack.rb):

```ruby
middleware.use ::ActionDispatch::Cookies if !config.api_only || config.session_store
```

Session insertion is unchanged:

```ruby
if !config.api_only && config.session_store
  middleware.use config.session_store, config.session_options
end
```

## Assembly rules (current source)

Default stack inserts Cookies, then the configured store, then Flash, in that order, and only for full-stack apps:

```76:89:railties/lib/rails/application/default_middleware_stack.rb
middleware.use ::ActionDispatch::Cookies unless config.api_only

if !config.api_only && config.session_store
  if config.force_ssl && config.ssl_options.fetch(:secure_cookies, true) && !config.session_options.key?(:secure)
    config.session_options[:secure] = true
  end
  middleware.use config.session_store, config.session_options
end

unless config.api_only
  middleware.use ::ActionDispatch::Flash
  ...
end
```

That order is required. [`middleware_test.rb`](file:///home/user/workspace/repo/railties/test/commands/middleware_test.rb) encodes it as Flash → Session → Cookies (later list entry is inner):

```128:139:railties/test/commands/middleware_test.rb
%w(ActionDispatch::Flash ActionDispatch::Session::CookieStore),
%w(ActionDispatch::Session::CookieStore ActionDispatch::Cookies),
```

Every session store writes the session id through `request.cookie_jar` ([`AbstractStore#set_cookie`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/session/abstract_store.rb), [`CookieStore`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/session/cookie_store.rb)). Cookies is the component that actually emits `Set-Cookie` ([`Cookies#call`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb)). The API guide is explicit: Cookies is required for all session management, not just CookieStore.

User `config.middleware.use` is appended after the default stack ([`MiddlewareStackProxy#use`](file:///home/user/workspace/repo/railties/lib/rails/configuration.rb) → [`MiddlewareStack#use`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/stack.rb)), so opt-in Cookies/Session land after Head/ETag and after DatabaseSelector, not in the default Cookies → Session → Flash slot.

## Why `config.session_store` is the wrong predicate

[`setup_default_session_store`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb) runs **before** `build_middleware_stack` and installs CookieStore unless the user already set a store:

```49:53:railties/lib/rails/application/finisher.rb
initializer :setup_default_session_store, before: :build_middleware_stack do |app|
  unless app.config.session_store?
    app.config.session_store :cookie_store, key: "_#{app_name}_session"
  end
end
```

There is no `api_only` guard. The getter used in the proposed `if` returns the class, not the raw `@session_store`; `:disabled` becomes `nil` ([`session_store`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb)). So at stack build:

| App | `config.session_store` | Proposed Cookies? | Session middleware? |
|---|---|---|---|
| Full-stack default | CookieStore | yes (already) | yes |
| Full-stack `:disabled` | `nil` | yes (`!api_only`) | no |
| API-only default | CookieStore (implicit) | **yes (new)** | **no** |
| API-only + explicit `:cookie_store` | CookieStore | yes | **no** |
| API-only + `:disabled` | `nil` | no | no |

The PR would add Cookies to a stock API app that never asked for sessions. It would still not insert the session store.

That contradicts the generator ([`application.rb.tt`](file:///home/user/workspace/repo/railties/lib/rails/generators/rails/app/templates/config/application.rb.tt): “session, flash, cookies can be added back manually”), the API guide ([`api_app.md`](file:///home/user/workspace/repo/guides/source/api_app.md) “Using Session Middlewares”), and [`test "api middleware stack"`](file:///home/user/workspace/repo/railties/test/commands/middleware_test.rb), which asserts no Cookies/Session/Flash.

## Cases

**Default API-only.** Today: no Cookies, no Session, no Flash. `request.session` is [`Http::Session.disabled`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/request.rb); `reset_session` is safe ([`session_test.rb`](file:///home/user/workspace/repo/railties/test/application/middleware/session_test.rb)). After the PR: Cookies sits after Callbacks. Every request can build a cookie jar; nothing in the default API controller stack writes cookies, but the Rack stack is no longer cookie-free.

**Default full-stack.** Unchanged. Cookies → CookieStore → Flash remain.

**`config.session_store` on an API app.** Setting the store does not insert session middleware today, and still would not. You get Cookies (unwanted for the default store; incomplete for a real session) and `request.session` stays disabled unless the user also `middleware.use`s the store.

**Manual `ActionDispatch::Cookies`.** Documented opt-in appends Cookies at the end. After the PR, following the guide adds a **second** Cookies. Both see an uncommitted jar (`Cookies#call` writes only `unless cookie_jar.committed?`; `CookieJar#write` does not commit). Duplicate `Set-Cookie` is a real risk.

**Manual Session.** Still required for API-only. If the user adds only Session, CookieStore/`AbstractStore` still need an outer Cookies. The PR would supply that only because the default store makes `config.session_store` truthy, not because Session was added. Session still lands at the end, inside DatabaseSelector if that is enabled — the situation [`session uses default options if previous sessions exist`](file:///home/user/workspace/repo/railties/test/application/middleware/session_test.rb) is covering.

**Manual Flash.** Still omitted by default. Flash depends on Session. Cookies alone does not make flash work.

**`:disabled`.** Getter is `nil`, so API-only stays cookieless. Full-stack keeps Cookies and Flash, drops Session — current behavior, covered by [`disabled session allows reads and delete but fail on writes`](file:///home/user/workspace/repo/railties/test/application/middleware/session_test.rb).

**Init order.** `setup_default_session_store` always wins before stack build, so the proposed condition cannot mean “user configured a store.” A store set in an initializer after `build_middleware_stack` is still ignored (guide already says this). `force_ssl` secure-cookie default still applies only inside the full-stack session branch.

## Observable request consequences

- Stock API-only: extra Cookies hop; `Cookie` is parsed only if something touches `request.cookie_jar`; no session cookie is set because Session is still absent.
- API-only + guide snippet: likely duplicate Cookies; possible duplicate `Set-Cookie`.
- API-only + Session only: Cookies would now be present in the default slot (good order vs Session-at-end), but only as a side effect of the implicit default store.
- CSRF / `cookies` helpers: `ActionController::API` still omits Cookies/Flash/RequestForgeryProtection; this is a Rack-stack change, not a controller-module change.

## Compatibility

Breaking for every `config.api_only = true` app that did not disable the session store: Cookies enters the default stack. Guide/generator comments become wrong and, if followed, harmful. No changelog/guide updates in the proposed diff.

## Narrower alternative

Do not key Cookies off `config.session_store` while the default initializer always sets CookieStore.

If the product goal is “API-only sessions work from `config.session_store` alone”:

1. Skip `setup_default_session_store` when `api_only` (treat unconfigured API apps as no store).
2. When `config.session_store` is present, insert **Cookies and the session store** in the default slot (including the `force_ssl` secure-cookie assignment). Leave Flash opt-in.
3. Update [`api_app.md`](file:///home/user/workspace/repo/guides/source/api_app.md) and the generator comment so users stop `middleware.use`-ing Cookies/Session.

If the goal is only “don’t run Session without Cookies,” keep the documented opt-in; the current `unless config.api_only` already keeps them paired on full-stack apps.

**Verdict: request changes.** Do not merge this condition.
