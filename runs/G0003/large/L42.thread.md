`Rails::Application#config_for` loads one YAML document, picks the requested environment (default `Rails.env`), optionally deep-merges a `shared` section, and returns either an `ActiveSupport::OrderedOptions` (hash roots) or the raw YAML value (arrays, scalars, or `nil`).

```text
config_for(name, env: Rails.env)
  resolve path → Pathname or config/#{name}.yml
  raise if missing
  ActiveSupport::ConfigurationFile.parse
    File.read
    ERB if content includes "<%"
    YAML.unsafe_load(_file) || {}
  Hash#deep_symbolize_keys
  config = all[env.to_sym], shared = all[:shared]
  if both hashes: shared.deep_merge(config)   # env wins
  elsif config nil: config = shared
  if Hash: wrap ActiveSupport::OrderedOptions
  return config
```

### Path and parse

Non-`Pathname` `name` is interpolated under the first existent `config` path (`paths.add "config"` in [`Rails::Engine::Configuration`](file:///home/user/workspace/repo/railties/lib/rails/engine/configuration.rb#L95)):

`:custom` and `"custom"` both become `config/custom.yml` because `"#{name}"` calls `to_s`. A `Pathname` is used as-is — tested by [`config_for uses the Pathname object if it is provided`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2735-L2744).

If that path does not exist, the method raises a bare `RuntimeError` (not `Errno::ENOENT`, not `FormatError`):


That string is the contract: [`config_for raises an exception if the file does not exist`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2746-L2756).

`ConfigurationFile.parse` is marked `:nodoc:` and is a shared YAML/ERB loader, not a `config_for`-specific API. `config_for` passes no extra kwargs and no ERB binding.

```ruby
def parse(context: nil, **options)
  source = @content.include?("<%") ? render(context) : @content
  if source == @content
    YAML.unsafe_load_file(@content_path, **options) || {}
  else
    YAML.unsafe_load(source, **options) || {}
  end
rescue Psych::SyntaxError => error
  raise FormatError, "YAML syntax error occurred while parsing #{@content_path}. " \
        "Please note that YAML must be consistently indented using spaces. Tabs are not allowed. " \
        "Error: #{error.message}"

```

ERB runs only when the raw file contains `"<" + "%"`. `config_for` does not pass `context`, so `ERB#result` uses `TOPLEVEL_BINDING`. Filename is set on the ERB object so a Ruby error in the template points at the YAML path — that backtrace behavior is asserted in [`activesupport/test/configuration_file_test.rb`](file:///home/user/workspace/repo/activesupport/test/configuration_file_test.rb), not in the railties `config_for` tests.

The `config_for` ERB contract is only “tags are evaluated”: [`config_for containing ERB tags should evaluate`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2820-L2829) (`<%= 'custom key' %>` → `"custom key"`).

Psych syntax errors become `ActiveSupport::ConfigurationFile::FormatError` with the “YAML syntax error occurred while parsing” prefix: [`config_for with syntax error show a more descriptive exception`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2831-L2841).

Incidental mechanics of the parser, not `config_for`’s documented contract:

- Files without `"<%"` are read twice (`File.read` then `unsafe_load_file`).
- Parse uses `YAML.unsafe_load*`, so aliases and Psych’s unsafe object graph are in play.
- `|| {}` means YAML `false`/`nil` (empty document) becomes `{}` before `config_for` sees it.
- A leading NBSP warns on stderr and is otherwise ignored.

### Symbolization happens after YAML, not in Psych

```ruby
all_configs = ActiveSupport::ConfigurationFile.parse(yaml).deep_symbolize_keys
```

[`Hash#deep_symbolize_keys`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/hash/keys.rb#L116-L118) walks hashes and arrays and does `key.to_sym rescue key`. Environment names and `shared` are therefore looked up as symbols:

```ruby
config, shared = all_configs[env.to_sym], all_configs[:shared]
```

That is why `env: "production"` and `env: :production` are the same, and why the YAML key `shared` is found as `:shared`.

This post-parse walk is the intentional compatibility with YAML stacks that do not honor Psych’s `symbolize_names`. In 2020 `config_for` stopped passing `symbolize_names: true` into the parser (`be2fd61137`, issue #40031) after `safe_yaml`-style `YAML.load` patches dropped that keyword. The surviving test is [`config_for handles YAML patches (like safe_yaml) that disable the symbolize_names option`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2856-L2867).

What that test actually establishes today: given string-keyed YAML (`{ "development" => { "key" => "value" } }`), `config_for` still returns `{ key: "value" }`. The `YAML.stub :load, …` wrapper is leftover from the `YAML.load` era. Current `ConfigurationFile` calls `unsafe_load_file` / `unsafe_load`, so the stub does not intercept the parser. Psych already returns string keys, so `deep_symbolize_keys` is what the assertion is exercising.

### `env:` and `shared`

`env:` defaults to `Rails.env` and is only used as `env.to_sym` for the top-level lookup. Override is an explicit contract: [`config_for allows overriding the environment`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2843-L2854) loads via `config_for('custom', env: 'production')` while the process is not in production.

`shared` merge is the other documented contract ([method RDoc](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L273-L290) and [configuring guide](file:///home/user/workspace/repo/guides/source/configuring.md#L4766-L4785)):

```ruby
if shared
  config = {} if config.nil? && shared.is_a?(Hash)
  if config.is_a?(Hash) && shared.is_a?(Hash)
    config = shared.deep_merge(config)
  elsif config.nil?
    config = shared
  end
end
```

| YAML shape | Result | Established by |
|---|---|---|
| both hashes, overlapping keys | env value wins | [`shared config is overridden`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2769-L2780) (`:from_env` over `:from_shared`) |
| both hashes, nested hashes | recursive merge, env wins at each leaf | [`merges shared configuration deeply`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2795-L2810); RDoc example `{ baz: 1, qux: 2 }` |
| env missing, `shared` hash | `shared` (then OrderedOptions) | [`shared config is returned when environment is missing`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2782-L2793) |
| env missing, `shared` array | the array, unwrapped | [`works with only a shared root array`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2709-L2719) |
| env array + `shared` array | **env array only**; no concat | [`returns only the env array when shared is an array`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2721-L2733) |

`Hash#deep_merge` is [`ActiveSupport::DeepMergeable`](file:///home/user/workspace/repo/activesupport/lib/active_support/deep_mergeable.rb): nested hashes merge; arrays and scalars are replaced, not concatenated. `shared.deep_merge(config)` means the environment hash is `other`, so env wins. That replacement-not-concat rule for arrays is the tested contract, not an accident of the `if`.

The `config = {} if config.nil? && shared.is_a?(Hash)` line only steers a missing env + hash `shared` into the `deep_merge` branch (which `dup`s) instead of `config = shared`. Same keys either way; the extra empty hash is incidental.

If `shared` is truthy but the types do not match (hash vs array, hash vs scalar), neither branch runs and the environment value is kept. The array/array case is tested; mixed-type `shared` vs env is not.

### Return value

```ruby
if config.is_a?(Hash)
  config = ActiveSupport::OrderedOptions.new.update(config)
end
config
```

**Hash root → `ActiveSupport::OrderedOptions`.** That is an intentional, tested type:

- [`returns an ActiveSupport::OrderedOptions`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2869-L2889): `config.some_key` method access; with `env: :test` and an empty `test:` section, `some_key` is still `"default"` from `shared`.
- [`makes all hash methods available`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2678-L2695): `keys`, `values`, `to_h`, `==` against a plain hash, because `OrderedOptions < Hash`.

[`OrderedOptions#[]`](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L41-L43) does `key.to_sym`. That is why the **root** is accessible as symbol or string: [`loads custom configuration from YAML accessible as symbol or string`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2653-L2663). String access is a property of `OrderedOptions`, not of the YAML hash.

**Nested hashes stay plain `Hash` with symbol keys.** They are not wrapped. [`loads nested custom configuration from YAML as symbol keys`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2665-L2676) only uses `[:foo][:bar][:baz]`. The 6.1 upgrade guide states nested string-key access was removed; `with_indifferent_access` is the documented escape hatch. Root string access remaining via `OrderedOptions` and nested string access failing is the intended split, even though [`guides/source/configuring.md`](file:///home/user/workspace/repo/guides/source/configuring.md#L4757) still shows `Rails.configuration.payment["merchant_id"]` — that hits the root wrapper.

**Array / non-hash root is returned unchanged.** [`does not assume config is a hash`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2697-L2707) is the scalar-or-collection contract as actually tested: a development array `%w(foo bar)` is the return value, not an OrderedOptions. A YAML scalar under the env key would take the same `is_a?(Hash)` false path; there is no dedicated scalar-root test.

### Absent environment, empty file, missing file

Three different nil/error paths:

**Missing file.** Existence check fails before parse. `RuntimeError` with `Could not load configuration. No such file - …/config/custom.yml`. Test above.

**File present, env key absent, no usable `shared`.** Lookup yields `nil`; the `shared` block is skipped; `nil` is not a Hash, so no wrap; return `nil`. [`config_for without the environment configured returns nil`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2758-L2767) (`test:` only, app booted as `development`).

If `shared` is present, absence of the env key is *not* `nil` — it falls through to the shared-return tests above. The empty `test:` section in the OrderedOptions test is YAML `nil`/empty mapping for that env, then hash `shared` fills it.

**Empty file.** `ConfigurationFile.parse` turns an empty document into `{}`. `{}[:development]` is `nil`, no `shared`, return `nil`. [`config_for with empty file returns nil`](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L2812-L2818). Empty file and “env not in file” are observationally the same `nil`; they are different inputs (parse produced `{}` vs a hash that simply lacks that key).

### Intentional contracts vs incidental mechanics

**Contract** (RDoc, guides, and the railties tests named above):

- Resolve `config/#{name}.yml` or an explicit `Pathname`.
- Evaluate ERB, then YAML.
- Missing file raises that exact `RuntimeError`.
- Bad YAML raises `ConfigurationFile::FormatError`.
- Keys are symbols after load, even if the YAML engine emitted strings.
- `env:` selects the top-level section; default `Rails.env`.
- Hash `shared` is deep-merged under the env hash; env wins.
- Missing env with `shared` returns `shared`.
- Hash result is `OrderedOptions` (root method + string/symbol `[]`).
- Array result is a Ruby array; arrays are not merged with `shared`.
- Empty file / unknown env without `shared` → `nil`.

**Incidental** (true of the code, not what the `config_for` tests pin):

- `unsafe_load*` rather than `safe_load`.
- Double-read of non-ERB files.
- ERB gated on the substring `"<%"`, evaluated in `TOPLEVEL_BINDING`.
- `config = {}` before `deep_merge` when env is missing and `shared` is a hash.
- Nested hashes are not `OrderedOptions`.
- The `YAML.stub :load` in the safe_yaml test does not wrap the current parser.
- `config_for` in `config/application.rb` works as a class-body call only because [`Rails::Railtie.method_missing`](file:///home/user/workspace/repo/railties/lib/rails/railtie.rb#L262-L268) forwards to the instance.
- `database_configuration`’s `shared` handling is a separate merge.

The method is a single pipeline with no cache. Each call re-reads and re-parses the file.
