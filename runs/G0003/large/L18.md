**Request changes.** `ids` cannot be reduced to `pluck(*primary_key)` at this revision. `pluck` already covers loaded relations, contradictions, query-cache skipping, and `async`, but it does **not** collapse parent rows produced by an eager-load join.

## Verdict

The claim is false. Current [`ids`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L376-L384) is already `pluck(*primary_key)` except for one path:

```376:384:activerecord/lib/active_record/relation/calculations.rb
    def ids
      if !loaded? && has_include?(primary_key)
        return apply_join_dependency.group(*primary_key).pluck(*primary_key)
      end

      pluck(*primary_key)
    end
```

That `group(*primary_key)` is the #46503 / #48080 behavior: unique parent primary keys when `includes` / `eager_load` LEFT OUTER JOIN a collection. [`pluck`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L310-L316) joins the same way and then selects the column with **no** grouping:

```310:316:activerecord/lib/active_record/relation/calculations.rb
      if has_include?(column_names.first)
        relation = apply_join_dependency
        relation.pluck(*column_names)
      else
```

[`has_include?`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L407-L409) is true for `eager_load` and for any present `includes`, even when the association is unused in `WHERE`/`ORDER`. `56c95aee03` already restored the `pluck` delegation and kept this branch on purpose.

I applied `def ids; pluck(*primary_key); end` and ran the existing ids tests (`sqlite3_mem`). Three failures, all duplicate parent ids:

## Minimal reproducer

```ruby
company = Company.first
2.times { company.contracts.create! }

rel = Company.includes(:contracts).where(id: company.id)

rel.map(&:id)  # => [company.id]          # records are uniqued
rel.ids        # => [company.id]          # GROUP BY primary key
rel.pluck(:id) # => [company.id, company.id]  # join fan-out
```

Observed on this checkout: `ids=[1]`, `pluck=[1, 1]`. Same split for `eager_load(:contracts)` and for `async_ids` (`[1]`) vs `async_pluck(:id)` (`[1, 1]`). Composite keys match:

## Case-by-case (this revision)

| Shape | Preserved if `ids` is only `pluck(*primary_key)`? |
|---|---|
| Unloaded `includes` / `eager_load` of a **collection** | **No** — duplicate parent ids. Existing tests already fail. |
| Same, **composite PK** | **No** — same fan-out. No existing test. |
| `async_ids` on that shape | **No** — `async.ids` keeps `@async` and still hits the group path today (`Promise::Complete` with unique ids). `async_pluck` duplicates. |
| Loaded relation with includes | Yes — both use in-memory records (`records.pluck`). |
| `preload` (no join) | Yes — `has_include?` is false. |
| `group(primary_key)` already present | Yes — grouping already collapses rows. |
| Order by a non-PK column | Yes on this sqlite fixture (`includes(:comments)` does not fan out). The group path exists so PG does not require `ORDER BY` columns in a `DISTINCT` select (#48080 / `test_ids_with_includes_and_non_primary_key_order`). Replacing group with bare pluck reintroduces duplicates whenever the ordered association actually multiplies rows. |
| `limit` / `offset` | Existing empty/offset tests still pass. Not generally safe: [`apply_join_dependency`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/finder_methods.rb#L452-L491) rewrites limit via `distinct_relation_for_primary_key`, then **keeps the collection join**, so `Company.includes(:contracts).where(id: company.id).limit(1)` was `ids=[1]` vs `pluck=[1, 1]`. |
| Contradictory `where(id: [])` | Yes — `pluck` returns `[]` / `Promise::Complete` with no query. |
| `skip_query_cache!` | Yes — both end in `pluck`’s `skip_query_cache_if_necessary`. Existing `#skip_query_cache! for #ids` still passed after the simplification. |

`Relation#none` is already identical (`pluck` short-circuits `@none`); it is not the interesting case.
