I have enough of the current `with_lock` baseline from source and tests. Drafting a behavioral brief only: no signatures, internals, or code changes.

**Problem frame:** An application developer already has a persisted record and needs one operation that starts (or joins) a database transaction, reloads that row under a chosen lock, and then runs work that must commit or roll back together. Today they can pass a custom lock clause or transaction options, but combining them is awkward, easy to get wrong, and fails in adapter-specific ways. That makes concurrent updates harder to do safely.

**Hypothesis about the pain (not a measured user report):** `with_lock` grew from “optional lock clause” into “lock clause plus transaction options.” Docs and tests mostly show those separately. `false` as a lock request is easy to confuse with transaction flags such as `joinable: false`. Unsupported lock SQL and unsupported isolation fail through different errors. I am treating “easier and safer” as: one obvious way to ask for both, with failures that name the conflict instead of looking like a generic SQL or transaction bug.

---

**Current observable baseline**

Evidence: pessimistic locking docs/tests, transaction isolation tests, custom-lock tests, write-prevention tests, and the public `lock!` / `reload` / `transaction` behavior those tests rely on. I did not run the suite in this orb.

What a caller can do today:

- `with_lock` with a block starts or joins a transaction, reloads a persisted record with a lock, then runs the block. The block receives the current transaction object (callers use it for things like `after_commit`).
- No lock argument means an exclusive row lock. On PostgreSQL that shows up as `FOR UPDATE`. On SQLite, lock SQL is omitted; the transaction still runs.
- A custom clause is sent as raw SQL. PostgreSQL tests use `FOR SHARE NOWAIT`; MySQL tests use `LOCK IN SHARE MODE`. The querying guide says an unsupported clause raises `ActiveRecord::StatementInvalid`.
- `false` as the lock request disables the row-lock clause: the record is still reloaded inside the transaction, without `FOR UPDATE` / equivalent.
- Transaction options `requires_new:`, `joinable:`, and `isolation:` are accepted and applied to the wrapping transaction. Isolation is only asserted on PostgreSQL in the locking tests.
- Successful work inside the block is committed and visible after reload. An exception in the block rolls back those writes.
- Nested default: a nested transaction joins the open parent. `requires_new: true` starts a distinct inner transaction (savepoint-style). `joinable: false` makes that inner transaction non-joinable.
- Isolation cannot be changed when joining an open transaction, or when starting a nested/savepoint transaction. Callers see `ActiveRecord::TransactionIsolationError` (`cannot set isolation when joining a transaction` / `cannot set transaction isolation in a nested transaction`).
- Adapters that cannot set isolation raise `ActiveRecord::TransactionIsolationError` (`adapter does not support setting transaction isolation`). SQLite reports that it supports isolation but only `:read_uncommitted`, and only with shared-cache enabled; other levels raise `TransactionIsolationError`, and shared-cache off raises a plain error about enabling shared-cache.
- `lock!` (and therefore the lock step of `with_lock`) refuses a persisted record with unsaved changes: a `RuntimeError` naming the changed attributes. This is tested on `lock!`, not on `with_lock` itself.
- If the row is gone at reload, `reload` raises `ActiveRecord::RecordNotFound`. This is documented on `reload`; there is no direct `with_lock` missing-row test.
- While write-prevention is on, default and custom locks raise `ActiveRecord::ReadOnlyError` (`Lock query attempted while in readonly mode`) before a lock query. Nesting `while_preventing_writes(false)` allows locking again.
- PostgreSQL rejects locked eager loads that would `SELECT ... FOR UPDATE` on an outer join; that case is skipped on PostgreSQL.

Not observed: a locking test that combines a custom clause with `requires_new` / `joinable` / `isolation` on `with_lock`. Combining them may already work, but that is unverified here.

---

**Desired outcomes**

1. A developer can, in one `with_lock` use, choose the lock (default exclusive, none via `false`, or a custom clause) and the transaction options (`requires_new`, `joinable`, isolation) without inventing a second wrapper.
2. Default lock, no-lock (`false`), and custom clause remain distinct, observable behaviors.
3. Unsaved changes, a missing row at reload, write-prevention, and unsupported lock/isolation combinations fail before conflicting writes commit, with errors that match the existing public types unless a later decision explicitly changes them.
4. Commit still persists the block’s writes; an exception still rolls them back.
5. The block still receives the transaction object for callbacks.
6. Nesting still follows existing transaction joining / new-inner-transaction / isolation-conflict rules; `with_lock` does not invent a second nesting model.
7. Adapter differences stay visible: unsupported clauses and isolation fail in the way that adapter already fails, rather than being silently rewritten into a portable lock dialect.

---

**Non-goals**

- A portable, adapter-neutral lock language (no mapping of `FOR SHARE` onto MySQL `LOCK IN SHARE MODE`, etc.).
- Changing optimistic locking, relation-level `lock`, or transaction semantics outside this helper.
- Making SQLite emulate row locks.
- Prescribing a new calling convention, keyword layout, or internal flow.
- Changing error classes unless a later decision says the current types are themselves the safety problem.
- Exhaustive coverage of every vendor lock hint.

---

**Risks**

- Existing callers already mix a positional clause with an options hash, or pass only one of them. A “clearer” convention can break those call sites.
- `false` (no row lock) and `joinable: false` remain easy to confuse if the request shape stays overloaded.
- Hiding adapter failures behind a generic error would make unsupported combinations *less* diagnosable.
- Joining a parent transaction while also asking for isolation already errors; making `with_lock` “just work” there could commit work at the wrong isolation.
- Missing-row and dirty-record behavior are inferred from `lock!` / `reload`, not proven on `with_lock`. If those paths diverge, the examples below are wrong.

**Acceptance examples** (required cases)

These are required behavioral examples, not an implementation or test plan. Where current tests do not cover `with_lock` directly, that is marked.

**1. Default lock**

Given a persisted person and no lock argument, when they run `with_lock` with an empty block, then a transaction runs and the reload uses the adapter’s exclusive lock. On PostgreSQL that is visible as `FOR UPDATE`. On SQLite no lock SQL is emitted; the block still runs in a transaction.

**2. `false` (no row lock)**

Given a persisted person, when they request lock `false`, then the record is reloaded inside the transaction without a row-lock clause. Concurrent writers are not blocked by this call. This is distinct from `joinable: false`.

**3. Custom clause**

Given PostgreSQL, when they pass `FOR SHARE NOWAIT`, then the reload SQL includes that clause. Given MySQL, when they pass `LOCK IN SHARE MODE`, then that clause appears. Given a clause the database rejects, they observe `ActiveRecord::StatementInvalid`, not a successful lock.

**4. Dirty persisted record**

Given a persisted person with an unsaved `first_name` change, when they lock, they get a runtime error mentioning `Changed attributes: "first_name"`, and they are told to save or reload. The in-memory change is not discarded by a successful locked reload. Proven on `lock!`; `with_lock` is expected to surface the same failure because it locks through that step.

**5. Commit**

Given a persisted person, when the block changes `first_name`, saves, and returns normally, then a later reload shows the new name.

**6. Exception rollback**

Given a persisted person, when the block saves a new name and then raises, then a later reload shows the original name.

**7. Yielding the transaction object**

Given a persisted person, when the block takes one argument, that argument is the current transaction (the same object `current_transaction` would return inside the block), so they can register `after_commit` / `after_rollback` callbacks.

**8. `requires_new` and `joinable`**

Given an already-open joinable transaction, when they call `with_lock(requires_new: true, joinable: false)`, then the block runs in a different, non-joinable inner transaction, not the outer one.

**9. Isolation**

Given PostgreSQL (or another adapter that can set isolation), when they call `with_lock(isolation: :read_uncommitted)` outside a conflicting parent, then the current transaction’s isolation is `:read_uncommitted`.

**10. Nesting without `requires_new`**

Given an open joinable transaction, when they call `with_lock` with no nesting options, then the block joins that parent: writes and rollback follow ordinary nested-transaction rules (a nested `ActiveRecord::Rollback` does not roll back the parent). Direct `with_lock` coverage of this join path was not in the locking tests; it is the documented default for `transaction`.

**11. Nesting plus isolation (counterexample)**

Given an open transaction, when they ask `with_lock` to set a *different* isolation without a real new transaction, they observe `ActiveRecord::TransactionIsolationError` about joining. When they ask for isolation on a `requires_new` inner transaction, they observe `TransactionIsolationError` about nested transactions. Same isolation on a join does not raise (proven on `transaction`, not on `with_lock`).

**12. Missing row during reload**

Given a persisted in-memory record whose row was deleted, when `with_lock` reloads to take the lock, they observe `ActiveRecord::RecordNotFound`. The block does not run. Inferred from `reload`; no direct `with_lock` test.

**13. Write-prevention mode**

Given `while_preventing_writes`, when they `with_lock` with the default lock or a custom clause, they observe `ActiveRecord::ReadOnlyError` / `Lock query attempted while in readonly mode`, and no lock query. Nested `while_preventing_writes(false)` allows `with_lock` again.

**14. Unsupported combinations, as users actually see them**

| Situation | What the user observes today |
| --- | --- |
| Custom lock SQL the database does not accept | `ActiveRecord::StatementInvalid` |
| Isolation on an adapter that cannot set it | `ActiveRecord::TransactionIsolationError` (`adapter does not support setting transaction isolation`) |
| SQLite isolation other than `:read_uncommitted` | `TransactionIsolationError` (`SQLite3 only supports the \`read_uncommitted\` transaction isolation level`) |
| SQLite `:read_uncommitted` without shared-cache | Error that they must enable shared-cache mode |
| Isolation while joining, or isolation on a nested/savepoint transaction | `TransactionIsolationError` with join/nested wording |
| Lock while writes are prevented | `ReadOnlyError` as in example 13 |
| PostgreSQL locked eager load with outer join | Database error; this path is not offered as working |

The work should not collapse these into one silent no-op. Whether messages should be more specific to `with_lock` is an open product choice.

---

**Steering evidence**

Investigate or stop if:

- Callers still cannot request a custom clause and transaction options in one use without a second transaction wrapper.
- `false` starts being treated as a transaction option or as “use default lock.”
- Dirty records get locked and persist mixed in-memory/database state.
- Exceptions in the block leave partial writes committed.
- The block stops receiving the transaction object.
- Write-prevention no longer blocks locking, or blocked locking looks like a SQL syntax error.
- SQLite begins failing default `with_lock` because a `FOR UPDATE` clause is now emitted.
- Isolation or lock-clause failures become silent success on adapters that previously errored.

Reconsider the problem framing if the real difficulty is documentation of the existing mix of clause + options, or adapter SQL literacy, rather than the helper’s observable contract. The locking tests never exercise clause + options together; that gap could be a docs/test gap, not a missing capability.

---

**Open questions**

- Is combining a custom clause with transaction options already possible and only poorly shown, or do callers hit a real conflict today? Unverified.
- Should `with_lock(false)` remain “transaction + reload, no row lock,” or is `false` too easy to confuse with `joinable: false`?
- Should dirty-record failure stay a `RuntimeError`, or is that part of “safer”?
- Should a missing row during `with_lock` stay `RecordNotFound`, or is a lock-specific error wanted? No current `with_lock` example.
- Should SQLite’s silent drop of lock SQL stay as-is, or should a custom clause on SQLite be an explicit unsupported combination?
- Must existing `with_lock(clause)` and `with_lock(opts)` call shapes keep working unchanged? Compatibility is likely required; it is not proven as a constraint from tests alone.

I am not treating a new signature or control flow as part of this brief. If this problem frame is right, next is confirmation of the dirty-record, missing-row, and clause-plus-options questions—not a design.
