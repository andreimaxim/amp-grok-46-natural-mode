## Assistant

Current conversion, update, merge, and replace already collapse `:key` and `"key"` with no signal. Below is a draft behavioral spec from that evidence — not a design.

I inspected the public HashWithIndifferentAccess contract, its tests, and live conversion/update/merge/replace (including nested and multi-hash cases). Tests never assert collision detection. Live runs on this Ruby show last insertion in the source hash winning, but the documented contract still calls that winner unspecified.

---

**Problem frame:** Someone ingesting configuration (or similar nested key/value data) into a hash that treats `:timeout` and `"timeout"` as the same name needs to know when those two forms carried different values. Today conversion and update keep one value and drop the other with no signal. When both forms arrive in one ordinary hash, which value is kept is not part of the public contract. Mixed-key ingestion can therefore lose settings and look successful.

Hypothesis: the painful case is ingesting a hash that already contains both forms (YAML strings plus Ruby symbols, merged sources, copy-paste config), not a later deliberate overwrite of a single setting.

**Current observable behavior**

- After conversion, only string keys remain for names that were symbols. `:key` and `"key"` become one entry.
- Building or updating from an ordinary hash that contains both forms leaves one value; the other is gone. Size, keys, and reads all look like a single setting. There is no error, warning, or other signal.
- Sequential writes on an already-indifferent hash last-write-win (`h[:key] = …` then `h["key"] = …`). That overwrite is visible at the write site.
- Nested hashes are converted the same way, so an inner collision can discard data even when the outer keys were not mixed.
- `update` / `merge` with several hashes applies each argument in order. A collision can happen inside one argument; a later argument can also replace an earlier value under the same indifferent name. Those are different events.
- Same-value mixed keys still collapse to one entry; nothing indicates two forms were present.
- Non-string, non-symbol keys are unchanged and are not this problem.

**Behavioral outcome:** When mixed symbol and string keys that name the same setting would collapse during conversion or update, the person ingesting the data can tell that a value was discarded. Default silent collapse for existing callers is a compatibility surface; whether detection is opt-in is open.

**Examples** (required unless marked illustrative)

1. **Single-hash conversion, mixed keys, different values**
   Given `{ :timeout => 30, "timeout" => 60 }`
   When it is converted to indifferent access
   Then the result has one `timeout` entry, one of 30 or 60 is gone, and today there is no signal. Either remaining value is compatible with the current contract.

2. **Insertion order does not define a public winner**
   Given `{ "timeout" => 60, :timeout => 30 }`
   When converted
   Then again one value remains and the other is discarded. On this Ruby the later insertion survived in both (1) and (2), but that is not a documented guarantee. Detection must not depend on callers knowing which form wins.

3. **Nested inner collision, outer keys clean**
   Given `{ database: { pool: 5, "pool" => 25 } }`
   When converted
   Then `database` is present, `pool` is a single value, and the other pool value is gone with no signal. Nested ingestion is in scope even when the top level looks fine.

4. **Nested outer collision drops a whole branch**
   Given `{ :outer => { inner: "kept_if_symbol_wins" }, "outer" => { inner: "kept_if_string_wins" } }`
   When converted
   Then one entire `outer` hash remains. The other branch is discarded as a unit, not merged field-by-field.

5. **Update from a mixed ordinary hash**
   Given an indifferent hash `{ "timeout" => 10 }`
   When it is updated with `{ :timeout => 30, "timeout" => 60 }`
   Then `timeout` becomes one of 30 or 60, the original 10 is replaced, and the unused mixed value is discarded with no signal.

6. **Multi-hash update: collision inside an argument vs later overwrite**
   - Inside one argument: `update({ :a => 1, "a" => 2 }, { b: 3 })` can discard 1 or 2 while ingesting that first hash.
   - Across arguments: `update({ a: "second" }, { "a" => "third" })` is ordinary later-hash-wins under one name. That is merge order, not a mixed-key pair inside one hash.
   These two must not be treated as the same event.

7. **Counterexample — one form only**
   Given `{ timeout: 30 }` or `{ "timeout" => 30 }`
   When converted or merged
   Then the value is kept and there is nothing to detect.

8. **Counterexample — sequential write on an indifferent hash** (illustrative boundary)
   Given `h[:timeout] = 30` then `h["timeout"] = 60`
   Then 60 remains. This is an explicit overwrite, not unnoticed mixed-key ingestion.

9. **Same values, both forms** (boundary; meaning open)
   Given `{ :timeout => 30, "timeout" => 30 }`
   When converted
   Then one entry remains. Whether that counts as discarded data is open: no value was lost, but a duplicate form was.

**Compatibility constraints**

- Silent collapse of mixed keys is documented and tested. Applications already ingest config this way and read one remaining value.
- The winner for a mixed ordinary hash is explicitly unspecified. Defining a winner or raising by default would change that contract.
- Last-write-wins for sequential assignment and for later hashes in `update`/`merge` is existing, observable behavior and is not the collision problem.
- Nested conversion is existing behavior; detection that only watches the top level would miss example 3.

**Steering evidence**

- Success: a mixed-key ingest with differing values is distinguishable from a clean ingest; the person can tell data was discarded without already knowing both forms were present.
- Contradicts success: conversion/update of examples 1–5 still looks like a normal one-key hash, or nested collisions remain invisible, or multi-hash later-overwrite is reported as if it were a mixed-key collapse (or the reverse).
- Suggests the framing is wrong: real ingestion never carries both forms; the actual pain is wanting a guaranteed winner rather than a discard signal; or the signal is so noisy (same-value duplicates, hot paths) that people cannot use it.
- Decision: if mixed-key loss cannot be seen from outside the hash, continue investigating. If the need is really “always keep the string” or “always keep the last write,” revise the outcome. If almost no caller has both forms, stop.

**Open questions**

- **Opt-in:** Is detection something a caller enables for ingestion, or does it apply to every conversion and update? Default-on would collide with the silent contract above.
- **Error versus observation:** Should mixed differing values fail the ingest, or only be visible (log, warning, callback, return channel) while still producing a collapsed hash?
- **Key disclosure:** If a discard is reported, which of these must be visible: the name, the original `:key` vs `"key"` forms, both values, nesting path, and which value was kept?
- **Performance:** Configuration hashes are usually small; some callers convert large, hot hashes. Any detection that always walks keys (especially nested, especially when no collision exists) could be too expensive — whether that constrains the outcome is unset.
- Also unset: do same-value mixed keys count? Are `replace`, `Hash[]`, and `store` in the same ingest story as `new`/`update`/`merge`? I treated them as the same collapse today, but the named pain is configuration ingestion.

---

I treated sequential last-write on an already-indifferent hash as out of scope, and I did not require a defined winner. Correct that if the pain is “I need to know which value wins,” not “I need to know that one was thrown away.”
