## Assistant

I have enough of the current baseline to draft the brief. One naming note first: `button_to` now lives on `ActionView::Helpers::NavigationHelper` (upgrade docs still say `UrlHelper`). The tests that pin it are in the navigation helper suite, not the URL helper suite.

---

**Problem frame:** A Rails view author needs a labeled control that submits to a URL, including for actions that change data, without relying on a link. A visitor — including keyboard and assistive-tech users — needs to perceive that control’s name, whether it will submit, and that it is a submit control rather than navigation.

Today those results vary by calling form in ways the author cannot reliably predict from the call site, and that the visitor cannot reliably perceive from the control. A string label and a block do not always produce the same kind of control. GET, POST, and DELETE do not present the same submission contract. `remote: true`, `disabled:`, nested `form:` options, and `authenticity_token` attach to different parts of the generated form or disappear. `false` omits a destination; `nil` as the URL is unspecified. A string label with markup is not covered the way `link_to` labels are.

That matters because authors copy patterns from docs and other helpers, then ship controls that submit the wrong verb, omit a CSRF token, put a confirmation or remote flag on the wrong element, or expose an unnamed or HTML-injected label. Visitors activate something that looks like a button and get a different outcome than a neighboring control.

**Hypothesis, not a reported incident:** the pain is inconsistent observable contracts across supported calling forms, not a single broken example in this repo.

**Evidence inspected:** the helper’s documented calling forms and generated output, URL conversion through `url_for`, method selection, authenticity-token handling, form-attribute assembly, block capture, the navigation-helper tests that pin those results, CSRF request tests for tokens on `button_to`, and the Action View / upgrade / JavaScript guides. I read those sources; I did not execute the tests. Claims below that the tests do not pin are labeled.

---

**Actors**

- **View author:** writes `button_to` in a template and needs the call’s meaning to be stable across label style, verb, remote, disabled, nested form options, and token settings.
- **Visitor:** activates the control with pointer, keyboard, or assistive technology; needs a name, a disabled state that matches whether submit is possible, and a submit control for non-GET actions.
- **Forgery-protected app:** must accept or reject the submission according to the intended verb and token policy.
- **Not in scope as primary actors:** search bots (the helper’s docs already treat a form as the safe mutating control), and runtime JavaScript libraries (their behavior is a non-goal).

**Constraints**

- Keep every calling form the helper already documents: string label plus URL, block label, model or nested model as URL, path helper, hash URL, and `false` as “no destination.”
- Stay a form-backed submit control for mutating actions; do not push authors toward a link for DELETE.
- Preserve CSRF policy: a POST-family submit can carry a token; a GET submit must not; an explicit token string, `true`, `false`, and “forgery protection off” must remain distinguishable.
- Do not require authors to learn a new helper to get a predictable, accessible control.
- Respect existing app config that currently chooses a submit `<input>` versus a `<button>` for string labels (Rails 7+ defaults to a button; upgraded apps may not).

**Non-goals**

- Redesigning `link_to`, `form_with`, or confirmation/remote JavaScript.
- Adding calling forms or options.
- Changing how per-form CSRF tokens are stored or validated on the server, except insofar as the helper must keep emitting a token that matches the intended verb.
- Prescribing markup, new attributes, or a test suite.
- Making `button_to` a general-purpose form builder (`params:` hidden fields stay supporting behavior, not the product).

---

**Current observable baseline**

**Calling forms.** With a string label, the first argument is the name and the second is the destination. With a block, the first argument is the destination and the block is the name; extra options apply to the submit control. A model or `[parent, child]` array is a destination; a new record posts to the collection, a persisted record patches the member. `false` as destination omits the form action. `nil` as the name uses the destination string as the visible name.

**URL conversion.** A string or path is used as the form action. Query characters in that action are escaped, including when the URL was marked HTML-safe. `url_for` receives anything other than `false`. **Untested:** `nil` as the destination; `url_for(nil)` elsewhere means “current path,” which would be a different outcome from `false`.

**Method selection.** Default is POST. GET renders a GET form and no method override. DELETE (and PATCH/PUT) keep a POST form and add a hidden `_method`. A persisted model infers PATCH; a new record infers POST. An explicit `method:` wins. Guides still warn that a persisted model in the URL changed from POST to PATCH in Rails 7.

**Authenticity token.** A token is emitted only when the form method is POST and forgery protection is on. A string token is used as-is; `true` uses the generated token; `false` omits it; default with protection on uses the generated token. GET emits no token. When protection is off, no token. CSRF tests show the token is bound to the intended verb (implicit POST, explicit POST/PATCH/DELETE), and a token for DELETE is rejected on PATCH.

**Generated form.** Default class is `button_to`. `form_class:` replaces that class and is escaped. A nested `form:` hash becomes attributes on the form; a class inside `form:` wins over `form_class:`. `remote: true` marks the form remote; `remote: false` does not. `data:` on the helper options lands on the submit control, not the form. Guides already tell authors that a Turbo confirmation for `button_to` must go in `form:`, unlike `link_to`.

**Block versus string.** A block is captured as the submit control’s content (so markup from the block can render). A string label becomes the control’s text. If the app still uses the pre-7.0 setting, a string label is an `<input type="submit">` and a block is a `<button>` — two different controls for the same helper. New apps use a button in both cases.

**Disabled.** `disabled: true` marks the submit control disabled. `disabled: false` does not.

**Unsafe HTML in labels.** `form_class` with a script tag is escaped. `link_to` string labels are escaped; HTML-safe `link_to` labels are not. **`button_to` has no equivalent label test.** String labels go through the same escaping content tags use; a block can carry already-safe markup. That gap is part of the predictability problem.

---

**Behavioral outcomes**

1. **Same intent, same kind of control.** When the author supplies a name as a string or as a block, the visitor gets a named submit control of one consistent kind for that app, not a text field-looking submit in one form and a true button in the other.

2. **The visible name is always a name.** A string name is shown as text, not as markup. A block name can include structured content the author wrote. A missing string name still yields a perceivable name (today: the destination). Markup the author did not mark safe does not execute.

3. **Verb is visible in the contract the form submits.** GET submits as GET with no override and no token. POST submits as POST. DELETE (and other override verbs) submit through the POST form plus an override the server already understands. A persisted model continues to mean PATCH unless the author overrides it.

4. **Remote is a form-level fact.** `remote: true` means the form is marked remote. `remote: false` means it is not. Authors can tell from the call that remote does not attach to the inner control.

5. **Disabled means not submittable.** `disabled: true` makes the control unusable; `disabled: false` leaves it usable. The disabled state is on the control the visitor activates.

6. **Nested `form:` options only describe the form.** Attributes the author puts in `form:` appear on the form. Attributes they put next to the name (class, data, disabled, name/value) appear on the submit control. Confirmations that must sit on the form are not silently applied to the button, and the other way around.

7. **Token policy is predictable from verb and explicit option.** Protection on + POST-family → token, unless `authenticity_token: false`. Explicit string → that string. `true` → generated token. GET → no token. Protection off → no token.

8. **No destination is explicit.** `false` means the form has no action. `nil` as destination must not be a quiet alias of “current page” or of `false` without a documented choice.

**Examples** (required unless marked illustrative)

**String label, default POST.** Author writes a labeled submit to a URL with no method. Visitor sees a named submit. Activating it POSTS to that URL. With forgery protection on, the submission includes a token; with it off, it does not.

**Block label.** Author wraps structured content (for example a span) in a block and passes only the URL. Visitor sees that content as the control’s name. The destination is the URL, not the block. The control kind matches the string-label case for that app.

**GET versus POST versus DELETE.** Author sets `method: :get` — visitor’s submit is a GET, no token, no override field. Author omits method — POST and token when protection is on. Author sets `method: :delete` — POST form, override to DELETE, token bound to DELETE. A visitor cannot tell the verb from the visible label alone; the author must be able to tell from the call.

**Persisted model (illustrative of today’s inference).** Author passes a saved record as the destination with a block name “Update”. Submission is PATCH to that record’s URL unless `method:` is set. This is current behavior and a known Rails 7 compatibility footgun.

**`remote: true`.** Author passes `remote: true`. The form is marked remote; the inner control is not. `remote: false` leaves the form unmarked.

**Disabled.** Author passes `disabled: true`. The visitor cannot submit. Author passes `disabled: false`. The visitor can.

**Nested `form:`.** Author passes `remote: true` plus `form: { class: "custom-class", "data-type" => "json" }`. The form has that class and data-type and is remote. The submit control does not receive those form attributes. A confirmation meant for the form must be passed in `form:`; a `data: { confirm: ... }` next to the name lands on the control. **Open:** whether that split is the desired long-term contract or the confusion to remove.

**Explicit authenticity token.** Protection on: string token appears as that value; `true` appears as the generated token; `false` omits the token. GET never shows a token even if a token option is passed — **untested combination; product question.**

**No destination.** `button_to("Hello", false)` and `button_to(false) { "Hello" }` both produce a named POST submit with no action.

**Nil destination (boundary; current behavior untested).** Author passes `nil` as the URL. Today this is not pinned. Desired outcome: it is either rejected, treated as “current path,” or treated like `false` — one documented meaning, not a third silent behavior.

**Unsafe HTML in the label.** Author passes a string `"Malicious <script>content</script>"`. Visitor sees that text, not a script. Author passes a block that deliberately includes a tag (as today’s span example). Visitor sees that structure. Author passes an HTML-safe string — **open whether that is trusted like `link_to` or always shown as text.**

**Nil name.** Author passes `nil` and a URL. Visitor’s control is named with the destination string, escaped as text.

---

**Compatibility risks**

- Apps on the old “string label → `<input>`” setting will see a control-type change if string and block are unified.
- Code that passed a persisted model and expected POST already had to add `method: :post` in Rails 7; tightening inference further would hit the same apps.
- Selectors and styles that target `form.button_to input[type=submit]` versus `button` will break if the inner control is unified.
- CSRF: omitting a token on POST, emitting one on GET, or binding a token to the wrong verb would fail existing request tests and real apps.
- Moving `data-confirm` / remote from button to form (or the reverse) would change which element UJS/Turbo observes.
- Treating `nil` like `false` would drop actions that today may submit to the current path.
- Escaping block content the same as string content would break authors who pass `content_tag` in a block.
- Docs and upgrade notes still say `UrlHelper#button_to`; authors grepping that name are looking at the right behavior in a renamed module.

---

**Open product questions**

1. When string and block disagree on control kind because of the pre-7.0 setting, is the desired outcome “always the new-app control,” “always honor the setting but document it,” or “setting remains, but both calling forms follow it”?
2. Should `nil` as destination mean current path, mean no action (like `false`), or be invalid?
3. Should a confirmation passed as `data:` on the helper apply to the form (what Turbo needs) or stay on the control (what the helper does today)?
4. Is an HTML-safe string label trusted markup (like `link_to`) or always plain text?
5. If the author passes `authenticity_token:` on a GET `button_to`, is the token ignored (today’s POST-only rule) or a mistake to surface?
6. Must the visitor be able to distinguish GET vs DELETE from the control alone, or is that only the author’s problem (label text, not the helper)?
7. Is `remote: true` still a first-class outcome, or a legacy alias authors should stop using in favor of Turbo attributes on `form:`?

**Steering evidence** (external, not a test plan)

**Success.** A view author can pick string or block, GET/POST/DELETE, remote or not, disabled or not, nested `form:` or not, and an explicit token option, and explain the destination, verb, name, enabled state, remote-ness, and token presence without looking at generated markup. A visitor using a keyboard or screen reader gets a named submit control; a disabled call is not submittable; a string with angle brackets shows as text. CSRF still accepts the matching verb and rejects a mismatched one.

**Contradicts success.** Two templates that only differ by string vs block produce different control roles or names. A DELETE call submits as GET or as POST without an override. `remote: true` is invisible on the form but present on the button, or the reverse of what authors who followed the JavaScript guide expect. `disabled: true` can still be submitted. `false` and `nil` destinations collapse into each other without a documented choice. A string label executes markup. POST with protection on has no token, or GET has one.

**Suggests the framing is wrong.** Authors are not confused by calling forms; they are blocked by missing documentation only. Visitors’ failures are layout/CSS, not name, role, or disabled state. Token bugs dominate and the accessibility/predictability frame is incidental.

Revise the outcome if the real need is “document `form:` vs `data:`” rather than change behavior. Stop if the only remaining gap is the UrlHelper vs NavigationHelper name in docs.
