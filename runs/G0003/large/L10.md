**Block.** The claim is false: `Hash#compact_blank!` is not Ruby `Hash#compact`/`compact!`, and switching the predicate from `blank?` to `nil?` is an API break. Existing tests already fail that change.

## The contract

[`Hash#compact_blank!`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L265-L276) is documented and implemented as blank-value removal, not nil-only compaction:

```265:276:activesupport/lib/active_support/core_ext/enumerable.rb
  # Removes all blank values from the `Hash` in place and returns self.
  # Uses Object#blank? for determining if a value is blank.
  #
  # ```
  # h = { a: "", b: 1, c: nil, d: [], e: false, f: true }
  # h.compact_blank!
  # # => { b: 1, f: true }
  # ```
  def compact_blank!
    # use delete_if rather than reject! because it always returns self even if nothing changed
    delete_if { |_k, v| v.blank? }
  end
```

The same example and predicate are the public Hash contract on [`Enumerable#compact_blank`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L190-L209) and the Hash override at [lines 259–263](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L259-L263). [`Object#blank?`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L7-L24) is explicitly `false`, empty, or whitespace — not `nil?`.

Ruby `Hash#compact` is the nil-only method. Rails already exposes that separately as [`ActionController::Parameters#compact` / `#compact!`](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb#L1031-L1052) (`nil` values removed). `compact_blank` is the blank variant.

I ran both on this checkout. They are not equivalent:

```text
input: { a: "", b: 1, c: nil, d: [], e: false, f: true, g: " ", h: {}, i: 0, j: "x" }

compact_blank => {b: 1, f: true, i: 0, j: "x"}
compact       => {a: "", b: 1, d: [], e: false, f: true, g: " ", h: {}, i: 0, j: "x"}
```

Simulating `delete_if { |_key, value| value.nil? }` on the documented Hash fixture yields `{a: "", b: 1, d: [], e: false, f: true}`, which does not match `{ b: 1, f: true }`.

Empty and whitespace strings, empty arrays, and empty hashes follow the same split. Only `nil` is treated the same.

## Return value / identity

The implementation comment is the contract: use `delete_if`, not `reject!`, so the method **always returns `self`**, even when nothing is removed.

Observed on this checkout:

- `h.compact_blank!` with no blanks: returns `h` (`equal?` true), never `nil`
- `h.compact!` with no nils: returns `nil`
- `h.delete_if { … }`: always `self`
- `h.reject! { … }` with no deletions: `nil`

So `delete_if { nil? }` would keep bang identity vs current `compact_blank!`, but that is **not** Ruby `compact!` identity. Equating the two APIs on return value is also wrong. Hash tests do not currently pin this; Array/Hash comments do. Parameters `#compact!` *does* pin the Ruby `nil` return ([`mutators_test.rb:196-198`](file:///home/user/workspace/repo/actionpack/test/controller/parameters/mutators_test.rb#L196-L198)); Parameters `#compact_blank!` uses `reject!` and is a separate identity story.

## Verdict

**Block.** This is not a behavior-preserving refactor. It would make `compact_blank!` mean `compact` (nil-only) while still returning `self`. That collides with a documented, tested, family-wide `blank?` API.

Do not ship without reverting the predicate. If someone still wants nil-only Hash compaction, that method already exists: `Hash#compact!`.
