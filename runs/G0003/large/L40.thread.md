## Active Storage download-link expiration — product shaping brief

This is **documentation-shaped work** with a possible **behavior-change** follow-on. The job is to make expiration of download links predictable to application developers. It is not a request to add a new download mechanism.

Developer-facing surfaces in scope: `ActiveStorage::Blob#signed_id`, `ActiveStorage::Blob#url`, `rails_storage_proxy_url`, and `rails_storage_redirect_url`.

---

### Current observable behavior (this revision)

Evidence from source and tests at `ace84a2`. Claims below are what a developer or end user can observe. Implementation structure is cited only as the basis for those observations.

#### Permanent versus expiring signed blob identifiers

A blob identifier that is not given a lifetime does not expire. Tests resolve such an identifier to the same blob immediately after it is issued.

A blob identifier **can** be given a lifetime as a duration (`expires_in`) or as a clock time (`expires_at`). While that lifetime has not elapsed, lookup succeeds. After traveling two minutes past a one-minute lifetime, non-raising lookup returns nothing.

Tampered or otherwise invalid identifiers do not resolve. A purpose that does not match the purpose used at issue also does not resolve. Raising lookup treats expired, tampered, and purpose-mismatched identifiers as invalid signatures; a still-valid identifier whose blob has been destroyed is a missing record.

Attachments issue the same identifier as their blob. An older identifier format that signs only the blob’s id with purpose `blob_id` still resolves.

Download requests that carry an invalid or expired identifier receive **404 Not Found**. That is tested for blob proxy and blob redirect. Representation requests with an invalid blob identifier or invalid variation key also receive 404. Representation helpers embed the same expiring identifier, but representation tests do not exercise expiry.

Default application-wide lifetime for these Rails download URLs is unset. When that default is set to one minute, a helper-generated URL that does not pass its own lifetime succeeds immediately and 404s after two minutes.

#### Expiry of service URLs (`#url`)

`#url` is a **different clock** from the signed blob identifier.

On a **public** service, `#url` is a permanent location of the object. Public S3 and GCS tests fetch that URL and receive HTTP 200. On Disk, a public blob’s `#url` still serves the file.

On a **private** service, `#url` is short-lived. The published default is five minutes. Private S3/GCS URLs are signed query URLs. Private Disk URLs are signed Disk paths whose verifier carries that lifetime. Invalid Disk keys 404.

Redirect-mode download does not return the file. It 302s to `#url`. The 302 itself is cached privately for the same default five-minute service lifetime (`Cache-Control: max-age=300, private`).

#### Proxy versus redirect, and cache headers

**Redirect:** Rails URL → 302 to a service URL. Default Rails URL does not expire. Default service URL expires in five minutes. Redirect response: `max-age=300, private`.

**Proxy:** Rails URL → file bytes from the app. Default Rails URL does not expire. Successful blob proxy responses are `Cache-Control: max-age=3155695200, public, immutable`. Representation proxy is documented the same way; tests only assert `no-cache` on proxy errors, not the success header.

If the file is missing during proxy download, the response is 404 with `no-cache`. Other download errors are 500 with `no-cache`.

Range requests on blob proxy are a separate path; tests do not assert cache headers for them.

Published guidance tells developers to use proxy mode in front of a CDN because proxy responses instruct intermediaries to cache. The same guidance still calls signed identifiers “hard to guess but permanent.”

#### Public versus private services

Private files are documented as not for public use; the service URL should sit behind a stable Rails URL so the app can change storage without rewriting links. Public files’ service URLs are the public object location and do not carry the five-minute lifetime.

Redirect mode still emits a five-minute **private** cache on the 302 even when the target service URL is permanent (public).

#### Variants and previews

Variant and preview download URLs carry the blob’s signed identifier plus a variation key. Invalid either part → 404. Redirect representations 302 to a short-lived service URL for that derivative. Proxy representations stream the derivative. Helper-level `expires_in` / `expires_at` apply to the blob identifier inside those URLs; that path is in the URL helpers, not in representation controller tests.

#### Boundary timing

Tests use a one-minute lifetime and travel **two** minutes. They do not assert the exact expiry instant.

Verifier behavior in this revision treats a message as expired when current UTC time is **greater than or equal to** the stored expiry. So the instant of expiry is already expired. If both a clock time and a duration are supplied at issue, the clock time is the one stored.

Three clocks can be in force at once:

1. Signed Rails identifier (default: never).
2. Service URL (default: five minutes, skipped for public services).
3. HTTP `Cache-Control` on the Rails response (redirect: five minutes private; proxy success: ~100 years public immutable).

Those clocks are not required to match. A proxy response fetched before identifier expiry can be cached far beyond identifier expiry. A redirect 302 cached for five minutes can outlive a Rails identifier that expired after one minute; the cached `Location` remains the service URL.

#### What published docs already say

Docs call `url_for(attachment)` a **permanent** URL, say redirect/proxy controller URLs **never expire** by default, document per-URL `expires_in` and `config.active_storage.urls_expire_in`, and separately document five-minute service URL expiry. They warn that expiry is not access control: a URL shared before expiry remains usable for its full lifetime. They do not document `expires_at` on controller URLs, the exact expiry instant, or the interaction of proxy `public, immutable` caching with expiring identifiers.

### Shaped proposal

#### Problem frame

An application developer needs to give a user, email, CDN, or another system a download link and know when that link will stop working.

Today that is hard to know. “The download link” can mean a Rails URL, a storage-service URL, or a cached copy of either. Defaults say Rails URLs last forever and service URLs last five minutes. Helpers and config can expire the Rails URL. Public storage does not expire the service URL. Proxy success responses tell shared caches to keep the file for about 100 years. Redirect responses tell the browser to remember the 302 for five minutes. Invalid and expired identifiers look the same to the client (404). Variants add a second token that can fail independently.

The pain is not missing expiry knobs. It is **not being able to predict which clock applies**, or that a cached successful fetch can outlive the identifier that would now 404.

#### Desired outcome

A developer who generates a download link with `signed_id`, `#url`, `rails_storage_proxy_url`, or `rails_storage_redirect_url` can answer, without experiment:

- Whether this link is meant to last indefinitely or to die at a known time.
- Which of the Rails URL, the storage URL, and cached copies can still work after that time.
- What the user sees when the identifier is expired, tampered, or for a missing file.
- How proxy versus redirect, and public versus private storage, change that answer.
- How a variant or preview link differs from the original file’s link.

Success is qualitative: the developer chooses a link shape and lifetime on purpose, and later observation matches that choice.

#### Appetite

**Hypothesis (not supplied by a ticket):** one short cycle to make the existing surfaces predictable — primarily by stating the rules developers can rely on, and only changing runtime behavior if a current combination contradicts those rules (the likely candidate is proxy/redirect caching versus identifier expiry).

#### Scope

In:

- Permanent versus expiring signed blob identifiers, including duration versus clock-time lifetime.
- Service URL lifetime for `#url`, including public versus private storage.
- Proxy versus redirect responses and their cache headers.
- Tampered, purpose-mismatched, expired, and missing-blob identifiers as the user observes them.
- Variants and previews that use the same helpers.
- Boundary timing: still valid just before expiry versus no longer valid at/after expiry.
- Distinguishing “this URL died” from “this file is access-controlled.” Expiry remains a lifetime, not authorization.

Out of the main outcome unless it blocks predictability:

- Whether the developer-facing explanation lives in a guide, API docs, warnings, or examples. That is a delivery choice, not the outcome.

#### Non-goals

- New download or authorization products (authenticated controllers, per-user ACLs, signed cookies, token rotation products).
- Changing default lifetimes unless needed so the stated rules are true.
- Direct-upload PUT URLs, except to keep them from being confused with download links.
- CDN vendor setup beyond what a developer must know about cache headers versus identifier expiry.
- Encryption of identifiers. They remain tamper-evident, not secret.
- Exact HTTP status differentiation among expired, tampered, and missing, unless predictability requires it. Today those cases are 404 to the client.

#### Risks

- **Cache versus expiry contradiction.** If we tell developers that an expiring proxy URL dies after N minutes, but a CDN that saw it once may serve the file for years, the brief has failed. Either the rule must describe that cache, or that combination must stop occurring.
- **Redirect cache versus Rails expiry.** A one-minute Rails URL with a five-minute cached 302 can keep working via the stored `Location`.
- **Public storage.** Developers may assume `#url` always expires in five minutes. On public services it does not.
- **Two knobs, similar names.** Application-wide Rails URL lifetime versus service URL lifetime. Mixing them up is the current failure mode.
- **False security.** Expiry is still not access control. A leaked unexpired link works until it dies.
- **Compatibility.** Existing apps rely on never-expiring Rails URLs and five-minute private service URLs. Predictability should not silently shorten working links.
- **Exact boundary.** Tests never hit the expiry instant. If “valid until time T” means valid **at** T to some developers and dead **at** T to the verifier, docs that say “until” will mis-train people.

#### Behavioral outcomes

1. **A developer can issue a non-expiring Rails download identifier and treat it as valid until the blob is gone or the identifier is revoked by other means.**
2. **A developer can issue a Rails download identifier that dies after a duration or at a clock time, and after that time a new request with that identifier does not yield the file.**
3. **A developer can predict that `#url` on private storage dies on the service-URL clock (default five minutes), and `#url` on public storage does not.**
4. **A developer can predict proxy versus redirect: proxy returns the file and, on success today, invites long-lived shared caching; redirect returns a short-lived 302 to `#url` and invites short private caching of that 302.**
5. **A developer can predict that expired, tampered, and unreadable identifiers are indistinguishable to the end user: the file is not returned (404).**
6. **A developer can predict that a variant/preview link dies if its blob identifier dies or its variation token is invalid, independently of the original file’s service URL.**
7. **A developer can predict boundary timing: a request before expiry can succeed; a request at or after expiry cannot (hypothesis pending confirmation of the “at” instant as the product rule).**
8. **A developer is not led to treat expiry as login or ownership checks.**

#### Acceptance examples

Required unless marked illustrative.

**Permanent Rails identifier**
A developer issues a download identifier with no lifetime and puts it in `rails_storage_redirect_url` or `rails_storage_proxy_url`. Days later, a user who still has that URL can open it (blob still exists). Observation: file or redirect, not 404.

**Duration expiry**
A developer issues a Rails download URL with a one-minute lifetime. A user opens it immediately and gets the file or a redirect. After more than one minute, the same URL does not yield the file (404).

**Clock-time expiry**
Same as above with an absolute expiry one minute from now. Same observations.

**Default application lifetime**
The app sets a default Rails URL lifetime of one minute. A helper URL with no per-link lifetime behaves like the duration example.

**Private service URL**
A developer uses `#url` on private storage with the default lifetime. A user who opens that storage URL immediately can get the file. After the service lifetime, that same storage URL does not work. The stable Rails redirect URL still works and issues a **new** storage URL.

**Public service URL**
A developer uses `#url` on public storage. That storage URL still works after five minutes. Observation: not an expiring signed query URL.

**Tampered identifier**
A user changes characters in a Rails download URL. Observation: 404, not the file.

**Expired identifier**
A user retries a once-valid expiring Rails URL after its lifetime. Observation: 404, same as tampered from the user’s point of view.

**Missing file, valid identifier**
The identifier is still valid but the blob or bytes are gone. Observation: the file is not returned (404 on proxy when bytes are missing). Distinct internally from a bad signature; not distinct to the anonymous user.

**Proxy cache (boundary / contradiction)**
A developer issues an expiring **proxy** URL. A user (or CDN) fetches it successfully before expiry and stores `Cache-Control: public, immutable` with a ~100-year max-age. After identifier expiry, a new request to **origin** 404s. A cache that does not revalidate may still serve the old bytes. This example is required because it is the main predictability trap. The product rule must either make this expected or make it stop happening.

**Redirect cache (boundary)**
A developer issues a one-minute **redirect** URL. A browser caches the 302 for five minutes. After the Rails identifier would 404, following the cached `Location` may still hit a live service URL until that service URL dies. Same trap, redirect flavor.

**Variant**
A developer generates a proxy or redirect URL for a variant with a one-minute lifetime. Before expiry, the variant is returned or redirected. After expiry, 404. An otherwise valid URL with a garbage variation token 404s immediately.

**Just before versus at expiry (boundary)**
Illustrative until confirmed: a URL that expires at time T succeeds at T minus a small delta. At T it does not. If product language should be “valid through T” instead, this example changes.

**Not access control (counterexample)**
A developer expires a link in five minutes and emails it. Anyone with the email can download until expiry, including people who were never logged in. Observation: expiry did not enforce who may download.

#### Steering evidence

We would treat the outcome as **met** if a developer can pick one of the four surfaces, state a lifetime intent, and a later fetch matches that intent — including cache behavior they were told to expect.

We would **investigate** if:

- Apps that never opted into expiry start getting 404s on previously permanent Rails URLs.
- Developers following the brief still ship expiring proxy URLs in front of a CDN and are surprised by cached hits after expiry.
- Public `#url` is documented as expiring but still works indefinitely.
- Expired and tampered URLs start returning different statuses that clients or caches treat as cacheable success.

We would **reconsider the framing** if the real pain is “I need authenticated downloads,” not “I cannot tell when this URL dies.” In that case expiry documentation will not satisfy the user.

#### Open questions

1. Is the product rule “at expiry the link is already dead,” or “the link remains valid through the expiry instant”? Current verifier behavior is the former; tests never pin it.
2. Must an expiring **proxy** URL also stop being cacheable as `public, immutable`, or is “origin 404s, caches may still serve” an acceptable published rule?
3. Must redirect `max-age` follow the Rails identifier lifetime, the service URL lifetime, or stay independently five minutes?
4. Should `expires_at` be first-class in developer-facing explanation? Tests support it; the overview guide currently shows only `expires_in`.
5. Should missing blob versus bad signature stay indistinguishable to clients?
6. Appetite: explanation-only versus also changing cache/expiry combinations so the simple sentence “this link dies after N minutes” is true end-to-end.
