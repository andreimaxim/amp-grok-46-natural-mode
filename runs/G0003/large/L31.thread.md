## Assistant

**Problem frame:** When a controller callback already produces a response, Rails stops the rest of that request’s callback chain. App developers and Rails maintainers who later ask “why didn’t this action (or later callback) run?” often cannot tell, from outside the process, whether that stop was an intentional performed response, a quiet around-callback that never handed control inward, a skipped conditional callback, an exception, or a second render that blew up after execution continued.

This is a working brief for that observability question. It does not propose a log line, notification, API, or other mechanism.

### Problem

A `before_action` that renders, redirects, or otherwise performs a response is a supported way to finish a request early. The original action does not run. Later before-callbacks and after-callbacks do not run either.

That early finish is easy to confuse with other outcomes that look similar from the outside:

- an `around_action` that never yields, which also skips the action and later callbacks, without having performed a response
- a callback that never ran because of `only` / `except` / `if` / `unless`
- an exception before or after `yield` in an around-callback
- an action that already rendered or redirected and then tried to do it again, which raises `AbstractController::DoubleRenderError` instead of quietly stopping

The HTTP result of an intentional halt is often a normal 200 or 302. The miss is not “the client got the wrong page.” It is “a person inspecting the request cannot tell which of those stories happened.”

**Hypothesis, not a measured incident:** the existing halt signal is easy to miss or too coarse to separate those stories. Current tests only assert one halt phrase for one redirecting before-callback.

### Affected actors

- **App developers** writing auth, authorization, or other before-callbacks that render or redirect, then debugging why an action body, later before-callback, or after-callback did not run.
- **App developers** using around-callbacks who expect `yield` to run the action, or who rescue around the action.
- **Operators and maintainers** reading request traces and trying to decide whether a short-circuited action was intended.
- **Rails maintainers** deciding whether today’s external signals are enough, without changing when the chain actually stops.

End users of the app are not the primary audience. They already receive the rendered body or redirect.

### Current observable baseline

Evidence is from Action Controller callback, `performed?`, terminator, render/redirect/`head`, and `DoubleRenderError` source and tests, plus the one halt-log test. These are behavioral facts, not a design.

**What counts as “performed.”** After `render`, `redirect_to`, or `head`, the controller is performed. Abstract controllers treat a set response body as performed. Action Controller also treats a committed response as performed. A later `render`, `redirect_to`, or `head` in the same processing raises `DoubleRenderError`. That error’s message says a render or redirect does **not** stop Ruby from continuing inside the current method; a `return` is required if the rest of that method must not run.

**What the terminator does.** The `process_action` chain stops when a callback has run and the controller is then performed. After-callbacks are skipped when that happens, including prepended after-callbacks. Remaining before-callbacks and the action do not run.

**What a person can already observe.**

- The client still gets the callback’s body, status, or redirect. Tests for a rendering before-callback return that body and never set the action’s “I ran” flag. Tests for a redirecting before-callback return a redirect to the target URL and never run the original action or after-callbacks.
- A halt hook fires for a **before**-callback that stops this way. Instrumentation publishes `halted_callback.action_controller` with the filter. The log subscriber records `Filter chain halted as :redirector rendered or redirected`. The structured subscriber emits `action_controller.callback_halted` with that filter. The documented payload is only the filter.
- That phrase is asserted only for a redirecting `before_action`. It always says “rendered or redirected,” including for other performed responses such as `head`.
- A non-yielding around-callback does **not** raise. Later before-callbacks, the action, and after-callbacks do not run. Tests do not assert a halt log or halt event for that case. Source-level observation: the before-callback halt hook is what publishes today’s halt event; a non-yielding around is a different skip.
- An around-callback that raises **before** `yield` never runs the action; the exception leaves the request. An around-callback that raises **after** `yield` has already run the action; the exception then leaves. An around-callback that rescues the action can still render a success body. Guide text: after-callbacks run only after a successful action, not when an exception is raised in the cycle; code after `yield` can still run if the around-callback uses `ensure`.
- `only` / `except` / `if` / `unless` decide whether a callback runs at all. A callback that does not run does not halt the chain. Tests show no filter side effects on excluded actions, and both before and after conditionals run together on included actions.
- If the action itself renders twice, or renders and then calls `head`, the request fails with `DoubleRenderError`. That is not the callback terminator. The first response was produced; execution inside the action continued.

**What today’s signals do not establish.** They do not say whether the stop was a performed before-callback, a non-yielding around, a skipped condition, or an exception. They do not say render vs redirect vs `head`. They do not say which later work was skipped. They do not explain `DoubleRenderError` as “the chain halted” — that error is “execution continued after a response.”

### Desired outcomes

These are claims about what people should be able to observe. They do not require any particular new channel.

1. **Performed halt is recognizable as an intentional completed response.** When a before-callback renders, redirects, or otherwise performs, a person inspecting that request can tell the remaining chain was skipped because a response already existed, and can tell which callback did it.
2. **That story is distinguishable from other skips.** The same person can tell a performed halt apart from: an around-callback that never yielded; a callback that never ran because of conditions; an exception before or after `yield`; and an action that performed once and then tried to perform again.
3. **Successful early responses still look successful to clients.** Auth-style redirects and “render something else” before-callbacks keep returning their current HTTP result. Clearer observability must not turn those into client-visible failures.
4. **Confusing continued execution stays visible as an error, not as a quiet halt.** A second render/redirect/`head` still fails loudly. People can tell that failure apart from “the chain stopped before the action.”

### Behavioral examples

Required cases for agreement, not an exhaustive catalog.

**Rendering before-callback.** A controller has a before-callback that renders `"something else"`, an action that would render `"ran action"`, and an after-callback. On the action’s request, the body is `"something else"`. The action did not run. The after-callback did not run. A prepended after-callback also did not run. Today that is asserted as chain-breaking behavior; a halt log is not asserted for this render path.

**Redirecting before-callback.** A before-callback redirects to another action. The original request is a redirect to that URL. The original action and after-callbacks did not run. The target action is a later HTTP request, not a continuation of this chain. Today this is the path that also logs `Filter chain halted as :redirector rendered or redirected`.

**Non-yielding around-callback.** A before-callback runs, then an around-callback records that it did not yield and returns. A later before-callback, the action, and an after-callback do not run. The process does not raise. This is a stop **without** performing a response. Treating it as the same signal as a rendering before-callback would hide the difference; omitting it entirely leaves a silent skip.

**Exception before yield.** An around-callback raises before `yield`. The action body does not run. The exception is the external result. After-callbacks do not run as a successful completion.

**Exception after yield.** An around-callback yields, the action runs and renders, then the around-callback raises. The action did run. The external result is the exception, not a quiet halt. Nested around-callbacks raise the exception that occurs first (before-yield beats after-yield when both are present).

**Conditional callbacks.** A before-callback (and optionally an after-callback) is limited with `only: :show`. On `show`, those callbacks run and the action runs. On another action, those callbacks do not run and the action still runs. Nothing halted. Silence here is a skip, not a performed response.

**Action that attempts a second render.** An action renders `"hello"` and then renders `"world"` (or calls `head` after rendering). The request raises `DoubleRenderError` with the message that render/redirect may happen at most once and do not terminate method execution. The client does not get a quiet first body as a successful halt. This is continued execution after a response, not terminator skip of the action.

### Explicit non-goals

- Changing when a performed callback stops the chain, or when after-callbacks are skipped.
- Changing `only` / `except` / `if` / `unless`, skip-callback APIs, or callback order.
- Making `render` / `redirect_to` / `head` return from the surrounding Ruby method.
- Removing or softening `DoubleRenderError`.
- Treating non-yielding around-callbacks as performed responses, or forcing them to yield.
- Changing the HTTP body, status, or location of a successful performed halt.
- Broader logging of every callback start/finish, request tracing products, or performance instrumentation.
- Any commitment to a new log line, notification name, API, flag, or dashboard.

### External success signals

Use these to judge whether observability improved. They are questions a person could answer from outside the process, not a required implementation.

**Signals that the halt was intentional**

- The response is the callback’s render, redirect, or empty `head` status, and it is clear that the action body was not supposed to run.
- The responsible callback can be named.
- The request is still a completed success or redirect from the client’s point of view, not an exception page.

**Signals that the control flow is a different story**

- No response was performed, later callbacks and the action did not run, and the around-callback never handed control inward.
- A named callback has no side effects on this action because conditions excluded it, and the action still ran.
- An exception is visible, and it is clear whether it occurred before the action or after the action had already run.
- `DoubleRenderError` is visible, and it is clear that a response already existed when a second render/redirect/`head` was attempted.

**Evidence that would contradict success**

- Clients start receiving errors for ordinary auth redirects or “render something else” before-callbacks.
- People still cannot tell a performed halt from a non-yielding around or a conditional skip when they inspect a request that “didn’t run the action.”
- Halt information is so noisy that intentional early responses are indistinguishable from accidents.
- Second-render failures become quieter, or first-render-in-an-action-without-return becomes easier to miss.

**Evidence that the problem framing is wrong**

- Developers who miss an action already find the current halt phrase and filter name sufficient, and the remaining confusion is only `DoubleRenderError` inside action methods.
- The painful cases are almost all non-yielding around-callbacks or exceptions, which are not “callback performed a response.”
- The painful cases are almost all production volume of intentional redirects, where more halt detail would be noise.

Those last points should trigger revise-the-outcome or stop, not more halt machinery.

### Unresolved product questions

1. Is today’s halt event plus `Filter chain halted as … rendered or redirected` enough for before-callback performs, if people know to look for it?
2. Must performed halt, non-yielding around, conditional skip, exception, and `DoubleRenderError` each be distinguishable, or only performed halt vs everything else?
3. Should a performed `head` or render be distinguishable from a redirect, or is “this callback performed” enough?
4. Who must see the distinction without extra setup: development logs, production operators, instrumentation subscribers, or only people who already subscribe to controller events?
5. Are intentional high-volume halts (unauthenticated redirect to login) allowed to stay quiet, even if accidental halts stay hard to see?
6. Should an around-callback that renders after rescuing an action count as a performed halt, as exception handling, or as a normal render?
7. Is the maintainer goal limited to Action Controller request processing, or should Abstract Controller’s `performed?` (response body only) be part of the same external story?

I treated “clearer observability” as distinguishing those stories without changing halt behavior or requiring a specific new signal. If the real pain is only `DoubleRenderError` inside actions, or only silent around-callbacks, the desired outcomes above should shrink.
