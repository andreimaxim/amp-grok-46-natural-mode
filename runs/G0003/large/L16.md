`after_commit` does not fire from `save` or `destroy`. Those methods only enroll the instance and set action flags. The connection’s transaction object decides later, at its own finalize, whether this instance may run `:commit` or `:rollback` callbacks, and `on:` then filters which of those callbacks are visible.

```diagram
save! / destroy
  with_transaction_returning_status
    add_to_transaction          ──▶ Transaction#add_record
    remember_transaction_record_state
    Persistence (sets action flags)
         │
         ▼
outer TransactionManager#commit_transaction or #rollback_transaction
  before_commit_records          (commit path only, if run_commit_callbacks)
  DB COMMIT / ROLLBACK / RELEASE or ROLLBACK TO SAVEPOINT
  commit_records / rollback_records
    prepare_instances_to_run_callbacks_on
    record.committed! / rolledback!
      _run_commit_callbacks / _run_rollback_callbacks
        on: → transaction_include_any_action?
```

## Registration: `on:` becomes an `:if` predicate

[`after_commit`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L284-L287) / [`after_rollback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L316-L318) register on the `:commit` / `:rollback` chains. `after_create_commit`, `after_update_commit`, `after_destroy_commit`, and `after_save_commit` are the same API with `on:` filled in.

[`set_options_for_callbacks!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L341-L356) and [`set_callback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L322-L337) compile `on:` into:

```ruby
-> { transaction_include_any_action?(fire_on) }
```

`on:` must be `:create`, `:update`, and/or `:destroy` ([`ACTIONS`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L7); [`test_after_commit_callbacks_should_validate_on_condition`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L463-L466)). That lambda is the only action filter. An `after_commit` with no `on:` still needs the instance to be selected to run transactional callbacks at all.

[`transaction_include_any_action?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L544-L556) reads instance flags at callback time, not “which method was just called”:

| `on:` | true when |
|---|---|
| `:create` | `persisted? && @_new_record_before_last_commit` |
| `:update` | `!_new_record_before_last_commit && !destroyed? && _trigger_update_callback` |
| `:destroy` | `_trigger_destroy_callback` |

`:create` and `:update` are mutually exclusive. `:create` wins if the instance was new at the start of this transaction.

## Enrollment and action flags

[`save`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L381-L383) / [`destroy`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L377-L379) wrap persistence in [`with_transaction_returning_status`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L430-L447):

1. Open or join a connection transaction.
2. [`add_to_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L560-L564) → [`Transaction#add_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L198-L206). Strong list if this is the outermost transaction or the class has commit/rollback/before_commit callbacks; otherwise a `WeakMap`.
3. [`remember_transaction_record_state`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L468-L483) snapshots `@new_record` once per outer transaction and sets `@_new_record_before_last_commit` from that snapshot (unless `committed!` is already running). Nested saves only bump `level`.
4. Persistence sets `@_trigger_update_callback` in [`_update_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L937-L945) or `@_trigger_destroy_callback` in [`destroy`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L424) (`persisted? && destroy_row > 0`). Failed validation never sets them.
5. `false` status raises `ActiveRecord::Rollback`.

[`trigger_transactional_callbacks?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L449-L451) is the coarse gate used at finalize:

```ruby
(@_new_record_before_last_commit || _trigger_update_callback) && persisted? ||
  _trigger_destroy_callback && destroyed?
```

Invalid `save` enrolls the record but this is false, so neither `after_commit` nor `after_rollback` run ([`test_dont_call_any_callbacks_after_transaction_commits_for_invalid_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L121-L131)).

## Nested transactions: join vs `requires_new`

[`DatabaseStatements#transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L496-L528):

```ruby
if !requires_new && current_transaction.joinable?
  yield current_transaction.user_transaction   # no new object
else
  within_new_transaction(...)
end
rescue ActiveRecord::Rollback
  # swallowed
```

[`TransactionManager#begin_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L529-L556) sets the important bit:

```ruby
run_commit_callbacks = !current_transaction.joinable?
```

A new real/savepoint transaction runs commit callbacks only when its parent is not joinable — the application’s outer boundary. Inside a joinable parent, `requires_new` builds a [`SavepointTransaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L417-L469) with `run_commit_callbacks: false`.

```diagram
joinable parent (run_commit_callbacks: true)
  nested transaction                    ── join, enroll on parent
  nested transaction(requires_new: true)
      SavepointTransaction              ── run_commit_callbacks: false
        commit  → RELEASE SAVEPOINT, re-enroll records on parent
        rollback → ROLLBACK TO SAVEPOINT, run after_rollback now
  parent commit / rollback              ── only place after_commit runs
```

Finalize order ([`commit_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L616-L629) / [`rollback_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L633-L641)):

- Commit: `before_commit_records` → pop stack → DB `COMMIT`/`RELEASE SAVEPOINT` → `commit_records`.
- Rollback: DB `ROLLBACK`/`ROLLBACK TO SAVEPOINT` → pop → `rollback_records`.

If `run_commit_callbacks` is false, [`commit_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L311-L337) does not call `committed!`. It re-adds each record (and any connection-level after_commit blocks) to the parent, now current after the pop. Rollback always runs [`rollback_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L267-L284) on that transaction’s own list. Savepoints pass `force_restore_state: false` (`full_rollback?` is false); the real transaction passes true.

[`committed!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L402-L409) / [`rolledback!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L414-L421) then run the chains. `committed!` clears the trigger flags in `ensure` so they cannot leak into the next transaction ([`test_dont_call_after_commit_on_update_based_on_previous_transaction`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L147-L155)).

## Which instance runs: same row, several objects

[`prepare_instances_to_run_callbacks_on`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L361-L381) walks enrollment order. Keys use `==` / `hash` (same class + id). `unique_records` uses `__id__`, so each object is visited, but only the chosen candidate gets `should_run_callbacks: true`.

Default in this codebase is [`run_commit_callbacks_on_first_saved_instances_in_transaction = true`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L97) (first enrolled instance wins). New apps set it false (last save wins), with two extra rules:

- A later non-destroyed instance cannot replace a destroyed candidate.
- If an earlier candidate was new in this transaction, that create flag is copied onto the later instance so `after_create_commit` still matches.

## Callback order

`before_commit` is a `:before` chain: definition order.

`after_commit` / `after_rollback` follow [`run_after_transaction_callbacks_in_order_defined`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L357-L362) (false in this gem, true in new apps). When true, after-callbacks are prepended so they run in definition order; explicit `prepend: true` then runs first and reversed among themselves.

[`test_callbacks_run_in_order_defined_in_model_if_using_run_after_transaction_callbacks_in_order_defined`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L695-L715) (flag true), create:

`[1, 2, "prepend 2", "prepend 1", 3, 4, "save", "create"]`

Same model, flag false ([`test_callbacks_run_in_reverse_order_defined_in_model_if_not_using_run_after_transaction_callbacks_in_order_defined`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L718-L739)):

`[1, 2, "create", "save", 4, 3, "prepend 1", "prepend 2"]`

Rollback skips `before_commit` and runs only `:rollback`. Filters still apply: create → `"create"` not `"update"`; update → `"update"`; destroy → `"destroy"` ([`test_after_commit_on_multiple_actions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L614-L627)). A callback with `on: [:create, :update]` fires on either matching action.

## Concrete cases

**Create then update, same instance, one transaction.** `remember_transaction_record_state` keeps the original `new_record` snapshot, so `@_new_record_before_last_commit` stays true through the update. `_trigger_update_callback` is also set, but `:update` requires that create flag to be false. Observable at outer commit: `:create` (and `:save` / unfiltered). Not `:update`. That is the same rule as `after_create` saving again before commit ([`test_only_call_after_commit_on_create_and_doesnt_leaky`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L224-L232)). A `save!` inside `after_create_commit` is a *new* transaction after `COMMIT`; `_committed_already_called` forces the create flag off, so that second save is `:update` ([`test_save_in_after_create_commit_wont_invoke_extra_after_create_commit`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L215-L221)).

**Saved only in an inner joined transaction.** No new transaction object; `add_record` hits the parent. Inner `ActiveRecord::Rollback` is swallowed and does not roll the parent back ([docs in `transactions.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L137-L148)). After-commit runs once, at the outer boundary, with the flags from that save.

**Inner `requires_new` rolled back, outer rescued.** Savepoint `ROLLBACK TO`; `rollback_records` on the savepoint only. Inner `Rollback` is swallowed. The inner record’s `after_rollback` (action filter from that inner save) runs immediately; it is not re-enrolled. Outer commit still runs `after_commit` for records that remained on the parent ([`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L329-L353): outer record `:commit`, inner-only record `:rollback`). Two inner rollbacks of the same instance both fire `after_rollback`; the outer save still gets one `after_commit` ([`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint_when_release_savepoint_fails`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L355-L375)).

**Inner savepoint released, then outer rollback.** Inner commit with `run_commit_callbacks: false` only `RELEASE SAVEPOINT` and moves records to the parent. No `after_commit` yet ([`test_only_call_after_commit_on_top_level_transactions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L241-L251)). Outer `Rollback` then runs `after_rollback` on those re-enrolled records, with the original action flags. Savepoint release does not freeze the action as “committed.”

**Destroy of a newly created record.** Never-saved: `destroy` sets `@_trigger_destroy_callback` only if `persisted?`, so the gate is false and nothing runs ([`test_no_after_commit_on_destroy_after_transaction_commits_for_destroyed_new_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L207-L213)). Create then destroy of the same instance in one transaction: `_trigger_destroy_callback` is true and `destroyed?` is true, so the coarse gate passes, but `:create` requires `persisted?` and `:update` rejects `destroyed?`. Observable: `:destroy` (and unfiltered). Not `:create`.

**Several in-memory instances of one row** ([`CallbacksOnMultipleInstancesInATransactionTest`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L907-L1024)), last-saved config (`false`):

| Sequence | Observable |
|---|---|
| create `A`, other instance updates to `B` | `:create` on the updater, title `B` (create flag copied). Not `:update`. |
| two updates, titles `two` then `three` | `:update` on the last instance, title `three` |
| update then destroy | `:destroy` on the destroyed instance |
| destroy then update on another instance | `:destroy` on the destroyed instance; later update is skipped |

First-saved config (`true`) keeps the first enrolled instance and does not copy the create flag forward, so create-then-update reports `:create` with title `A`. Destroy still wins over a later update on either setting, because a destroyed candidate is not replaced by a non-destroyed one.

I did not run create-then-update / create-then-destroy on one instance as extra tests; those two follow `transaction_include_any_action?` as written. The nested, savepoint, never-saved destroy, order, and multi-instance cases above were run in this checkout (14 tests, 0 failures).
