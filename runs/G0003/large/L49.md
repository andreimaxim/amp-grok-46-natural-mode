I validated current reload behavior from source and tests. Here is a first-draft maintenance brief — please correct anything that does not match the intended contract.

**Kind of work:** maintenance of the development route-reload failure contract. Successful routing of valid files is not supposed to change. What must become determinate is what a developer can observe after one watched route file becomes invalid Ruby, and when a later correction is used.

**Evidence basis:** I read `Rails::Application::RoutesReloader`, `app.routes_reloader`, engine registration of route sets and external draw paths, the request reloader hook, `config.file_watcher`, and `config.reload_classes_only_on_change`. I also read the matching tests and the configuring guide. I did not run tests or reproduce this in a running app. Claims about HTTP status after a failed reload are therefore inferences from that code, not observed request results.

---

**Problem frame**

A developer in development, with reloading enabled, edits one application or mounted-engine route file — `config/routes.rb` or a file under a watched `config/routes` draw directory — so that it is no longer valid Ruby.

They still need to know two things without restarting the server:

1. Whether routes that already worked are still answering requests.
2. When a saved correction will be the definition used.

Today that is not something they can tell from the next request alone.

**Current behavior (from source and tests)**

On a reload, every registered route set is cleared, then every registered route file is loaded, then the sets are finalized. Application and engine route files share one `app.routes_reloader`. External draw directories are watched as `.rb` trees; they are pulled in when a parent route file `draw`s them.

A failed `execute` on first load leaves routes unloaded; a waiter retries. That is tested. A later failed reload restores the previous “loaded” flag even though the sets were already cleared. That is in `reload!` / `execute`; there is no request-cycle test for it.

The request cycle only runs that execute when the application reloader decides a reload is due. With `config.reload_classes_only_on_change` true (default), that decision includes `routes_reloader.updated?` from `config.file_watcher`. Both shipped watchers mark the change consumed when `execute` runs, including when the load then raises. With the flag false, every request reloads.

Inferred, unexecuted request outcomes:

- First request after the bad save: the syntax/load error surfaces (development shows the exception; Reloader sits inside DebugExceptions).
- A following request with no new save, default flag true: the watcher no longer reports an update, so routes are not loaded again. The developer may get a 404 or a partial table rather than the same error, and rather than the old routes.
- A following request with the flag false: reload is attempted again from disk, so the same error should repeat until the file is valid.

No integration test covers invalid Ruby in an app or engine route file across boot → erroring request → next request → correction.

**Actors**

- Application developer editing the host app’s route file or an external draw file while the dev server is running.
- Engine developer editing a mounted engine’s route file or draw file in that same running app.

**Pain**

One invalid file makes the whole watched routing surface unpredictable. Old routes may already have been cleared. The error may appear once and then look like “missing routes.” A correction may need another save, another request, or a restart, and app vs engine vs draw-file edits do not obviously share one rule. `reload_classes_only_on_change` changes retry timing without documenting that for this failure.

**Desired observable outcomes**

These are the maintenance target: a determinate developer-visible contract at `RoutesReloader` / `app.routes_reloader`, the registered route sets, external draw paths, and `config.file_watcher`. They are not an implementation.

1. After a route-file syntax or load error, the developer can tell that the previous successful routing table is not still in effect (or, if the intended contract is to keep it, that it is still in effect). The brief does not choose which of those two is required; it requires that the result be stable and visible. **Open: preserve last good table vs empty/erroring table.**
2. A failed reload does not look like success on a later request that did not load a valid table.
3. Once the file is valid Ruby again, the next development request that is supposed to reload routes uses the corrected definition for every registered route set.
4. An invalid file in the application, a mounted engine, or a watched external draw path is the same observable failure for the shared reloader.
5. Deleting a watched route file has a determinate visible result (error, or that file’s routes gone and the rest still drawn), not an unexplained mix of old and missing routes.
6. Outcomes 1–5 hold for `config.reload_classes_only_on_change` true and false. Retry timing may differ; “did old routes survive?” and “did the correction take effect?” must not be ambiguous in either mode.
7. Valid route files that are never broken keep their current successful boot and reload behavior.

**Non-goals**

- Changing production or other non-reloading environments.
- Changing successful matching, helpers, or engine mounting when every watched file is valid.
- Changing class/i18n reload except as it already gates whether a request runs the routes reloader.
- New developer UI beyond making this failure and recovery observable on the request (or existing exception page).
- Console `reload!`, `bin/rails routes`, and eager-load boot, except as open questions below.
- A prescribed implementation, internal structure, or test design.

**Acceptance examples**

Required unless marked illustrative.

**Initial boot**

Given development, reloading on, all watched app and engine route files valid.
When the app boots and the first request (or first use of lazy routes) runs.
Then those routes answer as they do today. `app.routes_reloader` is the process’s reloader and uses `config.file_watcher`. Engine route sets and external draw directories are already registered.

**Syntax/erroring reload**

Given a successful boot as above.
When the developer saves invalid Ruby in one watched file (host `config/routes.rb`, engine `config/routes.rb`, or a drawn file under a watched `config/routes` directory) and makes a request that triggers reload.
Then that request does not silently keep serving the pre-edit table as if the save did nothing. The failure is visible as a load/syntax failure attributable to that file. Other still-valid files do not get a separate private success; they share this reload.

**The next request (no new save)**

Given the erroring reload already happened and the broken file is unchanged.
When the developer requests again.

- Flag true: it is defined whether they see the same failure, an empty/partial table, or the last good table — and it is not a different surprise each time.
- Flag false: same determinate rule, even if this mode retries from disk every request.

**Correction**

Given the file is now valid Ruby and saved.
When the next request that should reload routes runs.
Then the full corrected table is used: host, engines, and draw files together. No restart is required. A valid correction is not ignored because the failed execute already consumed the previous watcher update.

**Simultaneous application/engine changes**

Given the developer saves the host route file and a mounted engine route file before the next request, and one of them is invalid.
When that request reloads.
Then there is one visible failure for the shared reloader, not host success plus engine old routes (or the reverse). After both files are valid and saved, the next reload-capable request uses both new definitions.

**Deleted route files**

Given a watched `config/routes.rb` or a drawn external `.rb` is deleted (or a `draw` still names a missing file).
When the next reload-capable request runs.
Then the developer sees a determinate outcome: a missing-file error, or that file’s routes gone and remaining files drawn. Deleted files do not leave stale routes with no signal, and do not fail in a way that blocks later correction after the file is restored.

**`config.reload_classes_only_on_change` true vs false**

Given the same invalid file, then the same correction.

- True (default): reload is driven by watcher updates on registered paths and external draw directories. Failed consume-and-raise does not strand the developer with “error once, then unexplained 404s, and a fix that never applies.”
- False: every request may reload from disk. Invalid stays visibly invalid until the file is valid; the correction is used on the next request.

The two modes may differ in how soon a retry happens. They must not differ in whether old routes secretly survived, or whether a saved valid file is ignored.

**Steering evidence**

Investigate or stop if:

- A valid-only edit still hot-reloads on the next request in both flag modes (success path regressed).
- After invalid Ruby, a refresh with no new save sometimes uses old routes and sometimes does not.
- Fixing the file and requesting again still serves the pre-error table or an empty table until restart.
- An invalid engine or draw file leaves the host table looking updated and healthy.
- Deleting then restoring a route file does not recover without restart.
- Switching `file_watcher` between `FileUpdateChecker` and `EventedFileUpdateChecker` changes the failure/recovery contract.

Reconsider the framing if developers actually need the last good table to stay live during a typo (that is a behavior change, not this maintenance), or if the real pain is only exception-page quality.

**Open behavioral questions**

These change the contract; they are not implementation choices.

1. After a failed reload, should the last good table stay usable, or should routing stay failed until a valid load completes? Source currently clears first; that is not an accepted requirement.
2. After the erroring request, should a refresh with no new save repeat the error, or is “error once, then a non-success empty table” acceptable if it is documented and stable?
3. Must a correction take effect on the next request even if the watcher already recorded the bad save, or is an extra save/touch acceptable if that is explicit?
4. If host and engine files change together and only one is invalid, is “all route sets fail together” the contract, or should the valid side stay on its last good table? (Conflicts with a global clear-first reload.)
5. Does deleting `config/routes.rb` while routes were also declared in the application class stay the special case the engine reload test already describes?
6. Same contract for console `reload!` and `bin/rails routes`, or only the HTTP request cycle?
7. Same contract in `test` when reloading is on, or development only?
8. If `file_watcher` is a custom class whose `updated?` is always false, is “routes never retry after a failed load” accepted, as with the existing class-reload test?

**Evidence still to collect**
