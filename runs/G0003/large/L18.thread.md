### Case-by-case (this revision)

| Shape | Preserved if `ids` is only `pluck(*primary_key)`? |
|---|---|
| Unloaded `includes` / `eager_load` of a **collection** | **No** — duplicate parent ids. Existing tests already fail. |
| Same, **composite PK** | **No** — same fan-out. No existing test. |
| `async_ids` on that shape | **No** — `async.ids` keeps `@async` and still hits the group path today (`Promise::Complete` with unique ids). `async_pluck` duplicates. |
| Loaded relation with includes | Yes — both use in-memory records (`records.pluck`). |
| `preload` (no join) | Yes — `has_include?` is false. |
| `group(primary_key)` already present | Yes — grouping already collapses rows. |
| Order by a non-PK column | Yes on this sqlite fixture (`includes(:comments)` does not fan out). The group path exists so PG does not require `ORDER BY` columns in a `DISTINCT` select (#48080 / `test_ids_with_includes_and_non_primary_key_order`). Replacing group with bare pluck reintroduces duplicates whenever the ordered association actually multiplies rows. |
| `limit` / `offset` | Existing empty/offset tests still pass. Not generally safe: [`apply_join_dependency`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/finder_methods.rb#L452-L491) rewrites limit via `distinct_relation_for_primary_key`, then **keeps the collection join**, so `Company.includes(:contracts).where(id: company.id).limit(1)` was `ids=[1]` vs `pluck=[1, 1]`. |
| Contradictory `where(id: [])` | Yes — `pluck` returns `[]` / `Promise::Complete` with no query. |
| `skip_query_cache!` | Yes — both end in `pluck`’s `skip_query_cache_if_necessary`. Existing `#skip_query_cache! for #ids` still passed after the simplification. |

`Relation#none` is already identical (`pluck` short-circuits `@none`); it is not the interesting case.
