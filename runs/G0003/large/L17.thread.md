## Assistant

`strict_loading!` only stores two ivars on the record. Enforcement happens later, when an association actually tries to hit the database.

### What `strict_loading!` stores

[`ActiveRecord::Base#strict_loading!`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L736-L743) is just:

```ruby
def strict_loading!(value = true, mode: :all)
  unless [:all, :n_plus_one_only].include?(mode)
    raise ArgumentError, "The :mode option must be one of [:all, :n_plus_one_only] but #{mode.inspect} was provided."
  end

  @strict_loading_mode = mode
  @strict_loading = value
end
```

A new record starts from class defaults in [`init_internals`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L861-L862): `@strict_loading` from `strict_loading_by_default` (false), `@strict_loading_mode` from `strict_loading_mode` (`:all`). That default mode is what [`test_default_mode_is_all`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L125-L128) asserts.

`strict_loading?` is only `@strict_loading`. Mode is separate: `strict_loading_n_plus_one_only?` / `strict_loading_all?` look at `@strict_loading_mode` even if loading is currently off.

### The two modes, in one sentence

- **`:all`**: any lazy load of an unloaded association on this record is a violation.
- **`:n_plus_one_only`**: this record may lazy-load; a loaded `has_many` child is then marked `strict_loading!` (mode `:all`), so the *next* hop is the violation.

```diagram
:all
  parent.strict_loading!(mode: :all)
    parent.has_many / belongs_to   ──lazy──►  violation
    preloaded association          ──read──►  ok (already loaded)

:n_plus_one_only
  parent.strict_loading!(mode: :n_plus_one_only)
    parent.belongs_to              ──lazy──►  ok; child.strict_loading!(false, mode: :n_plus_one_only)
    parent.has_many                ──lazy──►  ok; each child.strict_loading!  (mode :all)
      child.anything               ──lazy──►  violation
```

### Where a violation is decided

Almost every lazy load funnels through [`Association#find_target`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L257-L284):

```text
record.assoc / record.assoc.to_a / record.assoc.first
  Association#reader
    SingularAssociation → reload → load_target → find_target
    CollectionAssociation → CollectionProxy → load_target → find_target
      Association#violates_strict_loading?
        yes → Base.strict_loading_violation!(owner: owner.class, reflection:)
        no  → query, then set_strict_loading(record) on each loaded child
```

[`violates_strict_loading?`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L235-L245) is the gate:

```ruby
def violates_strict_loading?
  return unless find_target?          # already loaded → not a violation
  return if @skip_strict_loading      # writers / concat / replace
  return unless owner.validation_context.nil?

  return reflection.strict_loading? if reflection.options.key?(:strict_loading)

  owner.strict_loading? && !owner.strict_loading_n_plus_one_only?
end
```

That last line is the mode split:

- `:all` → `strict_loading? && !false` → **true** → lazy load is a violation
- `:n_plus_one_only` → `strict_loading? && !true` → **false** → lazy load is allowed on *this* record

If the association declared `strict_loading: true` / `false`, that option wins and the owner’s mode is ignored. That is how `strict_loading_mentor` raises even without `developer.strict_loading!`, and how `strict_loading_off_mentor` does not raise under `strict_loading_by_default`.

Two extra entry points do **not** go through `find_target` and therefore check the same predicate themselves:

- [`CollectionProxy#pluck`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/collection_proxy.rb#L725-L728)
- [`CollectionAssociation#find_from_target?`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/collection_association.rb#L303-L307), which is true when `owner.strict_loading? && owner.strict_loading_all?`. That forces `first` / `last` / `take` to `load_target` the whole collection. In `:all` mode that load is itself a violation (`dev.audit_logs.first` raises). In `:n_plus_one_only` it stays false, so `first` issues a `LIMIT` query and does not mark the proxy loaded ([`test_strict_loading_n_plus_one_only_mode_does_not_eager_load_child_associations`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L113-L122)).

### How the flag reaches children

After a permitted load, [`Association#set_strict_loading`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L123-L128) writes state onto each child:

```ruby
def set_strict_loading(record)
  if owner.strict_loading_n_plus_one_only? && reflection.macro == :has_many
    record.strict_loading!                              # enable, mode defaults to :all
  else
    record.strict_loading!(false, mode: owner.strict_loading_mode)  # disable, keep mode
  end
end
```

Called from:

- the statement-cache path in `find_target`
- [`AssociationRelation#exec_queries`](file:///home/user/workspace/repo/activerecord/lib/active_record/association_relation.rb#L46-L50) (scoped association queries, including `collection.first` when the collection is not fully loaded)

The `strict_loading_n_plus_one_only?` check is **mode-only**. A belongs_to target can have `strict_loading? == false` and still pass `:n_plus_one_only` down, so a later `has_many` off that target still marks *its* children strict.

Preload / eager load uses different writers:

- Relation load: [`exec_queries`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb#L1490) does `record.strict_loading!(strict_loading_value)` on the root rows.
- Preloader: [`cascade_strict_loading`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/preloader/association.rb#L310-L312) copies the parent relation’s `strict_loading_value` onto the association scope, so preloaded children also come back strict.
- JOIN eager load: [`JoinDependency#construct_model`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/join_dependency.rb#L279-L297) calls `m.strict_loading!` from the relation flag, and again if the association scope itself was `-> { strict_loading }`.

A preloaded association does not raise on read because `find_target?` is false once `loaded?` is true.

#### 3. Preloaded association — no violation

[`test_does_not_raise_on_eager_loading_a_has_many_relation_if_strict_loading_by_default`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L618-L631), [`test_strict_loading_with_has_many`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L294-L308), [`test_preload_audit_logs_are_strict_loading_because_parent_is_strict_loading`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L379-L389):

```ruby
dev = Developer.includes(:audit_logs).strict_loading.first
dev.strict_loading?                      # true (relation flag applied to root)
dev.audit_logs.to_a                      # already loaded → no violation
dev.audit_logs.all?(&:strict_loading?)  # true (cascaded onto children)
dev.audit_logs.pluck(:id)                # also ok; find_target? is false
```

`includes` / `preload` / `eager_load` mark the association `loaded!` before the accessor runs, so `violates_strict_loading?` returns on `find_target?`.

#### 4. `has_many :through` and middle records (`:all`)

[`Developer`](file:///home/user/workspace/repo/activerecord/test/models/developer.rb#L84-L85) has `has_many :contracts` and `has_many :firms, through: :contracts`. [`test_strict_loading_with_has_many_through_cascade_down_to_middle_records`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L326-L344):

```ruby
dev = Developer.strict_loading.includes(:firms).first

dev.firms            # ok: firms preloaded
dev.firms.first.contracts.first  # raises: Firm is strict_loading; :contracts not loaded
dev.contracts.first  # raises: through middles were NOT associated onto dev
dev.ship             # raises: unrelated, not preloaded
```

The through preloader loads contracts only as a join to firms, with `associate_by_default: false` ([`ThroughAssociation#through_preloaders`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/preloader/through_association.rb#L116-L118)). So `dev.contracts` stays unloaded. Firms themselves are strict because `cascade_strict_loading` copied the parent relation’s strict-loading scope. `firm.contracts` is a fresh lazy load → violation.

#### 5. Validation-time association access

[`violates_strict_loading?`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L240) bails unless `owner.validation_context.nil?`. That is the implementation of the comment on `strict_loading!`: strict loading is disabled during validation.

[`test_strict_loading_is_ignored_in_validation_context`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L202-L210): creating `AuditLogRequired` (belongs_to developer, `required: true`) does not raise even though `Developer` is `strict_loading_by_default`.

[`test_strict_loading_with_reflection_is_ignored_in_validation_context`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L213-L220): `developer.required_audit_logs.build(...)` then `developer.save!` also does not raise.

#### 6. Parent → children → each child’s association in `:n_plus_one_only`

This is the mode’s whole reason for existing. [`test_strict_loading_n_plus_one_only_mode_with_has_many`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L56-L86):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)

developer.projects.to_a
## no raise: violates_strict_loading? is false because n_plus_one_only
## each project: set_strict_loading → project.strict_loading!   (mode :all)

developer.projects.all?(&:strict_loading?)  # true

developer.projects.detect { |p| p.id == project.id }.firm
## raise: Project is strict_loading in :all; belongs_to :firm is lazy
```

Same pattern through a belongs_to in [`test_strict_loading_n_plus_one_only_mode_with_belongs_to`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L88-L111):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)

developer.ship.parts.to_a          # no raise
developer.ship.strict_loading?     # false  (singular: strict_loading!(false, mode: :n_plus_one_only))
developer.ship.parts.all?(&:strict_loading?)  # true
developer.ship.parts.first.trinkets.to_a      # raise
```

Walk of that second example:

1. `developer.ship` is `has_one`, not `has_many` → `set_strict_loading` disables strict loading on the ship but **copies** `:n_plus_one_only`.
2. `ship.parts` is `has_many`. Owner mode is still `:n_plus_one_only`, so no violation on the load; each `ShipPart` gets `strict_loading!` (enabled, mode `:all`).
3. `part.trinkets` is a lazy `has_many` on a `:all` record → violation.

That is “one parent, its children, then each child’s association”: the first collection load is cheap on purpose; the per-child load is the N+1.

HABTM `:projects` is implemented as `has_many :through`, so `reflection.macro == :has_many` and the same cascade applies ([`has_and_belongs_to_many`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations.rb#L2037-L2063)).

#### Disabling on an instance

[`test_strict_loading!`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L45-L49):

```ruby
developer.strict_loading!(false)   # @strict_loading = false; mode reset to default :all
developer.audit_logs.to_a          # no raise
```

`strict_loading!(false)` still assigns `mode:` (default `:all`). Only `@strict_loading` gates `violates_strict_loading?` for owner-based checks. Relation-level off switch is `Developer.strict_loading(false)`, applied after instantiate in `exec_queries`.

#### Invalid mode

No test covers it; the method does:

```ruby
developer.strict_loading!(mode: :nplusone)  # ArgumentError
```

Anything other than `:all` or `:n_plus_one_only` raises before the ivars are written.
