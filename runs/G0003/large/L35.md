`stream_from` and `broadcast` are two ends of one named pubsub queue. The server encodes a payload onto that name; each subscribed channel handler decodes (or not) and either retransmits to the WebSocket or runs a user callback. Confirmation to the client waits until pubsub subscribe succeeds.

```diagram
Client subscribe
      │
      ▼
Channel#subscribe_to_channel
      │  subscribed → stream_from
      │
      ▼
pubsub.subscribe(name, handler, on_success)
      │                         │
      │                         ▼
      │              ensure_confirmation_sent
      │              → { type: "confirm_subscription" }
      │
App: server.broadcast(name, message, coder:)
      │
      ▼
coder.encode? → pubsub.broadcast(name, encoded)
      │
      ▼
handler.call(encoded)
      │
      ┣━ default: decode → transmit → socket JSON envelope
      ┗━ user callback: optional decode → worker pool → callback
```

## Default handler vs user callback

Handler construction is in [`worker_pool_stream_handler` / `stream_handler`](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L163-L223).

```163:223:actioncable/lib/action_cable/channel/streams.rb
        def worker_pool_stream_handler(broadcasting, user_handler, coder: nil)
          handler = stream_handler(broadcasting, user_handler, coder: coder)

          if user_handler
            -> message do
              connection.perform_work handler, :call, message
            end
          else
            handler
          end
        end
        ...
        def default_stream_handler(broadcasting, coder:)
          coder ||= ActiveSupport::JSON
          stream_transmitter stream_decoder(coder: coder), broadcasting: broadcasting
        end
```

| | Default (`stream_from "room"`) | User callback (`stream_from "room" { \|msg\| ... }`) |
|---|---|---|
| Inner handler | `stream_decoder` then `stream_transmitter` | `stream_decoder(user_handler, coder:)` only |
| Auto-transmit to the client | Yes, `transmit message, via: "streamed from …"` | No. The block must call `transmit` itself (docs at [streams.rb L54–L72](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L54-L72)) |
| `coder: nil` | Forced to `ActiveSupport::JSON` (`coder \|\|= …`) | No decoder; raw pubsub payload |
| Worker pool | Not used | Wrapped in `connection.perform_work` |

The comment on `worker_pool_stream_handler` says it always wraps; the `if user_handler` branch does not. Tests pin that split:

- [`"user supplied callbacks are run through the worker pool"`](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L368-L378) — after `server.broadcast "channel", {}`, `Thread.current[:ran_callback]` stays unset on the event-loop thread.
- [`"default stream handlers do not run through the worker pool"`](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L380-L392) — `socket.perform_work` is not called, and the client still gets `{ "foo" => "bar" }`.

`perform_work` is [`Socket#perform_work` → `Worker#async_invoke`](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L56-L59). The worker posts to a thread pool and rescues `Exception` ([worker.rb L52–L66](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L52-L66)). Default handlers run on the pubsub callback thread (async executor in tests), not that pool.

## `coder: nil` vs JSON vs server custom encoding

Three independent coder sites:

1. **Broadcast coder** (default JSON): `coder.encode(message)` or skip if `coder` is nil.
2. **Stream coder** (default nil in the method signature): applied only in `stream_decoder`.
3. **Socket coder** (always JSON in tests): wraps `{ identifier:, message: }` for the WebSocket.

Default round-trip, which the default-handler test observes:

```text
broadcast({ foo: "bar" }, coder: JSON)
  → '{"foo":"bar"}' on the pubsub queue
default_stream_handler (coder ||= JSON)
  → decode to { "foo" => "bar" }
  → Channel#transmit → Connection#transmit
  → Socket#encode of { identifier, message: { "foo" => "bar" } }
```

User callback + `coder: nil` (the method default, [streams.rb L84–L90](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L84-L90)): `stream_decoder` returns the callback unchanged ([L211–L213](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L211-L213)). The callback sees the **encoded** pubsub string, not a Hash, unless it asked for a decoder.

User callback + `coder: ActiveSupport::JSON`: decode first, then the callback (docs example at [L63–L72](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L63-L72)).

Server-side custom encoding is the `"custom encoder"` test ([stream_test.rb L356–L366](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L356-L366)):

```356:365:actioncable/test/channel/stream_test.rb
    test "custom encoder" do
      run_in_eventmachine do
        open_connection
        subscribe_to identifiers: { id: 1 }

        server.broadcast "test_room_1", { foo: "bar" }, coder: DummyEncoder
        wait_for_async

        assert_equal({ "foo" => "encoded" }, socket.last_transmission.fetch("message"))
```

`DummyEncoder.encode` always returns `'{ "foo": "encoded" }'` ([L38–L41](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L38-L41)). `ChatChannel` still subscribes with `pick_coder(nil)` → `ActiveSupport::JSON` ([L17](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L17), [L26–L34](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L26-L34)). So the stream decoder JSON-parses the custom-encoded string; `DummyEncoder.decode` is not on this path. The client message is `{ "foo" => "encoded" }` because that is what JSON decode of the dummy payload produces.

`pick_coder("none")` / `"custom"` exist in the test helper but no test in this revision passes those params into `subscribe_to`.

### Encode / decode failures

There is **no** dedicated rescue in `Broadcaster#broadcast` or `stream_decoder`. Behavior is therefore:

- **Encode failure** on `server.broadcast` raises to the caller. The `broadcast.action_cable` notification still wraps the encode ([broadcasting.rb L58–L60](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L58-L60)).
- **Decode failure on the default handler** raises on the pubsub callback thread (`SubscriberMap#invoke_callback`). Not worker-pooled, not rescued in Streams.
- **Decode failure on a user callback** runs inside `Worker#invoke`, which logs and calls `handle_exception` if the receiver defines it ([worker.rb L58–L66](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L58-L66)). The client gets no message from that broadcast.

No test in this revision covers a raising coder. Socket-level incoming JSON failures are a different path (`Socket#dispatch_websocket_message` rescue at [socket.rb L79–L87](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L79-L87)) and do not apply to stream decode.

`coder: nil` on broadcast plus a default stream handler is a mismatch: pubsub carries a Hash, then `ActiveSupport::JSON.decode` is asked to decode it. That combination is also untested here.

## Deferred subscription confirmation

The counter starts at 1 so confirmation waits for `subscribe_to_channel` to finish ([base.rb L168–L172](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L168-L172), [L253–L264](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L253-L264)):

```text
counter = 1
each stream_from → increment
pubsub on_success → ensure_confirmation_sent → decrement
subscribe_to_channel end → ensure_confirmation_sent → decrement
transmit confirmation when counter == 0 and not rejected
```

`transmit_subscription_confirmation` is idempotent via `@subscription_confirmation_sent` ([base.rb L322–L331](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L322-L331)). Evidence:

- [`"stream_from subscription confirmation"`](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L139-L147) — last transmission is `{ "type" => "confirm_subscription" }`.
- [`"subscription confirmation should only be sent out once"`](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L149-L160) — two `send_confirmation` calls, one wire message.
- [`"… once with multiple stream_from"`](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L394-L404) — `MultiChatChannel` streams two names, still one confirmation.

On `SuccessAdapter`, the success callback runs inside `subscribe` ([test_adapter.rb L89–L92](file:///home/user/workspace/repo/actioncable/test/stubs/test_adapter.rb#L89-L92)), so confirmation is immediate. On `Async`, it is posted to the executor ([subscriber_map.rb L67–L69](file:///home/user/workspace/repo/actioncable/lib/action_cable/subscription_adapter/subscriber_map.rb#L67-L69)); tests `wait_for_async`.

If the subscription was rejected, `ensure_confirmation_sent` returns without sending ([base.rb L253–L254](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L253-L254)).

## Stopped streams

`on_unsubscribe :stop_all_streams` ([streams.rb L80–L82](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L80-L82)). `unsubscribe_from_channel` sets `@unsubscribed = true` **before** those callbacks ([base.rb L213–L217](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L213-L217)), so a later `stream_from` is a no-op ([streams.rb L91](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L91)).

## String coercion of broadcasting names

Both ends stringify:

- `stream_from` / `stop_stream_from`: `broadcasting = String(broadcasting)` ([streams.rb L93](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L93), [L122](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L122))
