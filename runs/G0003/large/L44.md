**Request changes.** The leak claim is wrong for the supported embedding path, and the `old_argv`/`ensure` patch is the wrong layer.

## Verdict

Do not restore `ARGV` inside `RunnerCommand#perform`. Isolation already lives in `Rails::Command.invoke`. The proposed change is redundant there, unproven by `runner_test.rb`, and incomplete if the real goal is process-state hygiene.

## What the code actually does

[`RunnerCommand#perform`](file:///home/user/workspace/repo/railties/lib/rails/commands/runner/runner_command.rb#L24-L65) is supposed to mutate `ARGV` **for the duration of the script**:

```33:50:railties/lib/rails/commands/runner/runner_command.rb
        ARGV.replace(command_argv)

        wrap_with_executor = !options[:skip_executor]
        if code_or_file == "-"
          conditional_executor(wrap_with_executor, source: "application.runner.railties") do
            eval($stdin.read, TOPLEVEL_BINDING, "stdin")
          end
        elsif File.exist?(code_or_file)
          expanded_file_path = File.expand_path code_or_file
          $0 = expanded_file_path
          ...
              eval(code_or_file, TOPLEVEL_BINDING, __FILE__, __LINE__)
```

That `replace` is the #28515 contract: the code string / filename is not part of `ARGV`. File mode also assigns `$0` (and therefore `$PROGRAM_NAME`) and never puts it back.

CLI and in-process embedding go through [`Rails::Command.invoke`](file:///home/user/workspace/repo/railties/lib/rails/command.rb#L55-L76), which already wraps dispatch:

```140:146:railties/lib/rails/command.rb
        def with_argv(argv)
          original_argv = ARGV.dup
          ARGV.replace(argv)
          yield
        ensure
          ARGV.replace(original_argv)
        end
```

That is the same save/replace/`ensure` restore the PR wants, one layer up, for every command. It is tested as “ARGV is populated” / “ARGV is isolated” in [`railties/test/command/base_test.rb`](file:///home/user/workspace/repo/railties/test/command/base_test.rb#L116-L140). Generate and console also `ARGV.replace` without a local restore; runner is consistent with them.

So: after `Rails::Command.invoke("runner", ...)`, the caller’s `ARGV` is already restored. A leak exists only if someone calls instance/`Base.perform` and skips `invoke`. That is not the public embedding API.

`old_argv` captured at the start of `perform` is also not the original process vector. By then `bin/rails` has already `ARGV.shift`’d the command name, and `with_argv` has already installed the invoke args (code/file plus trailing args). The patch would restore that Thor argv, not `["rails", "runner", ...]`.

## Paths the PR needs to get right (and currently doesn’t reason about)

**Inline code.** `ARGV.replace(command_argv)` then `eval`. Restore after eval does not change what the snippet sees. `with_argv` already restores for the embedder.

**Ruby filename.** `File.exist?` → `Kernel.load`, and `$0 = expanded_file_path` with no restore. If embedding leakage is the concern, `$0`/`$PROGRAM_NAME` are the real process globals the patch ignores. After a successful file runner they stay pointed at the script.

**Stdin (`-`).** Same `ARGV.replace`; `$0` is left alone; source name is `"stdin"`. Restore is again redundant with `with_argv`.

**Syntax errors and missing `.rb` files.** Both sit in the `else` branch **after** `ARGV.replace`. `exit 1` raises `SystemExit`; `with_argv`’s `ensure` still runs. An inner `ensure` would also run, then the process would exit anyway on the CLI path.

**Nested / in-process invocation.** `invoke` → `with_argv` → `perform` → `ARGV.replace`. Inner `invoke` saves the already-narrowed runner `ARGV`, restores it, outer `with_argv` restores the embedder. A second restore inside `perform` is a no-op on this path.

**Executor wrapping.** `ARGV.replace` happens before `conditional_executor`. `--skip-executor` / `-w` does not change argv handling. Restore vs executor is a non-issue.

**Arguments beginning with `-`.** Already covered by [`test_should_set_argv_when_running_code`](file:///home/user/workspace/repo/railties/test/application/runner_test.rb#L40-L43): `--foo`, `-b`, `--moo` are script argv, not Thor options. The patch does not affect that during execution.

## Tests do not support the claim

Both [`railties/test/commands/runner_test.rb`](file:///home/user/workspace/repo/railties/test/commands/runner_test.rb) and [`railties/test/application/runner_test.rb`](file:///home/user/workspace/repo/railties/test/application/runner_test.rb) drive runner through `rails()`, which **forks** (or shells out), replaces `ARGV` in the child, and `exit!`s. The parent never sees a leaked vector. There is no in-process nested-runner test, no post-`invoke` `ARGV` assertion, and no `$0` restoration assertion (tests only check `$0` *during* file execution).

A green runner suite after this patch would not prove the claim.

## Compatibility risk

- Harmless double-restore on the `invoke` path.
- Behavior change only for direct `perform` callers that read `ARGV` after return and expected it to remain `command_argv`. Undocumented, but it is a change.
- File-mode `$0` mutation stays, so “embedding is clean” would still be false.
- `exit 1` on bad code still terminates; restoring argv does not make that embeddable.

## More precise change, if any

Leave `perform` as it is. If someone is calling `perform` directly, the fix is to go through `Rails::Command.invoke`.

If process-state isolation for *direct* `perform` is truly required, it is not an argv-only `ensure`:

1. Save and restore both `ARGV` and `$0`.
2. Add an in-process test (`Rails::Command.invoke("runner", ...)` then assert caller `ARGV` / `$0`), not another forked `rails("runner", ...)` case.
3. Do not describe it as restoring the original process argv; that is `with_argv`’s job, and CLI `ARGV.shift` has already happened.

**Request changes** — reject the `old_argv = ARGV.dup; ... ensure; ARGV.replace(old_argv)` patch as stated.
