So the subsequent `find_by!` cannot reuse a cached SELECT from this thread. [`test_reload_via_querycache`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb#L1699-L1725) loads a parrot with the cache on, updates the row inside `uncached`, then `reload` sees `"Mary"` rather than the cached `"Shane"`.

### Scoped vs unscoped lookup

```858:861:activerecord/lib/active_record/persistence.rb

A **plain** `default_scope` does not apply. Reload wraps the find in `unscoped`. [`test_default_scope_doesnt_run_on_reload`](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb#L301-L306) asserts the SQL has no `mentor_id`.

A default scope declared with `all_queries: true`, or a `scoping(all_queries: true)` block (which sets `global_current_scope`), does apply. Then `_find_record` is called with `all_queries: true` and uses `all_queries_scope`:

        base = if all_queries
          self.class.all_queries_scope
        else
          self.class.all
        end
        base = base.preload(strict_loaded_associations)

        if options && options[:lock]
          base.lock(options[:lock]).find_by!(_in_memory_query_constraints_hash)

          base.find_by!(_in_memory_query_constraints_hash)
        end
      end
```

Consequences, all of which query:

| Situation | SQL | Result |
|---|---|---|
| Plain default scope hides the row | unscoped `find_by!` | succeeds, attributes replaced |
| `default_scope ..., all_queries: true` hides the row | scoped `find_by!` | `ActiveRecord::RecordNotFound` |
| `reload(unscoped: true)` with an `all_queries` default scope | unscoped `find_by!` | succeeds ([test](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb#L333-L338)) |
| `Model.where(...).scoping { record.reload }` | no current scope | current scope ignored ([test](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb#L340-L348)) |
| `scoping(all_queries: true)` | merged into `all_queries_scope` | current scope applied ([test](file:///home/user/workspace/repo/activerecord/test/cases/scoping/relation_scoping_test.rb#L395-L410)) |

`find_by!` is `where(...).take!`, which raises `RecordNotFound` on a miss. A deleted row always queries, then raises. That is what [`test_delete_all`](file:///home/user/workspace/repo/activerecord/test/cases/relation/delete_all_test.rb#L79) asserts with `deleted_post.reload`.

`_in_memory_query_constraints_hash` uses the in-memory primary key (or `query_constraints` columns), so you can assign `id` on a new record and `reload` it into a persisted one ([`test_find_via_reload`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb#L1687-L1696)).

If the owner is `strict_loading?` (and not n+1-only), already-cached association names are preloaded onto `fresh_object` so a later read does not raise. That is [`test_strict_loading_has_one_reload`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L278-L293).

### Association cache: replace, then rebind owner

Reload does **not** walk existing associations and refresh their targets. It replaces the whole cache with the one from `fresh_object` (usually `{}` from `init_internals`, unless `after_initialize` or the strict-loading preload filled it), then points every stolen `Association` back at `self`:

```ruby
@association_cache = fresh_object.instance_variable_get(:@association_cache)
@association_cache.each_value { |association| association.owner = self }
```

`Association` stores `owner` as an `attr_accessor`. Without that loop, callbacks and inverse writes would mutate the discarded `fresh_object`. [`test_reload_sets_correct_owner_for_association_cache`](file:///home/user/workspace/repo/activerecord/test/cases/persistence/reload_association_cache_test.rb#L9-L19) is the regression: `Publication` builds `editor_in_chief` in `after_initialize` and mutates `name` in `after_save_commit`. After `reload`, later association writes still have to touch the original record.

So for an already-loaded association whose DB contents changed:

- `parent.clients` stays stale until something reloads it.
- `parent.reload` drops that cache. The next `parent.clients` queries and sees the new rows. The parent is the same object; the association proxy/targets are not.
- `parent.clients.reload` is a different method: it keeps the parent cache entry, clears query cache with `force: true`, and replaces the target ([`test_force_reload`](file:///home/user/workspace/repo/activerecord/test/cases/associations_test.rb#L117-L141), [`test_find_first_after_reload`](file:///home/user/workspace/repo/activerecord/test/cases/associations/has_many_associations_test.rb#L968-L977)).

- `@previously_new_record = false`

Then Dirty runs:

Nilling the trackers after `@attributes` is replaced matters: the next `mutations_from_database` is built from the new attribute set, and `mutations_before_last_save` falls back to `NullMutationTracker` (`saved_changes` → `{}`, `saved_changes?` → `false`).

### Observable edge cases

All of these keep the same object identity except where noted. “Queries” means Persistence issues `find_by!` after clearing the query cache.

**Unsaved local attribute change.** `pirate.catchphrase = "*hic*"` → `changed?` is true. `reload` queries, replaces `@attributes`, nils `@mutations_from_database`. `changed?` is false; the in-memory write is gone. Same object. [`test_reload_should_clear_changed_attributes`](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb#L410-L416). [`test_reload`](file:///home/user/workspace/repo/activerecord/test/cases/base_test.rb#L1321-L1327) is the other-process variant: `t2.reload` picks up `t1`’s saved title.

**`saved_changes` after a prior save.** After `save`, `saved_changes` is the last-save hash ([`saved_changes` tests](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb#L882-L904)). After `reload`, `@mutations_before_last_save = nil`, so `saved_changes` is `{}` and `saved_changes?` is false. That follow-through is from Dirty’s override plus `NullMutationTracker`, not from a dedicated reload test.

**Row hidden by default scope vs explicit option.** Plain default scope: reload queries unscoped and succeeds. `all_queries: true` default scope: reload queries with that predicate and raises `RecordNotFound` if the row does not match. `reload(unscoped: true)` queries without it and succeeds. Ordinary `scoping` is ignored; `scoping(all_queries: true)` is not.

**Deleted row.** `find_by!` queries, then raises `RecordNotFound`. No attribute or association replacement. Same object, still holding the old in-memory state.

**Already-loaded association, DB changed.** `record.reload` queries the owner, replaces `@association_cache`, rebinds owners. It does not refresh the old targets. The next association read queries. Association objects after that read are new; the owner is not.
