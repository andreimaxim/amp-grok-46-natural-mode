**Reject.** The claim is false at this revision. Query equality is not “current-scheme ciphertext only”; it is an `IN` of every `previous_types` serialization plus the value `serialize` produces. Read/decrypt is a different path and would keep working after the proposed cut.

## Query vs read

`ExtendedDeterministicQueries` only rewrites hash equality in `where` / `exists?` / `Base.find_by`. It expands when `type.previous_types` is non-empty:

```61:91:activerecord/lib/active_record/encryption/extended_deterministic_queries.rb
                if !type.previous_types.empty? && value = options[attribute_name]
                  options[attribute_name] = process_encrypted_query_argument(value, check_for_additional_values, type)
                end
...
            def additional_values_for(value, type)
              type.previous_types.collect do |additional_type|
                AdditionalValue.new(value, additional_type)
              end
            end
```

`previous_types` is previous schemes **and**, when `support_unencrypted_data?`, a `NullEncryptor` clean-text type. That is documented as query behavior, not just decrypt:

```46:47:activerecord/lib/active_record/encryption/encryptable_record.rb
        # * <tt>:previous</tt> - ... Also, when deterministic
        #   encryption is used, they will be used to generate additional ciphertexts to check in the queries.
```

Deserialize is independent: current decrypt, then previous types, then plaintext on `Errors::Decryption` if unencrypted data is allowed. Removing query expansion does not change that.

The “current scheme” part is also wrong for default deterministic encryption. `fixed?` is true by default, so `serialize` writes **oldest** previous ciphertext, not newest. Expansion then adds the other previous types and optional plaintext. Newest-scheme ciphertext is not in the predicate unless `deterministic: { fixed: false }`.

Executed SQL (`sqlite3_mem`, `support_unencrypted_data = true`):

- `where(name: "Dune")` → `name IN ('{"p":"DIohhw==",...}', 'Dune')`
- without expansion → `name = '{"p":"DIohhw==",...}'`
- `where(name: ["Dune", "Iliad"])` → four binds (two ciphertexts + two plaintexts); without expansion, the two plaintexts disappear
- `deterministic: { fixed: false }` + `previous:` → `IN ('current-ct', 'previous-ct', 'Dune')`; without expansion → `name = 'current-ct'`

Stubbing `additional_values_for` to `[]` (the proposed cut) made the existing unencrypted / previous-scheme lookups miss, while `reload` / `find(id)` still decrypted. Existing suites still pass because they keep expansion: `extended_deterministic_queries_test.rb` and `encryption_schemes_test.rb` (27 runs, 0 failures).

## Failing examples if expansion is removed

`where(email: value)` / `where(name: "Dune")`  
Unencrypted row `"Dune"` is readable via `EncryptedBook.find(id)` but `where(name: "Dune")` / `exists?` return empty. Same for an email column: the extra bind is plaintext, not another ciphertext.

Array predicates  
`where(name: ["Dune", "Iliad"])` today is `IN (ct, ct, "Dune", "Iliad")`. After the cut it is ciphertext-only. No existing encryption test covers arrays; this is a gap, not proof the feature is unused.

`find_by` and prepared/bound values  
`Base.find_by` is patched **because** of statement-cache. Expansion turns the value into an Array, `StatementCache.unsupported_value?` is true for Array, and the cached single-bind path is skipped. Without expansion, `EncryptedBook.find_by(name: "Dune")` caches one current/oldest ciphertext bind and misses plaintext. Relation `where(...).find_by` is the same `IN` as `where`.

Per-attribute `support_unencrypted_data`  
This is not global-only. `Scheme#support_unencrypted_data?` uses the attribute flag when set. With global `false` and attribute `true`, `EncryptedBookWithUnencryptedDataOptedIn.find_by(name: "Dune")` finds unencrypted rows today and misses them without expansion. Attribute `false` already skips the clean-text type; that case is not a reason to delete expansion.

`previous:` / key rotation  
With `deterministic: { fixed: false }`, current serialize is newest ciphertext. A row stored as previous-scheme ciphertext still decrypts (`klass.find(id).name == "Dune"`) but `where` / `find_by` miss it without expansion. With default `fixed: true`, serialize already uses oldest, so oldest rows keep matching; other previous schemes and newest-scheme leftovers do not. `encrypts :name, previous: [...]` exists specifically to generate those extra query ciphertexts.

`downcase`  
Current-scheme `downcase: true` does **not** need expansion for its own rows: `"DUNE"` serializes to the same ciphertext. Expansion is required when a **previous** scheme downcased and the current one does not (or the reverse). Global previous `[{ downcase: true, deterministic: true }]` plus current `downcase: false, deterministic: { fixed: false }` finds `"STEPHEN KING"` today via the extra downcased ciphertext; without expansion both `find_by` and `where` miss, while `find(id)` still returns `"stephen king"`.

`ignore_case` / `original_name`  
Query uses downcased `name`. Current-scheme `find_by(name: "dune")` works without expansion. `original_name` is a **read** accessor (`ignore_case` copies the original into `original_name` and `name` reads it). Do not treat `original_name` as a query-expansion concern. Unencrypted ignore_case rows **are** a query concern: the clean-text additional value is downcased, so stored `"dune"` is found with expansion and missed without it; mixed-case stored `"Dune"` is already not found even with expansion.

## What not to build

Do not replace expansion with a new API, a decrypt-on-read fallback in SQL, or “always re-encrypt in place.” Keep `extend_queries` as the query compatibility layer and `previous_types` / `support_unencrypted_data?` as the decrypt layer.
