## Current observable contract

This is what this checkout already does. It is not the proposal.

**Mailer default queue.** Every mailer has a class-level delayed-delivery queue, default `:mailers`. A mailer may set its own name. A subclass change does not change the parent. A mailer that does not set its own name follows `ActionMailer::Base`. Apps that load 6.1+ defaults set the global name to `nil`.

**What `nil` means.** `nil` is not a queue named `"nil"`. With the default delivery job, delayed mail goes to Active Job’s default queue (typically `"default"`).

**Symbols vs strings.** Mailers often store a symbol (`:mailers`). Once a job is enqueued, the queue identity observers see is a string (`"mailers"`). `:mailers` and `"mailers"` are the same queue for enqueue, assertion, and test filters.

**Per-send `queue:`.** `deliver_later(queue: …)` / `deliver_later!(queue: …)` place that one send on the given queue and skip the mailer’s delayed-delivery queue for that send. A falsy `queue:` does not override.

**Who owns the queue when the delivery job is custom.** With the default delivery job, the mailer’s delayed-delivery queue wins (unless a per-send `queue:` is given). If the mailer uses a custom delivery job, that job’s own queue is what is used. A custom job that still follows the default job’s rule continues to follow the mailer; a custom job that declares its own queue does not.

**Parameterized mail.** `Mailer.with(…).action.deliver_later` uses the same queue rules as a normal send of that mailer. Parameters do not pick a queue.

**Scheduled mail.** `wait:` / `wait_until:` still use the same queue. They only change when the send is due.

**Test delivery.** `deliver_enqueued_emails` runs delayed mailer jobs that this process recognizes as a mailer’s delivery job. With no filter it runs all of those. `queue:` runs only jobs whose enqueued queue string equals `queue` stringified. `at:` runs only mail due immediately or by that time; later mail stays unsent. Other jobs on the same queue are not sent.

**Test assertions.** `assert_enqueued_email_with` matches the mailer’s delivery job and, if no queue is given, the queue that job would use for that mailer. An explicit `queue:` is stringified before comparison.

## Shaping brief

**Kind of work:** behavior change — make existing delayed-mail queue targeting and test selection one reliable identity, not a new mailer or job product.

**Problem frame.** A developer or tester splits delayed mail across queues (by mailer, by send, or by custom delivery job) so production workers and tests can handle one stream at a time. Today the name they assign, the name that is enqueued, and the name a test filter matches are not always the same thing: symbols vs strings, `nil` vs a real default queue, subclass vs parent, custom job vs mailer setting, scheduled vs immediate, and adapters that prefix or otherwise normalize names. The pain is sending the wrong mail, leaving the intended mail unsent, or accepting a test that does not actually cover the queue they think they targeted.

**Hypothesis (not observed as an incident):** this shows up most when several mailers share a process, when a queue prefix is on, or when a mailer uses a custom delivery job.

**Desired outcome.** Someone can assign a delayed-mail queue at the mailer, override it on one send, and later in tests select exactly that delayed mail by the same queue identity — including several mailers, parameterized mail, scheduled mail, queue filters, and adapters that normalize names — without also sending unrelated mail or silently skipping the mail they meant.

**Appetite (inferred from the request, not a time box they supplied).** Only enough to make targeting and test selection trustworthy for delayed Action Mailer. Not a redesign of mail delivery, Active Job, or adapters.

**Scope.** Delayed mail via `deliver_later` / `deliver_later!` and test-time running/filtering via `deliver_enqueued_emails` (and the matching “was this mail enqueued on this queue?” check). Covers mailer-level names, per-send `queue:`, symbol/string/`nil`, inheritance, custom delivery jobs, parameterized mail, scheduled mail, queue filters, and name normalization.

**Non-goals.** Immediate `deliver_now` behavior; SMTP/adapters for actually sending mail; inventing new queue backends; changing the 6.1 global default of `nil`; making non-mail jobs look like mail; documenting internals as the product.

### Behavioral outcomes

1. **One queue identity.** The name a team assigns for delayed mail is the name they can use later to find or run that mail, after whatever string/`nil`/prefix/normalization the environment applies. `:mailers` and `"mailers"` are the same queue. `nil` means “Active Job’s default queue,” not a queue called nil.

2. **Mailer default vs one-off override.** A mailer’s delayed-delivery queue applies to every delayed send of that mailer until a send passes `queue:`. That override affects only that send.

3. **Inheritance.** A child mailer may have its own delayed-delivery queue. That does not change the parent or siblings. A child that does not set one follows the parent, including a global `nil`.

4. **Custom delivery job.** If the mailer uses the default delayed-delivery job, the mailer’s queue applies. If it uses a custom job that defines its own queue, that job’s queue is the identity for enqueue and for tests. Testers do not have to guess which of the two names won.

5. **Test selection.** Running delayed mail with a queue filter sends only recognized delayed-mail jobs on that queue identity. Mail on other queues stays unsent. A time filter sends only mail due immediately or by that time. Unfiltered run sends all recognized delayed mail, regardless of queue.

### Acceptance examples

Required cases, not an exhaustive catalog.

**Several mailers, filter one queue.** Customer mail is assigned `external_mailers`, employee mail `internal_mailers`. Both are delayed. The tester asks to run only `external_mailers`. Customer mail is sent; employee mail is not.

**Per-send override.** The customer mailer’s default queue is `external_mailers`. One send is delayed with `queue: :priority_mailers`. A filter for `external_mailers` does not send it. A filter for `priority_mailers` does.

**Symbol vs string.** The mailer assigns `:mailers`. The tester filters with `"mailers"` (or the reverse). That mail is selected. They are not asked to match types.

**`nil` means the default job queue.** The global delayed-mail queue is `nil`. Delayed mail is enqueued on Active Job’s default queue. A tester who selects that default queue gets the mail. A tester who selects `"nil"` or `:mailers` does not, unless that is actually the default.

**Inheritance.** `DelayedMailer` sets `:delayed_mailers`. `ActionMailer::Base` remains `:mailers`. Delayed `DelayedMailer` mail is selected only as `delayed_mailers`. Other mailers that never set a name still follow the base, including `nil` after 6.1 defaults.

**Custom delivery job with its own queue.** A mailer uses a delivery job whose queue is `delivery_job_queue`, not the mailer’s `deliver_later_queue_name`. Delayed mail lands on `delivery_job_queue`. Tests that select that job’s queue send it; tests that select the mailer’s unused name do not.

**Custom delivery job that still follows the mailer.** A mailer uses a custom job that does not declare a different queue. Delayed mail still follows the mailer’s delayed-delivery queue, including `nil` → default. Tests using that mailer queue identity succeed.

**Parameterized mail.** `InvitationsMailer.with(inviter:, invitee:).account_invitation.deliver_later` uses the same queue rules as a non-parameterized send of that mailer. A queue filter that selects that mailer’s queue sends it; a filter for another mailer’s queue does not. Parameters do not create a second queue.

**Scheduled mail plus queue filter.** Two delayed sends on `mailers`: one immediate, one `wait: 2.hours`. Running that queue with “due by one hour from now” sends only the immediate mail. The later mail stays unsent and still on `mailers`.

**Adapter normalizes names.** The environment prefixes queues (`prefix` + `custom_queue` → `prefix_custom_queue`) or otherwise normalizes them. The tester targets the queue the way this app assigns it (the mailer name or the per-send `queue:`). The mail is still selected. They are not required to hand-build the prefixed/normalized string to make the filter work, and a filter for a different assigned name still does not send it.

**Counterexample — wrong queue must not send.** Mail delayed on `internal_mailers` plus an unrelated non-mail job on that same queue. Running delayed mail for `internal_mailers` sends only the mail. The other job is untouched. Mail on `external_mailers` is untouched.

### Risks

- **Silent mismatch after normalization.** Prefix or adapter rewriting is the likely place assigned name and filter name diverge; tests can look green while they never ran the intended mail.
- **Custom job vs mailer name.** Teams set both and cannot tell which one production and tests actually used.
- **Unrecognized delivery jobs.** If a mailer’s job is not visible as a mailer delivery job in this process, `deliver_enqueued_emails` will not send it even on the right queue.
- **`nil` and 6.1 defaults.** Teams still thinking in `:mailers` will filter the wrong queue once the global name is `nil`.
- **Scheduled mail.** A queue filter without a time bound can send mail that was not due yet if the test runner also performs future jobs; a time bound without a queue bound can send the other mailer’s due mail.

### Steering evidence

**Success looks like:** a teammate can say which queue a delayed send used, then in a test run only that queue and see exactly those emails sent — across the examples above — including when the adapter prefixes or stringifies the name.

**Investigate / treat as failed if:** filtering by the name they assigned sends nothing while the mail sits on a prefixed or default queue; `:mailers` and `"mailers"` diverge; a subclass queue change moves the parent’s mail; parameterized mail ignores the mailer’s queue; scheduled mail on the selected queue is dropped or other queues’ mail is sent; custom-job mail is only findable under the unused mailer name.

**Reconsider the framing if:** the real pain is workers not consuming a queue in production, not test/targeting identity; or if teams do not actually split mail across queues and only want a global on/off for delayed mail.

### Open questions

- When an adapter prefixes or rewrites names, should the product identity stay the name the team assigned, or the name the backend stores? The examples assume assigned name is enough for testers.
- Should a custom delivery job that declares its own queue still honor a per-send `queue:`? Current enqueue options suggest yes; current docs emphasize the job owning the queue.
- Is matching `assert_enqueued_email_with` to the same identity in scope, or only `deliver_enqueued_emails`? This brief includes both because testers use them together.
- No appetite in weeks was given; treat the appetite above as a scope cap, not a schedule.

If the assigned-name vs processed-name identity is wrong, or custom jobs should always ignore the mailer queue even when they do not declare one, that changes outcomes 1 and 4 and the adapter/custom-job examples.
