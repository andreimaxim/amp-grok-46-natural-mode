## Assistant

**Problem frame:** An application or engine author runs `bin/rails generate` or `bin/rails destroy` when a generator would touch a path that already exists. They need a predictable keep / replace / delete outcome. Today generate and destroy do not present the same collision policy for that path, so a skipped or left-alone file can still disappear on destroy, and engine vs app runs can make the target root hard to trust.

This is **maintenance**: keep the documented collision contract, and only treat generate/destroy differences as defects if evidence shows they were not the intended contract.

**Users**
- App developers generating and later destroying in an application.
- Engine authors doing the same from an engine’s `bin/rails`.
- Non-interactive users (piped stdin, CI) who never see a prompt.

**Pain**
Help advertises `--force` (overwrite existing files) and `--skip` (leave existing files) for both commands. Generate then distinguishes identical content, differing content, flags, and an overwrite prompt. Destroy still removes an existing destination path if it is there. After generate skips a collision, destroy can delete a file generate never wrote. That is the reported inconsistency.

**Desired observable CLI behavior** (working contract; not a redesign)
A person can tell from the command, flags, prompt answers, and status lines what happens to an existing file, and that policy is the same for an app and for an engine once the destination root is known. Generate and destroy should resolve the same generator name the same way, including fallbacks. A missing generator fails visibly on both. Whether destroy may delete a file generate skipped is **not settled**.

**Non-goals**
- Changing what a clean generate creates or what a matching destroy removes when no collision occurred.
- Inventing new collision flags or prompt letters.
- Treating class-name reservation checks as this file-collision brief.
- Deciding internals, architecture, or test code in this brief.

Evidence inspected: `Rails::Generators` invoke/lookup/fallbacks, `GenerateCommand` / `DestroyCommand`, Thor create/revoke and the overwrite prompt, engine command root, and Railties generator integration tests. Those tests cover class-name collision on generate, migration identical/skip/force/revoke, namespaced and engine generate/destroy, and missing-generator lookup. They do **not** drive the file overwrite prompt, non-interactive stdin, or destroy after a skipped file collision.

---

**Acceptance examples** (required cases; outcome is what must be defined and stable)

Identical content, generate twice  
The file already matches what generate would write. Generate reports it identical and leaves the bytes unchanged. No overwrite prompt.

Differing content, generate, no flags  
The file exists with different bytes. Generate reports a conflict and asks whether to overwrite. Until the user answers, the file is unchanged.

`--force`  
Differing file. Generate overwrites without asking. Status shows the file was forced.

`--skip`  
Differing file. Generate leaves the file unchanged. Status shows skip. Identical content still reports identical, not skip.

Interactive answers (differing file, no `--force`/`--skip`)  
Prompt is `Overwrite <path>? (enter "h" for help) [Ynaqdhm]`.
- yes: overwrite this file only.
- no: leave this file; later collisions still prompt.
- all: overwrite this file and later collisions in this run without asking again.
- quit: abort; this file stays; the command does not continue applying later collisions.

Non-interactive stdin  
No TTY; stdin is EOF/null at the overwrite question. **Current observation:** Thor treats that as overwrite. **Open:** is silent overwrite the contract, or must generate refuse to overwrite without `--force`? Destroy does not ask, so this path does not currently apply to destroy.

Nested engine destination root  
From an engine’s `bin/rails`, generate and destroy act on the engine tree, not the host app or dummy app. A colliding path is the engine path. Destroy of a matching generate removes the engine artifacts, as today’s mountable-engine scaffold generate-then-destroy run shows.

Namespaced generator resolution  
`model`, `rails:model`, a nested name like `my:awesome:namespace`, and a configured fallback (e.g. a stand-in that resolves to another generator) select the same generator on generate and on destroy. Destroy of a namespaced scaffold removes the namespaced files and leaves parent namespace modules that other code still needs.

Missing generator  
An unknown name on generate or destroy does not write or delete app files. The command exits unsuccessfully and says the generator could not be found (with a suggestion when the name is close). **Open:** destroy currently points at `bin/rails generate --help`; whether that message must match the command that was run is unset.

Destroy after a skipped collision  
Generate `--skip` left a pre-existing differing file. Then destroy for the same generator and name. **Current observation:** destroy removes that path if it still exists. **This is the main intentionality question:** is destroy “remove these destination paths if present,” or “undo only what generate actually wrote”?

---

**Steering evidence**
- Success: for each example above, app and engine runs match the stated keep/replace/delete result and status; generator lookup matches on both commands.
- Investigate, do not “fix” yet: generate skips or asks, then destroy deletes the skipped file; `--force`/`--skip` on destroy do not mean overwrite/skip; EOF overwrites; migrations raise on conflict instead of prompting.
- Wrong framing: authors only care about class-name collisions, or they rely on destroy always deleting whatever sits at the generated path.

**Open questions** (block calling today’s differences bugs)
1. Is destroy allowed to delete a file generate skipped or never wrote?
2. Do destroy’s documented `--force` / `--skip` apply to existing files, or are they generate-only in practice?
3. On EOF/non-interactive conflict, is overwrite intended?
4. Must ordinary files and migrations share one collision UX, or is “migrations error, other files prompt” intended?
5. Must generate and destroy missing-generator help name the same command?

I treated generate’s identical / prompt / `--force` / `--skip` / yes-no-all-quit behavior as the published contract to preserve, and generate-vs-destroy divergence as unproven. Correct that if destroy’s unconditional remove is the contract you want kept.
