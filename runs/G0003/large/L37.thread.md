```ruby
  if processed?
```

### What `processed?` means

[`ActionMailer::MessageDelivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb) is a lazy `Delegator` around a `Mail::Message`. Construction stores the mailer class, action, and args and leaves the message unloaded:

```22:31:actionmailer/lib/action_mailer/message_delivery.rb
    def initialize(mailer_class, action, *args, **kwargs) # :nodoc:
      args << Hash.ruby2_keywords_hash(kwargs) unless kwargs.empty?
      @mailer_class, @action, @args = mailer_class, action, args

      # The mail is only processed if we try to call any methods on it.
      # Typical usage will leave it unloaded and call deliver_later.
      @processed_mailer = nil
      @mail_message = nil
    end
```

`processed?` is true once the delegate has been loaded:

```47:49:actionmailer/lib/action_mailer/message_delivery.rb
    def processed?
      @processed_mailer || @mail_message
    end
```

That happens on `#message`, on any method delegated onto `Mail::Message` (`subject=`, `to`, `body`, …), and on `deliver_now` / `deliver_now!`. Loading runs the mailer action now:

```33:35:actionmailer/lib/action_mailer/message_delivery.rb
    def __getobj__ # :nodoc:
      @mail_message ||= processed_mailer.message
    end
```

```136:140:actionmailer/lib/action_mailer/message_delivery.rb
      def processed_mailer
        @processed_mailer ||= @mailer_class.new.tap do |mailer|
          mailer.process @action, *@args
        end
      end
```

`deliver_later` is supposed to skip that path so the action runs only in the job. The docs state that explicitly: “`deliver_later` will execute your method from the background job.” ([`base.rb`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/base.rb) around line 166.)

### What is actually serialized

The job arguments are the mailer class name, action name, delivery method name, and the original method args. Not the generated mail:


[`MailDeliveryJob#perform`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb) rebuilds a *new* `MessageDelivery` and delivers that:

```21:29:actionmailer/lib/action_mailer/mail_delivery_job.rb
    def perform(mailer, mail_method, delivery_method, args:, kwargs: nil, params: nil)
      mailer_class = params ? mailer.constantize.with(params) : mailer.constantize
      message = if kwargs
        mailer_class.public_send(mail_method, *args, **kwargs)
      else
        mailer_class.public_send(mail_method, *args)

      message.send(delivery_method)
```

The proposed diff only deletes the `processed?` branch. The `perform_later` call is unchanged. The job still cannot see the in-memory `Mail::Message`.

### Laziness

`Notifier.welcome(user)` does not run `welcome`. Typical use leaves the wrapper unloaded and calls `deliver_later`. `deliver_all_later` is built the same way and asserts the wrappers stay unprocessed ([`message_delivery_test.rb` lines 163–178](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb)). After this PR, calling `#message` then `deliver_later` would run the action once in the caller *and* again in the job. Mailer side effects (logging, instrumentation, `before_action`, DB reads) would double.

### Parameterized mailers

[`Parameterized::MessageDelivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/parameterized.rb) is a subclass that must pass `params:`:

```144:150:actionmailer/lib/action_mailer/parameterized.rb
        def enqueue_delivery(delivery_method, options = {})
          if processed?
            super
          else
            @mailer_class.delivery_job.set(options).perform_later(
              @mailer_class.name, @action.to_s, delivery_method.to_s, params: @params, args: @args)
          end
        end
```

Today `processed?` → `super` → raise. After the parent raise is gone, `super` enqueues **without** `params:`. The job then does `mailer.constantize` instead of `mailer.constantize.with(params)` and delivers a different (usually empty-params) message. Unprocessed parameterized mail still works ([`parameterized_test.rb` lines 42–53](file:///home/user/workspace/repo/actionmailer/test/parameterized_test.rb)); the processed path is untested and would regress.

### `deliver_later` versus `deliver_later!`

Both call `enqueue_delivery`. The only difference is the delivery method name the job will invoke:

```77:78:actionmailer/lib/action_mailer/message_delivery.rb
    def deliver_later!(options = {})
      enqueue_delivery :deliver_now!, options
```

```104:105:actionmailer/lib/action_mailer/message_delivery.rb
    def deliver_later(options = {})
      enqueue_delivery :deliver_now, options
```

`deliver_later` → `deliver_now` (honors `perform_deliveries` / `raise_delivery_errors`). `deliver_later!` → `deliver_now!` (bypasses them). The `processed?` guard applies to both. The bang does not mean “deliver this already-built object.”

### Custom delivery jobs and queues

The job class is `mailer.delivery_job`, default `ActionMailer::MailDeliveryJob` ([`queued_delivery.rb` lines 8–9](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/queued_delivery.rb)). Custom jobs still receive `[class, action, delivery_method, args:]`, not a `Mail::Message` ([`message_delivery_test.rb` lines 101–108](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb)).

Queue selection is independent of the message object:

- `MailDeliveryJob` uses `arguments.first.constantize` then `deliver_later_queue_name` ([`mail_delivery_job.rb` lines 13–16](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb)).
- `set(options)` can override `:queue`, `:wait`, `:wait_until`, `:priority`.
- A custom `delivery_job` owns its own queue.

If the job actually received a `Mail::Message` as the first argument, `arguments.first.constantize` would break queue lookup. The proposed diff does not do that, so queues stay intact *and* the author’s serialization story is still wrong.

### Mutations before enqueue

Because this is a `Delegator`, `mail.subject = "Hacked"` loads the message, sets `processed?`, and mutates the local object. Current code raises. Proposed code enqueues original args; the job rebuilds from the mailer method and sends the unmutated mail. That is the failure the error string exists to prevent ([`message_delivery.rb` lines 143–151](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb)).

Even a read-only `mail.message` is enough: the only covering test is the raise itself ([`message_delivery_test.rb` lines 133–139](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb)). There is no test that mutations survive `deliver_later`, because they do not.

`deliver_all_later` never checks `processed?` at all ([`action_mailer.rb` lines 88–104](file:///home/user/workspace/repo/actionmailer/lib/action_mailer.rb)). Same silent-loss bug, already present, also untested.

### Serialization failures versus the no-prior-access path

Active Job will not serialize `Mail::Message`. Supported types are primitives, hashes/arrays/ranges, time types, and GlobalID; anything else hits `ActiveJob::Serializers.serialize` and raises `SerializationError: Unsupported argument type` ([`arguments.rb` lines 39–43, 52–93](file:///home/user/workspace/repo/activejob/lib/active_job/arguments.rb), [`serializers.rb` lines 32–33](file:///home/user/workspace/repo/activejob/lib/active_job/serializers.rb)). There is no Mail serializer.

So:

- **No prior access (keep this):** enqueue class/action/args; job regenerates; this is the supported path; existing tests cover delay, priority, queue, custom job, kwargs, parameterized params, and deserialization errors delegated to the mailer.
- **Prior access + this PR:** still serializes args, not `Mail::Message`. Enqueue succeeds. Delivery is a *new* message. Mutations and params can be lost. Mailer runs twice.
- **Author’s imagined design (pass `Mail::Message`):** enqueue would fail with `ActiveJob::SerializationError` unless a new serializer and a new job `perform` contract were added. Queue-as-class-name would also break.

The no-prior-access path is not the problem. The PR does not add a serialized-message path. It only removes the alarm.

### Gaps in the claim and tests

- Claim: “the job can serialize the generated `Mail::Message`.” Implementation: job args are still `@args` / `params:` + `@args`.
- No serializer, no `perform` change, no parameterized `params:` on the processed path.
- Tests cover unprocessed enqueue thoroughly. The only processed-path test is that `deliver_later` raises. No mutation test, no parameterized-after-`#message` test, no `deliver_later!` processed test, no `deliver_all_later` processed test.
- Custom jobs are assumed to keep the current four-argument contract. Serializing a message would be a breaking change for them.

### Smallest viable direction

Keep the raise. If someone needs “touch then send later,” the error already lists the real options: don’t touch before `#deliver_later`, mutate only inside the mailer action, or use a custom Active Job.

Do not teach `enqueue_delivery` to take a `Mail::Message` as a drive-by. That needs a new serializable payload (for example the encoded RFC822 string), a job that delivers that payload instead of re-invoking the mailer, a parameterized-safe branch, a custom-job compatibility story, and tests that mutated headers/body are what actually get sent.

If the only pain is the raise after a read-only `#message`, that is still not safe to allow: `Delegator` cannot tell read from write, and processing now plus again in the job doubles side effects. Leave the guard.
