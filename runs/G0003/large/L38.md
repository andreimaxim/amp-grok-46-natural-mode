Current contract is three cooperating pieces: schedule on processed status updates, run later on a delay, destroy only if still processed and past a `updated_at` cutoff. Existing tests cover the happy path and missing records; they do not pin the age predicate, rescheduling, or attachment purge.

```diagram
pending/processing ──status bang──► delivered|failed|bounced
                                            │
                 ActionMailbox.incinerate ──┤
                 status_previously_changed?─┤
                 processed? ────────────────┘
                                            ▼
                          after_update_commit
                          Incineratable#incinerate_later
                                            ▼
                          IncinerationJob.schedule
                          wait: incinerate_after
                          queue: ActionMailbox.queues[:incineration]
                                            ▼
                          IncinerationJob#perform
                          inbound_email.incinerate
                                            ▼
                          Incineration#run
                          destroy! iff due? && processed?
                          due?: updated_at < incinerate_after.ago.end_of_day
```

# Invariants vs incidental

**Preserve these.** Each is established by source, existing tests, or both.

1. **Schedule only on an update that lands in a processed status, and only when incineration is enabled.** Callback condition is `ActionMailbox.incinerate && status_previously_changed? && processed?` ([incineratable.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable.rb#L10)). Tests: delivered/bounced/failed enqueue; `incinerate = false` does not ([incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb)). Create-time processed status does not schedule (`after_update_commit`, not create). `pending`/`processing` updates do not.

2. **Each of `delivered!`, `bounced!`, `failed!` is a terminal that schedules.** Same three tests plus the guide ([action_mailbox_basics.md](file:///home/user/workspace/repo/guides/source/action_mailbox_basics.md) “Incineration of InboundEmails”). Do not treat `delivered` as the only terminal.

3. **Scheduling delay is `wait: ActionMailbox.incinerate_after`, evaluated at enqueue time.** [incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb#L17-L18); tests assert `at: 30.days.from_now` under `freeze_time` with the default duration.

4. **Job queue is `ActionMailbox.queues[:incineration]`, not a hardcoded symbol.** [incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb#L13); railties tests for 6.0 / 6.1 / override ([configuration_test.rb](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb) around the `ActionMailbox.queues[:incineration]` cases).

5. **`incinerate = false` only skips automatic scheduling.** It is not consulted by `#incinerate`, `Incineration#run`, or `#perform`. Conductor still calls `#incinerate` directly ([incinerates_controller.rb](file:///home/user/workspace/repo/actionmailbox/app/controllers/rails/conductor/action_mailbox/incinerates_controller.rb)). A job already enqueued while the flag was true still runs.

6. **Destruction is `destroy!` only when both `due?` and `processed?`.** [incineration.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable/incineration.rb#L13-L24). Unprocessed records stay. Not-yet-due records stay. No exception on the skip path.

7. **Due uses current `updated_at`, not `created_at` and not enqueue time.** Predicate is strict: `updated_at < ActionMailbox.incinerate_after.ago.end_of_day`. `end_of_day` is part of the contract, not sugar. A later non-status update can push `updated_at` past the cutoff so the originally scheduled job no-ops.

8. **Repeated processed-status changes enqueue again; same-status updates do not.** `status_previously_changed?` is the gate. `delivered!` on an already-delivered row does not enqueue. `delivered!` then `failed!` does. Extra jobs are safe because `#run` is a guarded destroy.

9. **Already-deleted records: the job must not raise.** `discard_on ActiveRecord::RecordNotFound, ActiveJob::DeserializationError::RecordNotFound` ([incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb#L15)); [incineration_job_test.rb](file:///home/user/workspace/repo/actionmailbox/test/jobs/incineration_job_test.rb) “ignoring a missing inbound email”.

10. **Successful incineration removes the `InboundEmail` row and the `raw_email` attachment.** `has_one_attached :raw_email` defaults to `dependent: :purge_later` ([inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb#L30); Active Storage `has_one_attached`). Existing tests only assert `InboundEmail.count` −1. Preserve both the row delete and attachment/blob teardown.

**Do not pin these** unless the refactor’s goal is to freeze internals:

- Nested `Incineratable::Incineration` vs an inline method vs another object.
- `after_update_commit` vs equivalent after-commit-on-update.
- Listing both `RecordNotFound` classes if missing-record jobs still discard.
- Hardcoded `:action_mailbox_incineration` (dummy apps on 6.1+ defaults use `nil`).
- Hardcoded `30.days` except as the default of `incinerate_after`.
- Existing tests’ `travel 30.days` as a definition of due. That wait equals `schedule`’s delay; due is looser because of `end_of_day`. Midday freeze makes `T0 < T0.end_of_day` true, which is why those tests pass.
- Comment text in `Incineration` (“processed after the incinerate_after time”) — it does not match the predicate.

# Time control

Use one frozen midday timestamp so `end_of_day` is a known offset, not “almost 30 days.”

```ruby
freeze_time Time.utc(2024, 6, 15, 12, 0, 0)
```

Compute from config, do not restated literals:

- enqueue time: `Time.current + ActionMailbox.incinerate_after`
- due threshold: `ActionMailbox.incinerate_after.ago.end_of_day`

Restore `ActionMailbox.incinerate` / `incinerate_after` in `ensure` (existing skip test does this). Prefer `Object#with` if you touch class config in new tests.

Do **not** use `travel 30.days` as the only due oracle. Use it to expire the job’s `wait`. For the age boundary, set `updated_at` (or travel) relative to `incinerate_after.ago.end_of_day`.

# Integration-level observation

One test through mailbox processing, not a status bang in isolation. Reuse the pattern in [state_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/mailbox/state_test.rb):

1. `freeze_time` midday.
2. Create inbound email (`status: :processing` is fine).
3. `SuccessfulMailbox.receive(inbound_email)` → `delivered!` inside `track_status_of_inbound_email`.
4. Assert exactly one `IncinerationJob` at `incinerate_after.from_now`.
5. `travel ActionMailbox.incinerate_after`.
6. `assert_difference` inbound count −1 while `perform_enqueued_jobs only: IncinerationJob`.
7. Perform `ActiveStorage::PurgeJob` and assert the `raw_email` blob is gone.

That is the production path: mailbox terminal → callback → delayed job → guarded `destroy!` → attachment purge. Conductor `POST .../incinerate` is a second integration if you want a no-job destroy, but it is outside the three classes; keep it optional.

# Oracle for “behavior preserved”

A refactor is good if:

- All cases above still pass with the same **database-visible** outcomes (row present/absent, status, attachment/blob).
- Enqueued job **class, run-at, arguments, queue** match on the schedule path.
- Missing-record perform remains silent.
- Failures are skipped destroys, not new exceptions.

A refactor is not a failure if it changes class nesting, callback macro, or whether `due?` is a private method — as long as the predicate and outcomes hold.
