A refactor is unchanged only if every branch still produces the same object graph, not just the same `==` string.

Pin the oracle: same Ruby, same file, UTF-8 source. For every case record `inspect`, `bytesize`, `encoding`, `class`, `frozen?`, `equal?(receiver)`, `valid_encoding?`, and the receiver after the call. Expected values below are the current method.

```text
truncate_bytes(n, omission:)
  bytesize <= n          → dup
  omission.bytesize > n  → ArgumentError
  omission.bytesize == n → omission.dup
  else                   → prefix of grapheme clusters
                           + omission, bytesize ≤ n
```

---

**1. Within-budget strings**

Inputs: `"hello".truncate_bytes(5)` and `"hello".truncate_bytes(10)`; `"👍👍".truncate_bytes(8)` (exactly 8 bytes).

Expect: result `==` receiver, `bytesize` unchanged, `encoding` and `class` unchanged, `frozen? == false`, `equal?(receiver) == false`.

That proves the `bytesize <= truncate_to` branch still copies and never walks graphemes or injects an omission. `"hello".truncate_bytes(5)` vs `truncate_bytes(10)` proves the cutoff is `<=`, not `<`. The thumbs-up case proves “within budget” is measured in bytes, not characters.

---

**2. ASCII truncation**

`"Hello World"` is 11 bytes. Default omission `"…"` is U+2026, 3 UTF-8 bytes.

| call | expect |
|---|---|
| `.truncate_bytes(11)` | `"Hello World"` (dup path) |
| `.truncate_bytes(10)` | `"Hello W…"` (7 prefix bytes + 3) |
| `.truncate_bytes(8)` | `"Hello…"` |
| `.truncate_bytes(8, omission: "..")` | `"Hello .."` |

Also assert `result.bytesize <= n` and `valid_encoding?`.

That proves room for the omission is `n - omission.bytesize`, that ASCII codepoints (1 byte each) fill that room exactly, and that a custom ASCII omission is counted in bytes and concatenated, not substituted by character count. `"Hello W…"` at 10 is the exact-fit ASCII case: one leftover byte is not enough for another letter plus `"…"`, so the letter is dropped.

---

**3. Multibyte truncation**

`"👍👍👍👍"` is four U+1F44D, 16 bytes. Each thumbs-up is 4 bytes.

| `n` | default `"…"` (3 bytes) | `omission: nil` | `omission: " "` | `omission: "🖖"` (4 bytes) |
|---|---|---|---|---|
| 16 | `"👍👍👍👍"` | same | same | same |
| 15 | `"👍👍👍…"` (15) | `"👍👍👍"` (12) | `"👍👍👍 "` (13) | `"👍👍🖖"` (12) |
| 12 | `"👍👍…"` (11) | `"👍👍👍"` | `"👍👍 "` | `"👍🖖"` |
| 8 | `"👍…"` (7) | `"👍👍"` | `"👍 "` | `"🖖"` |
| 5 | `"…"` (3) | `"👍"` (4) | `"👍 "` (5) | `"🖖"` |
| 4 | `"…"` (3) | `"👍"` (4) | `" "` (1) | `"🖖"` |
| 3 | `"…"` (3) | `""` | `" "` | `ArgumentError` |

Bytesize may be strictly less than `n` (12 → `"👍👍…"` is 11). That is required: the next 4-byte cluster does not fit in the remaining 1 byte.

That proves truncation is not `byteslice`. A byteslice at 15 would split the last thumbs-up and yield invalid UTF-8. It also proves the prefix budget is `n - omission.bytesize`, and that leftover bytes smaller than the next cluster are discarded rather than filled with a partial character.

---

**4. Grapheme clusters**

Do not use `chars` or `codepoints` as the unit. Use `each_grapheme_cluster`.

`"a ❤️ b"` clusters as `["a", " ", "❤️", " ", "b"]` with sizes `[1, 1, 6, 1, 1]` (`❤️` is U+2764 + U+FE0F). With `omission: nil`:

- `n=1` → `"a"`
- `n=2..7` → `"a "` (2 bytes) — ❤️ does not fit
- `n=8` → `"a ❤️"`
- `n=9` → `"a ❤️ "`
- `n=10` → full string (dup)

`"👩‍❤️‍👩"` is one 20-byte cluster. `omission: nil` and `n` in `1..19` → `""`; `n>=20` → the original (dup).

NFD `"é"` (`"e\u0301"`, 3 bytes, one cluster): `n=1` and `n=2` → `""`; `n=3` → the original. A codepoint walk would return `"e"` at 1.

That proves the walker is grapheme clusters, not bytes or codepoints. Combining marks and ZWJ sequences are kept whole or dropped whole. Returning `""` for a too-large first cluster proves there is no fallback to a partial cluster.

---

**5. Exact byte boundaries**

`"abc👍def"` is `a b c` + 4-byte emoji + `d e f` (10 bytes). `omission: nil` so the budget is the prefix itself:

| `n` | expect | bytesize |
|---|---|---|
| 1, 2, 3 | `"a"`, `"ab"`, `"abc"` | 1, 2, 3 |
| 4, 5, 6 | `"abc"` | 3 |
| 7 | `"abc👍"` | 7 |
| 8, 9, 10 | `"abc👍d"`, `"abc👍de"`, full | 8, 9, 10 |
| 11 | full, via dup | 10 |

That proves mid-character cut points do not emit a broken UTF-8 sequence: 4, 5, and 6 all refuse the emoji and stay at 3. 7 is the first legal include. Together with the 15-byte thumbs-up case, this is the invalid-encoding test: `valid_encoding?` must stay true at every `n`.

---

**6. Custom and nil omissions**

`omission ||= ""` is the first line. Probe it directly:

- `"Hello World".truncate_bytes(5, omission: nil)` → `"Hello"`
- `"Hello World".truncate_bytes(5, omission: "")` → `"Hello"` (nil and empty match)
- `"Hello World".truncate_bytes(8, omission: "[...]")` → `"Hel[...]"` (3 + 5 = 8)
- `"👍👍👍👍".truncate_bytes(15, omission: " ")` → `"👍👍👍 "`
- `"👍👍👍👍".truncate_bytes(15, omission: "🖖")` → `"👍👍🖖"`

That proves `nil` is empty string, not the default `"…"`. It proves the omission is appended after the prefix, not interpolated, and that its bytesize, not its character length, shrinks the prefix (`"🖖"` is 4 bytes, so only two thumbs-ups remain at 15). A refactor that treated `omission: nil` as “use default” would fail the first row.

**7. Omission equal to or larger than the budget**

Larger: `"Hello World".truncate_bytes(2, omission: "…")` and `"👍👍👍👍".truncate_bytes(3, omission: "🖖")` must raise `ArgumentError` whose message is:

`Omission "…" is 3, larger than the truncation length of 2 bytes`

(and the analogous 4/3 message for 🖖). Rescue the class, message, and confirm the receiver is unchanged.

Equal: `"Hello World".truncate_bytes(3, omission: "…")` → `"…"`. Hold the omission in a local `om`. Result must be `== om`, `!equal?(om)`, `!equal?(receiver)`.

That proves the `>` branch raises rather than returning a clipped omission or an empty string, and that the `==` branch returns a copy of the omission with no prefix. It also proves this path does not go through `self.class.new` (see subclass below).

---

**8. Encoding and subclass preservation**

Encoding, three paths:

- Within budget: `String.new("abc", encoding: Encoding::US_ASCII).truncate_bytes(10)` stays US-ASCII.
- Truncation with a compatible omission: same string `.truncate_bytes(5, omission: ".")` stays US-ASCII (`"abcd."`).
- Truncation with the default `"…"`: US-ASCII receiver becomes UTF-8 (`"ab…"`), because appending U+2026 transcodes the result. That is current behavior; a “preserve encoding at all costs” refactor that raised `EncodingError` would be a change.
- Explicit UTF-8: `String.new("a" * 30, encoding: Encoding::UTF_8).truncate_bytes(15)` is UTF-8, `"aaaaaaaaaaaa…"`.
- UTF-16LE: `"hello world".encode("UTF-16LE").truncate_bytes(10, omission: "…".encode("UTF-16LE"))` stays UTF-16LE, 10 bytes, valid.

Subclass:

```ruby
class MyString < String; end
s = MyString.new("hello world")
```

- `s.truncate_bytes(20)` → `MyString` (dup)
- `s.truncate_bytes(8)` → `MyString` (`self.class.new`)
- `s.truncate_bytes(3, omission: "…")` → `String`, not `MyString` (`omission.dup` copies the omission’s class)

That last row is the easy silent break: a refactor that always builds `self.class.new` would change it. Encoding on the truncation path comes from `force_encoding(encoding)` on a new instance of the receiver’s class; subclass plus US-ASCII together prove both the class and the encoding are taken from the receiver, not from a UTF-8 literal.

---

**9. Receiver mutation**

Use unfrozen copies (`+"hello world"`) so a bang-style refactor can actually mutate.

- `s = +"hello world"; before = s.dup; r = s.truncate_bytes(5)` → `s == before`, `!r.equal?(s)`, `r == "he…"`
- `s = +"hello"; r = s.truncate_bytes(5)` → `s == "hello"`, `!r.equal?(s)` (dup, not `self`)
- frozen receiver: `"hello world".freeze.truncate_bytes(5)` returns unfrozen `"he…"` and does not raise `FrozenError`
- mutate the result, not the input: `r = "hello".truncate_bytes(5); r << "!";` receiver stays `"hello"`

That proves every branch allocates. `dup` on the within-budget path, `omission.dup` on the equal path, and `self.class.new` on the walk path. Returning `self` when `bytesize <= n` would fail the identity check even though `==` still passes.
