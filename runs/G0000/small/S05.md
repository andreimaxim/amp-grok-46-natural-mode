The proposal would break the documented strict contract. Review comment:

`ActiveModel::Errors#add` must not append before the `options[:strict]` check. Strict is a substitute for adding, not a post-add raise.

Current order in [activemodel/lib/active_model/errors.rb](file:///home/user/workspace/repo/activemodel/lib/active_model/errors.rb):

```341:352:activemodel/lib/active_model/errors.rb
    def add(attribute, type = :invalid, **options)
      attribute, type, options = normalize_arguments(attribute, type, **options)
      error = Error.new(@base, attribute, type, **options)

      if exception = options[:strict]
        exception = ActiveModel::StrictValidationFailed if exception == true
        raise exception, error.full_message
      end

      @errors.append(error)

      error
    end
```

That matches the documented contract: `strict: true` raises `ActiveModel::StrictValidationFailed` instead of adding; `strict:` may also be any other exception class; after a strict raise, `person.errors.messages` is `{}`.

```321:329:activemodel/lib/active_model/errors.rb

    # ActiveModel::StrictValidationFailed instead of adding the error.
    # <tt>:strict</tt> option can also be set to any other exception.
    #
    #   person.errors.add(:name, :invalid, strict: true)
    #   # => ActiveModel::StrictValidationFailed: Name is invalid
    #   person.errors.add(:name, :invalid, strict: NameIsInvalid)
    #   # => NameIsInvalid: Name is invalid
    #
    #   person.errors.messages # => {}
```

`validates!` repeats the same “raise instead of adding” wording.

Appending first would break that:

- Collection mutation. After rescue, `@errors` would contain the new `ActiveModel::Error`. Callers and later `valid?` / `full_messages` / `added?` would see an error that the contract says was never recorded. The docs’ `person.errors.messages # => {}` example would be false.
- Exception class and message. The raise already carries the payload: `raise exception, error.full_message`. Rescuers get `ActiveModel::StrictValidationFailed` (or the custom class) with the full message (`"Title can't be blank"`). There is nothing useful on the collection that is not already on the exception. Tests in [activemodel/test/cases/validations_test.rb](file:///home/user/workspace/repo/activemodel/test/cases/validations_test.rb) cover this: default class, helper-level `strict: true`, `validates!`, `test_strict_validation_custom_exception` (`CustomStrictValidationException`), and `test_strict_validation_error_message`.
- Custom strict exception classes. `strict:` can be an arbitrary class (`NameIsInvalid`, `TokenLengthException`, `CustomStrictValidationException`). Those classes are not `ActiveModel::Error` wrappers and do not expose `.errors` / `.error`. Inspecting the collection after rescue is not part of that API; changing `add` to mutate first would still leave custom exceptions without a structured error object.
- Normal `add` return. Non-strict `add` already returns the `ActiveModel::Error` (`test "add creates an error object and returns it"`). The object exists before the strict branch; only `@errors.append` is skipped. Callers who need the object without raising already have it. Strict is the path that must not return or store it.

Rescuing and then reading `record.errors` is the non-strict model. Strict validations are exceptional and must leave the record’s error collection unchanged. Keep raise-before-append.
