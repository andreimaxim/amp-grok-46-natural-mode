Reject appending before the strict check. Strict `add` is defined as raise-instead-of-record, not raise-after-record.

Current `add` builds the `ActiveModel::Error` only so it can raise with `error.full_message`, then returns without recording:

```341:353:activemodel/lib/active_model/errors.rb
    def add(attribute, type = :invalid, **options)
      attribute, type, options = normalize_arguments(attribute, type, **options)
      error = Error.new(@base, attribute, type, **options)

      if exception = options[:strict]
        exception = ActiveModel::StrictValidationFailed if exception == true
        raise exception, error.full_message
      end

      @errors.append(error)

      error
    end
```

The documented contract is “raise … instead of adding the error.” After those examples, `person.errors.messages` is `{}`. `validates!` says the same: raise instead of adding. `StrictValidationFailed` is for failures that are exceptional, not accumulated.

Appending first breaks that. After `rescue`, the collection is mutated. Mixed validators would leave both the earlier non-strict errors and the strict one. Callers who catch and continue would see `empty?` / `messages` / `details` as if this were a normal validation. The docs’ `messages # => {}` example would be wrong.

Exception class and message are already the inspectable result. `strict: true` raises `ActiveModel::StrictValidationFailed` with `error.full_message` (`"Title can't be blank"` in `test_strict_validation_error_message`). `strict: SomeClass` raises that class with the same message (`test_strict_validation_custom_exception`, `strict: NameIsInvalid` in the `add` docs). Rescue already has type and message. Putting the object in `@errors` is not required for that, and a custom class is not a subclass of `StrictValidationFailed` with an attached error.

Non-strict `add` still returns the `ActiveModel::Error` and that object is `errors.objects.first` (`add creates an error object and returns it`). Strict `add` does not return; it raises. “Inspect it after rescuing” cannot mean the return value. It would mean `errors.last`, which is ambiguous once anything else is already recorded.

If someone needs the `Error` after rescue, attach it to the exception. Do not record it. The current order — construct, maybe raise, else append and return — is the contract.
