**Block.** The remaining enqueue path still serializes mailer identity plus original args/params and re-runs the action. It never serializes the generated `Mail::Message`, so prior access (and any mutation) is still silently discarded.

## What `processed?` means

[`ActionMailer::MessageDelivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb) is a lazy `Delegator` around a `Mail::Message`. Construction stores the mailer class, action, and args and leaves both the mailer instance and message unloaded:

```21:30:actionmailer/lib/action_mailer/message_delivery.rb
    def initialize(mailer_class, action, *args, **kwargs) # :nodoc:
      args << Hash.ruby2_keywords_hash(kwargs) unless kwargs.empty?
      @mailer_class, @action, @args = mailer_class, action, args

      # The mail is only processed if we try to call any methods on it.
      # Typical usage will leave it unloaded and call deliver_later.
      @processed_mailer = nil
      @mail_message = nil
    end
```

`processed?` is true once either exists:

```47:50:actionmailer/lib/action_mailer/message_delivery.rb
    def processed?
      @processed_mailer || @mail_message
    end
```

That happens if you call `#message`, any delegated `Mail::Message` method (`to`, `subject`, `body`, header writers, …) via [`__getobj__`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L32-L35), or `#deliver_now` / `#deliver_now!` (those go through [`processed_mailer`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L136-L140)). Processing runs the mailer action now:

```136:140:actionmailer/lib/action_mailer/message_delivery.rb
      def processed_mailer
        @processed_mailer ||= @mailer_class.new.tap do |mailer|
          mailer.process @action, *@args
        end
      end
```

Laziness is the contract: typical `deliver_later` never builds the message in the caller.

## What is actually serialized

The proposed diff still does this:

```153:154:actionmailer/lib/action_mailer/message_delivery.rb
          @mailer_class.delivery_job.set(options).perform_later(
            @mailer_class.name, @action.to_s, delivery_method.to_s, args: @args)
```

The job payload is:

- mailer class name
- action name as a string
- delivery method as a string (`"deliver_now"` or `"deliver_now!"`)
- original method args

Not the `Mail::Message`. [`MailDeliveryJob#perform`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L21-L30) rebuilds a *new* `MessageDelivery` and delivers that:

```21:30:actionmailer/lib/action_mailer/mail_delivery_job.rb
    def perform(mailer, mail_method, delivery_method, args:, kwargs: nil, params: nil)
      mailer_class = params ? mailer.constantize.with(params) : mailer.constantize
      message = if kwargs
        mailer_class.public_send(mail_method, *args, **kwargs)
      else
        mailer_class.public_send(mail_method, *args)
      end
      message.send(delivery_method)
    end
```

The current raise text is accurate: only the mailer method arguments travel with the job. The author’s “job can serialize the generated `Mail::Message`” claim does not match this implementation.

The no-prior-access path is already correct and is tested: [`should enqueue the email with :deliver_now delivery method`](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L57-L61) and the `deliver_later!` sibling at [L64–L67](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L64-L67) assert those args, not a message object.

## `deliver_later` vs `deliver_later!`

Both call `enqueue_delivery`; only the later delivery method differs ([`deliver_later!` → `:deliver_now!`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L77-L79), [`deliver_later` → `:deliver_now`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L104-L106)). The `processed?` guard applies to both. Removing it does not make bang delivery serialize the in-memory message; the job still re-runs the action and then calls `deliver_now!` (skipping `perform_deliveries` / `raise_delivery_errors`).

## Observable behavior after mutation

```ruby

mail.to = ["other@example.com"]   # processes via Delegator
mail.subject = "changed"
mail.body = "changed"
mail.deliver_later                # today: RuntimeError
```

After the PR, enqueue still sends `args: [1, 2, 3]`. The worker rebuilds the original mail. Header/body edits are dropped. Even `#message` with no edits still re-runs the action later: I18n/time, queries, callbacks, and any non-idempotent work in the mailer run twice, and the delivered object is not the one you inspected.

The only existing coverage is [`deliver_later after accessing the message is disallowed`](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L133-L138), which only asserts `RuntimeError`. There is no test that a mutated message is what gets delivered, because that is not the design.

## Serialization failures vs the no-prior-access path

[`job delegates deserialization errors to mailer class`](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L253-L266) injects a GlobalID arg whose `find`/`where` blow up. `MailDeliveryJob` rescues and hands `DeserializationError` to the mailer class. That is about **mailer arguments**, not `Mail::Message`.

If the claim were implemented (serialize the generated message), it would be a different job contract: `Mail::Message` is not GlobalID-backed; procs in `default`, Tempfile/IO attachments, and other runtime state often fail Active Job serialization. The proposed diff does not even attempt that.

Unprocessed `deliver_later` / `deliver_later!` should keep working. That is not a reason to drop the guard.

## Gaps in the claim and tests

- Claim: job serializes `Mail::Message`. Code: job serializes class/action/method/args (and params only when unprocessed parameterized).
- One test would start failing (`deliver_later after accessing…`); nothing replaces it with a mutation or identity assertion.
- No coverage for `deliver_later!` after access, parameterized-after-access (the params drop), custom `delivery_job` after access, or “serialize Mail::Message”.
- [`deliver_all_later`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer.rb#L88-L100) already skips the guard and always uses args/params; that is another reason not to treat “already processed” as “the in-memory message will be sent”.

## Smallest viable direction

Keep the `processed?` raise. The error’s workarounds are the real API: don’t touch the message before `#deliver_later`, mutate only inside the mailer action, or write a custom job that *does* accept a serializable payload.

Do not “just enqueue anyway.” If someone needs enqueue-after-inspect, that is a new job shape (snapshot or explicit serializable mail), plus parameterized `params:` on every path, plus tests for mutation, `deliver_later!`, custom jobs, and serialization failure. That is not this one-line deletion.
