**Problem frame:** A Rails maintainer or app developer investigating a request needs to tell why the action never ran or why later callbacks never ran. Today a callback that has already performed a response can stop the rest of the cycle on purpose, but that stop is easy to confuse with a skipped condition, an around callback that never continued, an exception, or a second render/redirect in the same action. The current halt signal exists only for some of those cases, names the filter, and always describes the stop as “rendered or redirected.”

This is **discovery** for maintainers considering whether that observability is enough. It is not a commitment to change halt, render, or redirect behavior.

**Actors:** Application developers writing `before_action`, `around_action`, and `after_action`. Maintainers and operators reading request logs or events when an action body or later callback did not run. Reviewers diagnosing `AbstractController::DoubleRenderError` after a response was already performed.

---

## Current observable baseline

Grounded in Action Controller / Abstract Controller behavior and tests, not in a proposed design.

A controller action runs inside `before_action` / `around_action` / `after_action`. After each **before** callback, the chain asks whether a response has already been performed (`performed?`: a response body is set, or the response is committed). If so, the remaining before callbacks, the action, and `after_action` callbacks do not run. That is the callback terminator. Active Support then invokes the halt hook, but **only for before callbacks**.

Performing a response is an observable state, not an exit from the current Ruby method. `render`, `redirect_to`, and `head` set that state. They do not return from the method. A second `render`, `redirect_to`, or `head` in the same action raises `AbstractController::DoubleRenderError`, whose message says you may call render or redirect at most once and that neither terminates execution.

Existing external signals, when a **before** callback performs a response:

- HTTP result is the callback’s response (body, redirect, or empty `head` body), not the action’s.
- Request log line: `Filter chain halted as :filter_name rendered or redirected` (info).
- Notification / structured event carrying the filter name (`halted_callback.action_controller` → `action_controller.callback_halted`).
- The action body and later `after_action` callbacks do not run, including prepended after callbacks.

What those signals do **not** currently establish:

- Whether the callback rendered, redirected, or used `head`.
- Why the callback performed a response.
- Whether an `around_action` stopped the cycle by not yielding (that path does not use the before terminator and does not emit the halt line in current tests).
- Whether a callback was simply skipped by `:only`, `:except`, `:if`, or `:unless` (skip is not a halt).
- The difference between an intentional halt and continuing in the same method into a second render/redirect (`DoubleRenderError`).

Guides already describe the halt as cancelling the action and remaining callbacks when a `before_action` renders or redirects. They also state that `after_action` does not run if an exception is raised, and that code after `yield` in an `around_action` can still run when the action raises if the callback uses `ensure`.

## Desired outcomes

When the work is complete, an investigator of a request should be able to tell, from **external** evidence, which of these happened:

1. A callback **intentionally performed a response**, so the action and remaining callbacks did not run.
2. A callback **did not run** because its condition did not match.
3. An `around_action` **did not continue** into the rest of the cycle (did not yield).
4. The action or an around callback **raised**, so later work did not run.
5. The same action **attempted a second render or redirect** after a response was already performed.

Success is qualitative: a person can distinguish those cases without inferring them from missing side effects alone. This does **not** require any particular new log line, notification, API, metric, or implementation.

**Hypothesis (not a user-supplied fact):** the painful case is not missing halt in the happy path, but the overlap between “halted because a response was performed,” “stopped because around never continued,” and “kept running and then double-rendered.”

---

## Explicit non-goals

- Changing when a performed response stops the callback chain.
- Making `render` / `redirect_to` / `head` return from the current method.
- Changing `DoubleRenderError` rules or message as the goal of this work.
- Treating skipped `:only` / `:except` / `:if` / `:unless` callbacks as halts.
- Requiring a specific log, event, dashboard, API, or instrumentation shape.
- Expanding into Action Mailer or other Abstract Controller users unless maintainers decide they share the same observability need.

## Behavioral examples

These are **required cases** for agreeing on the problem, not an acceptance-test catalog. “Observable result” is what exists today; desired distinction is what clearer observability would make possible.

**Rendering before callback**  
Given a `before_action` that renders and an action plus `after_action` that would also render or record work.  
When the request hits that action.  
Today: the callback’s body is the response; the action does not run; after callbacks do not run; if this is Action Controller, the halt line names that before filter and says it “rendered or redirected.”  
Desired distinction: an investigator can tell this was an intentional performed-response halt, not a missing action or a later callback failure.

**Redirecting before callback**  
Given a `before_action` that redirects and an action / after callback that would otherwise run.  
When the request hits that action.  
Today: the response is the redirect; the original action does not run; after callbacks do not run; the halt line still says “rendered or redirected.” The redirect target is a separate later request if followed.  
Desired distinction: halt because of redirect is separable from halt because of render, and from “the action ran and then redirected.”

**Non-yielding around callback**  
Given `before_action` A, `around_action` that does not yield, then another before, the action, and an after.  
When the request is processed.  
Today: A runs; the around runs and does not continue; later befores, the action, and afters do not run; this does not raise. Current halt logging is specified for before-callback termination, not this path.  
Desired distinction: “around did not continue” is not mistaken for “a before callback rendered or redirected,” especially if no response was performed.

**Exception before yield**  
Given an `around_action` that raises before yielding.  
When the request is processed.  
Today: the action does not run; the exception propagates; `after_action` does not run.  
Desired distinction: this is a failure, not a performed-response halt.

**Exception after yield**  
Given an `around_action` that yields, then raises.  
When the request is processed.  
Today: the action did run; the exception then propagates; `after_action` does not run. Code after `yield` can still run if the around uses `ensure`.  
Desired distinction: the action ran and then failed, which is not “the chain halted because a callback performed a response.”

**Conditional callbacks**  
Given a before callback limited with `:only` / `:except` or `:if` / `:unless`.  
When the request is for an action that does not match.  
Today: that callback does not run; the action still runs unless something else performs a response. Reused condition hashes and array lists behave the same: unmatched means skipped, not halted.  
Desired distinction: “did not run because it was not selected” is not reported as a halt.

**Action that attempts a second render**  
Given an action (or a callback that does not stop the method) that renders or redirects and then renders, redirects, or calls `head` again without leaving the method.  
When that code runs.  
Today: `AbstractController::DoubleRenderError` is raised, with a message that render/redirect do not terminate execution. This is the opposite of callback-chain halt: execution continued after a response was performed. If a before callback already performed the response, the action is not invoked, so this error does not come from the skipped action body.  
Desired distinction: continued-after-perform is not described as a successful halt.

## External success signals (not a chosen design)

Signals that **could** distinguish the cases, without requiring any one of them:

- Evidence that a named callback performed a response, versus evidence that no callback ran because of a condition.
- Evidence that the action body did or did not run, independent of whether a response was produced.
- Evidence that an around callback did not continue, even when `performed?` is still false.
- Evidence that an exception occurred before versus after the action ran.
- Evidence that a second render/redirect was attempted in the same action, as an error, not as a halt.
- Enough context to tell render, redirect, and `head` apart if maintainers decide that distinction matters; or a clear choice that they need not be distinguished.

Failure of the framing: if investigators already get this from the existing halt line plus `DoubleRenderError`, extra observability is not the problem. If the real pain is that `render`/`redirect_to` do not return, the problem is control flow, not observability.

Evidence that should trigger **stop / revise**: a change that makes skipped conditionals look like halts; that makes non-yielding around look like a performed-response halt; that suppresses `DoubleRenderError`; or that changes who receives the HTTP response.

---

## Unresolved product questions

- Is the audience primarily app developers in development logs, operators in production, framework maintainers, or all three?
- Must render, redirect, and `head` be distinguishable, or is “performed a response” enough?
- Is a non-yielding `around_action` in scope as a halt-like stop, a separate “did not continue” case, or out of scope?
- Should halt-like stops without a performed response (around never yields and never renders) be visible at all?
- Is Action Mailer / other Abstract Controller callback users in scope, given that the current halt log and event live on Action Controller?
- Is the existing before-callback halt line already sufficient for the before/render/redirect cases, leaving only the around / exception / double-render distinctions open?
- Should “clearer observability” include teaching the documented rule that render/redirect do not return, or only request-time evidence?

---

This is a working brief for confirmation, not a settled spec. The main assumption to veto: the job is to make **intentional performed-response halt** distinguishable from skip, non-continuation, exception, and double-render — not to change those behaviors. If that framing is wrong, the examples and success signals should change before any design work.
