Current contract, then the checks that pin it. The three types cooperate; they do not share one clock. Existing tests cover only the happy path for the three terminal statuses, disablement at schedule time, and a missing record.

# Current contract (this revision)

```text
status bang (delivered! / failed! / bounced!)
  InboundEmail#update!(status:)
    after_update_commit, if incinerate && status_previously_changed? && processed?
      Incineratable#incinerate_later
        IncinerationJob.schedule(email)
          set(wait: incinerate_after).perform_later(email)

IncinerationJob#perform(email)
  email.incinerate
    Incineration#run
      destroy!  iff  due? && processed?

due?        = updated_at < ActionMailbox.incinerate_after.ago.end_of_day   # strict <
processed?  = delivered? || failed? || bounced?
```

Sources: [incineratable.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable.rb), [incineration.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable/incineration.rb), [incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb), [inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb) (`processed?` at lines 41–43). Enum bang methods are `update!` ([enum.rb](file:///home/user/workspace/repo/activerecord/lib/active_record/enum.rb) around the `#{value_method_name}!` definition). `end_of_day` is 23:59:59.999999 ([time/calculations.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/time/calculations.rb)).

Two independent clocks:

- **Schedule clock** — `IncinerationJob.set(wait: ActionMailbox.incinerate_after)` ([incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb) `schedule`).
- **Destroy clock** — `updated_at < incinerate_after.ago.end_of_day` evaluated at perform time, against the **current** row ([incineration.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable/incineration.rb) `due?`).

Existing tests exercise the schedule clock (`at: 30.days.from_now`) and then `travel 30.days` before `perform_enqueued_jobs`. They do **not** pin `due?` independently, so a refactor that drops `end_of_day` or switches to `created_at` can still pass [incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb).

# Invariants vs incidental

**Preserve these.**

1. **Processed set.** `processed?` is exactly delivered, failed, or bounced — not pending or processing. [inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb) `processed?`; lifecycle comment at lines 10–17; guide [action_mailbox_basics.md](file:///home/user/workspace/repo/guides/source/action_mailbox_basics.md) “Incineration of InboundEmails”.
2. **Schedule only after a committed status change into that set, and only if `ActionMailbox.incinerate` is true.** Callback: `after_update_commit :incinerate_later, if: -> { ActionMailbox.incinerate && status_previously_changed? && processed? }`. Create-with-processed-status does not schedule. Rolled-back updates do not. Non-status updates do not. [incineratable.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable.rb); skip case in [incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb).
3. **Each qualifying status change enqueues another job.** The callback has no uniqueness/idempotency. Repeated `delivered!` does not, because `status_previously_changed?` is false. `delivered!` then `failed!` does.
4. **Job wait equals `ActionMailbox.incinerate_after` at schedule time.** Default `30.days` is config, not hardcoded in the trio ([action_mailbox.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox.rb), [engine.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/engine.rb)). Tests currently hardcode `30.days.from_now` ([incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb)); pin `wait:` / `at:` against the **current** `incinerate_after`, not the literal 30.
5. **Job queue is `ActionMailbox.queues[:incineration]`.** `nil` means Active Job’s default queue (Rails 6.1+). [incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb) `queue_as`; [configuration.rb](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb); [configuration_test.rb](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb) around the incineration queue tests.
6. **Perform re-reads eligibility. It does not destroy because a job exists.** `perform` → `incinerate` → `destroy!` only if `due? && processed?`. A later `updated_at`, or a move out of processed, cancels destruction without cancelling the job.
7. **`due?` is strict `<` against `incinerate_after.ago.end_of_day`, using `updated_at`.** Equality is not due. Time-of-day of `updated_at` does not matter except at exact `end_of_day` (that instant stays not-due until the following calendar day). Unexecuted by current tests.
8. **`ActionMailbox.incinerate = false` suppresses scheduling only.** It is not consulted in `Incineration#run` or `perform`. An already-enqueued job still incinerates if due and processed. Job comment overstates this ([incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb) lines 10–11).
9. **Missing record: job is discarded, no error surfaces.** `discard_on ActiveJob::DeserializationError::RecordNotFound` is the live path; covered by [incineration_job_test.rb](file:///home/user/workspace/repo/actionmailbox/test/jobs/incineration_job_test.rb).
10. **Successful incineration is `destroy!` of the inbound email.** The `raw_email` attachment row goes with it (`has_one …_attachment, dependent: :destroy`). Blob purge is Active Storage `dependent: :purge_later` — `PurgeJob` after commit, not inside `IncinerationJob`. [inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb) `has_one_attached`; [attached/model.rb](file:///home/user/workspace/repo/activestorage/lib/active_storage/attached/model.rb); [attachment.rb](file:///home/user/workspace/repo/activestorage/app/models/active_storage/attachment.rb) `purge_dependent_blob`.
11. **Unprocessed records are never destroyed by `incinerate`, even if `due?`.** Direct `Incineration#run` and the job share this gate.
12. **Public entry points stay: `incinerate_later`, `incinerate`, `IncinerationJob.schedule` / `perform`.** Conductor calls `incinerate` immediately ([incinerates_controller.rb](file:///home/user/workspace/repo/actionmailbox/app/controllers/rails/conductor/action_mailbox/incinerates_controller.rb)) and is still gated by `due? && processed?`.

**Do not pin these.**

- Existence of the `Incineration` command class, its private `due?` / `processed?` names, or the concern/job/command file split.
- `discard_on ActiveRecord::RecordNotFound` in addition to deserialization — `perform` never `find`s; that clause is unused on the current path.
- Callback *name* (`after_update_commit` vs `after_commit on: :update`).
- Test helper default `status: :processing` ([test_helper.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/test_helper.rb)).
- Hardcoded `30.days` in unit tests vs reading `incinerate_after`.
- Comment in `Incineration` (“processed after the incinerate_after time”) — it contradicts `due?`.
- Synchronous blob/file deletion inside the incineration job.
- Queue symbol `:action_mailbox_incineration` on apps with 6.1+ defaults (dummy loads current defaults, so the queue is `nil`).

# How to test (controls and assertions)

Use Action Mailbox’s dummy + `ActiveJob::TestHelper` already mixed into `ActiveSupport::TestCase` ([test_helper.rb](file:///home/user/workspace/repo/actionmailbox/test/test_helper.rb)). Keep incineration tests on the test adapter.

**Time.** `freeze_time` at an explicit wall clock, then `travel` / `travel_to`. Never rely on “now” being away from `end_of_day`. Split clocks:

- Schedule tests: freeze, trigger status change, `assert_enqueued_with job:, at:, queue:` (or `args:`), do **not** perform.
- Due-gate tests: call `email.incinerate` (or `Incineration.new(email).run` if the class remains) with `updated_at` and `Time.current` set explicitly; do **not** go through `wait:`.
- Combined tests: enqueue, travel, `perform_enqueued_jobs only: ActionMailbox::IncinerationJob`, then assert DB.

**DB-visible outcomes.** Prefer `ActionMailbox::InboundEmail.exists?(id)`, `count`, `reload` status, and `ActiveStorage::Attachment` / `Blob` existence — not in-memory `destroyed?` alone. `destroy!` is the success path; a no-op must leave the row and `updated_at` unchanged.

**Jobs.** `assert_enqueued_with` / `assert_no_enqueued_jobs only: IncinerationJob` / `assert_enqueued_jobs n, only:`. After a real destroy, allow `ActiveStorage::PurgeJob` (or equivalent) to be enqueued; do not `perform_enqueued_jobs` without `only:` if you are counting incineration jobs.

**Config.** `ActionMailbox.with(incinerate: false)` or assign/restore as the skip test does. For `incinerate_after` and queue, stub/assign around the example; do not assume 30 days inside new assertions.

## Record changed after scheduling

Freeze at a known time. `delivered!`. Capture job.

1. **Touch / bump `updated_at` after enqueue.** `travel incinerate_after`, perform job. Row remains. Then travel far enough that new `updated_at` satisfies `due?`, perform a *new* `incinerate` (or a second scheduled job if you enqueue one) — row gone. This is the core stale-job invariant.
2. **Move out of processed** (`processing!` after `delivered!`). Original job runs at the original wait — row remains (`processed?` false). Note `processing!` is itself a status change but not processed, so it must not enqueue a replacement incineration job.
3. **Stay processed, only `updated_at` moves** — same as (1). Attachment `touch` can do this if `ActiveStorage.touch_attachment_records` is true ([attachment.rb](file:///home/user/workspace/repo/activestorage/app/models/active_storage/attachment.rb)); an optional example attaching/replacing `raw_email` after delivery is enough.

Do these through `perform_enqueued_jobs only: IncinerationJob` so you prove the job path re-checks, not only `Incineration#run`.

## Age boundary (`updated_at`, `ago`, `end_of_day`)

Drive `incinerate` directly. Freeze to an explicit timestamp.

Let `T` be `updated_at`, `D = ActionMailbox.incinerate_after`. `due?` iff `T < (Time.current - D).end_of_day`.

Pin at least:

| Setup | Expect |
|---|---|
| Processed, `Time.current == T + D` (same clock as job wait), `T` not `end_of_day` | destroy (matches existing `travel 30.days` tests) |
| Processed, `Time.current` just **before** `(T.to_date + D).beginning_of_day` when that would make `(now - D).end_of_day <= T` | **no** destroy |
| Processed, `Time.current` at the first instant `T < (now - D).end_of_day` | destroy |
| Processed, `updated_at` **equal** to `D.ago.end_of_day` | **no** destroy (strict `<`) |
| Processed, `updated_at` one tick before that | destroy |
| Processed, `updated_at = Time.current.end_of_day`, then `travel D` | **no** destroy yet; due only after `(now - D)` falls on a **later** calendar day |
| Unprocessed, even with `updated_at` ancient | no destroy |

Implementation sketch (behavior, not required API):

```ruby
freeze_time Time.utc(2026, 1, 15, 12, 0, 0)
email = create_inbound_email_from_fixture("welcome.eml")
email.update!(status: :delivered, updated_at: Time.current)

travel_to Time.utc(2026, 2, 14, 12, 0, 0) # 30 days later, noon
assert ActionMailbox::InboundEmail.exists?(email.id)
email.incinerate
assert_not ActionMailbox::InboundEmail.exists?(email.id)
```

And a separate example at `end_of_day` to catch `<=` vs `<` and dropping `end_of_day`.

Do **not** treat “job ran” as “due?”. A refactor that destroys in `perform` without `due?` would still pass the current 30-day job tests whenever wait and freeze_time line up.
