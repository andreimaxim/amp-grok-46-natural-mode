### Security invariants vs String compatibility

**Security (must not regress; these are XSS contracts):**

1. On a **safe** receiver, raw `"<script>"` is escaped; `"<script>".html_safe` is not. Already-escaped html_safe input is not double-escaped.
2. `%` on a **safe** template escapes unsafe args and leaves html_safe args raw. Result stays `html_safe?`.
3. `safe_concat` never escapes. It is legal only while `html_safe?`. On an unsafe receiver it raises `SafeConcatError` and must not mutate.
4. An unsafe buffer concatenated onto a **safe** one is escaped (`clean + dirty` → `"hello&lt;&gt;"`).
5. Dirtied buffers stay `html_safe? == false` through `dup`, `*`, `%`, `[]`/`slice`/`slice!`, `chr`. Bang `gsub!`/`sub!` are the dirtier; they cannot be “cleaned” by later slice/copy/format.
6. `html_safe?` true means “insert into HTML as-is.” False means “still untrusted.” A refactor must not flip that bit back to true except via `String#html_safe`.

**String compatibility (must match, but not an XSS gate):**

- `SafeBuffer < String`; `<<` is `concat`; both return `self`.
- `+`, `%`, `*` return a **new** object; `concat`/`<<`/`safe_concat`/`gsub!`/`slice!` mutate.
- `concat(nil)` is a no-op and still returns `self`.
- Unsafe `[]`/`slice`/`slice!`/`chr` return a plain `String` via `to_str` (not a `SafeBuffer`). Safe ones wrap a new `SafeBuffer` and keep `html_safe?`.
- `gsub`/`sub` (non-bang) return a plain `String` that is not html_safe; bang versions mark the receiver unsafe then call `super`.

### Assertions that matter, by case

For **#1–4, 7, 9, 13–17, 19**: `assert_equal` the escaped/raw string, `assert_equal ActiveSupport::SafeBuffer, result.class`, `assert_predicate result, :html_safe?`, and `assert_same buf, buf << x` (or `assert_not_same` for `+`/`%`/`*`).

For **#5–6, 8, 18, 20–23**: the string may contain raw `<>` / `<script>`; that is required, not a bug. Assert `html_safe? == false` on **both** result and receiver. For #12 assert the exception **and** `buf == "<>"` afterward.

For **#10**: this is the privileged template path. Assert **no** escaping, `assert_same`, still `html_safe?`. If a refactor routes `safe_concat` through `concat`, this case becomes XSS.

For **#23 vs #24**: safety is preserved, but **class is not**. Unsafe slice must be `String`; safe slice must be `SafeBuffer`. Checking only `html_safe?` would miss a wrap/unwrap regression.

### What the existing file does not pin

- Success-path `safe_concat` (no escape, mutates, stays safe).
- Exact strings for `*` (`"<br /><br />"`, `"<><>"`), `%` on an unsafe receiver, positional `%` escaping, mixed html_safe/unsafe `%` args.
- Result **class** of `[]`/`slice`/`slice!` on an already-unsafe `SafeBuffer` (`String`).
- `concat`/`<<` identity (`assert_same`) and non-mutation of `+`/`%`/`*`.
- `safe_concat` after a failed raise (receiver unchanged) is implied by the raise test but not asserted.

Treat those as oracle checks for the refactor, not as invitations to change production code here.
