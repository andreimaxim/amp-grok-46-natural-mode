## Assistant

`strict_loading!` is instance state, not a query. It flips `@strict_loading` / `@strict_loading_mode` on that record. The raise (or log) happens later, when an association actually issues a lazy load.

Default mode is `:all`. `:n_plus_one_only` lets this record lazy-load, then turns the N+1 into a violation on the next hop.

I ran the relevant cases in [`strict_loading_test.rb`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb): 13 runs, 61 assertions, 0 failures.

### What `strict_loading!` stores

[`ActiveRecord::Core#strict_loading!`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L736-L742) is the instance API:

```736:754:activerecord/lib/active_record/core.rb
    def strict_loading!(value = true, mode: :all)
      unless [:all, :n_plus_one_only].include?(mode)
        raise ArgumentError, "The :mode option must be one of [:all, :n_plus_one_only] but #{mode.inspect} was provided."
      end

      @strict_loading_mode = mode
      @strict_loading = value
    end
    # ...
    def strict_loading_n_plus_one_only?
      @strict_loading_mode == :n_plus_one_only
    end
```

New records copy class defaults in `init_internals`: `strict_loading_by_default` (false) and `strict_loading_mode` (`:all`). Relation `Model.strict_loading` is a different method: it sets `strict_loading_value` on the relation, then [`Relation#exec_queries`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb#L1490) calls `record.strict_loading!(strict_loading_value)` on each result.

### Two modes

The mode is not checked at `strict_loading!` time. It is checked when an association is about to query, and again when child records are materialized.

```diagram
:all
  owner.strict_loading!                  # @strict_loading=true, mode=:all
       │
       ├── lazy has_many / belongs_to / has_one  → violation
       └── preload/eager_load                    → allowed; children also marked

:n_plus_one_only
  owner.strict_loading!(mode: :n_plus_one_only)
       │
       ├── lazy load on owner                    → allowed
       ├── has_many child                        → child.strict_loading!  (mode :all)
       │      └── that child's associations      → violation
       └── belongs_to / has_one child            → child.strict_loading!(false, mode: :n_plus_one_only)
              └── that child's has_many          → grandchild.strict_loading!
```

[`Association#violates_strict_loading?`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L235-L244) is the gate:

```235:244:activerecord/lib/active_record/associations/association.rb
      def violates_strict_loading?
        return unless find_target?

        return if @skip_strict_loading

        return unless owner.validation_context.nil?

        return reflection.strict_loading? if reflection.options.key?(:strict_loading)

        owner.strict_loading? && !owner.strict_loading_n_plus_one_only?
      end
```

In `:all`, `owner.strict_loading?` is true and `strict_loading_n_plus_one_only?` is false, so any unloaded association that would query violates.

In `:n_plus_one_only`, the last line is false, so this owner does not violate. The N+1 protection is applied in [`set_strict_loading`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L123-L128) when child rows are built:

```123:128:activerecord/lib/active_record/associations/association.rb
      def set_strict_loading(record)
        if owner.strict_loading_n_plus_one_only? && reflection.macro == :has_many
          record.strict_loading!
        else
          record.strict_loading!(false, mode: owner.strict_loading_mode)
        end
      end
```

That runs from `Association#find_target` (lazy load) and from [`AssociationRelation#exec_queries`](file:///home/user/workspace/repo/activerecord/lib/active_record/association_relation.rb#L46) (scoped association queries such as `#first` without loading the whole collection). HABTM is compiled to `has_many :through`, so `Developer#projects` still has `macro == :has_many`.

### Where the error is raised (or logged)

```text
record.audit_logs.to_a
  CollectionProxy#records
    CollectionAssociation#load_target
      Association#find_target
        violates_strict_loading?  → true
        Base.strict_loading_violation!(owner: owner.class, reflection:)
```

[`Association#find_target`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L260-L262) is the main trigger. [`CollectionProxy#pluck`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/collection_proxy.rb#L725-L726) checks the same predicate before running SQL, which is why `audit_logs.pluck(:id)` also raises.

[`ActiveRecord::Base.strict_loading_violation!`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L254-L264) then branches on `ActiveRecord.action_on_strict_loading_violation` (default `:raise`):

- `:raise` → `ActiveRecord::StrictLoadingViolationError` with [`reflection.strict_loading_violation_message`](file:///home/user/workspace/repo/activerecord/lib/active_record/reflection.rb#L347-L351): `` `Developer` is marked for strict_loading. The AuditLog association named `:audit_logs` cannot be lazily loaded. ``
- `:log` → `ActiveSupport::Notifications.instrument("strict_loading_violation.active_record", owner:, reflection:)`. [`LogSubscriber`](file:///home/user/workspace/repo/activerecord/lib/active_record/log_subscriber.rb#L11-L21) prints the same sentence at debug.

`test_strict_loading_violation_raises_by_default` and `test_strict_loading_violation_can_log_instead_of_raise` cover both. Polymorphic associations use “The polymorphic association named `:looter`…” (`test_strict_loading_violation_on_polymorphic_relation`).

An already-loaded target never violates: `return unless find_target?`. That is why preload/eager load is the escape hatch.

### Observable cases from the tests

#### 1. Lazy `has_many` in `:all`

[`test_strict_loading!`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L34-L42) / `test_raises_if_strict_loading_and_lazy_loading`:

```ruby
developer = Developer.first
developer.strict_loading!          # => true
developer.audit_logs.to_a          # StrictLoadingViolationError
```

`CollectionProxy#records` always `load_target`s. In `:all`, [`CollectionAssociation#find_from_target?`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/collection_association.rb#L299-L304) is also true (`owner.strict_loading? && owner.strict_loading_all?`), so `audit_logs.first` takes the same path and raises (`test_raises_on_unloaded_relation_methods_if_strict_loading`).

#### 2. Lazy `belongs_to` / singular in `:all`

Same predicate. `test_raises_on_lazy_loading_a_belongs_to_relation_if_strict_loading_by_default` uses class default; association-level `belongs_to :strict_loading_mentor, strict_loading: true` raises even when the owner is not marked, because `reflection.options.key?(:strict_loading)` short-circuits to `reflection.strict_loading?` (`test_raises_on_lazy_loading_a_strict_loading_belongs_to_relation`).

`has_one :ship` behaves the same as `belongs_to` here: both are not `:has_many`, and both go through `SingularAssociation#reader` → `reload` → `find_target`.

#### 3. Preloaded association does not raise; children inherit the flag

```ruby

dev.strict_loading?                         # true
dev.audit_logs.all?(&:strict_loading?)      # true
dev.audit_logs.to_a                         # no raise — already loaded
```

That is `test_preload_audit_logs_are_strict_loading_because_parent_is_strict_loading`. Two copy paths:

- [`Relation#preload_associations`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb#L1382-L1384) passes `StrictLoadingScope` into the preloader; [`cascade_strict_loading`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/preloader/association.rb#L310-L311) then does `scope.strict_loading` for child queries.
- [`JoinDependency#construct_model`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/join_dependency.rb#L279-L297) (eager load) calls `m.strict_loading! if strict_loading_value`.

`test_does_not_raise_on_eager_loading_a_strict_loading_belongs_to_relation` is the singular counterpart: `includes(:strict_loading_mentor)` then `developer.strict_loading_mentor` is fine.

#### 4. `has_many :through` and middle records

`Developer` has `has_many :contracts` and `has_many :firms, through: :contracts`. `test_strict_loading_with_has_many_through_cascade_down_to_middle_records`:

```ruby

dev.firms.first                 # ok — firms preloaded, and they are strict_loading
dev.firms.first.contracts.first # StrictLoadingViolationError  (Firm’s :contracts not loaded)
dev.contracts.first             # StrictLoadingViolationError  (middle assoc not preloaded)
dev.ship                        # StrictLoadingViolationError  (unrelated, also not loaded)
```

`includes(:firms)` does not load `dev.contracts` as an association you can walk. Strictness does cascade onto the preloaded `Firm` records, so the next hop (`firm.contracts`) is the violation. The through preloader also calls `cascade_strict_loading` on the through scope ([`preloader/through_association.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/preloader/through_association.rb#L145)).

#### 5. Validation-time association access is skipped

`violates_strict_loading?` returns unless `owner.validation_context.nil?`. `valid?` / `save!` set that to `:create` or `:update`, then restore it.

```ruby
## test_strict_loading_is_ignored_in_validation_context
with_strict_loading_by_default(Developer) do
  AuditLogRequired.create!(developer_id: developer.id, message: "i am a message")
end

## test_strict_loading_with_reflection_is_ignored_in_validation_context

developer.save!   # has_many validate: true loads/validates children; no raise
```

The comment on `strict_loading!` states this explicitly. After validation, context is nil again and lazy loads raise.

Writers also bypass via `@skip_strict_loading`: `<<`, `build`, and `audit_logs = [...]` do not raise (`test_strict_loading_on_concat_is_ignored` and neighbors). `concat` on a new record wraps `load_target` in `skip_strict_loading`.

#### 6. Parent → children → each child’s association in `:n_plus_one_only`

`test_strict_loading_n_plus_one_only_mode_with_has_many` (HABTM `projects`, runtime `has_many`):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)
developer.projects.to_a                         # no raise
developer.projects.all?(&:strict_loading?)      # true — set_strict_loading saw :has_many
developer.projects.detect { ... }.firm          # StrictLoadingViolationError
```

The child’s `belongs_to :firm` is a lazy load on a record now in `:all`.

Singular hop, then that record’s `has_many` (`test_strict_loading_n_plus_one_only_mode_with_belongs_to`; `ship` is actually `has_one`, same `set_strict_loading` branch as `belongs_to`):

```ruby
developer.strict_loading!(mode: :n_plus_one_only)
developer.ship.parts.to_a                       # no raise
developer.ship.strict_loading?                  # false — mode copied, flag off
developer.ship.parts.all?(&:strict_loading?)    # true
developer.ship.parts.first.trinkets.to_a        # StrictLoadingViolationError
```

That is the mode-copy rule: a `has_one`/`belongs_to` child is not itself strict, but it keeps `:n_plus_one_only`, so *its* `has_many` children get `strict_loading!`.

`test_strict_loading_n_plus_one_only_mode_does_not_eager_load_child_associations`: after `developer.projects.first`, the collection is still not `loaded?`. In `:n_plus_one_only`, `find_from_target?` is false, so `#first` is a `LIMIT 1` `AssociationRelation` query rather than loading every child. (The fixture project used there has `firm_id: nil`, so `.firm` does not query and does not raise.)

The public docs on `strict_loading!` describe the same walk: `user.comments.to_a` is allowed; `user.comments.first.ratings.to_a` is not.

### Disabling on an instance

```ruby
developer.strict_loading!          # enable, mode :all
developer.audit_logs.to_a          # raises
developer.strict_loading!(false)   # => false
developer.audit_logs.to_a          # loads
```

That is the rest of `test_strict_loading!`. `strict_loading!(false)` only clears `@strict_loading`; it still writes `@strict_loading_mode` (default `:all` unless you pass `mode:`). Association-level `strict_loading: false` is a separate override: `test_strict_loading_can_be_turned_off_on_an_association_in_a_model_with_strict_loading_on` (`strict_loading_off_mentor`).

### Invalid mode

Anything other than `:all` or `:n_plus_one_only` raises `ArgumentError` **before** the ivars are written:

```text
The :mode option must be one of [:all, :n_plus_one_only] but :bogus was provided.
```

That string is not covered in `strict_loading_test.rb`; it comes from the guard in `strict_loading!`. I confirmed the raise and the message against that method.

### What does *not* count as a violation

- Target already loaded (`find_target?` is false), including after `includes` / `preload` / `eager_load`.
- Owner is in `:n_plus_one_only` (this hop only).
- `owner.validation_context` is set.
- `@skip_strict_loading` during collection concat/replace.
- Association option `strict_loading: false` when that key is present.
- `reload` of a preloaded `has_one` after `developer.reload` (`test_strict_loading_has_one_reload`) — the suite treats that as allowed once the parent itself was loaded under strict-by-default and the association was preloaded first.
