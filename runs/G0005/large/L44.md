**Request changes.** The leak exists only if you call `RunnerCommand#perform` without `Rails::Command.invoke`. The supported path already restores `ARGV`. The proposed `dup`/`replace`/`ensure` is the wrong layer, untested by `runner_test.rb`, and incomplete.

## Claim vs implementation

[`RunnerCommand#perform`](file:///home/user/workspace/repo/railties/lib/rails/commands/runner/runner_command.rb#L24-L65) does replace the process vector with trailing args and never puts them back:

```33:33:railties/lib/rails/commands/runner/runner_command.rb
        ARGV.replace(command_argv)
```

That replace is the feature, not the bug. It strips the code/file so the script sees only its own arguments. [`test_should_set_argv_when_running_code`](file:///home/user/workspace/repo/railties/test/application/runner_test.rb#L40-L43) and [`test_passes_extra_args_to_file`](file:///home/user/workspace/repo/railties/test/application/runner_test.rb#L76-L82) lock that in, including values that look like switches (`--foo`, `-b`).

Isolation after the command returns is already implemented one layer up. [`Rails::Command.invoke`](file:///home/user/workspace/repo/railties/lib/rails/command.rb#L55-L69) wraps dispatch in `with_argv`:

```140:146:railties/lib/rails/command.rb
        def with_argv(argv)
          original_argv = ARGV.dup
          ARGV.replace(argv)
          yield
        ensure
          ARGV.replace(original_argv)
        end
```

[`railties/lib/rails/commands.rb`](file:///home/user/workspace/repo/railties/lib/rails/commands.rb) always goes through `invoke`. Nested in-process `invoke` nests `with_argv`, so an inner runner cannot leak into the outer command. I ran [`railties/test/command/base_test.rb`](file:///home/user/workspace/repo/railties/test/command/base_test.rb) `-i /ARGV/`: **2 runs, 3 assertions, 0 failures**, including `"ARGV is isolated"`.

A probe of the two embed styles:

- `with_argv` + `perform`: after invoke, `ARGV` was the pre-invoke vector (`["process-arg"]`).
- Direct `perform` then exception: `ARGV` stayed `["leaked"]`.

So the PR’s sentence is true only for the undocumented `perform` path. `GenerateCommand` does the same unrestored `ARGV.replace` and relies on the same invoke boundary.

## What the tests actually cover

[`railties/test/commands/runner_test.rb`](file:///home/user/workspace/repo/railties/test/commands/runner_test.rb) and [`railties/test/application/runner_test.rb`](file:///home/user/workspace/repo/railties/test/application/runner_test.rb) drive `bin/rails runner` via the forking `rails()` helper. They never observe `ARGV` after `perform` returns. Adding the ensure would not fail or pass any existing example.

Covered today:

| Path | Behavior | ARGV restore tested? |
|---|---|---|
| Inline code | `eval` in `TOPLEVEL_BINDING` | No (only stdout during run) |
| Ruby filename | `File.exist?` then `Kernel.load` | No |
| stdin `-` | `eval($stdin.read, …, "stdin")` | No |
| Missing `*.rb` | message + `exit 1` | No |
| SyntaxError / NameError | message + `exit 1` | No |
| Nested `invoke` | outer `with_argv` | Only in `base_test.rb`, not runner |
| `$0` / `$PROGRAM_NAME` | set to expanded path, never restored | Set during file run only |
| Executor | wrap vs `--skip-executor` | Unrelated to ARGV |
| Args starting with `-` | forwarded after the code/file | During run only |

`exit 1` is `SystemExit`. `with_argv`’s `ensure` still runs. CLI/invoke does not leak on those error paths either.

## Compatibility and a more precise change

Landing the proposed ensure as written:

- Restores whatever `ARGV` was **at `perform` entry**. Under `invoke` that is already the runner argv (`code_or_file` + extras), not the process argv. Outer `with_argv` still does the real restore. Harmless duplication on the supported path.
- Changes direct-`perform` callers: `ARGV` after return / `SystemExit` goes back. That is the only path this PR would fix.
- Does not restore `$0` / `$PROGRAM_NAME`, which file execution mutates the same way and which embedding would also leak.
- Does not change dashed-arg forwarding, stdin `-`, or executor wrapping, as long as `ARGV.replace(command_argv)` still happens **before** `eval`/`load`.
- Leaves a window where a script `at_exit` handler on the CLI path still sees post-`invoke` argv (the shifted command args from `commands.rb`), same as today.

If the goal is “embedding must not leak,” the precise fix is not another save/restore in `RunnerCommand`:

1. Document/embed via `Rails::Command.invoke("runner", args)` — already isolated.
2. If direct `perform` is a supported API (it is `:nodoc:` today), restore **both** `ARGV` and `$0` in `ensure`, and add an in-process test that calls `perform` (not forked `bin/rails`) and asserts both values after success, `SystemExit` from missing file, and `SystemExit` from `SyntaxError`.
3. Do not add a runner-only restore that `generate` / `console` do not share; isolation belongs on `invoke`, where it already lives.

**Verdict: request changes.** Reject the claim as a CLI/`invoke` leak; do not merge the ensure without an in-process test that currently fails, and without deciding whether `$0` is part of the same contract.
