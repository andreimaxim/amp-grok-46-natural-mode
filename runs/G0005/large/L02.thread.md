## Assistant

`#none` is a Null Object on a normal `Relation`: it stays a relation, stays chainable, and most read/write-all paths refuse to hit the database. That refusal is the `@none` flag, not the `1=0` predicate. The predicate is a SQL backup for anything that still compiles Arel.

### What `#none` actually sets

[`QueryMethods#none`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/query_methods.rb#L1352-L1366) is `spawn.none!`. `none!` is idempotent:

```ruby
def none!
  unless @none
    where!("1=0")
    @none = true
  end
  self
end
```

Two pieces of state, on purpose:

| State | Stored in | Survives `clone`/`spawn`? | Visible in Arel/`to_sql`? |
|---|---|---|---|
| `@none` | ivar, not `@values` | yes (`initialize_copy` does not clear it) | no |
| `where!("1=0")` | `where_clause` | yes, until something drops `:where` | yes (`WHERE (1=0)`) |

`null_relation?` is literally `@none`. `where_values_hash` ignores the SQL literal, so `Developer.none.where(salary: 100_000).where_values_hash` is still `{ "salary" => 100_000 }`.

`1=0` is **not** a `WhereClause` contradiction. [`contradiction?`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/where_clause.rb#L99-L107) only matches empty `IN` and unboundable equality. `User.where(id: [])` and `User.none` can both load as empty, but they take different branches, and only `@none` short-circuits `delete_all` / `update_all`.

### Chainability

`spawn` is `clone` (unless `_exec_scope` set `@delegate_to_model`). Clone copies `@none`. Query methods that `spawn` then mutate `@values` therefore keep none-ness:

```text
Model.none
  spawn → clone (@none=true, where 1=0)
    .where(...) / .limit / .order / .includes / ...
      still @none
      still 1=0 plus the new values
```

That is why [`Developer.none.where(name: "David")`](file:///home/user/workspace/repo/activerecord/test/cases/null_relation_test.rb#L22-L26) loads as `[]` with zero queries, and why an anonymous extension still responds after `.none`.

`Merger` plants the flag on the other side: `relation.none! if other.null_relation?`. Merging a none relation into a live one is how association scopes and `merge` stay empty.

`#or` is the spawn exception. If the receiver is already none, it does not combine clauses — it returns `other.spawn` and drops none-ness:

```ruby
def or(other)
  if @none
    other.spawn
  else
    spawn.or!(other)
  end
end
```

So `Post.none.or(Post.where("id = 1"))` is a real query. `Post.where("id = 1").or(Post.none)` stays on the left, ORs in `1=0`, and still queries. Both are covered in [`or_test.rb`](file:///home/user/workspace/repo/activerecord/test/cases/relation/or_test.rb#L23-L45).

`unscope(:where)` / `except(:where)` / `invert_where` do **not** clear `@none`. They can make `to_sql` stop saying `1=0` (or invert it to `NOT (1=0)`) while load/exists/count still short-circuit.

### Loading: `@none` vs contradiction

```text
Relation#load
  exec_queries
    skip_query_cache_if_necessary          ← always, even when @none
      exec_main_query
        if @none → [] / FutureResult.wrap([])   ← no SQL, before inner skip
        skip_query_cache_if_necessary
          if where_clause.contradiction? → [].freeze
          elsif eager_loading?
            apply_join_dependency
              if relation.null_relation? → [].freeze
              else SELECT
          else SELECT
```

[`exec_main_query`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb#L1495-L1526) therefore has two empty-load gates:

1. **`@none`** — explicit null object. Returns a fresh `[]` (or a wrapped future when `async:`). No Arel, no connection.
2. **`where_clause.contradiction?`** — empty `IN` / unboundable bind. Returns `[].freeze`. Still no SQL, but only after the `@none` check.

The eager-load branch re-checks `null_relation?` on the join-dependency relation because that object is not necessarily `self`.

`load_async` calls `exec_main_query` directly, not `exec_queries`. For `@none` with `async: true` it stores `FutureResult.wrap([])` in `@future_result`, sets `@loaded = true`, and reports `scheduled?` until something consumes the future. No SQL either way ([`test_async_query_on_null_relation`](file:///home/user/workspace/repo/activerecord/test/cases/null_relation_test.rb#L34-L38)).

### Calculations, `exists?`, `include?`

[`Calculations#calculate`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L217-L230) returns identities without SQL:

- `count` / `sum` → `0`, or `{}` if grouped
- `average` / `minimum` / `maximum` → `nil`, or `{}` if grouped
- async variants wrap that in `Promise::Complete`

[`#pluck`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L297-L304) returns `[]`. `#ids` / `#pick` go through pluck. Unloaded `#size` goes through `count(:all)`, so it is `0`.

If `@none` is false but the where clause is a contradiction, `execute_simple_calculation` / `execute_grouped_calculation` still skip SQL — they just do not use the identity table above; they build an empty `Result` / `{}`.

[`exists?`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/finder_methods.rb#L358-L382): `return false if @none` before argument handling. `Developer.none.exists?(1)` is false with no query. After constructing the EXISTS relation it also `return false if relation.where_clause.contradiction?`.

[`include?`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/finder_methods.rb#L389-L399) has no `@none` check of its own:

- wrong class → `false`
- loaded, or `offset`/`limit`/`having` → `records.include?` (load hits `exec_main_query`’s `@none` gate)
- otherwise → `exists?(pk hash)` (hits `exists?`’s `@none` gate)

`empty?` / `none?` / `any?` / `one?` / `many?` all return from `@none` before `exists?` or `limited_count`.

### `delete_all` / `update_all`

Both [`return 0 if @none`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb#L605) **before** invalid-method checks. A none relation with `distinct` / `with` therefore returns `0` instead of raising (delete) or warning (update). Contradiction-only relations (`where(id: [])`) do not take this return; they compile and execute the DELETE/UPDATE.

`delete(id)` is `where(pk => id).delete_all`, so the clone still has `@none` and returns `0`. `touch_all` is `update_all`. `destroy_all` does not check `@none`; it loads (`[]`) and iterates.

### Query-cache skip state

`skip_query_cache` lives in `@values` (`SINGLE_VALUE_METHODS`). `@none` does not. They compose, but not uniformly:

```text
skip_query_cache_if_necessary
  if skip_query_cache_value
    model.uncached { ... }    # disable query cache for the block
  else
    yield
```

| Path | `@none` short-circuit vs `uncached` |
|---|---|
| `load` / `exec_queries` | `@none` return is **inside** the outer `skip_query_cache_if_necessary`. A none relation with `skip_query_cache!` still enters `model.uncached`, then returns `[]`. |
| `load_async` | calls `exec_main_query` directly; `@none` returns **before** the inner skip. No `uncached`. |
| `exists?`, `calculate`, `pluck` | `@none` returns before any skip wrapper. No `uncached`. |
| contradiction load | empty result is **inside** the inner skip wrapper (and the outer one from `exec_queries`). |
| contradiction `exists?` / calculate | empty result **before** `skip_query_cache_if_necessary`. |

`values_for_queries` strips `:skip_query_cache`, so it is not part of query identity. `@none` is not in `@values` at all, so `except` / `only` / structural-compatibility checks never see it.

`in_batches` always `skip_query_cache!` on the batch relation. For a none relation the subsequent `records` / `pluck` still short-circuit, so the flag is set and then unused.

### What can still execute SQL after further scoping

The RDoc line “any subsequent condition chained … will not fire any query” is true for spawn-based scoping that keeps `@none`. It is not a global “this object never talks to the database.”

**`#or` from the left.** `Post.none.or(other)` is `other.spawn`. Load/count/exists on the result are normal queries.

**None as a predicate value.** [`RelationHandler`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/predicate_builder/relation_handler.rb#L6-L26) compiles `attribute.in(none_relation.arel)`. The outer relation is not none. `Comment.where(post_id: Post.none).count` runs SQL (`WHERE post_id IN (SELECT … WHERE (1=0))`). That is [`test_null_relation_in_where_condition`](file:///home/user/workspace/repo/activerecord/test/cases/null_relation_test.rb#L115-L118).

**Writes that do not consult `@none`.** `create` / `create!` go through `scoping { model.create }` and INSERT. `insert_all` / `upsert_all` go to `InsertAll.execute` with no `@none` check. `1=0` does not appear in `scope_for_create` because it is not an equality.

**Association scoping.** `Comment.none.scoping { post.comments.count }` still queries. Association scope is `target_scope.merge!(association_scope)`, not `current_scope`, unless `all_queries: true` installed a global scope. [`test_none_scoping`](file:///home/user/workspace/repo/activerecord/test/cases/scoping/relation_scoping_test.rb#L551-L557) asserts the association still sees its two comments.

**`cache_version`.** [`compute_cache_version`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation.rb#L483-L521) does not check `@none`. An unloaded none relation issues `COUNT(*)` / `MAX(timestamp)` with `WHERE (1=0)`.

**`to_sql`.** Compiles Arel (including `1=0`) through the connection; it is not a result query, but it is adapter work.

New records’ collection associations call `scope.none!` when `null_scope?` (`owner.new_record? && !foreign_key_present?`). That is the same mechanism: plant `@none` + `1=0` so the association stays chainable without a SELECT.
