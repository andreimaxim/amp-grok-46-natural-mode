`retry_on` is a `rescue_from` wrapper. On each raise it picks one handler, bumps that declaration’s counter, then either reenqueues the same job or treats the error as exhausted.

## Matching: last declared handler, then up the class

`retry_on` does not search its own list. It registers through [`rescue_from`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L53-L73). Each exception class is appended to inherited `rescue_handlers`. Lookup walks that array **backwards** and takes the first `klass === exception` hit ([`find_rescue_handler`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L124-L136)). For an exception class, `===` is `is_a?`, so subclasses match a superclass handler.

That is the “bottom to top, and up the class hierarchy” rule in the [`retry_on` docs](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L24-L25). Child `retry_on`/`discard_on` declarations are appended after the parent’s, so they win when both match. Only one handler runs.

[`AfterDiscardRetryJob`](file:///home/user/workspace/repo/activejob/test/jobs/after_discard_retry_job.rb#L18-L19) declares `retry_on AfterDiscardError` then `retry_on ChildAfterDiscardError`. Raising the child uses only the child handler: [`after_discard` runs once](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L423-L427), and the original `ChildAfterDiscardError` is re-raised after five attempts.

If no handler matches the raised object, Rescuable walks [`exception.cause`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L90-L101). Active Job’s exception tests do not cover that path.

## Counters: one per `retry_on` line, not per class

[`executions`](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L47) is the total run count. Retry limits use a different hash, [`exception_executions`](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L40-L44), keyed by `exceptions.to_s` of **that declaration’s argument array** ([`executions_for`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L207-L213)). The increment happens **before** the attempts check, so the first failure is attempt 1.

One declaration listing several classes shares one key and one limit:

```35:35:activejob/test/jobs/retry_job.rb
  retry_on FirstRetryableErrorOfTwo, SecondRetryableErrorOfTwo, attempts: 4
```

Three `First` + one `Second` exhausts on the fourth raise; the `Second` is not given its own four tries ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L42-L55)). Separate `retry_on` lines get separate keys, so four `DefaultsError` (limit 5) then three `FirstRetryableErrorOfTwo` (limit 4) still succeed ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L58-L75)). Interleaved polynomial vs custom waits keep independent delay sequences for the same reason ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L312-L335)).

Jobs serialized before this hash existed (`exception_executions == nil`) fall back to the global `executions` counter ([guard](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L210-L212); [AJ 5.2 tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L365-L388)).

`attempts` counts the original execution plus retries ([docs](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L33-L34)). Default is 5: four retries then success on the fifth run ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L26-L35)); a sixth failure re-raises ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L78-L83)).

`attempts: :unlimited` skips the comparison entirely ([condition](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L77)). Ten failures then success never exhausts ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L357-L363)).

## Wait: number, `:polynomially_longer`, or proc

Unsupported `wait` types raise `ArgumentError` at declaration ([check](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L67-L73); [tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L447-L465)).

[`determine_delay`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L181-L199) uses the **per-declaration** counter, already incremented.

**Numeric / Duration.** `to_f` plus jitter. Default wait is 3 seconds. `wait: 1.hour` and `wait: 4.5` schedule at `now + wait + rand * wait * jitter` ([tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L107-L135)).

**`:polynomially_longer`.** `(executions**4) + (Kernel.rand * executions**4 * jitter) + 2` ([implementation](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L185-L189)). With the per-handler counter that is ~3s, ~18s, ~83s, ~258s ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L137-L157)).

**Jitter.** The `jitter:` default is a sentinel. Unspecified → `self.class.retry_jitter` (0.0 on `ActiveJob::Base`; 0.15 in new apps via Railties). `jitter: nil` or `0` disables it ([`determine_delay` / `determine_jitter_for_delay`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L182-L204); [nil/zero tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L238-L264)). Non-zero, including negative, uses `Kernel.rand * delay * jitter`.

**Wait proc.** No jitter. Arity 2, or arity `< -1` (a second optional/rest arg), is called as `proc.call(executions, error)`; otherwise `proc.call(executions)` ([line](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L196)).

- `->(executions) { executions * 2 }` waits 2, 4, 6, 8 ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L266-L281)).
- `->(executions = 0) { ... }` has arity `-1`, so it still gets only `executions` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L284-L295)).
- `->(executions, error) { error.retry_after + executions }` waits 11 then 12 for `retry_after == 10` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L298-L309)).

## Exhaustion block and whether the error escapes

```80:90:activejob/lib/active_job/exceptions.rb
          else
            if block_given?
              instrument :retry_stopped, error: error do
                yield self, error
              end
              run_after_discard_procs(error)
            else
              instrument :retry_stopped, error: error
              run_after_discard_procs(error)
              raise error
            end
```

`block_given?` / `yield` refer to the block passed to `retry_on`. The job and the same error object are yielded.

| Path | Original exception |
|---|---|
| Retry | Swallowed. `rescue_with_handler` returns the error object; `perform_now` returns it and does not re-raise. |
| Exhaustion **with** block | Swallowed after the block. CustomCatchError after 6 tries writes the handler message and does not raise ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L102-L105)). |
| Exhaustion **without** block | Re-raised (`raise error`). DefaultsError after 5 failures is rescued as `DefaultsError` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L78-L83)). |
| No matching handler | `perform_now` runs `after_discard` then `raise` ([execution](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L409-L414)). |

`after_discard` runs on both exhaustion branches, including when the block is present ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L417-L420)).

## Queue and priority overrides

`retry_on` forwards `queue:` and `priority:` into `retry_job` → `enqueue` → [`set`](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L174-L181). `nil` leaves the current values (`if options[:queue]` / `if options[:priority]`). `queue: :low` is passed through `queue_name_from_part`.

[`retry_job`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L168-L174) snapshots `scheduled_at`, `queue_name`, and `priority`, enqueues, then restores them on the **in-memory** instance so the running job is not left on the retry queue. The serialized retry already has the overrides.

[`HeavyError` / `queue: :low`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L47) is performed first from `default`, then from `low` ([logging test](file:///home/user/workspace/repo/activejob/test/cases/logging_test.rb#L300-L307)). There is no exception test for `priority:` on `retry_on`; that path is source-only.

## Callbacks

`rescue_with_handler` sits **outside** the perform callback chain. A raise from `perform` skips `after_perform` and is handled afterward.

A retry runs the **enqueue** chain (`before`/`around`/`after_enqueue`), including the instrumentation `around_enqueue`. If `before_enqueue` raises a `retry_on` error, that error is handled on the same job object ([`RetriesJob` test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L390-L394)).

Exhaustion always runs `after_discard` procs, then either swallows (block) or re-raises (no block).
