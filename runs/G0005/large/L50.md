This is a **maintenance** brief: keep `generate` and `destroy` as inverses for an already-existing file, without adding generator features. Some present-day differences may still be intentional; those stay open.

**Problem frame.** Application and engine authors use `bin/rails generate` and `bin/rails destroy` as a pair. When the target file already exists, generate asks or honors `--force` / `--skip`; destroy often just removes. After a skipped collision, destroy can delete a file generate never took. That makes undo unsafe in apps, engines, and non-interactive runs. The desired progress is one shared, observable collision contract for both commands.

**Users.** App developers generating and undoing code; engine authors running the same commands from an engine root (including nested/mountable engines); anyone running generators in CI or piped stdin with `--force` or `--skip`.

**Pain (observed).** Generate on an existing file with different content prints `conflict`, then `Overwrite …? (enter "h" for help) [Ynaqdhm]`. `--force` prints `force` and replaces; `--skip` prints `skip` and leaves the file; identical content prints `identical` and leaves it. Destroy prints `remove` and deletes if the path exists—no overwrite question, and `--force` / `--skip` do not change that. A skipped generate followed by destroy therefore deletes the pre-existing file. A missing generator always tells the user to run `bin/rails generate --help`, including from destroy.

**Desired observable CLI behavior (working model).** For the same generator, arguments, destination root, and resolved name, generate and destroy should agree on whether that existing file is created, left alone, overwritten, or removed. Flags and answers should mean the same thing on both commands. Lookup, fallbacks, namespaced names, and engine roots should not change the collision contract. Hypothesis, not a settled product rule: destroy should not remove a file that generate just skipped.

**Non-goals.** New generators or templates; class-name collision (`--skip-collision-check`); migration-name clashes (those already error instead of prompting); pretend/quiet cosmetics; merge/diff tooling beyond today’s prompt letters; host-app files when the command is run from an engine.

**Acceptance examples** (required unless marked illustrative)

Identical content. File already matches what generate would write. Generate reports `identical` and does not rewrite. Destroy’s correct move is **open**: remove because the path exists, or leave it because generate did not create it.

Differing content, no flags, interactive. Generate prints `conflict` and the overwrite prompt. `y` / `yes` overwrite; `n` / `no` leave the file and print `skip`; `a` / `all` overwrite this file and later conflicts in the same run without asking again; `q` / `quit` print `Aborting...` and stop (later files untouched; files already written this run stay). Destroy today removes without asking. Whether destroy should prompt the same way, refuse, or only remove files this generate actually wrote is **open**.

`--force`. Differing existing file. Generate prints `force` and replaces. Destroy should still only touch the same resolved path under the same root; whether `--force` on destroy is a no-op (it already removes) or must be passed to remove is **open**.

`--skip`. Differing existing file. Generate prints `skip` and leaves content. Destroy after that skip must not delete that pre-existing file **if** skip means “generate did not take the file.” If destroy is defined as “delete this path if present,” skip then destroy would still delete—that is the main intentionality question.

Non-interactive stdin (EOF / no TTY). Generate currently treats a missing answer like yes and overwrites. Desired behavior is **open**: overwrite, skip, or abort. Whatever is chosen should be the same for generate and destroy if destroy ever prompts.

Nested engine destination root. From an engine (including a nested/mountable engine), both commands use that engine’s root, not the dummy or host app. Mountable namespacing (`FooBar::TopicsController` vs unnamespaced in a non-mountable engine) is the same for generate and destroy.

Namespaced generator resolution. `model`, `rails:model`, and `my:awesome:namespace` resolve the same generator for generate and destroy. A configured fallback that substitutes another group still follows the same collision contract. Generate and destroy must not silently write or delete different paths for the same name.

Missing generator. Both commands fail without writing or deleting, print `Could not find generator '…'`, and point at help. Whether destroy may say `bin/rails generate --help` (current) or must say destroy help is **open**. Suggestions (“Did you mean?”) may appear when the name is close.

Destroy after a skipped collision. Generate `--skip` on a differing existing file; then destroy with the same generator and name. If skip means no ownership, the file is still the original and destroy does not remove it. If destroy means “remove this path,” it does. Pick one and apply it in apps and engines.

**Steering evidence.** Investigate if generate still prompts (or honors `--force`/`--skip`) while destroy deletes a skipped file; if engine generate/destroy touch different roots or namespaced paths; if a missing generator still writes or deletes; if EOF overwrite surprises scripted users. Reconsider the frame if people rely on destroy always deleting whatever is on disk, or if generate/destroy were never meant to be file-level inverses (e.g. destroy is “remove this path,” generate is “create unless told otherwise”).

**Evidence already in hand.** Generate/destroy command entry points, generator invoke/lookup/fallbacks, Thor create vs revoke for existing files, Railties lookup/missing-generator/engine-namespacing coverage, migration identical/force/skip/revoke cases, and a small Thor create/revoke probe (identical, `--force`, `--skip`, `n`, EOF overwrite, revoke removes). Railties does not cover the generic overwrite menu, EOF stdin, or destroy-after-skip as a pair.

**Evidence still needed to tell accidental from intentional**

- Docs or issues that say destroy always removes an existing path, even if generate skipped it.
- Whether EOF-as-overwrite is relied on in CI, or is an accident of a missing answer.
- Whether migration “raise on conflict” is a special case or the model for all files.
- Whether destroy’s missing-generator help is copy-paste or a deliberate pointer to generate.
- Real engine workflows: dummy-app vs engine-root, nested engines, namespaced vs unnamespaced.

**Open questions that change the outcome.** Is destroy “undo what generate just did” or “delete this generated path if it exists”? If generate reports `identical`, may destroy still delete? On quit, must already-written files in that run be rolled back? Does `all` apply only to later file collisions in that process, including hooked generators?
