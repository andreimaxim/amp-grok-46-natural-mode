Current behavior is established from the public docs, the existing tests, and runtime conversion/update. The tests never assert a winner or a collision signal; `update` documents that a regular hash with both `:key` and `"key"` keeps only one value, and which one is unspecified.

**Working model:** A Rails author ingesting configuration (defaults plus YAML/JSON/env-style hashes) converts or updates into indifferent access so `:host` and `"host"` read as the same setting. Today that conversion can drop a value with no signal. The desired outcome is that discarded mixed-key data becomes detectable — not a new winner rule. That last part is a hypothesis.

---

**Problem frame:** A Rails or library author is ingesting configuration that may mix symbol-keyed defaults with string-keyed file or payload data. They convert or update that data into `ActiveSupport::HashWithIndifferentAccess` so string and symbol names can be read as one setting. A regular hash treats `:key` and `"key"` as two entries; indifferent conversion collapses them to one. Nested hashes and hashes inside arrays collapse the same way. The surviving value is unspecified. There is no signal that anything was discarded, so mixed-key configuration ingest cannot tell a complete load from silent data loss.

**Current observable behavior** (from docs, tests, and runtime):

- Converting `{ :key => "symbol-value", "key" => "string-value" }` yields one entry, `"key"`, and no error or other signal. In this run the later insertion survived (`"string-value"`). Reversing insertion order reversed the survivor.
- `new`, `with_indifferent_access`, `update`/`merge!`, `merge`, `replace`, and the `[]` constructor all collapse the same way when the source is a regular hash that holds both forms.
- Nesting does too: `{ config: { :host => "from-symbol", "host" => "from-string" } }` becomes `{ "config" => { "host" => "from-string" } }`. A hash inside an array collapses the same way.
- Updating several hashes in order is ordinary last-hash-wins (`update({ :key => "from-symbol" }, { "key" => "from-string" })` keeps `"from-string"`). A collision *inside* one of those hashes is the unspecified case.
- Sequential assignment on a hash that is already indifferent (`h[:key] = ...` then `h["key"] = ...`) overwrites; that is ordinary same-key write, not a two-key source collapse.
- `1` and `"1"` stay distinct. Same-name collapse is for symbol and string forms of the same name.
- The Active Support guide does not mention the collapse. Tests do not cover detecting it or pinning a winner.

**Behavioral outcome:** After converting or updating mixed-key input, the author can tell that a distinct value was discarded instead of treating the result as a complete ingest. Common indifferent access without a same-name pair still behaves as it does today.

- **Example (core, config ingest):** Defaults `{ adapter: "postgresql", pool: 5 }` merged with file data `{ "adapter" => "mysql2", "host" => "db.example" }` produce a regular hash with four entries. After indifferent conversion there are three (`adapter`, `pool`, `host`) and one adapter value is gone. Today the author cannot tell a value was discarded. After this work, they can.
- **Example (nested, required):** `{ database: { adapter: "postgresql", pool: 5 } }` merged with `{ "database" => { "adapter" => "mysql2", "host" => "db.example" } }` then converted keeps only the string-keyed `database` hash. `pool` is gone with the whole symbol-keyed subtree. Detection must apply at nested hashes, not only the top level.
- **Example (multi-hash vs one mixed hash, required):** `update({ :key => "from-symbol" }, { "key" => "from-string" })` is two sources; later source overwrites. `update({ :key => "s1", "key" => "s2" }, { other: 1 })` collapses two keys that were distinct in one source, then adds `other`. The author can tell those situations apart: ordinary overwrite across hashes vs discarded data inside one hash.
- **Example (array of hashes, required):** `{ items: [{ :key => "sym", "key" => "str" }] }` converted collapses the inner hash the same way as a top-level mixed hash, and that collapse is detectable.
- **Example (counterexample):** `{ black: "#000000", "white" => "#FFFFFF" }` converted still has both settings, readable as either strings or symbols. No discard signal.
- **Example (boundary):** `{ :key => "same", "key" => "same" }` collapses two keys that held the same value. Whether that counts as discarded data is still open.
- **Example (counterexample):** `{ 1 => "one", "1" => "str-one" }` still keeps both entries. This is not a same-name symbol/string pair.

**Compatibility constraints** (facts to respect, not a chosen design):

- Indifferent access’s purpose remains: `:foo` and `"foo"` are the same setting when only one form is present.
- Silent collapse with an unspecified survivor is documented public behavior for `update` of a regular hash that contains both forms. Existing callers can depend on “no exception, one entry.”
- Direct overwrite on an already-indifferent hash, and last-hash-wins across several arguments, are existing merge semantics and are not the gap.
- Whether new detection is default or opt-in is not settled.

**Steering evidence:**

- Success: an author ingesting mixed-key configuration can tell when a distinct `:name` / `"name"` pair was not fully preserved, including nested hashes and hashes in arrays; ordinary indifferent reads without such a pair still work.
- Investigate if detection fires on ordinary last-hash-wins across separate hashes, or on sequential assignment to a hash that is already indifferent.
- Reconsider the framing if the real pain is the unspecified winner (authors want a defined survivor) rather than inability to notice a drop; or if mixed-key pairs almost never appear in ingest and the silent collapse is acceptable.

**Open questions:**

- **Opt-in:** Must callers enable detection, or should mixed-key discard be visible by default?
- **Error versus observation:** Should a collapse fail the ingest, or only make the discard visible while still returning one value?
- **Key disclosure:** If a collapse is reported, must the discarded name and value be shown, or is it enough to know that some same-name pair was dropped?
- **Performance:** Is extra work on every convert/update acceptable, or only when the caller has asked to detect collisions?
- **Same values:** Does `{ :key => "same", "key" => "same" }` count as discarded data?

This is a draft of the shared understanding, not a locked spec. I assumed the work is about making discarded mixed-key data detectable, not about picking which key wins. Correct that if the pain is really the unspecified survivor.
