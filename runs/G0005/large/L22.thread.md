## Assistant

**Problem frame:** An application developer already has a persisted row and needs to lock it and do related writes in one critical section. They often need a non-default lock clause (share, `NOWAIT`, and similar) **and** transaction options (`requires_new`, `joinable`, isolation) at the same time. Today that combination is possible but easy to mis-specify, and whether it works depends on the adapter. Failures show up as generic lock, reload, SQL, isolation, or read-only errors rather than a clear “this lock plus these transaction options is or is not supported here.”

**Evidence for the current baseline:** Rails source and docs for pessimistic locking, reload, relation lock flags, and transactions; [activerecord/test/cases/locking_test.rb](file:///home/user/workspace/repo/activerecord/test/cases/locking_test.rb), [custom_locking_test.rb](file:///home/user/workspace/repo/activerecord/test/cases/custom_locking_test.rb), transaction isolation tests, and the querying guide. Limits: there is no `with_lock(false)` test and no `with_lock` test for a row that disappeared before reload. Those two cases are inferred from `lock!` / reload. Combining a custom clause with isolation in one `with_lock` call is also untested.

---

## Current observable baseline

Without arguments, `with_lock` opens a transaction, reloads the row with the default exclusive lock (`FOR UPDATE` on PostgreSQL), runs the block, and commits on success. The block receives the current transaction object, so the developer can register `after_commit` (and similar) callbacks.

A string clause is appended to the reload SQL on adapters that accept it. PostgreSQL tests cover `FOR SHARE NOWAIT`. MySQL/Trilogy tests cover `LOCK IN SHARE MODE` on relation `lock`. SQLite’s write-prevention tests treat `FOR UPDATE` as a no-op stand-in for a custom clause.

`false` as the lock value is not covered for `with_lock`. Related lock/reload behavior: a falsy lock skips appending a lock clause and reloads without row locking, while the transaction wrapper still runs. `nil` is **not** the same across APIs (relation `lock(nil)` means default lock; a falsy lock on reload skips locking). Treat `with_lock(false)` / `with_lock(nil)` as incompletely evidenced.

If the persisted record has unsaved changes, locking is refused **before** reload, with a runtime error that names the dirty attributes and tells the developer to save or reload. There is no `with_lock`-specific test; `with_lock` uses the same lock path.

Successful work in the block is committed and visible after reload. An exception in the block rolls the transaction back; the row’s persisted attributes are unchanged. `ActiveRecord::Rollback` is swallowed by the transaction API (existing transaction behavior, not `with_lock`-specific).

Transaction options reach the wrapping transaction: inside an open joinable transaction, `requires_new: true` and `joinable: false` start a distinct, non-joinable inner transaction. On PostgreSQL, `isolation: :read_uncommitted` is visible on the current transaction. Isolation is **not** tested on `with_lock` for MySQL/Trilogy/SQLite.

If the row is gone at reload, reload raises `ActiveRecord::RecordNotFound`. That is documented and tested for `reload`, not for `with_lock`.

While writes are prevented, default and custom `with_lock` raise `ActiveRecord::ReadOnlyError` (`Lock query attempted while in readonly mode`). Nested `while_preventing_writes(false)` restores the ability to lock.

**How users see adapter mismatch today**

- Unsupported **lock SQL** is a database statement error (`ActiveRecord::StatementInvalid`). The querying guide already warns that the database must accept the raw clause.
- PostgreSQL refuses `SELECT … FOR UPDATE` on an outer join (eager `lock` is skipped in tests). That is a lock-SQL limitation, not a `with_lock` example.
- Unsupported or invalid **isolation** is `ActiveRecord::TransactionIsolationError`: adapter does not support setting isolation; invalid level; cannot set isolation when joining a transaction; cannot set isolation in a nested/savepoint transaction.
- mysql2, Trilogy, and PostgreSQL are documented as supporting isolation. SQLite advertises isolation support but only `read_uncommitted` in shared-cache mode; other levels raise `TransactionIsolationError`; `read_uncommitted` without shared-cache raises a different error about enabling shared-cache. Isolation tests that assert real level behavior skip SQLite.
- A custom clause that is syntactically accepted but meaningless (SQLite `FOR UPDATE` as no-op in tests) can look successful while not providing the intended lock. Whether that is acceptable is an open product choice.

## Desired outcomes

These are user-visible claims, not an API or control-flow design. Call shape stays unspecified.

1. **Combined request.** A developer who needs a custom lock clause and transaction options can express both in one `with_lock` use and observe both take effect: the reload uses the requested clause (when the adapter accepts it), and the wrapping transaction uses the requested `requires_new`, `joinable`, and isolation (when the adapter accepts them).
2. **Unambiguous lock choice.** Default exclusive lock, “no lock clause” (`false`), and a custom clause remain distinguishable. Choosing one does not silently become another.
3. **Existing safety stays.** Dirty persisted rows are still refused before reload. A missing row still fails as “record not found.” Write-prevention still forbids locking. Commit and exception rollback still match ordinary transactions. The block still receives the transaction object for callbacks.
4. **Adapter mismatch is attributable.** When the adapter cannot honor the clause, the isolation, or that combination, the developer sees a failure they can tell apart from a successful lock—not a committed critical section that only looked locked. Silent no-op locks remain an explicit open question, not a requirement to “fix SQLite.”
5. **Easier to get right than today.** A mistaken combination (for example treating the lock clause as a transaction option) must not apply the default `FOR UPDATE` and proceed. It should fail in a way that points at the bad request, or be impossible to express. *How* that is made impossible is left open.

---

## Non-goals

- Redesigning relation `lock` / `lock!`, optimistic locking, or `transaction` as a whole, except insofar as `with_lock` already forwards transaction options.
- One portable lock dialect or one isolation matrix across MySQL, PostgreSQL, and SQLite.
- Making unsupported SQL or isolation succeed.
- New lock types, timeouts, or deadlock policy.
- Changing write-prevention semantics other than keeping lock attempts forbidden.
- Prescribing method signatures, keyword vs positional form, or internal sequencing.

---

## Risks

- Existing call sites that pass only a clause, only options, both as positional-plus-hash, or rely on default `FOR UPDATE` could change meaning if “easier” is interpreted as a new calling convention.
- SQLite and other adapters may accept lock text or isolation names that do not mean what the developer meant; tightening feedback could break apps that depend on today’s error *or* today’s no-op.
- Isolation already cannot be set when joining or nesting; combining isolation with `requires_new` / `joinable` can look like a `with_lock` bug when it is existing transaction policy.
- `false` vs `nil` vs omitted lock are not fully evidenced; tightening one can surprise the others.
- Yielding the transaction object is relatively new; changing block arity or when the lock is taken relative to yield would break callback registration.

## Acceptance examples

Required cases, not an exhaustive catalog. “Developer” is the application author using `with_lock` on a persisted model instance.

**Default lock.** Given a persisted person and no lock argument, when they run `with_lock` with an empty block, they observe a transaction and a reload whose SQL uses the adapter’s default exclusive lock (PostgreSQL: `FOR UPDATE`). The block runs with that row locked.

**No lock clause (`false`).** Given a persisted person, when they request `with_lock` with lock `false`, they still get a transaction and a reload, but the reload SQL does not append a row-lock clause. *Inferred from reload/lock-flag behavior; confirm this is the intended “false” meaning.*

**Custom clause.** Given PostgreSQL, when they request `FOR SHARE NOWAIT`, the reload SQL includes `FOR SHARE NOWAIT`. Given MySQL/Trilogy, `LOCK IN SHARE MODE` appears in SQL for the equivalent lock request. If the database rejects the clause, they observe `ActiveRecord::StatementInvalid` and the critical section does not complete as success.

**Dirty persisted record.** Given a persisted person with `first_name` changed in memory and not saved, when they call `with_lock`, they get a runtime error that locking unsaved changes is unsupported and that `first_name` changed. The row is not reloaded away from under the dirty state.

**Commit.** Given a persisted person, when the block assigns `first_name`, saves, and returns normally, a later reload shows the new name.

**Exception rollback.** Given the same setup, when the block saves a new name then raises, after the exception is handled a reload shows the original name.

**Yielded transaction.** When they take a block parameter, it is the same object as the model’s current transaction, and they can register `after_commit` on it. After a successful `with_lock`, that callback runs; after rollback it does not. *(Callback-on-rollback is ordinary transaction behavior; `with_lock` tests only the yield identity on PostgreSQL.)*

**`requires_new` and `joinable`.** Given an already open joinable transaction, when they call `with_lock` with `requires_new: true` and `joinable: false`, work inside the block runs in a different, non-joinable transaction from the outer one.

**Isolation.** Given PostgreSQL (evidenced), when they call `with_lock` with `isolation: :read_uncommitted`, the current transaction reports that isolation. Whether MySQL/Trilogy `with_lock` matches `transaction(isolation:)` is expected but not shown by a `with_lock` test.

**Nesting.** Given write-prevention on, then an inner `while_preventing_writes(false)`, `with_lock` succeeds. Given an outer transaction without `requires_new`, `with_lock` joins it unless `requires_new` is set (existing transaction joining rules). Given isolation plus a nested/savepoint transaction, they observe `TransactionIsolationError` (`cannot set transaction isolation in a nested transaction`), not a lock.

**Missing row during reload.** Given the in-memory record’s row was deleted, when they call `with_lock`, they observe `ActiveRecord::RecordNotFound` from the lock reload, and the block does not run. *Inferred from reload; no `with_lock` test.*

**Write-prevention.** Given `while_preventing_writes`, default `with_lock` and custom-clause `with_lock` both raise `ActiveRecord::ReadOnlyError`. The block does not run. Without write-prevention, both succeed (subject to adapter lock SQL).

**Unsupported combinations (adapters).**

| Situation | What the developer observes today | Desired (product, not mechanism) |
|---|---|---|
| Lock clause the database does not accept | `StatementInvalid` | Same class of failure: not a successful lock. Wording/timing may improve; not required. |
| Isolation the adapter cannot set | `TransactionIsolationError` (“adapter does not support…”, invalid level, joining, nested) | Same: isolation problems stay isolation errors, not silent default isolation. |
| SQLite isolation other than `read_uncommitted` | `TransactionIsolationError` | Unchanged unless product later says otherwise. |
| SQLite `read_uncommitted` without shared-cache | Error about enabling shared-cache | Unchanged; not a lock-clause error. |
| Custom clause accepted but ineffective (SQLite `FOR UPDATE` no-op in tests) | Success, no share-lock semantics | **Open:** keep today’s no-op, or treat “looks locked but isn’t” as a failure of the “safer” goal. |
| Lock clause stuffed into transaction options (e.g. a `lock:` key among `isolation:` / `requires_new:`) | Likely unknown-keyword / options error, or default lock if the clause is dropped | Must not silently default-lock. |
| Custom clause **and** isolation together, both supported | Untested | Both should take effect. |
| Custom clause supported, isolation not (or the reverse) | Untested; likely the failing half’s existing error | The developer can tell which half failed. The other half must not commit as if the whole request succeeded. |

## Steering evidence

**Success looks like:** developers can lock-and-transact with default lock, no lock clause, or a custom clause; they can add `requires_new`, `joinable`, and isolation without losing the lock choice; dirty, missing, read-only, commit, rollback, and yielded-transaction behavior stay as above; adapter refusals remain visible and classifiable.

**Investigate / do not ship if:** a custom clause plus options applies `FOR UPDATE` anyway; `false` starts locking or skips the transaction; dirty rows get reloaded (losing in-memory edits) instead of the current error; write-prevention allows a lock; a missing row runs the block; PostgreSQL no longer yields the transaction or no longer emits `FOR UPDATE` / custom SQL; isolation or lock failures become silent success.

**Reconsider the problem if:** the real pain is documentation of the existing positional-clause-plus-options form, not ambiguity or safety; or if the pain is only adapter SQL differences, which `with_lock` cannot hide without a portable lock language (a non-goal).

## Open questions

- Is “easier” mainly **expressing clause + options together without a footgun**, or also **clearer errors** when the adapter cannot honor them?
- Should `false` mean “transaction, reload, no lock SQL”? That is inferred, not specified by a `with_lock` test.
- Should an ineffective-but-accepted clause (SQLite no-op) count as a product failure?
- Must MySQL/Trilogy/SQLite `with_lock(isolation:)` match PostgreSQL’s observable isolation, or is forwarding to `transaction` enough even when tests only cover PostgreSQL?
- If isolation fails after a lock would have been taken (or the reverse), what should the developer still be able to observe? Sequencing is an implementation choice; the product need is “the combination does not succeed halfway without an error.”

This is a working brief, not a confirmed spec. The main hypothesis is that the gap is **safe combination of clause + transaction options under adapter limits**, not a new locking feature. Correct the problem frame, the meaning of `false`, or the SQLite no-op choice if those are wrong.
