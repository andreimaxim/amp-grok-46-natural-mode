**Block.** Changing `Hash#compact_blank!` from `value.blank?` to `value.nil?` does **not** preserve the Active Support API. It would reimplement Ruby’s `Hash#compact!` (nil-only) and break `compact_blank!`’s documented `Object#blank?` contract.

The author’s equivalence is the wrong comparison. `compact` / `compact!` drop only `nil`. `compact_blank` / `compact_blank!` drop every blank value. Those are two APIs; matching the first does not preserve the second.

### Contract at this revision

[Hash#compact_blank!](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L266-L275) is explicit:

```266:275:activesupport/lib/active_support/core_ext/enumerable.rb
  # Removes all blank values from the `Hash` in place and returns self.
  # Uses Object#blank? for determining if a value is blank.
  #
  # ```
  # h = { a: "", b: 1, c: nil, d: [], e: false, f: true }
  # h.compact_blank!
  # # => { b: 1, f: true }
  # ```
  def compact_blank!
    # use delete_if rather than reject! because it always returns self even if nothing changed
    delete_if { |_k, v| v.blank? }
  end
```

The non-bang sibling [Hash#compact_blank](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L261-L263) uses the same predicate (`reject { |_k, v| v.blank? }`). Enumerable’s public docs at [enumerable.rb:190–208](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L190-L208) show the same example: `false`, `""`, `[]`, and `nil` are removed; `1` and `true` stay.

[`Object#blank?`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L7-L9) is: *false, empty, or a whitespace string* — including `nil`, `''`, `'   '`, `[]`, `{}`, and `false`. Numbers and `true` are not blank ([Numeric#blank?](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L180-L188), [TrueClass#blank?](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L86-L90)).

Ruby `Hash#compact` is a different method. Ran on this checkout:

```text
{ a: nil, b: false, c: "", d: [], e: {}, f: 0, g: true }.compact
## => { b: false, c: "", d: [], e: {}, f: 0, g: true }
```

Action Pack even documents the split: [Parameters#compact](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb#L1030-L1036) removes `nil`; [Parameters#compact_blank](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb#L1042-L1052) uses `blank?`.

### Tests already contradict the claim

[test_hash_compact_blank](file:///home/user/workspace/repo/activesupport/test/core_ext/enumerable_test.rb#L380-L383) and [test_hash_compact_blank!](file:///home/user/workspace/repo/activesupport/test/core_ext/enumerable_test.rb#L385-L389) use `{ a: "", b: 1, c: nil, d: [], e: false, f: true }` and expect `{ b: 1, f: true }`.

A `nil?` rewrite would leave `""`, `[]`, and `false` in place and fail those two tests immediately. |---|---|---|---|---|
| `nil` | true | true | **removed** | **removed** |
| `false` | true | false | **removed** | kept |
| `""` | true | false | **removed** | kept |

On `{ a: "", b: 1, c: nil, d: [], e: false, f: true, g: " ", h2: {}, i: 0 }`:

- current `compact_blank!` → `{ b: 1, f: true, i: 0 }`
- proposed `delete_if { |_k, v| v.nil? }` → `{ a: "", b: 1, d: [], e: false, f: true, g: " ", h2: {}, i: 0 }`

Only `nil` vs `false`/`""`/`[]`/`{}`/`" "` is the break. Numerics and `true` are unchanged either way.

### Bang return / identity

The `delete_if` choice is intentional, not incidental. The comment at [enumerable.rb:273](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L273) is the contract: always return `self`, even if nothing changed.

Ran:

- `compact_blank!` on `{ a: 1, b: true }` → same object, not `nil`
- `Hash#delete_if` on a no-op → same object
- `Hash#compact!` on `{ a: 1 }` → **`nil`**
- `Hash#reject!` on a no-op → **`nil`**

So `delete_if { … nil? }` would keep the return-identity of `compact_blank!` (always `self`) while still changing *which* entries are deleted. It would **not** match `Hash#compact!`, which returns `nil` when nothing is removed. Equivalence to Ruby compact fails on both membership and bang return.

The existing bang tests never assert return value or object identity; they only mutate then check contents. That gap does not make the `self` contract optional — it is in the method comment and is why `delete_if` was chosen over `reject!`.

Note: [Parameters#compact_blank!](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb#L1051-L1052) uses `reject!`, so it *can* return `nil`. That is a different class; do not copy it onto `Hash`.

### Minimal regression matrix (do not implement here)

Keep the existing hash fixture as the first row. Add only what current tests omit.

1. **Membership (same receiver, assert contents)**  
   Start: `{ a: nil, b: false, c: "", d: " ", e: [], f: {}, g: 0, h: 1, i: true }`  
   After `compact_blank!`: `{ g: 0, h: 1, i: true }`  
   This is the row that fails under `nil?`.

2. **Identity / return**  
   `h = { a: 1 }; r = h.compact_blank!`  
   `assert_same h, r` and `assert_equal({ a: 1 }, r)`  
   Catches a mistaken switch to `compact!` / `reject!`.

3. **Non-bang pair**  
   Same input as (1) through `compact_blank` (new hash, original unchanged). Prevents bang-only drift.

4. **Whitespace / empty collections as values**  
   Already implied by (1); if you split cases, `" "`, `[]`, `{}` are the ones `nil?` would wrongly keep.

Do not add a test that expects Ruby-`compact` membership. That would lock in the bug.

**Ship/block:** block the refactor. `blank?` → `nil?` is a breaking behavior change, contradicted by docs, examples, and [enumerable_test.rb:380-389](file:///home/user/workspace/repo/activesupport/test/core_ext/enumerable_test.rb#L380-L389). The only part of the claim that is true is that `nil` is removed either way.
