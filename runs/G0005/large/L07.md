`Object#with` is a per-key begin/ensure overlay: for each keyword, it reads the current public value, then assigns the replacement, yields the receiver, and in `ensure` writes back only the values it actually captured.

```31:43:activesupport/lib/active_support/core_ext/object/with.rb
  def with(**attributes)
    old_values = {}
    begin
      attributes.each do |key, value|
        old_values[key] = public_send(key)
        public_send("#{key}=", value)
      end
      yield self
    ensure
      old_values.each do |key, old_value|
        public_send("#{key}=", old_value)
      end
    end
  end
```

### Assignment order

The kwargs hash is walked once, in insertion order. Each key is handled fully before the next:

1. `public_send(key)` — public reader
2. store that result in `old_values[key]`
3. `public_send("#{key}=", value)` — public writer

It is not “read all, then write all.” A later key is not touched until the earlier key’s write has returned. That is the whole body of the `each` at [with.rb:34-37](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/with.rb#L34-L37).

The comment’s single-attribute expansion at [with.rb:19-26](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/with.rb#L19-L26) matches one iteration of that loop, not a two-pass over the whole hash.

### What the block receives and returns

After every requested write has returned, the method does `yield self` ([with.rb:38](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/with.rb#L38)). The block therefore gets the original receiver, with the temporary values already applied.

`with`’s result is the block’s result: `yield self` is the value of the `begin` body, and `ensure` does not change that value unless it raises. Both are asserted:

- [with_test.rb:91-93](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L91-L93) — `@object.with(public_attr: "1", &:public_attr)` equals `"1"` (the yielded object, under the temporary value)
- [with_test.rb:95-98](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L95-L98) — `{ :block_result }` is what `with` returns

The happy-path test at [with_test.rb:32-43](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L32-L43) is the same sequence with two public attributes: inside the block both are the new values; after `with` returns both are the originals.

```text
with(public_attr: :changed, another_public_attr: :changed_too)
  old_values = {}
  public_send(:public_attr)            # => :public
  public_send("public_attr=", :changed)
  public_send(:another_public_attr)    # => :another_public
  public_send("another_public_attr=", :changed_too)
  yield self                           # block return value is with's return
ensure
  public_send("public_attr=", :public)
  public_send("another_public_attr=", :another_public)
```

Restore order is insertion order, not LIFO. First assigned is first restored.

### `ensure` when the block raises

`old_values` is populated before `yield`, so a raise inside the block still restores every successfully assigned key. The exception then propagates; `with` does not swallow it.

[with_test.rb:45-59](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L45-L59) is that path: both writers are public, the block sees `:changed` / `:changed_too`, raises `RuntimeError`, and after `assert_raise` both attributes are back to `:public` / `:another_public`. I ran `activesupport/bin/test test/core_ext/object/with_test.rb`; that file printed `7 runs, 31 assertions, 0 failures`.

### Two attributes: first write succeeds, second writer raises

This is [with_test.rb:61-73](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L61-L73) against `Record` ([with_test.rb:7-26](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L7-L26)):

- `public_attr` — public reader and writer
- `mixed_attr` — public reader, private writer (`attr_reader` at line 18, `attr_writer` under `private` at line 25)

Call:

```ruby
@object.with(public_attr: :changed, mixed_attr: :changed_too)
```

Kwargs insertion order is `public_attr` then `mixed_attr`, so:

1. `old_values[:public_attr] = public_send(:public_attr)` → `:public`
2. `public_send("public_attr=", :changed)` succeeds → object now has `:changed`
3. `old_values[:mixed_attr] = public_send(:mixed_attr)` → `:mixed`  
   The private writer has not run yet; the key is already in `old_values`.
4. `public_send("mixed_attr=", :changed_too)` raises `NoMethodError`  
   `mixed_attr` on the object is still `:mixed`.
5. `yield self` does not run (`assert false` at [with_test.rb:67](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L67) is never reached).
6. `ensure` walks `old_values` as `{ public_attr: :public, mixed_attr: :mixed }`:
   - `public_send("public_attr=", :public)` — this is the value that was actually restored; the object goes from `:changed` back to `:public`
   - `public_send("mixed_attr=", :mixed)` — same private writer, so this restore also is not a public send

After the call, the test asserts `public_attr == :public` and `mixed_attr == :mixed`. From the implementation, those two finals are not the same kind of restore:

- `public_attr` was overwritten and then written back from `old_values`
- `mixed_attr` never left `:mixed`; it is in `old_values` only because the reader ran before the writer raised

The test observes one escaping `NoMethodError` and those two finals. It does not distinguish the original setter failure from a second `NoMethodError` on the `mixed_attr` restore. Both writes use `public_send`, so a non-public writer fails in `ensure` the same way it failed on the way in.

### Public reader and public writer

Every access is `public_send`, so both the getter and the setter must be public ([with.rb:29-30](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/with.rb#L29-L30), [with.rb:35-36](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/with.rb#L35-L36), [with.rb:41](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/with.rb#L41)).

[with_test.rb:75-89](file:///home/user/workspace/repo/activesupport/test/core_ext/object/with_test.rb#L75-L89) covers the three failures:

| call | what fails | `old_values` | object afterward |
|---|---|---|---|
| `private_attr:` | public reader (`NoMethodError`) | empty | unchanged; `ensure` is a no-op |
| `protected_attr:` | same | empty | unchanged |
| `mixed_attr:` | public reader succeeds; public writer `NoMethodError` | `{ mixed_attr: :mixed }` | still `:mixed`; `ensure` retries the private writer |

Protected and private accessors are therefore unusable even from inside the object’s own methods, because `with` never uses a non-public send.
