---

**Problem frame:** A view author needs a single-control submit that performs a named action (sign in, delete, update) without being followed like a link. Today the same helper accepts a string label or a block, several URL shapes, and several verbs, but the page that comes out does not always match what the call looks like: the visible name, the real verb, whether a token is present, whether the control can be used, and where nested form options land. Keyboard and assistive-tech users then meet a form that may have a URL as its name, a disabled submit that is still a form, or a confirmation hook that never runs because it was attached to the wrong element. The desired progress is that every supported calling form produces a control whose destination, verb, name, enabled state, and safety behavior can be predicted from the call, and that people can operate or skip that control with the same understanding a sighted mouse user gets.

**Actors**
- View authors writing templates and helpers.
- People using the rendered page, including keyboard and assistive-tech users.
- App maintainers who already ship `button_to` in production templates.
- Automated clients (crawlers, prefetchers) that must not trigger state-changing actions.

### Current observable baseline

Evidence: helper docs and generated examples, the navigation helper tests above, `url_for(nil)` in the URL helper tests, Action Pack CSRF tests, and the Action View / JS / upgrade guides. Limits: no `button_to` test for a `nil` URL, no `button_to` test for a label containing markup, and GET token omission is shown with forgery protection off.

**Calling forms.** A string name plus URL is the default. A block treats the first argument as the URL (or model/hash) and the second as HTML options; the block body is the control’s content, including nested tags such as a span. `false` as the URL omits the form action, with or without a block. A `nil` name uses the URL string as the visible label. Path helpers, controller/action hashes, records, and nested record arrays all resolve through URL generation.

**URL conversion.** String URLs are used as the form action (query `&` escaped). `false` yields no action. Records and nested arrays use resource routing. `url_for(nil)` in a full view context is the current path; `button_to` with `nil` is untested, so whether that becomes “this page,” “no action,” or an error is not established for this helper.

**Method selection.** Default is POST on the form. GET is a GET form with no `_method` field and no authenticity field in the GET tests. DELETE (and PATCH/PUT) stay POST on the form and add a hidden `_method`. A new record infers POST; a persisted record infers PATCH. That PATCH inference is a documented Rails 7 change; arrays that end in a persisted record inherit it unless the author sets a method.

**Authenticity token.** Emitted only on the POST form path, and only when forgery protection is present and on. A string token is used as-is; `true` uses the generated token; `false` omits it. Per-form CSRF tests bind the token to the form’s action and verb: a DELETE `button_to` token is accepted for DELETE and rejected for PATCH. `remote: true` is not covered with forgery on for `button_to`; other remote form helpers can omit the token unless embedding is enabled. Whether `button_to remote: true` follows that policy is not established by these tests.

**Form attributes.** Default form class is `button_to`. `form_class` replaces that class and is escaped. A nested `form:` hash supplies extra form attributes (`class`, `data-type`, and similar). `remote: true` sets `data-remote` on the form; `remote: false` does not. Confirm and disable-with data land on the submit control in the helper tests, while the JS guide says Turbo confirmation for `button_to` must be passed through `form:`. `form:` does not win on method or action in current output: those are always the helper-chosen verb and URL.

**Block vs string control.** With the current default, both forms render a submit control whose accessible name is the string or the block content. When the older config is off, a string label becomes an `input type="submit"` whose name is the `value`, while a block still becomes a `button` whose name is its content.

**Disabled.** `disabled: true` marks the submit control disabled; `disabled: false` does not. The form is still present.

**Unsafe HTML.** `form_class` containing a script tag is escaped (tested). A string label is not tested for markup; the tag layer used for helper content escapes ordinary strings and keeps html_safe content. A block that yields already-built tags keeps that structure inside the control.

### User problems and desired outcomes

**String label vs block.** Authors cannot always tell which argument is the URL, which is options, or what will be announced as the control’s name. Users can get a raw URL as the name when the label is omitted, or rich inner content when a block is used, with no shared rule across the two forms.

*Outcome:* From either calling form, the author can tell what will be named and submitted, and the user hears/sees a name that matches that intent—not the destination URL unless the author chose that.

**GET vs POST vs DELETE.** GET looks like the same helper but navigates without a token. POST and DELETE look like buttons but DELETE is still a POST form with a hidden verb. Persisted records silently become PATCH. Users are not told the HTTP verb; they only have the visible name.

*Outcome:* The author can predict the effective verb from the call (including record and array URLs). Users can complete GET as navigation and POST/DELETE as an explicit action whose visible name states the effect. Crawlers still do not follow DELETE/POST as ordinary links.

**`remote: true`.** Remote is a form flag; confirm/disable data are on the submit control in helper output, but Turbo confirmation is documented as needing `form:`. Authors copy `data: { confirm: ... }` from `link_to` and the extra prompt never appears.

*Outcome:* Choosing remote does not change the named action, verb, or whether the user is asked to confirm. Authors can tell which options apply to the control they think they are clicking.

**Disabled buttons.** The submit control can be disabled while a form still sits in the page. Users may still land on a form that cannot be submitted, with no explanation.

*Outcome:* A disabled call is not operable by pointer, keyboard, or assistive tech. The control’s name and disabled state remain perceivable.

**Nested `form:` options.** Authors use `form:` for class and data, and may expect it to set method or action. Method and action currently come only from the helper. `form:` class wins over `form_class`.

*Outcome:* Nested form options that are honored stay honored across calling forms. Options that cannot change destination or verb fail in a way authors can predict, rather than being silently overwritten.

**Explicit `authenticity_token`.** String / `true` / `false` already differ, and GET never participates. Remote token policy is unclear relative to other forms. Wrong verb or missing token shows up as a forgery error after submit, not at the call site.

*Outcome:* Authors can predict whether a token is present from verb + token argument + forgery setting. Users submitting a well-formed control are not rejected for a token the helper omitted or bound to the wrong verb.

**Nil URLs.** `false` means no action (tested). `nil` is unspecified for `button_to` and, elsewhere, `url_for(nil)` is the current path. Authors can ship a form that posts to “here” without meaning to.

*Outcome:* A missing or nil destination has one explained result across string and block forms (current page, no action, or a visible failure)—not two silent meanings.

**Labels containing unsafe HTML.** Ordinary strings should not become markup in another user’s browser. Blocks are the path for intentional structure (icon plus text). That split is only partly tested.

*Outcome:* Untrusted label text cannot run as markup. Authors who pass intentional structure through a block still get that structure as the control’s name.

---

**Behavioral outcome (overall):** Across the supported calling forms, `button_to` yields one predictable, operable control: same destination, same verb, same name, same enabled state, same token presence, and same safety around untrusted labels—usable with keyboard and assistive tech without inspecting the HTML.

**Example (core, required):** An author writes a labeled control to delete a record with DELETE. A user who can see the page, tab to it, or hear it gets a control named like the label, can activate it, and the app runs the delete. A crawler following links does not.

**Example (block vs string, required):** The same destination and options with a string label and with a block that yields the same text produce a control with the same name, destination, and verb. Omitting the label does not silently substitute a URL unless the product decision is that that remains the fallback.

**Example (GET vs POST, required):** GET does not send a forgery token and does not change data as a side effect of being fetched. POST does require a token when forgery protection is on.

**Example (DELETE, required):** DELETE remains an explicit user action (not a GET link). The visible/accessible name still describes the effect, because the user is never told the hidden verb.

**Example (`remote: true`, required):** Remote does not drop the name, disable the control, or change the verb. If the author asked for a confirmation, the user gets that prompt before the action; if they did not, they do not.

**Example (disabled, required):** `disabled: true` cannot be submitted; `disabled: false` can. The name stays available.

**Example (`form:`, boundary):** Extra form attributes the author sets (class, data) appear on the form. Setting method or action only inside `form:` does not silently retarget the submit relative to the helper’s URL and verb.

**Example (token, required):** With forgery on, a custom token string is what is submitted; `false` submits none; `true` or omission uses the generated token for that action and verb. GET still has none.

**Example (nil URL, boundary):** `false` keeps producing a form with no action. `nil` must not be an undocumented second meaning; until product chooses, treat this as unresolved.

**Example (unsafe HTML, required):** A label of `<script>…</script>` does not execute for another user. A block that yields a span plus text remains structured content and that combined text is the name.

**Counterexample (out of scope):** This is not “make `link_to` with a method look like a button.” The existing purpose of `button_to` is a real user-activated submit so non-GET actions are not crawled.

---

**Constraints**
- Keep a user-activated submit for state-changing actions so bots and prefetch do not trigger them.
- Do not drop the calling forms already in use: string, block, path, hash, record, nested records, `false` URL.
- Keep forgery protection available and verb-correct for POST/DELETE/PATCH/PUT.
- Do not require authors to pass new arguments to keep current pages working, unless a documented compatibility break is an explicit product choice.
- Accessibility here means operable, named, and skippable controls—not a visual redesign.

**Non-goals**
- Changing `link_to`, `form_with`, or `url_for` as general APIs.
- Changing the CSRF protocol itself.
- New helper names or new options (not part of this shaping).
- Prescribing markup, ARIA, JavaScript, or Turbo internals.
- Restyling default buttons or changing routing.

**Compatibility risks (if later work changes what authors already rely on)**
- CSS and JS that target `form.button_to` or `input type="submit"`.
- Templates that depend on inferred PATCH for persisted records.
- Confirm/disable data on the button vs on the form (Turbo vs older UJS).
- Token presence on remote forms vs other helpers.
- `form:` being unable to override method/action.
- html_safe labels and block-built markup.
- Optional content-exfiltration prefix comments around the form.
- Older apps that still generate `input` instead of `button` for string labels.

---

**Steering evidence**
- Success looks like: authors stop checking rendered HTML to know destination, verb, token, and name; AT users can find and activate or skip the control from the label they were given; disabled actions do not submit; untrusted labels do not execute; DELETE/POST still do not behave like crawlable links.
- Investigate if authors still need a cheat sheet per calling form, or if GET/remote/disabled each produce a different user experience for the same label.
- Reconsider the framing if the real failures are Turbo confirmation placement only, or CSRF only, and not naming/operability across forms.
- Stop or narrow if changing output would break more existing pages than it helps, with no compatibility path.

**Measurable external success signals (qualitative; no numeric targets invented)**
- View authors can state destination, verb, token presence, enabled state, and accessible name from the call alone, for string and block forms.
- Keyboard users can tab to an enabled control and activate it; they cannot activate a disabled one.
- Screen-reader users get a name that matches the visible label (not an unnamed submit, and not a URL unless that was the label).
- Destructive actions still require an explicit submit, not a GET fetch.
- Forgery errors do not appear for helpers that were supposed to include a verb-correct token, and do not disappear for GET.
- Upgrade/issue reports do not cluster on “my confirm never ran,” “this posted PATCH,” or “this posted to the current page” after the change. If they do, the framing missed the actual pain.

**Open product questions**
1. Is `nil` as the URL “current page,” “same as `false`,” or an author error?
2. Should omitting the label still fall back to the URL as the accessible name?
3. Should GET stay in this helper, given that non-GET is the accessibility reason to prefer a real submit?
4. Should `remote: true` follow the same token-embedding rule as other remote forms?
5. Where must confirmation live so users actually get the prompt—without this brief specifying attributes?
6. Is inferred PATCH for persisted records still desired, or only explicit `method:`?
7. How much existing HTML (class names, `input` vs `button`, data placement) is frozen for compatibility?
8. Are view authors and AT users equal audiences, or is author predictability the primary goal with accessibility as a constraint?

I treated “predictability” as call-site → destination/verb/name/token/enabled state, and “accessibility” as being able to perceive, operate, or skip that control. I did not treat the `UrlHelper` → `NavigationHelper` move as in-scope work.
