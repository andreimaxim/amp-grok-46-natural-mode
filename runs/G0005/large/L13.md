**Problem frame:** Test and diagnostic authors need to watch notifications only while a block of code runs. Today that scoped watch exists, but it is a second-class, easy-to-misuse path next to long-running `subscribe`.

This is a **behavior-change** brief for the existing temporary-observation path. It does not add a new kind of instrumentation, and it does not change permanent subscribe/unsubscribe.

---

## Who feels this, and why it matters

The people writing Rails tests, query counters, and one-off diagnostic probes need to say: “while this block runs, tell me about matching events, then stop.” That is already the documented job of `ActiveSupport::Notifications.subscribed` ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L155-L191)). Rails itself uses it that way in [notification assertions](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L79-L88) and Active Record query assertions.

What they get today is workable but awkward:

- The public instrumentation guide teaches only long-running `subscribe` / `monotonic_subscribe`. It never shows a block-scoped watch.
- The API docs warn that temporary subscription is against the framework’s design because it wipes internal caches ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L157-L160)). People who need it for tests are told to use it sparingly.
- `subscribe` takes a pattern then a callback or block. `subscribed` takes the callback first, then an optional pattern. Callers cannot pass the observer as a block the way they do for `subscribe`.
- Nested watches and raising instrumented blocks still work through the general instrumentation contract, but the temporary API’s own tests cover only the happy path of “events during the block, silence after.” Authors of capture helpers have to infer the rest.

The desired progress is that a test or diagnostic author can observe matching events for the life of a block, and only that life, without fighting argument order, leftover listeners, or surprise around nesting and errors—while permanent subscribers keep behaving as they do now.

*Hypothesis, not a user-supplied fact:* the pain is usability of **scoped observation**, not missing event types or a desire to replace `subscribe`.

## Current behavior (this revision)

Stimuli: `instrument` / `publish` while a `subscribed` block is on the stack. Observable result: the supplied callback is invoked for matching events, then is gone.

**Exact-name matching.** Documented as watching one name for the block ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L168-L179)). Tested: inside `subscribed(callback, "foo")`, `"foo"` is seen twice and `"foofoo"` is not; after the block, another `"foo"` does not grow the list ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L241)).

**Regexp matching.** Documented for `subscribe` as “all events whose name matches a regexp” ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L141-L145)). `subscribed` takes the same `pattern` and passes it through ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L336)). Direct `SubscribedTest` coverage is exact-name and all-events only. Regexp-through-`subscribed` is tested by `capture_notifications(/post\./)`, which is implemented as `subscribed` ([notification_assertions.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L79-L88), [notification_assertions_test.rb](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L92-L97)). Long-running regexp subscribe is also tested on the notifier ([evented_notification_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications/evented_notification_test.rb#L171-L185), [notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L432-L441)).

**All-event matching.** Documented: omit the pattern and you subscribe to every event ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L147-L149)). `subscribed` defaults `pattern` to `nil`. Tested: with no pattern, `"foo"` and `"foofoo"` are both collected; after the block, further `"foo"` is not ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L260)). `capture_notifications` with no pattern behaves the same ([notification_assertions_test.rb](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L99-L104)).

**Automatic unsubscription after the block.** Documented: the callback is unsubscribed automatically when the block ends ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L178-L179)). The method always unsubscribes in `ensure` ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L336)). The success-path tests above are the tested proof: instrumentation after the block does not call the callback. There is no dedicated `subscribed` test that the listener is gone after the **block** raises.

**Wall-clock vs `monotonic: true`.** Documented: default timestamps are wall-clock; `monotonic: true` records monotonic start/finish; default is `false` ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L180-L191)). Tested on `subscribed`: five-argument callbacks see `Time`/`Time` by default and `Float`/`Float` with `monotonic: true`; a later instrument after the block does not overwrite those classes ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L309)). The same clock split exists on long-running `subscribe` vs `monotonic_subscribe` ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L134-L157); [instrumentation guide](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L31-L72)).

**Nested instrumentation and payload mutation.** Nested `instrument` publishes the inner event before the outer one, each with its own payload ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L486-L500)). Mutations the instrumented block writes into the yielded payload are what subscribers see ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L53), [L475-L479](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L475-L479); [instrumenter.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/instrumenter.rb#L85-L95)). Nested **temporary** watches have a start-vs-finish boundary: if an event starts under the outer `subscribed` and finishes under an inner one, only the outer callback receives it ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L223)). That is tested current behavior, not a defect report.

**Exceptions from the instrumented block.** Documented: the event is still published; payload gains `:exception` (`[class name, message]`) and `:exception_object`; the error is re-raised ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L98-L106); [instrumenter.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications/instrumenter.rb#L81-L95)). Tested on `instrument`, not on `subscribed` itself ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L502-L514)). Combined with `subscribed`’s `ensure`, the intended observable story is: the observer still sees the failed event, the original error still leaves the block, and the observer is not still registered afterward. The last of those three is documented by `ensure`, not by a `subscribed` test.

**Callback arities (must stay).** One argument yields an `Event`. Otherwise the callback receives `name, started, finished, unique_id, payload` ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L38-L70), [L279-L305](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L279-L305); guide [L31-L72](file:///home/user/workspace/repo/guides/source/active_support_instrumentation.md#L31-L72)). Tests: single-arity Event and callable ([notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L30-L43), [L106-L128](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L106-L128)); five-argument timed callbacks ([L134-L157](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L134-L157), [L279-L309](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L309)). `subscribed` examples use both Event lambdas and five-argument lambdas.

**Long-running `subscribe` / `unsubscribe` (must stay).** Permanent subscribe returns a subscriber; unsubscribe by object or by name; unsubscribing a string name does not remove a regexp subscriber from other matching names ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L193-L226); [notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L323-L373)). That path is the default; temporary watch is the exception.

## Desired observable outcomes

These are claims about what a test or diagnostic author can do. They are not a design.

1. **Scoped watch.** Given a callback and an optional matcher, the author runs a block and the callback is invoked only for matching events that complete while that block is in force. After the block returns or raises, later matching events do not invoke that callback.

2. **Same matchers as today.** Exact string name, regexp, and “all events” (no pattern) remain the three ways to choose what the scoped watch sees.

3. **Clock choice stays explicit.** Without `monotonic: true`, five-argument start/finish values remain wall-clock `Time`. With `monotonic: true`, they remain monotonic `Float`. Existing one-argument `Event` callbacks keep working.

4. **Nested work stays inspectable.** An instrumented block that itself instruments still produces an inner event then an outer event. Payload keys written during the block are visible to the scoped observer. An inner scoped watch does not silently inherit events whose start happened only under an outer watch—*unless we later decide that boundary is the usability bug; today it is tested behavior.*

5. **A raising instrumented block is still observable.** The error still comes out of the block. The observer still sees the event, including `:exception` and `:exception_object`. The scoped observer is not still listening afterward.

6. **Permanent subscribers are untouched.** `subscribe`, `monotonic_subscribe`, and `unsubscribe` keep their current matching, lifetime, name-based unsubscribe, and callback arities. A scoped watch does not unsubscribe someone else’s long-running listener.

## Non-goals

- Changing long-running `subscribe` / `monotonic_subscribe` / `unsubscribe`.
- Changing one-argument vs five-argument callback contracts, or evented start/finish listeners.
- Adding or renaming instrumentation events, or changing payload keys other than what `instrument` already writes on error.
- Making temporary observation the default for production, app-lifetime listeners.
- Prescribing classes, data structures, algorithms, or a new public type.
- Performance targets or cache-implementation work, except insofar as authors can keep using scoped observation in tests without leftover listeners.

---

## Compatibility constraints

- Callback arities stay: `Event` vs `name, started, finished, unique_id, payload`.
- Matcher vocabulary stays: `String`, `Regexp`, or omit for all events. Invalid pattern types continue to be rejected on subscribe ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L306-L310); [notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L545-L552)).
- Default clock for `subscribed` stays wall-clock; monotonic remains opt-in.
- Helpers that already call `subscribed`—`capture_notifications`, Active Record query assertions—must keep being able to collect events for a block and stop. Their public assertion behavior is out of scope except as a consumer that must not break.
- Unsubscribing a temporary watch must not strip a long-running regexp subscriber from unrelated names (current `unsubscribe` by name vs regexp exclusion, [notifications_test.rb](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L354-L373)).

## Representative examples

Required unless marked illustrative.

**Exact name, then silence.** Author passes a callback and `"sql.active_record"`, runs a block that instruments that name twice and another name once. Callback sees the two SQL events only. After the block, another SQL event is not delivered to that callback. *(Matches [test_subscribed](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L226-L241).)*

**Regexp.** Author watches `/post\./` and instruments `"post.submitted"`. The callback sees that event. A name that does not match is omitted. *(Matches [capture_notifications regexp](file:///home/user/workspace/repo/activesupport/test/testing/notification_assertions_test.rb#L92-L97).)*

**All events.** Author omits the pattern. Every instrumented name during the block is delivered; none are after. *(Matches [test_subscribed_all_messages](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L244-L260).)*

**Wall-clock vs monotonic.** Same five-argument callback, same event name. Default: `started`/`finished` are `Time`. With `monotonic: true`: they are `Float`. After the block, a further instrument does not invoke the callback. *(Matches [test_timed_subscribed](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L279-L294) / [test_monotonic_timed_subscribed](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L297-L309).)*

**Nested instrumentation and payload mutation.** Inside a scoped watch, an outer `instrument` block mutates its payload and runs an inner `instrument` with a different payload. The observer sees the inner event first, then the outer, and sees the mutated keys. *(Matches [nested events](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L486-L500) and [payload mutation](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L45-L53).)*

**Nested scoped watches (boundary).** Outer watch starts an event handle, inner watch is installed, then the handle finishes. Only the outer callback receives that event. *(Matches [test_subscribed_interleaved_with_event](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L197-L223). Treat as required current behavior unless we explicitly decide inner watches should see in-flight events.)*

**Raising instrumented block.** Inside `subscribed`, `instrument` raises. The error propagates. The callback still received the event, with `:exception` / `:exception_object`. A later matching instrument does not invoke that callback. *(Exception payload matches [test_instrument_publishes_when_exception_is_raised](file:///home/user/workspace/repo/activesupport/test/notifications_test.rb#L502-L514). Post-raise unsubscription is the `ensure` contract, not a current `subscribed` test.)*

**Counterexample — permanent subscribe stays.** A long-running `subscribe("render")` installed before a `subscribed` block still receives `render` events after that block ends. Unsubscribing the temporary watch does not remove it. *(Illustrative of the compatibility constraint; not a `subscribed` test today.)*

## Acceptance signals

**Success looks like:** A maintainer writing a capture helper or a one-off diagnostic can watch a name, a regexp, or everything for one block; choose wall-clock or monotonic timestamps; see nested and mutated payloads; still see the event when the block raises; and not have that observer fire afterward. Existing `subscribe` / `unsubscribe` callers, including one- and five-argument callbacks, notice no change.

**Investigate the implementation of the outcome if:** After a `subscribed` block returns or raises, the same callback still fires; a regexp or all-event watch misses or over-collects; monotonic/wall-clock types flip; or query/notification assertions start failing because they no longer collect only in-block events.

**Reconsider the problem framing if:** Authors were not struggling with scoped observation at all, but with leftover **permanent** subscribers in tests, with production performance of long-running subscribers, or with Event vs five-argument confusion on `subscribe` itself. Those are different problems.

**Stop or split if:** The work cannot preserve callback arities or long-running unsubscribe-by-name vs regexp behavior. Those are hard constraints, not tradeoffs.
