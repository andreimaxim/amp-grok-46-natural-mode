This is a **behavior-change** shaping draft: later-delivery already lands on queues, but targeting those queues in tests is unreliable at name and ownership boundaries. Correct the problem or examples if they miss how teams actually talk about queues.

## Current observable contract

Evidence from this checkout’s source, the existing Action Mailer / Active Job tests (all passing: 14 queue tests in `message_delivery_test`, 38 filtered tests in `test_helper_test`, 14 in `queue_naming_test`), and live enqueue/filter probes. Probes establish the exact landing names below; production adapters were not run.

**Who chooses the queue**

- Each mailer has a later-delivery queue setting. Unset, it is `:mailers`. A subclass can change its own setting without changing its parent or `ActionMailer::Base`. Apps on Rails 6.1+ defaults set the base value to `nil`. ([queued_delivery.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/queued_delivery.rb#L7-L9), [base.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/base.rb#L472-L476), [configuration.rb](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L216-L218), [configuration_test.rb](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L1451-L1484), [message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L119-L131))
- `deliver_later` / `deliver_later!` accept a per-send `queue:` that overrides the mailer’s setting for that send. `wait` / `wait_until` schedule without changing that queue rule. ([message_delivery.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L61-L107), [message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L94-L116))
- If the mailer uses a custom delivery job, that job owns the queue unless the send also passes `queue:`. A custom job that declares its own queue does **not** use the mailer’s later-delivery setting. Docs state the same. ([message_delivery.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L71-L76), [configuring.md](file:///home/user/workspace/repo/guides/source/configuring.md#L3086-L3105), probe: custom job landed on `"delivery_job_queue"`)

**What name actually lands**

Active Job turns the chosen part-name into the stored queue name: symbols become strings, `nil` becomes the Active Job default (`"default"`), and a configured prefix is prepended. The test adapter then compares with `queue.to_s`. ([queue_name.rb](file:///home/user/workspace/repo/activejob/lib/active_job/queue_name.rb#L47-L65), [core.rb](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L175-L178), [test_adapter.rb](file:///home/user/workspace/repo/activejob/lib/active_job/queue_adapters/test_adapter.rb#L68-L72), [queue_naming_test.rb](file:///home/user/workspace/repo/activejob/test/cases/queue_naming_test.rb#L32-L48))

**What testers can do today**

- `deliver_enqueued_emails` performs later-delivery jobs (default and custom delivery jobs). With no `queue:`, it performs every such job in scope. `queue:` keeps only jobs whose **stored** name equals `queue.to_s`. `at:` keeps only jobs due by that time. ([test_helper.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/test_helper.rb#L184-L223), [test_helper.rb](file:///home/user/workspace/repo/activejob/lib/active_job/test_helper.rb#L687-L697), [test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L581-L634))
- Observed filters: `queue: :external` and `queue: "external"` each delivered one of two mailers; `queue: mailer.deliver_later_queue_name` did the same. `queue: :external` delivered **none** when the stored name was `"prod_external"`. Filtering a custom-job mailer by its unused mailer setting delivered none; filtering by the job’s queue delivered it. `at: 1.hour.from_now` delivered the immediate send and not `wait: 2.hours`. Passing `queue: nil` is “no queue filter,” not “the nil/default queue.”
- `assert_enqueued_email_with` already resolves the expected queue through the mailer’s delivery job (so `nil`, symbols, custom jobs, and prefixes can match without the caller passing a name). `deliver_enqueued_emails` does not. ([test_helper.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/test_helper.rb#L146-L168), [test_helper_test.rb](file:///home/user/workspace/repo/actionmailer/test/test_helper_test.rb#L339-L437))

## Shaping brief

**Problem frame.** A team that splits later-delivery mail across queues (billing vs. notifications, a one-off urgent send, a custom delivery job) needs to perform or inspect **exactly** those emails in a test. Today they configure a queue in mailer terms (`:mailers`, `nil`, a subclass setting, a job-owned name) and then filter in adapter terms (string, prefix, default queue). The names often do not refer to the same work, so the test delivers the wrong mail, delivers none, or delivers everything.

**Desired outcome.** After mail is enqueued with `deliver_later`, a tester can perform or inspect that mail by referring to the queue the team already chose, and can exclude mail that does not belong to it. That identity stays stable across several mailers, parameterized sends, scheduled sends, symbol vs string vs `nil`, a custom delivery job, and adapters that stringify or prefix queue names. Success is qualitative: the intended emails are delivered in the test, and the others remain unsent.

**Appetite (hypothesis).** One small cycle aimed at reliable targeting against the contract above—not a new mail API and not a redesign of Active Job. If the work grows into adapter-specific matching rules, stop and split.

**Scope.** Make queue identity usable at the two moments teams already have: choosing a queue on `deliver_later`, and selecting later-delivery mail with `deliver_enqueued_emails` (including `queue:` and `at:`). The enqueue precedence in this revision stays the product rule: per-send `queue:` wins; else the custom job’s queue if it has one; else the mailer’s later-delivery setting; `nil` means the Active Job default; prefix applies to that resolved name. Inheritance stays per-mailer.

**Non-goals.** Changing when mail is sent in production, changing `deliver_now`, inventing a second queue model, making `deliver_enqueued_emails` perform non-mail jobs, or requiring every adapter to accept symbols. Document-only work is not enough if filters still miss prefixed or job-owned names.

**Risks.** Tightening “same queue” can break tests that pass today’s stringified name by accident. Prefixes create two plausible names (logical `:mailers` vs stored `"prefix_mailers"`). Custom jobs create two names (mailer setting vs job queue); the contract says the job wins, but testers still pass the mailer setting. Treating omitted `queue:` as “all queues” must not be confused with `nil` meaning the default queue.

**Steering.** Investigate if testers who copy the mailer’s setting still miss mail under a prefix or custom job. Reconsider the framing if the real pain is “I don’t know which queue this mailer uses,” not “I named it and the filter disagreed.” Stop if success requires per-adapter special cases.

### Acceptance examples

Required unless marked illustrative.

1. **Two mailers.** Customer mail is assigned the external queue and employee mail the internal queue. Both are sent with `deliver_later`. Performing later-delivery mail for the external queue delivers only the customer email.
2. **Parameterized mail.** `BillingMailer.with(...).invoice.deliver_later` uses BillingMailer’s queue, not a separate parameterized queue. A filter for that queue delivers it; a filter for another mailer’s queue does not.
3. **Per-send override.** A notifications mailer usually uses `:mailers`. One send uses `deliver_later(queue: :urgent)`. Performing `:urgent` delivers that send and not the usual notifications mail; performing `:mailers` does the reverse.
4. **Symbol / string.** The mailer is set to `:mailers` (or the send passes `queue: :mailers`). Targeting `"mailers"` and targeting `:mailers` select the same enqueued email.
5. **Nil / default.** The mailer’s later-delivery queue is `nil`. The send lands on the Active Job default queue. Targeting that default delivers it; targeting `"mailers"` does not. Omitting `queue:` still means “all later-delivery mail,” not “the default queue.”
6. **Adapter normalization / prefix.** With a prefix configured, stored names look like `"prefix_mailers"`. A tester who still thinks in the mailer’s `:mailers` can perform that mail without also performing other queues. A filter that names a different logical queue still does not deliver it. *(This is the main gap vs current filters, which match only the stored string.)*
7. **Custom delivery job.** A mailer uses a job that owns `:job_owned` and still has a unused mailer setting. Performing `:job_owned` delivers the email; performing the unused mailer setting does not. An explicit `deliver_later(queue:)` on that mailer is selected under the override name, not `:job_owned`.
8. **Scheduled + queue together.** On the external queue, one email is due now and one is wait-until two hours. Performing external-queue mail due within an hour delivers only the first. Internal-queue mail due now is not delivered.
9. **Counterexample (unchanged).** With no queue filter, `deliver_enqueued_emails` still delivers every later-delivery email in scope, including other mailers, parameterized sends, and custom jobs.

**Open questions.** When a prefix is set, should “the mailers queue” mean the logical name, the stored name, or both? If both, which mismatch should remain a miss so testers still catch a wrong queue? I treated “logical name still selects the mail” as the desired product behavior; say if teams should instead be forced to use the stored name.

This is the current shared understanding, not a locked spec. The enqueue precedence and landing names are from this revision; the targeting outcome in example 6 is the change to agree on.
