## Evolution of `Relation#ids`

### 1. Originally: `ids` was just `pluck(primary_key)`

Before December 2022, the implementation was effectively:

```ruby
def ids
  pluck primary_key
end
```

This became incorrect for eager-loaded collection associations because `pluck` applies the join dependency. A parent row is repeated once per joined child.

### 2. PR #46503 split `ids` from `pluck`

[PR #46503, “Fix: `ActiveRecord::Calculations#ids` returns duplicate ids”](https://github.com/rails/rails/pull/46503) was merged by [commit `4435b7a`](https://github.com/rails/rails/commit/4435b7afe3bf3f2d0f2f3b77aedd44d93219be18) on December 9, 2022.

Its explicit example was:

```ruby
Post.includes(:comments).where(id: 1).pluck(:id)
# => [1, 1, 1, 1, 1]

Post.includes(:comments).where(id: 1).ids
# => [1]
```

The PR explained that the duplication was caused by the join dependency applied by `pluck`. It therefore stopped delegating `ids` to `pluck` and implemented an independent PK-only query. The merged source changed from `pluck primary_key` to roughly:

```ruby
def ids
  if loaded?
    result = records.pluck(primary_key)
    return @async ? Promise::Complete.new(result) : result
  end

  columns = arel_columns([primary_key])
  relation = spawn
  relation.select_values = columns
  # execute and type-cast...
end
```

See the [merged source diff](https://github.com/rails/rails/blob/4435b7afe3bf3f2d0f2f3b77aedd44d93219be18/activerecord/lib/active_record/relation/calculations.rb#L320-L348) and the tests for [eager-load, preload, and includes](https://github.com/rails/rails/blob/4435b7afe3bf3f2d0f2f3b77aedd44d93219be18/activerecord/test/cases/calculations_test.rb#L975-L1008):

```ruby
def test_ids_with_eager_load
  company = Company.first
  5.times { company.contracts.create! }
  assert_equal Company.all.map(&:id).sort,
    Company.all.eager_load(:contracts).ids.sort
end

def test_ids_with_preload
  # ...
end

def test_ids_with_includes
  # ...
end
```

Thus the original special behavior was semantic: **`ids` means unique base-model identifiers, whereas `pluck(:id)` preserves rows produced by the join.**

### 3. PR #46697 restored join dependency handling using `DISTINCT`

The independent query introduced a regression for conditions referencing included tables. Follow-up [PR #46697](https://github.com/rails/rails/pull/46697), merged as [`ef02c3a`](https://github.com/rails/rails/commit/ef02c3a220b46e6f0794b47e5848a4fe7fc8cca2), added:

```ruby
if has_include?(primary_key)
  relation = apply_join_dependency.distinct
  return relation.ids
end
```

[Source](https://github.com/rails/rails/blob/ef02c3a220b46e6f0794b47e5848a4fe7fc8cca2/activerecord/lib/active_record/relation/calculations.rb#L327-L335)

It also added tests proving that the join is needed, including a predicate on the included table:

```ruby
def test_ids_with_includes_and_table_scope
  company = Company.first
  company.contracts.create!
  assert_equal [company.id],
    Company.includes(:contracts)
      .where("contracts.id" => company.contracts.first).ids
end
```

[Tests](https://github.com/rails/rails/blob/ef02c3a220b46e6f0794b47e5848a4fe7fc8cca2/activerecord/test/cases/calculations_test.rb#L1006-L1034)

So `apply_join_dependency` was required both to resolve included-table predicates and to deduplicate the resulting parent IDs.

### 4. PR #48101 changed `DISTINCT` to `GROUP BY primary_key`

`DISTINCT` then failed when the relation ordered by a non-PK column. PostgreSQL reported:

> `for SELECT DISTINCT, ORDER BY expressions must appear in select list`

That was [issue #48080](https://github.com/rails/rails/issues/48080). The fix was [PR #48101](https://github.com/rails/rails/pull/48101), merged as [`e856d7f`](https://github.com/rails/rails/commit/e856d7f1a24741c5295c9e562ffaf7ee0fce6680) on May 1, 2023.

The PR states why grouping was selected:

- it deduplicates like `DISTINCT`;
- it avoids PostgreSQL/MySQL’s requirement that `ORDER BY` columns appear in the `SELECT DISTINCT` list;
- adding ordering columns to the selection was inappropriate because `ids` should select only PK columns;
- a subquery was considered unnecessarily complicated.

The source changed to:

```ruby
primary_key_array = Array(primary_key)

if has_include?(primary_key)
  relation = apply_join_dependency.group(*primary_key_array)
  return relation.ids
end
```

[Source](https://github.com/rails/rails/blob/e856d7f1a24741c5295c9e562ffaf7ee0fce6680/activerecord/lib/active_record/relation/calculations.rb#L325-L344)

The regression test was:

```ruby
def test_ids_with_includes_and_non_primary_key_order
  rating = 1
  Company.all.each { |company| company.update!(rating: rating += 1) }

  assert_equal Company.all.sort_by(&:rating).map(&:id),
    Company.includes(:comments).order(:rating).ids
end
```

[Test](https://github.com/rails/rails/blob/e856d7f1a24741c5295c9e562ffaf7ee0fce6680/activerecord/test/cases/calculations_test.rb#L1049-L1054)

This is the historical reason for **grouping by PK rather than merely using `DISTINCT` or plain `pluck`**.

### 5. Composite-PK support made the grouping multi-column

[Commit `1217127`](https://github.com/rails/rails/commit/121712770326b9bca86022992d72811dadb1e133) changed the implementation to normalize the PK to an array and splat it:

```ruby
records.pluck(*Array(primary_key))
columns = arel_columns(Array(primary_key))
```

Its tests require CPK IDs to retain tuple shape:

```ruby
assert_equal [[book.author_id, book.number]],
  Cpk::Book.all.where(title: book.title).ids
```

[CPK source and tests](https://github.com/rails/rails/blob/121712770326b9bca86022992d72811dadb1e133/activerecord/test/cases/calculations_test.rb#L941-L959)

PR #48101 consequently grouped over all PK components.

### 6. In 2026 Rails delegated back to `pluck`—but retained the grouping exception

[PR #58259](https://github.com/rails/rails/pull/58259), commit [`56c95ae`](https://github.com/rails/rails/commit/56c95aee03ec642b37abd1c7e42964ae89bc6670), removed the duplicated `ids` query implementation because it had drifted from `pluck`. The PR cites CPK, `none`, contradictory scopes, and async behavior as examples of fixes that otherwise needed duplication.

But it explicitly says:

> “The only piece that genuinely needs custom handling is the deduplication when `has_include?(primary_key)` is true (the original #46503 fix).”

The resulting implementation is:

```ruby
def ids
  if !loaded? && has_include?(primary_key)
    return apply_join_dependency.group(*primary_key).pluck(*primary_key)
  end

  pluck(*primary_key)
end
```

[Current source](https://github.com/rails/rails/blob/main/activerecord/lib/active_record/relation/calculations.rb#L372-L382)

Current tests continue to distinguish the relevant relation shapes:

- loaded relations use no query: [lines 1136–1150](https://github.com/rails/rails/blob/main/activerecord/test/cases/calculations_test.rb#L1136-L1150)
- eager-load/preload/includes deduplicate IDs: [lines 1182–1198](https://github.com/rails/rails/blob/main/activerecord/test/cases/calculations_test.rb#L1182-L1198)
- non-PK ordering remains supported: [lines 1200–1204](https://github.com/rails/rails/blob/main/activerecord/test/cases/calculations_test.rb#L1200-L1204)
- included-table predicates remain supported: [lines 1206–1225](https://github.com/rails/rails/blob/main/activerecord/test/cases/calculations_test.rb#L1206-L1225)

## Conclusion

The claim that `Relation#ids` can **always** become `pluck(*primary_key)` is contradicted by Rails’ history and current implementation:

1. Plain `pluck` on an eager-loaded to-many join returns duplicate parent IDs.
2. `ids` promises base-model IDs, so it deduplicates them.
3. `DISTINCT` was tried but broke `includes(...).order(non_pk)` on PostgreSQL/MySQL.
4. `GROUP BY` all PK columns preserved uniqueness and ordering compatibility.
5. Rails later restored delegation to `pluck` for every ordinary/loaded relation shape, but deliberately retained:

```ruby
apply_join_dependency.group(*primary_key).pluck(*primary_key)
```

for unloaded relations whose PK pluck activates includes/eager loading.
