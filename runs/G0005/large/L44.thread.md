## Current behavior

[`RunnerCommand#perform`](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/runner/runner_command.rb#L22-L65) receives the code/file separately from trailing arguments, boots the application, and then replaces global `ARGV` with only those trailing arguments:

```ruby
def perform(code_or_file = nil, *command_argv)
  unless code_or_file
    help
    exit 1
  end

  boot_application!
  Rails.application.load_runner

  ARGV.replace(command_argv)

  # evaluate stdin, load a file, or eval code...
end
```

There is **no local `ensure`** in `RunnerCommand#perform`. This deliberately removes the code/file itself from the `ARGV` visible to the executed script. That behavior originated in commits [`5aea095`](https://github.com/rails/rails/commit/5aea0952e7cb445e614652e3cd9aba71a836eed0) and [`a06a643`](https://github.com/rails/rails/commit/a06a643e0572b8c983738c068ae637d020188c97), the latter fixing #28515.

## Restoration is handled by `Rails::Command.invoke`

[`Rails::Command.invoke`](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L55-L69) wraps command dispatch in `with_argv(args)`:

```ruby
with_argv(args) do
  if command && command.all_commands[command_name]
    command.perform(command_name, args, config)
  else
    invoke_rake(full_namespace, args, config)
  end
end
```

[`with_argv`](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L140-L146) already provides exception-safe restoration:

```ruby
def with_argv(argv)
  original_argv = ARGV.dup
  ARGV.replace(argv)
  yield
ensure
  ARGV.replace(original_argv)
end
```

Therefore, when runner is entered through the supported `Rails::Command.invoke` path, its internal `ARGV.replace(command_argv)` is contained by the outer `ensure`. Adding this inside `perform`:

```ruby
old_argv = ARGV.dup
ARGV.replace(command_argv)
ensure
  ARGV.replace(old_argv)
```

would be redundant for normal command invocation. It would only alter behavior for callers directly invoking `RunnerCommand#perform`, bypassing `Rails::Command.invoke`.

## Current runner tests

[`railties/test/commands/runner_test.rb`](https://github.com/rails/rails/blob/main/railties/test/commands/runner_test.rb#L6-L77) currently tests:

- stdin execution
- script-file execution
- missing files
- inline Ruby
- executor and `--skip-executor`
- syntax/name errors

All tests invoke runner through the CLI helper:

```ruby
def run_runner_command(*arguments, allow_failure: false)
  rails "runner", *arguments, allow_failure: allow_failure
end
```

There is currently **no runner-specific test for restoring `ARGV` after execution**, nor a direct `RunnerCommand#perform` embedding test.

The general command test verifies that invoke populates `ARGV` from its arguments in [`base_test.rb`](https://github.com/rails/rails/blob/main/railties/test/command/base_test.rb#L116-L124), though it does not explicitly assert post-invocation restoration.

## Relevant Rails discussion and history

The directly relevant work is broader command isolation rather than a runner-specific leak report:

- [PR #38495, “Isolate ARGV in Rails::Command.invoke”](https://github.com/rails/rails/pull/38495) explicitly states that mutations performed by a command must not affect code executing after `Rails::Command.invoke`. This introduced the outer save/replace/ensure/restore pattern.
- [PR #41611, “Populate ARGV with Rails::Command.invoke args”](https://github.com/rails/rails/pull/41611) changed invoke so commands see their passed arguments while preserving isolation between invocations. Its description explicitly says: “`ARGV` will still be isolated between invocations.”
- [Issue #40945](https://github.com/rails/rails/issues/40945) motivated #41611 because application templates and initializers expected command arguments in `ARGV`.
- [PR #38463](https://github.com/rails/rails/pull/38463) contains the earlier design discussion about commands accidentally relying on prior `ARGV` contents and finding a standard way to isolate them.

I found **no Rails PR or issue specifically reporting that embedded runner execution leaks arguments and proposing restoration inside `RunnerCommand#perform`**. The established Rails design places that responsibility at the `Rails::Command.invoke` boundary.

**Conclusion:** the proposed local restoration is unnecessary if embedding uses `Rails::Command.invoke("runner", ...)`. It is only justified if Rails intends direct `RunnerCommand#perform` calls to be an independently isolated API—which the existing implementation, tests, and PR discussion do not establish.

### Claim vs implementation

That replace is the feature, not the bug. It strips the code/file so the script sees only its own arguments. [`railties/lib/rails/commands.rb`](file:///home/user/workspace/repo/railties/lib/rails/commands.rb) always goes through `invoke`. ### Compatibility and a more precise change

Landing the proposed ensure as written:

- Restores whatever `ARGV` was **at `perform` entry**. Under `invoke` that is already the runner argv (`code_or_file` + extras), not the process argv. Outer `with_argv` still does the real restore. Harmless duplication on the supported path.
- Changes direct-`perform` callers: `ARGV` after return / `SystemExit` goes back. That is the only path this PR would fix.
- Does not restore `$0` / `$PROGRAM_NAME`, which file execution mutates the same way and which embedding would also leak.
- Does not change dashed-arg forwarding, stdin `-`, or executor wrapping, as long as `ARGV.replace(command_argv)` still happens **before** `eval`/`load`.
- Leaves a window where a script `at_exit` handler on the CLI path still sees post-`invoke` argv (the shifted command args from `commands.rb`), same as today.

If the goal is “embedding must not leak,” the precise fix is not another save/restore in `RunnerCommand`:

1. Document/embed via `Rails::Command.invoke("runner", args)` — already isolated.
2. If direct `perform` is a supported API (it is `:nodoc:` today), restore **both** `ARGV` and `$0` in `ensure`, and add an in-process test that calls `perform` (not forked `bin/rails`) and asserts both values after success, `SystemExit` from missing file, and `SystemExit` from `SyntaxError`.
3. Do not add a runner-only restore that `generate` / `console` do not share; isolation belongs on `invoke`, where it already lives.

**Verdict: request changes.** Reject the claim as a CLI/`invoke` leak; do not merge the ensure without an in-process test that currently fails, and without deciding whether `$0` is part of the same contract.
