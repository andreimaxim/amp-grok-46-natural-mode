**Problem frame:** An application author bulk-inserts rows with `insert_all` / `insert_all!` and expects `unique_by:` and `returning:` to mean the same thing on PostgreSQL, SQLite, MySQL, and MariaDB. Today those options are adapter-gated, the skip and bang forms do not treat duplicates the same way, and composite keys plus named indexes make the “default conflict target” easy to guess wrong. The work is a behavior change toward a contract people can observe without assuming every database agrees.

Evidence for current behavior: public docs on `ActiveRecord::Relation#insert_all` / `#insert_all!`, adapter support predicates, and the bulk-insert test suite. This is not a proposal to invent new SQL.

**Shared rules (all adapters that run these methods):** Neither form instantiates models or runs validations/callbacks. Values still go through Active Record type casting and serialization. Every hash in a batch must have the same keys. Empty input inserts nothing and returns an empty result. `insert_all` skips duplicate rows and keeps the rest. `insert_all!` raises `ActiveRecord::RecordNotUnique` and inserts no rows.

---

**Capability map (this revision, where supported)**

- Skip duplicates: PostgreSQL, SQLite, MySQL, MariaDB
- `unique_by:` (choose which unique index is the skip/conflict target): PostgreSQL, SQLite only
- `returning:` (values for successfully inserted rows): PostgreSQL, SQLite, MariaDB ≥ 10.5; not MySQL
- Expression unique indexes as a `unique_by` target: PostgreSQL and SQLite only

On an adapter that does not support an option, asking for it fails with `ArgumentError` naming the adapter and the option. Omitting it is not the same as asking for it.

---

**Behavioral outcomes**

1. An author can skip or reject duplicates without assuming one conflict rule for every database.
2. An author can request returned columns only where that is supported, and can turn returning off.
3. Shared input/result rules (empty batch, mismatched keys, casting, timestamps) do not depend on which adapter skipped or returned rows.
4. Unsupported `unique_by:` / `returning:` fail clearly; they do not silently mean something else.

---

**Acceptance examples**

Required unless marked illustrative. “Books” have a primary key `id`, a unique index on `[author_id, name]`, a partial unique index on `isbn` (only when `published_on` is present), and on PostgreSQL/SQLite a unique expression index on `lower(external_id)`. “Carts” use a composite primary key `[shop_id, id]`.

### Default conflict target (no `unique_by:`)

**Skip an existing primary key.** A book with `id: 1` already exists.
When the author calls `Book.insert_all [{ id: 1, name: "Agile Web Development with Rails" }]` on an adapter that can skip duplicates,
the row count does not change and the existing book is not updated.

**Bang is atomic.** The same batch is passed to `insert_all!`, including a row that collides with an existing unique value.
The author observes `ActiveRecord::RecordNotUnique`, and no row from that call is inserted.

**Same-batch duplicates without ids.** Two hashes share `author_id` and `name` and omit `id`.
When the author calls `insert_all`, exactly one book is inserted (the other is skipped as a duplicate of that unique pair). Autonumbered ids are not required for the skip to work.

**Same-batch duplicate ids.** Two hashes share `id: 111` with different names.
After `insert_all`, one row exists with that id. Observed in this revision: the stored name is the first hash’s name (`"expected_new_name"`), not the second. Whether “first wins” is the intended portable rule is an open question.

**Skip does not upsert.** A book exists with `format: "EXPECTED"` and a given `author_id`/`name`.
`insert_all` of the same pair with `format: "UNEXPECTED"` does not change the count or the existing `format`.

### Named, composite, and expression `unique_by:` (PostgreSQL, SQLite)

**Named column.** `insert_all` with `unique_by: :isbn` inserts a new book when that isbn is not taken.

**Index name.** `unique_by: :index_books_on_isbn` behaves the same as `unique_by: :isbn` for that index.

**Composite columns, order-insensitive.** `unique_by: %i[author_id name]` and the reversed column list both insert when that pair is new.

**Narrowed skip vs other uniques.** A book with `id: 1` already exists.
`insert_all [{ id: 1, name: "Agile Web Development with Rails" }], unique_by: :index_books_on_author_id_and_name` raises `RecordNotUnique` — the skip applies only to the named index, not to the primary key.

**Expression index.** A book exists with `external_id: "abc"`.
`insert_all [{ external_id: "ABC" }], unique_by: :index_books_on_lower_external_id` does not increase the count.

**Partial unique index (illustrative boundary).** The isbn uniqueness only applies when `published_on` is present.
`insert_all!` with `unique_by: :isbn` and a colliding isbn plus `published_on` set raises `RecordNotUnique`.

**Bang still accepts `unique_by:` on these adapters** and still raises on a colliding isbn. It is not established that bang uniqueness is limited to that index; the database still enforces every unique index. See open questions.

### Invalid or non-unique `unique_by:`

**Missing / non-unique target (PostgreSQL, SQLite).** `unique_by: :cats`, `unique_by: %i[author_id isbn]`, or `unique_by: :author_id` raises `ArgumentError` matching `No unique index`.

**Unsupported adapter (MySQL, MariaDB).** Any `unique_by:` on `insert_all` / `insert_all!` raises `ArgumentError` that the adapter does not support `:unique_by`. There is no silent ignore.

### Composite primary keys

**PostgreSQL, SQLite — skip needs an explicit target.** `Cart.insert_all [{ id: 2, shop_id: 1, title: "My cart" }]` without `unique_by:` raises `ArgumentError` matching `No unique index found for id` (the model’s `primary_key` is `id`, not `[shop_id, id]`).

**PostgreSQL, SQLite — explicit composite target.** `Cart.insert_all [{ id: 1, shop_id: 1, title: "My cart" }], unique_by: [:shop_id, :id]` inserts.

**PostgreSQL, SQLite — bang does not require `unique_by:`.** `Cart.insert_all! [{ id: 2, shop_id: 1, title: "My cart" }]` inserts.

**MySQL, MariaDB — skip without `unique_by:`.** The same `Cart.insert_all` without `unique_by:` inserts (these adapters cannot name a conflict target).

### `returning:`

**Default (PostgreSQL, SQLite, MariaDB ≥ 10.5).** `insert_all!` of one book returns an `ActiveRecord::Result` whose columns are the primary key (`id` for books).

**Default (MySQL, and MariaDB &lt; 10.5).** The same call still returns an `ActiveRecord::Result`, but not primary-key columns via `returning`. Asking for `returning: [:id]` raises `ArgumentError` that the adapter does not support `:returning`.

**Off.** On a supporting adapter, `returning: false` and `returning: []` both yield a result with no columns. The insert still happens.

**Selected columns.** `returning: [:id, :name]` includes the inserted name (`"Rework"`).

**SQL expression.** `returning: Arel.sql("UPPER(name) as name")` yields `"REWORK"`. A raw string (not wrapped as SQL) is rejected as dangerous.

**Alias.** `insert_all` with `{ title: "Remote", ... }` and `returning: :title` includes a `title` column on supporting adapters.

**Skipped rows (open).** Tests do not establish whether `insert_all`’s result includes skipped duplicates. Do not treat that as specified.

### Empty input, mismatched keys, casting, timestamps

**Empty batch.** `insert_all([])` and `insert_all!([])` return an empty result and insert nothing, on every adapter that can run these methods.

**Extra key.** `[{ name:, author_id: }, { name:, author_id:, isbn: }]` raises `ArgumentError` that all objects must have the same keys, mentioning `extra: ["isbn"]`.

**Missing key.** The reverse batch mentions `missing: ["isbn"]`.

**Unknown attribute.** `{ unknown_attribute: "Test" }` raises `ActiveRecord::UnknownAttributeError`.

**Enums.** Inserting `status: :published` / `:proposed` stores `"published"` / `"proposed"` as with ordinary creates.

**Serialization.** A string (or hash) written through `insert_all!` to a serialized column matches the value written through `create!` for the same coder, including JSON and a non-idempotent custom coder (no double encoding of strings).

**Type casting vs create.** On a returning-capable adapter, inserting a non-string `name` and creating one yield the same stored `name`.

**Timestamp override.** Public contract: omitted timestamp columns follow the model’s `record_timestamps`, unless `record_timestamps: true/false` is passed; an explicit timestamp in the hash is kept. Bulk-insert tests exercise the override mainly on `upsert_all`, not `insert_all`. Treat insert-specific timestamp override as documented but thinly evidenced (open question).

### Atomicity: skip vs bang

**Skip.** A batch with some new rows and some duplicates inserts only the new rows. Already-stored rows are unchanged.

**Bang.** If any row violates a unique index, the author sees `RecordNotUnique` and none of that batch is inserted.

That atomicity difference is part of the product, not an accident of one adapter.

---

**Non-goals**

- Unifying every adapter so `unique_by:` or `returning:` work everywhere
- Changing `upsert_all`, callbacks, or validations
- Prescribing SQL, conflict-clause shape, adapter internals, or a rollout
- Redefining “duplicate” to something other than the database’s unique indexes
- Numeric performance targets

**Unchanged:** bulk insert still does not run model callbacks or validations; casting/serialization still apply.

---

**Steering evidence**

Investigate or stop if:

- `insert_all` on a colliding primary key updates columns (secret upsert) on any supported adapter
- `insert_all!` leaves some rows inserted after `RecordNotUnique`
- MySQL/MariaDB accept `unique_by:` and skip only that index (they cannot today)
- MySQL returns requested `returning:` columns
- PostgreSQL/SQLite `insert_all` on `Cart` without `unique_by:` starts succeeding without a documented contract change
- Authors still cannot tell, from the error or result, whether `unique_by:` / `returning:` applied

Reconsider the framing if the real pain is “make MySQL behave like PostgreSQL” rather than “make the adapter-honest contract obvious.” Those are different products.

---

**Open questions**

- Should `unique_by:` on `insert_all!` do anything besides being accepted on PostgreSQL/SQLite? Docs say it limits which unique index is checked; bang still cannot ignore other unique indexes.
- Is “first hash wins” for duplicate ids in one `insert_all` batch the portable rule?
- What should `returning:` contain when `insert_all` skips some rows?
- Should composite-key models without `unique_by:` fail on PostgreSQL/SQLite forever, or should the default target be the full composite key?
- Should `insert_all`’s `record_timestamps:` override be specified to match `upsert_all`’s observed create-time behavior?
- Is MariaDB “returning yes, unique_by no” the long-term split, or only today’s capability line?
