The claim is **incorrect** at this revision. The one-line change is not a safe skip of “unnecessary” rewrites; it **disables the signed-cookie key/digest upgrade** that rotation is supposed to perform.

I restored the original line after probing. Existing tests already fail under the patch.

### Verdict

**Do not land.** `force_reserialize: rotated` is the only write trigger for a payload that is already in the current serializer format but was verified with a **fallback** secret or digest. Hardcoding `false` leaves those cookies signed with the retired key until something else overwrites them.

Current-key reads already do **not** rewrite. `on_rotation` fires only after a fallback verifier succeeds.

---

### High: rotation upgrade is dropped

**Claim:** skipping `force_reserialize` after rotation is safe.

**Fact:** signed jars verify with `NullSerializer`. The inner dump is loaded later. Key/digest rotation does not change that dump, so `reserialize?` stays false. Without `force_reserialize: rotated`, the jar never calls `[]=`, so no `Set-Cookie` with the current verifier.

Read path:

1. `SignedKeyRotatingCookieJar#[]` → `parse` with `purpose: "cookie.#{name}"`, then without purpose if that returns nil.
2. `@verifier.verified(..., on_rotation:)` — current secret/digest first; fallbacks from `cookies_rotations.signed`.
3. `SerializedCookieJars#parse` loads the inner payload, then:
   `self[name] = { value: value } if force_reserialize || reserialize?(dumped)`
4. That `[]=` goes through `commit` → `@verifier.generate` (current key/digest + metadata) → parent `CookieJar#[]=`, which queues `Set-Cookie` when the signed string changed.

Evidence:

- [actionpack/lib/action_dispatch/middleware/cookies.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L594-L647) — `reserialize?` is serializer-only; signed `parse` passes `force_reserialize: rotated`.
- [activesupport/lib/active_support/messages/rotator.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/messages/rotator.rb#L29-L47) — `on_rotation` runs only after a **fallback** `read_message` succeeds.
