This is a **behavior change**: required configuration reads already exist; the work is to make their failures understandable without changing successful results. Current behavior below is from source, the OrderedOptions test file (34 runs, 104 assertions, 0 failures), and direct probes for cases the tests do not assert.

**Problem frame:** A Rails app or plugin author is reading a configuration value they consider required—typically through a bang read on `ActiveSupport::OrderedOptions` or `ActiveSupport::InheritableOptions` (application config, plugin config, credentials). Today a failed required read always surfaces the same `KeyError` (`":name is blank"`), whether the name was never set, set to `nil`, set to `false`, or set to whitespace. The error does not identify the configuration object, does not carry a usable key, and does not say whether a child overrode a present parent with a blank value. Optional reads still return `nil` for a missing name, so absence is easy to miss until a bang read fails with an unhelpful message.

**Hypothesis:** the pain is diagnostic sameness on the required-read path, not the successful return values themselves.

# Desired outcomes

These are externally observable claims. They do not name new APIs or storage.

1. **Successful required reads stay the same.** If a required read succeeds today, it still returns the same value, including inherited present values and child present overrides. `false` remains stored and returned by optional reads; it still fails a required read because it is blank.

2. **A failed required read is diagnosable.** The author can tell which name was required, that this was a required read (not an optional `nil`), and which of these happened: never set; set but blank (`nil`, `false`, whitespace-only string, empty collection); or a child override that made a present parent value blank. **Hypothesis:** distinguishing those cases in the failure is the point of “easier to understand”; confirm if a richer message around a single “blank” failure is enough.

3. **Inherited vs overridden failures are distinguishable.** When a child required read fails, the author can tell whether the blankness came from the parent or from a child override. A present parent must not be reported as missing just because the child never wrote it.

4. **Optional reads, `respond_to?`, `dig`, symbol/string lookup, and Hash-like ordering stay as they are today.** Missing optional reads still return `nil`. `respond_to?` still returns true for arbitrary names. `dig` still returns `nil` on a missing path. Enumeration still yields symbol keys in insertion order (parent order, then child-only names, for inheritable options).

5. **Compatibility of success paths.** Callers that already rescue `KeyError` from a bang read still see a `KeyError`. Callers that compare successful return values, iterate keys, or round-trip `to_h` see no change.

# Non-goals

- Changing what counts as a successful required read (`0`, `true`, non-whitespace strings, and other present values).
- Changing optional-read `nil` for a missing name into an error.
- Making `respond_to?` report only written names.
- Making `key?` / `fetch` / `include?` treat strings like `[]` does.
- Auto-symbolizing string keys on an inheritable parent Hash.
- Changing Encrypted Configuration’s separate `require` / `option` reads, except that credentials bang reads that already go through OrderedOptions should benefit.
- New configuration surfaces, new required-read spellings, or any prescribed classes, methods, or storage.
- Numeric targets (error rates, boot time).

# Compatibility boundaries

Must remain true after the change:

- Present bang reads return the same object as the matching non-bang read.
- Symbol and string writes remain one symbol-keyed entry; lookup through `[]`, strings, and dynamic readers still agree.
- Insertion order of symbol keys is unchanged, including inheritable parent-then-child-only order and in-place updates.
- Child overrides still hide only that name; the parent object is unchanged.
- Optional missing reads still return `nil`; `false` is still stored and returned by optional reads.
- Failed required reads still raise `KeyError` (so existing rescues keep working).
- `respond_to?` remains true for arbitrary reader, writer, and bang names.
- `dig` still string-coerces only the first argument and still returns `nil` for missing paths.

# Example journeys

Required cases unless marked illustrative.

**1. Required secret is present (core success).**  
An author sets `some_api_key` to `"SOMEKEY"` and performs a required read. They receive `"SOMEKEY"`, the same value as the optional read. (Matches [security guide](file:///home/user/workspace/repo/guides/source/security.md#L1745-L1750) and [test_raises_with_bang](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L118-L119).)

**2. Required name was never set (core failure).**  
An author bang-reads `non_existing_key` on an empty options object. They get a `KeyError` from which they can tell the name was never set, not that it was set to a blank value. Today they only see `":non_existing_key is blank"`.

**3. Required name is `nil` or `false`.**  
An author sets `foo = nil` or `foo = false` and bang-reads `foo`. They get a `KeyError` from which they can tell the name was set and the value is blank, and can tell `nil` apart from `false` if that difference changes what they do next. Optional `foo` still returns `nil` or `false`. Today both bang failures say `":foo is blank"`.

**4. Required name is whitespace-only.**  
An author sets `token = "   "` (or `"\t\n\r"` / `"\u00a0"`) and bang-reads `token`. The required read fails as blank. `token = " blah "` still succeeds and returns `" blah "`.

**5. Inherited present value.**  
A parent has `foo = :bar`. A child that has not written `foo` bang-reads `foo` and receives `:bar`. The parent still has `:bar`.

**6. Inherited blank value.**  
A parent has `foo = nil` (or `false` / `"  "`). A child that has not written `foo` bang-reads `foo` and fails in a way that shows the blankness is inherited, not a missing child entry.

**7. Child override to a present value.**  
Parent `foo = nil`, child `foo = "now-present"`. Child bang-read returns `"now-present"`. Parent is still `nil`.

**8. Child override to blank (counterexample to “parent is present, so child required read succeeds”).**  
Parent `foo = "from-parent"`, child `foo = nil`. Child bang-read fails in a way that shows a child override made it blank. Parent is still `"from-parent"`. Today: `":foo is blank"` with no override hint.

**9. Optional missing read is unchanged (counterexample).**  
An author reads `missing` without requiring it. They still get `nil`. `respond_to?(:missing)` is still true. This work does not turn that into an error.

**10. Ordering is unchanged (illustrative compatibility).**  
Writes `a`, then `b`, then `c` (via dynamic writer, symbol, and string). Enumeration is still `[:a, :b, :c]` even after `a` is updated.

# Acceptance evidence

**We would accept the outcome if:** an author who hits a failed required read can say, without reading library source, which name failed, whether it was unset vs blank, and—on inheritable options—whether a child override caused the blankness; and every previously successful bang/optional/dig/enumeration example above still returns the same values in the same order.

**We would investigate implementation, not the framing, if:** success paths still match and failures still raise `KeyError`, but the new failure text is ambiguous for inherited vs overridden blanks.

**We would reconsider the framing if:** authors already diagnose these failures quickly from the current `":name is blank"` message; or they need missing optional reads to start failing (that is a different problem); or they need `false` to become a valid required value (that would break today’s blank semantics).

**We would stop if:** making failures more specific would change successful return values, reorder keys, or stop raising `KeyError` for cases callers already rescue.

# Open questions

1. On failure, must “never set” and “set but blank” be different, or is it enough that the failure still says “blank” as long as it also names the object and whether a child overrode the parent?
2. For credentials and other secrets, may a failure mention that a value was whitespace or `false`, or must it avoid any characterization that could leak a stored value?
3. Empty arrays/hashes fail today’s bang reads because they are blank. Are they in scope for clearer diagnosis, or only the configuration scalars (`nil`, `false`, strings) authors actually use as required settings?

Correct any of these if they miss the intent: the actor is the app/plugin author doing a required config read; the pain is indistinguishable blank failures, especially across parent/child options; success paths and ordering stay frozen; the work is better diagnosis of existing required reads, not a new required-read spelling.
