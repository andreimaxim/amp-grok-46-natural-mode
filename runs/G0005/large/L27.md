The claim is **incorrect** at this revision. The one-line change is not a safe skip of “unnecessary” rewrites; it **disables the signed-cookie key/digest upgrade** that rotation is supposed to perform.

I restored the original line after probing. Existing tests already fail under the patch.

## Verdict

**Do not land.** `force_reserialize: rotated` is the only write trigger for a payload that is already in the current serializer format but was verified with a **fallback** secret or digest. Hardcoding `false` leaves those cookies signed with the retired key until something else overwrites them.

Current-key reads already do **not** rewrite. `on_rotation` fires only after a fallback verifier succeeds.

## High: rotation upgrade is dropped

**Claim:** skipping `force_reserialize` after rotation is safe.

**Fact:** signed jars verify with `NullSerializer`. The inner dump is loaded later. Key/digest rotation does not change that dump, so `reserialize?` stays false. Without `force_reserialize: rotated`, the jar never calls `[]=`, so no `Set-Cookie` with the current verifier.

Read path:

1. `SignedKeyRotatingCookieJar#[]` → `parse` with `purpose: "cookie.#{name}"`, then without purpose if that returns nil.
2. `@verifier.verified(..., on_rotation:)` — current secret/digest first; fallbacks from `cookies_rotations.signed`.
3. `SerializedCookieJars#parse` loads the inner payload, then:
   `self[name] = { value: value } if force_reserialize || reserialize?(dumped)`
4. That `[]=` goes through `commit` → `@verifier.generate` (current key/digest + metadata) → parent `CookieJar#[]=`, which queues `Set-Cookie` when the signed string changed.

Evidence:

- [actionpack/lib/action_dispatch/middleware/cookies.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L594-L647) — `reserialize?` is serializer-only; signed `parse` passes `force_reserialize: rotated`.
- [activesupport/lib/active_support/messages/rotator.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/messages/rotator.rb#L29-L47) — `on_rotation` runs only after a **fallback** `read_message` succeeds.
- Existing tests already encode the upgrade contract:
  - `test_signed_cookie_rotating_secret_and_digest` ([cookies_test.rb:641](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L641-L656))
  - `test_rotating_signed_cookies_digest` ([cookies_test.rb:1000](file:///home/user/workspace/repo/actionpack/test/dispatch/cookies_test.rb#L1000-L1014))

  Both read an old cookie, then `verifier.verify(@response.cookies["user_id"])` with the **new** secret/digest.

Observed at this revision:

| Case | Current code | Proposed `force_reserialize: false` |
|---|---|---|
| Current SHA1/SHA256 signature | value `45`, no pending write | same |
| SHA256 configured, SHA1 rotation present, cookie already SHA256 | value `45`, no write | same |
| Old secret + SHA1 | value `45`, `Set-Cookie` with SHA256/current key | value `45`, **no write** |
| Same secret, old SHA1 digest | value `45`, rewrite to SHA256 | value `45`, **no write** |
| `:json` + old secret (payload already JSON) | rewrite | **no write** |
| `:hybrid` Marshal → JSON (`reserialize?`) | rewrite | still rewrite |
| Expired metadata | `nil`, no write | same |
| Tampered / purpose mismatch | `nil`, no write | same |

With the patch applied, those two rotation tests error:

```
CookiesTest#test_rotating_signed_cookies_digest
CookiesTest#test_signed_cookie_rotating_secret_and_digest
ActiveSupport::MessageVerifier::InvalidSignature: invalid message string
```

because `@response.cookies["user_id"]` is missing. The inner value is still readable in-process; the cookie on the wire is not upgraded.

That is not an optimization. After the old rotation is removed, those clients lose the cookie.

## Medium: encrypted jars still rewrite; signed would not

The same `on_rotation` → `force_reserialize: rotated` pattern is in `EncryptedKeyRotatingCookieJar#parse` ([cookies.rb:694-696](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L694-L696)). The proposed diff only touches signed cookies.

`test_encrypted_cookie_rotating_secret` and the legacy HMAC-CBC upgrade tests still expect a rewritten cookie. Shipping only the signed change would make signed and encrypted rotation diverge with no documented reason.

The patch also leaves `rotated` assigned and unused (`warning: assigned but unused variable - rotated`).

## Low: the “unnecessary rewrite” case already does not rewrite

Active Support already distinguishes current vs rotated vs dead messages:

- Current secret: `on_rotation` not called ([message_rotator_tests.rb](file:///home/user/workspace/repo/activesupport/test/messages/message_rotator_tests.rb#L59-L62), 14 rotator tests passed).
- Successful fallback: `on_rotation` called ([message_rotator_tests.rb:42-46](file:///home/user/workspace/repo/activesupport/test/messages/message_rotator_tests.rb#L42-L46)).
- Tampered / other secret: `verified` → `nil`, callback not called.
- Expiry is `:invalid_message_content` in [metadata.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/messages/metadata.rb#L80-L88). `verified` swallows it ([message_verifier.rb:225-233](file:///home/user/workspace/repo/activesupport/lib/active_support/message_verifier.rb#L225-L233)). Rotator does **not** treat that as a successful rotation, so `on_rotation` is not called. Probe: expired current and expired-old-secret both `value=nil`, no pending write.

Serializer upgrades are a **separate** trigger (`reserialize?`). Hybrid Marshal→JSON still rewrites with the patch; JSON-already-JSON + old **key** does not. That split is why `force_reserialize: rotated` exists.

## Tests this change would need (and does not have)

The suite already rejects the patch. Any revival of “don’t rewrite on rotation” would also need:

1. Keep `test_signed_cookie_rotating_secret_and_digest` / `test_rotating_signed_cookies_digest` passing — they require a response cookie verifiable with the **current** secret and digest. The proposed line makes that impossible without rewriting the tests to assert the opposite.
2. Same assertion for `:json` / `:hybrid` when the inner payload is **already** current format (the case `reserialize?` does not cover). Today only Marshal is exercised for signed secret rotation.
3. Negative cases that already hold and must remain true:
   - current signature + rotations configured → no `Set-Cookie` (`test_signed_cookie_using_hybrid_serializer_can_read_from_json_dumped_value` is the serializer analog; there is no current-key equivalent for signed rotation).
   - tampered → nil, no write (`test_tampered_with_signed_cookie`).
   - expired metadata → nil, no write (`test_signed_cookie_with_expires_set_relatively`).
4. If signed rewrite were ever made optional, encrypted rotation tests must be updated in lockstep, or the split documented.

I would not add tests that lock in “read old secret, do not `Set-Cookie`.” That would encode a broken rotation.

---

**Bottom line:** the rewrite after a successful signed rotation is the upgrade. The patch removes it, fails existing Action Pack tests, and does not change expiry, tamper, or current-signature behavior — those already skip the write.
