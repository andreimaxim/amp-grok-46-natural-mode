## Current Rails behavior

`credentials_defaults` resolves the two paths **independently**:

```ruby
content_path = config/credentials/<Rails.env>.yml.enc
content_path = config/credentials.yml.enc unless content_path.exist?

key_path = config/credentials/<Rails.env>.key
key_path = config/master.key unless key_path.exist?
```

See [`configuration.rb#L683-L690`](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L683-L690).

Therefore:

| Environment content exists? | Environment key exists? | `content_path` | `key_path` |
|---|---|---|---|
| Yes | Yes | `credentials/<env>.yml.enc` | `credentials/<env>.key` |
| Yes | No | `credentials/<env>.yml.enc` | **`master.key`** |
| No | Yes | `credentials.yml.enc` | `credentials/<env>.key` |
| No | No | `credentials.yml.enc` | `master.key` |

This independent selection can produce mismatched pairs. In particular, the proposed behavior—using `master.key` when an environment credentials file exists but its environment key does not—is already the explicit behavior on Rails `main`, and is documented in [`Rails::Application#credentials`](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L589-L607).

It only succeeds if that environment credentials file was actually encrypted with `master.key`. Rails does not inspect the ciphertext or try multiple keys.

## `RAILS_MASTER_KEY` and `require_master_key`

`Rails.application.credentials` constructs an `EncryptedConfiguration` using the selected paths. Its environment-key name defaults to `RAILS_MASTER_KEY`, while `raise_if_missing_key` is set from `config.require_master_key` ([`application.rb#L624-L630`](https://github.com/rails/rails/blob/main/railties/lib/rails/application.rb#L624-L630)).

The effective key lookup is:

1. nonblank `ENV["RAILS_MASTER_KEY"]`
2. selected `config.credentials.key_path`
3. missing-key handling

See [`encrypted_file.rb#L49-L60`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L49-L60) and [`#L119-L128`](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/encrypted_file.rb#L119-L128).

Consequences:

- `RAILS_MASTER_KEY` always wins, including for environment-specific credentials.
- It must contain the key that encrypted the **selected content file**—usually `<env>.key`, not necessarily `master.key`.
- `require_master_key = true` does not specifically require a file named `master.key`; it means Rails raises when neither `RAILS_MASTER_KEY` nor the selected key file supplies a key.
- With `require_master_key = false`, a missing key is tolerated until encrypted content is read; reading then raises `MissingContentError` rather than decrypting with another implicit source.
- A present but wrong key results in `ActiveSupport::MessageEncryptor::InvalidMessage`.

The command help confirms that `RAILS_MASTER_KEY` takes precedence over environment-specific and custom key files ([`credentials/USAGE#L58-L73`](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/credentials/USAGE#L58-L73)). There is also a direct test proving environment credentials work through `RAILS_MASTER_KEY` without the environment key file ([`credentials_test.rb#L31-L39`](https://github.com/rails/rails/blob/main/railties/test/application/credentials_test.rb#L31-L39)).

## Intended semantics and related GitHub discussion

The feature originated in [PR #33521, “Add support for multi environment credentials”](https://github.com/rails/rails/pull/33521):

- The intended content behavior was explicit: if `<env>.yml.enc` exists, use it instead of the global credentials file—**no merging**.
- Early discussion envisioned separate environment keys.
- The author also noted that using one `RAILS_MASTER_KEY` name was intentional because a process only needs the key appropriate to its active environment.
- The merged implementation ultimately chose paths independently, producing today’s `<env>.key → master.key` fallback.

Relevant follow-up issues:

- [Issue #38906](https://github.com/rails/rails/issues/38906) tested environment credentials with the environment key file removed and `RAILS_MASTER_KEY` supplied. Rails maintainers confirmed this should work; the reported failure was Spring retaining an old environment, not credential fallback.
- [Issue #46636](https://github.com/rails/rails/issues/46636) clarified that when using environment credentials, `RAILS_MASTER_KEY` normally needs the value from `config/credentials/<env>.key`, not `config/master.key`. That is operational guidance, not a prohibition against encrypting an environment file with `master.key`.
- [Issue #41830](https://github.com/rails/rails/issues/41830) discusses environment-file selection and notes the distinction between `master.key` as the ordinary global-file key and `RAILS_MASTER_KEY` as an override usable with every credentials file.

## PR-review conclusion

Falling back from a missing `config/credentials/<env>.key` to `config/master.key` is consistent with:

- the current implementation,
- current API documentation, and
- the general `RAILS_MASTER_KEY` override model.

It does **not** mean environment credentials conventionally share the global key. `credentials:edit --environment <env>` normally generates a separate `<env>.key`; the fallback chiefly supports an environment file deliberately encrypted with the global key or migrated into that layout. A test should cover both successful fallback with a matching `master.key` and `InvalidMessage` when the selected fallback key does not match the ciphertext.

## Finding

Rails originally intended `content_path` and `key_path` to be **paired**. The later independent fallback behavior is real and documented, but I found no maintainer discussion explicitly declaring the mismatched pair desirable or dismissing it as a footgun.

### PR #33521 originally paired the paths

In [PR #33521](https://github.com/rails/rails/pull/33521), DHH specified:

> If `config/credentials/$environment.yml.enc` is available, the key used to decrypt will be either `config/credentials/$environment.key` or `ENV["RAILS_..._KEY"]`.

He also emphasized that environment and global credentials are “separate files and separate stores.”

The merged implementation selected **both defaults from the existence of the environment-specific content file**:

```ruby
if credentials_available_for_current_env?
  content_path = "config/credentials/#{Rails.env}.yml.enc"
  key_path     = "config/credentials/#{Rails.env}.key"
else
  content_path = "config/credentials.yml.enc"
  key_path     = "config/master.key"
end
```

See the [original merged diff](https://github.com/rails/rails/blob/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba/railties/lib/rails/application/configuration.rb). The follow-up maintainer refactor preserved exactly that pairing in [commit `37c948c`](https://github.com/rails/rails/blob/37c948ce6715df8ecbcda2b64a1e6eee9c5d6bb6/railties/lib/rails/application/configuration.rb).

PR #33521’s changelog was likewise explicit: `production.yml.enc` could be decrypted with `RAILS_MASTER_KEY` or `production.key`, not implicitly with `master.key`.

### Current Rails independently falls back each path

Current `credentials_defaults` now checks each file independently:

- [`configuration.rb` lines 683–690](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L683-L690)

```ruby
content_path = env_content
content_path = global_content unless env_content.exist?

key_path = env_key
key_path = master_key unless env_key.exist?
```

Therefore this layout:

```text
config/credentials/production.yml.enc
config/master.key
# no config/credentials/production.key
```

selects `production.yml.enc` **and** `master.key`. If that encrypted file was generated with another key, accessing credentials raises `ActiveSupport::MessageEncryptor::InvalidMessage`.

The guide now explicitly documents that independent key fallback: [`config.credentials.key_path`](https://github.com/rails/rails/blob/main/guides/source/configuring.md) defaults to the environment key “if it exists, or `config/master.key` otherwise.”

### Reported confusion and `InvalidMessage`

[Issue #46636](https://github.com/rails/rails/issues/46636) captures essentially the operational confusion:

- The reporter created environment credentials but deployed with `config/master.key`.
- A participant explained that `RAILS_MASTER_KEY` must contain the environment-specific key when using environment credentials.
- The reporter fixed deployment by removing `config/master.key` and using `config/credentials/staging.key`.

That advice follows the original pairing model. However, it came from community participants; no Rails maintainer ruled on whether the fallback itself was intentional.

[Issue #33528](https://github.com/rails/rails/issues/33528) also demonstrates the general symptom: `InvalidMessage` means Rails found a key and attempted decryption, but the key did not match the encrypted content. It predates environment credentials, so it is supporting context rather than direct evidence about `credentials_defaults`.

### Did anyone propose pairing them?

**Yes—the original PR did more than propose it: it implemented pairing.** The environment content file’s existence controlled both defaults. The maintainer follow-up retained it.

What I did **not** find:

- a later issue/PR specifically proposing restoration of that paired fallback;
- a maintainer statement that independently selecting `production.yml.enc` and `master.key` is desirable;
- a maintainer discussion explicitly labeling the mismatch a footgun.

## Review implication

A change that **always** falls `key_path` back to `config/master.key` when the environment key is absent does **not** reflect PR #33521’s original design. It reflects current independent-default behavior, but that behavior can silently construct an incoherent content/key pair and turn a missing environment key into a misleading `InvalidMessage`.

The historically safer semantics are:

- environment content exists → environment key path, even when the key file is absent, so Rails reports a missing key;
- environment content absent → global content plus `master.key`;
- `RAILS_MASTER_KEY` may still override the selected key file at runtime.

## Why the claim is wrong

`credentials:edit --environment production` writes `config/credentials/production.yml.enc` and a **new** `production.key`, not `master.key` ([`CredentialsCommand#edit`](file:///home/user/workspace/repo/railties/lib/rails/commands/credentials/credentials_command.rb#L21-L24)). ## `require_master_key` and boot

[`active_support.require_master_key`](file:///home/user/workspace/repo/activesupport/lib/active_support/railtie.rb#L133-L141) only checks `app.credentials.key` (env var or selected `key_path`). It does not decrypt.

With env ciphertext and no env key:

- Proposed: `key_path` is `master.key`. If that file or `RAILS_MASTER_KEY` exists, boot succeeds. First credentials read then raises `ActiveSupport::MessageEncryptor::InvalidMessage`.
- Paired: `key_path` stays `config/credentials/production.key`. Boot fails with `MissingKeyError` naming that file.

`EncryptedConfiguration#read` rescues only `MissingContentError` (missing file **or** missing key when `require_master_key` is false) and returns `""`. It does **not** rescue `InvalidMessage`. Wrong-key fallback is louder and less actionable than a missing env key.

## Commands vs runtime

## Dev vs production

Development/test: `require_master_key` defaults false; `secret_key_base` can come from `tmp/local_secret.txt` ([`Configuration#secret_key_base`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L557-L565)). A bad env/key pair can look like empty credentials.

## Security / compatibility

Independent fallback does not decrypt with a second key; it will not leak env secrets unless `master.key` happens to be the env key. It does:

- Collapse the per-env key model (`credentials:edit --environment` exists specifically to use a different key).
- Turn “forgot `production.key` on the server” into “ciphertext looks corrupt”.
- Let `require_master_key` pass on the global key while env ciphertext stays unreadable.

Compatibility: anyone who encrypted `#{env}.yml.enc` with `master.key` on purpose would lose that if pairing is restored. The generator never produces that layout. The common layout (env file + env key, or global file + `master.key`, plus `RAILS_MASTER_KEY`) is unchanged by pairing.
