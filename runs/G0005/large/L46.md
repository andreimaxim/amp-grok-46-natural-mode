**Request changes.** Environment credentials must not fall back to `config/master.key`. `content_path` and `key_path` should stay paired; `ENV["RAILS_MASTER_KEY"]` is already the override.

This checkout already implements the independent fallback the PR wants:


That is not the original contract. [PR #33521](https://github.com/rails/rails/pull/33521) selected both paths from whether `config/credentials/#{env}.yml.enc` existed: env content → env key; otherwise global content → `master.key`. `credentials:edit --environment` still generates that paired layout.

# Why the claim is wrong

`Rails.application.credentials` decrypts `config.credentials.content_path` with `ENV["RAILS_MASTER_KEY"]` first, then `config.credentials.key_path` ([`EncryptedFile#key`](file:///home/user/workspace/repo/activesupport/lib/active_support/encrypted_file.rb#L53-L54)). It never tries a second key file. Falling `key_path` to `master.key` while keeping env ciphertext is not a fallback; it is a mismatched pair.

`credentials:edit --environment production` writes `config/credentials/production.yml.enc` and a **new** `production.key`, not `master.key` ([`CredentialsCommand#edit`](file:///home/user/workspace/repo/railties/lib/rails/commands/credentials/credentials_command.rb#L21-L24)). Runtime then using `master.key` for that file is the opposite of the command.

# Path matrix

Assume `production.yml.enc` was encrypted with `production.key` (what the command creates). `RAILS_MASTER_KEY` unset.

| `production.yml.enc` | `production.key` | `master.key` | Proposed `key_path` | What should happen | What this fallback does |
|---|---|---|---|---|---|
| yes | yes | either | `production.key` | decrypt | decrypt |
| yes | no | yes, different | `master.key` | missing `production.key` | `InvalidMessage` |
| yes | no | yes, same bytes | `master.key` | missing `production.key` | accidentally decrypts; env isolation gone |
| yes | no | no | `master.key` (also missing) | missing `production.key` | `MissingKeyError` names the wrong file |
| no | no | yes | `master.key` | global file + `master.key` | correct |
| no | yes | yes | `production.key` | global file + `master.key` | `InvalidMessage` on `credentials.yml.enc` |

The last row is the other half of independent selection. The PR only talks about env content without env key; it also leaves env key without env content broken.

`RAILS_MASTER_KEY` already covers the legitimate “no key file” case. [`reads credentials using environment variable key`](file:///home/user/workspace/repo/railties/test/application/credentials_test.rb#L31-L39) writes env ciphertext **without** `production.key` and decrypts via `RAILS_MASTER_KEY`. That test is the real fallback. Issue [#46636](https://github.com/rails/rails/issues/46636) is the operational version: after `credentials:edit --environment=staging`, `RAILS_MASTER_KEY` / `master.key` must be the **staging** key, not the global one.

# `require_master_key` and boot

[`active_support.require_master_key`](file:///home/user/workspace/repo/activesupport/lib/active_support/railtie.rb#L133-L141) only checks `app.credentials.key` (env var or selected `key_path`). It does not decrypt.

With env ciphertext and no env key:

- Proposed: `key_path` is `master.key`. If that file or `RAILS_MASTER_KEY` exists, boot succeeds. First credentials read then raises `ActiveSupport::MessageEncryptor::InvalidMessage`.
- Paired: `key_path` stays `config/credentials/production.key`. Boot fails with `MissingKeyError` naming that file.

`EncryptedConfiguration#read` rescues only `MissingContentError` (missing file **or** missing key when `require_master_key` is false) and returns `""`. It does **not** rescue `InvalidMessage`. Wrong-key fallback is louder and less actionable than a missing env key.

`config.require_master_key` docs say the app needs `ENV["RAILS_MASTER_KEY"]` or `config/master.key`. That sentence is already wrong for env credentials: the check uses whatever `key_path` was selected.

# Commands vs runtime

Without `--environment`, `credentials:show` / `fetch` use `config.credentials.*` ([`CredentialsCommand#content_path` / `#key_path`](file:///home/user/workspace/repo/railties/lib/rails/commands/credentials/credentials_command.rb#L80-L92)). With `--environment`, edit **forces** env paths unless `config.overridden?(:content_path)` / `:key_path`.

So in production with `production.yml.enc` and no `production.key`:

- `bin/rails credentials:show` → `master.key` (proposed/current defaults)
- `bin/rails credentials:show -e production` → `config/credentials/production.key`

Same app, two answers. Custom `config.credentials.content_path` / `key_path` in `application.rb` or `config/environments/*.rb` still win (`overridden?`); this PR should not touch that.

Edit with a missing key creates the **selected** `key_path` ([`ensure_encryption_key_has_been_added`](file:///home/user/workspace/repo/railties/lib/rails/commands/credentials/credentials_command.rb#L94-L101)). Under independent fallback, `credentials:edit` in production with env ciphertext present can add `config/master.key` and then fail to decrypt (`Couldn't decrypt ... Perhaps you passed the wrong key?`) instead of adding `production.key`.

# Dev vs production

Development/test: `require_master_key` defaults false; `secret_key_base` can come from `tmp/local_secret.txt` ([`Configuration#secret_key_base`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L557-L565)). A bad env/key pair can look like empty credentials.

Production: `secret_key_base` must come from credentials or `SECRET_KEY_BASE`. A `master.key` that cannot decrypt `production.yml.enc` becomes a boot-time `InvalidMessage` with no pointer at the missing env key.

# Security / compatibility

Independent fallback does not decrypt with a second key; it will not leak env secrets unless `master.key` happens to be the env key. It does:

- Collapse the per-env key model (`credentials:edit --environment` exists specifically to use a different key).
- Turn “forgot `production.key` on the server” into “ciphertext looks corrupt”.
- Let `require_master_key` pass on the global key while env ciphertext stays unreadable.

Compatibility: anyone who encrypted `#{env}.yml.enc` with `master.key` on purpose would lose that if pairing is restored. The generator never produces that layout. The common layout (env file + env key, or global file + `master.key`, plus `RAILS_MASTER_KEY`) is unchanged by pairing.

# Corrected diff

Pair the paths again. Do not fall `key_path` to `master.key` while `#{env}.yml.enc` exists.

```ruby
def credentials_defaults
  if (content_path = root.join("config/credentials/#{Rails.env}.yml.enc")).exist?
    { content_path: content_path, key_path: root.join("config/credentials/#{Rails.env}.key") }
  else
    { content_path: root.join("config/credentials.yml.enc"), key_path: root.join("config/master.key") }
  end
end
```

Keep `ENV["RAILS_MASTER_KEY"]` as the only override. If docs currently say `key_path` is env key “if it exists, otherwise `master.key`”, they should say env content and env key are selected together; otherwise global content and `master.key`.
