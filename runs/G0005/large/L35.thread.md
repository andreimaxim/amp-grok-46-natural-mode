`stream_from` does not push data. It registers a named pub/sub listener. `broadcast` is the other end: it encodes a payload and publishes it to that name. Clients only see a message if they are already streaming that name when the publish happens.

### `coder: nil` vs `ActiveSupport::JSON` vs custom encode

These two `coder:` kwargs are independent.

| Site | Default | `coder: nil` | JSON / custom |
|---|---|---|---|
| `Server#broadcast` | `ActiveSupport::JSON` | skip encode; publish `message` as-is | `coder.encode(message)` |
| `stream_from` + **callback** | `nil` (raw payload) | same: handler is returned unchanged | `coder.decode` then user handler |
| `stream_from` + **default handler** | documented `nil`, implemented as JSON | `coder \|\|= ActiveSupport::JSON` | decode then transmit |

So `coder: nil` on `stream_from` means “no decode” only when a callback is present ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L86-L90), [200-213](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L200-L213)). Without a callback, nil is replaced with JSON ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L195-L198)). That is why a JSON-encoded hash survives the default path as a Hash, not a String.

Server-side custom encoding is the broadcast `coder:`. The StreamFromTest “custom encoder” case publishes with `DummyEncoder` (`encode` always returns `'{ "foo": "encoded" }'`) while the channel still JSON-decodes on receive. Observable result: `{ "foo" => "encoded" }` ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L38-L41), [356-365](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L356-L365)). `DummyEncoder#decode` is never used there. `ChatChannel` can select `coder: nil` / JSON / `DummyEncoder` via params, but no StreamFromTest drives the `"none"` or `"custom"` subscribe coder ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L16-L33)).

There is a second encode on the way out: `Socket` JSON-encodes the Cable envelope ([socket.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L47-L51)). The default path is therefore encode (pubsub) → decode (handler) → encode (WebSocket). The source even notes that JSON-to-JSON proxying could skip that pair ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L191-L193)).

### Deferred confirmation

The counter starts at 1, “awaiting `#subscribe_to_channel`” ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L168-L172)). Each `stream_from` increments; each pubsub success and the end of `subscribe_to_channel` decrement. Confirmation is sent only when the counter reaches 0 and the subscription was not rejected ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L253-L264), [322-330](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L322-L330)).

That is why confirmation is not sent from `initialize` ([actioncable/test/channel/base_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/base_test.rb#L194-L202)), why `stream_from` waits for `pubsub#subscribe` success ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L94-L107)), and why two `stream_from` calls still produce one `{ type: "confirm_subscription" }` ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L139-L160), [394-403](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L394-L403)). `transmit_subscription_confirmation` is also gated on `@subscription_confirmation_sent`.

With a synchronous adapter (SuccessAdapter / Inline), the success callback often runs inside `stream_from` during `subscribed`; the counter is still > 0 until `subscribe_to_channel` decrements. With Async/Redis, confirmation typically comes later, from the success lambda.

### Decode / encode failures

This revision has no tests for encode or decode errors.

- **Encode** happens in `Broadcaster#broadcast` with no rescue. A failing `coder.encode` raises to the `broadcast` caller; pubsub is not called ([broadcasting.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L54-L61)).
- **Decode** happens in `stream_decoder` with no rescue ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L200-L207)). `ActiveSupport::JSON.decode` raises `JSON::ParserError` on bad input ([activesupport/lib/active_support/json/decoding.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/json/decoding.rb#L25-L49)).
- On the **callback** path, that decode runs inside `Worker#invoke`, which rescues `Exception`, logs it, and only calls `handle_exception` if the receiver (the handler proc) defines it — a lambda does not ([worker.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L59-L67)). The failure is logged and dropped; the client gets no message.
- On the **default** path, decode/transmit run on the adapter executor, not the worker pool, so that rescue does not apply. The exception leaves `invoke_callback`.

Invalid JSON on a default stream therefore does not become a client error frame; it is an unhandled executor exception. A user callback that swallows errors can still `transmit` something else.
