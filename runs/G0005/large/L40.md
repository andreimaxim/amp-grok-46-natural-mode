# Current behavior (revision evidence)

Revision [`ace84a2`](https://github.com/andreimaxim/rails-for-grok-large/commit/ace84a2f3e4138a823592864972adbfde084cfd0). Evidence is this checkout’s source, guides, and test assertions. Those tests were not re-run here. Claims below are what the tests and comments already lock in, plus a few boundaries only the verifier source states.

Inspected: blob/attachment signed-identifier APIs and tests; proxy and redirect download controllers and tests; route helpers; service URL generation for private vs public Disk/S3/GCS; variant/representation controllers; verifier expiry comparison; Active Storage guide and configuring guide.

Limits: variant download URLs inherit the same signed-identifier options as blob URLs in the helpers, but representation tests do not assert `expires_in` / `expires_at`. Success cache headers are asserted for blob proxy/redirect, not for representations. Exact-at-expiry behavior is asserted for signed messages generally, not for Active Storage download requests. Live cloud expiry after timeout was not observed in this session.

## Signed blob identifiers

`ActiveStorage::Blob#signed_id` (and the attachment that forwards it) is permanent unless the caller passes a duration or an absolute time. A valid identifier finds the blob. After the duration or timestamp has passed, a non-raising lookup returns nothing. Tampered, purpose-mismatched, and expired identifiers are all treated as invalid signatures. Download routes that require a signed identifier turn that failure into HTTP 404.

Tests cover: valid permanent IDs; IDs with `expires_in: 1.minute` and `expires_at: 1.minute.from_now` still working immediately; those same IDs returning nil / 404 after traveling 2 minutes. They do not request at the expiry instant.

The verifier treats a message as expired when current UTC time is greater than or equal to the stored expiry. `expires_at` wins if both a duration and an absolute time are supplied. That comparison is from message metadata tests, not Active Storage download tests.

## Rails download URLs vs service URLs

These are two clocks.

**Rails download URLs** (`rails_storage_proxy_url`, `rails_storage_redirect_url`, and `url_for` on a blob/attachment when it resolves to those routes): the identifier in the path is permanent by default. `config.active_storage.urls_expire_in` defaults to unset/nil. A per-URL `expires_in` or `expires_at` makes that identifier time-limited. When the application-wide default is set to 1 minute, helpers that omit a per-URL expiry also 404 after 2 minutes.

**Service URLs** (`Blob#url`, and the Location a redirect response sends the browser to): default lifetime is 5 minutes (`config.active_storage.service_urls_expire_in`). That clock is independent of the Rails download URL clock.

Guides and controller comments call the Rails URLs “permanent” and “never expire by default,” while also documenting optional expiry. `#url` is documented as permanent for public files and short-lived for private files.

## Proxy vs redirect, and cache headers

**Redirect**, valid identifier: HTTP redirect to a service URL; `Cache-Control: max-age=300, private`. The 300 seconds matches the default service-URL lifetime, but it is the redirect response being cached, not a guarantee that the service URL still works for those 300 seconds on a later follow.

**Proxy**, valid identifier, full-file response: HTTP 200 with the file; `Cache-Control: max-age=3155695200, public, immutable` (100 years). Missing stored file: 404 and `no-cache`. Other download error: 500 and `no-cache`. Invalid or expired identifier: 404 (cache header not asserted).

Byte-range proxy responses are tested for status and body, not for cache headers. Range requests take a different branch than the “cache forever” full-file path.

A valid request mints a fresh service URL at request time. An expired Rails identifier never gets that far.

## Tampered / expired identifiers

Invalid signed IDs 404 on blob proxy, blob redirect, variant proxy, and variant redirect. Expired blob proxy/redirect URLs 404 after travel-past-expiry. Expired and tampered are not distinguishable to the client: both are not found. Missing blob after a still-valid signature is a different failure (record not found), not covered as a download-link cache case in these tests.

## Public vs private services

`#url` on a public service returns a non-expiring public object URL (S3/GCS tests fetch it with HTTP 200). On a private service it returns a signed, time-limited URL. Disk public still goes through the Disk download path, but with no expiry on the verified key; Disk private signs that key with the 5-minute default.

Redirect mode still issues a Rails URL first, then redirects to whatever `#url` produced. Proxy mode never exposes the service URL to the client.

## Variants

Variant/preview download URLs put a signed blob identifier and a variation key in the Rails path. Invalid identifier or invalid variation key → 404. Redirect representations send the client to a representation service URL that uses the same 5-minute service default. Proxy representations stream the processed file and are written to be publicly cacheable indefinitely. Variant `#url` uses the same service-URL default as blobs.

Expiry options on representation URLs are implemented in the same helpers as blob URLs. Representation tests do not travel past expiry.

## Boundary timing (what is and is not proven)

Proven by Active Storage tests: 1-minute duration or timestamp still works immediately; after 2 minutes the Rails download URL 404s.

Proven by signed-message tests, not download tests: still valid 0.5s before a 1s expiry; invalid at the expiry instant (`>=`).

Not proven: whether a proxy/CDN copy cached under `public, immutable` can still be served after the signed identifier in that URL has expired; whether a privately cached redirect can be replayed after the Rails identifier expired; whether a private service URL is rejected by the storage provider at its own deadline.

```diagram
Developer generates a link
        │
        ├─ signed blob identifier
        │     default: no expiry
        │     optional: expires_in / expires_at
        │
        ├─ Rails proxy URL ──▶ 200 + file
        │     cache: public, immutable, ~100 years
        │     identifier expired/tampered: 404
        │
        ├─ Rails redirect URL ──▶ 302 Location: service URL
        │     cache: private, 5 minutes
        │     then service URL:
        │        private service: ~5 minutes
        │        public service: no expiry
        │
        └─ Blob#url (service URL directly)
              private: ~5 minutes
              public: no expiry
```

That split — three lifetimes, two of which can outlive or undercut each other — is the current contract.

# Shaping brief (draft)

This is the proposed product understanding, not a design. It does not prescribe how Rails should be changed.

## Problem frame

An application developer needs to hand someone a download link for a stored file — in a page, an email, an API, or a CDN — and know **until when that link will work**, and **what a browser or cache will keep serving**.

Today they meet three surfaces that sound like “the download URL”:

1. A signed blob identifier (`signed_id`)
2. A Rails proxy or redirect URL (`rails_storage_proxy_url` / `rails_storage_redirect_url`)
3. A storage-service URL (`#url`)

Those surfaces use different defaults, different clocks, and different cache rules. Guides call Rails URLs permanent; the same guides document optional expiry; service URLs expire in five minutes unless the bucket is public, in which case they do not expire. Proxy responses tell shared caches to keep the file for about a hundred years even when the identifier in the URL was minted to die in a minute.

The pain is not that expiry exists. It is that a careful developer cannot predict, from the APIs they already use, which clock governs the link they just generated, when access actually stops, or whether a cache will keep serving the file after they believe the link is dead. That shows up as surprise 404s, links that remain usable longer than intended, and public cache copies that ignore the expiry the developer thought they set.

**Hypothesis (correct me):** the work is for application developers first; end users only feel it as “the image/email/attachment link died” or “this file is still reachable.” The job is a predictable contract, not a new access-control product.

## Desired outcome

After this work, a developer using `signed_id`, `#url`, `rails_storage_proxy_url`, and `rails_storage_redirect_url` can answer these questions correctly without reading internals:

- Is this link permanent, or does it die?
- If it dies, at what instant, and which clock is that?
- If a client or CDN cached the response, does that cache outlive the link?
- If the identifier is tampered, expired, or the file is gone, what does the requester see?
- Do public storage, private storage, and image variants follow the same rules or named exceptions?

Success is qualitative: a developer can choose permanent vs time-limited access on purpose, explain that choice to a teammate, and observe the matching behavior at the boundary — including cache — rather than discovering a second hidden lifetime.

## Appetite

**Hypothesis:** one batch of product work to make the contract coherent and teachable. Enough to remove the surprises above. Not a rewrite of storage security, authentication, or CDN setup.

If aligning cache lifetime with identifier lifetime (or naming an explicit exception) does not fit that appetite, the outcome should say so and treat the mismatch as a documented rule, not an accidental footnote. Leaving it unnamed fails the outcome.

## Scope

In:

- Permanent vs time-limited signed blob identifiers (`expires_in` and `expires_at`, and the unset default)
- Application-wide default for Rails download URLs vs per-link override
- Service-URL lifetime, including public vs private storage
- Proxy vs redirect: status, body vs Location, and cache headers a client actually sees
- Tampered vs expired identifiers as the requester observes them
- Variants/previews reached through the same proxy/redirect URL helpers
- Boundary timing: still valid before expiry; behavior at the expiry instant; behavior after
- What a shared cache or private browser cache may still serve after expiry

Out of this batch unless you pull them in:

- Authenticated/authorized file controllers as a replacement for public download routes
- Direct-upload PUT URLs, except that they share the service-URL default duration
- Changing which files are public on the bucket
- New download products (streaming APIs, signed cookies, per-user tokens)

## Non-goals

- Making expiry a substitute for login or authorization. A valid link remains usable by anyone who has it until its own clock runs out.
- Hiding storage-provider URLs when the developer asks for `#url` on purpose.
- Promising that a purged or missing file stays downloadable until a URL expires.
- Distinguishing “expired” from “tampered” to end users unless we explicitly decide that is required. Today both are not found.

## Risks if we get the contract wrong

- **Cache vs expiry.** If proxy URLs remain `public, immutable` for ~100 years, a developer who mints a 1-minute proxy link can still have the file served from a CDN after the identifier is dead. Documenting expiry without this rule will recreate the original surprise.
- **Two defaults.** Rails download URLs default to never expire; service URLs default to 5 minutes. If we only clarify one, redirect-mode emails and `#url` in jobs will still desync.
- **Public storage.** On a public service, `#url` does not expire. A developer who copies that URL into a page has a permanent link even if they also generated an expiring Rails URL for the same file.
- **Redirect cache is private 5 minutes.** Browsers may reuse the redirect without re-checking the Rails identifier. Whether that is allowed after identifier expiry must be an explicit rule.
- **Variants.** If blob links expire and variant links do not (or the reverse), image tags will fail or leak on a different clock than the original file.
- **Existing callers.** Treat today’s defaults as compatibility surface until we decide otherwise: unset Rails-URL expiry stays unlimited; service URLs stay 5 minutes; public service URLs stay non-expiring. Changing those defaults is a product choice, not implied by “predictable.”

## Behavioral outcomes

1. **A signed blob identifier is unlimited unless the developer sets a lifetime.** With no duration and no timestamp, later lookups and download requests that accept that identifier still succeed. With a duration or timestamp, they succeed before expiry and fail after.

2. **Rails proxy and redirect URLs use that same identifier lifetime.** Per-link duration/timestamp and the application-wide Rails-URL default apply to both helpers, for blobs and for variants. After expiry, a request for that URL does not return the file.

3. **Service URLs are a separate lifetime the developer can predict from storage visibility.** Private: time-limited with a known default (today 5 minutes) unless overridden when asking for `#url`. Public: no time limit on the service URL itself. Redirect mode may mint a new service URL on each successful Rails request; that refresh does not revive an expired Rails identifier.

4. **Proxy and redirect advertise different cache rules, and those rules are part of the expiry contract.** Redirect: private, short-lived cache of the redirect. Proxy: public, long-lived cache of the file on a successful full response; errors that mean “do not remember this” are not cached. The contract must say whether a cached successful proxy/redirect response may be reused after the identifier expires. Until that is decided, predictability is incomplete.

5. **Tampered and expired identifiers fail closed to the requester.** The file is not returned. Today that is HTTP 404, same for both. Missing file on an otherwise valid proxy request is not found and not cacheable; other proxy download failures are server error and not cacheable.

6. **Variants follow the blob identifier’s lifetime.** A variant/preview download URL with an expired or tampered blob identifier does not return the derivative. An unreadable variation key also fails closed. The derivative’s service URL, in redirect mode, follows the service-URL rules in (3).

7. **Expiry is inclusive of the deadline.** At the expiry instant the identifier is no longer valid. Immediately before, it is valid. This matches signed-message behavior already in the framework; download links should not imply a different boundary.

## Acceptance examples

Required cases, not an exhaustive catalog.

**Permanent identifier.** A developer generates a signed blob identifier with no lifetime. Days later, a download URL built from it still returns the file (assuming the file still exists).

**Duration.** They generate a proxy URL with a 1-minute lifetime. A request before 1 minute returns the file. A request after 1 minute does not. Same for a redirect URL.

**Absolute time.** They generate a redirect URL that expires at a wall-clock time. Before that time: redirect to a service URL. After: no file.

**Application-wide Rails-URL default.** With a 1-minute default and no per-link override, a generated proxy/redirect URL works immediately and does not after 2 minutes. A per-link timestamp or duration still wins for that link.

**Service URL, private.** They call `#url` with no custom lifetime on a private service. The URL they hand out stops working on the storage side after the service default (5 minutes today), independently of any Rails download URL they also generated.

**Service URL, public.** They call `#url` on a public service. That URL has no expiry of its own. An expiring Rails URL for the same blob does not make this service URL expire.

**Tampered identifier.** A requester changes a character in the signed identifier of a proxy or redirect URL (blob or variant). They do not get the file.

**Expired vs immediately-before.** A link with a 1-second lifetime still works half a second later and does not at the 1-second mark.

**Proxy cache vs expiry (decision example).** A developer mints a 1-minute public proxy URL. A CDN caches the 200. After 1 minute, either (A) the cached file may still be served, and that is an explicit, documented rule, or (B) it must not be. One of these is the product rule; silence is not.

**Redirect cache vs expiry (decision example).** A browser cached a private 5-minute redirect. After the Rails identifier expires but before that 5 minutes elapses, either following the cached redirect is allowed or it is not. Same: pick one and make it observable.

**Variant.** A developer generates a proxy URL for a resized image with a 1-minute identifier lifetime. Before expiry, the variant is returned. After, it is not. An invalid variation key never returns a file.

**Error caching.** A proxy request for a valid identifier whose file is not in storage does not instruct caches to store that failure as the file.

**Not a goal example.** A developer puts an expiring Rails URL in an email and does not add application authentication. Anyone with the URL can fetch the file until that URL’s own clock ends.

## Steering evidence

We would treat the outcome as **not met** if:

- A developer following the public contract still cannot tell which clock a given helper uses.
- An expiring proxy or redirect URL returns the file after expiry on a first-party request (no cache).
- Public and private `#url` behavior is described as one lifetime but observed as two.
- Variant URLs expire on a different clock than blob URLs from the same helpers without that being a named exception.
- Cache headers still contradict the stated expiry rule (for example “this link is dead at T” while successful proxy responses remain `public, immutable` for ~100 years and we chose rule B above).

We would **reconsider the problem framing** if:

- Developers already treat Rails URLs as “unguessable forever capability URLs” and the real pain is only documentation wording — then the work is a contract restatement, not behavior alignment.
- The real pain is “anyone with the URL can fetch the file,” which is authorization, called out as a non-goal.
- Changing cache headers or defaults would break CDNs that depend on immutable proxy responses — then appetite must explicitly keep today’s cache headers and make that the named rule.

## Open questions

These change the outcome if answered differently:

1. **Cache after expiry.** May a cached successful proxy (or redirect) response still serve the file after the signed identifier has expired? This is the main product fork.
2. **Default permanence.** Keep Rails download URLs unlimited by default, or is changing that default in appetite? Predictability does not require changing it.
3. **Expired vs tampered.** Stay indistinguishable (not found), or must developers/clients tell them apart?
4. **Exact instant.** Confirm inclusive expiry (`>=` deadline) as the public rule for download links, not only for signed messages in general.
