A refactor of `#touch` is behavior-preserving only if every public effect of `record.touch(...)` stays the same. Judge the call from the outside: return value, exceptions, attribute readers, dirty/saved-change APIs, `reload`, callback side effects, and the `UPDATE` that hits the database. Do not compare `_touch_row`, `_update_row`, `@_touch_attr_names`, or `@_trigger_update_callback`.

The existing suite already pins several of these observations (`timestamp_test`, `locking_test`, `readonly_test`, `base_test`, `transaction_callbacks_test`; 16 focused examples, 53 assertions, all passing on sqlite3_mem). Destroyed records and the no-row-updated path are not similarly pinned and have to be established with the same public probes.

### How to observe, not how it is implemented

Drive every case through `record.touch` / `record.touch(*names, time:)`. Record this tuple:

- **Call result:** return value, or exception class and message.
- **In-memory attributes:** `updated_at` / `updated_on` (and aliases), any named attributes, `lock_version`.
- **Persistence flags:** `new_record?`, `persisted?`, `destroyed?`, `readonly?`.
- **Dirty vs saved:** `changed?`, `changed`, `saved_changes?`, `saved_changes`.
- **Database:** `reload` (or a second `find`) plus the `UPDATE` captured with a query assertion.
- **Callbacks:** counters/history from `after_touch`, `after_commit` (including `on: :update`), `after_rollback` (including `on: :update`). Also assert `after_validation` / `after_save` / `after_update` do **not** run.

That tuple is the contract. A refactor that keeps it identical has preserved behavior even if every private helper changed.

### Record state: persisted, new, destroyed, readonly

**Persisted.** A loaded, saved record is the happy path. `#touch` returns truthy. `updated_at`/`updated_on` move forward in memory and after `reload`. One `UPDATE` is issued. `after_touch` and `after_commit(on: :update)` run; `after_rollback` does not. Unrelated in-memory edits are not written (`Developer#salary` stays dirty; `reload` restores the old salary). That last point is already in `test_touching_a_record_updates_its_timestamp`.

**New.** `Model.new.touch` and `Model.new.touch(:updated_at)` both raise `ActiveRecord::ActiveRecordError` with `Cannot touch on a new or destroyed record object...`. No `UPDATE`, no `after_touch`/`after_commit`. `test_touch_should_raise_error_on_a_new_object` covers the named-column form; the no-arg form is the same public error.

**Destroyed.** `record.destroy` then `record.touch` must raise that same error. `destroyed?` is true, `persisted?` is false, and the row is already gone — so this is not the no-row-updated case. The observation is: error before any write, timestamps unchanged on a fresh `find`, no `after_touch`.

**Readonly record vs readonly attribute.** Two different public errors, both before any `UPDATE`:

- `record.readonly!` then `touch` → `ActiveRecord::ReadOnlyRecord`, message `"#{model} is marked as readonly"` (`test_cant_touch_readonly_record`).
- `touch(:born_at)` on `Person` (`attr_readonly :born_at`) → `ActiveRecord::ActiveRecordError`, `"born_at is marked as readonly"` (`test_cant_touch_readonly_column`).

Default timestamp columns on a readonly record must not be an exception to the record-level check.

### Timestamp columns, custom attributes, aliases, explicit time

**Default timestamps.** On a model whose table has `updated_at`/`updated_on` (or the aliased `legacy_updated_*` on `Developer`), bare `touch` writes those columns only. Public readers change; `saved_changes.keys` are the **real column names** (`legacy_updated_at`, `legacy_updated_on` on `Developer`). `created_at` is left alone unless named.

**Custom names.** `task.touch(:ending)` and `task.touch(:starting, :ending)` write those columns **and** the update timestamps, all to the same clock. `test_touching_an_attribute_updates_it` / `test_touching_many_attributes_updates_them` already observe this via readers and `Time.now`.

**Aliases.** `touch(:updated_at)` on `Developer` must resolve the alias: `updated_at` and `legacy_updated_at` both show the new time, `saved_changes` still uses `legacy_updated_at`, and `changed?` is false afterward (`test_touching_update_at_attribute_as_symbol_updates_timestamp`). Passing the raw column name must produce the same readers, `saved_changes`, and `UPDATE` columns.

**Explicit `time:`.** `touch(time: t)` and `touch(:created_at, time: t)` set every touched column to `t` in memory and after `reload`, not `Time.current`. Equality to `t` (not merely “newer than before”) is the observation (`test_touching_updates_timestamp_with_given_time`, `test_touching_an_attribute_updates_timestamp_with_given_time`).

**No timestamp columns.** `Car.first.touch` raises nothing and issues no timestamp `UPDATE` (`test_touching_a_record_without_timestamps_is_unexceptional`). `after_touch` still runs; `after_commit(on: :update)` does not, because no row was reported as updated.

### Optimistic locking

Use `Person` (has `lock_version`). Public observations:

- Successful `touch` increments `lock_version` in memory and after `reload`, includes `"lock_version"` and `"updated_at"` in `saved_changes`, and leaves `changed?` false (`test_touch_existing_lock`).
- The `UPDATE` `WHERE` includes the **pre-touch** `lock_version`; a second instance that already saved raises `ActiveRecord::StaleObjectError` with action `"touch"`. After the error, `saved_changes?` is false and in-memory `lock_version` is unchanged (`test_touch_stale_object`).
- `preserve_lock_version_on_touch` is a documented-in-tests public knob: lock version does not bump, stale objects do not raise, `saved_changes` is only `["updated_at"]`. Only required if the refactor still exposes that API.

A refactor that writes timestamps but skips `lock_version`, or that swallows the stale error, fails these observations even if private update helpers look equivalent.

### Dirty tracking and saved changes

`#touch` is not `#save`. The public split is:

- Touched attributes are **not** dirty afterward (`changed` / `updated_at_changed?` false).
- Touched attributes **are** in `saved_changes` with `[old, new]`.
- Pre-existing dirty attributes stay dirty and stay **out** of `saved_changes` and **out** of the `UPDATE` (`salary` in `test_touching_a_record_updates_its_timestamp`).
- `saved_changes?` is true on a successful row update.

That is the whole dirty contract. Do not inspect how changes are snapshotted internally; if those four facts hold before and after the refactor, dirty behavior is preserved.

### Callbacks: `after_touch`, `after_commit`, `after_rollback`

Docs state that `#touch` skips validations and runs only `after_touch`, `after_commit`, and `after_rollback`. Prove that with listeners, not by tracing callback stacks.

- **`after_touch`:** increment a counter on the model. It runs on a successful persisted `touch` (see `Topic#after_touch_called`), and it does **not** run under `Model.no_touching` (`test_no_touching_with_callbacks`).
- **`after_commit`:** `touch` on an existing record is an update commit. `test_only_call_after_commit_on_update_after_transaction_commits_for_existing_record_on_touch` already asserts history `[:commit_on_update]`. Nested transactions must still defer until the outermost commit (`test_only_call_after_commit_on_top_level_transactions`).
- **`after_rollback`:** `transaction { record.touch; raise ActiveRecord::Rollback }` yields `[:rollback_on_update]`, not commit (`test_only_call_after_rollback_on_update_after_transaction_rollsback_for_existing_record_on_touch`). After rollback, `reload` shows the pre-touch timestamps.
- **Negative:** `after_validation`, `after_save`, and `after_update` counters stay at 0. An invalid record (`validates :name, presence: true` with `name = nil`) still touches.

If a refactor starts running `after_update`, or stops running `after_commit(on: :update)`, the public history arrays change even when SQL matches.

### No row updated

This is the gap. Create a persisted instance, delete its row without going through that instance (`Model.delete(id)` or `delete_all`), then call `touch` on the still-`persisted?` object. Use a model **without** optimistic locking so a zero-row `UPDATE` is not turned into `StaleObjectError`.

Observe, don’t assume:

- Does `#touch` return false, raise, or return true?
- Does `after_touch` run (it wraps the public call)?
- Does `after_commit(on: :update)` run? It must not if the commit trigger is “exactly one row”.
- Does `after_rollback` run? A false status from `#touch` rolls the implicit transaction back.
- After the call, do in-memory timestamps stay at the written time or revert (`reload` is meaningless; the row is gone — compare to the values captured **before** `touch`)?
- `saved_changes?` after a failed/zero-row touch.

Whatever that tuple is on mainline is the contract. A refactor that reports success, fires `after_commit`, or leaves timestamps assigned when the old code rolled them back has not preserved behavior. Do not “fix” this by asserting a private `affected_rows` local.

On a locking model the same setup is **not** this case: it must keep raising `StaleObjectError` (`test_touch_stale_object`). Zero rows and stale lock are different public outcomes.

### What would falsify “behavior preserved”

| Claim | Public observation that must not change |
|---|---|
| Persisted touch | truthy return, timestamps on record and `reload`, one `UPDATE`, `after_touch` + `after_commit(on: :update)` |
| New / destroyed | same `ActiveRecordError` message, no `UPDATE`, no callbacks |
| Readonly record / column | `ReadOnlyRecord` vs `"#{attr} is marked as readonly"`, no `UPDATE` |
| Default + aliased timestamps | readers, `saved_changes` keys (real columns), `UPDATE` column list |
| Custom names | named attrs and update timestamps share one clock |
| `time:` | equality to the given time in memory and DB |
| Locking | `lock_version` +1, `saved_changes` includes it; stale → `StaleObjectError`, `saved_changes?` false |
| Dirty | unrelated `changed` preserved; touched attrs only in `saved_changes` |
| Callbacks | only `after_touch` / `after_commit` / `after_rollback`; invalid records still touch |
| Zero-row `UPDATE` | same return/exception, same callback set, same in-memory attributes as current mainline |

If those observations match, the refactor preserved `#touch`. If you need private helpers to be equal to believe it, the strategy has slipped off the contract.
