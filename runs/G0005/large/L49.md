Current request-level behavior is not what the stubbed reloader tests describe: a failed development reload can drop or split live routes, consume the file change, and leave later requests looking like ordinary misses. Here is the maintenance brief from that evidence.

**Problem frame:** In development, a developer editing the application’s or a mounted engine’s route file (or a file pulled in through an external draw path) can save invalid Ruby. Today it is unclear whether the previous routes still serve traffic and when a corrected file becomes the live routing. That uncertainty belongs at the development reload boundary: [`Rails::Application::RoutesReloader`](file:///home/user/workspace/repo/railties/lib/rails/application/routes_reloader.rb) via `app.routes_reloader`, the route sets and external draw paths registered there, and `config.file_watcher`. Successful routing when every route file is valid is not the intended change.

**Kind of work:** Maintenance of that failure/recovery contract. If you instead want prior routes to keep serving, or the load error to keep appearing until the file is valid, that is a behavior change and would reclassify the work.

---

## Actors and pain

The actor is a developer in a reloading development process (HTTP request, and likely console/job wrappers that go through the same reloader). They edit `config/routes.rb`, a mounted engine’s route file, or a file loaded with `draw`.

Pain: after a bad save, the next request may show a load error, a routing miss, or a mix (application routes live, engine routes gone). A later request with the file still invalid may not show the load error again. After a fix, it is unclear whether they must restart, wait, or hit the app once.

## Current behavior (from source, tests, and request probes)

Inspected: [`routes_reloader.rb`](file:///home/user/workspace/repo/railties/lib/rails/application/routes_reloader.rb), [`finisher.rb`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb) reload hooks, engine registration of paths/route sets/external routes, `Mapper#draw`, `config.file_watcher` / `FileUpdateChecker`, [`routes_reloader_test.rb`](file:///home/user/workspace/repo/railties/test/application/routes_reloader_test.rb), routing/engine tests, plus request-level probes in a generated development app.

What that supports:

- Initial boot with valid files: development can leave routes undrawn until first use (`loaded` false until a request). The first request serves the declared routes.
- Existing tests cover a stubbed watcher raising `RuntimeError`, concurrent first-load retry, successful reload of valid files, and that the reloader uses `config.file_watcher`. They do **not** cover a syntax-erroring route file, leftover routes after a failed reload, deleted files, engines, or `reload_classes_only_on_change`.
- After a successful boot, saving invalid Ruby and requesting: first request is a 500 with `SyntaxError`. Application routes from that file are gone; only prepended internal routes remain. `loaded` stays true.
- **Next request, file still invalid, `reload_classes_only_on_change` true (default):** 404 routing error, not another load error. The bad save is not retried.
- **Same sequence, `reload_classes_only_on_change` false:** every request reloads, so the next request is still 500 `SyntaxError` until the file is valid.
- **Correction:** saving valid Ruby and requesting once serves the new routes without restart (both flag values).
- **Engine file invalid, application file valid:** first request 500 `SyntaxError`; later requests serve the application routes and 404 the engine. Engine named routes are empty.
- **Simultaneous application + engine edits (app valid with a new route, engine invalid):** first request 500; later requests serve the new application routes and 404 the engine.
- **Deleted application `config/routes.rb`:** first request 500 `LoadError`; next request 404.
- **Deleted engine route file:** first request 500 `LoadError`; later application routes work, engine 404.
- **Deleted external draw file:** first request 500 `ArgumentError` (draw target missing); next request 404 for both the drawn routes and other routes in the same draw.
- **Invalid file at boot (lazy development):** first request fails (probe: exception middleware reported `ArgumentError` wrapping `SyntaxError`; a direct reload raises `SyntaxError`). `loaded` stays false. A later valid save is picked up on the next request.

Hypothesis, not a product requirement: the file watcher treats the failed reload as consumed, so with on-change-only reloading the error is easy to miss after the first request.

## Desired observable outcomes

When this boundary is in good condition, a developer can observe all of the following without guessing or restarting:

1. **After an invalid save**, whether previously working routes are still serving, or that they are not, is obvious from the next request (error vs routed response)—not a silent mix that looks like an unrelated 404.
2. **While the file stays invalid**, later requests do not hide the fact that routing is not in a successful loaded state (especially with the default on-change-only setting).
3. **After a correcting save**, the next request uses the corrected routes; the developer does not need a process restart.
4. **Application, mounted engine, and external draw files** follow the same observable failure and recovery story.
5. **`config.reload_classes_only_on_change` true or false** may differ in how often a reload is attempted, but must not differ in whether the developer can tell “load failed” from “route missing.”
6. **Valid reload behavior is unchanged:** changing a valid file still takes effect on the next request; `config.file_watcher` remains the change detector.

Outcomes 1–2 are the uncertainty to remove. They do not yet choose “keep old routes” vs “keep showing the load error.” That is an open question below.

## Non-goals

- Production / `config.enable_reloading = false`.
- Changing what valid route files define, route syntax, or `draw` lookup when the file exists.
- Replacing or redesigning `config.file_watcher`.
- Implementation, internal data structures, or a test/code design.
- Adjacent exception-page wrapping of `SyntaxError` (seen at boot) unless you pull it in.

## Acceptance examples

Required cases, not an exhaustive catalog. “Current” is probed; “desired” is the uncertainty to close.

**Initial boot, valid files.** Developer starts the app and requests a declared path. Observes the declared response. Desired: unchanged.

**Initial boot, invalid application route file.** First request does not serve application routes; a failure tied to that file is visible. After a correcting save, the next request serves the new routes.

**Syntax/erroring reload after a working boot** (`reload_classes_only_on_change` true). Save invalid Ruby in the application route file; request a path that worked. Current: 500 `SyntaxError`; old path is not served. Desired: the developer can tell this is a failed reload of that file, not a successful empty router.

**The next request, file still invalid** (default on-change true). Current: 404 `No route matches`. Desired: still obvious that routing has not recovered; a 404 that looks like “that route was never defined” is the failure mode to avoid.

**The next request, `reload_classes_only_on_change` false.** Current: 500 `SyntaxError` again. Desired: still clearly a failed reload; must not be the only setting where the error remains visible.

**Correction.** Save a valid file that adds a path. Next request serves old-still-wanted and new paths. Desired: unchanged, and true after a prior failed reload.

**Simultaneous application and engine changes.** Application file gains a valid new path; engine file is invalid. Current: first request 500; later requests serve the new application path and 404 the engine. Desired: the developer can tell the engine load failed and whether application routes are live; not a silent engine miss.

**Deleted route files.** Delete application `config/routes.rb`, or an engine route file, or an external draw file. Current: first request errors (`LoadError` / `ArgumentError`); later requests 404 or serve leftover sibling routes. Desired: same visibility as an invalid file: failure vs leftover routing is distinguishable, and a restored file takes effect on the next request.

**External draw path.** Invalid or missing `config/routes/<name>.rb` used via `draw`. Current: follows the application-file pattern (first request errors, later 404s including other routes in the same draw). Desired: same observable contract as the main route file.

## Steering evidence

- **Success:** After an invalid save, a developer can say from the next few requests whether old routes are live and that loading failed; after a fix, one request is enough to see the new routes; engines and draw files match that story; valid reloads still work.
- **Investigate the implementation, not the frame, if:** valid files stop reloading, or `config.file_watcher` is ignored.
- **Reconsider the frame if:** the real pain is only the exception page wrapping `SyntaxError`, or only production, or developers already treat “restart after any routes error” as acceptable.

## Open behavioral questions

1. After a failed reload, should prior routes keep serving until a successful reload, or is dropping them acceptable if the failure stays visible?
2. After the first erroring request, must later requests keep showing the load error until correction, or is another clear “not recovered” signal enough?
3. If only an engine (or only a draw file) fails, should already-drawn sibling route sets stay live?
4. Are console, rake, and Active Job in scope, or HTTP only?
5. Is boot-time `SyntaxError` wrapping as `ArgumentError` on the error page in scope?

## Evidence still worth collecting

- Concurrent requests during a failed reload (unit test covers stubbed first load, not this).
- `ActiveSupport::EventedFileUpdateChecker` vs the default checker.
- Runtime errors in a route file (`NameError`) vs `SyntaxError`.
- Retouching an unchanged invalid file (mtime-only change).
- Whether `/rails/info` after a failed reload is considered leftover routing.
