`reload` keeps the same Ruby object and replaces its internals from a fresh `SELECT`. It always hits the database. If that lookup finds nothing, it raises `ActiveRecord::RecordNotFound` and leaves the original object untouched.

```text
record.reload(options)
  AutosaveAssociation#reload          # clear marked_for_destruction
    AttributeMethods::Dirty#reload
      Persistence#reload
        connection_pool.clear_query_cache
        apply_scoping?(options)?
          yes → _find_record(options.merge(all_queries: true))
          no  → unscoped { _find_record(options) }
        steal @association_cache from fresh_object
        rebind each association.owner = self
        steal @attributes from fresh_object
        @new_record = false
        @previously_new_record = false
        return self
      then nil @mutations_before_last_save
           nil @mutations_from_database
```

The public method is [Persistence#reload](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L748-L763). [Dirty#reload](file:///home/user/workspace/repo/activerecord/lib/active_record/attribute_methods/dirty.rb#L62-L68) wraps it. [AutosaveAssociation#reload](file:///home/user/workspace/repo/activerecord/lib/active_record/autosave_association.rb#L243-L247) sits outside both (included later on `Base`) and only clears `marked_for_destruction`.

```diagram
┌──────────────┐     SELECT by PK      ┌──────────────┐
│ record (self)│                       │ fresh_object │
│ object_id N  │                       │ object_id M  │
└──────┬───────┘                       └──────┬───────┘
       │                                      │
       │  steal @attributes                   │ discarded
       │  steal @association_cache            │
       │  association.owner = self            ▼
       ▼                                 (GC)
  same object, new internals
```

## Query-cache clearing

The first line of `Persistence#reload` is `self.class.connection_pool.clear_query_cache`. That runs before the `SELECT`, so a cached identical query cannot satisfy the reload.

The pool method ([QueryCache::ConnectionPoolConfiguration#clear_query_cache](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/query_cache.rb#L187-L195)) clears the current thread’s cache, and increments a shared version when a connection is pinned so other threads drop theirs too.

[test_reload_via_querycache](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb#L1699-L1722) is the contract: populate the cache with `Parrot.find`, update the row inside `uncached`, then `reload` returns `"Mary"` from the database, not the cached name.

## Scoped versus unscoped lookup

[`apply_scoping?`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L858-L860) is true only when `options` does not include `unscoped: true` **and** the model has either a `default_scope ..., all_queries: true` or a `global_current_scope`.

- Ordinary `default_scope` (no `all_queries: true`) does **not** apply. Reload goes through `self.class.unscoped { _find_record(options) }`, which sets `current_scope` to a bare relation ([`unscoped`](file:///home/user/workspace/repo/activerecord/lib/active_record/scoping/default.rb#L50-L52)).
- `default_scope ..., all_queries: true` does apply. Reload calls `_find_record(options.merge(all_queries: true))`.
- `reload(unscoped: true)` forces the unscoped path even when `all_queries` default scopes exist.

[`_find_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L832-L847) then chooses the relation:

- `all_queries: true` → [`all_queries_scope`](file:///home/user/workspace/repo/activerecord/lib/active_record/scoping/named.rb#L59-L67): default scopes whose `all_queries` flag is set, merged with `global_current_scope`
- otherwise → `self.class.all`, which under the `unscoped` block is the bare relation

Lookup is `find_by!(_in_memory_query_constraints_hash)` — primary key, or `query_constraints`, from **in-memory** attribute values. Missing row → `RecordNotFound`. `reload(lock: true)` adds `FOR UPDATE`.

`all_queries_scope` merges `global_current_scope`, not ordinary `current_scope`. So:

- `Model.where(...).scoping { record.reload }` does **not** add that `WHERE`
- `Model.where(...).scoping(all_queries: true) { record.reload }` does

That split is exactly what [default_scoping_test](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb#L301-L367) asserts: no `mentor_id` on a plain default scope; `mentor_id` when `all_queries: true`; `unscoped: true` strips it; regular `scoping` does not add `salary`; `scoping(all_queries: true)` does.

## Association cache: replace, then rebind owner

After the find:

```ruby
@association_cache = fresh_object.instance_variable_get(:@association_cache)
@association_cache.each_value { |association| association.owner = self }
@attributes = fresh_object.instance_variable_get(:@attributes)
```

`fresh_object` is a different instance. Its cache is usually `{}`. Associations already in **self**’s cache whose owner is `strict_loading?` (and not n-plus-one-only) are preloaded onto `fresh_object` first ([`strict_loaded_associations`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L827-L830)), so strict-loading records keep those associations loaded after reload ([strict_loading tests](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb#L278-L310)).

The cache objects still have `owner` pointing at the discarded `fresh_object`. [`Association` has `attr_accessor :owner`](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L36); reload rebinds each one to `self`. Without that, later writes would mutate the throwaway record. [ReloadAssociationCacheTest](file:///home/user/workspace/repo/activerecord/test/cases/persistence/reload_association_cache_test.rb#L9-L19) covers that: `Publication`’s `after_initialize` builds `editor_in_chief`; after reload, assigning `editors` still touches the original publication (`name` becomes `"Rails Way (touched)"` via `after_save_commit`).

## Persistence flags and Dirty trackers

Persistence then sets `@new_record = false` and `@previously_new_record = false`, and returns `self`. It does not copy `@destroyed` from `fresh_object`.

Dirty runs only if that succeeds (`super.tap`):

```ruby
@mutations_before_last_save = nil
@mutations_from_database = nil
```

Next read of `saved_changes` lazily builds [`NullMutationTracker`](file:///home/user/workspace/repo/activemodel/lib/active_model/attribute_mutation_tracker.rb#L156-L188) (`saved_changes?` → false, `saved_changes` → `{}`). Next dirty check builds a new `AttributeMutationTracker` over the **new** `@attributes`. That is the same pair `clear_changes_information` nils; [test_reload_should_clear_changed_attributes](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb#L410-L416) asserts `changed?` is false after reload.

If `_find_record` raises, `tap` never runs and `@attributes` is never replaced.

[test_find_via_reload](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb#L1687-L1696) is the persistence-flag case: `Post.new; post.id = 1; post.reload` queries, loads the row, and `new_record?` becomes false.

## Edge cases

I ran the existing tests above (8 runs, 33 assertions, all pass) and a one-off probe against the same fixtures. Object-id / SQL / exception results below are from that probe.

**Unsaved local attribute change.** Queries. Same object. In-memory write discarded.

Probe: `topic.title = "LOCAL UNSAVED"` (`changed?` true, `object_id` 7448) → `reload` issues `SELECT "topics".* ... WHERE "topics"."id" = ?` → title `"The First Topic"`, `changed?` false, `returned.equal?(topic)` true. Matches [test_reload](file:///home/user/workspace/repo/activerecord/test/cases/base_test.rb#L1321-L1328) (other instance’s save becomes visible) and the dirty test.

**`saved_changes` after a prior save.** Queries. Previous-save changelog wiped.

Probe: after `save!`, `saved_changes?` true and `saved_changes` had `catchphrase` `["ahoy", "yar"]`. After `reload`: `saved_changes?` false, `saved_changes` `{}`, `@mutations_before_last_save` is `NullMutationTracker`, `@mutations_from_database` is `nil`. Save-time `saved_changes` itself is tested in [dirty_test](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb#L882-L904); the wipe is the Dirty override, not Persistence.

**Row hidden by default scope vs explicit scoping.**

| Setup | Queries? | Result |
|---|---|---|
| Ordinary `default_scope { where(mentor_id: 1) }`, row’s `mentor_id` updated to 99 | Yes, **unscoped** `WHERE id = ?` | Succeeds; in-memory `mentor_id` becomes 99 |
| `default_scope ..., all_queries: true`, same hidden row | Yes, `WHERE mentor_id = ? AND id = ?` | **Raises `RecordNotFound`** |
| Same all-queries model, `reload(unscoped: true)` | Yes, `WHERE id = ?` | Succeeds; `mentor_id` 99 |
| `Model.where(salary: 80000).scoping { reload }` | Yes, all-queries default only | No `salary` predicate ([test](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb#L340-L348)) |
| `scoping(all_queries: true)` | Yes | Default **and** current `WHERE` ([test](file:///home/user/workspace/repo/activerecord/test/cases/scoping/default_scoping_test.rb#L351-L359)) |

Ordinary default scopes hide `find`/`all` but not `reload`. Only `all_queries: true` (or `global_current_scope`) can make reload miss the row.

**Deleted row.** Queries, then **raises `RecordNotFound`**. Internals are not replaced (raise happens inside `_find_record`, before the ivar copies and before Dirty’s `tap`). Probe used `Topic.delete(id)` then `reload`; message was `Couldn't find Topic with [WHERE "topics"."id" = ?]`. Same raise is asserted for `delete_all` victims in [delete_all_test](file:///home/user/workspace/repo/activerecord/test/cases/relation/delete_all_test.rb#L79).

**Already-loaded association whose DB contents changed.** Parent `reload` queries **only the parent**. The old association cache is replaced (usually with `{}`). Accessing the association later issues a new `SELECT` and sees DB changes. Parent identity is unchanged; association records are new objects.

Probe: `post.comments` cached (2 rows). `update_all` plus an extra comment. In-memory collection still 2 / old body. `post.reload` SQL was only `SELECT "posts".* WHERE id = ?`. After reload `association_cached?(:comments)` was false, cache keys `[]`. Then `post.comments` ran `SELECT "comments".* WHERE post_id = ?` and returned 3 rows with `"CHANGED IN DB"` / `"brand new"`.

If the parent is `strict_loading?`, those already-cached associations are preloaded on `fresh_object` and copied back, so the next read does not lazy-load (and would not pick up mid-reload association-table changes unless that preload query sees them).

**Identity vs replaced state.** `reload` returns `self`. Probe: `object_id` unchanged; `@attributes` object_id changed; `@association_cache` object_id changed; `@new_record` and `@previously_new_record` false. The `fresh_object` from `find_by!` is discarded after its ivars are stolen.
