`after_commit` does not run when a row is written. It runs when a **real transaction boundary** finishes, and only for records that both **enrolled** in that transaction and still **look like a create, update, or destroy** at that boundary.

### Registration: `on:` is an action predicate, not a second callback list

[`after_commit`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L284-L287) / [`after_rollback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L316-L318) install Active Support callbacks on `:commit` and `:rollback`. The shortcuts (`after_create_commit`, `after_update_commit`, `after_destroy_commit`, `after_save_commit`) only inject an `on:` option.

[`set_options_for_callbacks!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L341-L356) (and [`set_callback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L323-L337) again for `:commit`/`:rollback`) turn `on:` into an `:if` proc:

```ruby
options[:if] = [
  -> { transaction_include_any_action?(fire_on) },
  *options[:if]
]
```

Allowed actions are only `[:create, :destroy, :update]` ([`ACTIONS`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L7)). Anything else raises, which [`test_after_commit_callbacks_should_validate_on_condition`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L463-L466) asserts.

The filter is evaluated **later**, on the instance, from flags captured during the transaction:

```545:555:activerecord/lib/active_record/transactions.rb
def transaction_include_any_action?(actions)
  actions.any? do |action|
    case action
    when :create
      persisted? && @_new_record_before_last_commit
    when :update
      !(@_new_record_before_last_commit || destroyed?) && _trigger_update_callback
    when :destroy
      _trigger_destroy_callback
    end
  end
end
```

`on: [:create, :update]` means **any** of those actions, not “both happened.” An unfiltered `after_commit` has no `on:` predicate and runs whenever `committed!` actually runs callbacks.

Same filter name is deduplicated by Active Support. Two `after_commit :do_something` definitions collapse; `on:` on one definition does not. That is why the docs recommend `on:` over stacking `after_create_commit` / `after_save_commit` with the same method.

### Enrollment: persistence opens or joins a transaction, then registers the record

`save` / `save!` / `destroy` all go through [`with_transaction_returning_status`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L428-L447):

1. Open an implicit transaction, or join the one already open.
2. [`add_to_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L558-L563) → [`connection.add_transaction_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L561-L563) → [`Transaction#add_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L198-L207).
3. [`remember_transaction_record_state`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L467-L483) snapshots `@new_record` on first enrollment and sets `@_new_record_before_last_commit` from that snapshot.
4. `yield` the real persist. False status raises `ActiveRecord::Rollback`.

Create/update/destroy then set the trigger flags:

- create: `@_new_record_before_last_commit` stays true from the original `@new_record` snapshot
- update: [`@_trigger_update_callback`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L942-L945) when a row is updated (or there were no attributes to write)
- destroy: [`@_trigger_destroy_callback ||= persisted? && destroy_row > 0`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L424) **before** `@destroyed = true`

[`trigger_transactional_callbacks?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L449-L452) is the gate used at the boundary:

```ruby
(@_new_record_before_last_commit || _trigger_update_callback) && persisted? ||
  _trigger_destroy_callback && destroyed?
```

Failed validations never persist, so this is false. [`test_dont_call_any_callbacks_after_transaction_commits_for_invalid_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L121-L129) shows empty history for both commit and rollback. The record may still be enrolled; it just is not a candidate to run callbacks.

Flags are cleared after `committed!` so they cannot leak into the next transaction ([`test_dont_call_after_commit_on_update_based_on_previous_transaction`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L147-L155)).

### Nested transactions: join vs `requires_new`

[`DatabaseStatements#transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L496-L523) is the fork:

```ruby
if !requires_new && current_transaction.joinable?
  yield current_transaction.user_transaction   # no new Transaction
else
  within_new_transaction(...)                  # Real / Savepoint / RestartParent
end
```

[`begin_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L529-L555) sets one bit that later decides **when** commit callbacks run:

```ruby
run_commit_callbacks = !current_transaction.joinable?
```

| Kind | SQL | `@run_commit_callbacks` when parent is joinable |
|---|---|---|
| Outer real txn | `BEGIN` | true (`NullTransaction` is not joinable) |
| Nested join | none; same `Transaction` | n/a |
| Nested `requires_new` | savepoint (or restart-parent if the parent is still restartable) | **false** |

So a joined inner block is not a callback boundary. A `requires_new` block is a rollback boundary, but **not** a commit-callback boundary while the parent is still joinable.

Test fixtures wrap examples in a **non-joinable** transaction. In that setting even a plain `Model.transaction` opens a savepoint with `run_commit_callbacks: true`, which is why `after_commit` fires inside tests. Several suites set `use_transactional_tests = false` to avoid that.

### Commit and rollback propagation

[`within_new_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L645-L673): exception → rollback; success → commit. `ActiveRecord::Rollback` is swallowed by [`transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L520-L521).

**Rollback** ([`rollback_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L633-L641)): SQL rollback / `ROLLBACK TO SAVEPOINT` first, then [`rollback_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L267-L285). Rollback **always** runs record `after_rollback` and transaction-level `after_rollback` callbacks. It does not consult `@run_commit_callbacks`.

[`SavepointTransaction#full_rollback?`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L467) is false, so [`rolledback!(force_restore_state: false)`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L414-L421) only restores instance state at nesting level 1. The inner record is restored; the outer transaction keeps going.

**Commit** ([`commit_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L616-L629)):

1. [`before_commit_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L287-L309) — only if `@run_commit_callbacks`
2. pop the stack
3. SQL `COMMIT` or `RELEASE SAVEPOINT`
4. [`commit_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L311-L337)

```diagram
┌─────────────────────────────┐
│ Outer RealTransaction       │
│ run_commit_callbacks: true  │
│ records: [outer, inner*]    │
└──────────────┬──────────────┘
               │ requires_new
               ▼
┌─────────────────────────────┐
│ SavepointTransaction        │
│ run_commit_callbacks: false │
└──────────────┬──────────────┘
               │
     ┌─────────┴──────────┐
     │ success            │ rollback (rescued)
     ▼                    ▼
 RELEASE SAVEPOINT     ROLLBACK TO SAVEPOINT
 add_record → parent   rollback_records NOW
 append_callbacks      (after_rollback on inner)
     │                    │
     ▼                    ▼
 outer commit/rollback  outer still open
 runs forwarded work
```

On savepoint **success**, records and transaction-level callbacks are forwarded onto the parent. They do not run yet. [`test_only_call_after_commit_on_top_level_transactions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L241-L251) and [`test_transaction_after_commit_callback`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L101-L125) both assert history stays empty until the outer block exits.

On savepoint **rollback**, inner `after_rollback` runs immediately. The outer record is untouched. [`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L329-L353) is the regression for that split: outer gets `after_commit`, inner gets `after_rollback`. Transaction-level `after_rollback` on the **outer** object is not run by an inner savepoint rollback ([`test_transaction_after_rollback_callback`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L167-L183)).

### Execution at the outer boundary

At a boundary that **does** run callbacks, [`prepare_instances_to_run_callbacks_on`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L361-L382) picks **one** instance per database row.

Enrollment uniqueness is by object id (`uniq(&:__id__)`), so the same Ruby object saved twice is one record. Candidate selection is by Active Record equality ([`==` / `hash` on class+id](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L645-L662)), so two in-memory objects for the same row collide.

Then [`committed!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L403-L409) / [`rolledback!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L414-L421) run `_run_commit_callbacks` / `_run_rollback_callbacks`, and each callback’s `on:` proc reads the flags **on that chosen instance**.

Non-chosen enrolled instances still get `committed!(should_run_callbacks: false)` so their transaction state is cleared without firing hooks.

### Concrete cases

#### 1. Create then update of the same instance in one transaction

First `save` snapshots `new_record: true` and sets `@_new_record_before_last_commit`. The second `save` does not replace that snapshot (`@_start_transaction_state ||=`). `_trigger_update_callback` becomes true, but the `:update` predicate requires `!@_new_record_before_last_commit`.

At the outer commit only **create** matches. `on: :update` does not. `on: [:create, :update]` does, because `:create` is enough. Unfiltered `after_commit` also runs.

[`test_only_call_after_commit_on_create_and_doesnt_leaky`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L224-L232) does this via `after_create { save! }`: one transaction, create then update, and only `on: :create` is observed. A later `save!` in a **new** transaction does not re-fire create.

A `save!` **inside** `after_create_commit` is a different story: `committed!` has already set `@_committed_already_called`, so the nested save records `@_new_record_before_last_commit = false` and [`test_save_in_after_create_commit_wont_invoke_extra_after_create_commit`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L217-L222) sees `[:commit_on_create, :commit_on_update]`.

#### 2. Record saved only in an inner **joined** transaction

No new `Transaction` object. `add_record` goes on the outer list. Callbacks wait for the outer boundary.

If the outer commits, that inner-only record’s `after_commit` runs there, with the action of that save (`:create` or `:update`). If the outer rolls back, its `after_rollback` runs with the same action filter.

An `ActiveRecord::Rollback` raised in the inner joined block is swallowed and **does not** roll back the outer transaction (documented in [`ClassMethods`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L117-L147)). The inner save stays enrolled and will `after_commit` with the outer.

#### 3. Rollback of an inner `requires_new` block, rescued by the outer block

Savepoint rolls back; inner record runs `after_rollback` immediately, filtered by the action that happened **inside the savepoint**. Outer records are not in that savepoint’s `@records`.

When the outer later commits, only the outer record’s `after_commit` runs. Evidence: [`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L329-L353) (`@first` commits, `second` rolls back). Repeating that pattern twice on the **same** object adds two inner rollbacks plus one outer commit ([`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint_when_release_savepoint_fails`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L355-L376)).

#### 4. Outer rollback after an inner savepoint **release**

Inner `requires_new` succeeds: savepoint is released, records/callbacks move to the parent, **no** `after_commit` yet ([`test_only_call_after_commit_on_top_level_transactions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L241-L251)).

Outer then rolls back: forwarded records run `after_rollback`, not `after_commit`. SQL already released the savepoint; the **real** `ROLLBACK` undoes those writes. Action filters still reflect the inner save (create/update/destroy), because those flags live on the record, not on the savepoint.

#### 5. Destroy of a newly created record

Never persisted, then `destroy`: `@_trigger_destroy_callback` stays false (`persisted?` was false). [`trigger_transactional_callbacks?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L449-L452) is false. [`test_no_after_commit_on_destroy_after_transaction_commits_for_destroyed_new_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L207-L213) expects `[]` — no `after_commit` and no `after_rollback` action.

Create **then** destroy of that same instance in one transaction is different: destroy sees a persisted row, sets `@_trigger_destroy_callback`, then `@destroyed = true`. At the boundary `persisted?` is false, so `:create` does not match; `:destroy` does. Observable filters: unfiltered `after_commit` / `after_rollback`, and `on: :destroy` (including `on: [:create, :destroy]`). Not `on: :create`, not `on: :update`.

#### 6. Multiple in-memory instances of the same database row

Two objects with the same class and id hash to one candidate.

Modern Rails (`load_defaults 7.1+`) sets [`run_commit_callbacks_on_first_saved_instances_in_transaction = false`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L283): **last** enrolled instance wins, with two overrides in [`prepare_instances_to_run_callbacks_on`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L361-L382):

- A later non-destroyed instance cannot replace an earlier **destroyed** candidate.
- `@_new_record_before_last_commit` is copied forward, so a create followed by an update on a **reload** still runs **create** callbacks on the last instance.

[`CallbacksOnMultipleInstancesInATransactionTest`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L903-L1024) pins this:

| Sequence in one txn | Default (last instance) | Old config (first instance) |
|---|---|---|
| create A, find+update to B | `Created (title = "B")` | `Created (title = "A")` |
| update to two, update to three | `Updated (title = "three")` | `Updated (title = "two")` |
| update then destroy | `Destroyed` on the destroy instance | `Updated` on the first saver |
| destroy then update on another instance | `Destroyed` (destroy sticks) | `Destroyed` (first wins anyway) |

Only the chosen instance’s callbacks are observable. The other instance still has its in-memory attributes, but `committed!(should_run_callbacks: false)` skips its hooks.

### Callback order, and which `on:` filters you can see

`before_commit` always runs in definition order, **before** SQL commit, and only at a `run_commit_callbacks` boundary.

`after_commit` / `after_rollback` order depends on [`ActiveRecord.run_after_transaction_callbacks_in_order_defined`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L358-L364) (true from Rails 7.1). When true, after callbacks are registered with inverted `prepend` so they run in definition order; `prepend: true` then runs **earlier**. [`CallbackOrderTest`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L694-L754):

- create, flag true: `[1, 2, "prepend 2", "prepend 1", 3, 4, "save", "create"]`
- update, flag true: same prefix, then `"save", "update"`
- destroy, flag true: `"destroy"` instead of save/create
- rollback, flag true: `["rollback1", "rollback2"]`
- flag false: after callbacks reverse (`"create", "save", 4, 3, "prepend 1", "prepend 2"`)

Action filters at that moment — one commit/rollback, not one per inner save:

| What actually happened on the chosen instance | `on: :create` | `on: :update` | `on: :destroy` | `on: [:create, :update]` | unfiltered |
|---|---|---|---|---|---|
| new record saved | yes | no | no | yes | yes |
| existing record saved | no | yes | no | yes | yes |
| persisted record destroyed | no | no | yes | no | yes |
| create then update, same object | yes | no | no | yes | yes |
| create then destroy, same object | no | no | yes | no | yes |
| never-persisted destroy | no | no | no | no | no |
| inner joined save, outer commit | as above | as above | as above | as above | as above |
| inner `requires_new` rolled back | inner `after_rollback` only, same action table | | | | |
| inner savepoint released, outer rolled back | forwarded record: `after_rollback` with that action | | | | |
| two instances, last-wins create+update | create on last instance (flag copied) | no | no | yes | yes |

[`test_after_commit_on_multiple_actions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L614-L626) is the standalone-action version of that table: create fires every callback whose `on:` list includes `:create`, in definition order.

The next place to look if this misfires is almost always “which transaction object did `add_record` land on?” and “which instance did `prepare_instances_to_run_callbacks_on` keep?” — not whether the SQL write itself succeeded.
