Reject appending before the strict check. Strict `add` is documented and implemented as raise-instead-of-add, not add-then-raise.

```341:354:activemodel/lib/active_model/errors.rb
    def add(attribute, type = :invalid, **options)
      attribute, type, options = normalize_arguments(attribute, type, **options)
      error = Error.new(@base, attribute, type, **options)

      if exception = options[:strict]
        exception = ActiveModel::StrictValidationFailed if exception == true
        raise exception, error.full_message
      end

      @errors.append(error)

      error
    end
```

The rdoc is explicit: `:strict` raises **instead of adding**, and after that raise `person.errors.messages # => {}`. I ran that path: `add(:name, :invalid, strict: true)` raises `ActiveModel::StrictValidationFailed` with `"Name is invalid"`, leaves `errors.messages` as `{}`, and `added?(:name, :invalid)` is false. A later strict raise also leaves preexisting errors untouched (`size` stays 1).

Exception class and message do not depend on collection membership. `true` still maps to `ActiveModel::StrictValidationFailed`; any other class is raised as-is with `error.full_message`. `test_strict_validation_error_message` pins `"Title can't be blank"`; `test_strict_validation_custom_exception` pins `CustomStrictValidationException`. Those would still pass after this change, so they are not a reason to accept it.

Collection mutation is the break. Appending first means a rescued strict `add` leaves the `ActiveModel::Error` in `@errors`. That contradicts the documented empty collection, makes `added?` true, and poisons later `valid?` / error inspection. Validators all funnel through this method (`PresenceValidator` does `record.errors.add(..., **options)`), so every `strict: true` / `validates!` failure would start leaving errors behind.

Normal `add` already returns the `ActiveModel::Error` after append (`test "add creates an error object and returns it"`). The strict path never returns; rescue does not get that return value. Callers who want the object after rescue should put it on the exception, not mutate the collection as a side effect of `raise`.

Custom strict classes have the same contract: `strict: NameIsInvalid` raises `NameIsInvalid` with `"Name is invalid"` and still leaves `messages` as `{}`. Those classes are not required to wrap the `Error`, so appending is not a supported inspection API for them either.

Keep the raise-before-append order.
