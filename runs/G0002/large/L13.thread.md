## Assistant

**Problem frame:** Rails maintainers and test/diagnostic authors need to watch notifications only for one block of work. Today that path is a second-class add-on to a long-running subscribe API: they must pre-build a callback, pick a pattern and timestamp mode, and trust cleanup. That is easy to get wrong and is copied into every helper. After the change, they should be able to observe a slice of events for a block as clearly as they subscribe for process lifetime, without changing long-running `subscribe` / `unsubscribe` or callback arities.

This brief specifies desired *behavior*. It does not choose types, classes, algorithms, or code changes.

### Who hurts, and why it matters

The actor is someone writing a test helper, an app test, or a diagnostic around a code path that already calls `ActiveSupport::Notifications.instrument`.

They already have a long-running API: `subscribe`, `monotonic_subscribe`, and `unsubscribe`. Temporary observation exists as [`subscribed`](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L332-L337), documented as “subscribe while a block runs” and auto-unsubscribe ([docs](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L159-L189)). Framework tests already depend on it: [`capture_notifications`](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L81-L89), Active Record query assertions, and `capture_sql`.

Pain today:

- **Callback-first, block-second.** `subscribe` takes a block. `subscribed` requires a callable *and* the observed block. Helpers reassemble that each time (`->(n) { notifications << n }`, `SQLCounter.new`, and similar).
- **A warned-against path.** Docs say the framework is designed for long-running subscribers and that temporary use wipes internal caches ([warning](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L164-L167)). Test/diagnostic use is exactly temporary, so authors work against the stated design.
- **Easy to leak or miss events.** Matching, timestamp mode, nested start/finish, payload mutation, and exceptions are real rules. If unsubscription or arity is wrong, tests see later events, drop inner events, or mis-time durations.

Hypothesis (not a measured product metric): most misuse is in tests and one-off diagnostics, not production request subscribers. If that is wrong, the “test and diagnostic tooling” frame should be dropped.

### Desired observable outcomes

1. **Scoped observation.** A test/diagnostic author can watch matching events only while a chosen block runs, then see no further deliveries from that observation.
2. **Same matching rules.** Exact string, regexp, and “all events” mean the same as they do today.
3. **Same timestamps.** Default observation still reports wall-clock `Time`. Opting into monotonic still reports `Float` start/finish for five-argument callbacks.
4. **Same callback shapes.** Existing one-argument Event callbacks and five-argument callbacks keep working for both temporary observation and long-running subscribe.
5. **Nested work stays intelligible.** An outer event that wraps an inner event still notifies inner-then-outer. Payload edits made during the instrumented block are visible. An observer attached only around the finish of an already-started event still does not receive that event.
6. **Failures stay visible and contained.** If the observed block raises, observers still see the exception-bearing event, the exception still surfaces to the caller, and the temporary observation does not outlive the block.
7. **Long-running API unchanged.** Process-lifetime `subscribe` / `monotonic_subscribe` / `unsubscribe` keep today’s manual lifecycle, name-based unsubscribe, and regexp leftovers.

### Non-goals

- Changing long-running `subscribe` / `unsubscribe` behavior, return values, or when a subscriber object is required.
- Changing callback arity rules (Event vs five-tuple vs `start`/`finish` evented objects).
- Changing exception payload keys or swallowing the original exception.
- Making temporary observation the normal production subscriber.
- Expanding matching beyond String, Regexp, and empty/all.
- Redesigning instrumentation, payload shape, or Rails hook names.
- Performance work except as it would change *observable* subscribe/unsubscribe/event behavior (the cache-wipe warning stays a documented cost unless a later brief reopens it).

### Compatibility constraints

- Call sites that pass a callable into `subscribed` and a block to observe must keep working, including [`capture_notifications`](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/notification_assertions.rb#L87) and Active Record SQL counters.
- `monotonic: false` remains the default; `monotonic: true` remains the opt-in for monotonic start/finish.
- `unsubscribe` by subscriber object vs by string name stays distinct, including regexp subscribers that remain matched on other names.
- Authors must not have to change working one-arg or five-arg callbacks to adopt easier temporary observation.

### Representative examples

Required cases, not an exhaustive catalog.

**Exact name, then silence**

Given a temporary observer on `"foo"`, when the block instruments `"foo"`, `"foofoo"`, `"foo"`, the observer records two `"foo"` events. When `"foo"` is instrumented after the block, the record is unchanged.

**All events, then silence**

Given a temporary observer with no pattern, when the block instruments `"foo"`, `"foofoo"`, `"foo"`, the observer records all three. After the block, further events are absent.

**Regexp (via the tested helper path)**

Given capture of `/post\./`, when the block instruments `"post.submitted"`, the captured list has that one event and its payload. A non-matching name during the same style of capture is absent.

**Wall-clock vs monotonic**

Given a five-argument callback without `monotonic: true`, start and finish are `Time`. With `monotonic: true`, they are `Float`. A later instrument of the same name, outside the block, does not overwrite those classes.

**Nested instrument + payload mutation**

Given an observer of all events and:

```text
instrument "awesome", payload: "notifications" do
  instrument "wot", payload: "child" { }
end
```

the observer first sees `"wot"` with `{ payload: "child" }`, then `"awesome"` with `{ payload: "notifications" }`. If the inner block writes extra keys into the yielded payload hash (including nested hashes), those keys are present on the delivered event.

**Nested temporary observers around split start/finish**

Given outer observation of `"foo"`, a handle that `start`s `"foo"` inside the outer block, and inner observation of `"foo"` only around `finish`: the outer observer receives the event; the inner observer receives none.

**Raising observed block**

Given temporary observation around `instrument("awesome") { raise "FAIL" }`: the observer still receives one event whose payload includes `exception: ["RuntimeError", "FAIL"]` and the exception object; the caller still sees `RuntimeError`; later `"awesome"` events are not delivered to that observation.

**Counterexample: long-running subscribe is not temporary**

Given `subscribe("render") { ... }` with no `unsubscribe`, when `"render"` fires after the original code path returns, the callback still runs. Temporary observation must not start behaving like this. Manual `unsubscribe(subscriber)` and `unsubscribe("render")` must keep stopping those long-running callbacks as they do today.

### Acceptance signals

**Success looks like**

- A maintainer can add or read a test/diagnostic that observes notifications for one block without a leftover subscription on the next example.
- Exact, regexp, and all-event examples above remain true.
- Nested and raising examples remain true.
- Existing one-arg and five-arg subscribers, including production-style `subscribe` / `unsubscribe`, need no rewrite.
- Query-count and `capture_notifications` style helpers still see only events from the block they wrap.

**Investigate the implementation if**

- Events from after the block appear in the observation.
- A raising block skips the exception event, swallows the exception, or leaves observation on.
- Inner events disappear, or payload edits made in the instrumented block are missing.
- `monotonic: true` still yields `Time`, or the default yields `Float`.
- One-arg Event callbacks start receiving five arguments, or five-arg callbacks start receiving an Event.

**Reconsider the problem frame if**

- Authors still have to pre-build a callback and remember `ensure`-style cleanup to get a correct slice (usability did not move).
- The change is mainly used on hot production paths despite the cache-wipe warning (the “test and diagnostic” audience was wrong).
- People needed different matching, different exception payload, or a change to long-running subscribe—the constraint set was the real pain.

### Open questions

- Is the pain the **callback-first calling shape**, the **documented “use sparingly” warning**, or **missing guidance** for nested/raising blocks? The outcomes above treat all three as in scope for *experience*; only the first two would change what authors type.
- Must regexp matching gain a first-class `subscribed` example, or is the existing `capture_notifications(/.../)` path enough evidence?
- Should temporary observation remain explicitly discouraged in production, or only documented as a cost?

This is the current shared understanding of the problem and desired behavior, not a build plan. Correct the frame if temporary observation was meant to become a production-default subscriber, or if long-running arities were in play after all.
