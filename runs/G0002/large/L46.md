**Request changes.** Do not treat independent `master.key` fallback as the product contract.

The claimed one-way fallback already exists in [`credentials_defaults`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L683-L690): content and key are chosen by separate existence checks. Environment content without an environment key does select `config/master.key`. That is only half of what the independent checks do, and the other half is a boot-breaking mismatch.

I executed the pairing matrix against `ActiveSupport::EncryptedConfiguration` using this selection logic. Existing railties tests do not cover the crossed states.

## What the current defaults actually do

```683:690:railties/lib/rails/application/configuration.rb
        def credentials_defaults
          content_path = root.join("config/credentials/#{Rails.env}.yml.enc")
          content_path = root.join("config/credentials.yml.enc") if !content_path.exist?

          key_path = root.join("config/credentials/#{Rails.env}.key")
          key_path = root.join("config/master.key") if !key_path.exist?

          { content_path: content_path, key_path: key_path }
        end
```

[`Rails.application.credentials`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L605-L606) then loads `config.credentials.content_path` with `config.credentials.key_path`. [`EncryptedFile#key`](file:///home/user/workspace/repo/activesupport/lib/active_support/encrypted_file.rb#L51-L54) reads `ENV["RAILS_MASTER_KEY"]` first, then the selected key file. `config.require_master_key` defaults to `false` and is not enabled in this checkout’s production template.

Until 2023 this was a coupled pair keyed off environment-content existence (env files together, otherwise global files together). Independent fallback was a side effect of later wiring commands through `config.credentials.*`.

| Files present | Result |
|---|---|
| Env content + env key | Env pair; decrypts |
| Env content encrypted with env key, only `master.key` | Paths become env content + `master.key`; `InvalidMessage` |
| Env content encrypted with `master.key`, no env key | Claimed fallback works |
| Env content, no keys, `require_master_key = false` | Empty credentials (`""` / `{}`) |
| Env content, no keys, `require_master_key = true` | `MissingKeyError` naming `config/master.key` and `RAILS_MASTER_KEY` |
| Env content + wrong env key | `InvalidMessage`; no retry of `master.key` |
| Global content + `master.key` | Global pair; decrypts |
| Global content + stale env key | **Bug:** `credentials.yml.enc` + `<env>.key` → `InvalidMessage` |
| `RAILS_MASTER_KEY` set | Always wins; wrong ENV does not fall back to the file |
| Explicit `content_path` / `key_path` | Authoritative; setting both is unambiguous |
| Short/malformed key | `ArgumentError` (“key must be 16 bytes”) on read; `InvalidKeyLengthError` on write |

AES-GCM fails closed. A wrong key does not leak plaintext. The damage is availability and isolation, not disclosure.

## Blocking defects

**1. Reverse pairing.** Independent checks mean a leftover `config/credentials/production.key` is preferred even when only global `config/credentials.yml.enc` exists. Deleting an environment override can fail production boot with `InvalidMessage`. Coupled selection would still decrypt with `master.key`.

**2. `credentials:edit --environment` disagrees with runtime / show / fetch.** Show, fetch, and diff inherit `credentials_defaults`. Edit still force-pairs env content with an env key:

```21:25:railties/lib/rails/commands/credentials/credentials_command.rb
        if environment_specified?
          @content_path = "config/credentials/#{environment}.yml.enc" unless config.overridden?(:content_path)
          @key_path = "config/credentials/#{environment}.key" unless config.overridden?(:key_path)
        end
```

Reproduced sequence:

1. `production.yml.enc` encrypted with `master.key`; no `production.key`.
2. `credentials:show --environment production` decrypts.
3. `credentials:edit --environment production` creates a random `production.key`, then cannot decrypt.
4. Runtime later prefers that leftover key and fails.

That split is extra evidence the independent fallback is accidental, not an intended pair.

## Production vs development

- Development/test can synthesize `secret_key_base` via `tmp/local_secret.txt` when credentials are empty and `require_master_key` is false.
- Production still needs a real `secret_key_base`; missing credentials become `ArgumentError` on boot.
- `require_master_key = true` aborts in the `active_support.require_master_key` initializer as soon as the key is missing. A present but wrong key still raises `InvalidMessage` when credentials are read, in any environment.
- Reusing `master.key` for environment files enlarges that key’s blast radius and weakens fail-closed environment isolation. Do not add decrypt-and-retry: an existing wrong environment key must keep raising.

## Corrected tiny diff

Keep the useful directional fallback. Do not restore 2018 strict coupling (that would break apps that already encrypt env content with `master.key`). Do not ship independent checks.

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")

  if content_path.exist?
    key_path = root.join("config/credentials/#{Rails.env}.key")
    key_path = root.join("config/master.key") unless key_path.exist?
  else
    content_path = root.join("config/credentials.yml.enc")
    key_path = root.join("config/master.key")
  end

  { content_path: content_path, key_path: key_path }
end
```

Also change `credentials:edit --environment`: use the same selected key as runtime when the env content file already exists; create an environment key only when creating new env content. Explicit `config.credentials.*` overrides stay authoritative. Update [`configuring.md`](file:///home/user/workspace/repo/guides/source/configuring.md#L325-L343), which currently documents the independent wording.
