`after_commit` does not run when a record is saved. It runs later, and only if that record is still enrolled on a transaction that actually commits at the outer boundary. `on:` does not pick the persistence method that just ran. It filters against flags the instance accumulated for the whole transaction.

```diagram
save / destroy
  with_transaction_returning_status
    add_to_transaction ──▶ current Transaction.records
    remember_transaction_record_state
    INSERT / UPDATE / DELETE  (sets action flags)

nested transaction(requires_new: true) commits
  RELEASE SAVEPOINT
  records + txn callbacks move to parent     ← no after_commit

nested savepoint rolls back
  ROLLBACK TO SAVEPOINT
  after_rollback now                         ← inner boundary

outer joinable transaction commits
  before_commit → SQL COMMIT → after_commit  ← outer boundary
```

## Registration: `on:` becomes an `:if`

[`after_commit`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L284-L287) / [`after_rollback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L316-L318) register on the `:commit` / `:rollback` chains. Shortcuts just force `on:`:

- `after_create_commit` → `on: :create`
- `after_update_commit` → `on: :update`
- `after_destroy_commit` → `on: :destroy`
- `after_save_commit` → `on: [:create, :update]`

[`set_options_for_callbacks!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L341-L356) (and [`set_callback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L322-L336) for runtime `set_callback`) prepends:

```ruby
-> { transaction_include_any_action?(fire_on) }
```

Allowed actions are only `[:create, :destroy, :update]`. `:save` and string `"create"` raise ([`test_after_commit_callbacks_should_validate_on_condition`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L463-L466)).

No `on:` means the callback is not action-filtered. If the instance is chosen to run transactional callbacks, an unfiltered `after_commit` fires for create, update, and destroy.

Same filter name is deduplicated by Active Support. `after_commit :do_something` plus `after_create_commit :do_something` is one callback. `on: [:create, :update]` on a single registration is not the same as two separately named callbacks.

## Enrollment and action flags

[`save`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L382-L384) / [`destroy`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L378-L380) wrap persistence in [`with_transaction_returning_status`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L430-L447):

1. Open or join a transaction.
2. [`add_to_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L558-L563) → [`current_transaction.add_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L198-L207).
3. Snapshot state in [`remember_transaction_record_state`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L466-L483).
4. Run the INSERT/UPDATE/DELETE.
5. Raise `ActiveRecord::Rollback` if the persistence method returned false (failed validation never sets action flags, so neither commit nor rollback callbacks run: [`test_dont_call_any_callbacks_after_transaction_commits_for_invalid_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L121-L133)).

The snapshot is taken once per open transaction (`||=`) and then only a nesting `level` increments. `@_new_record_before_last_commit` is copied from that first snapshot’s `new_record`, unless `committed!` is already running (that path is how an `after_create_commit` that saves again becomes an update: [`test_save_in_after_create_commit_wont_invoke_extra_after_create_commit`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L214-L221)).

Action flags come from persistence, not from `on:`:

| Flag | Set when |
|---|---|
| `@_new_record_before_last_commit` | first enrollment in this txn saw `@new_record` |
| `@_trigger_update_callback` | [`_update_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L937-L952) ran |
| `@_trigger_destroy_callback` | [`destroy`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L416-L424) deleted a persisted row (`persisted? && destroy_row > 0`) |

At fire time, [`transaction_include_any_action?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L544-L556) is:

```ruby
:create  → persisted? && @_new_record_before_last_commit
:update  → !(@_new_record_before_last_commit || destroyed?) && _trigger_update_callback
:destroy → _trigger_destroy_callback
```

Create and update are mutually exclusive for one instance: if the transaction still thinks the row was new, `:update` is false even if an UPDATE also ran.

[`trigger_transactional_callbacks?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L449-L452) is the gate for being a candidate at all:

```ruby
(@_new_record_before_last_commit || _trigger_update_callback) && persisted? ||
  _trigger_destroy_callback && destroyed?
```

## Joinable nesting vs `requires_new`

[`ConnectionAdapters::DatabaseStatements#transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L496-L527):

```ruby
if !requires_new && current_transaction.joinable?
  yield current_transaction.user_transaction   # join: no new stack frame
else
  within_new_transaction(...)
end
```

A joined inner `transaction` is a Ruby block around the same `Transaction`. Saves enroll on the outer object. An inner `ActiveRecord::Rollback` is swallowed by that inner `rescue` and does **not** roll back the outer work ([docs and](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L396-L421) [`test_no_savepoint_in_nested_transaction_without_force`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L910-L929)).

`requires_new: true` always pushes a child. [`TransactionManager#begin_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L529-L556) sets:

```ruby
run_commit_callbacks = !current_transaction.joinable?
```

Inside a joinable outer transaction that is false. The child is a [`SavepointTransaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L417-L468) once the parent is dirty, or a [`RestartParentTransaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L387-L414) if the parent can still be restarted. Both have `full_rollback? == false`. Neither runs `after_commit` when the child completes.

```diagram
┌─ RealTransaction  joinable  run_commit_callbacks=true ─┐
│  records: [topic]                                      │
│                                                        │
│   ┌─ SavepointTransaction  run_commit_callbacks=false ┐│
│   │  save / rollback here                              ││
│   │  commit: move records + callbacks to parent        ││
│   │  rollback: after_rollback immediately              ││
│   └────────────────────────────────────────────────────┘│
│                                                        │
│  SQL COMMIT / ROLLBACK is the only after_commit home   │
└────────────────────────────────────────────────────────┘
```

[`commit_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L616-L627) order:

1. `before_commit_records` (only if `@run_commit_callbacks`)
2. pop the stack
3. SQL `COMMIT` or `RELEASE SAVEPOINT`
4. `commit_records`

[`commit_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L308-L338) with `@run_commit_callbacks == false` does not call `committed!` with callbacks. It re-adds each record to `connection.current_transaction` (now the parent) and [`append_callbacks`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L341-L343) any transaction-level blocks. That is why [`test_only_call_after_commit_on_top_level_transactions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L241-L251) sees an empty history until the outer block ends, and why [`Topic.current_transaction.after_commit`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L106-L114) registered inside `requires_new` also waits.

[`rollback_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L629-L638) always SQL-rolls-back first, then [`rollback_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L267-L285). There is no “defer rollback to parent.” Savepoint rollback runs `after_rollback` at that inner boundary. `rolledback!` gets `force_restore_state: full_rollback?`, so a savepoint restores only the innermost snapshot; a real outer rollback restores the original instance state ([`test_nested_transaction_with_new_transaction_applies_parent_state_on_rollback`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L774-L793)).

## Who runs, and in what order

On the outer commit/rollback, [`prepare_instances_to_run_callbacks_on`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L358-L383) walks enrolled records in enrollment order, unique by `__id__` (so two objects that spoof `object_id` still both run: [`test_saving_two_records_that_override_object_id_should_run_after_commit_callbacks_for_both`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L504-L521)).

Candidates are hashed with Active Record identity (`eql?` / `hash` = class + id). Several in-memory objects for one row collapse to one runner:

- Default gem: `run_commit_callbacks_on_first_saved_instances_in_transaction` is `true` — first enrolled instance wins.
- Rails 7.1+ `load_defaults`: that flag is `false` — last instance that still `trigger_transactional_callbacks?` wins, except a later non-destroyed instance cannot replace a destroyed one.

If the earlier candidate was created in this transaction, the later instance receives `@_new_record_before_last_commit = true`, so the runner still sees `:create` even if it only performed an UPDATE.

Then [`committed!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L398-L409) / [`rolledback!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L412-L421) run the chain. Non-chosen duplicates get `should_run_callbacks: false` (state is still cleared). A raise in one record’s `after_commit` skips later records ([`test_after_commit_chain_not_called_on_errors`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L469-L486)).

Per-instance order ([`CallbackOrderTest`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L644-L738)):

- `before_commit` always definition order, and it runs **before** SQL `COMMIT`.
- `after_commit` / `after_rollback` follow `ActiveRecord.run_after_transaction_callbacks_in_order_defined` (false in the gem, true from Rails 7.1). When true, after-callbacks are auto-prepended so they run in definition order; `prepend: true` then inverts that again.
- Matching `on:` filters run as part of that same chain, not as a separate pass. On create with the 7.1 ordering: unfiltered `after_commit`s, then `after_save_commit`, then `after_create_commit`. `after_update_commit` / `after_destroy_commit` stay silent because their `:if` fails.

## The six cases

**1. Create then update of the same instance in one transaction**

```ruby
Topic.transaction do
  record = Topic.create!(title: "A")
  record.update!(title: "B")
end
```

One object, one enrollment identity. The first snapshot still has `new_record: true`, so `@_new_record_before_last_commit` stays true through the UPDATE. At the outer commit:

- observable: unfiltered `after_commit`, `after_save_commit`, `after_create_commit` / `on: :create`
- not observable: `after_update_commit` / `on: :update` (`:update` requires `!@_new_record_before_last_commit`)
- not observable: anything `on: :destroy`

Separate transactions would fire create, then later update ([`test_after_commit_callbacks_with_optimistic_locking`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L581-L586)). The same-transaction collapse is the `@_new_record_before_last_commit` rule, not a second commit.

**2. Record saved only in an inner joined transaction**

```ruby
Topic.transaction do
  Topic.transaction do          # joins; no savepoint
    record.save!
  end
  # history still empty
end
# after_commit here
```

The inner call does not push a `Transaction`. The record is on the outer `RealTransaction`. Callbacks wait for that outer SQL `COMMIT`. Joining does not create a callback boundary.

**3. Inner `requires_new` rolled back, outer rescued and continues**

```ruby
Topic.transaction do
  first.save!                              # outer
  Topic.transaction(requires_new: true) do
    second.save!
    raise ActiveRecord::Rollback           # swallowed
  end
end
```

[`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L329-L353): `second` gets `after_rollback` (and `on: :update` / `:create` matching what that inner save did) **immediately** when the savepoint rolls back. `first` is not in that child, so it is untouched there and gets `after_commit` at the outer commit. `second` gets no `after_commit`. The same split holds for transaction-level `after_rollback` registered on the inner `current_transaction` ([`test_transaction_after_rollback_callback`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L166-L185)).

**4. Outer rollback after an inner savepoint release**

```ruby
Topic.transaction do
  Topic.transaction(requires_new: true) do
    record.save!
  end                                      # RELEASE SAVEPOINT; record moved to parent
  raise ActiveRecord::Rollback
end
```

The inner commit did not run `after_commit`. After the move, the outer rollback runs `after_rollback` with the action filters from that save (`on: :create` if it was a create). In-memory persistence flags are restored because this is a full rollback ([`test_nested_transaction_with_new_transaction_applies_parent_state_on_rollback`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L774-L793)). No `after_commit` is observable.

If the inner savepoint instead fails to release and the manager rolls it back, that is also `after_rollback` for those inner saves, not commit ([`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint_when_release_savepoint_fails`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L355-L378)).

**5. Destroy of a newly-created record**

Never persisted:

```ruby
new_record = Topic.new(...)
new_record.destroy
```

[`test_no_after_commit_on_destroy_after_transaction_commits_for_destroyed_new_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L207-L211): `@_trigger_destroy_callback` stays false because `destroy` only sets it when `persisted? && destroy_row > 0`. History is empty — no `after_commit`, no `after_rollback`, no `on: :destroy`.

Created then destroyed in the **same** open transaction: the instance is `destroyed?`, so `:create` (`persisted? && …`) is false and `:update` is false. `:destroy` is true. Observable: unfiltered `after_commit` / `after_rollback` and `on: :destroy`. Not observable: `on: :create`, even though an INSERT happened in that transaction. Multiple destroys of the same row still produce one destroy callback ([`test_trigger_once_on_multiple_deletions_in_a_transaction`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L804-L814)).

**6. Multiple in-memory instances of the same row**

[`CallbacksOnMultipleInstancesInATransactionTest`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L898-L1024) (Rails 7.1 last-saved behavior, `run_commit_callbacks_on_first_saved_instances_in_transaction = false`):

| Transaction | Runner | Observable filter | History |
|---|---|---|---|
| `create!(title: "A")` then `find(id).update!(title: "B")` | last instance | `:create` (flag copied from the creator) | `Created (title = "B")` — not `Updated` |
| two `find(id).update!` | last instance | `:update` | `Updated` with last title |
| `update!` then `destroy!` | destroyed instance | `:destroy` | `Destroyed` |
| `destroy!` then `update!` on the other object | destroyed instance stays | `:destroy` | later update cannot replace it |

With the old first-saved default, the first instance runs instead (`Created (title = "A")`, `Updated (title = "two")`), and an early update can hide a later destroy.

Only the chosen instance’s callbacks run. The other objects are `committed!(should_run_callbacks: false)`. Filters are evaluated on the chosen instance’s flags, which is why a last-saved updater can still fire `after_create_commit`.
