## Assistant

This is a working maintenance brief, grounded in current `generate`/`destroy` CLI behavior. The intended collision contract is still open.

**Problem frame:** App and engine authors run `bin/rails generate` and `bin/rails destroy` against the same generator name when a target file already exists. Today those commands do not give the same collision conversation: generate compares content and may leave the file, prompt, skip, or overwrite; destroy removes an existing target without that conversation. Help for both commands advertises `--force` / `--skip` as overwrite/skip of existing files. That mismatch is painful when someone skipped a collision, customized a generated file, ran a script with no TTY, or generated inside an engine whose destination root is not the dummy app. **Hypothesis:** they want one documented, observable collision policy for the same existing file in both commands, in apps and engines, without changing what a generator would create when no file is in the way.

**Kind of work:** Maintenance of collision handling as a shared CLI contract. Whether today’s generate/destroy differences are defects or the intended contract is not yet settled; that question has to be answered before any change is treated as success.

**Users**
- An application developer generating or destroying files in a Rails app.
- An engine author doing the same from the engine’s `bin/rails`, whose destination root is the engine tree.
- A person or script running those commands with flags, a TTY prompt, or no interactive stdin (CI, pipes).

**Current pain (observed, not a verdict)**
- `bin/rails generate GENERATOR …` and `bin/rails destroy GENERATOR …` resolve the same generator name the same way, then apply opposite file actions: create versus remove.
- On generate, an existing file is `identical` (unchanged), `force` (replaced), `skip` (left), or `conflict` (prompted). On destroy, an existing file at that destination is `remove`d if present; content is not compared and `--force` / `--skip` do not change that.
- Destroy help still lists `-f` as “Overwrite files that already exist” and `-s` as “Skip files that already exist.”
- Class-name collision (“The name 'Post' is either already used…”) is generate-only and is a different event from a file already being on disk.
- Evidence for this is command entry, generator lookup, Thor create/remove actions, and Railties generator tests. Live TTY/EOF sessions were not run here; prompt and EOF outcomes below are taken from Thor’s collision menu, not from a captured terminal session.

**Desired observable CLI behavior (working claim)**
For a given generator name, arguments, destination root, and existing target file, generate and destroy should each have a stable, documented collision result that a person can predict from the command, flags, and answers—not from knowing which command they typed after the fact. The same generator name should resolve the same way in an app and in an engine; only the destination root should change where the file is considered “existing.” Missing generators should fail the same way for both commands. A later destroy should not silently undo a skip the user just accepted unless that is explicitly the chosen contract.

**Non-goals**
- Changing which files a generator would create or remove when no collision exists.
- Changing templates, hook generators, or after-generate callbacks.
- Changing reserved/class-name collision text, except to keep it distinct from file collision.
- New flags, new generators, or a new help command.
- Prescribing how lookup, Thor, or engines are structured.

**Acceptance examples** (required cases unless marked illustrative)

Identical content, generate then destroy
- Situation: the target already contains exactly what generate would write.
- Action: `bin/rails generate …` then `bin/rails destroy …` with the same name.
- Observe: generate reports `identical` and does not rewrite the file. Destroy’s result is an open contract: either it still reports `remove` and deletes, or it treats “never written by this generate” as leave-in-place. Current observed behavior is delete.

Differing content, no flags, TTY

- Action: generate without `--force` or `--skip`.

  - `n`: file left; later files still prompt.
  - `a`: this file and later conflicts overwritten without another prompt.
  - `q`: `Aborting...` and the command stops; remaining files untouched.
- Destroy with the same existing differing file and no flags: currently deletes without that prompt. Whether that remains acceptable is open.

`--force`
- Generate: differing file overwritten; status `force`. Class-name collision is also suppressed on generate.
- Destroy `--force`: currently still deletes if the file exists. Whether `--force` on destroy should mean “delete even if customized” versus be meaningless is open.

`--skip`

- Observed from Thor’s menu: a `nil` answer is treated as yes (overwrite). Empty string is also yes.
- Open: scripts without a TTY should overwrite, skip, or abort with a non-zero status. This is the highest-risk ambiguity for CI.

Nested engine destination root
- Situation: engine `bin/rails` (ENGINE_ROOT set); generate/destroy a file that already exists under the engine tree, not under `test/dummy`.
- Observe: “existing file” is evaluated in the engine destination root for both commands. A same-named file in the dummy app is irrelevant. Engine generator config and app generator config can differ; that must not silently retarget the file into the dummy app.

Namespaced generator resolution
- Situation: `model`, `rails:model`, a configured fallback (`shoulda:model` → test_unit model), or `admin/role` under an isolated engine namespace.
- Observe: generate and destroy resolve to the same generator. Namespaced output paths (e.g. `app/models/test_app/admin/role.rb`) are the collision paths. Destroy of `admin/role` removes that resource’s files and does not remove parent namespace files left for other resources.

Missing generator
- Action: `bin/rails generate unknown` and `bin/rails destroy unknown`.
- Observe: both print `Could not find generator 'unknown'.` and exit 1. Current message always tells the user to run `bin/rails generate --help`, even from destroy. Open whether destroy should name destroy help.

Destroy after a skipped collision
- Situation: generate hit a differing file, user or `--skip` left it; then destroy with the same generator name.
- Current observe: destroy removes the file that generate refused to touch.
- Desired observe is the decision this brief exists to settle: either destroy may delete a file generate skipped, or destroy must leave a skipped file, or destroy must prompt because the file was not produced by this generate.

**Steering evidence**
- Success looks like: a person can predict, from the command line alone, what happens to an existing file for generate and destroy in an app and in an engine, including flags, Y/n/a/q, and no-TTY runs.
- Investigate (do not treat as done) if: destroy still deletes a file generate just skipped; destroy `--skip` deletes; generate with closed stdin overwrites; engine generate collides in the dummy app instead of the engine root; or a namespaced/fallback name generates one path and destroys another.
- Reconsider the framing if: the intended product is “destroy always removes whatever sits at the generated path, even if generate skipped or the user edited it,” and the only bug is help text / class-name collision wording. That would be documentation of an intentional difference, not collision unification.

**Open questions (these decide the contract)**
1. Are generate and destroy supposed to share one file-collision policy, or is destroy intentionally unconditional remove of the target path?
2. After generate `--skip` or `n`, may destroy delete that file without asking?
3. Should destroy honor `--skip` / `--force` as help describes, ignore them, or error because they do not apply?
4. On generate with no TTY / EOF, is overwrite, skip, or abort the intended default?
5. Is class-name collision in or out of scope? Tests cover it on generate only; the report is about an existing file.
6. Should a missing generator on destroy mention destroy help, or is the shared generate-help line intentional?
7. For migrations, generate already errors on a differing same-name migration instead of prompting; destroy removes it. Is that a second intentional exception?

I treated “inconsistent” as a reported pain, not as proof that destroy must start prompting. The examples above are the cases that would confirm or refute a single collision contract.

Which of (1) and (2) is the intended outcome—unify generate/destroy, or keep destroy as unconditional remove and only make the advertised flags/help match that?
