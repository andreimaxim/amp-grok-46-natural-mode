## Current behavior

`RunnerCommand#perform` replaces the process-global `ARGV` with only the arguments following the code/file argument:

```ruby
def perform(code_or_file = nil, *command_argv)
  # ...
  ARGV.replace(command_argv)
  # evaluate/load runner code
end
```

See [`runner_command.rb` lines 22–49](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/runner/runner_command.rb#L22-L49).

It does **not** restore `ARGV` itself.

However, normal dispatch through `Rails::Command.invoke("runner", args)` is already protected. `invoke` wraps command execution in `with_argv` ([`command.rb` lines 55–69](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L55-L69)), which saves and restores `ARGV` in an `ensure`:

```ruby
def with_argv(argv)
  original_argv = ARGV.dup
  ARGV.replace(argv)
  yield
ensure
  ARGV.replace(original_argv)
end
```

See [`command.rb` lines 140–146](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L140-L146). Tests explicitly verify that command mutations do not escape `invoke`: [`base_test.rb` lines 116–140](https://github.com/rails/rails/blob/main/railties/test/command/base_test.rb#L116-L140).

Therefore:

- **Through `Rails::Command.invoke`: yes, `ARGV` is restored, including after exceptions.**
- **Calling `RunnerCommand.perform` directly:** no outer restoration is guaranteed, so its `ARGV.replace(command_argv)` leaks.
- Adding save/restore inside `RunnerCommand#perform` would mainly protect direct Thor/class invocation or other paths bypassing `Rails::Command.invoke`; it is redundant for normal command dispatch.

## History

The restoration predates `with_argv` as a named helper:

- [PR #38495, “Isolate ARGV in Rails::Command.invoke”](https://github.com/rails/rails/pull/38495), merged **March 13, 2020**, introduced save/restore around `invoke` specifically so mutations would not affect later in-process code.
- [PR #41611](https://github.com/rails/rails/pull/41611) / commit [`ddcfde2`](https://github.com/rails/rails/commit/ddcfde2226217c0d65bd83a5d8dd25d7d3244f86), authored **March 3, 2021** and merged **April 3, 2021**, changed invocation from clearing `ARGV` to populating it from `args`, while retaining `ensure { ARGV.replace(original_argv) }`. Its stated goal was identical CLI/programmatic behavior while keeping `ARGV` isolated between invocations.

The current extraction into the private `with_argv` method is structural; the core restore guarantee dates to #38495, while argument population dates to #41611.

## Related reports

I found **no Rails issue or PR specifically reporting that runner leaks `ARGV` after embedded/in-process invocation**.

Related work instead supports the existing outer isolation model:

- [PR #38495](https://github.com/rails/rails/pull/38495): explicitly addresses commands mutating global `ARGV` during library/in-process invocation.
- [PR #41611](https://github.com/rails/rails/pull/41611): explicitly says programmatic and CLI invocations should behave identically and "`ARGV` will still be isolated between invocations."
- [Issue #40945](https://github.com/rails/rails/issues/40945): reported that commands/templates could no longer see invocation arguments after #38495; it motivated #41611, not a runner leak fix.
- [Issue #28515](https://github.com/rails/rails/issues/28515) and commit [`a06a643`](https://github.com/rails/rails/commit/a06a643e0572b8c983738c068ae637d020188c97): corrected runner’s *contents* of `ARGV` so the Ruby code itself was excluded.
- Commit [`5aea095`](https://github.com/rails/rails/commit/5aea0952e7cb445e614652e3cd9aba71a836eed0): restored passing trailing runner arguments to loaded files.

**Review implication:** unless the proposed change intentionally supports direct `RunnerCommand.perform` invocation, claiming it fixes ordinary embedded use through `Rails::Command.invoke` would be inaccurate—the outer `with_argv` already restores `ARGV`.

### Verdict

The inner `ARGV.replace(command_argv)` in [`RunnerCommand#perform`](file:///home/user/workspace/repo/railties/lib/rails/commands/runner/runner_command.rb#L24-L65) is intentional: it is how the executed code sees trailing args, not the command name or the Ruby snippet/filename.

**stdin (`-`).** Matched before `File.exist?`, so a file named `-` is not loaded. `ARGV.replace` still runs, so stdin scripts can see extra args. Tests never pass extra args to `-`. Restore would not affect the eval.

**Syntax errors / missing files.** `ARGV.replace` happens before `eval`. Missing `*.rb` uses the file-not-found branch and `exit 1`; other bad input uses the syntax/name-error branch and `exit 1`. **Nested / in-process invocation.** Through `Rails::Command.invoke`, isolation already exists. Direct `RunnerCommand.perform(...)` or Thor dispatch that skips `invoke` does leak `ARGV`. That is not how Rails embeds commands, and no test exercises it. The proposed restore would help only that unsupported path, and it would restore *perform-entry* `ARGV` (under `invoke`, the full runner args including the code/file), not “the process ARGV before runner,” which `with_argv` already does.

**`$0` / `$PROGRAM_NAME`.** Set only for files, never restored. Unrelated to the proposed diff; incomplete if the PR is about embedding hygiene.

**Executor wrapping.** `ARGV.replace` is outside [`conditional_executor`](file:///home/user/workspace/repo/railties/lib/rails/command/base.rb). Scripts inside the executor correctly see runner args.
