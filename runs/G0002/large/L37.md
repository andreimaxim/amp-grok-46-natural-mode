**Block.** The claim is false, and the diff does not do what the claim describes. `enqueue_delivery` never puts a `Mail::Message` on the job. ## What `processed?` actually means

[`MessageDelivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb) is a lazy `Delegator` around a `Mail::Message`. Construction stores the mailer class, action, and args and leaves both caches nil:

```21:31:actionmailer/lib/action_mailer/message_delivery.rb

  args << Hash.ruby2_keywords_hash(kwargs) unless kwargs.empty?
  @mailer_class, @action, @args = mailer_class, action, args
  @processed_mailer = nil
  @mail_message = nil
end
```

`processed?` is true once either cache is set:

```47:50:actionmailer/lib/action_mailer/message_delivery.rb

  @processed_mailer || @mail_message
end
```

Calling [`#message`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L43-L45), or any delegated `Mail::Message` method (`to`, `subject`, `body`, header writes), runs [`processed_mailer`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L135-L140), which instantiates the mailer and `process`es the action in the current process. That is the opposite of the documented lazy path: “Typical usage will leave it unloaded and call `deliver_later`.”

## What is actually serialized

The unprocessed branch does this:

```152:154:actionmailer/lib/action_mailer/message_delivery.rb
@mailer_class.delivery_job.set(options).perform_later(
  @mailer_class.name, @action.to_s, delivery_method.to_s, args: @args)
```

Active Job therefore serializes four values: a class name `String`, an action `String`, a delivery-method `String`, and the original args (plus `params:` for parameterized mailers). [`MailDeliveryJob#perform`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L20-L28) then constantizes the mailer and calls the action again:

```20:28:actionmailer/lib/action_mailer/mail_delivery_job.rb
def perform(mailer, mail_method, delivery_method, args:, kwargs: nil, params: nil)
  mailer_class = params ? mailer.constantize.with(params) : mailer.constantize
  message = if kwargs
    mailer_class.public_send(mail_method, *args, **kwargs)
  else
    mailer_class.public_send(mail_method, *args)
  end
  message.send(delivery_method)
end
```

The proposed diff still calls that same `perform_later(...)`. It does not pass `@mail_message`. The worker cannot “use the generated message” because it never receives it.

The raise text already states the contract the PR would violate: “Only the mailer method *arguments* are passed with the delivery job.”

## The author’s serialization claim

Even a revision that *did* pass the generated message would fail at enqueue time. [`ActiveJob::Arguments`](file:///home/user/workspace/repo/activejob/lib/active_job/arguments.rb#L62-L107) only accepts primitives, Hash/Array, a small serializer list (Symbol, Date, Time, Duration, Range, BigDecimal, Module), and `GlobalID::Identification`. `Mail::Message` is none of those. [`Serializers.serialize`](file:///home/user/workspace/repo/activejob/lib/active_job/serializers.rb#L31-L33) raises `ActiveJob::SerializationError` (`Unsupported argument type: Mail::Message`).

The mail gem’s `to_yaml` / `from_yaml` is unrelated. Active Job does not use it, and there is no `Mail::Message` serializer under `activejob/lib/active_job/serializers/`.

## Serialization failures vs the no-prior-access path

No-prior-access is the supported path and must stay: do not call `#message` / delegated mail methods; `deliver_later` enqueues args; the worker runs the mailer. Tests already pin that for delay, priority, `wait_until`, queues, kwargs, custom jobs, and parameterized params ([message_delivery_test.rb](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L62-L131), [parameterized_test.rb](file:///home/user/workspace/repo/actionmailer/test/parameterized_test.rb#L41-L52)). This PR does not improve that path.

[`job delegates deserialization errors to mailer class`](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L250-L263) is about GlobalID args failing **at perform**, rescued by [`MailDeliveryJob`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L18). That is not `Mail::Message` serialization. Passing an unsupported type fails at **enqueue** with `ActiveJob::SerializationError`, which the mailer’s `rescue_from` never sees.

[`deliver_all_later`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer.rb#L88-L100) also builds jobs from `mailer_class` / `action` / `params` / `args` and asserts the wrappers stay unprocessed ([tests](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L164-L178)). It would have the same silent-loss problem if callers mutated first; this PR does not touch it.

## Gaps

The revision and the claim disagree. The diff only deletes the guard. It does not serialize `Mail::Message`, change `MailDeliveryJob#perform`, add a serializer, or update parameterized `super`. Tests that would have to exist for the claim — mutation preserved after enqueue, `Mail::Message` round-trip, parameterized-after-`#message`, `deliver_later!`, custom job arity, enqueue-time `SerializationError` — are absent. The one test that exists would fail.

## Smallest viable direction

Keep the `processed?` raise. The documented workarounds are already the right ones: do not touch the message before `deliver_later`, mutate only inside the mailer action, or write a custom job.

If the product goal is “inspect or mutate, then `deliver_later` and keep those edits,” that is a new job contract, not a one-line deletion: serialize an encoded RFC822 string (not the live `Mail::Message` object), teach `MailDeliveryJob` (and parameterized / `deliver_all_later`) to deliver that payload without re-running the action, and add tests for mutation preservation, parameterized params, `deliver_later!`, custom jobs, and enqueue-time serialization failure. Do not ship the guard removal as a substitute.
