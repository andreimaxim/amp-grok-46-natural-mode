`recognize_path` is a recognition-only API. It does not dispatch. It builds a fake request, asks Journey for matching routes, then returns `req.path_parameters` only if the matching app is a dispatcher whose controller constantizes. ### Public entry: `recognize_path`

[actionpack/lib/action_dispatch/routing/route_set.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/route_set.rb#L911-L924) is the only public construction of the request:

1. Verb defaults to `"GET"` and is uppercased. Tests pass `:get`, `:post`, `"GET"`, etc.; all become Rack `REQUEST_METHOD` via `env_for`.
2. Relative paths (no `"://"`) go through `Journey::Router::Utils.normalize_path`. Absolute URLs skip that.
3. `environment[:extras]` is stashed for later merge. It is not parsed from the query string.
4. `Rack::MockRequest.env_for(path, method:)` turns the string into `PATH_INFO`, `QUERY_STRING`, `HTTP_HOST`, scheme. `URI::InvalidURIError` is re-raised as `ActionController::RoutingError` with the URI message.
5. `make_request` is `ActionDispatch::Request.new(env)`. Then `recognize_path_with_request`.

This is not the live request path. `RouteSet#call` always normalizes `req.path_info` and then `@router.serve`. `recognize_path` never calls `serve`.

On a Rails app, [railties/lib/rails/engine/lazy_route_set.rb](file:///home/user/workspace/repo/railties/lib/rails/engine/lazy_route_set.rb#L106-L113) reloads routes first, then `super`. Recognition logic is unchanged.

### Journey match: `Router#recognize`

[actionpack/lib/action_dispatch/journey/router.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/journey/router.rb#L43-L99) matches on `req.path_info` only. Query string is ignored.

Candidate collection:

- Anchored routes with anchored requirements come from the GTG simulator (`filter_routes` → `simulator.memos(path_info)`).
- Unanchored / custom-requirement routes are appended if `r.path.match?(path_info)`.
- Non-HEAD: `routes.select! { |r| r.matches?(req) }`.
- HEAD: try verb-constrained HEAD routes; if none, temporarily set `GET` and reuse GET routes ([match_head_routes](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/journey/router.rb#L114-L125)).
- Multiple survivors are sorted by `precedence` (definition order).

`Journey::Route#matches?` ([route.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/journey/route.rb#L172-L189)) is verb + **request** constraints (`subdomain`, `protocol`, `ip`, …). Path-segment regexps (`id: /\d+/`) are compiled into the Journey pattern, not checked here.

For each survivor:

1. `r.path.match(path_info)` again, to get captures.
2. Start from existing `req.path_parameters` merged with `r.defaults` (controller, action, frozen default ids, etc.).
3. Named captures containing `%` are `CGI.unescapeURIComponent`’d, then forced to UTF-8. `+` is left as `+`.
4. Anchored routes yield immediately. Unanchored (mounted) routes rewrite `script_name` / `path_info` to the remainder, yield, then restore.
5. After the yield, `req.path_parameters` is restored to the pre-route hash. That is why [TestRecognizePath](file:///home/user/workspace/repo/actionpack/test/dispatch/routing_test.rb#L5439-L5475) can have adjacent hash/proc/class constraints without leaking captures.

`serve` uses the same `recognize` enumerator, then `route.app.serve`. `recognize_path` does not.

### Acceptance: `recognize_path_with_request`

[route_set.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/route_set.rb#L926-L954) is the filter that turns a Journey hit into a params hash:

1. `params.merge!(extras)` — this is how query-string-like keys get into the result. `assert_recognizes` documents that appending `?view=print` to the path does not work; you pass `extras:` ([assertions/routing.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/testing/assertions/routing.rb#L156-L162), [routing_assertions_test.rb](file:///home/user/workspace/repo/actionpack/test/dispatch/routing_assertions_test.rb#L99-L101)).
2. Every String value is BINARY-forced and `URI::RFC2396_PARSER.unescape`’d again. This is a second decode on top of Journey’s `unescapeURIComponent`.
3. `req.path_parameters = params` runs encoding checks (`BadRequest` on invalid path params).
4. `app = route.app`. Then `app.matches?(req)`:
   - Bare `Dispatcher`: always true ([endpoint.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/endpoint.rb#L8-L10)).
   - `Mapper::Constraints`: hash/proc/class constraints, now able to read `req.path_parameters` ([mapper.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L52-L57)).
5. Dispatcher: `req.controller_class`. Success returns `req.path_parameters`. `NameError` (including `ActionDispatch::MissingController`) becomes RoutingError with the missing-controller message.
6. Engine: recurse with `raise_on_missing: false`. A nested hit is returned; a nested miss continues the parent enumerator.
7. Redirects, Rack apps, constraint failures: no return. Next candidate.
8. Enumerator exhausted: `raise_on_missing` (true from the public API) → `RoutingError, "No route matches #{path.inspect}"`. Nested engine calls return `nil`.

`controller_class` ([request.rb](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/request.rb#L85-L108)) does `params[:action] ||= "index"`, then `"#{name.underscore.camelize}Controller".constantize`. Missing *that* constant becomes `MissingController`. Any other `NameError` is re-raised, then still swallowed by the `rescue NameError` in `recognize_path_with_request`.

The unmatched / missing-controller split is the important one. Journey matching succeeding is not enough. `recognize_path` still requires a dispatcher app **and** a constantizable controller. Unmatched path, wrong verb, failed constraint, or non-dispatcher endpoint all collapse to the same `"No route matches #{path.inspect}"`. A path that *did* match a dispatcher whose controller is absent is a different RoutingError, and only on this API — live dispatch surfaces `MissingController` instead.

`recognize_path` therefore answers “which controller/action hash would this path map to?”, not “what would this request do?”. Query strings, Rack apps, redirects, and missing constants are the places that difference is visible.
