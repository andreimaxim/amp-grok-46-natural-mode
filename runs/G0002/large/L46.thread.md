## Claimed `credentials_defaults` → `master.key` behavior

The review established:

- Environment content + environment key: normal environment pair.
- Environment content + no environment key + `config/master.key`: it decrypts **only if the environment content was encrypted with the master key**.
- Environment content + neither file key:
  - `config.require_master_key = false`: empty credentials.
  - `true`: `MissingKeyError`, naming the selected `master.key`.
- Environment content + wrong environment key: `ActiveSupport::MessageEncryptor::InvalidMessage`; no fallback after an authentication failure.
- Global content + `master.key`: normal global pair.
- **Global content + stale environment key: bug.** The independent checks pair global `config/credentials.yml.enc` with `config/credentials/<env>.key`, which can fail decryption and abort production boot.
- `ENV["RAILS_MASTER_KEY"]` takes precedence over either selected key file. A wrong ENV key fails; Rails does not retry the file key.
- Explicit `config.credentials.content_path` and `config.credentials.key_path` remain authoritative; configuring both avoids ambiguous pairing.
- Wrong valid-length keys yielded `ActiveSupport::MessageEncryptor::InvalidMessage`; malformed key lengths can yield `ArgumentError` on read or `InvalidKeyLengthError` on write.

## Complete review verdict / analysis

**Verdict: Request changes.**

The fallback itself was considered defensible only as an explicit, directional contract, but a `credentials_defaults`-only change was judged incomplete and unsafe.

### Blocking defects

1. **Mismatched global-content/environment-key pairing**

   Independent content/key existence checks mean an obsolete `config/credentials/production.key` is selected even when only global `config/credentials.yml.enc` exists. The review reproduced `InvalidMessage` and a production boot failure.

2. **`credentials:edit --environment` disagrees with runtime/show/fetch/diff**

   In `railties/lib/rails/commands/credentials/credentials_command.rb`, the `edit` environment branch hardcodes the environment key:

   ```ruby
   if environment_specified?
     @content_path = "config/credentials/#{environment}.yml.enc" unless config.overridden?(:content_path)
     @key_path = "config/credentials/#{environment}.key" unless config.overridden?(:key_path)
   end
   ```

   Reproduced sequence:

   1. `config/credentials/production.yml.enc` is encrypted using `config/master.key`; `config/credentials/production.key` is absent.
   2. `credentials:show --environment production` decrypts successfully.
   3. `credentials:edit --environment production` creates a random `production.key`, then cannot decrypt the existing file.
   4. The leftover key becomes preferred by runtime defaults, causing later credential loads—and potentially production boot—to fail.

### Security/compatibility conclusions

- AES-GCM authentication prevents plaintext disclosure with a wrong key.
- Nevertheless, automatic global-key reuse increases the master key’s blast radius and weakens environment isolation/fail-closed behavior.
- The command-created “poison” environment key is an operational/availability regression.
- Production commonly evaluates credential-backed configuration during boot, so the mismatch can be an outage. Development/test may tolerate truly missing credentials when `require_master_key` is false via a local secret, but an invalid ciphertext/key still raises when credentials are read.

### Recommended tiny correction

Make fallback directional: only environment content may fall back to the master key; global content must always pair with the master key.

```ruby
def credentials_defaults
  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")

  if content_path.exist?
    key_path = root.join("config/credentials/#{Rails.env}.key")
    key_path = root.join("config/master.key") unless key_path.exist?
  else
    content_path = root.join("config/credentials.yml.enc")
    key_path = root.join("config/master.key")
  end

  { content_path: content_path, key_path: key_path }
end
```

Also change `credentials:edit --environment` to use `config.key_path` when its content already exists; create an environment key only when creating new environment content. If global-key reuse is not an intentional product contract, restore strict coupled environment-content/environment-key behavior instead.

### Missing regression coverage

- Full content/key matrix, especially stale environment key + global content.
- Environment content encrypted by `master.key`, no environment key.
- No key with `require_master_key` both true and false.
- Wrong and malformed keys.
- `RAILS_MASTER_KEY` precedence for both global and environment content.
- Explicit custom path pairs.
- Production boot versus development credential access.
- Consistency of `show`, `fetch`, `diff`, and `edit`; specifically, edit must not generate an environment key for existing master-encrypted environment content.

## Historical behavior

Environment-specific credentials arrived in [`e0d3313` on 2018-09-19](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba) (“Support environment specific credentials file”, PR #33521).

Its configuration used **one shared predicate**—whether `config/credentials/#{Rails.env}.yml.enc` existed—to select both paths:

```ruby
def default_credentials_content_path
  if credentials_available_for_current_env?
    # config/credentials/#{Rails.env}.yml.enc
  else
    # config/credentials.yml.enc
  end
end

def default_credentials_key_path
  if credentials_available_for_current_env?
    # config/credentials/#{Rails.env}.key
  else
    # config/master.key
  end
end
```

See the introducing [configuration diff](https://github.com/rails/rails/blob/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba/railties/lib/rails/application/configuration.rb#L276-L296).

Therefore the original choices were coupled:

| Environment content exists? | Content | Key |
|---|---|---|
| Yes | `config/credentials/<env>.yml.enc` | `config/credentials/<env>.key` |
| No | `config/credentials.yml.enc` | `config/master.key` |

Notably, if environment content existed but its key did not, Rails still selected the missing environment key; it did **not** silently use `master.key`. That matches the isolation intent stated in the commit: the environment file is decrypted by `RAILS_MASTER_KEY` or its corresponding `config/credentials/<env>.key`.

[`d69b04d` on 2018-09-20](https://github.com/rails/rails/commit/d69b04de0ff33237209afea6f6cac3ab27934908) corrected the environment-variable name so environment-specific credentials used the common `RAILS_MASTER_KEY`, rather than a generated `RAILS_<ENV>_KEY`.

## Decision: request changes

The **environment-content → `master.key` fallback is a defensible contract**, but the current independent implementation should not be codified as-is. It also permits the nonsensical reverse pairing, and `credentials:edit --environment` is incompatible with the claimed fallback.

### Material defects

- Independent selection in [`credentials_defaults`](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L683-L690) allows global content to pair with a stale environment key. This can turn deleting an environment override into an `InvalidMessage` boot outage.
- [`credentials:edit --environment`](file:///home/user/workspace/repo/railties/lib/rails/commands/credentials/credentials_command.rb#L18-L29) always selects the environment key. For existing environment content encrypted with `master.key`, it can create a new environment key, fail decryption, and leave subsequent runtime lookup selecting that wrong key.
- These are availability and operational-safety problems, not plaintext-disclosure vulnerabilities. AES-GCM fails closed. Do not add decrypt-and-retry behavior: an existing but wrong environment key should continue raising rather than silently trying `master.key`.

### Recommended correction

Use the **directional patch**, not the 2018 fully coupled behavior—but the patch alone is insufficient.

It provides the sensible precedence:

1. Existing environment content:
   - environment key when present;
   - otherwise `master.key`.
2. No environment content:
   - global content with `master.key`, ignoring stale environment keys.

This preserves the useful, currently documented environment/master fallback while removing the accidental reverse pairing. Restoring strict coupling would break applications relying on the documented fallback since 2023. Anyone intentionally pairing global content with an environment key can preserve that unusual setup through explicit `config.credentials.key_path`.

Also align `credentials:edit --environment`:

- For an **existing** environment content file, use the same selected key as runtime.
- For a **new** environment content file, retain the current behavior of creating an environment key.
- Explicit content/key overrides remain authoritative.

Update the guide’s currently independent wording in [`configuring.md`](file:///home/user/workspace/repo/guides/source/configuring.md#L325-L343) to describe this directional relationship.

### Tests that matter

1. **Claimed fallback integration:** environment content encrypted with the file `master.key`, no environment key, decrypts through `Rails.application.credentials`. The existing `RAILS_MASTER_KEY` test does not prove file fallback because ENV bypasses `key_path`.
2. **Reverse regression:** global content plus stale environment key selects/decrypts with `master.key`.
3. **Edit consistency:** editing existing environment content encrypted with `master.key` succeeds and does not create an environment key; subsequent runtime/show still decrypts.
4. **Fail-closed invariant:** when an environment key exists but is wrong, reading raises `InvalidMessage` and does not retry `master.key`.

Existing tests already cover creating a new environment pair and explicit overrides, so those need not be duplicated.
