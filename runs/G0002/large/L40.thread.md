## Assistant

Current behavior is established from this checkout’s Active Storage source, tests, and guides. Evidence is below the brief so the proposal stays user-facing.

**Working model:** an application developer generating download links cannot tell which clock they set, when a client will stop getting the file, or how proxy vs redirect caching changes that. The work is to make those clocks and outcomes predictable, not to invent new download modes.

## Product shaping brief: predictable expiration for Active Storage download links

### Problem frame

An application developer needs to hand out a download link for a stored file or a variant and know, without reading framework internals, how long that link will work and what a client will see when it stops working.

Today they use three surfaces that look related but expire independently:

- a signed blob identifier (`signed_id`)
- a service URL (`url`)
- an application download URL (`rails_storage_proxy_url` / `rails_storage_redirect_url`)

Those surfaces sit on two clocks. Application URLs are permanent by default and only expire if the developer (or a global default) asks them to. Service URLs for private storage expire in five minutes by default. Public storage service URLs do not expire. Redirect responses tell browsers to cache the *redirect* for five minutes. Proxy responses tell browsers and CDNs to cache the *file* forever.

That mix is easy to misread. Guides call application URLs “permanent” and also document `expires_in`. A developer who expires an application URL can still have the file linger in a public immutable cache. A developer who treats a service URL as a stable download link will see it die in five minutes. Tampered or expired identifiers fail closed as “not found,” which is correct but easy to confuse with a missing file.

The desired progress is that a developer can choose permanent vs expiring application identifiers, choose proxy vs redirect, and predict what a client observes at generation time, near expiry, after expiry, and after tampering — including variants and public vs private storage.

### Desired outcome

When this work is complete, an application developer can answer these questions from the product contract, without guessing:

1. Which of the three surfaces they generated, and which clock that surface uses.
2. Whether a signed blob identifier is permanent or time-bounded, and how `expires_in`, `expires_at`, and the application-wide default interact.
3. How long a private service URL remains usable, and that a public service URL is not on that clock.
4. What a client gets from a proxy URL vs a redirect URL while the application identifier is valid, and after it is not.
5. That variants and previews follow the same application-identifier and service-URL clocks as the original file.
6. That a tampered or expired identifier is indistinguishable from an unknown file: the client does not get the file.
7. That expiring an application URL is not access control, and that caches may outlive the application URL.

### Appetite

**Hypothesis:** Small Batch — make the existing contract teachable and decide whether a few surprising edges are documented contract or defects. Not a redesign of download routing, storage services, or authentication.

Correct this if the intent is a larger change (for example, making proxy cache lifetime follow application-URL expiry).

### Scope

In scope:

- Permanent vs expiring signed blob identifiers, including per-link duration, per-link instant, and the application-wide default.
- Expiry of service URLs for private vs public storage.
- Proxy vs redirect client behavior and cache headers while the application identifier is valid, and after it is not.
- Tampered and expired identifiers.
- Variants and previews generated through the same application URL helpers.
- Boundary timing: still valid before expiry; not valid after expiry; what is promised at the exact expiry instant if anything.
- What a developer can and cannot infer from a “not found” response.

Out of scope (non-goals):

- Authenticated or per-user authorization of downloads.
- Changing whether built-in download URLs are publicly reachable if the identifier is known.
- Direct-upload URLs, except to note they are a different short-lived surface.
- CDN host configuration, mirroring, or switching storage providers.
- Filename, content type, or content-disposition rules, except where they appear on the same response as expiry/cache behavior.
- New download modes, new identifier types, or data-model changes.

### Risks

- **Two clocks stay invisible.** If the brief is treated as “make URLs expire” without naming application identifier vs service URL, developers will keep mixing them.
- **Proxy cache outliving an expiring application URL.** A successful proxy response is public, immutable, and cached for about 100 years. A later request with the same URL may still be served from cache after the signed identifier would no longer be accepted. If that is left unspecified, “expiring proxy URLs” will be misunderstood as “the file becomes unreachable.”
- **Redirect cache vs service-URL lifetime.** Redirect responses are cached privately for the service-URL lifetime (five minutes by default). A client may reuse the redirect without re-checking the application identifier during that window. The destination service URL may then expire on its own clock.
- **Public storage bypasses the private service-URL clock.** `url` on a public service is a lasting locator. Putting that locator in a page or email is not the same as handing out an application download URL.
- **Expiry is not revocation.** A link shared before expiry remains usable until that expiry. Treating expiry as access control will fail.
- **Exact-instant behavior is currently unproven.** Tests only show “works now” and “gone after a later travel.” Promising inclusive vs exclusive expiry without deciding it will recreate the unpredictability this work is meant to remove.
- **“Not found” collapses several failures.** Tampered identifier, expired identifier, unknown identifier, and (likely) a deleted blob all look like a missing file. That is good for not leaking existence, but bad if developers expect a distinct “expired” signal.

### Acceptance examples

Required unless marked illustrative.

#### Permanent application identifier (core)

Given a stored file and no expiry option and no application-wide expiry default  
When the developer generates a proxy or redirect application URL  
Then a client that later requests that same URL still receives the file  
And the identifier does not stop working merely because time has passed.

#### Expiring application identifier by duration

Given a stored file  
When the developer generates a proxy or redirect URL that expires in one minute  
Then a client who requests it immediately receives the file (proxy: the file body; redirect: a redirect toward the file)  
And a client who requests the same URL after two minutes does not receive the file and gets a not-found response.

#### Expiring application identifier by instant

Given a stored file  
When the developer generates a proxy or redirect URL that expires at a specific future time  
Then a client who requests it before that time receives the file  
And a client who requests it after that time gets not found.

#### Application-wide default expiry

Given the application is configured so all Active Storage application URLs expire after one minute  
When the developer generates a proxy or redirect URL without passing a per-link expiry  
Then the URL behaves as a one-minute expiring identifier: valid immediately, not found after two minutes.

#### Permanent signed identifier used as a client-side reference

Given a stored file  
When the developer takes a signed blob identifier with no expiry  
Then looking up that identifier still finds the file after time has passed  
And the same identifier with a one-minute expiry finds the file immediately and finds nothing after two minutes.

#### Tampered or junk identifier

Given a proxy or redirect URL whose signed identifier is replaced with junk, or otherwise altered  
When a client requests it  
Then the client gets not found  
And does not receive the file.

This includes an invalid variation key on a variant/preview URL.

#### Private service URL (core)

Given a file on a private service  
When the developer asks for the file’s service URL with default settings  
Then that URL is short-lived (five minutes unless they asked for another duration)  
And it is not suitable as a stable public locator  
And the documented guidance is to expose a stable application URL that redirects to it, not to publish the service URL itself.

#### Public service URL

Given a file on a public service  
When the developer asks for the file’s service URL  
Then that URL is a lasting public locator, not a five-minute signed URL  
And a client can fetch the file from it without a temporary service signature.

#### Redirect response while the application identifier is valid

Given a valid redirect application URL  
When a client requests it  
Then the client is redirected to the current service URL  
And the redirect response is privately cacheable for the service-URL lifetime (five minutes by default).

#### Proxy response while the application identifier is valid

Given a valid proxy application URL  
When a client requests it  
Then the client receives the file body from the application, not a redirect  
And the successful response is publicly cacheable and marked immutable for about 100 years.

#### Proxy failure must not be cached as the file

Given a valid proxy application URL whose file cannot be read from storage  
When a client requests it  
Then the client does not receive a successful cached-forever file response  
And a missing file is not found with a no-cache response  
And an unexpected download failure is a server error with a no-cache response.

#### Variants and previews follow the same clocks

Given a variant or preview  
When the developer generates a proxy or redirect application URL with or without expiry  
Then the application identifier clock is the blob identifier’s clock  
And a valid request serves or redirects to the representation  
And an invalid blob identifier or invalid variation key is not found  
And the representation’s service URL uses the same private-vs-public service-URL clock as other files.

*Gap in current tests:* variant/preview controllers are proven for invalid identifiers, not for time travel past `expires_in` / `expires_at`. The intended contract is that they match blob URLs.

#### Boundary timing

Given an application identifier that expires at time T or after duration D  
When a client requests it clearly before T / before D elapses  
Then they receive the file  
When they request it clearly after  
Then they get not found.

**Open at the exact instant:** current revision evidence does not show whether a request at exactly T succeeds or is not found. The outcome of this work must state that rule in developer-facing language so “predictable” includes the boundary, not only “later.”

#### Expiry vs cache (counterexample / decision)

Given a proxy URL generated with a short expiry that was successfully fetched while valid  
When a later client requests the same URL after the identifier would no longer be accepted, but a public cache still holds the earlier successful response  
Then, under today’s observed headers, the cached file can still be served.

This is either:

- **accepted contract:** expiring a proxy URL stops *origin* acceptance; it does not unpublish cached copies, or
- **defect:** an expiring proxy URL must not be advertised as publicly immutable forever.

The work is not done until this choice is explicit. Hypothesis: treat it as accepted contract and make it unmistakable, because changing cache headers is a behavior change beyond “predictable semantics.” Correct this if the intent is to change it.

#### Expiry is not access control (counterexample)

Given a developer who expires application URLs in one hour instead of authenticating downloads  
When a recipient shares the URL at minute five  
Then that recipient and anyone they share with can use it until expiry  
And expiry does not implement “only this user may download.”

### Steering evidence

We would treat the work as succeeding when a developer who only reads the product contract can correctly predict, for a named combination of identifier permanence, proxy vs redirect, and public vs private storage:

- whether a client gets the file now
- whether they get it after the relevant clock
- what status they see on tamper/expiry
- whether a cache is allowed to keep serving a successful response

We would investigate or reconsider the framing if:

- developers still cannot tell application-identifier expiry from service-URL expiry after the contract is published
- “not found” on expiry is treated as a bug by the intended audience and they need a distinct expired signal (that would be a different outcome)
- the real pain is authorization (“only my users can download”), which this work explicitly does not solve
- making expiry predictable requires changing proxy cache headers, which would mean the appetite was larger than Small Batch

### Open questions

1. **Exact instant of expiry.** Inclusive or exclusive of `expires_at` / the end of `expires_in`? Current tests never hit the instant.
2. **Proxy cache vs expiring application URLs.** Document today’s public immutable cache as contract, or treat it as a defect?
3. **Deleted file with a still-valid identifier.** Controllers are tested for invalid signatures, not for a valid identifier whose blob was removed. Hypothesis: the client still sees not found. Confirm if that must be part of the contract.
4. **`expires_at` vs `expires_in` in developer-facing docs.** Behavior exists for both on application URLs; the overview currently leads with `expires_in`. Should both be first-class in the contract?
5. **Appetite confirmation.** Is this Small Batch (predictability of current behavior, including naming surprises) or a behavior change at the cache/expiry edges?

**Application download URLs embed that identifier and inherit the same default.** `rails_storage_proxy_url` / `rails_storage_redirect_url` take `expires_in` (default `urls_expire_in`, which is nil) and `expires_at`, and put the resulting signed id in the path. Default `urls_expire_in` is nil (permanent). Guides and controller comments: URLs “never expire” unless `expires_in` or `config.active_storage.urls_expire_in` is set.

**Invalid or expired application identifiers are not found.** Blob proxy/redirect tests: junk signed id → 404; URL with 1-minute `expires_in` or `expires_at` works now and is 404 after 2 minutes; with `urls_expire_in = 1.minute`, a default-generated URL works now and is 404 after 2 minutes. Variant/preview tests: invalid blob id or invalid variation key → 404. They do **not** time-travel an expiring representation URL.

**Service URLs are a second clock.** `url` defaults `expires_in` to `service_urls_expire_in` (5 minutes). Private services emit a short-lived signed URL; public services emit a lasting public URL. Disk public generation passes no expiry; S3/GCS public tests fetch the public URL with HTTP 200 and no temporary signature. Redirect controllers send the client to `@blob.url` / `@representation.url` and set `Cache-Control` from that 5-minute default (`max-age=300, private` in the blob redirect test).

**Proxy vs redirect cache headers differ on purpose.** Redirect: 302 to the service URL, `max-age=300, private`. Proxy success: file body, `max-age=3155695200, public, immutable`. Proxy download miss: 404 + `no-cache`. Proxy unexpected error: 500 + `no-cache`. Same no-cache failure headers exist for representation proxy.

**Public vs private is about the service URL, not the application URL.** Application proxy/redirect URLs are publicly reachable if the identifier is known; guides warn they are not access control. Public vs private changes whether `url` is lasting or five-minute-signed.

**Variants use the blob’s signed id plus a variation key.** Representation routes take `signed_blob_id` and `variation_key`. Representation `url` uses the same `service_urls_expire_in` default. Representation redirect/proxy comments match blob controllers on permanent-by-default application URLs and optional `expires_in`.

**Boundary timing is coarse in tests.** Established: valid at generation; invalid after a later travel (1 minute expiry, 2 minute travel). Not established: request at the exact expiry instant; representation URLs after expiry; valid identifier after the blob is deleted (SetBlob rescues invalid signature only).

**Docs already distinguish the two clocks, incompletely.** Overview: application URLs never expire by default; `expires_in` per URL or `urls_expire_in`; service URLs default to 5 minutes via `service_urls_expire_in`; expiry is not access control. Configuring guide: `service_urls_expire_in` default 5 minutes for `url` / variant / preview / direct-upload service URLs; `urls_expire_in` default nil. `expires_at` is implemented and tested on blob application URLs but is not the overview’s primary example.
