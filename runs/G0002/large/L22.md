**Problem frame:** An application developer already has a persisted Active Record instance and needs one action that starts a transaction, locks that row, and then runs work that must commit or roll back together. Today that action is `with_lock`. When the work also needs a non-default lock clause and transaction wrapping (`requires_new`, `joinable`, isolation), the developer has to combine two independent requests in one call, while lock SQL and isolation support differ by adapter. Getting the combination wrong is easy; the failure is often a database error, a transaction-isolation error, or a silent join into an outer transaction rather than a clear “this lock-and-transaction request cannot be honored.”

This is a shaping brief, not a design. It does not choose a call shape, control flow, or code change. Current behavior is taken from pessimistic locking, reload, relation locking, transaction isolation, guides, and locking tests. Combinations without a dedicated `with_lock` example are labeled as such.

**Evidence inspected:** locking API and docs; reload/missing-row behavior; relation lock `true` / `false` / string; transaction isolation and nesting errors; [pessimistic locking tests](file:///home/user/workspace/repo/activerecord/test/cases/locking_test.rb), [custom locking tests](file:///home/user/workspace/repo/activerecord/test/cases/custom_locking_test.rb), isolation tests, and the querying guide. Not observed: a dedicated `with_lock(false)` example, a dedicated missing-row `with_lock` example, or a dedicated unsupported-clause `with_lock` example.

# Current observable baseline

Without arguments, `with_lock` wraps the block in a transaction, reloads the persisted row with the default exclusive lock (`FOR UPDATE` on adapters that emit it), and yields the current transaction object so commit callbacks can be registered. PostgreSQL tests assert the `FOR UPDATE` SQL and that the yielded object is the current transaction. A successful block persists; an exception in the block rolls the wrapped work back.

A custom clause is a raw SQL fragment appended to the reload. PostgreSQL tests use `FOR SHARE NOWAIT` on `lock!`. MySQL tests use `LOCK IN SHARE MODE` on relation `lock`. SQLite tests treat `FOR UPDATE` as a no-op lock string. The guide says a clause the database cannot parse or honor raises `ActiveRecord::StatementInvalid`. There is no dedicated `with_lock` example for an unsupported clause.

`false` as a lock request is defined on relation locking: it does not append a lock clause. Reload only applies a lock when the lock request is truthy, so `with_lock(false)` is expected to wrap a transaction and reload without `FOR UPDATE`. That combination is not covered by a dedicated `with_lock` test.

Transaction options on `with_lock` are the same wrapping options as `transaction`: `requires_new`, `joinable`, and `isolation`. Tests show `requires_new: true, joinable: false` starts a distinct, non-joinable inner transaction. Isolation on `with_lock` is asserted only on PostgreSQL (`isolation: :read_uncommitted`). mysql2, trilogy, and PostgreSQL can set isolation; SQLite only `read_uncommitted`, and only with shared-cache enabled. Unsupported isolation, joining an open transaction with a conflicting isolation, and setting isolation on a nested/savepoint transaction raise `ActiveRecord::TransactionIsolationError`. SQLite’s shared-cache restriction is a different error.

Safety already visible to callers:

- A persisted dirty record refuses to lock: a `RuntimeError` naming the changed attributes. Tested on `lock!`, not on `with_lock`.
- If the row is gone at reload, `reload` raises `ActiveRecord::RecordNotFound`. Not tested on `with_lock`.
- Write-prevention mode (`while_preventing_writes`) raises `ActiveRecord::ReadOnlyError` (“Lock query attempted while in readonly mode”) for default `with_lock` and custom-clause `with_lock`. Nested `while_preventing_writes(false)` allows the lock again.

PostgreSQL also rejects `SELECT ... FOR UPDATE` on an outer join; that is relation `lock`, not instance `with_lock`, but it is the same class of adapter-specific lock refusal.

# Desired outcomes

After this work, a developer can request, in one action, both a lock style and transaction wrapping for a persisted instance, and can tell from the result whether that request was honored.

1. **Default lock.** Omitting a lock style still means exclusive row lock inside a transaction, then the block runs against the locked instance.
2. **No lock SQL.** A `false` lock style still wraps a transaction and reloads, but does not ask the database for `FOR UPDATE` (or equivalent). It is not silently upgraded to the default lock.
3. **Custom clause.** A database-specific clause is sent on the lock/reload. If that adapter/database cannot honor it, the developer sees a failure for that request, not a successful unlocked block.
4. **Dirty persisted record.** Unpersisted in-memory changes still block locking. The instance is not reloaded in a way that would drop those changes. The developer sees which attributes were dirty.
5. **Commit and rollback.** Work that finishes in the block is committed with the wrapping transaction. An exception in the block rolls that work back; the persisted row matches the pre-block state.
6. **Yielded transaction.** The block receives the transaction object for this wrapping, and can register after-commit (and similar) callbacks on it.
7. **Transaction wrapping options.** `requires_new`, `joinable`, and `isolation` have the same meaning as when used on `transaction`. The developer can observe a new/non-joinable inner transaction when they asked for one, and can observe the isolation they asked for when the adapter allows it.
8. **Nesting.** Nested lock-and-transaction requests either join, take a savepoint, or refuse isolation according to the same transaction rules developers already rely on. They do not silently change isolation of an outer transaction.
9. **Missing row.** If the row cannot be reloaded because it is gone, the developer sees `ActiveRecord::RecordNotFound` (or an equally specific “this row is gone” failure). The block does not run as if the lock succeeded.
10. **Write-prevention.** In write-prevention mode, both default and custom lock requests fail with `ActiveRecord::ReadOnlyError` before the block runs as a successful lock. Temporarily disabling write-prevention allows the lock again.
11. **Adapter differences.** Supported clauses and isolation levels remain adapter- and database-specific. Unsupported combinations fail in a way the developer can observe at the `with_lock` call, using the same error families already used for lock SQL vs isolation (`StatementInvalid` / `TransactionIsolationError`, plus SQLite’s shared-cache restriction). This work does not invent a portable lock dialect.

# Non-goals

- Changing optimistic locking, relation `lock` / `find` locking, or `lock!` except insofar as `with_lock` already depends on them.
- Making every adapter accept the same lock SQL or isolation levels.
- Specifying a new call signature, keyword vs positional lock, or internal ordering of transaction vs reload.
- Redefining write-prevention, `ActiveRecord::Rollback` swallowing, or concurrent lock-wait/deadlock behavior (existing tests call that cumbersome and mostly unasserted).
- Quietly treating SQLite `FOR UPDATE` as a real exclusive lock; current tests document it as a no-op string.

# Risks

- Call sites that already pass a clause plus transaction options must keep working; a “safer” combination must not drop the clause when options are present, or drop options when a clause is present.
- Isolation plus nesting already fails on purpose. Making `with_lock` “easier” must not start setting isolation on a joined or savepoint transaction.
- A custom clause that one adapter no-ops (SQLite `FOR UPDATE`) can look like success while another adapter locks. Callers can misread that as portability.
- Dirty-record failure is a generic `RuntimeError` today. Changing the error type would be user-visible; whether to keep it is open.
- Missing-row and `false` lock behavior are inferred from reload/relation locking, not from `with_lock` tests. Treating them as new product promises without confirming today’s call-site behavior could surprise existing apps.
- Clearer adapter errors could change rescue behavior if `StatementInvalid` or `TransactionIsolationError` were replaced rather than preserved.

# Acceptance examples

Required cases. Each is about what the developer does and what they can observe. None specifies how the call is spelled.

**Default lock.** Given a persisted person with no in-memory changes, when they run work inside `with_lock` with no lock style, they observe a transaction, a reload with the adapter’s default exclusive lock (`FOR UPDATE` where that SQL is emitted), and the block running against that instance.

**`false`.** Given the same persisted person, when they request lock style `false`, they observe a transaction and a reload, and they do not observe `FOR UPDATE` (or equivalent) on that reload. The block still runs.

**Custom clause.** Given PostgreSQL, when they request `FOR SHARE NOWAIT`, they observe that clause on the lock/reload. Given MySQL, when they request `LOCK IN SHARE MODE`, they observe that clause. Given a clause the current database rejects, they observe `ActiveRecord::StatementInvalid` (guide baseline) and the block does not complete as a successful lock.

**Dirty persisted record.** Given a persisted person whose `first_name` was changed in memory and not saved, when they request `with_lock`, they observe a failure that includes `Changed attributes: "first_name"`, and the in-memory change is not discarded by a reload.

**Commit.** Given a persisted person, when the block assigns `first_name` and saves, after `with_lock` returns they observe the new name in the database.

**Exception rollback.** Given a persisted person, when the block saves a new name and then raises, after the exception they observe the original name in the database.

**Yielded transaction.** Given a successful `with_lock`, when the block takes the yielded argument, they observe that it is the current transaction and can register `after_commit` on it.

**`requires_new` and `joinable`.** Given an already open joinable transaction, when they request `with_lock` with `requires_new: true` and `joinable: false`, they observe an inner transaction that is not the outer one and is not joinable.

**Isolation.** Given PostgreSQL (the adapter with a `with_lock` isolation example), when they request `isolation: :read_uncommitted`, they observe that isolation on the current transaction. Given an adapter that cannot set isolation, they observe `ActiveRecord::TransactionIsolationError`. Given SQLite without shared-cache, even `read_uncommitted` is not silently honored.

**Nesting.** Given an outer transaction, when they nest `with_lock` without asking for a new transaction, they observe the work joining the outer transaction (same wrapping rules as `transaction`). When they nest and also request a new isolation, they observe `ActiveRecord::TransactionIsolationError` (“cannot set isolation when joining a transaction” or “cannot set transaction isolation in a nested transaction”), not a changed outer isolation.

**Missing row during reload.** Given a persisted instance whose row was deleted by another connection, when they request `with_lock`, they observe `ActiveRecord::RecordNotFound` (reload baseline). The block does not run as if the row were locked.

**Write-prevention mode.** Given `while_preventing_writes`, when they request default `with_lock` or `with_lock` with a custom clause, they observe `ActiveRecord::ReadOnlyError` and the block does not run as a successful lock. Given a nested `while_preventing_writes(false)`, they observe the lock succeeding again.

# Adapter differences (how users observe them)

Lock clauses are raw SQL. MySQL examples use `LOCK IN SHARE MODE`; PostgreSQL examples use `FOR SHARE` / `FOR UPDATE NOWAIT`; SQLite tests use `FOR UPDATE` as a no-op. A clause the database does not accept is observed as `ActiveRecord::StatementInvalid`. PostgreSQL refusing `FOR UPDATE` on an outer join is the same family of refusal, even though that example is on relation `lock`.

Isolation is not a lock clause. mysql2, trilogy, and PostgreSQL can set `:read_uncommitted`, `:read_committed`, `:repeatable_read`, and `:serializable`. SQLite only `:read_uncommitted`, and only with shared-cache. An adapter that cannot set isolation, an invalid level, joining with a conflicting isolation, or isolation on a nested/savepoint transaction is observed as `ActiveRecord::TransactionIsolationError`. SQLite’s shared-cache requirement is a separate, explicit failure, not a lock-clause error.

Whether a future `with_lock` should keep these two error families distinct is an open product choice; collapsing them would change what callers rescue.

# Steering evidence

Investigate or stop if: a custom clause plus wrapping options causes the default `FOR UPDATE` to be used, or causes wrapping options to be ignored; `false` starts emitting a lock clause; dirty records get reloaded and lose in-memory changes; write-prevention allows a lock; a missing row still yields the block; isolation is changed on a joined/nested transaction; or SQLite no-op locks are documented as exclusive locks.

Reconsider the problem framing if: the remaining pain is only documentation of the existing combination; or if most incidents are lock-wait/deadlock under concurrency, which this brief does not claim to solve.

# Open questions

- Is the remaining pain call-site confusion when combining a clause with wrapping options, uneven errors, missing docs, or all three?
- Should unsupported lock SQL stay `StatementInvalid`, and unsupported isolation stay `TransactionIsolationError`?
- Should dirty-record failure stay a generic `RuntimeError`?
- Is `with_lock(false)` a supported product mode or only a spillover of relation `lock(false)`?
- Should SQLite’s no-op `FOR UPDATE` remain success, or become an observable limitation?

I kept the call shape, argument order, and internal sequence unset on purpose. If the problem is “combining clause + wrapping must be hard to get wrong” rather than “preserve today’s combination and make failures obvious,” that should replace the problem frame before any design work.
