## Assistant

`#strict_loading!` is instance state, not association state. The association object only *reads* that state (plus an optional reflection option) when it is about to hit the database. `:all` forbids that lazy hit on the owner. `:n_plus_one_only` allows it, then turns loaded `has_many` children into `:all` records so the *next* hop is what raises.

### What `#strict_loading!` actually sets

A new record copies class defaults in `init_internals`: `@strict_loading` from `strict_loading_by_default` (false), `@strict_loading_mode` from `strict_loading_mode` (`:all`). So every record is `strict_loading_all?` even when it is not strict-loading.

```736:754:activerecord/lib/active_record/core.rb
    def strict_loading!(value = true, mode: :all)
      unless [:all, :n_plus_one_only].include?(mode)
        raise ArgumentError, "The :mode option must be one of [:all, :n_plus_one_only] but #{mode.inspect} was provided."
      end

      @strict_loading_mode = mode
      @strict_loading = value
    end

    attr_reader :strict_loading_mode

    def strict_loading_n_plus_one_only?
      @strict_loading_mode == :n_plus_one_only
    end

    def strict_loading_all?
      @strict_loading_mode == :all
    end
```

`strict_loading?` is only `@strict_loading`. Mode is independent. That split is the whole `:n_plus_one_only` design.

Disable is the same method: `strict_loading!(false)` writes `@strict_loading = false` and, unless you pass `mode:`, resets mode to `:all`. After that, lazy loads succeed (`test_strict_loading!`).

An invalid mode never writes state; it raises `ArgumentError` with the inspected value. There is no coverage of that path in [strict_loading_test.rb](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb).

### The two modes

| | `:all` (default) | `:n_plus_one_only` |
|---|---|---|
| Owner lazy-loads any association | violation | allowed |
| Loaded `has_many` children | `strict_loading!(false, mode: :all)` — not marked | `strict_loading!` — marked `:all` |
| Loaded `belongs_to` / `has_one` children | not marked | not marked, but **keep** `:n_plus_one_only` mode |
| `CollectionProxy#first` | `find_from_target?` is true → loads the whole collection (and would violate if unloaded) | `find_from_target?` is false → `LIMIT` query, collection stays unloaded |

The gate is `violates_strict_loading?`:

```235:244:activerecord/lib/active_record/associations/association.rb
      def violates_strict_loading?
        return unless find_target?

        return if @skip_strict_loading

        return unless owner.validation_context.nil?

        return reflection.strict_loading? if reflection.options.key?(:strict_loading)

        owner.strict_loading? && !owner.strict_loading_n_plus_one_only?
      end
```

So a violation needs all of:

1. The association still needs a DB load (`find_target?` — not already loaded, and for `belongs_to` the FK must be present).
2. Mutation is not inside `skip_strict_loading`.
3. The owner is not currently validating (`validation_context` is nil).
4. Either the reflection has `strict_loading: true`, or the owner is strict-loading **and not** in `:n_plus_one_only`.

`:n_plus_one_only` fails step 4 for the *owner*. That is why `developer.projects.to_a` and `developer.ship` do not raise. The N+1 catch is pushed onto children via `set_strict_loading`.

### How the flag reaches association objects and children

The association object never stores the flag. `HasManyAssociation` / `BelongsToAssociation` read `owner` and `reflection`.

Children get their own `@strict_loading` only when they are materialized as association targets:

```123:128:activerecord/lib/active_record/associations/association.rb
      def set_strict_loading(record)
        if owner.strict_loading_n_plus_one_only? && reflection.macro == :has_many
          record.strict_loading!
        else
          record.strict_loading!(false, mode: owner.strict_loading_mode)
        end
      end
```

That runs from `Association#find_target` (statement-cache load) and `AssociationRelation#exec_queries` (scoped association queries such as `first`).

`strict_loading_n_plus_one_only?` checks **mode only**, not `strict_loading?`. A `belongs_to` child is therefore `strict_loading!(false, mode: :n_plus_one_only)`: not strict itself, but still in that mode, so *its* `has_many` children get marked.

HABTM (`Developer#projects`) is implemented as `has_many :through`. The live reflection’s `macro` is `:has_many`, so those children take the `has_many` branch.
