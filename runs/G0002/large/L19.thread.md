## Assistant

The claim is **wrong**. **Reject** dropping previous-scheme / unencrypted expansion.

Query equality is a byte comparison against whatever is stored. Current-scheme `serialize` only ever emits one representation. Read/decrypt can walk `previous:` and fall back to plaintext; `WHERE` / `find_by` cannot unless those extra values are bound.

Expansion already no-ops when `previous_types` is empty, so the cheap current-ciphertext path already exists.

```61:64:activerecord/lib/active_record/encryption/extended_deterministic_queries.rb
                if !type.previous_types.empty? && value = options[attribute_name]
                  options[attribute_name] = process_encrypted_query_argument(value, check_for_additional_values, type)
                end
```

`previous_types` is previous schemes plus a `NullEncryptor` type when `support_unencrypted_data?` is on (global or per-attribute). That list is query compatibility, not decrypt compatibility.

---

**Query vs read.** `deserialize` tries the current scheme, then `previous_types`, then returns plaintext if `support_unencrypted_data` is on. `EncryptedBook.find(id).email` can succeed while `EncryptedBook.where(email: value)` misses the same row if expansion is removed. Do not treat decrypt fallback as a substitute for `IN` expansion.

---

**Minimal failing examples** (these are the regressions; not a redesign):

**1. `where(email: value)` + unencrypted data**

```ruby
## config.extend_queries = true, support_unencrypted_data = true
## encrypts :email, deterministic: true
UnencryptedBook.create!(email: "jorge@hey.com")
EncryptedBook.where(email: "jorge@hey.com") # must find
```

Current serialize is ciphertext. Stored value is plaintext. Without the `NullEncryptor` extra bind this is `WHERE email = <ciphertext>` and misses. Already covered by “Finds records when data is unencrypted”.

**2. Array-valued predicates**

```ruby
UnencryptedBook.create!(email: "a@x.com")
EncryptedBook.create!(email: "b@x.com")
EncryptedBook.where(email: ["a@x.com", "b@x.com"]) # must return both
```

Expansion is per element (`Array(value)` + `flat_map` of `previous_types`). Current-scheme-only binds two ciphertexts and drops the unencrypted row. No existing test; add this.

**3. `find_by` vs prepared/bound values**

`CoreQueries#find_by` expands *before* `ActiveRecord::Base#find_by` statement caching. After expansion the value is an `Array`, so `StatementCache.unsupported_value?` is true and it falls through to `where` (`IN` + multiple binds). The `check_for_additional_values` flag stops a second expansion.

Removing expansion would restore a single-bind cached `find_by` (`email = <current ciphertext>`). That is the performance temptation. It is also why unencrypted / previous-scheme `find_by` breaks.

```ruby
UnencryptedBook.create!(email: "jorge@hey.com")
EncryptedBook.find_by(email: "jorge@hey.com") # core path
EncryptedBook.where("id > 0").find_by(email: "jorge@hey.com") # relation path
```

Keep both; they are already in `extended_deterministic_queries_test.rb`.

**4. Per-attribute `support_unencrypted_data` overrides global**

`Scheme#support_unencrypted_data?` uses the attribute flag when set, else the global config. Expansion keys off `type.previous_types`, which includes clean-text only when that method is true.

```ruby
## global false, attribute true
ActiveRecord::Encryption.config.with(support_unencrypted_data: false) do
  UnencryptedBook.create!(email: "jorge@hey.com")
  EncryptedBookWithUnencryptedDataOptedIn.find_by(email: "jorge@hey.com") # must find
end

## global true, attribute false
UnencryptedBook.create!(email: "jorge@hey.com")
EncryptedBookWithUnencryptedDataOptedOut.find_by(email: "jorge@hey.com") # must be nil
```

Removing expansion makes the opted-in case miss even though decrypt still works. Existing tests in `extended_deterministic_queries_test.rb` (lines 59–97).

**5. `previous:` / scheme rotation (query, not decrypt)**

Current serialize with default `fixed: true` uses the *oldest* previous scheme. Rows still stored under a newer scheme, or any previous scheme that is not that oldest one, do not match. `deterministic: { fixed: false }` writes the *newest* scheme; old rows only match via extra ciphertexts. The guide states this; decrypt-with-previous (e.g. `encryption_schemes_test.rb` “can decrypt … previous scheme”) does not cover queries.

```ruby
## encrypts :email, deterministic: { fixed: false },
##   previous: { deterministic: true, downcase: true }  # or a different key/encryptor
## row stored under previous scheme:
EncryptedContact.find_by(email: "Jorge@Hey.com")  # must find
EncryptedContact.where(email: "Jorge@Hey.com")    # must find
```

Also the global-previous query test: `previous = [{ downcase: true, deterministic: true }, { downcase: false, deterministic: true }]` then `encrypts :name, deterministic: true, downcase: false`. `find_by_name("STEPHEN KING")` and `find_by_name("stephen king")` both work because both ciphertexts are bound. Current-only serialize cannot express both.

Add a query test that *writes with a previous type* (`without_encryption` + `previous_type.serialize(value)`) and asserts `where` / `find_by`. Today that is mostly a decrypt test.

**6. `downcase:`**

Downcase is applied in `serialize_with_current` (and on the clean-text previous type). Encrypted `find_by(name: "DUNE")` still works without expansion. Unencrypted rows do not:

```ruby
## downcase: true, support_unencrypted_data: true
UnencryptedBook.create!(name: "dune") # stored cleartext
EncryptedBookWithDowncaseName.find_by(name: "DUNE") # needs NullEncryptor additional value ("dune")
```

Do not use the existing “Works well with downcased attributes” test as proof expansion is unused; that row is encrypted.

**7. `ignore_case:` + `original_name`**

`ignore_case` sets downcase on `name` and stores original case in `original_name`. Queries run against `name`, not `original_name`. `original_name` is a read-path column (`book.name` returns the preserved value). Removing expansion does not break encrypted `find_by_name("dune")` → `"Dune"`. It does break finding an unencrypted `name` while `support_unencrypted_data` is on, and it must not start querying `original_name`.

```ruby
## ignore_case: true
EncryptedBookThatIgnoresCase.create!(name: "Dune")
book = EncryptedBookThatIgnoresCase.find_by_name("dune")
assert_equal "Dune", book.name # read path: original_name

## unencrypted name column, support_unencrypted_data: true
create_unencrypted_book_ignoring_case(name: "Dune")
EncryptedBookThatIgnoresCase.find_by(name: "dune") # query path: needs plaintext bind on name, not original_name
```

---

**What not to do.** Do not replace expansion with “always encrypt with current and re-encrypt old rows.” Do not fold this into uniqueness-validator changes. Do not treat empty-`previous_types` (already unexpanded, statement-cached `find_by`) as evidence the mixed-data path is redundant.

**Regression tests to add, focused:**

- `where(email: [unencrypted, encrypted])` returns both
- previous-scheme ciphertext written with `previous_types.first.serialize`, then `where` / `find_by` / `exists?`
- `deterministic: { fixed: false }` plus `previous:`, mixed old/new ciphertexts
- attribute-level `support_unencrypted_data: true` with global `false` on `where`, not only `find_by`
- `downcase` + unencrypted cleartext
- `ignore_case` + unencrypted `name`, asserting `original_name` is unused in SQL

Existing coverage already kills the unencrypted `find_by` and per-attribute override cases. The claim fails those without any new tests.
