**Problem frame:** An application developer bulk-inserts rows with `insert_all` / `insert_all!` and needs one portable story for “skip or fail on duplicates” (`unique_by:`) and “what this call hands back” (`returning:`). Today the public contract, adapter capability predicates, and bulk-insert tests do not agree across PostgreSQL, SQLite, MySQL, and MariaDB, so the same call can skip, raise, return keys, return nothing, or refuse the options. That makes multi-database apps hard to write and easy to get wrong. The desired progress is a single observable contract: what each adapter will do, refuse, or leave unchanged, without pretending the databases match.

Evidence for current behavior: the public `insert_all` / `insert_all!` contract, adapter predicates (`supports_insert_on_duplicate_skip?`, `supports_insert_conflict_target?`, `supports_insert_returning?`, `supports_expression_index?`), and `insert_all_test.rb`. Implementation was read only to pin stimuli, outcomes, and guards. `record_timestamps` on `insert_all` is documented; most timestamp examples in tests are on `upsert_all`.

---

**Who is in pain, and why it matters**

The actor is a Rails developer inserting many hashes in one call—imports, backfills, association-scoped creates—often against more than one database.

What hurts now:

- Docs say skip-without-`unique_by` treats rows as unique by **every** unique index, and that `unique_by:` (PostgreSQL and SQLite only) narrows that to **one** index. MySQL and MariaDB skip on any unique collision and **reject** `unique_by:`.
- `returning:` is documented for PostgreSQL, SQLite, and MariaDB. MySQL, and MariaDB before 10.5, reject an explicit `returning:` and otherwise return no columns.
- Composite primary keys: on PostgreSQL/SQLite, skip without `unique_by:` errors (`No unique index found for id` when the model’s `primary_key` is only `:id`). Bang does not need `unique_by:`. MySQL/MariaDB skip and bang both work without it.
- `insert_all!` documents `unique_by:` as “check only this index,” but tests only show the option is **accepted** on conflict-target adapters and that a duplicate still raises. Whether bang actually ignores other unique indexes is unverified.
- Skip vs bang atomicity is easy to confuse: skip keeps non-duplicates and leaves existing rows unchanged; bang raises `ActiveRecord::RecordNotUnique` and inserts **no** rows from that call.

---

**Behavioral outcomes** (what should be observable)

1. **Capability is explicit.** If the connected database cannot skip duplicates, target one unique index, or return inserted columns, the call fails with a clear argument error naming that limit. It does not silently ignore `unique_by:` or `returning:`.
2. **Skip (`insert_all`) vs bang (`insert_all!`) stay distinct.** Skip inserts non-conflicting rows and leaves already-stored rows untouched. Bang either inserts the whole batch or inserts none and raises `RecordNotUnique`.
3. **Default skip uniqueness** (no `unique_by:`) skips a row that collides with **any** unique index on the table, including in-batch duplicates, on every adapter that can skip.
4. **Named skip uniqueness** (`unique_by:` where supported) skips only collisions on that unique index (column(s), index name, or expression index). A collision on a *different* unique index raises `RecordNotUnique`. An unknown or non-unique `unique_by:` raises `ArgumentError` (`No unique index found for …`).
5. **Returning** (where supported) defaults to the primary key column(s) of successfully inserted rows; `returning: false` or `[]` returns no columns; attribute lists and known-safe SQL expressions return those values. Unsupported adapters return no columns unless `returning:` is requested, which errors.
6. **Shared guards** hold on every adapter: empty input returns an empty result and writes nothing; mismatched hash keys error with missing/extra keys; values are type-cast and serialized like `create!`; `record_timestamps:` can force or suppress automatic timestamps, and an explicit timestamp in the hash wins.

---

**Non-goals**

- `upsert_all` / replace-on-conflict (contrast only).
- Instantiating models, callbacks, or validations (they stay off).
- Making MySQL/MariaDB honor `unique_by:` or making MySQL honor `returning:` if the database cannot.
- Unifying SQL dialects, adapter internals, or a rollout plan.
- Changing association `create_with` / STI / unknown-attribute behavior except as they already affect these calls.

**Acceptance examples**

Required unless marked illustrative. “Where supported” means the adapter predicate is true; otherwise the call must error as in the adapter table below.

**Adapter table (this revision)**

- **Skip duplicates:** PostgreSQL, SQLite, MySQL, MariaDB — yes.
- **`unique_by:` (choose one unique index):** PostgreSQL, SQLite — yes. MySQL, MariaDB — no; explicit `unique_by:` raises `ArgumentError` (`does not support :unique_by`).
- **`returning:`:** PostgreSQL, SQLite — yes. MariaDB 10.5+ — yes. MySQL, and MariaDB before 10.5 — no; explicit `returning:` raises `ArgumentError` (`does not support :returning`); default is no columns.
- **Expression unique indexes:** PostgreSQL, SQLite — yes. MySQL 8.0.13+ — yes as a database feature; MariaDB — no. `unique_by:` on an expression index still requires `unique_by:` support (so not MySQL/MariaDB).

**1. Duplicate under the default conflict target**

- Given books already include `id: 1`, when the developer calls `Book.insert_all [{ id: 1, name: "Agile Web Development with Rails" }]`, the table count does not change and the existing row is unchanged.
- Given two hashes in one skip call with the same `author_id` and `name` (unique together) and no ids, when they call `insert_all`, exactly one row is inserted (in-batch duplicate skipped on that unique index, including PostgreSQL/SQLite, not only MySQL).
- Given two hashes with the same `id` and different names in one skip call, when they call `insert_all`, one row exists and it has the **first** hash’s name.
- Given an existing book, when they skip-insert a hash that matches a unique index but changes another column (`format:`), count is unchanged and the stored `format` is unchanged (skip is not a hidden upsert).

**2. Named, composite, and expression `unique_by:` (PostgreSQL, SQLite)**

- When they skip-insert with `unique_by: :isbn`, `%i[author_id name]`, `unique_by: :index_books_on_isbn`, or `unique_by: :id`, a non-conflicting row is inserted. Column order of a composite unique index may be reversed and still match.
- Given an existing `id: 1`, when they `insert_all` that same id with `unique_by: :index_books_on_author_id_and_name`, they get `RecordNotUnique` (skip is only for the named index).
- Given a book with `external_id: "abc"` and an expression unique index on `lower(external_id)`, when they `insert_all [{ external_id: "ABC" }], unique_by: :index_books_on_lower_external_id`, count does not change.
- Bang: `insert_all!` / `insert!` with `unique_by: :isbn` inserts a new ISBN. If that ISBN already exists under the index (including a partial unique index that applies, e.g. `isbn` unique when `published_on` is present), bang raises `RecordNotUnique`. **Open:** whether bang with `unique_by:` still raises on a *different* unique index.

**3. Invalid or non-unique `unique_by:`**

- PostgreSQL/SQLite: `unique_by: :cats`, `%i[author_id isbn]`, or `:author_id` (not a unique index) raises `ArgumentError` matching `No unique index`.
- MySQL/MariaDB: any `unique_by:` raises `does not support :unique_by`.

**4. Composite primary keys (`Cart`, table PK `shop_id, id`, model `primary_key = :id`)**

- PostgreSQL/SQLite skip/upsert without `unique_by:` raises `No unique index found for id`. With `unique_by: [:shop_id, :id]`, the row is inserted.
- PostgreSQL/SQLite bang without `unique_by:` inserts.
- MySQL/MariaDB skip and bang without `unique_by:` both insert.

**5. `returning:`**

- Where supported, default `insert_all!` of one book returns an `ActiveRecord::Result` whose columns are `id`.
- `returning: false` and `returning: []` return no columns.
- `returning: [:id, :name]` includes `name` (e.g. `"Rework"`).
- `returning: Arel.sql("UPPER(name) as name")` returns the expression (`"REWORK"`). A raw SQL string that is not known-safe is refused.
- `returning: :title` (alias of `name`) includes `title` where returning is supported.
- MySQL / MariaDB &lt; 10.5: default returns no columns; passing `returning:` raises.

**6. Empty input, mismatched keys, casting, timestamps**

- `insert_all([])` and `insert_all!([])` return an empty result and write nothing.
- Hashes with different keys raise `ArgumentError`: all objects must have the same keys, with `missing:` / `extra:` (e.g. extra or missing `isbn`).
- Unknown attributes raise `UnknownAttributeError`.
- Type casting and serialization match `create!` (array-typed names, custom coder string/hash, JSON-coder string; no double-encoding through a non-idempotent coder).
- When automatic timestamps are on, omitted timestamp columns are set; `record_timestamps: false` leaves them unset; `record_timestamps: true` sets them even if the model config is off; a timestamp present in the hash is kept. *(insert_all examples here follow the documented option and upsert_all tests; insert_all-specific timestamp tests are thinner.)*

**7. Atomicity: skip vs bang**

- Skip: a batch with some unique collisions inserts only the non-colliding rows; existing rows keep their attributes.
- Bang: a batch with any unique-index violation raises `RecordNotUnique` and inserts **no** rows from that call (documented: “in that case, no rows are inserted”).
- Bang does not require a resolvable `unique_by:` / unique index on PostgreSQL/SQLite (composite PK cart inserts without it). Skip on those adapters does, when the default lookup cannot resolve a unique index.

---

**Steering evidence**

Investigate or stop if: skip updates existing columns; bang leaves partial rows from the same call after `RecordNotUnique`; `unique_by:` or `returning:` is ignored on an adapter that cannot support it; PostgreSQL/SQLite default skip fails in-batch duplicates on a non-PK unique index; MySQL/MariaDB skip starts requiring `unique_by:`; returning includes skipped rows rather than successfully inserted ones.

Reconsider the framing if the real pain is upsert/replace, or if developers only ever use one database and the portable matrix is unused.

---

**Open questions**

1. Should `insert_all!`’s `unique_by:` **narrow** uniqueness to one index (as the docs say), or only be accepted for API symmetry while every unique index still raises?
2. For composite PK models whose `primary_key` is not the full table PK, should skip-without-`unique_by:` keep erroring on PostgreSQL/SQLite, or skip on the table’s composite PK like MySQL/MariaDB?
3. Is version-split MariaDB returning (10.5+ vs older) the intended portable story, or should callers treat MariaDB like MySQL unless they opt in?
4. Should skipped rows ever appear in `returning:` results, or only rows actually inserted? (Docs: successfully inserted records.)
5. Confirm `record_timestamps:` on `insert_all` / `insert_all!` is the same as on `upsert_all`; tests lean on upsert.

---

This is a working specification, not a locked one. Correct the problem frame, adapter splits, bang-`unique_by` meaning, or composite-PK default if any of those is the wrong outcome.
