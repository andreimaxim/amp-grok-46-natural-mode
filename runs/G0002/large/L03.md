This is a **new capability**, not a defect: mixed-key collapse is the documented contract today. The missing piece is a way to notice that configuration data was discarded.

I inspected the public indifferent-access contract, its tests, and live conversion. Construction, `update`, and `merge` all collapse `:key` and `"key"` into one entry. Nested hashes and hashes inside arrays are converted the same way. The source hash is left unchanged. For a **single** regular hash that contains both forms, the surviving value is unspecified. For **separate** hashes passed to `update`/`merge`, later arguments overwrite earlier ones on purpose.

**Problem frame:** A developer ingesting configuration (defaults, YAML/JSON, overrides) into an indifferent-access hash needs both values when the same name arrives as a symbol and as a string. Today one value disappears, the survivor is not guaranteed, and nothing reports the loss—so a timeout, host, or credential can be wrong with no signal.

**Behavioral outcome:** After converting or updating with mixed string/symbol names, the developer can tell that a value was discarded. Ordinary indifferent access, last-write-wins across separate hashes, and hashes with no mixed pair stay as they are unless the developer opts into something stricter.

**Example — core, single hash:** Configuration is `{ :timeout => 5, "timeout" => 30, :host => "a" }`. After indifferent conversion the result has one `timeout` and `"a"` for host. Today the caller cannot tell that a timeout value was dropped. Desired: that discard is observable.

**Example — nested and lists:** `{ database: { :timeout => 5, "timeout" => 30, pool: 2 } }` and `{ servers: [{ :port => 80, "port" => 443 }] }` collapse the inner pairs the same way. Desired: the nested discard is observable, not only a top-level one.

**Example — multi-hash update:** Updating with `{ :a => 1, "a" => 2 }` is the same intra-hash collapse (unspecified survivor). Updating with `{ "key" => "from-string" }` then `{ key: "from-symbol" }` is ordinary later-wins; that is not the discarded-data problem unless we decide otherwise.

**Counterexample:** `{ timeout: 5 }` converted and read as `hash["timeout"]` still returns `5`. Successive writes `h[:k] = "sym"; h["k"] = "str"` still leave `"str"`.

**Compatibility:** Silent collapse and unspecified survivor remain the default. Hashes without mixed pairs, nested conversion, non-mutation of the source, and later-hash overwrite must not change for existing callers.

**Steering evidence:** Success if mixed-key ingestion can show that a value was discarded, including nested cases, without changing default collapse. Investigate if detection is noisy on ordinary overwrite, misses nesting, or changes hashes that never mixed keys. Reconsider the framing if the real pain is choosing a survivor or refusing mixed keys, rather than noticing loss.

**Open questions:**
- **Opt-in:** Default remains silent, or does every conversion start reporting?
- **Error vs observation:** Fail the conversion, or convert as today and surface the discard?
- **Key disclosure:** Report that *some* name collided, or name the keys and dropped values (config may be secret)?
- **Performance:** Is a cost on large nested conversions acceptable, or only when explicitly requested?

I treated “detect discarded data” as the outcome, not “pick a winner” or “always refuse mixed keys.” Correct that if the intent is stricter.
