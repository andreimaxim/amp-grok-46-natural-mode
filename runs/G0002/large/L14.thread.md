## Assistant

**Problem frame:** A Rails app or library author needs a configuration name to be present and usable at boot or at the point of use. Today they can require that with a bang-style read on `ActiveSupport::OrderedOptions` (and on `InheritableOptions`, including inherited names). When that required read fails, every failure looks the same, so they cannot tell whether the name was never set, was set to a blank value, or was inherited and then overridden to blank. Optional reads make “never set” and “set to nil” look identical. That is the pain this work should remove, without changing successful reads or Hash-like ordering.

Evidence for current behavior comes from [ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb), [ordered_options_test.rb](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb), [blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb), the credentials bang example in [security.md](file:///home/user/workspace/repo/guides/source/security.md#L1745-L1751), and a runtime check for bang cases the tests do not name (false, whitespace-only strings, empty collections). Tests do not assert those extra blank cases; source plus `Object#blank?`/`presence` plus that runtime check do.

---

### Current observable behavior

**Symbol and string assignment and lookup.** Assigning through a symbol or a string stores the same name. Reading through a symbol, a string, or a dynamic reader returns that value. Insertion order is preserved, and later string/symbol assignments show up as symbols in iteration and `to_h`.

- Assign `a["else_where"] = 56`, then `a[:else_where]` is `56`; size counts one name. [test_usage](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L10-L27)
- After `a[:allow_concurrency] = true` then `a["else_where"] = 56`, iteration is `[:allow_concurrency, true]` then `[:else_where, 56]`. [test_looping](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L29-L42)
- Mixed writers (`one =`, `[:two] =`, `["three"] =`) yield `{ one:, two:, three: }` in that order. [test_ordered_options_to_h](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L155-L164)
- `key?` is true for the symbol form and false for the string form of the same name. [test_ordered_options_key](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L216-L227)

**Dynamic readers and writers.** An unset name’s reader returns `nil`, same as `[]` / string `[]`. Setting `a.allow_concurrency = true` then `false` updates that name in place; `a.else_where = 56` is readable as `a.else_where`. [test_method_access](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L64-L81), class examples at [ordered_options.rb L19–L26](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L19-L26).

**`respond_to?`.** Any name answers true, including a never-assigned reader, its writer, and its bang form. [test_introspection](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L109-L114) (`:blah`, `:blah=`); [test_raises_with_bang](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L116-L117) (`:foo!`). Runtime: `respond_to?` is also true for a never-seen bang name. You cannot use `respond_to?` to tell whether a name exists.

**`dig`.** First segment accepts a symbol or a string and returns the value; further segments follow ordinary Hash `dig` (including `nil` when an index is missing). ---

### User pain

The author is trying to fail fast when a required setting is unusable. Today:

1. **Every required-read failure is the same sentence.** Never set, `nil`, `false`, whitespace, and empty collections all say `:<name> is blank`. The author cannot tell what to fix: assign it, stop assigning nil, stop assigning false, trim env/YAML whitespace, or undo a child override.
2. **Optional reads hide the same distinction.** `config.x.payment_processing.not_set` is `nil` ([configuring.md](file:///home/user/workspace/repo/guides/source/configuring.md#L4728-L4730)), which is also what you get after an explicit `= nil`.
3. **Inheritance hides who won.** A child can fail a required read because the parent never set it, the parent set blank, or the child overrode a good parent value with blank. The failure does not say which.
4. **Probing does not help.** `respond_to?` is always true, so it cannot confirm that a name exists before a required read.

This matters at boot and in credentials/custom config, where the next action is “set this” vs “stop blanking this” vs “look at the parent.”

---

### Desired outcomes

These are externally observable claims. They do not add names, types, or storage.

1. **A successful required read is unchanged.** If today’s bang read returns a value, it still returns that same value. That includes non-blank strings, `true`, `0`, and other present objects, including values seen only by inheritance and values that override a parent.
2. **A failed required read is diagnosable.** When a required read still fails, the author can tell at least:
   - the name that was required;
   - whether that name was never assigned in the object being read;
   - whether it was assigned a blank value (`nil`, `false`, whitespace-only string, empty collection);
   - for inheritable options, whether the blank value came from the parent or from a child override of a parent name.
3. **Optional reads stay optional.** Unset ordinary readers, `[]`, string `[]`, and `dig` still return `nil` and do not raise.
4. **Assignment, lookup, and order stay as they are.** Symbol/string writers still alias; readers still accept both; `key?` stays symbol-true / string-false; iteration / `to_h` / `keys` keep Hash insertion order and inheritable parent-then-child order with child overrides replacing values.
5. **`respond_to?` stays universally true** for these dynamic names, unless a later compatibility decision says otherwise (open; see below).

Hypothesis, labeled: “easier to understand and diagnose” means **richer failure feedback for the existing failure set**, not a new success set. `false` and whitespace-only strings still fail a required read.

---

### Non-goals

- Changing which values succeed a required read (`false`, `nil`, `""`, whitespace, `[]` remain failures).
- Changing optional-read results, Hash-like ordering, or symbol/string aliasing on assign/lookup/`dig`.
- Redesigning `Rails.application.config`, `config.x`, credentials files, or encrypted-configuration `require`.
- Changing global `blank?` / `presence`.
- New configuration surfaces, new required-read spellings, or new inspection APIs (out of scope here; not proposed).
- Making `respond_to?` a presence test, unless compatibility review later asks for that.
- Performance, internals, or how values are stored.

---

### Compatibility boundaries

Must not change:

- Successful bang/ordinary return values and object identity of those returns (tests assert `a.foo == a.foo!` for a present value).
- `KeyError` as the failure kind for a failed required read (callers and guides already name `KeyError`). The message and diagnostic detail may get clearer; the kind stays.
- Symbol/string assignment and lookup aliasing; first-segment `dig` symbolization; missing `dig` → `nil`.
- Hash insertion order; inheritable `to_h` / `keys` / `each` merge order; `overridden?` meaning (parent has name and child has its own).
- Ordinary missing reader → `nil`.
- `respond_to?` true for arbitrary reader/writer/bang names, unless explicitly reopened.

May change:

- The text and diagnostic content of the `KeyError` on a failed required read, so missing vs assigned-blank vs inherited-blank vs overridden-blank can be told apart.

### Example journeys

**J1 — Required setting is present (core success).**  
An author assigns `secret = "abc"` (or inherits `"abc"` and does not override). They require `secret`. They get `"abc"`, same as the ordinary read. No error.

**J2 — Required setting was never assigned (core diagnosis).**  
They never assign `api_key`. Ordinary `api_key` is `nil`. Required `api_key` fails. The failure names `api_key` and makes it clear it was **not assigned**, not that it was assigned blank. Today both say `:api_key is blank` ([L31](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L31), [L125](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L125)).

**J3 — Required setting is explicit `nil`.**  
They assign `api_key = nil`. Ordinary read is `nil`. Required read fails and makes it clear the name **is assigned** and the value is `nil`. Distinct from J2.

**J4 — Required setting is `false` (boundary).**  
They assign `allow_concurrency = false` (a real config pattern in [test_usage](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L21-L24)). Ordinary read is `false`. Required read still fails (compatibility). Diagnosis says the name is assigned `false`, not “missing” and not a vague “blank” that could be `nil` or `""`.

**J5 — Whitespace-only string from env/YAML (boundary).**  
They assign `token = "   "` or `"\u00a0"`. Ordinary read returns that string. Required read fails and shows that a whitespace-only string was assigned, so they look at stripping/source data rather than “did I forget to set it?”

**J6 — Child inherits a good parent value (inheritable success).**  
Parent has `foo = :bar`. Child does not override. Child required `foo` returns `:bar`. [test_inheritable_options_with_bang](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L128-L132).

**J7 — Child overrides parent with blank (inheritable diagnosis).**  
Parent has `foo = :bar`. Child sets `foo = nil`. Child required `foo` fails and shows the child **overrode** a parent value with blank. Today it only says `:foo is blank` ([L134–L137](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L134-L137)).

**J8 — Parent held blank, child did not override (inheritable diagnosis).**  
Parent has `foo = nil`. Child does not assign `foo`. Child required `foo` fails and shows the blank comes from the parent, not from a child assignment.

**J9 — Counterexample: optional read of a missing nested name.**  
`Rails.configuration.x.payment_processing.not_set` remains `nil` and does not raise. [configuring.md](file:///home/user/workspace/repo/guides/source/configuring.md#L4728-L4730). This work does not turn optional reads into required reads.

**J10 — Counterexample: order and aliasing.**  
Assign `z`, then `[:a]`, then `["m"]`. `to_h` keys stay `[:z, :a, :m]`. Reading `"z"` and `:z` still match. A required-read diagnosis must not reorder or split those names.

### Acceptance evidence

**Success looks like:**

- Present required reads, including inherited present values, still return the pre-change value.
- A required-read failure for a never-set name is visibly different from a failure for an assigned blank (`nil`, `false`, whitespace, empty collection).
- On inheritable options, a failure after a child blank override is visibly different from a failure that only exists because the parent is blank or unset.
- Optional missing reads still return `nil`; `dig` of a missing name still returns `nil`; iteration order of mixed symbol/string writes is unchanged.
- Existing `KeyError` rescues around bang reads still see a `KeyError`.
- Guides that show `KeyError: :some_api_key is blank` can be updated to the clearer failure text without changing the “bang means required” story.

**Investigate the implementation, not the outcome, if:** successful returns change; `false` or `0` flip success/failure; string/symbol aliasing breaks; order of `to_h`/`keys`/`each` changes; optional reads start raising.

**Reconsider the framing if:** authors still cannot choose a next action from the failure (set it vs stop blanking it vs inspect parent vs child); or they needed `false` to be a valid required boolean and this framing wrongly kept it as a failure (that would be a different product: change the success set).

**Stop if:** the only remaining complaints are about `blank?` in general, `config.x` auto-vivification, or credentials `require` vs bang—those are separate surfaces.

### Open questions

1. **How fine-grained must diagnosis be?** Distinguishing never-set vs assigned-blank is required for the outcome above. Distinguishing `nil` vs `false` vs whitespace vs `[]` is included because those drive different fixes; collapse them only if you want a smaller change.
2. **Should `respond_to?` stay always-true?** Treated as compatibility preserve. Reopen only if diagnosis without a required read is in scope.
3. **Credentials bang vs `require`.** Same OrderedOptions failure vs encrypted `Missing key` is user-visible. This brief does not change `require`; whether credentials bang should match `require`’s wording is unsettled and should not silently expand scope.

This is the working product brief, not an implementation sketch. Correct the failure-set hypothesis (especially `false`) or the inheritance diagnostic depth if those are wrong.
