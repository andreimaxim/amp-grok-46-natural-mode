# 2. What `performed?` means

## Definition

**`actionpack/lib/action_controller/metal.rb`, `performed?` and adjacent response methods (approximately lines 240-275 in the 372-line file)**

```ruby
def response_body=(body)
  if body
    body = [body] if body.is_a?(String)
    response.body = body
    super
  else
    response.reset_body!
  end
end

# Tests if render or redirect has already happened.
def performed?
  response_body || response.committed?
end
```

`performed?` does not return a normalized Boolean. It returns either:

1. `response_body`, when truthy; or
2. the result of `response.committed?`.

Therefore, “performed” means that the controller has assigned a response body **or** the response has already been committed.

## Replacing the response explicitly

Same file:

```ruby
# Assign the response and mark it as committed. No further processing will
# occur.
def response=(response)
  set_response!(response)

  # Force `performed?` to return true:
  @_response_body = true
end
```

Assigning a complete response explicitly forces `performed?` to become true.

## Rendering makes it true

**`actionpack/lib/abstract_controller/rendering.rb:22-34`**

```ruby
# Normalizes arguments and options, and then delegates to render_to_body and
# sticks the result in `self.response_body`.
def render(*args, &block)
  options = _normalize_render(*args, &block)
  rendered_body = render_to_body(options)
  if options[:html]
    _set_html_content_type
  else
    _set_rendered_content_type rendered_format
```

A successful render assigns `response_body`; the following terminator check therefore sees `performed?` as truthy.

# 3. Callback terminator mechanics

## Active Support execution

**`activesupport/lib/active_support/callbacks.rb`, `Filters::Before#call`**

```ruby
def call(env)
  target = env.target
  value  = env.value
  halted = env.halted

  if !halted && user_conditions.all? { |c| c.call(target, value) }
    result_lambda = -> { user_callback.call target, value }
    env.halted = halted_lambda.call(target, result_lambda)
    if env.halted
      target.send :halted_callback_hook, filter, name
    end
  end

  env
end
```

Consequences:

- Conditions are checked first.
- The before callback runs through `result_lambda`.
- Action Controller’s terminator checks `performed?` after that callback.
- When true, `env.halted` is set.
- The halt hook is called with the callback filter and callback-chain name.

## What stops

**`activesupport/lib/active_support/callbacks.rb`, `run_callbacks`**

```ruby
next_sequence.invoke_before(env)
env.value = !env.halted && (!block_given? || yield)
next_sequence.invoke_after(env)
```

A halted environment prevents the wrapped event block from yielding. For controllers, that wrapped block is `super`, which dispatches the action.

Later before callbacks also see `env.halted` and do not run.

Around sequences use:

```ruby
def skip?(arg)
  arg.halted || !@user_conditions.all? { |c| c.call(arg.target, arg.value) }
end
```

Thus not-yet-entered around callbacks are skipped after a halt.

## What happens to after callbacks

**`activesupport/lib/active_support/callbacks.rb`, `Filters::After#call`**

```ruby
def call(env)
  target = env.target
  value  = env.value
  halted = env.halted

  if (!halted || !@halting) && user_conditions.all? { |c| c.call(target, value) }
    user_callback.call target, value
  end

  env
end
```

Action Controller configured:

```ruby
skip_after_callbacks_if_terminated: true
```

Therefore ordinary `after_action` callbacks do not run when a before callback terminates the chain.

Code after `yield` in an **already-entered around callback** is different: normal Ruby control returns to that around callback, so its post-yield code can run if no exception interrupts it. This is not an `after_action`.

## Return value

The general Active Support contract says:

```ruby
# If the callback chain was halted, returns +false+. Otherwise returns the
# result of the block, +nil+ if no callbacks have been set, or +true+
# if callbacks have been set but no block is given.
```

Controller dispatch does not expose that callback return as the HTTP response. The response already produced by the halting callback is what the client observes.


## F. Action attempts a second render

## Guard

**`actionpack/lib/action_controller/metal/rendering.rb`, approximately lines 191-195**

```ruby
# Check for double render errors and set the content_type after rendering.
def render(*args)
  raise ::AbstractController::DoubleRenderError if response_body
  super
end
```

Redirect has the same guard:

```ruby
raise AbstractController::DoubleRenderError if response_body
```

Thus render→render, render→redirect, redirect→render, or redirect→redirect raises when the second operation sees an existing response body.

## Exception and message

**`actionpack/lib/abstract_controller/rendering.rb:9-15`**

```ruby
class DoubleRenderError < Error
  DEFAULT_MESSAGE = "Render and/or redirect were called multiple times in this action. Please note that you may only call render OR redirect, and at most once per action. Also note that neither redirect nor render terminate execution of the action, so if you want to exit an action after redirecting, you need to do something like \"redirect_to(...); return\"."

  def initialize(message = nil)
    super(message || DEFAULT_MESSAGE)
  end
end
```

### Observable result

- The second render/redirect raises `AbstractController::DoubleRenderError`.
- The exception explicitly characterizes this as erroneous control flow.
- Normal exception reporting/logging sees the error and request processing does not complete normally.
- The key contrast is:
  - render/redirect in a completed before callback is a recognized successful chain terminator;
  - continuing within the same callback/action and trying to render or redirect again is an exception.

## Baseline summary

| Situation | HTTP response | Exception | Callback-halt log | Other visible evidence |
|---|---|---:|---:|---|
| Before callback renders | Callback-rendered response | No | Yes, info | Action/later callbacks absent |
| Before callback redirects | 3xx + `Location` | No | Yes, info | Redirect destination; optional source |
| Around callback does not yield | Depends on callback/implicit response | No | No | Nested callbacks/action silently absent |
| Around exception before yield | Error response via exception handling | Yes | No terminator halt | Stack trace/error reporting |
| Around exception after yield | Action may have performed response, then request errors | Yes | No terminator halt | Stack trace/error reporting |
| Condition excludes callback | Normal action response | No | No | Callback side effects absent |
| Second render/redirect | Request fails | `DoubleRenderError` | Not itself a callback halt | Explicit diagnostic message |

The principal confusing-control-flow baseline is the difference between:

1. **A before callback’s method returning after performing a response:** Rails treats that as a successful callback-chain stop and logs it.
2. **Code after `render`/`redirect_to` inside that same Ruby method:** it continues.
3. **An around callback not yielding:** nested execution disappears without the before-callback halt notification.
4. **A second response attempt:** Rails raises loudly.

# 7. Halt-as-success versus halt-as-bug language

## Success/intentional behavior

Controller callback docs:

```ruby
# If the callback renders or redirects, the action will not run. If there are
# additional callbacks scheduled to run after that callback, they are also
# cancelled.
```

The Action Controller guide describes callbacks as potentially halting the request cycle. Tests use names such as:

```ruby
test_rendering_breaks_actioning_chain
test_before_action_redirects_breaks_actioning_chain_for_after_action
test_non_yielding_around_actions_do_not_raise
```

These tests explicitly establish response-performing before callbacks and non-yielding around callbacks as supported, non-exceptional behavior.

## Bug/error behavior

`DoubleRenderError::DEFAULT_MESSAGE` says:

```text
Render and/or redirect were called multiple times in this action.
Please note that you may only call render OR redirect, and at most once per action.
Also note that neither redirect nor render terminate execution of the action...
```

Redirect documentation similarly warns:

```ruby
# Statements after `redirect_to` in our controller get executed, so
# `redirect_to` doesn't stop the execution of the function.
```

The source therefore draws the boundary at **multiple response attempts**, not at the first render/redirect that intentionally stops a before-action chain.

## Halting mechanism

Action Pack defines one `:process_action` callback chain around normal action dispatch:

```ruby
define_callbacks :process_action,
  terminator: ->(controller, result_lambda) {
    result_lambda.call
    controller.performed?
  },
  skip_after_callbacks_if_terminated: true
```

— [`actionpack/lib/abstract_controller/callbacks.rb` lines 34–38](https://github.com/rails/rails/blob/main/actionpack/lib/abstract_controller/callbacks.rb#L34-L38)

`process_action` runs that chain, with the action itself as the callback block:

```ruby
def process_action(...)
  run_callbacks(:process_action) do
    super
  end
end
```

— [`callbacks.rb` lines 262–269](https://github.com/rails/rails/blob/main/actionpack/lib/abstract_controller/callbacks.rb#L262-L269)

For each **before callback**, Active Support:

1. executes the callback;
2. invokes the terminator;
3. sets `env.halted`;
4. invokes `halted_callback_hook` if halted.

— [`activesupport/lib/active_support/callbacks.rb` lines 163–184](https://github.com/rails/rails/blob/main/activesupport/lib/active_support/callbacks.rb#L163-L184)

Therefore, it is not the callback's return value that halts Action Pack. It is whether the callback has made `performed?` truthy.

Rails documents this directly:

> “If the callback renders or redirects, the action will not run. If there are additional callbacks scheduled to run after that callback, they are also cancelled.”

— [`callbacks.rb` lines 133–142](https://github.com/rails/rails/blob/main/actionpack/lib/abstract_controller/callbacks.rb#L133-L142)

## Before, around, and after behavior

- **`before_action`**: after each callback returns, the terminator checks `performed?`. If true, remaining before callbacks and the action are skipped.
- **`after_action`**: `skip_after_callbacks_if_terminated: true` means after callbacks are skipped when a before callback halts the chain.
- **`around_action`**: it wraps the callback sequence/action. Code before its `yield` has already run; normal unwinding after `yield` follows Active Support’s around-callback semantics. Around callbacks are not themselves evaluated by the before-callback terminator in the same way; whether their inner sequence runs depends on whether they yield.

## Assistant

I have source and test evidence for halt, `performed?`, around-callback skip, and DoubleRenderError. Drafting a proposed shaping brief from that baseline, with no implementation design.

**Problem frame:** An application developer or Rails maintainer investigating a request whose action never ran cannot always tell whether the callback chain stopped because a callback already produced a response (documented, supported behavior), or because control flow went somewhere else that happens to look similar from the outside.

That gap matters because Action Controller treats some stops as successful request completion and others as errors, while a third group produces neither an error nor a halt signal. People debugging “why didn’t `show` run?” are left to reconstruct intent from side effects, skipped work, and a thin existing trail.

**Affected actors**
- Application developers writing `before_action` / `around_action` / `after_action` filters (authentication, redirects, early renders).
- Maintainers and reviewers tracing why an action, later callbacks, or after-work did not run.
- Operators reading request traces who need to classify a finished response versus a silent skip versus a failure.

**Evidence basis:** Current behavior is taken from Action Controller / Abstract Controller callback, rendering, redirecting, and DoubleRenderError source and tests, plus Active Support’s callback terminator and Action Controller’s halt instrumentation/logging. This orb could not execute those tests; claims below are what the source and assertions specify, not a live run.

---

**Current observable baseline**

A `before_action` that returns after rendering or redirecting is a **recognized successful stop**. The terminator asks `performed?` after that callback. If a response body exists or the response is committed, the action does not run, later before callbacks do not run, and `after_action` callbacks do not run (`skip_after_callbacks_if_terminated`). Docs in [callbacks.rb](file:///home/user/workspace/repo/actionpack/lib/abstract_controller/callbacks.rb) state this as intended: if the callback renders or redirects, the action and later callbacks are cancelled.

`performed?` becomes true when `render` assigns a body, when `redirect_to` assigns an empty body (plus location/status), or when a full response is assigned. Render and redirect do **not** stop the Ruby method they sit in; only the chain notices after that method returns. Redirect docs in [redirecting.rb](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/redirecting.rb) say later statements in the same function still run unless the method returns.

What a person can already see for that recognized stop:
- The client gets the callback’s render body or a redirect (`Location`, typically 302).
- No exception is raised for the halt itself.
- An info log of the form `Filter chain halted as :filter rendered or redirected`.
- A `halted_callback.action_controller` notification whose payload is the filter name.
- Redirects also log destination (and optionally source location). The halt wording does not say whether the callback rendered or redirected, which later work was skipped, or whether that stop matched application intent.

An `around_action` that never yields is a **different, quieter stop**. Nested before callbacks, the action, and after callbacks do not run. Rails does not raise. Tests treat this as supported (`test_non_yielding_around_actions_do_not_raise`). This path does not go through the `performed?` terminator and does not emit the halt log/hook. Unless the around callback itself builds a response, HTTP outcome is whatever implicit processing does; the focused tests assert order and “no exception,” not a particular body.

Exceptions in an around callback are already loud: they propagate. Before `yield`, nested work never runs. After `yield`, nested work has already run. An around callback may rescue and then render a successful body.

Conditional `only` / `except` / `if` / `unless` are **not a halt**. The callback is simply absent from that request. No terminator, no halt log.

A second `render` or `redirect_to` in the same action, after a body already exists, is already classified as **erroneous control flow**: `AbstractController::DoubleRenderError`, with a message that render/redirect may happen at most once and do not terminate the Ruby method.

So today, three stories that all can mean “the action didn’t run” are not equally visible: recognized before-callback halt (info + filter name), around-without-yield (silent skip), and double response (exception).

---

**Desired outcomes**

These are claims about what people should be able to observe, not a requirement to add a log, notification, API, or any other channel.

1. After a request whose action did not run, an investigator can classify the stop into one of the stories below without having to reverse-engineer the callback graph from source alone.
2. They can tell a **documented halt** (a before callback produced a response, remaining chain cancelled) from **confusing or accidental control flow** (work after `render`/`redirect_to` in the same method, an around callback that never continued, a callback that was never selected, or a second response attempt).
3. They can tell whether the action and ordinary `after_action` work were skipped as a consequence of that stop, versus never having been eligible.
4. Existing error behavior for a second render/redirect remains a distinct failure signal, not blended into “halted successfully.”

---

**Behavioral examples** (required cases for agreement, grounded in current tests)

**Rendering before callback.** A `before_action` renders `"something else"`; the action would render `"ran action"`; an `after_action` would record that it ran. The client receives `"something else"`. The action does not run. The after callback does not run. No exception. A halt signal names that before filter as having rendered or redirected. This is documented success, not a bug. ([filters_test.rb](file:///home/user/workspace/repo/actionpack/test/controller/filters_test.rb): `test_rendering_breaks_actioning_chain`, `test_before_action_rendering_breaks_actioning_chain_for_after_action`)

**Redirecting before callback.** A `before_action` redirects to another action; the original action and an `after_action` would record that they ran. The client receives a redirect to that location. The original action does not run on this request; the redirect target is not invoked internally. After callbacks do not run. No exception. Halt signal plus redirect destination are visible. Statements after `redirect_to` **inside the same before method** still run unless that method returns; the chain only stops after the method returns. (`test_before_action_redirects_breaks_actioning_chain_for_after_action`)

**Non-yielding around callback.** An earlier `before_action` runs; an `around_action` records that it did not yield; later `before_action`, the action, and `after_action` would record if they ran. No exception. Only the earlier before callback and the around callback’s pre-continue work ran. There is no halt signal of the “rendered or redirected” kind. Nested work is simply absent. (`test_non_yielding_around_actions_do_not_raise`, `test_after_actions_are_not_run_if_around_action_does_not_yield`)

**Exception before yield.** An `around_action` raises before continuing. Nested callbacks and the action do not run. The exception propagates and is visible as a failure, not as a halt. (`test_with_symbol` / `raises_before`)

**Exception after yield.** An `around_action` continues, then raises. Nested work and the action have already run; then the exception propagates. If the action already rendered, this is a failed request after a response was produced, not a clean halt. (`raises_after`)

**Conditional callbacks.** A `before_action` with `if: false`, or `only:` / `except:` that excludes this action, does not run. The action runs normally. This is not a chain stop. No halt signal. Absence of that callback’s side effects is the only external clue unless someone inspects the declared chain. (`test_running_conditional_options`, `test_running_only_condition_actions`, `test_running_except_condition_actions`)

**Second render.** An action (or the same method after an earlier render/redirect) calls `render` or `redirect_to` again while a body already exists. `AbstractController::DoubleRenderError` is raised. The message states that render/redirect may occur at most once and do not terminate method execution. This is the framework’s existing “confusing control flow” error, distinct from a before-callback halt.

**Counterexample that should not be treated as halt:** a callback excluded by `only`/`if` looks, from “filter didn’t run,” similar to “filter ran and stopped the chain.” Those must remain distinguishable.

---

**External success signals** (what would show the outcome exists, without requiring a particular new channel)

Success is distinguishability, not a prescribed instrument.

- Given reproductions of the six examples, an investigator using only externally available request evidence (client response, exceptions, and whatever the framework already emits for that request) can assign each run to the matching story: documented halt, around-without-continue, exception before continue, exception after continue, callback not selected, second-response error.
- Two runs that differ only in halt vs around-without-continue do not collapse into the same “action didn’t run, no error” picture.
- A documented halt still completes as a normal response (body or redirect), not as an exception.
- A second render still fails with `DoubleRenderError`, not as a successful halt.
- A conditional miss still lets the action run.

Evidence that the outcome is **not** met: people still cannot tell a rendering/redirecting before callback from an around callback that never continued; or they start treating documented halt as a failure because the only loud signal is DoubleRenderError.

Evidence the **problem framing is wrong:** investigators already classify these cases reliably from today’s halt line, redirect logs, and exceptions; or the painful case is almost never “which stop happened” and is instead “render/redirect didn’t return from the method.” In the first case, extra observability work is unnecessary. In the second, the problem is method-level control flow, which DoubleRenderError already names.

---

**Explicit non-goals**
- Changing whether a rendering or redirecting `before_action` skips the action and later callbacks.
- Changing whether `after_action` is skipped when the chain is terminated.
- Making `render` / `redirect_to` return from the current Ruby method.
- Changing `DoubleRenderError` semantics or making a first render/redirect in a before callback raise.
- Making a non-yielding `around_action` raise, unless a later product decision says that story is an error.
- Requiring a new log, notification, API, metric, debugger, or UI. Those are possible later means, not part of this outcome.
- Expanding into callback ordering redesign, `raise_on_missing_callback_actions`, or implicit rendering.

---

**Unresolved product questions**
- Is an around callback that never continues the same *kind* of stop as a `performed?` halt, or a separate story that should stay distinct?
- For before-callback halt, is “which filter rendered or redirected” already enough, with the real gap only the silent around path?
- Does “skipped after work” need to be visible, or is knowing that the chain stopped at a named filter enough?
- Who is the primary audience: someone reading development logs, production traces, failing tests, or framework docs?
- Should a before callback that assigns a body without `render`/`redirect_to` count as the same documented halt? `performed?` already treats it that way.
- If an around callback rescues and then renders, is that a successful early response, exception handling, or something investigators must be able to tell apart from a before-callback halt?

This is a proposed understanding for correction, not a confirmed spec. The central claim to accept or reject: the work worth considering is **distinguishability of documented halt from look-alike control flow**, not a mandate to add any particular new signal.
