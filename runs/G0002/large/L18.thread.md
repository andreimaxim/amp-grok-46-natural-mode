## Assistant

**Request changes.** At this revision, `Relation#ids` cannot be reduced to `pluck(*primary_key)`. `pluck` already joins and type-casts, but it does not keep one ID per parent row when includes/eager load multiply rows. That is the behavior `#ids` is specified to preserve.

Current code in [`activerecord/lib/active_record/relation/calculations.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L376-L382):

```376:382:activerecord/lib/active_record/relation/calculations.rb
    def ids
      if !loaded? && has_include?(primary_key)
        return apply_join_dependency.group(*primary_key).pluck(*primary_key)
      end

      pluck(*primary_key)
    end
```

`pluck` only does `apply_join_dependency` then plucks, with no `GROUP BY` ([`calculations.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L315-L317)). `has_include?` is true for `eager_load` and for any present `includes`, even when the include is later preloaded rather than joined ([`calculations.rb`](file:///home/user/workspace/repo/activerecord/lib/active_record/relation/calculations.rb#L407-L409)).

That `group(*primary_key)` branch is the #46503 fix, later kept on purpose in `56c95aee03` (“Delegate `ids` back to `pluck`”). Dropping it reopens the original bug.

```ruby
## same split as includes
```

SQL for the includes path today:

```sql
SELECT ... FROM companies
LEFT OUTER JOIN contracts ON contracts.company_id = companies.id
GROUP BY companies.id
```

Plain `pluck(:id)` emits the same join without `GROUP BY`.

Existing tests already fail under the proposed body. I ran `bin/test test/cases/calculations_test.rb -i /test_ids/` (21 runs, 0 failures) on the current implementation, then compared `ids` vs `pluck(*primary_key)` on the same fixtures. `test_ids_with_includes`, `test_ids_with_eager_load`, and `test_ids_with_includes_and_scope` all assert uniqueness against `map(&:id)`; a `pluck`-only `#ids` returns the duplicated join rows.

### Shape-by-shape

| Shape | Preserved by `pluck(*primary_key)`? |
|---|---|
| Unloaded `includes` / `eager_load` of a collection | **No.** Duplicate parent IDs. |
| Duplicate parent rows from a has_many join | **No.** This is the regression. |
| Scalar PK `group(*primary_key)` | **No.** `"id"` splats to one group column; `pluck` does not group. |
| Composite PK `group(*primary_key)` | **No.** `Cpk::Book` PK is `["author_id", "id"]`. With two chapters: `#ids` → `[[author_id, id]]`; `#pluck(*pk)` → that pair twice. Loaded CPK relations stay unique. |
| Loaded relation | Yes. `!loaded?` already falls through to `pluck`. In-memory records are unique, so loaded includes match. |
| `preload` (no join) | Yes. |
| `joins` without includes | Yes, including duplicates. `#ids` does not unique a plain join today. |
| Order by a non-PK column | Same values only when the include does not multiply rows. `Company.includes(:comments).order(:rating)` matched in the existing test because no extra comments were created. `Company.includes(:contracts).order(:rating)` became `[…, 2, 1]` vs `[…, 2, 1, 1, 1, 1, 1]`. |
| Limit / offset | **No** once a collection join multiplies. `Company.includes(:contracts).order(:id).limit(2)` → `#ids` `[1, 2]`, `#pluck` `[1, 1, 1, 1, 1, 2]`. `apply_join_dependency` uniquifies the limited ID set, then `pluck` still joins children. Current Topic limit/offset tests mostly have 0–1 replies, so they would not catch this. |
| `async_ids` | **No** on the same includes/eager-load relations. `async_ids` is `async.ids`, so it inherits the group path. `async_pluck(:id)` already returns the duplicates. |
| Contradictory scope (`where(id: [])`, `where("0 = 1")`) | Yes. Both short-circuit through `pluck`. Not a reason to drop grouping. |
| `skip_query_cache!` | Yes. The includes path still ends in `pluck`. |

`Relation#none` is not needed here; the failing case is a normal includes/eager-load collection join.
