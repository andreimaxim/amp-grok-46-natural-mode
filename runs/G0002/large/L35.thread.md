def worker_pool_stream_handler(broadcasting, user_handler, coder: nil)

  if user_handler
    -> message do
      connection.perform_work handler, :call, message
    end
  else

  end
end

def stream_decoder(handler = nil, coder:)

      else
        message
      end

Three contracts, from this revision:

**`stream_from` keyword default is `coder: nil`.** Docs and the method signature say a user callback then gets the raw pubsub payload. That matches `stream_decoder` returning `handler` unchanged when `coder` is falsy.

**The default (no-callback) handler ignores that nil.** It substitutes `ActiveSupport::JSON` before decoding, then transmits. Passing `coder: nil` to `stream_from` without a callback is therefore still a JSON retransmitter.

**Server `broadcast` defaults the other way:** `coder: ActiveSupport::JSON`. `coder: nil` skips `encode` and publishes `message` as-is ([broadcasting.rb L59](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L59)).

### Deferred subscription confirmation

The counter starts at 1 so confirmation waits for `subscribe_to_channel` itself ([base.rb L167–172](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L167-L172)). Each `stream_from` increments it; each `ensure_confirmation_sent` decrements and sends only when the counter hits 0 and the subscription was not rejected ([L253–264](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L253-L264)). `transmit_subscription_confirmation` also no-ops after the first send ([L322–331](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L322-L331)).

Observable result: the client gets one `{ "type" => "confirm_subscription" }` after pubsub subscribe succeeds, not when `subscribed` returns.

- One `stream_from`: confirmation arrives after subscribe ([stream_test.rb L139–145](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L139-L145)).
- Two `stream_from`s in `subscribed`: still one confirmation ([L342–343, L394–402](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L394-L402)).
- Manual double `send_confirmation`: still one wire message ([L147–157](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L147-L157)).

### Stopped streams

`on_unsubscribe :stop_all_streams` ([streams.rb L80–82](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L80-L82)) runs from `unsubscribe_from_channel`, which first sets `@unsubscribed = true` ([base.rb L211–216](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L211-L216)).

[`stop_stream_from`](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L121-L129) `String()`s the name, deletes that exact handler from `streams`, and `pubsub.unsubscribe`s it. Other channels on the same broadcasting stay subscribed ([stream_test.rb L193–219](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L193-L219)). [`stop_all_streams`](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L138-L143) unsubscribes every entry then `clear`s the hash ([L159–186](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L159-L186)).

After unsubscribe, further `stream_from` is a no-op (`return if unsubscribed?`). The concurrent test ([L267–318](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L267-L318)) is about that race against `streams.each` in `stop_all_streams`: it asserts no `RuntimeError` from mutating the hash while iterating, not that late streams are delivered.

### Rejected subscriptions

[`stream_or_reject_for`](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L147-L153) is the stream-specific reject helper: present model → `stream_for`; `nil` → `reject`.

`reject` only sets a flag ([base.rb L271–273](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L271-L273)). After `subscribed` returns, `subscribe_to_channel` removes the subscription and transmits `{ "type" => "reject_subscription" }` ([L204–205, L333–343](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L333-L343)). `ensure_confirmation_sent` returns immediately if rejected, so the client never gets `confirm_subscription`.

Evidence: nil to `stream_or_reject_for` yields that rejection envelope and nothing else ([stream_test.rb L125–136](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L125-L136)). The same wire type is asserted for a plain `reject` in [rejection_test.rb L23–36](file:///home/user/workspace/repo/actioncable/test/channel/rejection_test.rb#L23-L36). Rejected channels also ignore later `perform_action` ([L38–53](file:///home/user/workspace/repo/actioncable/test/channel/rejection_test.rb#L38-L53)).

### Decode / encode failures

This revision has **no tests** for encode or decode exceptions. Behavior follows the lack of rescue at those call sites.

- **Broadcast encode** (`coder.encode(message)`) runs in the caller of `broadcast`. A failing coder raises out of `Broadcaster#broadcast`. Instrumentation still wraps the call, so a raised encode still emits `broadcast.action_cable`.
- **Default-handler decode** runs on the pubsub callback thread (`handler.call message`). There is no rescue in `stream_decoder` or `stream_transmitter`. A bad JSON payload raises there; the client gets no `transmit`.
- **User-callback decode** runs inside the worker-pool invocation. [`Worker#invoke`](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L58-L66) rescues `Exception`, logs class/message/backtrace, and calls `handle_exception` if the receiver defines it. A `Proc` does not, so a decode failure is logged and swallowed; the callback never runs.

`coder: nil` on either side skips that `encode`/`decode` call entirely, so those failures cannot occur on that hop.
