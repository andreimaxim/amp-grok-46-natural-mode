`isolate_namespace` is class-definition setup. It does not dispatch requests. It stamps the engine class and the given module so later route drawing, helper inclusion, naming, and mount-time wiring behave as an isolated engine. Request-time work is ordinary Rack dispatch into the engine’s endpoint, plus URL generation through mounted helpers.

## Class-level setup

[`Rails::Engine.isolate_namespace`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L384-L419) runs when the engine class body is evaluated:

```384:419:railties/lib/rails/engine.rb
      def isolate_namespace(mod)
        engine_name(generate_railtie_name(mod.name))

        config.default_scope = { module: ActiveSupport::Inflector.underscore(mod.name) }

        self.isolated = true

        unless mod.respond_to?(:railtie_namespace)
          name, railtie = engine_name, self

          mod.singleton_class.instance_eval do
            define_method(:railtie_namespace) { railtie }
            # table_name_prefix, use_relative_model_naming?,
            # railtie_helpers_paths, railtie_routes_url_helpers
          end
        end
      end
```

Four things always happen on the **engine class**:

1. `engine_name` is set from `mod.name`, not from the engine class name.
2. `config.default_scope` becomes `{ module: underscored mod.name }` on the engine’s config object.
3. `self.isolated = true`.
4. Module singleton methods are installed **only if** `mod` does not already respond to `railtie_namespace`.

[`Application#isolate_namespace`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L390-L392) is the same class method. The multiple-applications test only asserts that `railtie_namespace` is set on the module ([`test_isolate_namespace_on_an_application`](file:///home/user/workspace/repo/railties/test/application/multiple_applications_test.rb#L133-L137)).

A second `isolate_namespace` on the same module still marks **that** engine isolated and still overwrites **that** engine’s `engine_name` / `default_scope`. It does not rebind the module’s `railtie_namespace` or URL-helper methods. The first engine that wins the `respond_to?(:railtie_namespace)` race owns those ([`using namespace more than once…`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1228-L1255)).

## `engine_name` and `isolated?`

`engine_name` is an alias of `railtie_name`. `isolated?` is an alias of the `isolated` flag. Instances delegate both to the class ([`engine.rb` 354–356, 437](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L354-L437)).

Without isolation, [`Railtie.railtie_name`](file:///home/user/workspace/repo/railties/lib/rails/railtie.rb#L178-L181) defaults to `generate_railtie_name(self.name)`: underscore the class name and turn `/` into `_`. `MyEngine::Engine` is therefore `my_engine_engine`, matching the class comment ([`engine.rb` 184–188](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L184-L188)).

`isolate_namespace` always calls `engine_name(generate_railtie_name(mod.name))`, so isolation **replaces** that default with the namespace. `isolate_namespace Bukkits` makes `Bukkits::Engine.engine_name` `"bukkits"` ([integration assertion](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L951-L953)).

`generate_railtie_name` is [`underscore(string).tr("/", "_")`](file:///home/user/workspace/repo/railties/lib/rails/railtie.rb#L250-L252). Nested isolation `Bukkits::Awesome` therefore names the engine `bukkits_awesome`.

An explicit `engine_name "my_engine"` is the documented override ([`engine.rb` 188](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L188)). There is no integration test for combining it with `isolate_namespace`. From the method bodies:

- Call `engine_name` **before** `isolate_namespace`: isolation overwrites `@railtie_name` from `mod.name`.
- Call `engine_name` **after** `isolate_namespace`: later `Engine.engine_name` and `mount`’s default `:as` (`app.railtie_name`) use the assigned string. `table_name_prefix` already closed over the name from isolation (`name, railtie = engine_name, self`) and does not change.

Mount uses that name as the default `:as` ([`Mapper#mount`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L639-L644), [`app_name`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L689-L696)).

## Anonymous or unnamed namespaces

There is no Railties test for `isolate_namespace` on an anonymous module. The executed path is:

[`Inflector.underscore`](file:///home/user/workspace/repo/activesupport/lib/active_support/inflector/methods.rb#L113-L114) returns `camel_cased_word.to_s.dup` when the argument does not match `/[A-Z-]|::/`. `Module.new.name` is `nil`; `underscore(nil)` is `""`; `generate_railtie_name(nil)` is `""`.

- `engine_name` becomes `""` (`railtie_name` does `name.to_s`).

An anonymous `Class.new(Rails::Engine)` **without** isolation hits the same `generate_railtie_name(self.name)` empty-string path when `engine_name` is first read.

## Mount helpers and `main_app`

Two different helpers:

**1. Application named route for the mount point.** `mount Bukkits::Engine => "/bukkits"` with default `:as` uses `engine_name`, so the parent route set defines `bukkits_path` / `bukkits_url` as the script name of the engine.

**2. Mounted helper proxy** for the engine’s **internal** named routes.

[`Mapper#mount`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L644-L717) after `match` calls `define_generate_prefix(app, target_as)` when `app < Rails::Railtie`. That:

- Builds a `script_namer` that calls the parent named route (`bukkits_path`) with the mount’s dynamic segments.
- Calls `app.routes.define_mounted_helper(name, script_namer)` on the **engine** route set.
- Extends the engine route set with `find_script_name` so engine `url_for` gets that prefix.

[`RouteSet::MountedHelpers`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/route_set.rb#L508-L540) is a **shared** module on `ActionDispatch::Routing::RouteSet`. Defining a helper on the engine still appears on `Rails.application.routes.mounted_helpers`. Controllers already `include` that module, so application code can call `bukkits.foo_path`.

The proxy is [`ActionDispatch::Routing::RoutesProxy`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/routes_proxy.rb#L9-L45): missing methods go to the target route set’s `url_helpers`, merging `script_name` from `script_namer`.

[`main_app`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb#L60-L62) is the same mechanism with no `script_namer`:

```
initializer :define_main_app_helper do |app|
  app.routes.define_mounted_helper(:main_app)
end
```

Engine controllers/views use `main_app.bar_path` to reach the application. Isolation test: view renders `foo_path` + `main_app.bar_path` as `/bukkits/foo, /bar` ([lines 964–965](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L964-L965)). Mounted-engine tests cover `main_app.url_for` / `main_app.root_path` from inside `Blog::Engine`, and `blog.posts_path` from the application ([`mounted_engine_test.rb`](file:///home/user/workspace/repo/railties/test/railties/mounted_engine_test.rb#L114-L150)). Sub-path / `SCRIPT_NAME` cases show the proxy merging mount prefix with request script name ([`paths are properly generated…`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1659-L1754)).

A non-isolated engine (Weblog in that same test) still gets a mount helper (`weblog`); isolation is what stops application helpers leaking **into** the engine, not what creates the mount proxy.

## Lazy versus eager route loading

[`Finisher#set_routes_reloader_hook`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb#L160-L185):

| Condition | When routes draw |
|---|---|
| Not `LazyRouteSet` (production / non-local) | At boot |
| `LazyRouteSet` and `config.eager_load` | At boot |
| `LazyRouteSet` and not eager | First `reload_routes_unless_loaded` |

[`Application#reload_routes_unless_loaded`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L168-L169) is `initialized? && routes_reloader.execute_unless_loaded`. [`RoutesReloader#execute_unless_loaded`](file:///home/user/workspace/repo/railties/lib/rails/application/routes_reloader.rb#L57-L82) loads every registered path into every registered route set, including isolated engines.

[`LazyRouteSet`](file:///home/user/workspace/repo/railties/lib/rails/engine/lazy_route_set.rb) forces that reload on `call`, `recognize_path`, `url_helpers` (`ProxyUrlHelpers`), `_path`/`_url` `method_missing`, and mounted-helper `method_missing` (not for `_path`/`_url` names — those stay on the url-helper module). Tests: engine helpers lack `root_path` until invoked; `GET /plugin/` draws; `helpers.plugin_engine.posts_path` draws; `main_app` is defined on the lazy mounted-helpers module after load ([`lazy_route_set_test.rb`](file:///home/user/workspace/repo/railties/test/engine/lazy_route_set_test.rb#L23-L273)).

Isolation does not choose lazy vs eager. It only means the engine’s `default_scope` and named routes appear when that shared reloader first draws.

## What is visible outside the engine

From the isolation integration test ([`isolated engine routes and helpers are isolated…`](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L830-L966)):

- Inside the engine, short helpers: `foo_path` → `/bukkits/foo` (mount prefix from `script_namer`, unnamespaced helper name from isolation).
