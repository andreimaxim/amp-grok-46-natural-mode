`#none` is a sticky Ruby-side null object on a live `Relation`, not an empty array and not the same thing as a contradictory where clause.

```1331:1366:activerecord/lib/active_record/relation/query_methods.rb

    #
    # The returned relation implements the Null Object pattern. ...
    def none
      spawn.none!

    def none! # :nodoc:

      @none
```

Two pieces of state are set together, and they stay independent after that:

- `@none` — instance flag, default `false` in `Relation#initialize`. Not stored in `@values`.
- `where!("1=0")` — a SQL literal in `where_clause`, visible to Arel/`to_sql`/subqueries.

`null_relation?` is just `@none`.

## Chainability

`#none` is `spawn.none!`. Spawn is `clone` (unless already inside a scope method, in which case it is `model.all`, which itself clones `current_scope`).

`initialize_copy` dups `@values` and `reset`s loaded/arel/sql state. It does not touch `@none`. Ruby clone copies the ivar, so every later `where`/`order`/`limit`/`select`/… spawn keeps `@none == true`.

That is why `Developer.none.where(name: "David")` is still a `Relation`, still empty, and still issues no SELECT. Returning `[]` from a scope would not be chainable; this is.

`@none` is outside `@values`, so `unscope` / `except` / `only` / `rewhere` / `invert_where` can strip or invert the `1=0` predicate and the flag still stays on. `reset` also leaves it. The ways off the null object are a fresh relation, or `#or` (below).

`Relation::Merger` re-applies it when the RHS is null:

```70:70:activerecord/lib/active_record/relation/merger.rb
        relation.none! if other.null_relation?
```

So `scope.merge(Post.none)` calls `none!` on the merge target (sets both the flag and `1=0`). Collection associations on new records without an FK do the same via `scope.none!`.

`#or` is the chain that drops null-ness instead of preserving it:

```1237:1245:activerecord/lib/active_record/relation/query_methods.rb
    def or(other)
      if other.is_a?(Relation)
        if @none
          other.spawn
        else
          spawn.or!(other)
        end
```

`Post.none.or(Post.where(id: 1))` is `Post.where(id: 1)` with `@none == false`.

`#and` does not special-case the flag. `Post.none.and(other)` keeps `@none`. `Post.where(id: 1).and(Post.none)` only `|`s where clauses: the result has `1=0` in SQL and `@none == false`.

## Loading: `@none` vs `where_clause.contradiction?`

These are two different empty-result mechanisms.

```1497:1513:activerecord/lib/active_record/relation.rb
        if @none
          if async
            return FutureResult.wrap([])
          else
            return []
          end
        end

        skip_query_cache_if_necessary do
          if where_clause.contradiction?
            [].freeze
          elsif eager_loading?

              apply_join_dependency do |relation, join_dependency|
                if relation.null_relation?
                  [].freeze
```

```99:109:activerecord/lib/active_record/relation/where_clause.rb
      def contradiction?
        predicates.any? do |x|
          case x
          when Arel::Nodes::In
            Array === x.right && x.right.empty?
          when Arel::Nodes::Equality
            x.right.respond_to?(:unboundable?) && x.right.unboundable?
          end
        end
      end
```

```diagram
  exec_main_query
        │
        ▼
   @none? ──yes──▶ [] / FutureResult.wrap([])     ← no skip_query_cache, no adapter
        │
        no
        ▼
   skip_query_cache_if_necessary
        │
        ▼
   where_clause.contradiction? ──yes──▶ [].freeze  ← still enters uncached if flagged
        │
        no
        ▼
   eager_loading? ──yes──▶ apply_join_dependency
        │                       │
        │                       └── relation.null_relation? ──▶ [].freeze
        ▼
   _query_by_sql(arel)
```

`1=0` is a SQL literal. It is **not** a `WhereClause` contradiction. Contradiction is empty `IN ()` and unboundable binds (`where(id: [])`, out-of-range integer binds, etc.).

So:

| Construction | `@none` | `contradiction?` | Load |
|---|---|---|---|
| `Model.none` | true | false | empty, no SQL, before cache skip |
| `Model.where(id: [])` | false | true | empty, no SQL, inside cache skip |
| `Model.where("1=0")` | false | false | SQL `WHERE (1=0)` |
| `Model.where(id: 1).and(Model.none)` | false | false | SQL with `AND (1=0)` |

Eager load has a second `null_relation?` check after `apply_join_dependency` because that path `except`s includes/eager_load/preload and `joins!`s; the flag is cloned onto that relation.

`load_async` goes through the same `@none` branch and returns `FutureResult.wrap([])`.

## Calculations, `exists?`, `include?`

`calculate` short-circuits on `@none` before any Arel/connection work:

- `count` / `sum` → `0`, or `{}` if grouped
- `average` / `minimum` / `maximum` → `nil`, or `{}` if grouped
- async wrappers return `Promise::Complete.new(result)`

`pluck` (and therefore `ids` / `pick`) returns `[]` the same way.

`size` has no `@none` check; unloaded it calls `count(:all)`, which does. `empty?` / `none?` / `any?` / `one?` / `many?` all return the empty-collection answers on `@none` before `exists?` or `limited_count`.

```357:375:activerecord/lib/active_record/relation/finder_methods.rb
    def exists?(conditions = :none)
      return false if @none
      ...
      relation = construct_relation_for_exists(conditions)
      return false if relation.where_clause.contradiction?
```

`exists?` bails on `@none` even when called with an id (`exists?(1)`). The contradiction check is a second, later gate on the constructed exists-relation.

`include?` / `member?`:

- wrong class → `false` (no `@none` check needed)
- loaded, or `limit`/`offset`/`having` present → `records.include?(record)` → `#load` → `exec_main_query` empty
- otherwise → `exists?(pk hash)` → `@none` → `false`

None of those paths hit the adapter on a null relation.

## Query-cache skip state

`skip_query_cache!` is a normal single-value (`skip_query_cache_value`), cloned with `@values`. The wrapper is:

```1539:1544:activerecord/lib/active_record/relation.rb
      def skip_query_cache_if_necessary(&block)
        if skip_query_cache_value
          model.uncached(&block)
        else
          yield
        end
      end
```

On load, `@none` returns **before** that wrapper. A null relation never enters `model.uncached`, never talks to the adapter, and therefore neither reads nor writes the query cache — including when `skip_query_cache_value` is set.

`where_clause.contradiction?` on the load path is **inside** the wrapper. `Model.where(id: []).skip_query_cache!` still runs `uncached`, then returns `[]` with no SQL.

`exists?` is different again: both `@none` and `contradiction?` return before `skip_query_cache_if_necessary`. `pluck`/`calculate` match load: `@none` before the wrapper; contradiction (in `pluck` / `execute_simple_calculation` / grouped calc) inside or after other work.

`values_for_queries` strips `:skip_query_cache` (and `:extending`, `:strict_loading`) so that flag is not part of query-cache identity. That is independent of `#none`.

## Operations that can still execute SQL after further scoping

The rdoc claim that “any subsequent condition chained … will not fire any query” is true for the QueryMethods spawn path while `@none` stays set. It is not a global “this object never touches the database.”

Still runs SQL:

- **`#or` out of null.** `none.or(other)` is `other.spawn`. That relation loads/counts/updates for real.
- **RHS `#and` / where-clause-only combination.** `rel.and(Model.none)` and a handwritten `where("1=0")` do not set `@none`. Load goes to the adapter with `1=0` in SQL. Contradiction short-circuit does not apply.
- **Null relation as a value.** `Comment.where(post_id: Post.none)` uses `PredicateBuilder::RelationHandler`: `attribute.in(subquery)`. The subquery contains `WHERE (1=0)`. The outer query runs. (`null_relation_test` asserts count 0, not `assert_no_queries`.)
- **Writes that do not consult `@none`.** `create` / `create!` run through `scoping { model.create }` and INSERT. `insert` / `insert_all` / `upsert` go to `InsertAll`, which only uses `scope_for_create` (equality predicates + `create_with`). `1=0` is not an equality, so it does not even constrain the insert.
- **`#to_sql` / explain plumbing** still compile Arel (connection `to_sql`, not necessarily a executed SELECT). The `1=0` is in that string even when load would not run.

Does **not** start running SELECTs just because you stripped the predicate:

- `unscope(:where)`, `except(:where)`, `invert_where`, `rewhere(...)` keep `@none`. Load/calculate/`delete_all` still short-circuit. `to_sql` may no longer show `1=0`; the Ruby flag is what matters.

`in_order_of` with an empty `values` array is the inverse: it *enters* the null object (`spawn.none!`) rather than leaving it.
