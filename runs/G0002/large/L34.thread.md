## Assistant

`retry_on` is a `rescue_from` wrapper. On each failed `perform_now`, Active Job walks handlers last-declared first, increments a per-declaration counter, then either re-enqueues or exhausts. Exhaustion with no block re-raises the same exception; a block swallows it.

```diagram
perform_now
  executions += 1
  run_callbacks(:perform) { perform }
       │
       │ exception
       ▼
rescue_with_handler ──no match──▶ after_discard, re-raise
       │ match (reverse handlers, klass === error)
       ▼
executions_for(declaration) += 1
       │
       ├── attempts == :unlimited or count < attempts
       │     report? → Rails.error
       │     retry_job(wait, queue, priority)
       │       enqueue_retry notification
       │       enqueue callbacks → adapter
       │     return handled (exception does not escape)
       │
       └── exhausted
             retry_stopped notification
             yield job, error   (if block)
             after_discard
             raise error        (only if no block)
```

### Registration

[`retry_on`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L66-L94) validates `wait`, then registers one `rescue_from` handler per exception class, all sharing the same block:

```66:94:activejob/lib/active_job/exceptions.rb
      def retry_on(*exceptions, wait: 3.seconds, attempts: 5, queue: nil, priority: nil, jitter: JITTER_DEFAULT, report: false)
        case wait
        when :polynomially_longer, Integer, Float, ActiveSupport::Duration, Proc
          # Supported wait type, continue.
        else
          raise ArgumentError, "Unsupported argument type for :wait, ..."
        end

        rescue_from(*exceptions) do |error|
          executions = executions_for(exceptions)
          if attempts == :unlimited || executions < attempts
            ActiveSupport.error_reporter.report(error, source: "application.active_job") if report
            retry_job wait: determine_delay(...), queue: queue, priority: priority, error: error
          else
            # exhaustion: block and/or re-raise
          end
        end
      end
```

Unsupported `wait` raises at class-definition time ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L447-L454)). Supported types are integer, float, duration, proc, and `:polynomially_longer` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L456-L466)).

`rescue_from` appends `[klass.name, handler]` onto the inherited `rescue_handlers` array ([`rescuable.rb`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L53-L74)). Subclass declarations are copied from the parent, then appended ([rescuable test](file:///home/user/workspace/repo/activesupport/test/rescuable_test.rb#L159-L163)).

### When the handler runs

[`Execution#perform_now`](file:///home/user/workspace/repo/activejob/lib/active_job/execution.rb#L44-L57) increments the global `executions` counter, then runs perform callbacks around `perform`. The `rescue` sits **outside** those callbacks:

```44:57:activejob/lib/active_job/execution.rb
    def perform_now
      self.executions = (executions || 0) + 1
      deserialize_arguments_if_needed
      _perform_job
    rescue Exception => exception
      handled = rescue_with_handler(exception)
      return handled if handled
      run_after_discard_procs(exception)
      raise
    end
```

So:

- `before_perform` / `around_perform` / `after_perform` run on every attempt, including retries.
- `after_perform` does not run if `perform` raises.
- An `around_perform` that swallows the error prevents `retry_on` from seeing it.
- `DeserializationError` during `deserialize_arguments_if_needed` is also eligible ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L351-L354)).

If a handler returns without raising, `rescue_with_handler` returns the exception object ([`rescuable.rb`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L87-L91)), `perform_now` returns that, and the original error does **not** escape.

### Bottom-to-top and superclass lookup

Lookup is `rescue_handlers.reverse_each.detect` with `klass === exception` ([`find_rescue_handler`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L127-L139)). That is last-declared matching handler wins. For exception classes, `===` is `is_a?`, which is what the [`retry_on` docs](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L24-L25) describe.

Consequences:

- Later `retry_on`/`discard_on` on the same job class shadows an earlier one for any exception the later `klass` matches.
- A later superclass handler shadows an earlier subclass handler, because `Super === Child` is true.
- A later subclass handler wins over an earlier superclass handler. [`AfterDiscardRetryJob`](file:///home/user/workspace/repo/activejob/test/jobs/after_discard_retry_job.rb#L18-L19) declares `retry_on AfterDiscardError` then `retry_on ChildAfterDiscardError`; a `ChildAfterDiscardError` uses only the child handler, so [`after_discard` runs once](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L423-L427).
- Job-class inheritance: child handlers are later in the array, so they are searched before inherited parent handlers.

If nothing matches the exception, Rescuable walks `exception.cause` ([`rescue_with_handler`](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L94-L101)). Active Job’s exception tests do not cover that path.

Only one handler runs. A handler that raises does not fall through to the next handler ([Rescuable docs](file:///home/user/workspace/repo/activesupport/lib/active_support/rescuable.rb#L51-L52)).

### Counters: shared vs separate

[`executions_for`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L207-L214) increments `exception_executions[exceptions.to_s]` as a side effect, including on the exhausting attempt:

```207:214:activejob/lib/active_job/exceptions.rb
      def executions_for(exceptions)
        if exception_executions
          exception_executions[exceptions.to_s] = (exception_executions[exceptions.to_s] || 0) + 1
        else
          executions
        end
      end
```

The key is the **entire argument list** of that `retry_on` call (`[A, B].to_s`), not the class that actually raised.

- One declaration, several classes → one counter. [`retry_on FirstRetryableErrorOfTwo, SecondRetryableErrorOfTwo, attempts: 4`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L35) treats three `First` + one `Second` as four attempts and then lets `SecondRetryableErrorOfTwo` escape ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L42-L56)).
- Separate declarations → separate keys. Four `DefaultsError` plus three `FirstRetryableErrorOfTwo` both stay under their own limits and succeed ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L58-L76)).
- Delay math uses this per-declaration count, not `job.executions` ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L309-L334)).

The hash is initialized `{}`, serialized, and deserialized with the job ([`core.rb`](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L40-L44), [L110-L111](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L110-L111), [L125-L126](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L125-L126), [L167](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L167)). If it is `nil` (Rails 5.2 payloads), the code falls back to the global `executions` counter ([tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L365-L385)).

`job.executions` still counts every `perform_now`, including the original. Retry fixtures raise while `executions < attempts_arg` ([`RetryJob#perform`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L60-L67)).

### `attempts` and `:unlimited`

`attempts` counts the original execution plus retries. Default is 5. The retry condition is `attempts == :unlimited || executions < attempts` ([L77](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L77)).

- `DefaultsError` (default 5): four failures then success ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L25-L33)). A sixth raise happens on the 5th execution and exhausts ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L78-L83)).
- `attempts: :unlimited` never takes the else branch. [`UnlimitedRetryError`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L45) succeeds on the 10th execution ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L356-L362)).

### Wait: numeric, one-arg proc, two-arg proc, `:polynomially_longer`

[`determine_delay`](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L181-L198):

```181:198:activejob/lib/active_job/exceptions.rb
      def determine_delay(seconds_or_duration_or_algorithm:, executions:, error: nil, jitter: JITTER_DEFAULT)
        jitter = jitter == JITTER_DEFAULT ? self.class.retry_jitter : (jitter || 0.0)
        case seconds_or_duration_or_algorithm
        when :polynomially_longer
          delay = executions**4
          delay_jitter = determine_jitter_for_delay(delay, jitter)
          delay + delay_jitter + 2
        when ActiveSupport::Duration, Integer, Float
          delay = seconds_or_duration_or_algorithm.to_f
          delay_jitter = determine_jitter_for_delay(delay, jitter)
          delay + delay_jitter
        when Proc
          algorithm.arity == 2 || algorithm.arity < -1 ? algorithm.call(executions, error) : algorithm.call(executions)
        end
      end
```

Jitter is `Kernel.rand * delay * jitter`, or `0.0` if `jitter.zero?` ([L200-L203](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L200-L203)). `jitter: nil` becomes `0.0`. The sentinel `JITTER_DEFAULT` uses `self.class.retry_jitter` (class default `0.0` at [L11](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L11); new apps set `0.15` from [Rails 6.1 defaults](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L191)). The method docs still describe 15% ([L36](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L36)).

Observed wait behavior:

- Numeric/`Duration`: `wait + rand * wait * jitter`. [`LongWaitError` / `FloatWaitError`](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L107-L133).
- `:polynomially_longer`: `(executions**4) + (rand * executions**4 * jitter) + 2`. With count 1, 2, 3, 4 that is ~3s, ~18s, ~83s, ~258s ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L135-L157)). Jitter is applied to `executions**4`, not to the `+ 2`.
- One-arg proc: `->(executions) { executions * 2 }` waits 2, 4, 6, 8… ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L257-L272)). `->(executions = 0)` has arity `-1`, so it also gets one argument ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L274-L286)).
- Two-arg proc: arity `2` or `< -1` gets `(executions, error)`. [`error.retry_after + executions`](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L42) waits 11s then 12s ([test](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L288-L307)).
- Procs do **not** get extra jitter on top of what they return.

`jitter: nil` and `jitter: 0.0` both disable it ([tests](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L237-L255)).

### Queue and priority overrides

### Whether the original exception escapes

| Path | Escapes? |
|---|---|
| Retry (`count < attempts` or `:unlimited`) | No. Handler re-enqueues and returns. |
| Exhaustion **with** block | No. Block runs; error is not re-raised. |
| Exhaustion **without** block | Yes. `raise error` (same object). |
| No matching handler | Yes, after `after_discard`. |

That is the whole `retry_on` path in this revision: match last-declared `klass === error`, bump the declaration’s counter, retry or exhaust, and only let the original exception out when retries are spent and no exhaustion block absorbed it.
