The claim is wrong: `safe_concat` is the trusted, no-escape path. Making it escape ordinary strings would not make capture safer; it would HTML-escape every ERB template literal.

### Verdict

**Do not merge.** The one-line change inverts `OutputBuffer#safe_concat` / `#safe_append=` and would break template rendering. Capture is already escaped on the untrusted paths that `CaptureHelper#capture` owns.

### Findings

#### Blocker — `safe_concat` is the trusted-append API; this inverts it

`safe_concat` / `safe_append=` means “already safe, do not escape.” `#<<` / `append=` is the escaping append. The proposed line makes them the same for ordinary strings.

Every ERB/Herb static chunk goes through `safe_append=` with a frozen ordinary String. `ERB::Util.html_escape("<div class=\"x\">")` is `"&lt;div class=&quot;x&quot;&gt;"`. Views would render escaped markup instead of HTML.

Existing tests that would fail immediately:

- [`#safe_append= bypasses HTML safety`](file:///home/user/workspace/repo/actionview/test/buffers_test.rb#L14-L19) expects `"<p>This is fine</p>"`.
- Any template rendering test that asserts real tags.

Helpers that `safe_concat` already-`html_safe` fragments (form options, `content_tag`, cache fragments) would coincidentally survive because `html_escape` short-circuits `html_safe?`. The compiler path does not.

This is also a security **regression in the other direction** only in the sense that it looks like a hardening: it trains the API to treat “safe” as “escape anyway,” while `<%==` / `safe_expr_append=` and `raw` remain unescaped. XSS via `safe_concat(user_input)` is the same class of bug as `raw(user_input)`. Capture does not make it special.

#### Blocker — capture is already the wrong layer for this change

`OutputBuffer#capture` never concatenates the block return value. It swaps `@raw_buffer`, yields, and returns `new_buffer.html_safe`.

Untrusted **returns** are handled in `CaptureHelper#capture` (`ERB::Util.html_escape(string)`). Untrusted **writes** are handled by `#<<`. Tests already cover both.

The author’s “make capture safer” hole is: `safe_concat` / `raw` inside a capture still injects trusted HTML into a result later marked html_safe. That is the method’s contract, and `#raw respects #capture` asserts it. Closing that hole in `safe_concat` would also close the only path ERB has for literal HTML.

If capture of untrusted `safe_concat` were the real bug, the fix would have to live in capture policy (and would still have to leave ERB literals alone). Changing `safe_concat` is not a capture fix.

#### High — `StreamingBuffer#safe_concat` left unchanged

```121:124:actionview/lib/action_view/buffers.rb
    def safe_concat(value)
      @block.call(value.to_s)
    end
```

Buffered templates would escape `safe_append=` literals; streaming would not. Same template, two outputs.

#### Medium — silent contract changes besides escaping

- `nil`: `TypeError` → empty append.
- non-String: `String#<<` (integer codepoint, etc.) → `html_escape` → `to_s`.
- `html_escape` wraps a `SafeBuffer` on every call; `#<<` uses `unwrapped_html_escape` because `@raw_buffer` is a plain String. Extra allocations on every static ERB chunk.

`RawOutputBuffer` is already the explicit unescaped writer. This patch does not touch it, so the “always escape unless raw” story is incomplete even on its own terms.

---

### Compatibility / security

- **Compatibility:** breaking for all HTML templates and for any caller of `safe_concat` / `TextHelper#safe_concat` with trusted ordinary strings (e.g. [`safe_concat render(plain: "<ul>...")`](file:///home/user/workspace/repo/actionview/test/template/test_case_test.rb#L331)). Not a minor default tweak.
- **Security:** does not close a capture XSS that `#<<` and `CaptureHelper#capture` do not already handle. It would paper over `safe_concat(untrusted)` by destroying the trusted-literal API. `raw`, `safe_expr_append=`, and `RawOutputBuffer#<<` remain unescaped.
