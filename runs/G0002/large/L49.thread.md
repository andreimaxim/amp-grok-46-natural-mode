**Problem frame:** In development, a developer editing an application or mounted-engine route file (including an external draw file) can save invalid Ruby and then not know whether the last good routes are still live, whether the process is now routing with an empty or mixed set, or which later request will pick up a correction. That uncertainty is the pain. The work is bounded to `Rails::Application::RoutesReloader` / `app.routes_reloader`, the route sets it reloads, external draw paths, and `config.file_watcher`. Success is that those developers can tell, from the next request or equivalent, whether routes failed to update and when a good file became the live set.

This is maintenance of that development reload boundary. It is not a new routing DSL, not a production-reload feature, and not a change to how routes are declared.

---

**Actors:** A developer in development, including one changing a mounted engine’s routes in the same process.

**Pain:** After an invalid save they cannot tell whether old routes still work, whether nothing (or only some files) is live, or when a fix will take effect. A single error page followed by 404s, or a mixed app/engine set, reads as “reloading is broken” rather than “this file is still invalid.”

**Desired observable outcomes**

1. A route file that fails to load is visible on the request (or other access) that first sees the bad file, and remains visible until a successful load of the corrected files — the developer is not left with silent empty or mixed routes.
2. Previously live routes are not a mystery: either they stay in effect until a whole reload succeeds, or they do not — but the process does not look as if the old set is still there when it is not.
3. After a successful correction, the next request that runs after `config.file_watcher` reports the files current uses only the corrected application, engine, and external-draw routes together.
4. Application routes, mounted-engine routes, and external draw paths are one unit for “did this change take effect?”
5. Removing a still-required route file is a visible failure, not continued service of that file’s last contents.
6. Outcomes 1–5 hold for both `config.reload_classes_only_on_change` true and false. Cadence may differ (only on reported change vs every request); visibility and “when the fix is live” must not.

**Non-goals**

- Production with reloading disabled; changing the routing DSL or `draw` file format; watcher performance; Spring/multi-process except as an open question; a prescribed recovery mechanism, data structure, or test suite.

**Acceptance examples** (required cases)

*Initial boot.* Given development and a valid application (and optional engine/external) route file, when the process starts and the first request runs, those routes are the live set. Given a syntax or load error in a required file before the first successful draw, that first request shows the error; boot may still complete when routes are lazy. A later request retries until the files load.

*Syntax/erroring reload.* Given a successful draw, when the developer saves invalid Ruby in the application `config/routes.rb`, an engine `config/routes.rb`, or an external draw file, the next request that runs after the watcher reports the change shows the error. It does not silently keep serving a set the developer cannot distinguish from “reload did nothing.”

*The next request (still invalid).* Given that failed reload and no correction, the next request still makes the failure obvious. It does not look like an empty app, a partial engine, or the old routes “just working again.”

*Correction.* Given the developer then saves valid files, the next request after the watcher reports that change serves only the new routes. Removed routes and helpers are gone; new ones work. No extra restart.

*Simultaneous application and engine changes.* Given both files change before the next reload, a successful reload exposes both new sets together. If only one file is invalid, the developer sees that failure and is not left to guess whether the other file’s new routes are live.

*Deleted route files.* Given a required watched route file is deleted, the next reload attempt fails visibly and does not keep serving that file’s previous routes as if it were still there. A missing optional external file that `draw` still names fails visibly with the usual missing-file outcome.

*`config.reload_classes_only_on_change` true.* Reloads and retries of a bad file happen when the configured `config.file_watcher` reports a relevant change (route files or another reload that already redraws routes). After a bad save, the developer still sees the failure until correction; after a good save, the next such request is live.

*`config.reload_classes_only_on_change` false.* Each request may redraw routes. A bad file errors on those requests until corrected; the next request after a good save is live. Same visibility and “when it takes effect” as the true case.

**Steering evidence**

- Contradicts success: after a bad save, a later request 404s or uses old/partial routes with no error; after a fix, a later request still errors or still serves the pre-correction set; app and engine diverge after a joint edit; deleting a required file leaves its old routes in effect.
- Suggests the framing is wrong: developers already always see a persistent error and a single atomic cutover, and the confusion is only watcher lag or editor mtimes. Then stop and treat this as a docs/watcher issue.
- Decision: if the silent-empty or mixed-set path is confirmed in a running development app, the outcomes above are the target. If a running app already matches them, the report is mistaken and this work should not proceed.

**Open behavioral questions**

1. After a failed reload of previously good routes, must subsequent requests keep raising until correction, or is another equally obvious signal enough? (Hypothesis: keep raising; that matches first-load retry.)
2. Should the last successful set stay live until a full reload succeeds (atomic), or is “not live, and obviously so” enough? This changes the meaning of example 2.
3. If one of several files fails mid-reload, must none of the new files be live?
4. Does “deleted” include only `config/routes.rb`, or also an external file under `config/routes` that is no longer `draw`n?
5. Same visibility for console, `reload!`, integration tests, and `bin/rails` as for a web request?
6. Watcher lag (especially evented): is “not live until the watcher reports” accepted, or must a retry after save always see the new bytes?
7. Runtime `raise` in a route file vs `SyntaxError` — same outcomes?

**Evidence to collect** (observation, not a test design)

- After a good boot, save a syntax error in `config/routes.rb`, hit a known-good path twice, then save a correction and hit once more. Repeat with `reload_classes_only_on_change` false.
- Same for a mounted engine’s `config/routes.rb` and for an external draw file, including one valid and one invalid at the same time.
- Delete a required route file after boot; request; restore.
- Note whether the first-boot error path already retries (tests say it does) while the after-boot path does not (source suggests it may not).
- If cheap, confirm in a running development app; do not treat the unit tests as covering those examples.
