The task was to review a PR claiming:

> “API-only applications should include cookies whenever a session store is configured.”

Proposed diff in `Rails::Application::DefaultMiddlewareStack#build_stack`:

```diff
- middleware.use ::ActionDispatch::Cookies unless config.api_only
+ middleware.use ::ActionDispatch::Cookies if !config.api_only || config.session_store
```

No separately labeled “reference answer” or literal “L45” was found. The thread’s final review is the reference/verdict.

## Full review / verdict: **Request changes**

The change fixes a real case but is broader than its claim.

Rails’ `setup_default_session_store` assigns a default `CookieStore` immediately before middleware-stack construction, including for API-only apps. Consequently, `config.session_store` is truthy during stack construction for every normally initialized API-only application. The proposed condition therefore adds `ActionDispatch::Cookies` to **all** normal API-only apps—not only ones where the application explicitly configured sessions.

| Configuration | Result with proposal |
|---|---|
| Full-stack default | Unchanged: Cookies → Session → Flash |
| API-only default | Cookies only; no Session or Flash |
| API + explicit `session_store` | Cookies only; no Session or Flash |
| API + manual Session | Cookies precedes Session; session `Set-Cookie` persists |
| API + documented manual Cookies + Session | Two Cookies middleware entries |
| API + disabled sessions | No Cookies, Session, or Flash |
| Full-stack + disabled sessions | Cookies and Flash remain; Session absent |
| Manual Flash without Session | No persistence; Flash requires an enabled session |

`ActionDispatch::Cookies` only commits a cookie jar when it was used; it does **not** activate sessions. A manually added `CookieStore` depends on that jar. Thus, the proposal genuinely fixes the API case where Session was manually added: session writes now emit `Set-Cookie` and persist on the next request; the baseline did not.

### Compatibility and ordering findings

- The behavior conflicts with the generated API-app comment and API guide, which tell API apps to add Cookies manually.
- Apps following that documented recipe get duplicate Cookies middleware. It remains generally functional—inner Cookies commits, outer sees the committed jar—but adds redundant middleware/instrumentation and leaves docs stale.
- `config/application.rb` and initializers run early enough to affect stack construction. `after_initialize` is too late: the Rack app is already memoized.
- `config.session_store :disabled` resolves to `nil`, so disabled API behavior remains without Cookies/Session/Flash.
- Manually adding Flash alone cannot persist flash; it operates through the session. A full manual Cookies → Session → Flash chain preserves the required order.

### Verification recorded

With the proposal applied:

- Custom assembly/request matrix: **11 runs, 45 assertions**, passing.
- Session tests: **13 runs, 34 assertions**, passing.
- Cookie tests: **7 runs, 19 assertions**, passing.
- Active Storage API custom-session test: passing.
- Middleware command tests: **1 failure**: the expected default API stack unexpectedly gained Cookies.

The existing isolation fixture configured a store, but a focused probe removing that configuration still got Cookies because Rails’ finisher reinstates the default store.

### Missing PR coverage

- Clean default API app without fixture-induced store configuration.
- Explicit and disabled API stores.
- Full-stack behavior with sessions disabled.
- Actual session persistence / `Set-Cookie`.
- Duplicate manual Cookies setup.
- Flash with and without Session.
- Early configuration versus `after_initialize`.

### Supported narrower alternative

Make the decision in `setup_default_session_store`, **before** Rails fills an absent store. If an API app already has an explicitly configured, non-disabled store, queue `ActionDispatch::Cookies` with `insert_before Rack::Head`; otherwise install Rails’ default store without adding Cookies. This preserves today’s default API stack while fixing explicit session opt-in, though duplicate manual-Cookies handling or migration documentation would still be needed.

**Request changes.** The one-line condition is broader than its claim: it installs `ActionDispatch::Cookies` on every normally initialized API-only app, not only on apps that opted into a session store.

### What the condition actually means

Today in [`default_middleware_stack.rb`](file:///home/user/workspace/repo/railties/lib/rails/application/default_middleware_stack.rb#L76-L86):

```76:86:railties/lib/rails/application/default_middleware_stack.rb
          middleware.use ::ActionDispatch::Cookies unless config.api_only

          if !config.api_only && config.session_store
            ...
            middleware.use config.session_store, config.session_options
          end

          unless config.api_only
            middleware.use ::ActionDispatch::Flash
```

The proposed `if !config.api_only || config.session_store` uses the **getter**. That getter is already truthy by the time the stack is built.

[`setup_default_session_store`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb#L49-L56) runs immediately before `:build_middleware_stack` and does **not** skip `api_only`. Unless the app already set a store, it assigns `:cookie_store`. The getter then returns `ActionDispatch::Session::CookieStore` (truthy) except for `:disabled`, which resolves to `nil`.

So the new Cookies line is true for every default API app. Session and Flash stay gated on `!config.api_only`, so this does **not** turn on sessions.

### Observed stacks

I applied the patch, ran the existing middleware/session/cookie tests plus a temporary assembly/request matrix, then reverted.

| Configuration | With the patch |
|---|---|
| Full-stack default | Unchanged: Cookies → Session → Flash, before `Rack::Head` |
| API-only default | **Cookies only**; Session and Flash still absent |
| API + explicit `session_store` | Same: Cookies only |
| API + `session_store :disabled` | No Cookies, Session, or Flash |
| Full-stack + `:disabled` | Cookies and Flash remain; Session absent |
| API + manual Session | Cookies precedes Session; session `Set-Cookie` persists |
| API + documented Cookies + Session | **Two** Cookies entries; still works |
| API + Flash, no Session | No persistence (`Flash` is a no-op wrapper; flash lives in the session) |
| Initializer / `config/application.rb` | Early enough to affect the stack |
| `after_initialize` | Too late: Rack app is already memoized |

Existing [`test "api middleware stack"`](file:///home/user/workspace/repo/railties/test/commands/middleware_test.rb#L92-L114) failed as expected: default API stack gained `ActionDispatch::Cookies` between Callbacks and `Rack::Head`. Full-stack and dependency-order tests still passed.

Isolation’s [`build_app`](file:///home/user/workspace/repo/railties/test/isolation/abstract_unit.rb#L140) always sets `config.session_store :cookie_store`. Removing that still got Cookies, because the finisher reinstates the default store.

### Request-level consequences

[`ActionDispatch::Cookies#call`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L712-L726) only writes `Set-Cookie` if the jar was used (`have_cookie_jar?`) and not already committed. An unused Cookies middleware does not emit cookies. It also does **not** enable `session` or `flash`.

[`CookieStore`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/session/cookie_store.rb#L117-L126) writes through `request.cookie_jar`. [`Response#before_sending`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/response.rb#L529) only marks the jar committed; it does not write headers. Without Cookies in the stack, a manually added Session store mutates the jar and then nothing emits `Set-Cookie`. That is the real bug the PR would fix — but only for apps that also `middleware.use` a session store.

[`ActionController::API`](file:///home/user/workspace/repo/actionpack/lib/action_controller/api.rb#L116-L147) still omits `ActionController::Cookies`. Adding the middleware does not give API controllers a `cookies` helper.

Documented API recipe in [`guides/source/api_app.md`](file:///home/user/workspace/repo/guides/source/api_app.md#L442-L456) and the generated [`application.rb.tt`](file:///home/user/workspace/repo/railties/lib/rails/generators/rails/app/templates/config/application.rb.tt#L32-L35) comment both say to add Cookies manually. After this change that recipe produces:

```text
… Callbacks, Cookies, Rack::Head, ConditionalGet, ETag, Cookies, Session::CookieStore
```

Inner Cookies commits; outer sees a committed jar and skips. Functional, but redundant, and the guide/comment become wrong.

### Compatibility

- Default API stack changes for every app, including those that never wanted cookies.
- Extra middleware on every API request (cheap if the jar is unused, still always present and instrumented).
- Duplicate Cookies for anyone following the current API guide.
- `:disabled` is handled correctly (`nil` getter).
- Does not install Session/Flash on API apps, so `config.session_store :cookie_store` alone still does not persist sessions.

### Test gaps in the PR as claimed

No coverage for:

- A clean API app without the isolation fixture store (the case this condition gets wrong)
- Explicit vs disabled API stores
- Full-stack `:disabled`
- Actual session persistence / `Set-Cookie`
- Duplicate manual Cookies
- Flash with and without Session
- Initializer vs `after_initialize`

Existing tests that would need updates: [`middleware_test.rb`](file:///home/user/workspace/repo/railties/test/commands/middleware_test.rb) API stack. [`session_test.rb`](file:///home/user/workspace/repo/railties/test/application/middleware/session_test.rb) covers API `reset_session`, disabled writes, and a custom Cookies+Session chain, but not this default-store interaction.

### Narrower alternative

Keep `unless config.api_only` for Cookies. Decide in `setup_default_session_store` **before** filling an absent store:

- If the API app already has an explicit, non-disabled store (`session_store? && session_store`), `insert_before Rack::Head, ActionDispatch::Cookies`.
- Otherwise assign the default CookieStore and leave the API stack unchanged.

That matches the claim, preserves today’s default API stack, and still needs a docs/migration note for apps that also `use ActionDispatch::Cookies`. Auto-inserting Session would be a larger behavior change than the PR describes and is not required to fix the missing-`Set-Cookie` case.
