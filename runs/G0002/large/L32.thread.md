## Assistant

This is a **behavior change**: authors already have `button_to`; the work is to make its supported calling forms more predictable and more usable with assistive technology. Evidence came from the helper’s documented calling forms, the generated HTML those forms produce, the navigation-helper examples that currently catalog `button_to`, the URL-helper examples (which do **not** cover `button_to`), and the public guides. I did not operate the control with a keyboard or screen reader, and two requested cases—**nil destination** and **unsafe HTML in the label**—have no dedicated `button_to` examples, so those baseline claims are labeled.

**Problem frame:** A Rails view author needs a one-control submit that goes to a chosen destination with a chosen HTTP verb, so people (including keyboard and screen-reader users) can trigger a real action without it looking like a crawlable link. Today that control’s destination, verb, CSRF token, enabled state, remote/Ajax hint, and visible name shift with how the author calls it. String label vs block, GET vs POST vs DELETE, `remote: true`, disabled, nested `form:` options, explicit authenticity tokens, nil destinations, and labels that contain HTML do not all behave in ways authors—or people using the page—can reliably predict. Public docs still talk about this as a URL helper, while the working examples live with navigation helpers, which makes the contract harder to find. The desired progress is: the same intent yields the same destination, verb, token, name, and operability across those calling forms, and people using assistive technology can find, understand, and use or skip the control.

**Actors:** View authors; people activating the control, including keyboard and screen-reader users; crawlers that must not treat a mutating action as a GET link; app maintainers who already ship these controls.

**Constraints:** Existing calling forms stay valid. CSRF protection for non-GET submits stays in force unless the author turns it off. Verb inference from a persisted vs new record is an established contract since Rails 7. Apps already depend on default POST, `remote` landing on the submitted form, `form:` vs control-level options, and the documented `false` destination that omits an action. Older apps may still generate a submit input instead of a button for a string label.

**Non-goals:** Redesigning ordinary links. Changing CSRF policy itself. Inventing new author-facing options. Prescribing markup, JavaScript behavior, internal helper structure, or how examples are automated.

---

**Current observable baseline**

With a **string label and URL**, the page gets a small form whose default class is `button_to`, method is POST, action is that URL, and inner submit shows the label. Query strings in the action are escaped. A **false** destination omits `action` entirely, with or without a block.

With a **block**, the first argument is the destination, not the label; the block becomes the control’s contents (including nested tags). `button_to(url) { … }` and `button_to(routing_hash, html_options) { … }` are the documented block forms. Passing a label *and* a URL *and* a block is not cataloged; that call would have to treat the URL as HTML options, which is a likely author footgun.

**URL conversion:** a string is used as-is; a path helper, routing hash, model, or array of models is converted the same way other URL helpers convert them. A new record posts to the collection; a persisted record patches the member. **Nil destination is untested.** The surrounding URL helper treats `nil` as “current path,” which is **not** the same as documented `false` (no action). Whether `button_to("Hello", nil)` omits the action, targets the current page, or errors is an open baseline question.

**Method:** GET puts `method="get"` on the form and adds no `_method` field and no authenticity token. POST uses `method="post"` with no `_method`. DELETE (and PATCH/PUT) still POST at the form level and carry a hidden `_method`. A persisted model without an explicit method behaves as PATCH.

**Authenticity token (when forgery protection is on, non-GET):** omitted if protection is absent or `authenticity_token: false`; a specific string is used when one is passed; `true` or omission uses the generated token. GET never includes it. Token fields currently carry `autocomplete="off"` unless that global hidden-field behavior is turned off.

**Form vs control attributes:** `class` on the call styles the inner control; `form_class` or `form: { class: … }` styles the form (`form:` wins if both class sources exist). Other `form:` entries appear on the form. `remote: true` marks the **form** as remote even when not nested under `form:`; `remote: false` adds nothing. `data: { confirm: … }` and `data: { disable_with: … }` land on the **control**. Guides already warn that a Turbo confirmation must be attached to the form via `form:`, not to the control via `data:`.

**Disabled:** `disabled: true` disables the inner control; the form, destination, and hidden fields still render. `disabled: false` matches the default enabled control.

**Missing label:** `button_to(nil, url)` uses the URL string as the visible name.

**Unsafe HTML in the label:** not cataloged for `button_to`. Ordinary links escape a raw string label and keep already-safe HTML. `button_to` form *classes* are escaped. **Hypothesis:** a string label is escaped, and a block can include tags when that content is already treated as safe—same family of rules as links, but unproven here.

URL-helper examples cover `url_for`, `mail_to`, `sms_to`, and `phone_to` only. They do not establish `button_to` behavior.

---

**Desired outcomes**

1. **Calling form does not silently retarget.** A string label plus destination, and a block whose first argument is the destination, produce the destination and visible name the author meant. A mistaken third combination fails in a way the author can see, rather than submitting to the label or treating a URL as attributes.

2. **Verb is obvious from the call, then from what is submitted.** GET navigates without a token. POST and DELETE (and inferred PATCH on a persisted record) submit as mutating form actions, not as crawlable links. DELETE remains a form submit with an explicit override, not a GET.

3. **`remote: true` is consistently a form-level hint.** Authors can tell which options affect the submitted form (`form:`, form class, remote, method, token, extra params) versus the control people focus (visible name, disabled, control-level data). Confirmations meant to gate submit are attachable to the form people actually submit.

4. **Disabled means not operable.** Keyboard and pointer users cannot activate it; assistive technology presents it as unavailable. Hidden fields remaining in the page must not create a second way for a typical visitor to fire the same action.

5. **Token intent is honored.** Explicit token, generated token, and “no token” stay distinct on non-GET submits, and GET stays token-free.

6. **Nil vs false destinations are distinct and documented as such.** `false` keeps “no action.” Nil does one agreed thing everywhere (current page, same as false, or a visible author error)—not a quiet mix of those.

7. **HTML in the name follows one safety rule.** Unsafe markup in a string label cannot run as markup. Intentionally safe content, including a block that already produced tags, can render as structure. That rule matches what authors already expect from neighboring helpers unless we explicitly choose otherwise.

8. **People using assistive technology can use the control.** They can find it, hear a sensible name (label, block contents, or a decided fallback—not a raw surprise URL unless that was the author’s only name), know whether it is disabled, and activate it with keyboard the same way they activate other buttons. Mutating actions remain buttons/forms, not links, which is already the stated accessibility reason this helper exists.

---

**Behavioral examples** (required unless marked illustrative)

- **String label, POST.** Author writes a named control to a URL with no method. The visitor sees a button named “Hello” that POSTs to that URL, with a token if CSRF is on.

- **Block.** Author passes only the URL (or routing hash plus control options) and a block that includes a tag. The visitor sees that block content as the control name; the form still POSTs to that URL. **Counterexample:** label + URL + block must not POST to “Hello” or treat the URL as HTML options without a clear failure.

- **GET vs DELETE.** GET: form GET, no token, no method override. DELETE: still a form POST plus delete override, token when CSRF is on, not a link.

- **`remote: true` with nested `form:`.** The form carries the remote hint and the nested form attributes (including a custom class). Confirm/disable data passed beside `data:` stay on the control. **Illustrative pitfall (already documented):** a confirmation intended to run on submit does not run if it is only on the control.

- **Disabled.** `disabled: true` → control cannot be activated and is exposed as disabled. `disabled: false` → same as omitting it.

- **Explicit token.** String → that value; `true` → generated; `false` → none; GET → none even if a token option is in play. **Boundary:** no forgery-protection method → no token field.

- **Nil URL (open until chosen).** Today `false` omits action. After this work, nil is either that same omission, the current page, or an author-visible error—one behavior, all calling forms.

- **Unsafe HTML label.** String `"Malicious <script>content</script>"` appears as text, not a script. A block (or already-safe name) may include a `<span>` as structure. **Hypothesis until proven for this helper.**

---

**Compatibility risks**

Changing argument shifting, nil destinations, escaping, where `remote`/confirm land, default POST vs inferred PATCH, token presence, or default form class can retarget or break existing screens, CSRF, UJS/Turbo confirmations, and CSS. Treating block HTML like an escaped string would strip intended icons/names; treating string labels like safe HTML would introduce XSS. Disabled-but-still-submittable forms are a security/AT risk if “disabled” is only visual.

**Open product questions**

- What should **nil** as the destination mean, and is it different from **false**?
- If someone passes **label + URL + block**, is that an error or a defined third form?
- Should **`remote: true`** remain a first-class contract or only a legacy hint?
- How much must GET-as-button vs mutating-as-button be distinguishable to AT users beyond “it is a button”?
- Must a **disabled** control still emit a complete submittable form for progressive enhancement, or is “cannot submit” the product rule?
- Should a **missing label** keep falling back to the URL (including query string), or is that a predictability/AT defect?
- Is matching **link** HTML-safety enough, or does `button_to` need a stricter “always escape strings” rule?
- Does success include older apps that still generate a submit **input** for string labels, or only the current button-shaped default?

**Steering evidence (external, not a test plan)**

- **Success:** Authors using string vs block get the destination and name they intended; GET has no token; POST/DELETE still mutate through a form; `form:` and `remote` affect the submitted form; disabled cannot be activated and is announced that way; unsafe string names do not become markup; keyboard and screen-reader users can complete or skip the action without a hidden extra submit path.
- **Investigate:** Reports of “the button sent the wrong place / verb,” confirmations that never appear, tokens on GET or missing on POST, disabled controls that still submit, or AT users landing on a URL-as-name with no role as a button.
- **Wrong framing:** If pain is mostly docs/naming (URL helper vs navigation helper) or only Turbo confirm placement, tighten docs and examples rather than changing runtime behavior.
- **Stop / split:** If nil-URL, block-arity, and AT-operability cannot share one outcome without breaking CSRF or existing calls, split rather than ship a mixed change.

I treated “predictability” as *same intent → same destination, verb, token, name, and operability*, and “accessibility” as *keyboard and AT users can find, understand, and use or skip a real button/form action*. That is a hypothesis. Does that match what you want, and which open question (especially **nil vs false** and **label + URL + block**) should be decided before this is treated as agreed?
