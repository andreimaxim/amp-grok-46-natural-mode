## Assistant

`reload` mutates the receiver in place and returns it. It always issues a primary-key (or query-constraint) `find_by!` after clearing the connection pool’s query cache. The Ruby object stays the same; `@attributes`, `@association_cache`, persistence flags, and Dirty mutation trackers are replaced or nilled.

### Call chain

For a typical model the instance method is stacked, later `include`s first:

```text
AutosaveAssociation#reload
  Dirty#reload                          # AttributeMethods::Dirty
    Persistence#reload                  # the implementation
      connection_pool.clear_query_cache
      _find_record / unscoped { _find_record }
      steal @association_cache, rebind owners
      steal @attributes
      @new_record = @previously_new_record = false
```

[`AutosaveAssociation#reload`](file:///home/user/workspace/repo/activerecord/lib/active_record/autosave_association.rb#L243-L246) clears `@marked_for_destruction` and `@destroyed_by_association`, then `super`.

[`Dirty#reload`](file:///home/user/workspace/repo/activerecord/lib/active_record/attribute_methods/dirty.rb#L62-L67) runs Persistence, then nils both mutation trackers:

```63:67:activerecord/lib/active_record/attribute_methods/dirty.rb
      def reload(*)
        super.tap do
          @mutations_before_last_save = nil
          @mutations_from_database = nil
```

Models that use `composed_of` also wrap this with [`Aggregations#reload`](file:///home/user/workspace/repo/activerecord/lib/active_record/aggregations.rb#L11-L14), which clears `@aggregation_cache` first. Active Storage attachments nil `@attachment_changes` after `super`.

### Persistence#reload

```748:762:activerecord/lib/active_record/persistence.rb

      self.class.connection_pool.clear_query_cache

      fresh_object = if apply_scoping?(options)
```

`fresh_object` is a different Ruby object from `find_by!`. Reload copies two ivars off it and discards it. `self` is unchanged; only internals are swapped.

Assigning `id` on a new record and calling `reload` therefore loads that row ([`test_find_via_reload`](file:///home/user/workspace/repo/activerecord/test/cases/persistence_test.rb#L1687-L1696)). ### Scoped vs unscoped lookup

[`apply_scoping?`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L858-L860) is true only when `options[:unscoped]` is not set **and** the model has an `all_queries: true` default scope **or** a `global_current_scope`:


| Condition | Path | What the SELECT includes |
|---|---|---|
| Ordinary `default_scope` (no `all_queries`) | `unscoped { _find_record }` | Bare relation; default scope **not** applied |
| `default_scope ..., all_queries: true` | `_find_record(all_queries: true)` | [`all_queries_scope`](file:///home/user/workspace/repo/activerecord/lib/active_record/scoping/named.rb#L59-L70): those default scopes |
| `Model.where(...).scoping { reload }` (no `all_queries`) | unscoped branch | Current scope **not** applied; it is not `global_current_scope` |
| `scoping(all_queries: true) { reload }` | scoped branch | Default `all_queries` scopes **plus** the global current scope |
| `reload(unscoped: true)` | unscoped branch | Neither |

`all_queries: true` on `_find_record` is injected internally when `apply_scoping?` is true. It is not a documented `reload` option. The documented extra keys are `lock:` and `unscoped:`.

### Association cache: replace, then rebind owner

Reload does not walk the old associations and reset them. It **replaces** the whole `@association_cache` with the hash from `fresh_object`, then sets `association.owner = self` on every value.

A normal `find_by!` record has an empty cache unless something populated it (`preload`, `after_initialize`, inverses). [`strict_loaded_associations`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L827-L831) is the exception: if the **receiver** is `strict_loading?` (and not n-plus-one-only), already-cached association names are `preload`ed on the fresh find so the next access does not violate strict loading.

Owner rebinding is required because those `Association` objects were built for `fresh_object`. Without it, later writes go to the discarded object. [`test_reload_sets_correct_owner_for_association_cache`](file:///home/user/workspace/repo/activerecord/test/cases/persistence/reload_association_cache_test.rb#L9-L18) covers that: `Publication`’s `after_initialize` builds `editor_in_chief`, so the stolen cache is non-empty; after reload, `build_editor_in_chief` / `save!` still update `self` (`after_save_commit` retouches `name`).

`Association` exposes `owner` as `attr_accessor` ([association.rb](file:///home/user/workspace/repo/activerecord/lib/active_record/associations/association.rb#L35)).

### Persistence flags and Dirty trackers

Persistence sets only `@new_record = false` and `@previously_new_record = false`. It does **not** assign `@destroyed`. That does not matter for the deleted-row case: `find_by!` raises first, so the receiver stays destroyed and the flags are untouched.

Dirty then nils:

- `@mutations_from_database` — unsaved changes (`changed?`, `changes`)
- `@mutations_before_last_save` — last-save changes (`saved_changes`, `previous_changes`)

Readers rebuild lazily: `mutations_from_database` from the new `@attributes`; `mutations_before_last_save` as `NullMutationTracker` ([ActiveModel::Dirty](file:///home/user/workspace/repo/activemodel/lib/active_model/dirty.rb#L382-L395)).

### Observable cases

Identity vs internals in every case: **`object_id` is unchanged; `@attributes` and `@association_cache` are replaced.** Reload returns `self`.

**Unsaved local attribute change** — [`test_reload_should_clear_changed_attributes`](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb#L410-L416):

- Before: `pirate.catchphrase = "*hic*"` → `changed?` true; in-memory value is the assignment.
- After: **queries**; `@attributes` come from the DB; both mutation trackers are nilled; `changed?` is false; catchphrase is the persisted value. The assignment is discarded, not written.

**`saved_changes` after a prior save, then reload** — `save` moves `mutations_from_database` into `@mutations_before_last_save` (`changes_applied`). Dirty `#reload` then sets that ivar to `nil`. Next `saved_changes` / `previous_changes` is `{}`. Same file: after `save`, an assignment, then `reload`, `previous_changes` is empty ([dirty_test.rb](file:///home/user/workspace/repo/activerecord/test/cases/dirty_test.rb#L547-L550)). The nil is unconditional; a save with no further assignment behaves the same. **Queries; does not raise.**

**Row hidden by default scope vs explicit scoping**

- Default scope **without** `all_queries`: reload is unscoped. **Queries; finds the row.**
- Default scope **with** `all_queries: true`, or `scoping(all_queries: true)` whose predicate excludes the row: **queries; raises `RecordNotFound`.**
- `reload(unscoped: true)`: **queries; finds the row** even with an all-queries default scope.

**Deleted row** — [`delete_all_test`](file:///home/user/workspace/repo/activerecord/test/cases/relation/delete_all_test.rb#L79): `deleted_post.reload` **queries; raises `RecordNotFound`**. Same if `destroy` already removed the row. The in-memory object is not reset; it never reaches the ivar-steal.

**Already-loaded association whose DB contents changed**

Reload does **not** re-query the association unless strict-loading preload applied. It drops the old cache.

```diagram
before reload
  post ──@association_cache──▶ Association(owner: post, target: [c1, c2])

reload
  clear query cache
  fresh = Post.find_by!(id)     ━━━ SELECT posts
  post.@association_cache = fresh.@association_cache   (usually {})
  rebind owners

next post.comments
  new Association(owner: post)  ━━━ SELECT comments WHERE post_id = …
```

- Parent identity: same `post`.
- Association proxy / targets: new objects on next access, reflecting the DB.
- Reload itself: **one query** (the record). The association query happens on next read, not inside `reload` (unless strict-loading preload).
- Does not raise unless the parent row is gone.

If you skip `reload` and read `post.comments` again, you still see the stale in-memory targets.
