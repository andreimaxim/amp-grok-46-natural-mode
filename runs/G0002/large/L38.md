## Current contract

Three stages, with two different clocks:

```text
status update commit
  Incineratable after_update_commit
    if incinerate && status_previously_changed? && processed?
      IncinerationJob.schedule(email)
        set(wait: incinerate_after).perform_later(email)

IncinerationJob.perform(email)
  email.incinerate
    Incineration.new(email).run
      destroy! if due? && processed?

due?  = updated_at < incinerate_after.ago.end_of_day
```

`processed?` is `delivered? || failed? || bounced?` ([inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb#L41-L43)). `pending` and `processing` are not processed. Mailbox processing reaches a terminal status via `processing!` then `delivered!` / `bounced!` / `failed!` ([base.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/base.rb#L122-L129), [state_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/mailbox/state_test.rb)).

Defaults: `ActionMailbox.incinerate = true`, `incinerate_after = 30.days` ([action_mailbox.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox.rb#L22-L23), [engine.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/engine.rb#L17-L18)). Queue is `ActionMailbox.queues[:incineration]` (`nil` under 6.1+ defaults, so the Active Job default queue; `:action_mailbox_incineration` on 6.0) ([engine.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/engine.rb#L20-L21), [configuration.rb](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L212), [configuration_test.rb](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L4110-L4151)).

Destruction is `destroy!` of the `InboundEmail`. `has_one_attached :raw_email` uses Active Storage’s default `dependent: :purge_later`, so the attachment row goes with the record and the blob is purged asynchronously ([inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb#L30), [attached/model.rb](file:///home/user/workspace/repo/activestorage/lib/active_storage/attached/model.rb#L121-L141), [attachment.rb](file:///home/user/workspace/repo/activestorage/app/models/active_storage/attachment.rb#L51)).

The scheduling wait and the destruction gate are not the same predicate. The job is delayed by the duration `incinerate_after`. Destruction then re-checks `updated_at` against `incinerate_after.ago.end_of_day`. A later touch can make a due job a no-op.

## Time control

`due?` is calendar-sensitive. Do not freeze at midnight UTC.

- `freeze_time` at a mid-afternoon instant, e.g. `Time.utc(2026, 6, 15, 15, 30, 0)`, so `end_of_day` is hours away from `updated_at`.
- Capture `updated_at` from the record after the status update (DB time, not the freeze instant assumed equal).
- Drive the job clock with `assert_enqueued_with job:, at:` / `wait:` and `travel` / `travel_to`.
- Drive the destruction gate independently by stubbing time around `Incineration.new(email).run` without going through the job wait. The two clocks must be tested apart.

Threshold for a given record:

```text
cutoff = ActionMailbox.incinerate_after.ago.end_of_day
destroy iff email.updated_at < cutoff
```

With default 30 days and freeze at `T = 2026-06-15 15:30:00 UTC`:

- Job `at:` is `T + 30.days` (duration wait).
- At that same instant, `30.days.ago.end_of_day` is `T.end_of_day`, so `updated_at ≈ T < T.end_of_day` and the existing tests’ destroy succeeds.
- Equality (`updated_at == cutoff`) must **not** destroy (`<`, not `<=`).
- `updated_at >= cutoff` must not destroy.

Use `ActiveSupport::TestCase` + `ActiveJob::TestHelper` as the current files do. Prefer `ActionMailbox.incinerate = false` restoration via `Object#with` in new tests ([AGENTS.md](file:///home/user/workspace/repo/AGENTS.md) configuration pattern), matching the existing ensure-block in [incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb#L48-L56).

## Focused unit tests (`Incineration`)

Put these next to [incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb) or in a dedicated `incineration_command_test.rb`. Call `Incineration.new(email).run` (or `email.incinerate`) with jobs **not** performed, so scheduling is out of the way.

**Unprocessed records.** Create via `create_inbound_email_from_fixture` (default status `:processing`, [test_helper.rb](file:///home/user/workspace/repo/actionmailbox/lib/action_mailbox/test_helper.rb#L9)). Also cover `:pending`. Travel past the cutoff. `run` must leave `InboundEmail.count` unchanged and `raw_email` attached. Source: `processed?` guard.

**Age boundary.** Processed record (`delivered!`). Freeze mid-afternoon.

1. `travel_to` just before `updated_at` would be `< incinerate_after.ago.end_of_day` → no destroy.
2. `travel_to` so `updated_at` is strictly before cutoff → row gone.
3. Force `updated_at` equal to cutoff (update column, or travel so cutoff equals stored `updated_at`) → no destroy.

Assert `ActionMailbox::InboundEmail.exists?(id)` and count delta, not the private `due?` method. That keeps the tests valid if `due?` is inlined.

**Record changed after scheduling (command side).** `delivered!`, then `touch` or a non-status update that bumps `updated_at`. Travel to the **original** job run time (`30.days` after first update). `run` must no-op because `updated_at` is no longer before cutoff. This is the invariant the job wait alone does not encode.

**Already processed but not due.** `delivered!` then immediate `incinerate` at `T` → record remains. Conductor hits this path ([incinerates_controller.rb](file:///home/user/workspace/repo/actionmailbox/app/controllers/rails/conductor/action_mailbox/incinerates_controller.rb#L9)).

**`incinerate = false` does not change `run`.** With the flag false, a due processed record passed to `incinerate` still `destroy!`s. The flag only gates the callback.

**Attachment/record destruction.** After a successful due `run`: no `InboundEmail`; no `ActiveStorage::Attachment` for that record; after `perform_enqueued_jobs` (purge job), blob `key` is gone from the test service. Store `raw_email_blob.key` before incineration.

## Focused job / callback tests

Keep [incineration_job_test.rb](file:///home/user/workspace/repo/actionmailbox/test/jobs/incineration_job_test.rb) as the discard test; extend it rather than asserting on job internals.

**Terminal status transitions.** One example per status is already in [incineration_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb). Keep all three. Assert:

```ruby
assert_enqueued_with job: ActionMailbox::IncinerationJob,
                     args: [inbound_email],
                     at: ActionMailbox.incinerate_after.from_now
```

Do not hardcode `30.days` in new tests; the invariant is “wait equals `incinerate_after`,” and [configuration_test.rb](file:///home/user/workspace/repo/railties/test/application/configuration_test.rb#L4116-L4123) already shows that duration is configurable. One extra example with `ActionMailbox.incinerate_after = 14.days` (restored after) proves the job wait follows config, not a literal 30.

**Queue.** `assert_enqueued_with job: ActionMailbox::IncinerationJob, queue: …` using the current `ActionMailbox.queues[:incineration]` (or Active Job’s default when that is `nil`). Optionally stub `ActionMailbox.queues` to `:another_queue` and expect that name. Do not hardcode `:action_mailbox_incineration`.

**Non-terminal updates do not enqueue.** `processing!` from pending, or create with default `:processing`: `assert_no_enqueued_jobs only: ActionMailbox::IncinerationJob`.

**Repeated updates.**

- Already `delivered?`, call `delivered!` again → no additional job (`status_previously_changed?` is false).
- Non-status `update!` / `touch` → no job.
- `delivered!` then `failed!` → **second** job enqueued (`assert_enqueued_jobs 2, only: ActionMailbox::IncinerationJob`). This is the current callback, not coalescing.
- Status change inside an uncommitted transaction that rolls back → no job (`after_update_commit`).

**`ActionMailbox.incinerate = false`.** Keep the existing test. Add: flag false during `delivered!` (no job), then set true and `failed!` (job enqueued). The flag is read at callback time, not at create time.

**Create already processed.** `create_inbound_email_from_fixture(..., status: :delivered)` must **not** enqueue. Scheduling is update-commit only. Easy to break by switching to `after_save_commit`.

**Already-deleted records.** Keep [incineration_job_test.rb](file:///home/user/workspace/repo/actionmailbox/test/jobs/incineration_job_test.rb): destroy, `perform_later`, `perform_enqueued_jobs`, `assert_nothing_raised`. Also enqueue **before** destroy, then destroy, then perform: same outcome. That is the documented “ignore emails already deleted” behavior ([incineration_job.rb](file:///home/user/workspace/repo/actionmailbox/app/jobs/action_mailbox/incineration_job.rb#L7-L8)).

**Job perform delegates.** `IncinerationJob.perform_now(email)` on a due processed record deletes it; on an unprocessed or not-due record it does not. That pins `perform` → `incinerate` without requiring the command class to exist.

**Record changed after scheduling (job side).** `delivered!` (capture job), `touch`, `travel` to original `at:`, `perform_enqueued_jobs only: IncinerationJob` → row still present. Then `travel` until the **new** `updated_at` is due and perform a freshly scheduled job (or call `incinerate`) → row gone. This is the preservation case that naive “job wait == delete” refactors will fail.

## Integration-level observation

One path through mailbox processing, not enum bangs in isolation:

1. `freeze_time` mid-afternoon.
2. `create_inbound_email_from_mail(...)` (status `:processing`).
3. `SuccessfulMailbox.receive inbound_email` from [state_test.rb](file:///home/user/workspace/repo/actionmailbox/test/unit/mailbox/state_test.rb) (this does `processing!` then `delivered!`).
4. Assert **exactly one** `IncinerationJob` enqueued, `at: incinerate_after.from_now`, args the same record. The intermediate `processing!` must not enqueue.
5. Assert the row and `raw_email` blob still exist.
6. `travel incinerate_after` and `perform_enqueued_jobs only: ActionMailbox::IncinerationJob`.
7. Assert inbound email count −1, `exists?(id)` false, attachment gone, and after remaining jobs (purge) the blob key is absent.

That is the observable product behavior described in [action_mailbox_basics.md](file:///home/user/workspace/repo/guides/source/action_mailbox_basics.md) (“processed … incinerated after 30 days”) and [inbound_email.rb](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb#L14-L17). Repeat once for `UnsuccessfulMailbox` (`failed`) or `BouncingMailbox` (`bounced`) if the refactor touches status tracking; one successful path is the minimum.

Optional second integration: POST conductor incinerate on a not-due processed email and assert redirect + row still present; same request after travel past cutoff deletes. Only needed if `incinerate`’s public entry points are in scope.

## How to use this during a refactor

1. Land the new tests against **this** revision and confirm they pass. Until then they are the contract, not the refactor’s opinion.
2. Refactor. Re-run:
   - `cd actionmailbox && bin/test test/unit/inbound_email/incineration_test.rb test/jobs/incineration_job_test.rb` plus the new files
   - the mailbox state test if the integration example lives there
3. Failures that only mention private method names, class nesting, or comment text are over-constrained tests; fix the test. Failures on enqueue count/time/queue, row presence, `exists?`, blob keys, or “no exception on missing record” are contract breaks.

The two clocks are the usual breakages: treating `wait: incinerate_after` as sufficient to destroy, dropping `.end_of_day`, using `created_at` or status-entered-at instead of `updated_at`, coalescing repeat jobs, or scheduling on create/save instead of update-commit.
