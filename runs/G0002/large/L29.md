Current contract is HTTP-visible: `fresh_when` / `stale?` write validators and `Cache-Control`, then 304 when `request.fresh?(response)` is true. The predicate lives on the request, not in the controller. A refactor can change private helpers as long as that boundary stays put.

## What the helpers actually do

```text
fresh_when(...)
  cache_control.delete(:no_store)
  derive weak_etag / last_modified from object unless strong_etag
  set response.strong_etag or response.weak_etag via combine_etags
  set Last-Modified if present
  merge public / cache_control
  head :not_modified if request.fresh?(response)

stale?(...)
  fresh_when(...)
  return !request.fresh?(response)
```

[`fresh_when`](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/conditional_get.rb#L137-L155) always strips `no_store`, then sets validators. Weak ETag is the default (`etag:` or the object). `strong_etag:` wins and suppresses the weak path. `last_modified` falls back to `updated_at` or `maximum(:updated_at)`. An ETag is written if there is a strong validator, a weak validator, or a `template:` value. Then it may call `head :not_modified`.

[`stale?`](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/conditional_get.rb#L236-L239) is not a separate freshness algorithm. It runs `fresh_when` (so a fresh request already has status 304 and an empty body) and returns the negated predicate so the `if stale?` block is skipped.

ETag bytes come from the response, not the controller: weak is `W/"…"`, strong is `"…"`, both from `ActiveSupport::Cache.expand_cache_key` + hexdigest. Extra `etag { }` blocks, [template digest](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/etag_with_template_digest.rb), and [flash](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/etag_with_flash.rb) are mixed in only on `ActionController::Base`. `ActionController::API` has `ConditionalGet` without those etaggers.

```diagram
┌──────────────┐   headers    ┌─────────────────────────┐
│ GET/HEAD/…   │─────────────▶│ ConditionalGet          │
│ INM / IMS    │              │ fresh_when / stale?     │
└──────────────┘              └────────────┳────────────┘
                                           ┃
                    ETag / Last-Modified / Cache-Control
                                           ┃
                                           ▼
                              ┌─────────────────────────┐
                              │ Request#fresh?(response)│
                              └────────────┳────────────┘
                         true ┃            ┃ false
                              ▼            ▼
                         304, empty    200, action body
                         stale? false  stale? true
```

## Freshness algebra (the public predicate)

[`Request#fresh?`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/cache.rb#L49-L67) is the contract `fresh_when`/`stale?` must keep.

- `If-None-Match` is split on commas and compared as opaque strings. `"*"` matches any present response ETag; a missing ETag does not match. Weak and strong differ by the `W/` prefix; they do not compare equal.
- `If-Modified-Since` is `Time.httpdate` (IMF-fixdate, RFC 850, asctime). Unparseable → treated as absent. Fresh iff `IMS >= Last-Modified`.
- `Last-Modified` is stored with [`Time#httpdate`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/cache.rb#L193-L194), so subseconds never leave the process.
- `strict_freshness` (false originally, true from Rails 8.0 `load_defaults`): if true, `If-None-Match` alone decides when both headers exist; if false, both must succeed.

Neither helper inspects the HTTP method. Matching validators 304 GET, HEAD, QUERY, and POST alike. `Rack::ConditionalGet` / `Rack::Head` are app-stack only; controller tests never see them. QUERY 304 is already documented as a controller-level contract.

`Cache-Control` is committed later in [`merge_and_normalize_cache_control!`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/cache.rb#L313-L358) / [`handle_conditional_get!`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/http/cache.rb#L304-L310):

- `fresh_when(etag: …)` with empty options → `max-age=0, private, must-revalidate`
- `public: true` only → `public` (default max-age/must-revalidate are not applied)
- `cache_control: { no_cache: true }` → `no-cache`, optionally `public, no-cache`
- `no_store` then `fresh_when` → default private validator header
- `fresh_when` then `no_store` → `no-store`

## How this detects semantic drift without locking internals

Assert only what a client can see plus one test-owned side effect:

- Status 304 vs 200
- Body empty vs the action’s payload
- `ETag` prefix (`W/` vs not) and round-trip identity
- `Last-Modified` equal to `.httpdate` of the input time
- `Cache-Control` exact string
- Whether the `stale?` block ran (`work_calls`)

Do **not** assert `combine_etags` array shape, etagger list order, that `stale?` calls `fresh_when`, hexdigest inputs, or `request.fresh?` call counts. A refactor that inlines `stale?`, sets headers in a different order, or hashes validators differently is allowed **if** the captured ETag still 304s on replay and still misses on `"nomatch"`.

The high-leverage traps:

- **Subsecond IMS 304** fails if comparison uses the original `Time` instead of the HTTP-date round-trip.
- **`INM: *` with no ETag → 200** fails if `*` is implemented as “always fresh”.
- **Strict vs non-strict both-headers** fails if precedence is hardcoded one way.
- **Strong vs `W/`-prefixed INM → 200** fails if matching strips weakness.
- **`work_calls` on 304 stays 0** fails if 304 is applied after the block, even if the HTTP status is later patched.
- **`public: true` → `Cache-Control: public`** fails if someone “fixes” it to `max-age=0, public, must-revalidate`.
- **POST 304** fails if a method check is introduced; that is current helper behavior, not Rack’s.

Request tests (rows 28, plus existing `RequestEtag` / `RequestIfModifiedSince`) pin the predicate in isolation. Controller tests pin that `fresh_when`/`stale?` still feed that predicate and still emit the same headers. Together they freeze the HTTP contract without freezing the implementation.
