Treat `#touch` as a black box. A refactor preserves behavior only if every case below still produces the same **public** outcomes: exceptions and messages, in-memory attributes, database rows (via `reload` / a second `find`), dirty APIs (`changed?`, `changed`, `saved_changes?`, `saved_changes`), and which callbacks actually run. Do not assert on `_touch_row`, `@_trigger_update_callback`, `@_touch_attr_names`, or any other private helper — those can change while the contract stays the same.

The public contract is the documented one on [`Persistence#touch`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L764-L816): it writes `updated_at`/`updated_on` (and any extra names) without validations; only `after_touch`, `after_commit`, and `after_rollback` run; it requires a persisted, writable record.

Instrument each model with flags for `after_touch`, `after_commit` / `after_update_commit`, `after_rollback` / `after_rollback on: :update`, plus `before_validation` / `after_save` / `after_update` as negative controls. Use a second process of the same row (`Model.find(id)`) as the database oracle.

## Record lifecycle

**Persisted.** `record = Model.create!(...); record.touch`

- Returns without error; `persisted?` stays true.
- In-memory `updated_at`/`updated_on` move forward; `record.reload` shows the same values (the UPDATE landed).
- `after_touch` ran; `after_commit` / `after_update_commit` ran; `after_save` / `after_update` / validations did not.
- An invalid record (`valid? == false`) still touches. That is the “no validation” clause.

**New.** `Model.new.touch` and `Model.new.touch(:updated_at)`

- Raises `ActiveRecord::ActiveRecordError` with `Cannot touch on a new or destroyed record object`.
- `new_record?` remains true; no INSERT (`Model.count` unchanged).
- `after_touch` / `after_commit` did not run — the callback chain does not complete if the method raises.

**Destroyed.** `record.destroy; record.touch`

- Same exception and message as new (both fail `persisted?`).
- `destroyed?` stays true; a `find` of that id still misses; no UPDATE of a resurrected row.
- Callbacks do not run.

**Readonly record.** `record.readonly!; record.touch`

- Raises `ActiveRecord::ReadOnlyRecord` with `"#{Model} is marked as readonly"`.
- DB timestamps unchanged on `Model.find(id)`.
- `after_touch` does not run.

**Readonly attribute** (distinct from a readonly record): `person.touch(:born_at)` raises `ActiveRecord::ActiveRecordError` with `"born_at is marked as readonly"` and writes nothing.

These four exception/state observations are the lifecycle contract. They do not depend on how persistence is implemented internally.

## Timestamp columns, custom attributes, aliases, explicit time

Use two models: one with real `updated_at` (e.g. `Topic`/`Person`), one with aliased timestamps (`Developer`: `updated_at` → `legacy_updated_at`), one with extra datetime columns (`Task#ending` / `#starting`), and one with **no** timestamp columns (`Car`).

| Call | Public observations that pin the contract |
|---|---|
| `topic.touch` | Both in-memory and reloaded `updated_at`/`updated_on` change; `created_at` does not. |
| `developer.touch` | Accessors `updated_at`/`updated_on` change; `saved_changes.keys` are the **real** columns (`legacy_updated_at`, `legacy_updated_on`), not the alias names. |
| `developer.touch(:updated_at)` | Same as default touch — the alias resolves; not a no-op and not a missing-attribute error. |
| `developer.touch(:created_at)` | `created_at` **and** update timestamps all move; `created_at` is not left dirty. |
| `task.touch(:ending)` | `ending` moves (≈ now); update timestamps move too if the table has them. |
| `task.touch(:starting, :ending)` | Every named column plus update timestamps share one time. |
| `record.touch(time: t)` | In-memory and reloaded `updated_at` **equal** `t` (not merely “later”). |
| `record.touch(:created_at, time: t)` | Named columns **and** update timestamps all equal `t`. |
| `Car.first.touch` | No exception; no UPDATE required; `after_touch` still runs. |
| `record_timestamps = false` then `touch` | `save` would skip timestamps; `touch` must **not**. In-memory and DB `updated_at` still change. |

The alias case is established by `saved_changes` keys plus `reload` of `legacy_updated_at`, not by inspecting `attribute_aliases`. The explicit-time case is established by equality to `t` on both the instance and a fresh `find`, not by stubbing `current_time_from_proper_timezone`.

## Optimistic locking

On a locking model (`Person` with `lock_version`):

**Fresh row.** `p.touch`

- In-memory and reloaded `lock_version` increment by 1.
- `changed?` is false; `saved_changes?` is true; `saved_changes.keys` include `"lock_version"` and `"updated_at"`.
- `StaleObjectError` is not raised.
- `after_touch` and `after_update_commit` run.

**Stale row.** Load `p1` and `p2`; `p1.update!(...)`; `p2.touch`

- Raises `ActiveRecord::StaleObjectError` whose public message is `Attempted to touch a stale object: Person` (`attempted_action` is `"touch"`, not `"update"`).
- `p2.saved_changes?` is false (the failed UPDATE does not become the last save).
- Reloaded `lock_version` is the value `p1` wrote — `p2.touch` did not persist a bump.
- `after_touch` / `after_commit` do not run (the method raised).
- `p2.lock_version` in memory is restored to the pre-touch value (the bump is not left visible after the error).

**Missing row with locking.** `Person.delete(p.id); p.touch` is the same stale path (`StaleObjectError`), not the silent no-row path. That distinction is part of the locking contract.

`Locking::Optimistic.preserve_lock_version_on_touch` is a public (if advanced) API: inside the block, `touch` must not bump `lock_version` in memory or in the DB, must not raise on a stale object, and `saved_changes` must omit `lock_version`. Outside the block, the bump returns. Include it only if the refactor claims to preserve locking, which it must.

## Dirty tracking and saved changes

These observations are independent of how `_touch_row` clears changes.

**Clean record.** After `touch`: `changed? == false`, `saved_changes? == true`, `saved_changes` contains exactly the touched timestamp columns (plus `lock_version` when locking applied).

**Dirty record.** Assign `developer.salary += 1` (do not save), then `touch`:

- `changed?` stays true; `changed == ["salary"]`; `salary_changed?` is true — pre-existing dirt is not consumed.
- `saved_changes` is only the touched timestamps, not `salary`.
- `reload` restores the old salary: `touch` did not persist non-touched dirty attributes.
- In-memory `updated_at` is the new time even before reload.

**Named attribute.** `touch(:created_at)` leaves `created_at_changed? == false` and `changed? == false`; the new value is still visible on the instance and after `reload`.

**Failed locking touch.** `saved_changes?` stays false, as above. Do not require a particular `changed?` on timestamps after `StaleObjectError` unless you first record current behavior on this codebase — writes happen before the UPDATE, and that in-memory dirt is observable.

## Callbacks

Negative controls matter as much as positive ones. On a persisted successful touch:

1. `after_touch` ran (and ran **before** `after_commit` — set a flag in `after_touch` and assert it is already set inside `after_commit`).
2. `after_commit` ran once, only after the implicit transaction commits.
3. Nested `transaction { transaction(requires_new: true) { touch } }` — `after_commit` is empty until the outer block exits, then fires once.
4. `after_save`, `after_update`, `before_save`, `before_update`, `before_validation`, `after_validation` did **not** run.
5. `after_update_commit` / `after_commit on: :update` ran for a successful persisted touch (the public stand-in for “this counted as an update”).

**Rollback.** `Model.transaction { record.touch; raise ActiveRecord::Rollback }`

- `after_rollback` / `after_rollback on: :update` ran; `after_commit` did not.
- In-memory `updated_at` and `lock_version` match the pre-touch values after the rollback (state restore is public).
- A subsequent `find` shows the pre-touch row.

**`no_touching`.** `Model.no_touching { record.touch }` — timestamps unchanged, `after_touch` does not run. That is a public override of the whole method, not an internal short-circuit you should reimplement in the strategy.

## No row updated

This is a different contract from stale locking. Use a **non-locking** model (`Topic`, `Developer`) so a 0-row UPDATE does not become `StaleObjectError`.

```ruby
topic = Topic.find(id)
Topic.delete(id)          # or delete_all; this instance still reports persisted?
topic.touch
```

Public observations:

- No exception (`persisted?` is still true on this instance; `readonly?` is false).
- In-memory `updated_at` **does** change — the instance still assigns the touch time.
- `Topic.find(id)` raises `RecordNotFound` — nothing was written.
- `after_touch` **does** run (the method completed).
- `after_commit` and `after_update_commit` **do not** run. That is the public meaning of “no row updated”: the touch is not an update for transactional callbacks.
- `after_rollback` also does not run if you then `transaction { topic.touch; raise Rollback }` after the delete — the record is not treated as having performed an update.
- `changed?` is false; `saved_changes?` is true for the timestamp keys (in-memory dirty tracking still treats it as a completed touch). Compare this with the locking missing-row case, where `StaleObjectError` is raised and `saved_changes?` is false.

A second no-row setup: `default_scope` **with** `all_queries: true` that excludes the row. A default scope **without** `all_queries` must **not** produce this case — `DeveloperCalledJamis` still persists the timestamp even when the scope would exclude it. That pair of observations pins which scopes affect `touch` without reading `_build_update_manager`.

## How to use this as a preservation check

Run the same scripted cases against current `main` and the refactored branch (or keep this suite as regression tests). Equality of these observations is the proof:

- exception class + message
- `persisted?` / `new_record?` / `destroyed?` / `readonly?`
- attribute values in memory and after `reload`/`find`
- `changed` / `saved_changes` key sets
- `lock_version` and `StaleObjectError#attempted_action`
- which callback flags flipped, and in what order
- whether a second connection still sees the old row

If those match, the refactor preserved `#touch`. If any private helper was inlined, renamed, or removed, that is irrelevant unless one of the observations above changes.
