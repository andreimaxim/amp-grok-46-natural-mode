That matches `StrictValidationFailed` itself: these failures are exceptional and not meant to land in the user-facing errors collection.

**Exception class and message.** `strict: true` becomes `ActiveModel::StrictValidationFailed`; any other truthy value is used as the exception class. The message is `error.full_message` (attribute + generated message), which is what [`test_strict_validation_error_message`](file:///home/user/workspace/repo/activemodel/test/cases/validations_test.rb) asserts (`"Title can't be blank"`). The `Error` is built first only so that message can be computed; it is not stored. After rescue, callers already have the string on `exception.message`. The exception does not carry the `ActiveModel::Error` object, so appending first still does not yield that object from the rescue.

**Collection mutation.** Append-then-raise leaves a recorded error after the stack unwinds. Rescue handlers would see `errors` non-empty, `added?` true, and `messages` populated — the opposite of the documented `{}`. Validation aborts on the first strict failure, so the collection would hold a partial result while later validators never ran. Anything that rescues and then renders, re-validates, or copies `errors` would observe leftover state. `valid?` tests only assert the raise today; they do not license this mutation.

**Normal `add` return.** Non-strict `add` appends and returns the `ActiveModel::Error` ([`add creates an error object and returns it`](file:///home/user/workspace/repo/activemodel/test/cases/errors_test.rb)). Strict `add` never returns; `raise` unwinds. Reordering does not change that. Inspecting the collection after rescue is a new side channel, not a completion of the return contract.

**Custom strict exception classes.** `strict:` may be any exception, as in `strict: NameIsInvalid` and [`test_strict_validation_custom_exception`](file:///home/user/workspace/repo/activemodel/test/cases/validations_test.rb) (`CustomStrictValidationException < StandardError`). Those classes still receive only the full-message string. They have no slot for the `Error` instance. Mutating `@errors` on the way out is especially surprising when the rescued type is an app-specific exception handled far from the model.

If a caller truly needs the `Error` after a strict failure, that belongs on the exception API (a separate, breaking change), not as a leftover entry in `errors`. Keep raise-before-append.
