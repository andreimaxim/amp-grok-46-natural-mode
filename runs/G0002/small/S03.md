`String#truncate_bytes` has four branches: within-budget `dup`, omission larger than the budget (`ArgumentError`), omission equal to the budget (`omission.dup`), and a grapheme walk that then appends the omission. A refactor is unchanged only if every branch still produces the same value, encoding, class, object identity, and error.

Run the cases below against the pre-refactor method and the new one (same Ruby, same `truncate_to` / `omission`). Do not use the existing tests as the oracle: they miss subclass, mutation, exact ASCII cuts, and the US-ASCII truncation path. Record `inspect`, `bytesize`, `encoding`, `class`, `object_id`, `frozen?`, `valid_encoding?`, and the receiver after the call.

Fixed sizes used below: `"…"` is 3 bytes, `"👍"` / `"🖖"` are 4, `"é"` is 2, `"❤️"` is one 6-byte cluster, `"👩‍❤️‍👩"` is one 20-byte cluster.

---

**1. Within-budget strings**

```ruby
s = "hello"
r = s.truncate_bytes(5)
r2 = s.truncate_bytes(100)
```

Expect `r == "hello"`, `r2 == "hello"`, `!r.equal?(s)`, `!r2.equal?(s)`, `r.encoding == s.encoding`. Repeat with a frozen receiver: result is unfrozen and still a different object.

This proves the early `bytesize <= truncate_to` path still copies, including the equal-bytesize case, and does not return `self`. A `byteslice`/`self` refactor would fail identity or freeze.

**2. ASCII truncation**

`"abcdef"` is 6 bytes. Default omission:

| `truncate_to` | result | bytesize |
|---|---|---|
| 0, 1, 2 | `ArgumentError` | — |
| 3 | `"…"` | 3 |
| 4 | `"a…"` | 4 |
| 5 | `"ab…"` | 5 |
| 6, 7 | `"abcdef"` | 6 |

`omission: nil` at 3 → `"abc"`; at 5 → `"abcde"`.

This proves the cut is in bytes, not characters, that the omission is included in the budget (`cut_at = truncate_to - omission.bytesize`), and that the within-budget branch takes over at exactly 6. If someone truncated on `length` or appended the omission without reserving room, 4/5 would be wrong.

**3. Multibyte truncation (codepoints)**

`"👍👍👍👍"` is 16 bytes (4×4). `"café!!"` is 7 (`é` = 2).

- `"👍👍👍👍".truncate_bytes(15)` → `"👍👍👍…"` (15 bytes)
- `"👍👍👍👍".truncate_bytes(16)` → `"👍👍👍👍"`
- `"café!!".truncate_bytes(4, omission: nil)` → `"caf"` (3 bytes), **not** 4 bytes
- `"café!!".truncate_bytes(5, omission: nil)` → `"café"` (5 bytes)
- every result `valid_encoding? == true`

The 4-byte café case is the codepoint test: a 2-byte `é` does not fit in the remaining byte, so it is dropped whole. A `byteslice` refactor that splits `é` would yield 4 bytes and `valid_encoding? == false`. The thumbs 15 vs 16 case proves a 4-byte emoji is not split to fill the last byte of the budget.

**4. Grapheme clusters**

`"a ❤️ b"` clusters: `["a", " ", "❤️", " ", "b"]` with sizes `[1, 1, 6, 1, 1]` (10 bytes). `"❤️"` is U+2764 + U+FE0F, two codepoints, one cluster.

With `omission: nil`:

- 1 → `"a"`
- 2 through 7 → `"a "` (2 bytes)
- 8 → `"a ❤️"`
- 9 → `"a ❤️ "`
- 10+ → original

`"👩‍❤️‍👩"` is one 20-byte cluster: `truncate_bytes(n, omission: nil)` is `""` for every `n < 20`, and the original at 20.

This proves the walk is `each_grapheme_cluster`, not `each_char`. A codepoint walk would emit `"a ❤"` (heart without VS16) somewhere in 2..7, or a prefix of ZWJ sequences for the couple. Budgets 3 and 7 are the ones that look like they have spare room and must still refuse to split the cluster.

**5. Exact byte boundaries**

Hold the input fixed and step `truncate_to` across every cluster edge:

- ASCII: result bytesize equals `truncate_to` when truncating, and equals `bytesize` when not.
- `"café!!"` / nil: 3 → `"caf"`, 4 → `"caf"` (still 3), 5 → `"café"`.
- thumbs / default `"…"`: 12 would be three thumbs plus no room? `cut_at = 12-3 = 9` → two thumbs (8) + `"…"` = `"👍👍…"` (11 bytes). 15 → `"👍👍👍…"` (15). 16 → original.

Also assert `result.bytesize <= truncate_to` on every passing call.

The “budget 4 on café stays 3 bytes” observation is the one that proves “at most N bytes” is not “as close as possible by splitting.” Going over N, or landing on an invalid UTF-8 sequence, is a behavior change.

**6. Custom and nil omissions**

On `"👍👍👍👍"` (from the existing examples, which you should re-check, not trust):

| budget | `omission:` | result |
|---|---|---|
| 16 | `nil`, `" "`, `"🖖"` | `"👍👍👍👍"` (omission unused) |
| 15 | `nil` | `"👍👍👍"` |
| 15 | `" "` | `"👍👍👍 "` |
| 15 | `"🖖"` | `"👍👍🖖"` |
| 5 | `nil` | `"👍"` |
| 5 | `" "` | `"👍 "` |
| 5 | `"🖖"` | `"🖖"` |
| 4 | `nil` | `"👍"` |
| 4 | `" "` | `" "` |
| 4 | `"🖖"` | `"🖖"` |

Nil is `omission ||= ""` before the case, so it is an empty omission, not “use the default.” Custom ASCII (`" "`) vs custom multibyte (`"🖖"`) proves the reserved room is `omission.bytesize`, not `omission.length`. Budget 4 with `" "` returning only `" "` proves that when the next cluster (4 bytes) does not fit in `cut_at` (3), the prefix is empty and you still append the omission.

**7. Omission equal to or larger than the budget**

```ruby
"hello world".truncate_bytes(3, omission: "…")  # == "…", not equal to the omission object
"👍👍👍👍".truncate_bytes(3, omission: "🖖")   # ArgumentError
"hello".truncate_bytes(2, omission: "…")        # ArgumentError
```

Equal: result equals the omission, `!result.equal?(omission)`, class is the omission’s class (`String`), not the receiver’s class. Larger: `ArgumentError` with `Omission "🖖" is 4, larger than the truncation length of 3 bytes` (inspect + both sizes). Empty omission at 0 is allowed (`nil` / `""` → `""`).

This isolates the two middle branches. Returning `omission` itself would share mutation; returning `self.class.new(omission)` would change class on this path; swallowing the error or truncating without the omission would change the documented contract.

**8. Encoding and subclass preservation**

```ruby
class MyString < String; end
ms = MyString.new("hello world")

String.new("hello world", encoding: Encoding::US_ASCII).truncate_bytes(20).encoding  # US-ASCII
String.new("hello world", encoding: Encoding::UTF_8).truncate_bytes(5).encoding      # UTF-8
String.new("a" * 30, encoding: Encoding::UTF_8).truncate_bytes(15).encoding          # UTF-8
```

| path | class | encoding |
|---|---|---|
| within budget (`ms.truncate_bytes(20)`) | `MyString` | receiver’s |
| grapheme walk (`ms.truncate_bytes(5)`) | `MyString` | receiver’s (then `<< omission` may transcode) |
| omission == budget (`ms.truncate_bytes(3, omission: "…")`) | `String` | omission’s |
| US-ASCII truncated with default `"…"` | `String` | **UTF-8** |

The last row is real: `"he…"` is UTF-8 because the default omission is UTF-8. A “always force UTF-8” or “always keep receiver encoding” change would show up here. The omission-equal path returning `String` rather than `MyString` is also current behavior (`omission.dup`); “preserving subclass everywhere” would be a change, not a preservation.

**9. Receiver mutation**

```ruby
orig = "hello world"
copy = orig.dup
orig.truncate_bytes(5)
# orig == copy, orig.bytesize == 11

f = "hello world".freeze
f.truncate_bytes(5)  # no FrozenError; f still "hello world"
```

Result `object_id` never equals the receiver’s, including within-budget and frozen receivers. The receiver’s bytes, encoding, class, and frozen bit are unchanged.

This proves every branch allocates (`dup`, `omission.dup`, or `self.class.new`). In-place `replace` / `concat` on `self` would fail this even if the returned string looked right.

---

**How to treat a mismatch**

A difference on any row above is a behavior change. The existing tests in [string_ext_test.rb](file:///home/user/workspace/repo/activesupport/test/core_ext/string_ext_test.rb) already cover thumbs, the heart/couple graphemes, and UTF-8 encoding of a truncated ASCII string; they do **not** cover ASCII exact cuts, café codepoint boundaries, subclass, mutation, frozen receivers, or US-ASCII. Those are the observations that catch a “cleaner” `byteslice` rewrite.

I assumed “unchanged” means the four-branch contract above, including the omission-equal path returning a `String` and US-ASCII + `"…"` becoming UTF-8 — not a stricter idealized contract.
