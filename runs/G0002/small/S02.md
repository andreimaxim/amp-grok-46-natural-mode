The proposed one-liner is not equivalent. It drops the class-owned compatibility hook, so I would leave this on the `deep_merge!` line.

`deep_merge?` is the compatibility API. This removes it from the only call site.

`#deep_merge!` currently does:

```ruby
if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
  this_val.deep_merge(other_val, &block)
elsif block_given?
  block.call(key, this_val, other_val)
else
  other_val
end
```

`deep_merge?` is documented as the including class’s way to restrict or expand what may be deep-merged into `self`. Default is `other.is_a?(self.class)`, not `other.is_a?(DeepMergeable)`:

```54:56:activesupport/lib/active_support/deep_mergeable.rb
    def deep_merge?(other)
      other.is_a?(self.class)
    end
```

Hash and Parameters already specialize that, for different reasons:

- `Hash#deep_merge?` → `other.is_a?(Hash)` so `HashWithIndifferentAccess` can merge with a plain `Hash`
- `Parameters#deep_merge?` → `other.is_a?(DeepMergeable)` because `Parameters#merge!` converts via `to_h`

`other_val.is_a?(DeepMergeable)` is the Parameters rule, applied to every includer. Two `DeepMergeable` objects are not interchangeable. The mixin only requires `merge!(other, &block)`. `Hash#merge!` will not accept a `Wrapper`; `Wrapper#merge!` expects `#underlying`. Compatibility belongs on `this_val`, which is why the hook is `this_val.deep_merge?(other_val)`.

That is covered by the tests, not just the comment:

- [`deep_merge does not deep merge non-subclass values by default`](file:///home/user/workspace/repo/activesupport/test/deep_mergeable_test.rb#L89-L92) — `Wrapper` vs `OtherWrapper` (`Wrapper.dup`). Both include `DeepMergeable`. Today the nested value is replaced. After this change both sides pass `is_a?(DeepMergeable)`, so the nested value is recursively merged and this assertion fails.
- [`deep_merge? can be overridden to allow deep merging of non-subclass values`](file:///home/user/workspace/repo/activesupport/test/deep_mergeable_test.rb#L94-L97) — `OmniWrapper` would keep working by accident, and the override would never be called.
- Subclass merging still works (`SubWrapper` is still `DeepMergeable`), which hides the break if you only run the happy path.

Block fallback moves with the same condition. A rejected pair currently hits `block.call(key, this_val, other_val)` or `other_val`. After this change any two `DeepMergeable` values recurse instead, so a block used as the escape hatch for “same mixin, not merge-compatible” never runs. If `merge!` then cannot handle `other`, the old replace-or-block path becomes an exception.

Mutation and return of the receiver are unchanged: nested recursion is still non-bang `this_val.deep_merge(...)`, and `deep_merge!` still returns whatever `merge!` returns. The observable change is which nested values take that path.

Please keep `this_val.deep_merge?(other_val)`. A type check on `other_val` cannot replace a hook that Hash, Parameters, and custom includers already disagree on.
