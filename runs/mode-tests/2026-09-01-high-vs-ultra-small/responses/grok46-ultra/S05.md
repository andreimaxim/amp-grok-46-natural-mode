**Review: reject appending before the `strict:` raise.**

`ActiveModel::Errors#add` must keep raising *instead of* adding. Appending first is a contract break, not a convenience for rescue handlers.

### Strict contract

Docs on `#add` are explicit:

> If the `:strict` option is set to `true`, it will raise `ActiveModel::StrictValidationFailed` **instead of adding the error**. `:strict` option can also be set to any other exception.

The documented example then shows the collection still empty:

```ruby
person.errors.add(:name, :invalid, strict: true)
# => ActiveModel::StrictValidationFailed: Name is invalid
person.errors.add(:name, :invalid, strict: NameIsInvalid)
# => NameIsInvalid: Name is invalid

person.errors.messages # => {}
```

Same wording in `validates` / `validates!` and the Active Model guide: strict validations raise **instead of adding**. The current body matches that:

```ruby
error = Error.new(@base, attribute, type, **options)

if exception = options[:strict]
  exception = ActiveModel::StrictValidationFailed if exception == true
  raise exception, error.full_message
end

@errors.append(error)
error
```

The `Error` is built only so the exception can carry `error.full_message`. It is not part of `@errors`.

### Exception class and message

- `strict: true` → `ActiveModel::StrictValidationFailed` with `error.full_message` (`"Name is invalid"`, `"Title can't be blank"`).
- `strict: SomeException` → that class, same string. Not wrapped, not `StrictValidationFailed`.
- Covered by `test_strict_validation_in_validates`, `test_strict_validation_error_message` (`assert_equal "Title can't be blank", exception.message`), and `test_strict_validation_custom_exception` (`CustomStrictValidationException`).

Callers already get the human-readable message on the exception. They do not need the `Error` object in the collection after rescue.

### Collection mutation

`@errors.append(error)` runs only on the non-strict path. After a strict raise, `errors.messages` is `{}` even if the caller rescues. That is the documented, intended state.

Appending first would leave a leftover `ActiveModel::Error` after:

```ruby
begin
  record.errors.add(:name, :invalid, strict: true)
rescue ActiveModel::StrictValidationFailed
  record.errors # now non-empty
end
```

That breaks `errors.empty?`, `full_messages`, `valid?` follow-ups, and any code that treats “we rescued a strict failure” as “the record was not marked invalid.” Strict validations are exceptional; they are not a second way to populate `errors`.

### Normal `add` return

Non-strict `add` appends, then returns the `ActiveModel::Error`:

```ruby
error = person.errors.add(:name, :blank)
assert_equal error, person.errors.objects.first
```

(`"add creates an error object and returns it"` in `errors_test.rb`.)

The strict path does not return. `raise` unwinds before `@errors.append` and before `return error`. Moving the append above the raise would not give rescue handlers that return value; it would only mutate the collection as a side effect of an exception. If someone wants the object, they already have `error.full_message` on the exception — that is the public payload.

### Custom strict exception classes

Any truthy `options[:strict]` other than `true` is raised as the exception class (`NameIsInvalid`, `CustomStrictValidationException`, `TokenLengthException`). Message is still `error.full_message`. Custom classes do not change whether the error is stored; they only change what is raised. Appending before raise would leak into `@errors` for those classes too, including app-specific exceptions people rescue by type.

### Verdict

Do not reorder. Keep: build `Error` → if `strict`, raise mapped class with `full_message` → else append and return `error`. The “inspect after rescue” use case contradicts the documented “raise instead of adding” contract and would be a silent breaking change for anyone who rescues and then reads `errors`.
