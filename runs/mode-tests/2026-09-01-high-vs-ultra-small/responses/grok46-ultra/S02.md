**Don’t land this.** It removes the receiver-owned compatibility check that `deep_merge?` exists for.

```ruby
# current — this_val decides whether other_val can be merged into it
if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
  this_val.deep_merge(other_val, &block)
elsif block_given?
  block.call(key, this_val, other_val)
else
  other_val
end
```

[`DeepMergeable#deep_merge?`](file:///home/user/workspace/repo/activesupport/lib/active_support/deep_mergeable.rb#L50-L56) is the hook classes use to restrict or expand what they recurse into, defaulting to `other.is_a?(self.class)`. Hash and Parameters already override it, and the custom-class tests exist specifically for this:

- [`Hash#deep_merge?`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/hash/deep_merge.rb#L45-L47) → `other.is_a?(Hash)` (so `HashWithIndifferentAccess` can merge a plain Hash; a non-Hash DeepMergeable is not assumed mergeable)
- [`Parameters#deep_merge?`](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb#L1086-L1088) → `other.is_a?(DeepMergeable)` (Parameters *chooses* the broader domain)
- default / `Wrapper`: subclass values merge; `OtherWrapper` does not (`deep_merge does not deep merge non-subclass values by default`)
- `OmniWrapper`: override can *widen* the domain (`deep_merge? can be overridden to allow deep merging of non-subclass values`)

Replacing `this_val.deep_merge?(other_val)` with `other_val.is_a?(DeepMergeable)` makes compatibility a global type check instead of a decision owned by `this_val`. Consequences:

1. **Custom DeepMergeable classes** — `Wrapper.deep_merge(OtherWrapper)` would recurse instead of replacing the nested value. That fails the non-subclass test. Any override that *restricts* the domain is ignored; `deep_merge?` becomes dead on this path.
2. **Block fallback** — mixed DeepMergeable pairs currently miss the `if` and hit `block.call(key, this_val, other_val)` (or `other_val`). After this change they recurse and never reach the block.
3. **Hash vs Parameters / other DeepMergeable** — Hash would start treating any DeepMergeable nested value as mergeable. Today `Hash#deep_merge?(Parameters)` is false, so the nested Parameters is replaced (or passed to the block). Recursing into `Hash#deep_merge(non_hash)` is not a contract Hash opted into; `merge!` can TypeError on objects without Hash’s merge protocol.
4. **Mutation / return** — the recursive call is still `this_val.deep_merge` (non-bang), so outer `deep_merge!` still mutates `self` and still does not mutate nested values *when the branch does not change*. Cases that flip from replace/block to recurse do change the returned nested object (new merged value vs `other_val` / block result). That is an observable behavior change, not a no-op cleanup.

`other_val.is_a?(DeepMergeable)` is neither necessary nor sufficient for `this_val.deep_merge(other_val)`. The `is_a?(DeepMergeable)` check on `this_val` is what makes the recursive call safe; `deep_merge?` is what makes it compatible. Keep both.
