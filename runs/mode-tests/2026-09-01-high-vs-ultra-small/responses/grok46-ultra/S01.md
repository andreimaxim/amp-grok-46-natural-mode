`travel_to` freezes “now” for the rest of the test (or for a block) by stubbing a small set of class methods. Non-block travels are cleared in `after_teardown` via `travel_back`. Implementation: [activesupport/lib/active_support/testing/time_helpers.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/testing/time_helpers.rb). Tests: [activesupport/test/time_travel_test.rb](file:///home/user/workspace/repo/activesupport/test/time_travel_test.rb).

## What a test author should expect

```text
travel_to(date_or_time, with_usec: false)
  reject nested block-form if in_block
  normalize date_or_time → Time `now`
  drop usec unless with_usec: true
  now = now.getlocal          # system TZ, not Time.zone
  remember previous Time.now if Time.now is already stubbed
  stub Time.now / Time.new / Date.today / DateTime.now
  if block
    in_block = true
    yield
    restore previous travel OR travel_back
    in_block = false
```

`Time.current` / `Date.current` are not stubbed. They keep working through `Time.zone` on top of the stubbed `Time.now`, so they honor the application zone. Prefer those in app code; `Time.now` / `Date.today` are process-TZ clocks.

## Input normalization

DateTime is a Date in Ruby, so the Date branch is `is_a?(Date) && !is_a?(DateTime)`.

- **Date** (not DateTime): `date.midnight.to_time`. `Date#midnight` is `beginning_of_day` → `in_time_zone`, i.e. 00:00:00 in `Time.zone` (or process local if no zone). Then `#to_time`.
- **String**: `Time.zone.parse(date_or_time)`. Application zone; missing parts filled from `Time.zone.now`. A string with milliseconds is parsed, then usually truncated (see `with_usec`).
- **Everything else**: keep it if `is_a?(Time)` (this includes `ActiveSupport::TimeWithZone`, which lies about being a Time). Otherwise `#to_time`. DateTime takes this path (`DateTime#to_time` keeps the same UTC offset).

Then always:

1. `now = now.change(usec: 0)` unless `with_usec: true`
2. `now = now.getlocal` so later `Time.at(now)` and `now.to_date` use the **system** timezone

That is why a time constructed in Ekaterinburg (+5) shows up on `Time.now` / `Date.today` / `DateTime.now` as the equivalent US/Eastern (−5) wall clock. `Time.zone.now` still shows the application-zone instant.

## What is stubbed

Only these four singleton methods, via `SimpleStubs` (alias original, `define_singleton_method` replacement):

| Call | Stub |
|---|---|
| `Time.now` | `Time.at(now)` |
| `Time.new` | see below |
| `Date.today` | `Date.jd(now.to_date.jd)` |
| `DateTime.now` | `DateTime.jd(date, hour, min, sec + subsec, offset as Rational day)` |

Subclasses (`TimeSubclass.now`, etc.) are not stubbed; they keep their own class methods. They typically still *read* the stubbed base clocks, so their values match but their class is unchanged.

Re-stubbing the same method first unstubs, so the recorded “original” stays the real implementation, not an earlier stub.

## `Time.new` with arguments

```ruby
stubs.stub_object(Time, :new) do |*args, **options|
  if args.empty? && options.empty?
    at(now)   # Time.new and Time.new() → frozen now
  else
    Time.send(stub.original_method, *args, **options)  # real Time.new
  end
end
```

- `Time.new` / `Time.new()` → same as `Time.now`
- `Time.new(2021)`, `Time.new(2004, 11, 25)`, `Time.new(precision: 3)`, `Time.new("2000-12-31 23:59:59.56789", precision: 3)` → real Ruby `Time.new`

Any positional arg **or** kwarg bypasses the freeze. `precision:` alone is enough.

## `with_usec`

Default `false`: `change(usec: 0)` before stubbing. Prevents MySQL-style round-vs-floor off-by-one-second errors. `Time.now.usec` and `DateTime.now.usec` are 0.

`with_usec: true`: keep fractional seconds. `DateTime.now` gets them through `now.sec + now.subsec`. `travel` / `freeze_time` forward this flag.

A string like `"2004-11-24T01:04:44.123-05:00"` still lands on the whole second unless you pass `with_usec: true`.

## Block cleanup

Before installing stubs, if `Time.now` is already stubbed:

```ruby
stubbed_time = Time.now if stubs.stubbing(Time, :now)
```

After the block (`ensure`, so it runs on raise too):

- previous travel existed → `travel_to stubbed_time` (non-block; reinstalls that freeze)
- otherwise → `travel_back` (drop all TimeHelpers stubs)

Then `in_block = false`.

So:

- `travel_to t1` (no block); later `travel_to t2 do ... end` → inside: t2; after: **t1**, not real time
- `travel_to t do ... end` with no prior travel → after: real time
- non-block `travel_to` with no later block → stays until `travel_back` or `after_teardown`

`in_block` and `simple_stubs` are **per test-case instance**. Another object that includes `TimeHelpers` has its own flag and stub table; its block-form `travel_to` does not trip this test’s nested-block guard, and its `travel_back` does not restore this test’s stubs.

## Why nested block-form is rejected

At the top of `travel_to`:

```ruby
if block_given? && in_block
  raise <<~MSG
    Calling `travel_to` with a block, when we have previously already made a call to `travel_to`, can lead to confusing time stubbing.
    ...
  MSG
end
```

`in_block` is a single boolean, set only around a block-form call. It is not a nest counter.

Rejected: block-form inside an already-open block-form on the **same** helper instance.

Allowed:

- non-block `travel_to` inside a block (just replaces the freeze; outer `ensure` still restores)
- sequential non-block calls
- block-form after a non-block travel (cleanup restores the outer freeze, as above)

The confusing case in the error is relative times:

```ruby
travel_to 2.days.from_now do
  travel_to 3.days.from_now do
    # 5 days from real now — inner 3.days.from_now is evaluated against already-stubbed time
  end
end
```

Cleanup would also be wrong if nesting were allowed: the inner `ensure` would `travel_back` or `travel_to stubbed_time` and then set `in_block = false` while the outer block was still running.
