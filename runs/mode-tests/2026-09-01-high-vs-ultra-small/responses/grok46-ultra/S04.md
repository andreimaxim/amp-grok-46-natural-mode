# `content_for` for layout debugging

`content_for` parks named chunks on the view’s `@view_flow` so a layout (or another template/helper) can read them later. Storage is `ActionView::OutputFlow`: a Hash whose missing-key default is a fresh `ActiveSupport::SafeBuffer`. Layout `yield :name` does not call `content_for`; it goes through `ActionView::Context#_layout_for`, which is `view_flow.get(name).html_safe`.

```text
template/helper
  content_for(name, content = nil, options = {}, &block)
    write?  content || block_given?
      block → options = content if content; content = capture(&block)
      if content
        flush ? @view_flow.set(name, content)
              : @view_flow.append(name, content)
      return nil
    read
      @view_flow.get(name).presence
```

## Write vs read

Dispatch is the `content || block_given?` test in [`capture_helper.rb`](file:///home/user/workspace/repo/actionview/lib/action_view/helpers/capture_helper.rb).

- Write: second argument is truthy, or a block is given. Always returns `nil`.
- Read: `content_for(:title)` with no block and no content. Returns `@view_flow.get(name).presence`, so a missing or blank slot is `nil`.

Because `nil`/`false` are falsy, `content_for(:title, nil)` and `content_for(:title, false)` are reads, not writes. The block form `content_for :title, nil, flush: true do ... end` still writes: `block_given?` is true, and `options = content if content` does not clobber the options hash.

## Block capture vs direct content

**Direct:** `content_for :title, "foo"` (or a symbol, which later becomes `"foo"` via `to_s`). The value is stored as-is. `capture` is not used.

**Block:** if the second argument is present it is treated as `options`, then `content = capture(&block)`. That is why `content_for :title, flush: true do ... end` works.

`CaptureHelper#capture` does not swap the `OutputBuffer` object. It calls `OutputBuffer#capture`, which temporarily replaces `@raw_buffer` with a new string, yields, then returns that string as `html_safe`. After the yield:

```ruby
string = if @output_buffer.equal?(value)
  buffer
else
  buffer.presence || value
end
```

- Markup written with `<<` / ERB concatenation is taken from the temporary buffer.
- If that buffer is blank (`presence` is nil), the block’s return value is used instead. A whitespace-only ERB body that returns `nil` therefore stores nothing (`if content` fails). Tests in [`capture_helper_test.rb`](file:///home/user/workspace/repo/actionview/test/template/capture_helper_test.rb) cover this: `output_buffer << "  \n  "; nil` does not change the slot.
- Non-strings (`capture { 1 }`) become `nil` and are not stored.
- The chosen string is then:
  - `OutputBuffer` → `to_s` (already `html_safe`)
  - `SafeBuffer` → passed through (no second escape)
  - plain `String` → `ERB::Util.html_escape`

So a block that returns `"<em>bar</em>"` stores the escaped form; a block that returns `content_tag(:p, "title")` or `raw(...)` stores trusted HTML.

## Append order

Default write is `@view_flow.append(name, content)` → `@content[key] << value.to_s`.

Repeated writes concatenate in call order. `content_for :title, "foo"` then `content_for :title, :bar` reads as `"foobar"`. The same holds for mixed direct/block writes, and for `flush: false`.

`append` is a no-op for the slot when `content` is falsy after capture. Whitespace-only blocks that return `nil` do not insert spaces between neighboring writes (`"foo"` + whitespace block + `"bar"` → `"foobar"`).

## `flush: true`

`options[:flush]` chooses `set` instead of `append`:

```ruby
def set(key, value)
  @content[key] = ActiveSupport::SafeBuffer.new(value.to_s)
end
```

That replaces the entire slot. Later writes without `flush` append onto the new buffer. `flush: true` with a whitespace-only nil-returning block does not call `set` (`if content` is false), so the previous value remains until a later truthy write with `flush: true` replaces it — see `test_content_for_with_whitespace_block_and_flush`.

`content_for :title, "", flush: true` does replace: `""` is truthy. The slot becomes an empty `SafeBuffer`. A following block write then appends onto that empty buffer. `test_content_for_should_be_html_safe_after_flush_empty` is about that path still being `html_safe?`.

## Write vs read returns

| Call | Return |
|---|---|
| Write (direct, block, flush or not) | always `nil` |
| Read, slot missing or blank | `nil` |
| Read, slot present | the `SafeBuffer` (truthy string) |

Use `<% content_for :title do ... end %>` in templates. `<%= content_for :title do ... end %>` prints nothing on write, which is deliberate so the captured markup does not also leak into the current buffer.

`<%= content_for :title %>` is the read. `yield :title` is the same named slot via `_layout_for`, except `_layout_for` always returns `get(name).html_safe` (empty string if never written), while `content_for(:title)` uses `.presence` and returns `nil` when blank.

## `content_for?`

```ruby
def content_for?(name)
  @view_flow.get(name).present?
end
```

True only when the stored buffer is non-blank. Independent names do not affect each other. `get` uses a Hash default proc that **assigns** an empty `SafeBuffer` for a missing key, so a probe still returns false (`present?` is false) but the key now exists in `@content`.

## Safety relative to the view buffer

Named content lives in `OutputFlow` as `SafeBuffer`s, not in `@output_buffer`. Capture isolates writes: the main template buffer is restored after the block, so `<% content_for :x do %>...<% end %>` does not leak into the body.

When the layout later does `<%= content_for :title %>` or `<%= yield :title %>`, the value is already a `SafeBuffer`, so the view buffer’s `<<` will not escape it again.

How it became safe depends on the write path:

- **Block:** `capture` already escaped plain strings or preserved `SafeBuffer`/`OutputBuffer` output. `append`/`set` then store that result.
- **Direct + `append` (default):** `SafeBuffer#<<` runs `implicit_html_escape_interpolated_argument`. A plain `"<p>title</p>"` is escaped; `raw("<p>title</p>")` is not. That is why `provide :title, "<p>title</p>"` (same `append`) yields `hi&lt;p&gt;title&lt;/p&gt;` in the helper tests.
- **Direct + `set` (`flush: true`):** `SafeBuffer.new(value.to_s)` copies bytes and marks the copy html-safe. There is no extra escape pass on that path.

`OutputBuffer#<<` and `SafeBuffer#<<` both skip another escape when the incoming value is already `html_safe?`. That is why captured helper output (`content_tag`, `javascript_include_tag`, etc.) survives a round-trip into the layout without being entity-encoded, and why a second `capture` of `raw("&lt;em&gt;...")` does not double-escape.

`provide` is the streaming cousin: it also `capture`s a block, but calls `append!`. On `StreamingFlow`, `append!` resumes the layout fiber; `content_for`’s `append` does not. For non-streaming `OutputFlow`, `append!` is just `append`.
