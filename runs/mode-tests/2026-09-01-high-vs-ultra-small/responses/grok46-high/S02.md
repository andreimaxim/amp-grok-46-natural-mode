**Do not take this simplification.** It is not equivalent. It drops the documented compatibility hook and changes merge vs replace.

`deep_merge!` currently does:

```ruby
if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
  this_val.deep_merge(other_val, &block)
elsif block_given?
  block.call(key, this_val, other_val)
else
  other_val
end
```

The left-hand nested value owns whether recursion happens. Default `deep_merge?` is `other.is_a?(self.class)`. Hash and Parameters override it, and the tests treat that as public behavior.

Replacing the hook with `other_val.is_a?(DeepMergeable)` breaks four things:

**Custom `DeepMergeable` classes.** `OtherWrapper = Wrapper.dup` includes the module independently, so both sides pass `is_a?(DeepMergeable)`. Today `Wrapper#deep_merge?` is still false, so the nested value is replaced (`deep_merge does not deep merge non-subclass values by default`). After this diff that test fails: the nested `OtherWrapper` is recursed into and the result is a `Wrapper`. The override test (`deep_merge? can be overridden to allow deep merging of non-subclass values`) would keep passing only by coincidence — `OmniWrapper#deep_merge?` would never be called. You also could no longer restrict the domain.

**Compatibility ownership.** Hash and Parameters already disagree on purpose:

- `Hash#deep_merge?` → `other.is_a?(Hash)`
- `Parameters#deep_merge?` → `other.is_a?(DeepMergeable)`
- default → `other.is_a?(self.class)`

The proposed check uses Parameters’ wider rule for everyone. Nested `Hash` + `Parameters` currently replaces. After the change, `Hash#deep_merge` is invoked with Parameters; `merge!` coerces via `to_hash`, and unpermitted Parameters raise `UnfilteredParameters`.

**Block fallback.** The block is the fallback when deep merge does *not* apply — including two `DeepMergeable` values that `deep_merge?` rejects. Today `Wrapper` + `OtherWrapper` with a block calls the block with those two objects. After this diff it recurses and the block is only used at leaves.

**Mutation / return.** Recursion still goes through `this_val.deep_merge` (dup, then `deep_merge!`), so nested values still are not mutated in place and `deep_merge!` still returns `self`. The observable change is *which* nested values recurse: replace keeps `other_val`; recurse returns `this_val.dup` merged (new object, left-hand class).

Keep `this_val.deep_merge?(other_val)`. The extra `is_a?(DeepMergeable)` on `this_val` is the cheap guard so we do not call `deep_merge?` on non-participants; the predicate decides merge vs replace vs block.
