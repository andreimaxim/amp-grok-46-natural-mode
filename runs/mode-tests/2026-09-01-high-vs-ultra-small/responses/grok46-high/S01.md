`travel_to` freezes “now” for the rest of a test (or for a block) by stubbing four class methods on `Time`, `Date`, and `DateTime`. It lives in [`activesupport/lib/active_support/testing/time_helpers.rb`](activesupport/lib/active_support/testing/time_helpers.rb). `travel` and `freeze_time` both call it. Non-block stubs are also cleared in `after_teardown` via `travel_back`.

## What a test author actually gets

After `travel_to(target)`:

- `Time.now` / `Time.new` with no arguments return the frozen instant in the **system** timezone
- `Date.today` returns that instant’s calendar date
- `DateTime.now` returns that instant as a `DateTime`
- `Time.current` / `Date.current` still go through `Time.zone` if one is set, so they honor the **application** timezone of the same instant
- `Time.new(2004, 11, 25)`, `Time.new(precision: 3)`, and any other `Time.new` with args/kwargs are **not** frozen; they call real Ruby `Time.new`

The stubs do not tick. Unlike a real clock, `sleep` does not advance them.

```text
travel_to(date_or_time, with_usec: false)
  reject nested block-form if in_block
  normalize input → Time-like `now`
  now = now.change(usec: 0) unless with_usec
  now = now.getlocal
  capture previous Time.now if Time.now already stubbed
  stub Time.now, Time.new, Date.today, DateTime.now
  if block
    in_block = true
    yield
    restore previous stubbed time OR travel_back
    in_block = false
```

## Input normalization (Date / String / Time)

Normalization happens **before** usec stripping and **before** `getlocal`. `DateTime` is a `Date` subclass, so the Date branch is `is_a?(Date) && !is_a?(DateTime)`.

**Date** (plain `Date`, not `DateTime`):

```ruby
now = date_or_time.midnight.to_time
```

`Date#midnight` is `beginning_of_day`, which is `in_time_zone` — midnight in the **application** time zone (`Time.zone`). Then `#to_time` turns that `ActiveSupport::TimeWithZone` into a `Time`. Docs match this: a Date is “the timestamp at the beginning of the day in the application time zone.” `Time.current` will show that midnight; `Time.now` will show the equivalent system-local time, which can fall on the previous/next calendar day if the zones disagree.

**String**:

```ruby
now = Time.zone.parse(date_or_time)
```

Parsed in `Time.zone` (application TZ). Fractional seconds in the string survive parse, then the later usec step may zero them. Tests cover `"2004-11-24 01:04:44"` and `"2004-11-24T01:04:44.123-05:00"`. There is no `Time.zone` fallback in this method; a missing zone would raise on `Time.zone.parse`.

**Everything else** (Time, DateTime, TimeWithZone, other `#to_time` objects):

```ruby
now = date_or_time
now = now.to_time unless now.is_a?(Time)
```

- A real `Time` is kept as-is (`Time#to_time` is identity, but it is skipped because `is_a?(Time)`).
- `ActiveSupport::TimeWithZone` also reports `is_a?(Time)` (`TimeWithZone#is_a?` special-cases `Time`), so it is **not** converted with `#to_time` here. It then goes through `#change` and `#getlocal` as a TimeWithZone.
- `DateTime` is not a `Time`, so it becomes `DateTime#to_time` → `getlocal(utc_offset)`, preserving the offset.

After that:

```ruby
now = now.change(usec: 0) unless with_usec
now = now.getlocal
```

`getlocal` is required because the stubs below use `Time.at(now)` and `now.to_date`, which follow `now`’s timezone. The comment in the method is explicit: `now` must be in the local system timezone.

Practical consequence from `test_time_helper_travel_to_with_different_system_and_application_time_zones`: traveling to `Time.new(2023, 12, 1, 5, 6, 7, +5h)` with system TZ US/Eastern yields `Time.now` / `Date.today` / `DateTime.now` at **2023-11-30 19:06:07 -05:00**, not the +05 wall time.

## What is stubbed

`SimpleStubs` rewrites singleton methods on the class objects. If a method is already stubbed, it unstubs first so the saved “original” is always the real implementation, not a previous stub.

| Call | Stub body | Effect |
|---|---|---|
| `Time.now` | `{ at(now) }` | `Time.at(now)` → frozen system-local `Time` |
| `Time.new` | see next section | no-arg only is frozen |
| `Date.today` | `{ jd(now.to_date.jd) }` | `Date` from that local calendar day |
| `DateTime.now` | `{ jd(now.to_date.jd, now.hour, now.min, now.sec + now.subsec, Rational(now.utc_offset, 86400)) }` | `DateTime` with the same civil time, subsec, and offset |

Not stubbed: `Time.current`, `Date.current`, `Time.zone.now`, `Time.utc`, `Time.local`, `DateTime.current`. Those still work, but they read the stubbed `Time.now` / `Date.today` underneath when that is how they are implemented (`Time.current` is `Time.zone.now` if a zone is set, else `Time.now`).

Subclasses (`TimeSubclass.now`, `DateSubclass.today`) keep their class; they inherit the stubbed class methods and still construct subclass instances. Tests assert class identity is preserved.

## `Time.new` with arguments

```ruby
stubs.stub_object(Time, :new) do |*args, **options|
  if args.empty? && options.empty?
    at(now)
  else
    stub = stubs.stubbing(Time, :new)
    Time.send(stub.original_method, *args, **options)
  end
end
```

- `Time.new` / `Time.new()` → frozen time (`Time.at(now)`), same as `Time.now`
- **Any** positional arg or keyword (`Time.new(2021)`, `Time.new(2004, 11, 25)`, `Time.new(precision: 3)`, `Time.new("2000-12-31 23:59:59.56789", precision: 3)`) → original Ruby `Time.new`

`precision:` alone is enough to bypass the freeze. That is why tests assert `Time.new(precision: 3)` is not the traveled time even inside `travel_to`. Construction of real timestamps during a freeze still works.

## `with_usec`

Default `with_usec: false` runs `now.change(usec: 0)` after normalization. Comment and tests say this avoids MySQL-style rounding of usec ≥ 500000 into the next second.

Effects:

- `travel_to Time.new(2004, 11, 24, 1, 4, 44) + 0.1` → `Time.now` is exactly `2004-11-24 01:04:44` with usec 0
- `travel_to Time.utc(2014, 10, 10, 10, 10, 50, 999999)` → `Time.now.sec == 50`, `Time.now.usec == 0`, and the same for `DateTime.now`
- String/DateTime inputs with fractional seconds are also zeroed after parse/`to_time`

`with_usec: true` skips `change(usec: 0)`. Subseconds are kept through `Time.now` and through `DateTime.now` (`now.sec + now.subsec` in the `DateTime.jd` call). Tests assert `DateTime.now.usec == 999999` and `sec_fraction == Rational(999999, 1000000)` when traveling to that UTC time with `with_usec: true`.

`travel` and `freeze_time` forward `with_usec`.

## Block cleanup: real time vs pre-existing non-block travel

Before installing stubs, `travel_to` snapshots:

```ruby
stubbed_time = Time.now if stubs.stubbing(Time, :now)
```

That is `true` only if **this** helper instance already stubbed `Time.now` (typically a previous **non-block** `travel_to` / `travel` / `freeze_time`).

If a block is given:

```ruby
begin
  self.in_block = true
  yield
ensure
  if stubbed_time
    travel_to stubbed_time
  else
    travel_back
  end
  self.in_block = false
end
```

Two restore paths:

1. **No prior stub** (`stubbed_time` nil): `travel_back` → `simple_stubs.unstub_all!`. Real `Time.now` / `Date.today` / `DateTime.now` / `Time.new` return. This is the usual `travel_to(t) { ... }` case.

2. **Prior non-block travel** (`stubbed_time` is that frozen `Time.now`): after the inner block, `travel_to stubbed_time` re-installs stubs at the **outer** frozen instant. Test: `test_time_helper_travel_with_subsequent_block` — `travel_to outer`; then `travel_to(inner) { ... }`; after the block `Time.now` is `outer` again, not real time.

`ensure` runs on exception too, so a failing assertion inside the block still restores.

`in_block` is per helper instance (`attr_accessor` on the test case). A different object that includes `TimeHelpers` has its own stubs and its own `in_block`. That is why `TravelClass#travel_to_block` inside a test’s `travel_to` block does not raise, and why its `travel_back` restores the **test’s** outer stub (it unstubs only its own SimpleStubs layer, which had aliased over the outer stub).

Non-block `travel_to` with no surrounding block leaves stubs in place until `travel_back` or `after_teardown`. Subsequent non-block `travel_to` calls just replace the stubs (`SimpleStubs` unstubs first). Nested non-block `travel_to` **inside** a block is allowed and overwrites “now” for the rest of that block; the outer block’s ensure still restores using the **pre-block** snapshot, not the inner destination (`test_time_helper_travel_to_with_nested_calls`).

## Why nested block-form `travel_to` is rejected

Guard at the top:

```ruby
if block_given? && in_block
  raise ...
end
```

`in_block` is set only while already inside a `travel_to` **block** on the same helper. A second `travel_to(...) do` therefore raises `RuntimeError` whose message starts with:

> Calling `travel_to` with a block, when we have previously already made a call to `travel_to`, can lead to confusing time stubbing.

The raise happens **before** any new stubs. The outer freeze stays in effect.

Why it would be confusing (the comment’s example):

```ruby
travel_to 2.days.from_now do
  travel_to 3.days.from_now do
    # people read this as “5 days from today”
  end
end
```

`travel_to` is **absolute**, not relative. The inner call would freeze to `3.days.from_now` evaluated **under the already frozen clock** (so ~5 days from real today), then its ensure would `travel_to stubbed_time` back to the outer freeze, then the outer ensure would `travel_back` to real time. Two overlapping ensure paths plus absolute-vs-relative reading is the failure mode they refuse.

Allowed combinations:

- Nested **non-block** `travel_to` inside a block (overwrites until outer ensure)
- Block-form `travel_to` after a **non-block** `travel_to` (`in_block` is still false; restore goes back to the non-block freeze)
- Sequential sibling blocks, or `travel 2.days` / `travel 5.days` as the error message suggests

Not allowed: block inside block on the same helper instance.
