**Review: reject appending before the `strict:` check.**

`ActiveModel::Errors#add` already builds the `ActiveModel::Error`, then raises when `options[:strict]` is set, and only then appends. That order is the contract, not an accident.

**Strict contract.** The method docs say `strict: true` raises `ActiveModel::StrictValidationFailed` *instead of adding the error*, and any other truthy value is used as the exception class. The example then shows `person.errors.messages # => {}`. `validates` / `validates!` repeat the same “raise instead of adding” wording. Appending first would contradict that documented behavior.

**Exception class and message.** `strict: true` is rewritten to `ActiveModel::StrictValidationFailed`; any other truthy value is raised as-is. Both paths use `raise exception, error.full_message`. Tests match that: `test_strict_validation_error_message` asserts `"Title can't be blank"`, and `test_strict_validation_custom_exception` asserts `CustomStrictValidationException`.

**Collection mutation.** A rescued strict `add` must leave `@errors` unchanged. That is what the docs show (`messages => {}`) and what “instead of adding” requires. Mutating the collection before raise would leave a recorded error after an exceptional failure, which callers of `valid?` / `validate!` do not expect.

**Normal `add` return.** Non-strict `add` appends and returns the `ActiveModel::Error` (`test "add creates an error object and returns it"`). Strict `add` never returns; it raises. Callers already get the object from a successful `add`. They do not need a post-rescue collection side effect.

**Custom strict exception classes.** Custom classes receive the message string, not the error object (`raise exception, error.full_message`). Inspecting `@errors` after rescue is therefore not a supported way to recover the `ActiveModel::Error`, and it still would not attach that object to a user-supplied exception. If someone needs the error after rescue, the exception API would have to carry it — mutating the collection does not.

Recommend keeping the current order: build → maybe raise → append → return.
