**Normal `add` return.** Non-strict `add` returns the `Error` (`test "add creates an error object and returns it"`). Strict `add` never returns: `raise` unwinds before `error`. Appending first does not change that. Rescue still cannot use the return value; the only new handle would be `errors.objects.last`, which is the collection break above.

**Custom strict exception classes.** `strict: SomeException` is already supported (`test_strict_validation_custom_exception`, docs with `NameIsInvalid` / `TokenLengthException`). Those classes also do not carry an `ActiveModel::Error`. Custom-exception callers are using control-flow abort, not “record then raise.” Recording into `errors` would surprise them the same way, without making the rescued exception any richer.

Keep the raise-before-append order. If someone needs the `Error` after rescue, that is a new API on the exception, not a silent mutation of the collection.
