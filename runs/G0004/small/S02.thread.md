**Reject this.** `deep_merge?` is the compatibility hook; replacing it with `other_val.is_a?(DeepMergeable)` hardcodes `Parameters` policy for every includer.

`deep_merge!` only recurses when the receiver value opts in:

```39:48:activesupport/lib/active_support/deep_mergeable.rb
    def deep_merge!(other, &block)
      merge!(other) do |key, this_val, other_val|
        if this_val.is_a?(DeepMergeable) && this_val.deep_merge?(other_val)
          this_val.deep_merge(other_val, &block)
        elsif block_given?
          block.call(key, this_val, other_val)
        else
          other_val
        end
      end
    end
```

`deep_merge?` is documented as the place classes restrict or expand that domain, defaulting to `other.is_a?(self.class)`. Rails already uses both directions:

- `Hash#deep_merge?` keeps the Hash family (`Hash` / `HashWithIndifferentAccess`) and **rejects** other `DeepMergeable` objects such as `Parameters`.
- `Parameters#deep_merge?` **widens** to any `DeepMergeable`, which is why params can recurse into hashes.
- Custom classes get the narrow default; `OmniWrapper` in the tests overrides it to opt in.

`other_val.is_a?(DeepMergeable)` is exactly the `Parameters` override. After this, `Hash#deep_merge?`, `Parameters#deep_merge?`, the default, and app overrides are never consulted.

That fails the existing custom-class contract in [activesupport/test/deep_mergeable_test.rb](file:///home/user/workspace/repo/activesupport/test/deep_mergeable_test.rb):

- `Wrapper` + `SubWrapper` still recurse (`is_a?(self.class)`).
- `Wrapper` + `OtherWrapper` currently **do not** (`OtherWrapper = Wrapper.dup` is not a subclass). Both include `DeepMergeable`, so the patch would recurse instead of replacing.
- `OmniWrapper` would keep passing by accident, which hides that the override is now dead.

Block fallback moves with that gate. Incompatible `DeepMergeable` pairs today take `block.call(key, this_val, other_val)` or else `other_val`. After the patch those pairs never reach the block; the block only sees non-`DeepMergeable` leaves. A `Wrapper`/`OtherWrapper` merge with `&@sum_values` would stop being a conflict-resolution call.

Observable result also changes on the reject path. Recursion uses non-bang `this_val.deep_merge`, which is `dup.deep_merge!`, so you get a new object of **the receiver’s** class. The current reject path returns `other_val` as-is (same class, same object). For `Wrapper` vs `OtherWrapper` the nested value would become a `Wrapper` instead of `OtherWrapper`. For `Hash` vs nested `Parameters`, `Hash#merge!` would try `Parameters#to_hash` (raises if unpermitted) instead of replacement.

Leave the `deep_merge?` call. If Hash/`Parameters` duplication is the itch, that already belongs in their overrides, not in the generic mixin.
