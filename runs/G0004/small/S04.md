`content_for` is a write/read pair over `@view_flow`, not over `@output_buffer`. A write captures or accepts a string, then `append`s or `set`s it on the named slot. A read returns that slot. The current template buffer is only borrowed during block capture, then restored.

```text
content_for(name, content = nil, options = {}, &block)
  content || block? ──yes──▶ write
    block? ──yes──▶ options = content if content
                     content = capture(&block)
    content truthy? ──yes──▶ flush? set : append
    return nil
  ──no──▶ read: view_flow.get(name).presence
```

## Write vs read

The branch is `if content || block_given?`. Any truthy second argument or a block is a write. Only `content_for(:name)` with neither is a read.

Write always returns `nil`, including `flush: true` and including a block whose capture is blank. That is why templates use `<% content_for ... %>` / `<% content_for ... do %>`. `<%= %>` on a write prints nothing; the markup is not left in the current buffer.

Read returns `@view_flow.get(name).presence`, so a missing or blank slot is `nil`. Layout `yield :name` is different: [`_layout_for`](file:///home/user/workspace/repo/actionview/lib/action_view/context.rb#L27-L30) does `view_flow.get(name).html_safe` and will give you an empty safe string, not `nil`.

## Block capture vs direct content

**Direct:** `content_for :title, "foo"`. The second argument is stored as-is (`to_s` at the flow). No `capture`, no trip through `@output_buffer`.

**Block:** `content_for :title do ... end`. If a second argument is present, it is treated as `options`, not as content (`options = content if content`). Then:

```ruby
content = capture(&block)
```

[`capture`](file:///home/user/workspace/repo/actionview/lib/action_view/helpers/capture_helper.rb#L47-L66) does not swap the `OutputBuffer` object. [`OutputBuffer#capture`](file:///home/user/workspace/repo/actionview/lib/action_view/buffers.rb#L72-L78) swaps `@raw_buffer` for a new string, yields, marks that string `html_safe`, and restores the previous raw buffer in `ensure`. Same buffer object, original contents intact.

What `capture` then keeps:

1. If the block returns the output buffer object itself (`@output_buffer.equal?(value)`), use the captured substring — not the whole view buffer.
2. Otherwise `buffer.presence || value`. A whitespace-only buffer is blank, so it is discarded and the return value is used. That is why a block that only writes `"  \n  "` and returns `nil` does not append.
3. Result typing:
   - `OutputBuffer` → `to_s` (already safe)
   - `SafeBuffer` → kept
   - other `String` → `ERB::Util.html_escape`
   - non-string (e.g. `1`) → `nil`, and the write is skipped (`if content`)

ERB `<% content_for :title do %>…<% end %>` almost always hits path 1/2 via buffer writes. Builder / a Ruby block that returns a string hits path 3.

## Append order and `flush: true`

Store is [`ActionView::OutputFlow`](file:///home/user/workspace/repo/actionview/lib/action_view/flows.rb#L6-L28):

```ruby
@content = Hash.new { |h, k| h[k] = ActiveSupport::SafeBuffer.new }

def set(key, value)
  @content[key] = ActiveSupport::SafeBuffer.new(value.to_s)
end

def append(key, value)
  @content[key] << value.to_s
end
```

Default write is `append`. Repeated writes concatenate in call order: `"foo"` then `:bar` → `"foobar"`.

`flush: true` is `set`: replace the slot, previous chunks gone. `flush: false` is append. A flush write whose captured/direct `content` is falsy does **not** replace — the `if content` guard skips the store. That is the whitespace-block-plus-flush case: `"foo"`, then a blank flush block, then `"bar"` with flush → `"bar"`. The blank flush was a no-op.

`get` uses the Hash default proc, so a read or `content_for?` on a never-written name inserts an empty `SafeBuffer`. The slot exists; it is just blank.

## `content_for?`

```ruby
def content_for?(name)
  @view_flow.get(name).present?
end
```

True only if the slot is non-blank. Empty string, whitespace-only stored content, and a never-written name are all false. It does not distinguish “never written” from “written then flushed to empty.”

## Safety vs the view buffer

Captured output is kept off the current template buffer, then marked so a later `<%= content_for :name %>` / `<%= yield :name %>` will not escape it again.

```diagram
┌─────────────┐  block   ┌──────────────────┐  append/set  ┌────────────┐
│ @output_    │─────────▶│ capture → safe   │─────────────▶│ @view_flow │
│ buffer      │ restore  │ string           │              │ [name]     │
└──────▲──────┘          └──────────────────┘              └─────┬──────┘
       │   layout <%= yield :name %> / content_for(:name)        │
       └──────────── html_safe concat, no second escape ─────────┘
```

Three layers:

1. **During capture.** `OutputBuffer#<<` escapes anything not `html_safe?` before it lands in the temporary raw string. `capture` then returns that as a `SafeBuffer`, or `html_escape`s a plain string return. The original `@raw_buffer` is restored, so the block never leaks into the view body.
2. **At the flow.** `append` is `SafeBuffer#<<`, which escapes a non-safe `value.to_s`. `set` (`flush: true`) wraps `value.to_s` in a new `SafeBuffer`, which is `html_safe` by construction. Direct unsafe strings are escaped on append; on flush they are wrapped, not escaped.
3. **When the layout concatenates.** The stored value is a `SafeBuffer`. The layout’s `OutputBuffer#<<` sees `html_safe?` and concatenates raw. `content_tag` / other already-safe chunks stay tags; they are not turned into `&lt;p&gt;`. Flushing to `""` then appending a `content_tag` still yields an `html_safe?` slot — that is the invariant [`test_content_for_should_be_html_safe_after_flush_empty`](file:///home/user/workspace/repo/actionview/test/template/capture_helper_test.rb#L168-L178) locks.

Debugging layout slots: if the name never shows up, check write-vs-read (`<%= content_for :x %>` in the view is a read, not a write), check that the block actually produced a truthy `capture` (whitespace + `nil` is dropped), and check `flush: true` on a later write. If markup is escaped twice or not at all, check whether the write was append vs `set`, and whether the value was already a `SafeBuffer` when it hit the flow.
