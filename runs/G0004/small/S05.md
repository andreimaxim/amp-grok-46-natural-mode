**Reject this reorder.** Strict `add` is documented and implemented as raise-instead-of-record, not record-then-raise. Appending first would not give callers a useful return value, and it would break the collection and `valid?` contract after rescue.

Current [`add`](file:///home/user/workspace/repo/activemodel/lib/active_model/errors.rb#L341-L353):

```341:353:activemodel/lib/active_model/errors.rb

      attribute, type, options = normalize_arguments(attribute, type, **options)
      error = Error.new(@base, attribute, type, **options)

      if exception = options[:strict]
        exception = ActiveModel::StrictValidationFailed if exception == true
        raise exception, error.full_message
      end

      @errors.append(error)

      error
    end
```

I ran that path on this checkout. `add(:name, :invalid, strict: true)` raises `ActiveModel::StrictValidationFailed` with `"Name is invalid"`, leaves `errors.size == 0` / `messages == {}`, and never returns. `strict: NameIsInvalid` raises that class with the same message and still does not append. Non-strict `add` returns the `ActiveModel::Error` and that object is `errors.objects.first`.

**Strict contract.** The docs are explicit: `:strict` raises **instead of adding** the error, and after the example `person.errors.messages # => {}`. Same wording on `validates` / `validates!` and on [`StrictValidationFailed`](file:///home/user/workspace/repo/activemodel/lib/active_model/errors.rb#L507-L525). Appending before `raise` turns “abort without recording” into “record and abort.” After rescue, `empty?`, `messages`, `added?`, and a later `valid?` would all see a failure that today’s API treats as never recorded. [`test_strict_validation_*`](file:///home/user/workspace/repo/activemodel/test/cases/validations_test.rb#L396-L448) only assert the exception class/message; they do not lock the empty collection, but the documented example does.

**Exception class and message.** Reordering does not change what is raised. `true` still becomes `ActiveModel::StrictValidationFailed`; any other truthy value is raised as-is. The message is `error.full_message` (`"Name is invalid"`, `"Title can't be blank"` in `test_strict_validation_error_message`). `StrictValidationFailed` is a bare `StandardError` — it does not wrap the `Error` object — so rescuing still does not yield that object.

**Collection mutation.** That is the actual behavior change, and it is the wrong one. The `Error` is already built before the strict check; it is intentionally not appended. A rescued strict `add` on a collection that already has errors would grow it (today a later strict add leaves the previous errors untouched). Callers that rescue and keep using the model would see a poisoned `errors` object. If the goal is “inspect after rescue,” put the `Error` on the exception; do not mutate `@errors` on a path whose contract is not to add.

**Normal `add` return.** Non-strict `add` returns the `Error` (`test "add creates an error object and returns it"`). Strict `add` never returns: `raise` unwinds before `error`. Appending first does not change that. Rescue still cannot use the return value; the only new handle would be `errors.objects.last`, which is the collection break above.

**Custom strict exception classes.** `strict: SomeException` is already supported (`test_strict_validation_custom_exception`, docs with `NameIsInvalid` / `TokenLengthException`). Those classes also do not carry an `ActiveModel::Error`. Custom-exception callers are using control-flow abort, not “record then raise.” Recording into `errors` would surprise them the same way, without making the rescued exception any richer.

Keep the raise-before-append order. If someone needs the `Error` after rescue, that is a new API on the exception, not a silent mutation of the collection.
