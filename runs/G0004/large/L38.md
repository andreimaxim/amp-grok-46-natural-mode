## Current contract

Three objects, two moments:

```text
status bang (delivered! / bounced! / failed!)
  InboundEmail#save
    after_update_commit :incinerate_later
      if ActionMailbox.incinerate && status_previously_changed? && processed?
        IncinerationJob.schedule(self)
          set(wait: ActionMailbox.incinerate_after).perform_later(self)

later, IncinerationJob#perform
  inbound_email.incinerate
    Incineration.new(self).run
      destroy! if due? && processed?
```

`processed?` is not a status. It is `delivered? || failed? || bounced?` ([`inbound_email.rb`](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email.rb#L31-L43)). `pending` and `processing` are unprocessed.

Scheduling is an **update-commit** side effect ([`incineratable.rb`](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable.rb#L9-L18)). Destruction is a **later re-check**, not “the job exists, therefore delete” ([`incineration.rb`](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable/incineration.rb#L13-L24)).

`wait:` and `due?` are different predicates. That difference is the contract, not a bug to “fix” while preserving behavior.

**I7. `due?` is `updated_at < ActionMailbox.incinerate_after.ago.end_of_day` (strict `<`).**  
Source: [`incineration.rb` L18–L19](file:///home/user/workspace/repo/actionmailbox/app/models/action_mailbox/inbound_email/incineratable/incineration.rb#L18-L19). No unit test pins this formula; existing tests only `travel 30.days` then destroy ([`incineration_test.rb` L12–L17](file:///home/user/workspace/repo/actionmailbox/test/unit/inbound_email/incineration_test.rb#L12-L17)).  
Probe under UTC `freeze_time` at `2026-09-02 21:45:51`:

- T+0: `due?` false, row remains  
- T+29d: threshold `2026-09-01 23:59:59.999999999`, still not due, row remains  
- T+30d (the `wait:` instant): `30.days.ago == updated_at`, but `30.days.ago.end_of_day` is that calendar day’s 23:59:59.999999999, so `due?` is **true** and the row is destroyed  
- `updated_at` 1s after that `end_of_day`: not due, row remains  

So at the scheduled run time, incineration succeeds because of `end_of_day`, not because `updated_at < incinerate_after.ago`. Replacing `due?` with “job ran” or with a strict duration compare would change T+30d behavior.

`end_of_day` follows `Time.zone` (dummy is UTC). Zone is part of the observed predicate; do not treat UTC-only timestamps as the whole contract.

### Incidentals (do not pin)

- Nested class name `InboundEmail::Incineratable::Incineration` vs an instance method.  
- `after_update_commit` vs an equivalent after-commit hook, as long as rolled-back updates do not enqueue.  
- Job / command file layout.  
- Comment text (the Incineration comment’s “processed after the incinerate_after time” does not match the code).  
- `destroy!` vs `destroy` if failures are still surfaced; `destroy!` is only required insofar as a failed destroy must not look like success.  
- Active Job payload fields (`job_id`, locale, timezone).  
- Dummy-app queue name `"default"` as a hardcoded string (pin “nil queue → default_queue_name”).  
- Sibling jobs (`ActiveStorage::SyncMetadataJob`) enqueued on create.  
- DB timestamp rounding vs `end_of_day` nanoseconds. Do not assert `updated_at == end_of_day` after `update_column`; assert the `<` predicate on values you control.  
- `freeze_time` making a later `update!` keep the same `updated_at` (clock artifact).

## What a safe refactor may change

Internal split between concern / job / command, as long as:

- enqueue policy stays the `after_update_commit` predicate (I2–I5, I11)  
- destroy policy stays `due? && processed?` with the `updated_at` / `ago` / `end_of_day` formula (I6–I8, I10)  
- missing records stay discarded (I9)  
- `incinerate = false` still means “do not auto-schedule,” not “do not destroy” (I3)

A change that unifies `wait:` with `due?`, schedules on create, skips `delivered → failed` re-enqueue, or destroys unprocessed/not-due rows is a behavior change, not preservation.

I did not add these tests to the tree; this is the preservation strategy for a later refactor. Existing incineration tests remain green on this revision.
