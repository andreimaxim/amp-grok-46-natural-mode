### Chainability

`none` is `spawn.none!`. `spawn` clones unless a named-scope `_exec_scope` is already on the stack, in which case it returns `model.all`.


`@none` is an ivar, not a value method. `initialize` sets it `false`. `initialize_copy` dups `@values` and `reset`s loaded state; it does not clear `@none`. Clone therefore keeps the flag. Every ordinary chain (`where`, `joins`, `limit`, `includes`, …) stays a null relation without re-calling `none!`.

That is why `except` / `only` / `unscope` cannot turn it off. They replace `@values` on a spawn, which can drop the `1=0` predicate, but the clone still has `@none == true`. Loading still returns `[]`. `to_sql` may then omit `WHERE (1=0)` while the object remains empty.

Merger is the one place that re-applies the flag from another relation:

`or` is the inverse: a none receiver discards itself.


3. Else eager load: `apply_join_dependency` can still see `null_relation?` after `except(:includes, :eager_load, :preload)` (clone keeps `@none`). That inner check is dead for a none receiver, because step 1 already returned.
4. Else real SQL.

`load` / `records` / Enumerable go through `exec_queries` → `exec_main_query`. `load_async` calls `exec_main_query` directly and treats an Array result as already loaded, so `Developer.none.load_async.load` never hits the adapter.

`1=0` without `@none` does **not** take this exit. It runs `SELECT ... WHERE (1=0)`.

### Calculation and `exists?` / `include?`

`calculate` inspects `@none` before `perform_calculation`:

| op | ungrouped | grouped |
|---|---|---|
| `count`, `sum` | `0` | `{}` |
| `average`, `minimum`, `maximum` | `nil` | `{}` |

Async wraps those in `Promise::Complete`. `pluck` / `ids` return `[]` (or a complete promise). `pick` is `limit(1).pluck`, so it inherits the pluck short-circuit.

`size` has no `@none` check of its own. Unloaded, it is `count(:all)`, which does.

`exists?` returns `false` on `@none` before constructing a relation, before `contradiction?`, before `skip_query_cache_if_necessary`. Extra arguments do not matter: `exists?(1)` is still false with no SQL.

`include?` / `member?`:

- wrong class → `false` (no SQL, no `@none` check)
- loaded, or `offset` / `limit` / `having` → `records.include?` → load short-circuit
- otherwise → `exists?(pk hash)` → `@none` short-circuit

`empty?` / `none?` / `any?` / `one?` / `many?` all return from `@none` before `exists?` or `limited_count`. `none?` / `any?` / `one?` with a block or argument still hit `super` only after that guard, so an empty enumerator never loads.

### `delete_all` / `update_all`

Both return `0` on `@none` before validity checks and before compiling Arel.


Consequences:

- `none.distinct.delete_all` returns `0` instead of raising `delete_all doesn't support distinct`.
- `none.distinct.update_all(...)` returns `0` instead of the 8.2 deprecation.
- `delete(id)` is `where(pk => id).delete_all`, spawn keeps `@none`, so `0`.
- `touch_all` / `update_counters` go through `update_all`, so they are also `0`.

`destroy_all` and `update`/`update!` (instance path) do not check `@none`. They load via `records` / `each`, get `[]`, and issue no writes.

### Query-cache skip state

`skip_query_cache` lives in `@values`. `@none` does not. Spawn keeps both independently.

`skip_query_cache_if_necessary` is `model.uncached` if the value is set, else `yield`. It does not itself talk to the cache.

On a none relation the methods that check `@none` (`exists?`, `calculate`, `pluck`, `delete_all`, `update_all`, `exec_main_query`) return **before** that wrapper. `skip_query_cache!` is a live value with no effect on those paths: no SQL, so nothing to bypass.

`exec_queries` is the exception. It wraps the whole load, including the `@none` empty array:

```1477:1484:activerecord/lib/active_record/relation.rb
        skip_query_cache_if_necessary do
          rows = if scheduled?
            ...
          else
            exec_main_query
          end
```

`relation.none.skip_query_cache!.load` still enters `model.uncached` and then gets `[]` from `exec_main_query`. `load_async` does not take that outer wrap; it calls `exec_main_query` and returns immediately on `@none`.

The contradiction path is the reverse nesting: it sits *inside* `skip_query_cache_if_necessary` in `exec_main_query`, `pluck`, and `execute_simple_calculation`. Same empty result, different place relative to uncached.

Batching always does `relation.skip_query_cache!` on the batch relation. For a none source, `pluck` / `records` still short-circuit, so the flag is set and then unused.

### Operations that can still execute SQL

`#none`’s rdoc (“any subsequent condition… will not fire any query”) is true for spawn-chains that keep `@none` and then hit a short-circuit method. It is not a relation-wide IO barrier.

Still hits the adapter:

- **`or` on a none receiver.** Returns `other.spawn`. The result is a live query.
- **`and` / merge of the `1=0` clause without `none!`.** `@none` stays false. `SELECT`/`UPDATE`/`DELETE` run with `WHERE (1=0)`.
- **`unscoped`.** New relation, no flag.
- **None relation as a subquery value.** `PredicateBuilder::RelationHandler` does `attribute.in(value.arel)`. `Comment.where(post_id: Post.none).count` runs an outer query whose subquery contains `1=0`. The none object is not asked to load.
- **`excluding(Post.none)`.** `excluding` calls `ids` on the argument (short-circuit `[]`), then builds `where.not(id: [])` on the *receiver*. The receiver is not none; that query runs.
- **`cache_version` / `cache_key` when versioning is off.** `compute_cache_version` has no `@none` check. Unloaded, it `select_rows` a `COUNT(*), MAX(timestamp)` with the `1=0` where.
- **Writes that do not go through `update_all`/`delete_all`.** `insert` / `insert_all` / `upsert_all` ignore `@none` and insert. `create` / `create!` / `new` use `scoping` + `where_values_hash`; `"1=0"` does not appear in the hash (`Developer.none.where_values_hash == {}`), so they insert like an unscoped create. `find_or_create_by` short-circuits the find (`nil`) then creates.
- **`explain` on calculations that already short-circuit** still goes through `ExplainProxy`, which runs the method. The method itself issues no SQL; `to_sql` / `exec_explain` can still talk to the connection depending on adapter explain plumbing.

`to_sql` itself does not query, but it compiles Arel with `1=0`, which is how the subquery and cache-key fingerprint paths keep working.

The durable invariant: emptiness for reads is the `@none` flag; `1=0` is only so the same object remains a valid, chainable query tree. Lose the flag, keep the predicate, and the adapter runs. Keep the flag, strip the predicate, and reads still return empty.
