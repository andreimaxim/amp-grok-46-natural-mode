I used the public `insert_all` / `insert_all!` contract, adapter support flags, option validation, and bulk-insert tests as the baseline. This is a first-draft shaping brief, not a final spec.

**Evidence used:** public method docs, adapter “does this database support skip / returning / a named conflict target?” flags, option refusal and defaulting, and the bulk-insert examples. Those show **observable** results only. They do **not** show that every database agrees.

**Working interpretation:** this is a **behavior-change** toward a clearer, adapter-honest contract—not a promise that PostgreSQL, SQLite, MySQL, and MariaDB will do the same thing. Hypothesis: “clearer” means a developer can predict skip vs raise vs refuse vs return values from the adapter they are on, without assuming a single SQL dialect.

# Developers cannot tell what `unique_by:` and `returning:` will do on their database

**Problem frame:** An application developer bulk-inserts rows with `insert_all` (skip conflicts) or `insert_all!` (fail on conflicts) and optionally names a uniqueness target (`unique_by:`) or asks for inserted values back (`returning:`). They need to know, for the database they are on, whether rows are inserted, skipped, or refused; whether existing rows stay unchanged; whether the call fails as one unit; and what comes back. Today that differs by adapter, and the public wording (“unique by every unique index”, “PostgreSQL and SQLite only”, “PostgreSQL, SQLite3, and MariaDB only”) does not match every case they actually hit—especially composite primary keys, a named/composite/expression unique index, MySQL vs MariaDB, and the bang form.

**Who:** Developers using Active Record bulk insert across PostgreSQL, SQLite, MySQL, and MariaDB.

**Why it matters:** A call that skips on one database raises or is refused on another. A `unique_by:` that looks like it narrows uniqueness may be ignored, rejected, or only affect the skip form. A `returning:` that looks portable may yield primary keys, no columns, or an unsupported-option error.

---

# What should be true when this is done

These are desired **observable** outcomes. They use this revision as baseline and ask for **clarity and honesty**, not identical behavior on every database.

1. **Skip vs bang is a visible uniqueness policy.** `insert_all` skips rows that conflict with the uniqueness rule in force and leaves already-stored rows unchanged. `insert_all!` raises `ActiveRecord::RecordNotUnique` on a uniqueness conflict and inserts **no** rows from that call.

2. **Adapter support is visible at the call, not after a surprising write.** If the database cannot skip duplicates, cannot honor `unique_by:`, or cannot honor `returning:`, the developer gets a clear argument error and no write. If it can, the documented result for that adapter happens.

3. **Default skip uniqueness is adapter-honest.** Where the database can skip duplicates, default `insert_all` (no `unique_by:`) skips a row that collides with **any** uniqueness the table already enforces (primary key or unique index). It does not update the existing row.

4. **`unique_by:` narrows skip only where a named conflict target is supported.** On PostgreSQL and SQLite, `insert_all(..., unique_by:)` skips only collisions on that unique index (column list, reversed column list, index name, or expression index). A collision on a **different** unique index still raises `RecordNotUnique`. On MySQL and MariaDB, passing `unique_by:` is refused.

5. **Bang does not use `unique_by:` to skip.** On adapters that accept `unique_by:`, `insert_all!` may take the option but still raises on **any** unique-index violation and still inserts no rows. *(Open: should bang refuse `unique_by:` as meaningless? See open questions.)*

6. **`returning:` is adapter-honest.** PostgreSQL, SQLite, and MariaDB (when that server can return inserted rows) default to returning primary-key columns for successfully inserted rows. `returning: false` and `returning: []` insert as usual and return no columns. Selected columns and a known-safe SQL expression return those values. MySQL (non-MariaDB) does not support `returning:`; an explicit `returning:` is refused. When returning is unsupported, the default call still inserts and returns a result with no returned columns.

7. **Input shape fails before a partial write.** Empty input returns an empty result and inserts nothing. Hashes with different keys raise with missing/extra keys named. Unknown attributes raise. Values go through the same type casting and serialization as ordinary create (enums, serialized columns, custom coder). Timestamp columns follow the model setting unless `record_timestamps:` overrides; an explicit timestamp in the payload wins.

8. **Composite primary keys are not silently treated as a single `id`.** On PostgreSQL/SQLite, skip insert on a composite-key table needs a uniqueness target that actually exists (including the composite key). Bang insert does not require that target. On MySQL/MariaDB, skip and bang insert succeed without `unique_by:`.

# Non-goals

- Making all four databases behave identically.
- Changing `upsert_all` except where it is needed to contrast skip vs replace.
- Instantiating models, running validations, or running callbacks on bulk insert.
- Prescribing SQL, adapter internals, schema-cache mechanics, or a rollout/migration plan.
- Inventing new options beyond `unique_by:`, `returning:`, and `record_timestamps:`.
- Numeric performance targets.

# Acceptance examples

Required unless marked illustrative. “Supported” means this revision’s adapter flags: skip-duplicates on all four; named conflict target on PostgreSQL and SQLite only; returning on PostgreSQL, SQLite, and MariaDB 10.5+ only.

Books used below have a primary key `id`, a unique index on `[author_id, name]`, a unique index on `isbn` that applies only when `published_on` is present, and—where the database allows expression indexes—a unique index on `lower(external_id)`.

## Default conflict (no `unique_by:`)

**Skip a duplicate primary key, leave the original unchanged**  
Given a book already stored with `id: 1` and some format.  
When the developer calls `Book.insert_all [{ id: 1, name: "Agile Web Development with Rails" }]` (or the same row with a different `format`).  
Then on PostgreSQL, SQLite, MySQL, and MariaDB: row count is unchanged, the stored format is unchanged, and no error is raised.

**Same-batch duplicate identifiers keep one row**  
When they `insert_all` two hashes with `id: 111` and different names.  
Then one row exists with the **first** name, on every adapter that can skip duplicates.

**Two new rows that collide only on `[author_id, name]`, with different or omitted ids**  
When they `insert_all` two “Refactoring” rows for the same author.  
Then exactly one row is inserted (skip), on every adapter that can skip duplicates.

**Bang is all-or-nothing**  
When they `insert_all!` a batch that includes a row colliding with an existing unique value.  
Then they observe `ActiveRecord::RecordNotUnique` and **no** new rows from that call, on every adapter.

## Named, composite, and expression `unique_by:`

**Named / column / composite unique index — skip only that target (PostgreSQL, SQLite)**  
When they `insert_all` a row whose `id` already exists, with `unique_by: :index_books_on_author_id_and_name` (and the author/name pair is new).  
Then they get `RecordNotUnique` (the untargeted primary-key collision is not skipped).  
When they `insert_all` new rows with `unique_by: :isbn`, `unique_by: %i[author_id name]`, `unique_by: :index_books_on_isbn`, or `unique_by: :id`, and those targets do not collide.  
Then the rows are inserted.

**Reversed composite columns still identify the same unique index (PostgreSQL, SQLite)**  
When they pass `unique_by: [:name, :author_id]` for an index defined on `[:author_id, :name]`.  
Then the insert is accepted the same as the index’s column order.

**Expression unique index (PostgreSQL, SQLite, where expression indexes exist)**  
Given a book with `external_id: "abc"`.  
When they `insert_all [{ external_id: "ABC" }], unique_by: :index_books_on_lower_external_id`.  
Then row count is unchanged (case-insensitive collision skipped).

**MySQL and MariaDB refuse `unique_by:`**  
When they pass `unique_by: :isbn` (or any target) to `insert_all` / `insert_all!`.  
Then they get an argument error that the adapter does not support `:unique_by`, and no write occurs.  
*(Suite today asserts this on `upsert_all`; the shared option check is the same. Confirm on `insert_all` / `insert_all!`.)*

## Invalid or non-unique `unique_by:`

**Missing or non-unique target (PostgreSQL, SQLite)**  
When they pass `unique_by: :cats`, `unique_by: %i[author_id isbn]`, or `unique_by: :author_id`.  
Then they get an argument error matching “No unique index”, and no write occurs.

## Composite primary keys

**PostgreSQL / SQLite skip needs a real uniqueness target**  
Given `Cart` stored with composite key `[shop_id, id]` while the model’s configured primary key is `id`.  
When they `Cart.insert_all [{ id: 2, shop_id: 1, title: "My cart" }]` with no `unique_by:`.  
Then they get an argument error matching “No unique index found for id”.  
When they pass `unique_by: [:shop_id, :id]`.  
Then the row is inserted.

**PostgreSQL / SQLite bang does not require `unique_by:`**  
When they `Cart.insert_all! [{ id: 2, shop_id: 1, title: "My cart" }]`.  
Then the row is inserted.

**MySQL / MariaDB composite insert without `unique_by:`**  
When they `insert_all` and `insert_all!` new carts without `unique_by:`.  
Then the rows are inserted.

## `returning:`

**Default columns (PostgreSQL, SQLite, MariaDB when returning is supported)**  
When they `insert_all!` one book with no `returning:`.  
Then the result includes the primary-key column(s) (`id` for books).

**`returning: false` and `returning: []`**  
When they insert with either option on a returning-capable adapter.  
Then the row is inserted and the result has no columns.

**Selected columns**  
When they pass `returning: [:id, :name]`.  
Then the result includes those columns for successfully inserted rows (e.g. name `"Rework"`).

**SQL expression**  
When they pass a known-safe SQL expression such as `UPPER(name) as name`.  
Then the result uses that expression (e.g. `"REWORK"`). A raw string that is not marked known-safe is refused.

**MySQL (not MariaDB) refuses explicit `returning:`**  
When they pass `returning: :id` (or any returning list/expression).  
Then they get an argument error that the adapter does not support `:returning`, and no write occurs.  
A default call (no `returning:`) still inserts and returns a result without those columns.

**MariaDB too old for returning**  
Treat like MySQL: no returned columns by default; explicit `returning:` refused. *(Version cutover is a capability flag, not a product promise of a specific version string.)*

## Empty input, mismatched keys, types, timestamps

**Empty input**  
When they `insert_all([])` or `insert_all!([])`.  
Then they get an empty result and no rows, on adapters that can perform bulk insert.

**Mismatched keys**  
When one hash has `isbn` and the next does not (or the reverse).  
Then they get an argument error that all objects must have the same keys, naming `extra:` / `missing:`, and no write occurs.

**Unknown attribute**  
When a hash includes an unknown attribute.  
Then they get `ActiveRecord::UnknownAttributeError` and no write.

**Type casting / serialization**  
When they insert enum values, a serialized column, or a custom coder payload.  
Then stored values match ordinary `create!` for the same input (including no double-encoding of strings through a non-idempotent coder).

**Timestamp override**  
When the model would auto-set timestamps and they pass `record_timestamps: false`, omitted timestamp columns stay unset.  
When the model would not auto-set them and they pass `record_timestamps: true`, create timestamps are set.  
When the payload includes `updated_at` / `updated_on`, those values are stored rather than overwritten.  
*(Bulk-insert tests today lean on `upsert_all` for timestamps; insert_all should match this contract.)*

## Atomicity: skip vs bang

**Skip inserts the non-conflicting rows**  
When a batch contains one new id and one id that already exists, with default uniqueness.  
Then only the new row is inserted; the existing row is unchanged.

**Skip + `unique_by:` is not “skip everything”**  
When they skip only by `[author_id, name]` but collide on `id`.  
Then on PostgreSQL/SQLite they get `RecordNotUnique` (targeted skip does not swallow other unique failures).

**Bang inserts none**  
When any row in the batch violates a unique index.  
Then they observe `RecordNotUnique` and the table is unchanged by that call—including when `unique_by:` was passed on PostgreSQL/SQLite.

# Steering evidence

**Success looks like:** A developer can read the options, know whether their adapter accepts them, and observe the matching example above without a silent no-op, a secret update of existing columns, or a different uniqueness rule than advertised.

**Investigate / do not call it done if:**

- Skip updates an existing row’s non-key columns (“secret upsert”).
- Bang leaves some rows from the failed batch in the table.
- MySQL or MariaDB accepts `unique_by:` and then ignores it.
- MySQL accepts `returning:` and then ignores it.
- PostgreSQL/SQLite `unique_by:` skips collisions on a **different** unique index than the one named.
- Default skip on PostgreSQL/SQLite does **not** skip a non-PK unique collision (contradicts “any unique index” / current skip examples).
- Composite-key skip on PostgreSQL/SQLite succeeds without a real uniqueness target, or MySQL/MariaDB starts requiring `unique_by:` for the same call.
- Empty input, mismatched keys, or unsupported options write a subset of rows.

**Reconsider the problem framing if:** Developers are not confused by adapter differences but by skip vs upsert, or if the real pain is only documentation while the observed examples already match what they need. In that case this is a documentation outcome, not a behavior change.

# Open questions

1. Should `insert_all!` **refuse** `unique_by:` (it cannot skip), or keep accepting it on PostgreSQL/SQLite as a no-op for skip behavior while still raising on any unique violation?
2. Should `returning: false` and `returning: []` stay the same externally (no columns), or is distinguishing them part of “clearer”?
3. For composite-key models whose configured primary key is not the table’s full primary key, is the PostgreSQL/SQLite argument error the desired message, or should skip default to the table’s actual primary key without `unique_by:`?
4. Is same-batch “first hash wins” the desired skip rule, or should that stay unspecified?
5. Should timestamp examples be required for `insert_all` itself, given tests today mostly use `upsert_all`?
6. Are Trilogy and mysql2 both “MySQL” for this contract, with MariaDB the only MySQL-family returning exception?

---

Correct the problem frame, any outcome, or any example that should not be required. The main hypothesis to confirm or reject: **we are specifying adapter-honest behavior, not one behavior on all four databases.**
