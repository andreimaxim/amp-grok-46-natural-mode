## Current contract (this revision)

This is what delayed mail and its test helpers do today. It is not a proposal.

**Who sets the queue.** `deliver_later` / `deliver_later!` enqueue the mailer’s `delivery_job` (default: `ActionMailer::MailDeliveryJob`). A per-call `queue:` is applied on that job before enqueue. If `queue:` is omitted, the default job asks the mailer for `deliver_later_queue_name`. A custom job that names its own queue is what actually gets used; the mailer’s `deliver_later_queue_name` does not override it.

## Shaping brief

**Kind of work.** Behavior change: make existing delayed-mail targeting and test delivery trustworthy across the queue names teams already use. Not a new mail product.

**Problem frame.** A developer splits delayed mail across queues (transactional vs bulk, internal vs external) and needs tests that send only one of those queues. Today they can set a mailer queue, override one send, inherit settings, or swap the delivery job—but the name they configure is not always the name that was recorded, and the name they filter on in tests is not always the name the adapter kept. Symbol vs string, `nil` meaning “default,” a subclass vs its parent, a custom job that ignores the mailer, scheduled mail still sitting on a queue, and adapters that rewrite names all make “deliver this queue” miss mail or send the wrong mail. That makes queue splits unsafe to rely on.

**Behavioral outcome.** A team can point delayed mail at a queue, and later select that same mail in tests, using the name they think they used. Matching is by the queue the send actually landed on, not by which mailer class was involved. Different queues stay isolated.

**Appetite (hypothesis).** Small: enough to make targeting and test selection agree for the cases below. Not enough to add routing UI, new queue types, or adapter-specific dashboards. Correct this if the cycle should be larger.

**Scope.** Delayed send (`deliver_later` / `deliver_later!` and bulk equivalents) and test helpers that deliver or assert those sends, including `deliver_enqueued_emails`’s queue filter. Covers mailer-level queue names, per-send overrides, inheritance, custom delivery jobs, parameterized mail, scheduled send, and test selection when the stored name is a symbol, string, `nil`, or an adapter-normalized form of the same queue.

**Non-goals.** Immediate send (`deliver_now`). Mail content, callbacks, or error handling. Worker/process management. Redesigning Active Job. Teaching every adapter’s rewriting rules. Changing what “due” means for `wait` / `wait_until` except as it interacts with “only this queue.”

**Risks.** Tightening matching could start delivering mail existing tests meant to leave queued, or skip mail they meant to send. Treating a custom job’s queue as the mailer’s queue (or the reverse) would reroute production mail. `nil` vs default-queue is easy to get wrong in apps on 6.1+ defaults. Adapter rewriting can make two names look like one queue or one name look like two. Queue prefixes can be applied twice if both the app and the adapter add them.

### Acceptance examples (required)

**Several mailers, one filter.** Customer mail is targeted at `external_mailers`, employee mail at `internal_mailers`. The team asks tests to deliver only `external_mailers`. They observe the customer mail sent and the employee mail still queued.

**Per-send override.** A mailer’s usual queue is `mailers`. One welcome send is told to use `priority`. A filter for `priority` sends that welcome and leaves other mail on `mailers` queued.

**Symbol and string are the same queue.** The mailer is configured with `:billing`; the test filter is `"billing"` (and the reverse). Both sends of that mail are delivered. A different name is not.

**Nil means the default queue.** The mailer’s delayed-mail queue is unset/`nil`. The send lands on Active Job’s default queue. A test that delivers that default queue sends this mail. A test that delivers a named mail queue does not.

**Inheritance stays local.** Parent keeps `:mailers`. Child sets `:throttled`. Child sends land on `throttled`; parent sends still land on `mailers`. Changing the child does not move the parent.

**Custom delivery job owns the queue.** A mailer uses a job that itself sits on `delivery_job_queue`, and also has a mailer-level `deliver_later_queue_name`. The send is observed on `delivery_job_queue`. Filters for the mailer-level name do not deliver it. Filters for `delivery_job_queue` do.

**Custom job that still follows the mailer.** A mailer uses a custom job that does not name its own queue. The send is observed on the mailer’s delayed-mail queue, and that is the name tests use.

**Parameterized mail.** `Invites.with(inviter:, invitee:).account_invitation.deliver_later` on `invites` is delivered by a `queue: "invites"` test pass and left queued by a filter for another queue. Params do not change which queue is selected.

**Scheduled mail on a filtered queue.** On `mailers`, one send is due now and one is due in two hours. Delivering `mailers` due within an hour sends only the first. The later one stays queued on `mailers`. A filter for a different queue sends neither.

**Adapter-normalized names.** The app targets `:Mailers` (or `:mailers`) and the adapter stores `"mailers"` (or another documented equivalent). Test delivery by the name the team used still sends that mail. A genuinely different stored queue is not sent.

**Counterexample: unfiltered test delivery.** With no queue filter, delayed mail from every mailer, custom job, and parameterized send that is due is delivered. Queue isolation is opt-in.

### Steering evidence

- **Success:** Teams can split mailers across queues and write tests that send only one split, including the examples above, without caring whether the name was typed as a symbol, a string, or left nil.
- **Investigate:** Filters sometimes send nothing, or send mail from another queue, especially with custom jobs, prefixes, or `nil` defaults.
- **Wrong frame:** Failures are actually missing workers, `perform_deliveries`, or schedule timing, and queue names already match. Then stop and treat this as ops/docs, not targeting behavior.
- **Stop:** Making names agree would change which queue production mail uses for existing apps.

### Open questions

1. Is the appetite actually small, or should custom-job-vs-mailer queue ownership be a separate decision?
2. When an adapter rewrites a name, what counts as “the same queue” beyond symbol/string/`nil` (case, prefix, extra namespace)?
3. Should `deliver_later(queue: nil)` mean “do not override” (today’s implied behavior) or “use the default queue”?

This is the current shared understanding, not a locked spec. Correct the problem, the custom-job ownership rule, or what “same queue” means under adapter rewriting if any of those is wrong.
