## Verdict: **Request changes**

The intended fallback—environment credentials content using `config/master.key` when its environment key is absent—is defensible, and Rails 7.1 shipped independent defaults (PR #47107 / `1068945b`). But the PR is incomplete and unsafe as a `credentials_defaults`-only change. The fallback must be **directional**, and `credentials:edit --environment` must match runtime behavior.

### Pairing analysis

Current defaults select paths independently:

- Content: environment file if it exists, else global `config/credentials.yml.enc`.
- Key: environment key if it exists, else `config/master.key`.

That permits the intended case:

| Files | Result |
|---|---|
| Env content + env key | Normal environment pair |
| Env content + no env key + master key | Env content decrypts with master key, **only if it was encrypted with that key** |
| Global content + master key | Normal global pair |

But it also permits an invalid reverse pairing:

| Files | Bad result |
|---|---|
| No env content + global content + stale env key | Global content is paired with env key → `MessageEncryptor::InvalidMessage` |

That global-content/env-key pairing has no legitimate workflow and can abort production boot when `secret_key_base` is read from credentials. This is a blocker.

A wrong existing environment key must **not** fall back to `master.key`: it should fail closed with `InvalidMessage`. A lost environment key plus env content may now produce `InvalidMessage` if master exists but did not encrypt the content, rather than a missing-env-key error.

### Compatibility and security consequences

- `RAILS_MASTER_KEY` remains highest precedence, ahead of the selected key file. A wrong ENV key fails; it does not retry a file key.
- Explicit `config.credentials.content_path` / `key_path` remain authoritative; setting both is unambiguous. ENV still overrides a custom key file.
- `require_master_key` only changes a missing selected key into `MissingKeyError`; it does not validate keys or try alternatives. With the directional fallback, the error correctly names `config/master.key`.
- With neither file key, `require_master_key: false` yields empty credentials; `true` raises `MissingKeyError`.
- Wrong valid-length keys raise `ActiveSupport::MessageEncryptor::InvalidMessage`; malformed keys can raise `ArgumentError` when reading or `InvalidKeyLengthError` when writing.
- AES-GCM prevents plaintext disclosure from a wrong key. But global-key reuse broadens the master key’s blast radius and weakens environment isolation/fail-closed behavior.
- In production, credential-backed settings—especially `secret_key_base`—are often read during boot, so bad pairing is an availability regression. Development/test may tolerate *missing* credentials through `tmp/local_secret` when `require_master_key` is false, but invalid decryption still raises when credentials are accessed.

### Command inconsistency: blocker

`show`, `fetch`, and runtime loading follow config defaults. But `credentials:edit --environment` hardcodes:

```ruby
@content_path = "config/credentials/#{environment}.yml.enc"
@key_path = "config/credentials/#{environment}.key"
```

Reproduced behavior for existing env content encrypted with `master.key`, with no env key:

1. `credentials:show --environment production` succeeds.
2. `credentials:edit --environment production` generates `production.key`.
3. Edit fails with “wrong key.”
4. The generated key remains.
5. Next runtime load selects that new env key and can fail boot with `InvalidMessage`.

Also, `edit` without `--environment`, but with `RAILS_ENV` set, follows config defaults—so behavior differs by invocation form.

### Recommended tiny diff

Make fallback directional: only environment content may fall back to master; global content always uses master.

  content_path = root.join("config/credentials/#{Rails.env}.yml.enc")

  if content_path.exist?
    key_path = root.join("config/credentials/#{Rails.env}.key")
    key_path = root.join("config/master.key") unless key_path.exist?
  else
    content_path = root.join("config/credentials.yml.enc")
    key_path = root.join("config/master.key")
  end

  { content_path: content_path, key_path: key_path }
end
```

Mirror that in `edit --environment`, preserving new-file behavior:

```ruby
if environment_specified?
  @content_path = "config/credentials/#{environment}.yml.enc" unless config.overridden?(:content_path)

end
```

## Analysis and security issues

With environment ciphertext, no environment key, and a present `master.key`, boot tries the global key against environment ciphertext:

- A wrong key raises `ActiveSupport::MessageEncryptor::InvalidMessage`, not `MissingKeyError`.

This is chiefly a configuration-integrity and availability issue, rather than a confidentiality issue: an incorrect key cannot decrypt, but store selection can be silently wrong and weaken the `require_master_key` check. `RAILS_MASTER_KEY` already supports a deployment with no key file without mixing stores.

## Historical behavior

Environment-specific credentials were introduced by [PR #33521 / commit `e0d3313`](https://github.com/rails/rails/commit/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba) in September 2018.

Originally, selection was **coupled to the existence of the environment-specific encrypted file**:

```ruby
def default_credentials_content_path
  if credentials_available_for_current_env?
    # config/credentials/<env>.yml.enc
  else
    # config/credentials.yml.enc
  end
end

def default_credentials_key_path
  if credentials_available_for_current_env?
    # config/credentials/<env>.key
  else
    # config/master.key
  end
end
```

Thus:

| `config/credentials/<env>.yml.enc` exists? | Content | Key |
|---|---|---|
| Yes | `<env>.yml.enc` | `<env>.key`, whether or not that key file exists |
| No | `credentials.yml.enc` | `master.key` |

See the [original implementation](https://github.com/rails/rails/blob/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba/railties/lib/rails/application/configuration.rb#L279-L298).

## Independent key fallback

Independent existence checks were introduced by [commit `1068945`](https://github.com/rails/rails/commit/1068945b8fc9324c795224ca8e16c45d9ff15f10), **“Use config.credentials.* in credentials commands,”** in January 2023. The commit belongs to **PR #47107**.

That refactor replaced the coupled methods with `credentials_defaults`:

```ruby
content_path = env_content
content_path = global_content unless env_content.exist?

key_path = env_key
key_path = master_key unless env_key.exist?
```

See the [change](https://github.com/rails/rails/blob/1068945b8fc9324c795224ca8e16c45d9ff15f10/railties/lib/rails/application/configuration.rb#L540-L547) and the [current implementation](https://github.com/rails/rails/blob/main/railties/lib/rails/application/configuration.rb#L683-L690).

Therefore, since that commit, this combination is intentional observable behavior:

- `config/credentials/<env>.yml.enc` exists
- `config/credentials/<env>.key` does not
- `content_path` → environment encrypted file
- `key_path` → `config/master.key`

The accompanying guide explicitly documented each fallback independently: content defaults according to whether the environment content exists, while key defaults according to whether the environment key exists ([documentation added by the commit](https://github.com/rails/rails/blob/1068945b8fc9324c795224ca8e16c45d9ff15f10/guides/source/configuring.md#L263-L280)).

## Intended pairing

The **original feature’s intent was clearly a paired layout**:

- `config/credentials/<env>.yml.enc`
- `config/credentials/<env>.key`

The original PR description, changelog, command option description, tests, and usage documentation all describe the environment encrypted file as decrypted by its corresponding environment key. `config/master.key` belonged to the global `config/credentials.yml.enc` arrangement. See the [original changelog](https://github.com/rails/rails/blob/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba/railties/CHANGELOG.md#L1-L9) and [usage text](https://github.com/rails/rails/blob/e0d3313bac6bd2fbf10df27d79d72157f63ae6ba/railties/lib/rails/commands/credentials/USAGE#L42-L50).

So the historical conclusion is nuanced:

- **Original semantic intent:** environment content and environment key were a pair.
- **Since PR #47107:** Rails deliberately/documentedly computes their defaults independently, allowing environment content to pair with `master.key`.
- Consequently, calling the current fallback simply a longstanding bug is difficult to support. It originated in a refactor primarily concerned with command/config consistency, but was explicitly documented as independent fallback behavior and has remained Rails behavior.

`ENV["RAILS_MASTER_KEY"]` is separate from the path choice and takes precedence over either key file.

## `credentials:edit --environment`

Originally, `credentials:edit --environment production` unconditionally targeted:

- `config/credentials/production.yml.enc`
- `config/credentials/production.key`

PR #47107 changed the command to load the selected Rails environment and respect `config.credentials.content_path` and `key_path`. For an explicit `--environment`, it substitutes the conventional environment paths only when the corresponding setting was **not overridden**:

```ruby
@content_path = "config/credentials/#{environment}.yml.enc" unless config.overridden?(:content_path)
@key_path = "config/credentials/#{environment}.key" unless config.overridden?(:key_path)
```

See [`credentials_command.rb`](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/credentials/credentials_command.rb#L20-L29).

The edit command then:

1. Uses the resolved `key_path`.
2. Creates that key when no usable key exists.
3. Passes the same `content_path` and `key_path` pair to the credentials generator.
4. Opens that encrypted file with that key.

See [key/path resolution and generation](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/credentials/credentials_command.rb#L80-L119).

Notably, explicit `--environment` normally forces `<env>.key`; therefore it does **not generally inherit the runtime `credentials_defaults` fallback to `master.key`**, unless configuration explicitly overrides `key_path`.

New env files still get an env key; existing master-encrypted env files keep using `master.key`. Document that as directional, not “always the global key.” Strict pairing (env content never uses `master.key`) is the cleaner security story, but it would break the documented independent fallback; directional fallback is the compatible fix.
