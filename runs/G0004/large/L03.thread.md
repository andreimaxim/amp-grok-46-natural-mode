## Assistant

Inspected the public contract, conversion/update/merge/replace tests, and live mixed-key probes. Tests cover mixed **non-colliding** keys and nested conversion; they do not cover `:key`/`"key"` collisions. Collapse is silent. The class docs already say the winner is unspecified.

Working draft — correct anything that is off.

**Problem frame:** A Rails app or library author ingesting configuration (or other data) that can carry both `:key` and `"key"` converts or updates into indifferent access so string and symbol lookups work. Today that conversion keeps one entry and drops the other with no signal, and which value survives is unspecified. They cannot tell that configuration was discarded, and they cannot tell which source they actually got.

**Behavioral outcome:** After conversion or update, they can observe that a colliding string/symbol pair was collapsed and that a value was discarded. Indifferent lookup of a single remaining key still works. Mixed keys that do not collide still remain two entries.

**Current behavior (observed):**
- A regular hash may hold both `:key` and `"key"` (size 2). After conversion, construction, `update`, `merge`, `replace`, or `reverse_merge`, the result has one string key `"key"` and size 1.
- In this environment the survivor followed source insertion order, but that is not a public guarantee; the contract says the winner is unspecified.
- There is no user-visible signal that an entry was dropped — including when the two values are equal.
- Nested hashes and hashes inside arrays convert the same way, so a collision at any depth collapses at that depth.
- `update(hash_a, hash_b)` of two separate hashes is different: a later argument overwriting an earlier one is ordinary multi-hash update, not the unspecified intra-hash collapse.
- Sequential assignment on an already-indifferent hash (`h[:key] = …` then `h["key"] = …`) is ordinary overwrite of one key, not discarded dual entries.
- Integer `1` and string `"1"` do not collapse.

**Examples** (required unless marked illustrative)

*Core — conversion discards one value with no signal*
A source hash is `{ :timeout => 5, "timeout" => 30 }`. After conversion, size is 1, both `:timeout` and `"timeout"` read the same remaining value, and nothing indicates that 5 or 30 was dropped.

*Nested collision*
A source hash is `{ db: { :host => "a", "host" => "b" } }`. After conversion, `db` has one `"host"` and one of `"a"` or `"b"` is gone, with no signal at the inner hash.

*Top-level collision of nested hashes*
A source hash is `{ :key => { a: 1 }, "key" => { b: 2 } }`. After conversion, one entire nested hash is gone; the result has a single `"key"`.

*Multi-hash update — two arguments, one form each*
`update({ :key => "from-first" }, { "key" => "from-second" })` leaves `"from-second"`. That is later-argument overwrite, which already has a defined meaning.

*Multi-hash update — one argument contains both forms*
`update({ :key => "s", "key" => "t" })` leaves one value; which one is unspecified, and nothing indicates the other was discarded.

*Multi-hash update — each argument itself mixed*
`update({ :a => 1, "a" => 2 }, { :a => 3, "a" => 4 })` can discard inside each argument, then the later argument overwrites. Two different kinds of loss can happen in one call.

*Counterexample — mixed non-colliding keys*
`{ :a => 1, "b" => 2 }` still becomes two entries `"a"` and `"b"`. Detection of collapse must not treat this as discarded data.

*Counterexample — already-indifferent overwrite*
Writing `:key` then `"key"` on an indifferent hash overwrites one key. That is not mixed-key ingestion losing a second entry.

**Compatibility constraints**
- Indifferent lookup (`:foo` and `"foo"` as one key) remains the existing product behavior.
- Mixed non-colliding keys, nested conversion, and multi-argument update/merge keep their current observable meaning.
- The unspecified intra-hash winner is already documented public behavior; making a different value survive by default, or raising by default, would change existing conversion.

**Steering evidence**
- Success: ingesting a mixed-key config hash, the author can tell that a colliding pair collapsed and that a value was discarded; non-colliding mixed keys and ordinary indifferent lookup still look as they do today.

- Reconsider the framing if authors only need a specified winner, not a way to see that data was discarded — specifying a winner would not by itself make discarded data detectable.
- Stop or revise if the only acceptable signal would break existing conversion for params-style hashes that already collapse silently.

**Open questions**

- **Error versus observation:** On collapse, should conversion fail, or succeed and leave an observation that data was discarded?
