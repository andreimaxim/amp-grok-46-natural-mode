## Product shaping brief: predictable Active Storage download-link expiration

This is a **behavior-change** brief with a documentation outcome attached: application developers should be able to predict when a download link still works, what a recipient or cache will still hold after that moment, and what failure looks like. It is not a request to add a new serving mode.

The actor is an application developer who generates download links with `ActiveStorage::Blob#signed_id`, `#url`, `rails_storage_proxy_url`, or `rails_storage_redirect_url`, and then reasons about whether those links remain usable for a user, email, CDN, or browser cache.

### Shaped proposal

#### Problem frame

An application developer needs to hand a download link to a user, email, CDN, or another system and know, without surprise:

1. whether that link stays valid forever or dies at a chosen time;
2. whether a later request still receives the file, a redirect to storage, or a dead link;
3. whether a browser or CDN might keep serving the file after the link is supposed to be dead.

Today those three clocks are easy to mix up. Application URLs are permanent by default. Service URLs expire in five minutes unless the service is public, in which case they do not expire. Redirect responses cache privately for five minutes (the service clock). Proxy responses tell caches they may keep a public copy essentially forever. Expiry of the application URL does not, on current evidence, change those cache headers. Expired and forged links both look like “not found.” Variants inherit the blob identifier’s expiry, but that is easy to miss because representation tests never show it.

The pain is not missing knobs. The knobs exist. The pain is that a developer cannot predict from the names (`signed_id`, `#url`, proxy, redirect, public, private, variant) which clock actually governs a recipient’s next request.

#### Desired outcome

After this work, a developer who generates a download link can state, for that link:

- whether the identifier is permanent or time-limited, and by which clock (`duration from generation` vs `absolute time`);
- what a recipient observes while it is valid (file body vs redirect to storage);
- what they observe after it is no longer valid;
- whether a cache or CDN is allowed to keep serving the content past that moment;
- that public vs private storage changes the **service** URL, not the application URL, unless they are linking at the service URL itself;
- that a variant/preview link lives and dies with the blob identifier in that URL;
- that expiry is not permission: anyone who has a still-valid URL can fetch the file.

Success is qualitative: a developer can choose permanent vs expiring, proxy vs redirect, public vs private, original vs variant, and then correctly predict the next request and the cache’s behavior. They should not need to discover that proxy cache headers and application-URL expiry disagree.

#### Appetite

**Hypothesis, not a supplied constraint:** a short, bounded clarification of existing download-link lifetime — small enough that serving modes, storage providers, and authentication are left alone. Enough to make the lifetime story teachable and the observable outcomes consistent with that story. Not a redesign of Active Storage.

Correct this if the appetite is “docs only,” “change defaults,” or “make expiring proxy links actually uncacheable.”

#### Scope

In scope:

- Permanent vs expiring signed blob identifiers, including duration (`expires_in`), absolute time (`expires_at`), and an application-wide default for generated application URLs.
- Service-URL expiry on `#url`, including the 5-minute private default and non-expiring public service URLs.
- Proxy vs redirect: the response the client sees, and the cache headers on that response, including how those headers relate to application-URL expiry.
- Tampered, purpose-mismatched, and expired identifiers, and the user-visible result.
- Public vs private services, including disk’s public path still being a signed disk URL with no expiry.
- Variant/preview links that share the blob identifier.
- Boundary timing: still valid before expiry; no longer valid at and after expiry.

The work is complete when a developer can predict those cases from documented, consistent externally visible behavior — not when a particular internal mechanism exists.

#### Non-goals

- Authenticated or per-user authorization for downloads. Expiry remains a stop-using-this-URL control, not access control.
- Changing how files are stored, mirrored, or uploaded.
- New serving modes beyond proxy and redirect.
- Distinguishing expired from tampered from missing in the HTTP status, unless that distinction is later judged necessary for predictability (it is not required by this brief).
- Changing Content-Disposition / XSS attachment forcing, byte-range serving, or CDN host routing, except where cache lifetime is part of expiration predictability.
- Direct-upload PUT URL lifetime, except as a reminder that it is a third, upload-only clock and out of this download-link story.

#### Risks

- **Cached content outliving the link.** If proxy responses remain forever-public while the signed URL expires, a CDN or browser can keep serving the file. Treating “URL expired” as “content gone” would be wrong. If the product instead tightens cache headers to match URL expiry, existing CDNs that relied on immutable proxy caching will refetch more often.
- **Redirect cache vs service URL.** Redirect responses are cached for the service-URL lifetime (5 minutes, private). A 1-minute application URL can still have its redirect cached on a different clock. A public service URL behind a redirect can remain reachable after the application URL is dead if the recipient kept the redirected location.
- **Silent default permanence.** Existing apps generate permanent, hard-to-guess public application URLs. Making expiry the default, or changing cache headers globally, would break bookmarks, emails, and CDNs.
- **404 collapsing failure modes.** Developers debugging “why did this link die?” cannot tell expiry from tampering from a deleted blob over HTTP.
- **Variants.** Developers may assume a representation has its own lifetime. Only the blob identifier in that URL expires; an unexpired blob identifier with a still-valid variation key continues to work.
- **Guide vs helpers.** `expires_at` already works on the helpers but is absent from the expiring-URL guide. Docs-only fixes can still leave cache/expiry mismatch in live responses.
- **Public disk ≠ public cloud.** A developer who sets a disk service public may expect a never-signed object URL; they still get a signed disk URL, just one that does not expire.

#### Behavioral outcomes and acceptance examples

**1. A developer can mint a permanent application download link.**

- **Example (required):** They generate a proxy or redirect URL with no expiry and no application-wide default. A recipient can open it now and again much later; it still works. The identifier is unguessable but not time-limited.

**2. A developer can mint a time-limited application download link by duration or absolute time.**

- **Example (required):** They generate the URL with a 1-minute duration. Opening it immediately succeeds (proxy: file body; redirect: redirect toward the file). Opening the same URL after two minutes does not succeed; the recipient gets not found.
- **Example (required):** Same, with an absolute expiry one minute from now.
- **Example (required):** They set an application-wide default lifetime of one minute and generate a URL with no per-link override. Same live-then-dead behavior.
- **Boundary (required):** A request before the expiry instant succeeds. A request at or after that instant does not. (Hypothesis from signed-message behavior; Active Storage HTTP tests do not currently show the exact instant.)
- **Counterexample:** Supplying both an absolute time and a duration does not leave the developer guessing: the absolute time is the one that counts. (Hypothesis from signed-message tests; Active Storage download tests do not show both together.)

**3. A developer can tell application-URL expiry apart from service-URL expiry.**

- **Example (required):** They generate a private-service `#url` with the default. That storage URL works for a short window (documented as 5 minutes) and is not the stable application URL they would put in a page or email.
- **Example (required):** On a public service, `#url` is a permanent public object URL and does not inherit the 5-minute private default.
- **Example (required):** An application redirect URL can remain valid long after any single service URL it redirected to would have expired; each visit may receive a fresh service URL.
- **Counterexample:** Setting service-URL expiry does not, by itself, make `rails_storage_proxy_url` / `rails_storage_redirect_url` expire, and vice versa.

**4. Proxy and redirect remain distinct, including cache behavior the developer can predict.**

- **Example (required):** Redirect: the client receives a redirect, not the bytes, and the redirect response is privately cacheable for the short service-URL window (5 minutes by default).
- **Example (required):** Proxy: the client receives the file from the application. On success today, caches are told they may store it publicly and indefinitely.
- **Example (required, conflict to resolve):** A developer generates a **proxy** URL that expires in one minute. After one minute, a **new** request with that URL is not found. The brief requires a predictable answer to: may a cache that already stored the successful response keep serving the file? Today’s source says yes (forever public immutable). The desired product answer must be explicit: either “yes, caches may outlive the URL” or “no, cache lifetime will not exceed link lifetime.” This is the main unresolved product choice.
- **Example (illustrative):** Proxy range requests and failed downloads are not offered as forever-public cacheable success responses (404/500 use `no-cache`).

**5. Forged, expired, and unknown identifiers fail closed in the same user-visible way.**

- **Example (required):** A tampered identifier yields not found, not the file.
- **Example (required):** An expired identifier yields not found, not the file.
- **Example (required):** An invalid variation key yields not found even if the blob identifier is valid.
- **Counterexample:** Expiry is not a substitute for signed-in access control. A still-valid URL fetched by anyone who has it still returns the file.

**6. Variants and previews follow the blob identifier in the URL.**

- **Example (required):** A developer generates a proxy/redirect URL for a variant with a 1-minute expiry. It works immediately and is dead after two minutes, same as the original blob URL.
- **Example (required):** A permanent variant URL keeps working. Invalid blob id or invalid variation key never returns the file.
- **Note:** Representation expiry is currently inferred, not shown by Active Storage tests.

**7. Public versus private storage does not secretly change application-URL expiry.**

- **Example (required):** `rails_storage_proxy_url` / `rails_storage_redirect_url` still take their lifetime from the signed blob identifier, whether the service is public or private.
- **Example (required):** Private `#url`: short-lived. Public cloud `#url`: permanent public object URL. Public disk `#url`: still a signed disk URL, but without expiry, and it serves the file.

#### Steering evidence

We would treat the outcome as **not yet achieved** if a developer following the documented story is surprised by any of:

- a link they believed permanent dying, or a link they believed expired still working on a **new** request;
- proxy vs redirect cache headers that contradict the story they were given about link lifetime;
- a variant link living or dying on a different clock than the blob identifier in that URL;
- a public service changing application-URL expiry rather than only service-URL shape;
- expired and valid-but-forged links returning the file.

We would **reconsider the problem framing** if:

- developers only needed a documentation map of the two clocks, and live cache/expiry mismatch is an accepted, load-bearing CDN feature;
- the real pain is authorization (“only this user may download”), which expiry cannot solve;
- changing cache headers to match URL expiry would cost more in CDN traffic than the predictability is worth.

Evidence that should trigger **continue**: developers can predict the examples above, including an explicit stance on whether caches may outlive expiring proxy URLs.

Evidence that should trigger **stop / split**: if “make expiry predictable” and “make proxy CDN-cacheable forever” cannot both be true, split CDN caching from link expiry rather than blending them into one outcome.

#### Open questions

1. **Caches vs expiring proxy URLs (material).** Should a successful proxy response be allowed to live in browsers/CDNs after the signed URL expires, or must cache lifetime not exceed link lifetime? Current behavior is the former; many developers will assume the latter.
2. **Appetite.** Docs-and-examples only, or also align live cache headers / defaults with the story?
3. **Default permanence.** Keep application URLs permanent by default (current), or is a default `urls_expire_in` now desirable? This brief assumes keep the default; changing it is a separate, compatibility-heavy decision.
4. **Exact instant.** Confirm product language: dead **at** expiry, not only after. That matches signed-message behavior; Active Storage HTTP tests do not show it.
5. **`expires_at` in the developer-facing story.** Helpers already support it; the expiring-URL guide does not mention it. Include it as a first-class choice?
6. **Redirect to a public service URL.** If the application URL expires but the client cached the redirected public location, that location may keep working. Is that an accepted consequence of redirect mode, or a hole in the story?

---

Assumption I made on your behalf: the work is to make **existing** download-link expiration predictable, not to change the permanent-by-default application URL or to add authentication. The one product choice that must be decided before implementation is whether expiring **proxy** links are allowed to remain in public caches after the URL is dead.

If that cache question, the appetite, or the “keep permanent defaults” assumption is wrong, say so and the outcomes/examples should change before any design work.
