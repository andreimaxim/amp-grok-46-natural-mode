## Assistant

`after_commit` does not run when a row is written. It runs later, on enrolled record instances, and only if the real (outer) transaction commits. `on:` does not mean “this save was a create/update/destroy.” It means “the instance’s transaction-local flags still look like that action when the outer boundary fires.”

```diagram
save / destroy
  with_transaction_returning_status
    add_to_transaction ──▶ current Transaction.@records
    remember_transaction_record_state
    INSERT / UPDATE / DELETE
      sets @_new_record_before_last_commit
          @_trigger_update_callback
          @_trigger_destroy_callback
                    │
                    ▼
     ┌──────── joinable nested block ────────┐
     │  no new Transaction                   │
     │  Rollback is swallowed, SQL stays     │
     └───────────────────────────────────────┘
                    │
                    ▼
     ┌──── requires_new (usually savepoint) ─┐
     │  commit: re-enroll into parent        │
     │  rollback: after_rollback now         │
     └────────────────━━─────────────────────┘
                    ┃
                    ▼
         outer COMMIT or ROLLBACK
           before_committed!          (commit only)
           SQL COMMIT / ROLLBACK
           committed! / rolledback!   (action filters here)
```

## Registration: `on:` becomes an `if:`

[`after_commit`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L284-L287) / [`after_rollback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L316-L318) register on the `:commit` / `:rollback` callback chains. `after_create_commit`, `after_update_commit`, `after_destroy_commit`, and `after_save_commit` are the same chain with a baked-in `on:`.

[`set_options_for_callbacks!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L341-L355) (and [`set_callback`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L323-L337) when `on:` is passed that way) prepends:

```ruby
-> { transaction_include_any_action?(fire_on) }
```

Valid actions are only `[:create, :destroy, :update]`. `:save` is rejected ([test](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L457-L466)).

Same filter name is deduplicated by Active Support. `after_commit :do_something` plus `after_create_commit :do_something` is one callback. `on: [:create, :update]` is not that same filter, so it is not collapsed.

`if:` from `on:` is prepended onto any existing `if:`, and does not mutate the caller’s array ([test](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L545-L553)).

## When the filters actually look at the instance

Filters run at the outer boundary inside [`committed!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L402-L409) / [`rolledback!`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L414-L421), not at INSERT/UPDATE/DELETE time.

[`transaction_include_any_action?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L545-L555):

- `:create` — `persisted? && @_new_record_before_last_commit`
- `:update` — not new-at-start, not `destroyed?`, and `@_trigger_update_callback`
- `:destroy` — `@_trigger_destroy_callback`

Those flags are written during persistence:

- [`remember_transaction_record_state`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L466-L482) snapshots `@new_record` on first enrollment in this transaction. Later saves in the same transaction reuse that snapshot, so `@_new_record_before_last_commit` stays true if the instance started new. After `committed!` has started, a nested save inside an `after_commit` forces it false so a follow-up save is an update ([test](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L212-L220)).
- [`_update_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L942-L945) sets `@_trigger_update_callback`.
- [`destroy`](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb#L424) sets `@_trigger_destroy_callback` only if the instance was already `persisted?` and the DELETE affected a row.

Even an unfiltered `after_commit` / `after_rollback` is skipped unless [`trigger_transactional_callbacks?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L449-L451) is true: a persisted create/update, or a destroyed instance that actually deleted a row. Failed validation enrolls the record then raises `Rollback`, but the flags never say a write happened, so history stays empty ([tests](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L121-L145)).

`:create` and `:update` cannot both be true on one instance: `:update` requires `!@_new_record_before_last_commit`. `:create` and `:destroy` also cannot both be true: `:create` requires `persisted?`.

## Enrollment: the record is queued on the current `Transaction`

[`save` / `destroy`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L380-L387) wrap work in [`with_transaction_returning_status`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L428-L445), which always [`add_to_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L558-L563) before the write.

[`Transaction#add_record`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L198-L206) either appends to `@records` or parks the instance in a `WeakMap` when this save did not open the transaction and the class has no commit/rollback/before_commit callbacks.

## Nested transactions: join vs savepoint vs outer boundary

[`DatabaseStatements#transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb#L495-L527):

```ruby
if !requires_new && current_transaction.joinable?
  yield current_transaction.user_transaction   # join
else
  within_new_transaction(...)                  # new Real / RestartParent / Savepoint
end
rescue ActiveRecord::Rollback
  # swallowed; does not re-raise
```

Join means there is no inner `Transaction`. Enrollment, SQL, and callbacks all belong to the outer object. An inner `raise ActiveRecord::Rollback` is swallowed and does not undo SQL. That is the Kotori/Nemu case in the [module docs](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L140-L176), and [`test_no_savepoint_in_nested_transaction_without_force`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L910-L928).

`requires_new: true` always calls [`begin_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L529-L563). `run_commit_callbacks` is `!current_transaction.joinable?`. Under a normal joinable outer transaction that is already dirty, the inner object is a [`SavepointTransaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L416-L466) (`SAVEPOINT active_record_N` / `RELEASE` / `ROLLBACK TO`), and `run_commit_callbacks` is false.

[`TransactionManager#commit_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L625-L637) / [`#rollback_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L639-L649):

```text
commit:   before_commit_records → pop → SQL commit/release → commit_records
rollback: SQL rollback         → pop → rollback_records
```

On an inner savepoint **commit**, [`commit_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L312-L337) does not run model callbacks. It re-enrolls each record on the parent and [`append_callbacks`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L342-L344) for transaction-object blocks. That is why [`test_only_call_after_commit_on_top_level_transactions`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L241-L251) sees an empty history until the outer block ends, and why [`Topic.current_transaction.after_commit`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L92-L117) registered inside `requires_new` also waits for the outer commit.

On an inner savepoint **rollback**, [`rollback_records`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L267-L284) always runs. [`SavepointTransaction#full_rollback?`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L468) is false, so instance state is restored only one savepoint level, not to the pre-outer snapshot. `after_rollback` fires at the savepoint. Those records are not handed to the parent.

If the parent was still clean, nested `requires_new` can be a [`RestartParentTransaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L387-L413) instead of a savepoint ([`test_nested_transactions_skip_excess_savepoints`](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L1469-L1503)). Callback transfer is the same: inner commit still has `run_commit_callbacks: false`.

## Concrete cases

**Create then update of the same instance in one transaction.** First `save` snapshots `@new_record` as true. The later update keeps `@_new_record_before_last_commit` and also sets `@_trigger_update_callback`. At the outer commit, `:create` is true and `:update` is false. Observable: unfiltered `after_commit`, `after_create_commit`, `after_save_commit`. Not observable: `after_update_commit`. Same filters on rollback if the outer block raises `Rollback` after both writes: `after_rollback` / `on: :create` only ([filter](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L545-L555), create/update tests at [L178-L198](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L178-L198)).

**Record saved only in an inner joined transaction.** Inner `transaction` without `requires_new` is a yield. The instance is on the outer `Transaction`. `after_commit` runs once, at the outer `COMMIT`. If the inner block raises `Rollback` and the outer does not, the write stays and `after_commit` still runs. That is join swallowing, not a savepoint.

**Rollback of an inner `requires_new` rescued by the outer block.** Inner `Rollback` is swallowed. Inner `rollback_records` already ran. The inner save’s `after_rollback` (and its `on:` filter) is visible immediately; its `after_commit` never runs. The outer transaction can still commit other records. [`test_only_call_after_rollback_on_records_rolled_back_to_a_savepoint`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L329-L352): outer `@first` gets 1 commit / 0 rollbacks; inner `second` gets 0 commits / 1 rollback. Same-instance version: one surviving outer save commits, each savepoint rollback increments rollback ([L355-L375](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L355-L375)). Transaction-object `after_rollback` on the inner user transaction fires at the savepoint; one registered on the outer does not ([L167-L190](file:///home/user/workspace/repo/activerecord/test/cases/transactions_test.rb#L167-L190)).

**Outer rollback after an inner savepoint release.** Inner `requires_new` success does `RELEASE SAVEPOINT` and re-enrolls the record on the parent. If the outer block then rolls back, that instance is in the parent’s `@records`, so it gets `after_rollback` at the outer `ROLLBACK`, not `after_commit`. The savepoint release does not freeze a commit callback.

**Destroy of a newly created record.** Never-persisted `destroy` does not set `@_trigger_destroy_callback` (`persisted?` is already false). [`trigger_transactional_callbacks?`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L449-L451) is false. [`test_no_after_commit_on_destroy_after_transaction_commits_for_destroyed_new_record`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L207-L211) asserts empty history: no `after_commit`, no `on: :destroy`, no `on: :create`. Create-then-destroy of the same instance in one open transaction is different: the create made it persisted, destroy sets `@_trigger_destroy_callback`, `persisted?` is then false, so only `:destroy` matches. Unfiltered `after_commit` / `after_destroy_commit` run; `after_create_commit` does not.

**Multiple in-memory instances of the same row.** Enrollment is per instance (`uniq(&:__id__)`). Callback selection hashes by [`ActiveRecord::Core#==` / `#hash`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L645-L665) (class + id), so those instances collapse to one candidate in [`prepare_instances_to_run_callbacks_on`](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L361-L381). Only that candidate’s `__id__` gets `should_run_callbacks: true`; the others get `committed!(should_run_callbacks: false)`.

Default in the gem: [`run_commit_callbacks_on_first_saved_instances_in_transaction`](file:///home/user/workspace/repo/activerecord/lib/active_record/core.rb#L97) is true — first enrolled instance wins. Rails 7.1+ sets it false ([configuration](file:///home/user/workspace/repo/railties/lib/rails/application/configuration.rb#L283)): last instance wins, except a destroyed candidate is not replaced by a later updater, and `_new_record_before_last_commit` is copied onto the winner so a create on instance A plus update on instance B still fires `after_create_commit` with B’s attributes ([tests](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L912-L1024)). Distinct rows that happen to share `object_id` still both run, because uniqueness is `__id__` ([L504-L521](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L504-L521)).

## Callback order at the outer boundary

On commit, for the chosen instance: `before_commit` (definition order), SQL `COMMIT`, then `after_commit` filters.

Gem default [`run_after_transaction_callbacks_in_order_defined = false`](file:///home/user/workspace/repo/activerecord/lib/active_record.rb#L393-L394): `after_*` run reverse of definition. Rails 7.1 flips it to true by inverting `prepend` in [`enforced_prepend_option`](file:///home/user/workspace/repo/activerecord/lib/active_record/transactions.rb#L357-L363). [`CallbackOrderTest`](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L695-L741) is the oracle:

- true, create: `[1, 2, "prepend 2", "prepend 1", 3, 4, "save", "create"]`
- true, update: same with `"update"` instead of `"create"`
- true, destroy: `[1, 2, "prepend 2", "prepend 1", 3, 4, "destroy"]` — no save/create/update
- rollback: only `"rollback1", "rollback2"` (or reversed if the flag is false). No `before_commit`, no `after_commit`.

`on: [:create, :update]` / `[:create, :destroy]` / `[:update, :destroy]` fire when *any* listed action matches, in definition order under the 7.1 flag ([L614-L627](file:///home/user/workspace/repo/activerecord/test/cases/transaction_callbacks_test.rb#L614-L627)). A create therefore shows `:create_and_update` and `:create_and_destroy`, not `:update_and_destroy`.

Transaction-object callbacks ([`ActiveRecord::Transaction#after_commit`](file:///home/user/workspace/repo/activerecord/lib/active_record/transaction.rb#L85-L105)) are a separate list on the adapter `Transaction`. They follow the same parent-transfer / savepoint-rollback rules, then run after the record callbacks on that transaction.
