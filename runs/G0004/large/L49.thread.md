- After a successful load, a later `execute_unless_loaded` does not draw again.
- The reloader uses `config.file_watcher`.
- In development, changing `config/routes.rb` or a drawn `config/routes/*.rb` file is picked up on a later request (happy path).
- Application and engine route files are registered on the same application reloader, including external draw directories.

Inferred from source, **not** covered by tests or a live reproduction:
- A reload clears every registered route set before loading files; a mid-load error does not put the previous routes back.
- After a failed reload of routes that had already loaded, the next request may not retry under default `config.reload_classes_only_on_change = true`, because the watcher already consumed that change.
- Under `reload_classes_only_on_change = false`, every request re-runs reload, so the error (or a later fix) is more likely to be attempted again.
- Development first-draw is often deferred until the first request.

Those inferred points are the uncertainty the brief is about, not accepted product rules.

---

**Actors:** An application developer in development, and a developer of a mounted engine whose routes participate in that application’s reload.

**Pain:** After one invalid route file, they cannot tell from the running app whether old routes still work, whether routing is simply gone, or when a saved correction will be used.

**Desired observable outcomes**
- After a successful boot or reload, requests use the routes from the current files.
- After an erroring reload, the developer can tell that the new files did not take effect, and is not left to infer that from a silent 404, a stale success, or an error that appears once and then vanishes.
- After they correct the file, they can tell when the correction is in effect, without an unexplained extra edit or restart.
- Application and engine files, and external draw files, are one reload as far as the developer can see: a failure in one is a failed routing reload, not an unexplained mix of old and new sets.
- Deleting a watched route file is a real change, with the same visibility rules as an invalid edit.
- Both `config.reload_classes_only_on_change` values remain understandable: true still means “reload when watched files change”; false still means “reload on the request cycle even without a detected change.” Neither mode should strand a failed or corrected routes file.

**Non-goals**
- No intended change to successful reload, production with reloading off, or how developers write routes.
- No requirement to keep previous routes working after a failed reload, and no requirement to drop them — that choice is still open.
- No change to the watcher API contract, and no expansion into class/i18n reload generally.
- No prescribed implementation, internal bookkeeping, or test design.

**Scope boundary (required technical target, not a design):** Completion is judged at `Rails::Application::RoutesReloader` exposed as `app.routes_reloader`, the route sets registered with it, the external draw paths it watches, and `config.file_watcher` as the change detector. Custom watchers that conform to the existing watcher API are in that boundary.

---

**Acceptance examples** (required cases for the work; “observe” means the HTTP response, exception page, or equivalent console/reload result — not an internal flag)

1. **Initial boot, valid files.** Development app with application and mounted-engine route files. First request uses those routes, including anything drawn from `config/routes`.

2. **Initial boot, invalid Ruby.** Same setup, one route file is invalid before the first draw. The first request (or first forced reload) shows a load failure for that file. The developer can tell routes from that draw are not in effect. A later request, with the file still invalid, does not quietly look like a successful empty or stale routing table.

3. **Syntax/erroring reload after a good load.** App has been answering with the last good routes. Developer saves invalid Ruby in the application `config/routes.rb`, an engine `config/routes.rb`, or a drawn external file. The request that picks up that change shows that routing reload failed. It is visible that this is not “the old routes still work as before,” unless that preservation is later chosen as the rule.

4. **The next request, file still invalid.** Without another save, the following request does not leave the developer guessing. Either the same load failure remains visible, or — if previous routes are defined as still usable — those previous routes remain visible and are clearly the last good set. What must not happen: one erroring request, then unexplained empty/404 or unexplained old success, with no signal that routing reload is still failed.

5. **Correction.** Developer saves valid Ruby that defines a new recognizable route. The next request that is supposed to see file changes uses the corrected routes (application, engine, and external draw files together). They do not need a second dummy edit or a process restart unless the chosen `reload_classes_only_on_change` mode is documented to require a full reload cycle they can observe.

6. **Simultaneous application and engine changes.** In one interval, both the application and a mounted engine route file change; one of them is invalid. The developer observes a single failed routing reload, not a mix where one set updated and the other did not. After both files are valid, the next qualifying request uses both new files.

7. **Deleted route file.** A watched `config/routes.rb` or a drawn external file is deleted. That is treated as a change. The next qualifying request either fails in a way that names the missing file, or — if remaining files are enough — uses only what still exists. It does not keep serving the deleted file’s routes with no signal.

8. **`config.reload_classes_only_on_change = true` (default).** With no other watched files changing: an erroring routes edit is detected; a later correction of that same file is detected; the developer is not stuck after the failed attempt as if “nothing changed.”

9. **`config.reload_classes_only_on_change = false`.** Requests keep attempting routing reload even without a new file change. An invalid file keeps failing in an observable way; a correction appears on a subsequent request without needing an extra file touch.

---

**Open behavioral questions** (these would change the outcome if answered)
- After a failed reload, should the last good routes keep answering, or should routing be unusable until a successful reload? The report only says developers cannot tell.
- Should later requests keep showing the original load error until a successful reload, or is a distinct “routes are not loaded” result enough?
- Does “next request after correction” mean the immediate next HTTP request, or is a console `reload!` / process restart an acceptable extra step in either config mode?
- Are runtime errors inside the draw (not just syntax) the same visibility problem?
- Are undrawn new files under `config/routes` in scope, or only files already drawn plus `config/routes.rb`?
- Must `rails/info/routes` and URL helpers match the request-time picture, or is the HTTP request the source of truth?
- Is an evented watcher allowed to differ in timing from the polling watcher, as long as both eventually show the same outcomes?

**Evidence to collect before treating inferred failure-path claims as facts**
- Live development app: valid load → invalid save → the erroring request → the next request with no further save → valid save → the next request. Repeat for application file, engine file, and a drawn external file.
- The same sequence with `reload_classes_only_on_change` true and false, and with the configured `file_watcher` (default and evented).
- What the client actually sees each time (exception page, 404, old body, new body), plus `bin/rails routes` / `/rails/info/routes` if those are considered developer-facing.
- Simultaneous app+engine edits, and delete of `config/routes.rb` vs delete of a drawn external file.
- First request when the file is already invalid at boot (lazy first draw) versus an error after a successful draw.

I treated “developers should not have to guess” as the outcome, and left “keep old routes” vs “fail until fixed” open. If you want one of those as the rule, that changes examples 3–5.
