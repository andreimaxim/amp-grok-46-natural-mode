## Product shaping brief: safer `with_lock` when a custom lock and transaction options are both needed

### Problem frame

An application developer already has a persisted Active Record object and needs a short critical section: start a database transaction, take a row lock, work on the fresh row, then commit or roll back.

That often requires two kinds of control at once:

- a **lock clause** (default exclusive lock, no extra lock, or a database-specific clause such as share / nowait)
- **transaction options** (start a nested transaction, whether later work may join it, isolation)

Today those two concerns are already reachable from one `with_lock` call, but the call is easy to get wrong and failures are adapter-specific. A mistaken argument can lock the wrong way, join the wrong transaction, or fail only on some databases. Dirty in-memory state, a row deleted before reload, write-prevention mode, and nested isolation all fail in different ways. Developers fall back to a manual `transaction` plus `lock!`, which is easy to omit or nest incorrectly.

**Why it matters:** a lock that does not actually lock, a nested section that joins the outer transaction, or an isolation request that is silently invalid can corrupt concurrent updates. The failure is often visible only under load or on one adapter.

### Current observable baseline

Evidence: [pessimistic locking](file:///home/user/workspace/repo/activerecord/lib/active_record/locking/pessimistic.rb), [reload](file:///home/user/workspace/repo/activerecord/lib/active_record/persistence.rb), [transactions](file:///home/user/workspace/repo/activerecord/lib/active_record/connection_adapters/abstract/database_statements.rb), [locking tests](file:///home/user/workspace/repo/activerecord/test/cases/locking_test.rb), [isolation tests](file:///home/user/workspace/repo/activerecord/test/cases/transaction_isolation_test.rb), [querying guide](file:///home/user/workspace/repo/guides/source/active_record_querying.md). Tests were read, not executed.

**What `with_lock` does today**

- Wraps the block in a transaction, reloads the persisted record with the requested lock, then yields. The block receives the current transaction object (changelog + PostgreSQL test).
- With no lock argument, PostgreSQL issues a `FOR UPDATE` reload. That is the documented default exclusive row lock.
- A custom SQL fragment is appended to the reload `SELECT`. PostgreSQL tests this on `lock!("FOR SHARE NOWAIT")`, not on `with_lock` itself.
- `false` as the lock value is treated as “no locking clause” by the relation lock API; reload then finds the row without `FOR UPDATE`. **No `with_lock(false)` test.** Inferred from `lock!` → `reload(lock:)` → `find_by!`.
- Keyword options go to the wrapping transaction: `requires_new`, `joinable`, `isolation`. Tested: `requires_new: true, joinable: false` starts a distinct nested transaction that is not joinable. Isolation is tested only on PostgreSQL (`isolation: :read_uncommitted`).
- Successful work is committed; an exception rolls the `with_lock` transaction back (both tested).
- A persisted record with unsaved changes cannot be locked: `lock!` raises a runtime error naming the changed attributes. **Tested on `lock!` only.**
- Reload uses a bang finder. If the row is gone, the caller sees `ActiveRecord::RecordNotFound` and the transaction does not yield the block. **No `with_lock` test.**
- While writes are prevented, locking raises `ActiveRecord::ReadOnlyError` (`"Lock query attempted while in readonly mode"`), for default and custom clauses. Nested `while_preventing_writes(false)` allows locking again.

**Adapter differences users already observe**

Lock clauses:

- PostgreSQL: `FOR UPDATE`, `FOR SHARE NOWAIT`, and similar fragments appear in SQL. `SELECT ... FOR UPDATE` on an outer join is rejected (eager `lock` test skipped on PostgreSQL).
- MySQL: docs use `LOCK IN SHARE MODE` / `FOR UPDATE NOWAIT`. Unsupported SQL surfaces as `ActiveRecord::StatementInvalid` (guide warning). Not covered by `with_lock` tests.
- SQLite: the write-prevention suite uses `"FOR UPDATE"` as a custom clause and comments it as a no-op. Whether SQLite actually locks is an open question.

Isolation:

- mysql2, trilogy, and PostgreSQL can set isolation (`:read_uncommitted`, `:read_committed`, `:repeatable_read`, `:serializable`).
- SQLite only supports `:read_uncommitted`, and only with shared-cache mode; other levels raise `ActiveRecord::TransactionIsolationError` (`"SQLite3 only supports the \`read_uncommitted\` transaction isolation level"`). Shared-cache off raises a generic error about enabling shared-cache.
- Adapters that cannot set isolation raise `TransactionIsolationError` (`"adapter does not support setting transaction isolation"`).
- Isolation cannot be changed when joining an open transaction (`"cannot set isolation when joining a transaction"`) or when opening a nested/savepoint transaction (`"cannot set transaction isolation in a nested transaction"`).
- An invalid isolation name raises `TransactionIsolationError` (`"invalid transaction isolation level: ..."`).

**What is not jointly demonstrated**

Passing a **custom lock clause and transaction options in one `with_lock` call** is described in docs and Rails 7 notes, but locking tests never combine them. How argument mix-ups present to the user (wrong SQL vs wrong transaction vs a Ruby error) is therefore not established.

### Desired outcomes

When this work is done, a developer who needs a locked critical section can:

1. **State lock intent and transaction intent together** without dropping into a separate `transaction` / `lock!` pair, including default exclusive lock, no extra lock clause, and a custom clause.
2. **See the same transaction semantics as a normal Active Record transaction:** commit on success, rollback on exception, optional nested/non-joinable wrapping, optional isolation where the adapter allows it, and access to the transaction object for after-commit/after-rollback callbacks.
3. **Be stopped before losing work or locking stale in-memory state** when the persisted record has unsaved changes.
4. **Get a clear, existing-style failure** when the row disappears before the locked reload, when locking is attempted in write-prevention mode, or when the database/adapter cannot honor the requested clause or isolation — not a silent weaker lock or a silent join.
5. **Keep current successful paths working** for default `with_lock`, custom clauses that the database accepts, and transaction options that `transaction` already honors.

These are behavioral claims, not an API shape. How callers spell the lock vs the options remains open.

### Non-goals

- Changing optimistic locking, relation-level `lock`, or `find`/`lock` query chains, except insofar as `with_lock` still reloads through that existing lock/reload behavior.
- Inventing a portable lock dialect or hiding that clauses are database SQL.
- Making every adapter support every clause or isolation level.
- Changing write-prevention policy (locking remains a write-mode operation).
- Prescribing method signatures, argument order, keyword names, or internal control flow.
- Broader transaction redesign (`after_commit` timing relative to outer transactions, savepoint semantics) beyond what `with_lock` already inherits.

### Risks and steering evidence

| If we observe… | It suggests… | Then… |
| --- | --- | --- |
| Callers still wrap `transaction` + `lock!` to combine a clause with `requires_new` / isolation | The combined call is still unclear or untrusted | Revisit the outcome, not just docs |

### Acceptance examples

Required cases unless marked illustrative. Results are what the application developer observes, not how the method is written.

#### 1. Default lock

**Situation:** A persisted person exists; no lock argument is given.

**When:** The developer enters `with_lock` and reads/updates the record in the block.

**Then:** Work runs inside a transaction. The row is reloaded with the adapter’s default exclusive lock (PostgreSQL: SQL includes `FOR UPDATE`). After the block, the lock is released with the transaction.

#### 2. No extra lock clause (`false`)

**Situation:** Same persisted person. The developer asks for no locking clause.

**When:** They enter `with_lock` with a false lock intent and change an attribute.

**Then:** A transaction still wraps the block and the record is reloaded from the database, but the reload SQL does not add `FOR UPDATE` / a custom fragment. Unsaved in-memory edits from before the call are still refused (same dirty-record rule as a real lock).

*Baseline note:* `with_lock(false)` is not tested; this is the intended reading of `lock!(false)` plus reload.

#### 3. Custom clause

**Situation:** PostgreSQL. The developer needs a non-default clause (e.g. `FOR SHARE NOWAIT`).

**When:** They pass that clause into `with_lock` (alone or with transaction options).

**Then:** The locked reload SQL includes that fragment. If another session already holds a conflicting lock, they observe the database’s usual error (e.g. lock not available), not a hung default `FOR UPDATE`.

**Counterexample (MySQL / other):** A PostgreSQL-only fragment or a MySQL `LOCK IN SHARE MODE` on a database that does not accept it fails the reload with `ActiveRecord::StatementInvalid` (or the adapter’s wrapped database error). The block does not run as if the row were locked.

**SQLite:** Whether `"FOR UPDATE"` or `"FOR SHARE"` has any locking effect is **open**. Callers must not assume a portable lock.

#### 4. Dirty persisted record

**Situation:** Person is persisted; `first_name` is changed in memory and not saved.

**When:** They call `with_lock` (any lock intent).

**Then:** Locking is refused. They see an error that names the changed attributes and tells them to save or reload. The unsaved value is still in memory; the database row is unchanged. The block does not run.

#### 5. Commit

**Situation:** Clean persisted person.

**When:** Inside `with_lock` they assign `first_name` and save, then the block ends normally.

**Then:** A later reload shows the new name. The transaction has committed.

#### 6. Exception rollback

**Situation:** Same, but the block saves and then raises.

**When:** The exception propagates out of `with_lock`.

**Then:** A later reload shows the original name. The in-block save is not visible in the database.

#### 7. Yielding the transaction object

**Situation:** Clean persisted person.

**When:** The block takes a parameter.

**Then:** That object is the current transaction for this `with_lock` (same object `current_transaction` would report inside the block). They can register `after_commit` / `after_rollback` on it. Callbacks run according to existing transaction rules (outermost commit), not a new callback model.

*Tested on PostgreSQL only.*

#### 8. `requires_new`, `joinable`, and isolation

**`requires_new` + `joinable`**

**Situation:** Already inside a joinable transaction.

**When:** They call `with_lock` asking for a new, non-joinable transaction.

**Then:** The block runs in a different transaction than the outer one, and that inner transaction is not joinable. An exception in the inner block rolls back inner work without depending on a later outer rollback. Isolation is **not** set in this nested case unless the product later says otherwise; today nested isolation raises (see nesting).

**Isolation**

**Situation:** PostgreSQL (or mysql2/trilogy), no conflicting open transaction.

**When:** They call `with_lock` with `isolation: :read_uncommitted` (or another supported level).

**Then:** The wrapping transaction’s isolation is that level.

**Unsupported isolation (required observation):**

- Adapter cannot set isolation → `ActiveRecord::TransactionIsolationError`, message that the adapter does not support setting isolation. Block does not run as an isolated transaction.
- SQLite + level other than `:read_uncommitted` → `TransactionIsolationError` stating only `read_uncommitted` is supported.
- SQLite + `:read_uncommitted` without shared-cache → error telling them to enable shared-cache.
- Invalid level name → `TransactionIsolationError` naming the invalid level.
- Isolation requested while joining an existing transaction with a different isolation → `TransactionIsolationError` (`cannot set isolation when joining a transaction`).

#### 9. Nesting

**Situation:** Outer `with_lock` or `transaction` is open; inner `with_lock` is called.

**When:** Inner call does **not** ask for a new transaction.

**Then:** It joins the open joinable transaction; the row lock is taken inside that same transaction. Isolation cannot be changed; attempting to set it is observed as `TransactionIsolationError`.

**When:** Inner call asks for `requires_new`.

**Then:** Inner work is a nested (savepoint) transaction. Setting isolation on that nested transaction is observed as `TransactionIsolationError` (`cannot set transaction isolation in a nested transaction`). Custom lock clauses still apply to the inner reload if the database accepts them.

#### 10. Missing row during reload

**Situation:** The in-memory record is persisted, but the row has been deleted (or is otherwise unfindable) before `with_lock` reloads it.

**When:** They call `with_lock`.

**Then:** They observe `ActiveRecord::RecordNotFound`. The block does not run. No lock is held for that id. Any wrapping `with_lock` transaction does not commit as if the lock succeeded.

*Inferred from reload’s bang finder; not a `with_lock` test.*

#### 11. Write-prevention mode

**Situation:** `ActiveRecord::Base.while_preventing_writes` is in effect.

**When:** They call `with_lock` with the default lock or a custom clause.

**Then:** They observe `ActiveRecord::ReadOnlyError` (`Lock query attempted while in readonly mode`). The block does not run.

**When:** Inside that, they nest `while_preventing_writes(false)` and call `with_lock`.

**Then:** Locking proceeds as when writes are allowed.

### Open questions

Leave these unresolved until product owners choose; do not fill them in from implementation taste.

1. **Combined-call spelling.** Docs imply a lock value plus transaction options in one call, but tests never combine them. What mix-up (hash as lock, options swallowed as SQL, `false` vs “no options”) do we still need to make impossible? Unknown without caller evidence.
2. **`false` lock.** Should “no clause” still reload inside a transaction, or is that a footgun? Current code reloads; users may think `false` skips locking *and* the transaction.
3. **SQLite lock clauses.** Is a no-op `FOR UPDATE` acceptable, or must SQLite users see an explicit “this adapter does not take row locks” failure?
4. **Error family for dirty records.** Today this is a runtime error, not `ActiveRecordError`. Changing the class would be user-visible; whether that is in scope is open.
5. **Missing-row vs outer transaction.** If `with_lock` is nested and the inner reload raises `RecordNotFound`, should that abort only the inner section or the whole outer transaction? Inherited transaction rules vs a dedicated outcome is unspecified.
6. **Portable “share / nowait / skip locked” intent.** Some apps want that meaning without raw SQL. No evidence this brief must provide a portable vocabulary; treating SQL as adapter-specific remains valid.
7. **MySQL/Trilogy isolation through `with_lock`.** Isolation is tested on `transaction` broadly and on `with_lock` only for PostgreSQL. Whether `with_lock` isolation must be demonstrated on MySQL is a coverage choice, not a known behavioral gap.

### Working model (for correction)

The user is an application developer who must lock one already-loaded row and control the surrounding transaction in the same step. Today that is possible but uneven: default lock, commit/rollback, some transaction options, and write-prevention are observable; custom clause plus options, `false`, missing rows, and non-PostgreSQL isolation/clauses are thinly specified and fail differently per adapter. Success is a combined locked section that keeps current safety rails (dirty records, read-only mode, real adapter errors) and never pretends an unsupported clause or isolation was applied.

This is a shaping brief, not an implementation plan: no signature, no control-flow prescription, no code change.

If the problem is really “document the existing combined call” rather than “change what callers can safely observe,” say so — that would shrink this to docs and examples, not behavior change.
