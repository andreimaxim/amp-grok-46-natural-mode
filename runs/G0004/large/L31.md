Discovery used Action Controller and Active Support source plus test assertions (not a live test run): callback terminator and `performed?`, render/redirect/`head`/`DoubleRenderError`, halt log/event, and the filter examples below.

**Problem frame:** App authors and Rails maintainers need to tell whether a request stopped because a callback intentionally performed a response, or because control flow was misunderstood. Today a `before_action` that renders or redirects skips the action and `after_action`s, while `render`/`redirect_to`/`head` do not return from the current method. The only dedicated halt signal names the filter and always says it “rendered or redirected.” A non-yielding `around_action` can skip the same inner work without that signal. That mix makes intentional denial (auth redirect) look like a skipped action, missed cleanup, or a pending `DoubleRenderError`.

**Affected actors:** Application authors writing or debugging callback chains; framework maintainers reproducing “action never ran” / “after never ran”; operators reading request logs or events.

**Current observable baseline**

- After each `before_action`, the process-action terminator treats `performed?` as halt. In Action Controller, `performed?` is true when a response body is set or the response is committed. `render`, `redirect_to`, and `head` all set a body (redirect/`head` use an empty body).
- Halt skips later `before_action`s, the action, and `after_action`s, including prepended afters (`skip_after_callbacks_if_terminated`).
- `render` / `redirect_to` / `head` do not stop the current Ruby method. Remaining lines in that callback still run. A second perform in that same method raises `AbstractController::DoubleRenderError` (message: only one render or redirect per action; neither terminates execution; use `return` if you want to exit).
- Existing halt feedback, only when a **before** callback makes `performed?` true: log `Filter chain halted as :filter rendered or redirected`; notification `halted_callback.action_controller` with `filter`; structured event `action_controller.callback_halted` with `filter`. Payload is the filter, not render vs redirect vs `head`, not skipped later callbacks, not “same-method continued after perform.”
- A non-yielding `around_action` skips nested befores, the action, and afters **without** that halt signal and without requiring `performed?`.
- Exceptions in an `around_action` before or after `yield` propagate; they are not this terminator. A rescuing around can still perform a response after catching.
- `:only` / `:except` / `:if` / `:unless` that fail mean the callback does not run; no halt from that callback; the action runs if nothing else performed.
- Implicit render runs only if the action path ran and `performed?` is still false.

**Desired outcomes** (observability of existing halt behavior, not a new halt rule)

1. A person debugging a request can tell **intentional halt after a callback performed a response** from **confusing control flow** (method continued after render/redirect; around never yielded; exception; callback skipped by condition).
2. For a performing `before_action`, they can still observe that the performed response is what the client got, and that the action and afters did not run.
3. Boundary cases below remain distinguishable from that halt, including `DoubleRenderError` on a second perform in the same method.

**Non-goals**

- Changing when the chain halts, what `performed?` means, or when `DoubleRenderError` is raised.
- Requiring any particular new log, notification, API, metric, or UI.
- Making around-not-yielding, exceptions, or conditionals behave like `performed?` halt.
- Exhaustive catalog of every callback option.

**Behavioral examples** (required for this discussion)

*Rendering before callback.* `before_action` renders a body; action would render something else; `after_action` would record that it ran. **Observe:** client body is the before’s; action did not run; after did not run; existing halt signal may name that before as “rendered or redirected.”

*Redirecting before callback.* Same shape with `redirect_to`. **Observe:** redirect response; action/afters skipped; halt signal uses the same “rendered or redirected” wording. A later `head` in a before chain is the same `performed?` halt (empty body, non-success status in the multi-before tests).

*Non-yielding around callback.* `before_action` A runs; `around_action` does not `yield`; later before, action, and after would run if yielded. **Observe:** A and the around ran; later before/action/after did not; no exception; **no** before-halt “rendered or redirected” signal unless something also performed. If the around also never performed, this is a skip without a performed response.

*Exception before yield.* `around_action` raises before `yield`. **Observe:** exception propagates; action did not run; this is not terminator halt. *Exception after yield.* Around yields, action runs (and may render), then around raises. **Observe:** exception after the action ran; not a `performed?` halt. *Rescuing around* may catch and render; client sees that body without a before-halt signal from the around itself.

*Conditional callbacks.* `before_action` with `:except` / `:only` (or `:if` / `:unless`) does not apply to this action. **Observe:** that callback does not run; no halt from it; action runs. On an action the condition includes, a performing before still halts as in the first examples.

*Action attempts a second render.* Action (or a callback that has not returned yet) renders or redirects, then renders/`head`s again. **Observe:** `DoubleRenderError`, not a quiet halt. Contrast: a single perform in a `before_action` that then returns is a successful halt, not an error—even though the action never runs.

**Steering evidence** (external signals that could distinguish intentional halt from confusing control flow—without requiring a specific mechanism)

Success-shaped observations, if observability is actually clearer:

- For an auth-style before redirect/render, a debugger can answer: which callback performed, that halt was due to a performed response, that the action and afters were skipped **because of that**, and that this was not `DoubleRenderError` and not an around that never yielded.
- For a method that performs then continues, they can see continuation in the same callback as distinct from chain halt after that callback returns.
- For around-not-yielding vs before-performed vs exception vs conditional skip, those four remain separable from the outside (response, exception, presence/absence of halt-as-performed, whether the action ran).

Investigate or reconsider the framing if:

- People still cannot tell a skipped action from a performed before without reading controller source.
- Any added signal aliases around-not-yielding, exceptions, or conditionals as “rendered or redirected.”
- Noise from intentional halts (login redirect on most requests) drowns the cases that are actually confusing.
- Authors start treating halt visibility as a substitute for `return` after render/redirect, or expect afters to run after a performing before.

**Open product questions**

- Is the pain mainly **same-method continuation** after render/redirect, **silent around-not-yielding**, **afters not running**, or the **generic halt wording**?
- Must around-not-yielding stay out of “performed response” observability, or do maintainers want it in the same story as a *different* kind of stop?
- Is today’s filter-only “rendered or redirected” line enough in development and too little in production, or the reverse?
- Does distinguishing render vs redirect vs `head` vs assigning a committed response matter, or only “performed vs not”?
- Should skipped later callbacks be visible, or only the callback that performed?
- Any compatibility expectation around the existing log sentence and `filter`-only payload?

This is a draft for maintainers, not a decision to add instrumentation. If the problem is really “halt rules are surprising” rather than “halt is hard to see,” the outcome should shift from observability to teaching or behavior change—and that is a different brief.
