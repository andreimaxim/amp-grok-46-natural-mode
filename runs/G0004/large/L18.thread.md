## Evolution of `Relation#ids`

### 1. Originally: direct delegation to `pluck`

Before Rails 7.1, `ids` was effectively:

```ruby
def ids
  pluck primary_key
end
```

That meant `ids` inherited `pluck`’s include-handling. When `includes` became a join dependency, a one-to-many association produced one parent ID per joined child row.

Issue [#46455](https://github.com/rails/rails/issues/46455) demonstrated:

> “A post ID is returned 5 times if the post has 5 comments.”

The important distinction was intentional: ordinary joins may still return duplicate IDs, but includes/eager-loading should match materialized parent records, which Active Record deduplicates.

---

### 2. PR #46503: split `ids` from `pluck` to prevent duplicate parent IDs

PR [#46503](https://github.com/rails/rails/pull/46503), merged as [`4435b7a`](https://github.com/rails/rails/commit/4435b7afe3bf3f2d0f2f3b77aedd44d93219be18), introduced a separate implementation. Its operative commit was [`8fd3369`](https://github.com/rails/rails/commit/8fd336927a5d7519adac4361c47aa09a295bfe3d).

The PR explains the intent:

> “only return the unique ids of the base model, ignoring the join on eager loaded, preloaded and included associations.”

Rather than call `pluck`, the implementation directly selected the primary key:

```ruby
columns = arel_columns([primary_key])
relation = spawn
relation.select_values = columns
```

See [`calculations.rb`](https://github.com/rails/rails/blob/8fd336927a5d7519adac4361c47aa09a295bfe3d/activerecord/lib/active_record/relation/calculations.rb#L320-L350).

The changelog made the desired behavior explicit:

```ruby
Post.includes(:comments).where(id: 1).pluck(:id)
# => [1, 1, 1, 1, 1]

Post.includes(:comments).where(id: 1).ids
# => [1]
```

See [`CHANGELOG.md`](https://github.com/rails/rails/blob/8fd336927a5d7519adac4361c47aa09a295bfe3d/activerecord/CHANGELOG.md#L1-L16).

Tests covered all loading forms:

```ruby

  company = Company.first
  5.times { company.contracts.create! }
  assert_equal Company.all.map(&:id).sort,
    Company.all.eager_load(:contracts).ids.sort

def test_ids_with_preload
  ...

```

See [`calculations_test.rb`](https://github.com/rails/rails/blob/8fd336927a5d7519adac4361c47aa09a295bfe3d/activerecord/test/cases/calculations_test.rb#L968-L996).

---

### 3. PR #46697: explicit include/join dependency plus `DISTINCT`

Follow-up commit [`0c16feb`](https://github.com/rails/rails/commit/0c16feb4bc53526b004c76f6db99b93f1a53f02d), from PR [#46697](https://github.com/rails/rails/pull/46697), added the recognizable special case:

```ruby
if has_include?(primary_key)
  relation = apply_join_dependency.distinct
  return relation.ids
end
```

See [`calculations.rb`](https://github.com/rails/rails/blob/0c16feb4bc53526b004c76f6db99b93f1a53f02d/activerecord/lib/active_record/relation/calculations.rb#L327-L335).

This is where database-side deduplication became explicit. It applied only when the requested primary-key projection caused include/eager-load processing through `has_include?`; plain `joins` retained normal SQL multiplicity.

The follow-up tests distinguished those paths and covered associated-table predicates:

### 5. PR #48101: replace `DISTINCT` with `GROUP BY primary_key`

The `DISTINCT` solution failed on PostgreSQL and MySQL when ordering by a non-selected, non-primary-key column. Issue [#48080](https://github.com/rails/rails/issues/48080) reported:

```ruby
Post.order(:created_at).includes(:comments).ids
```

raising:

```text
PG::InvalidColumnReference:
for SELECT DISTINCT, ORDER BY expressions must appear in select list
```

PR [#48101](https://github.com/rails/rails/pull/48101), merged as [`6cee834`](https://github.com/rails/rails/commit/6cee8343f1dc37997dd66a04be84574505c3df59), with implementation commit [`e856d7f`](https://github.com/rails/rails/commit/e856d7f1a24741c5295c9e562ffaf7ee0fce6680), changed:

```ruby
relation = apply_join_dependency.distinct
```

to:

```ruby
primary_key_array = Array(primary_key)

if has_include?(primary_key)
  relation = apply_join_dependency.group(*primary_key_array)
  return relation.ids
end
```

See [`calculations.rb`](https://github.com/rails/rails/blob/e856d7f1a24741c5295c9e562ffaf7ee0fce6680/activerecord/lib/active_record/relation/calculations.rb#L325-L347).

The PR rationale was:

> “use `#group` over `#distinct` to avoid having a `DISTINCT` that would be incompatible with the selected columns.”

It also noted that adding ordering columns to `SELECT` was inappropriate because `ids` should select only primary keys.

The regression test was:

```ruby
def test_ids_with_includes_and_non_primary_key_order
  rating = 1
  Company.all.each { |company| company.update!(rating: rating += 1) }

  assert_equal Company.all.sort_by(&:rating).map(&:id),
    Company.includes(:comments).order(:rating).ids
end
```

See [`calculations_test.rb`](https://github.com/rails/rails/blob/e856d7f1a24741c5295c9e562ffaf7ee0fce6680/activerecord/test/cases/calculations_test.rb#L1049-L1055).

Thus, `GROUP BY primary_key` serves two purposes:

1. Deduplicate parent rows created by the eager-load join.
2. Preserve `ORDER BY non_primary_column` compatibility that `SELECT DISTINCT primary_key` lacks on PostgreSQL/MySQL.

---

### 6. Current simplification: delegate everything else back to `pluck`

Commit [`56c95ae`](https://github.com/rails/rails/commit/56c95aee03ec642b37abd1c7e42964ae89bc6670) deliberately restored delegation while retaining that one semantic exception:

```ruby
def ids
  if !loaded? && has_include?(primary_key)
    return apply_join_dependency.group(*primary_key).pluck(*primary_key)
  end

  pluck(*primary_key)
end
```

See [`calculations.rb`](https://github.com/rails/rails/blob/56c95aee03ec642b37abd1c7e42964ae89bc6670/activerecord/lib/active_record/relation/calculations.rb#L373-L381).

Its commit message summarizes the history:

> “Before #46503, `ids` was implemented simply as `pluck(primary_key)`.”

> “The only piece that genuinely needs custom handling is the deduplication when `has_include?(primary_key)` is true (the original #46503 fix).”

It also records why broad duplication between `ids` and `pluck` was undesirable: fixes had drifted between them, including composite keys and null relations.

## Conclusion

Replacing the method unconditionally with:

```ruby
pluck(*primary_key)
```

would revert the behavior fixed by #46503/#46697: an unloaded `includes` or `eager_load` relation whose join has multiple child rows can return duplicate parent IDs.

The grouping branch is not general-purpose `ids` machinery. It is the narrowly retained eager-load semantic:

```ruby
if !loaded? && has_include?(primary_key)
  apply_join_dependency
    .group(*primary_key)
    .pluck(*primary_key)
else
  pluck(*primary_key)
end
```

`group(*primary_key)` specifically preserves:

- one ID per base record despite duplicate joined child rows;
- all columns of a composite primary key;
- ordering by non-primary-key columns without the `DISTINCT` database error.
