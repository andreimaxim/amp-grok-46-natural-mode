**Block.** The guard is not a convenience check. Removing it still enqueues the original mailer class, action, and arguments; the generated `Mail::Message` is never serialized. Mutations, parameterized params, and one-time mailer work would be dropped or re-run.

## What `processed?` actually means

[`MessageDelivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb) is a lazy `Delegator` around a `Mail::Message`. Construction stores `@mailer_class`, `@action`, and `@args` and leaves `@processed_mailer` / `@mail_message` nil ([lines 22–29](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L22-L29)).

```48:50:actionmailer/lib/action_mailer/message_delivery.rb
    def processed?
      @processed_mailer || @mail_message
    end
```

`processed?` becomes true when the mailer action has already run. That happens through:

- `#message` → [`#__getobj__`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L33-L35) → [`#processed_mailer`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L136-L140), which does `@mailer_class.new.process(@action, *@args)`
- any delegated `Mail::Message` call (`to`, `subject`, `body`, header writes, …)
- `#deliver_now` / `#deliver_now!`

It is not limited to an explicit `#message` call.

## What is actually serialized

The proposed diff still runs this enqueue:

```153:154:actionmailer/lib/action_mailer/message_delivery.rb
          @mailer_class.delivery_job.set(options).perform_later(
            @mailer_class.name, @action.to_s, delivery_method.to_s, args: @args)
```

Payload is four values: mailer class **name**, action **name**, delivery method **name**, original **args**. Not `@mail_message`.

The job rebuilds mail from those values and then delivers:

```21:28:actionmailer/lib/action_mailer/mail_delivery_job.rb
    def perform(mailer, mail_method, delivery_method, args:, kwargs: nil, params: nil)
      mailer_class = params ? mailer.constantize.with(params) : mailer.constantize
      message = if kwargs
        mailer_class.public_send(mail_method, *args, **kwargs)
      else
        mailer_class.public_send(mail_method, *args)
      end
      message.send(delivery_method)
    end
```

The author’s claim (“the job can serialize the generated `Mail::Message`”) does not match this code. Active Job also has no `Mail::Message` serializer; putting one in `perform_later` would normally raise `ActiveJob::SerializationError`.

The current error text already states the real contract: only mailer method arguments travel with the job ([lines 144–151](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L144-L151)).

## Laziness, `deliver_later` vs `deliver_later!`

Unprocessed `deliver_later` is the intended path: do not run the mailer now; the job runs it later ([base.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/base.rb#L164-L166)).

Both later methods share `enqueue_delivery`:

- [`deliver_later`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L104-L105) → `"deliver_now"`
- [`deliver_later!`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/message_delivery.rb#L77-L78) → `"deliver_now!"`

The bang only changes the method the job will call (`perform_deliveries` / `raise_delivery_errors`). It does not serialize a built message. Tests already pin both argument lists ([test/message_delivery_test.rb:62–71](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L62-L71)).

If you process first and then enqueue, the mailer action runs **now** and **again in the job**. Time-dependent content, I18n, record state, and mailer side effects are not frozen by `#message`.

## Parameterized mailers

[`Parameterized::MessageDelivery#enqueue_delivery`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/parameterized.rb#L144-L151) is a second implementation. Unprocessed mail sends `params:` plus `args:`. Processed mail calls `super`.

Today `super` raises. After this diff, a processed parameterized delivery would enqueue **without** `params:`:

```ruby
# unprocessed
perform_later(name, action, method, params: @params, args: @args)

# processed, after the proposed change
perform_later(name, action, method, args: @args)  # params dropped
```

The job would then do `mailer.constantize` instead of `mailer.constantize.with(params)` ([mail_delivery_job.rb:22](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L21-L22)). `before_action` / `default` headers that read `params` would see `{}`. The proposed diff does not touch this file.

Unprocessed parameterized enqueue is already tested ([parameterized_test.rb:42–52](file:///home/user/workspace/repo/actionmailer/test/parameterized_test.rb#L42-L52)); the processed path is not.

## Custom jobs and queue selection

Enqueue always uses `@mailer_class.delivery_job` ([queued_delivery.rb:8–9](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/queued_delivery.rb#L8-L9)). Custom jobs get the same `(class name, action, delivery method, args:)` tuple ([test:100–106](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L100-L106)). They do not receive a `Mail::Message` unless rewritten.

Default queue comes from `MailDeliveryJob.queue_as`, which does `arguments.first.constantize` then `deliver_later_queue_name` ([mail_delivery_job.rb:14–17](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L14-L17)). That is why first-arg-as-class-name is load-bearing. `deliver_later(queue:)` still works via `.set(options)` ([test:113–116](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L113-L116)). Serializing a message as the first argument would break queue lookup even if serialization succeeded.

[`ActionMailer.deliver_all_later`](file:///home/user/workspace/repo/actionmailer/lib/action_mailer.rb#L88-L100) never consults `processed?` and always builds jobs from class/action/params/args. This PR does not fix that either.

## Observable behavior after mutating before enqueue

```ruby
mail = DelayedMailer.test_message(1, 2, 3)
mail.message.to = ["other@example.com"]
mail.subject = "changed"
mail.body = "changed"
mail.deliver_later
```

**Today:** `RuntimeError` from `enqueue_delivery` ([test:133–139](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L133-L139)).

**With this PR:** enqueue succeeds; the job re-runs `DelayedMailer.test_message(1, 2, 3)` and sends the original to/subject/body from the mailer method. Local edits are silently lost. That is exactly what the current error exists to prevent.

Access without mutation is not a freeze either: the job still regenerates mail later from args, so “I looked at `#message`” is not “this exact object will be sent.”

## Serialization failures vs the no-prior-access path

No-prior-access path is already correct and well tested: `deliver_later` / `deliver_later!`, delay, priority, `wait_until`, per-mailer queue, per-call queue, custom job, kwargs ([message_delivery_test.rb:62–131, 269–273](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L62-L131)). Leave it alone.

Current serialization failures are about **args**, not the message. Unserializable args fail at enqueue. GlobalID args that vanish later become `ActiveJob::DeserializationError`, delegated to the mailer ([test:257–266](file:///home/user/workspace/repo/actionmailer/test/message_delivery_test.rb#L257-L266), [mail_delivery_job.rb:32–45](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/mail_delivery_job.rb#L32-L45)). This PR does not add a message serializer and does not change that path.

## Gaps in the claim and tests

The claim is false on the enqueue line it leaves in place. Tests never assert that a processed message is serialized, that mutations survive, that parameterized `params` survive after `#message`, or that `Mail::Message` is an Active Job argument. The one existing test (`deliver_later after accessing the message is disallowed`) would have to be inverted, and that inversion would encode the bug.

## Smallest viable direction

Keep the `processed?` raise. The workarounds in the error are the real API: don’t touch the message before `#deliver_later`; put header/body changes inside the mailer method so they are reproduced from args/params; or write a custom job that serializes whatever it can actually send.

If enqueue-after-inspect is required, it is not a one-line deletion. You would need a distinct job payload for an already-built message, a `Mail::Message` (or encoded RFC822) serializer, a `perform` path that does not re-run the mailer, parameterized `params` handling, `queue_as` that still finds the mailer class, custom `delivery_job` compatibility, and tests for mutation preservation plus the unprocessed args path. That is a new delivery mode, not a safe removal of this guard.
