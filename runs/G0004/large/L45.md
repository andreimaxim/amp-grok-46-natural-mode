**Request changes.** The one-liner does not implement the claim, and it would put `ActionDispatch::Cookies` on default API-only apps that never opted into sessions.

## What the stack actually does today

In [`railties/lib/rails/application/default_middleware_stack.rb`](file:///home/user/workspace/repo/railties/lib/rails/application/default_middleware_stack.rb#L75-L90):

```75:90:railties/lib/rails/application/default_middleware_stack.rb
          middleware.use ::ActionDispatch::Callbacks
          middleware.use ::ActionDispatch::Cookies unless config.api_only

          if !config.api_only && config.session_store
            if config.force_ssl && config.ssl_options.fetch(:secure_cookies, true) && !config.session_options.key?(:secure)
              config.session_options[:secure] = true
            end
            middleware.use config.session_store, config.session_options
          end

          unless config.api_only
            middleware.use ::ActionDispatch::Flash
            middleware.use ::ActionDispatch::ContentSecurityPolicy::Middleware
            middleware.use ::ActionDispatch::PermissionsPolicy::Middleware if config.permissions_policy
          end
```

Canonical order is Callbacks → Cookies → session store → Flash. Tests lock that in: [`railties/test/commands/middleware_test.rb`](file:///home/user/workspace/repo/railties/test/commands/middleware_test.rb#L22-L145) asserts the full-stack list, the API-only list (no Cookies/session/Flash), and the dependency `Flash → Session::CookieStore → Cookies`.

`config.session_store` is the getter, not `session_store?`. `:disabled` becomes `nil`; a real store is a class. That part of the proposed condition is the right predicate — if it were actually used only as an opt-in.

It is not an opt-in. [`setup_default_session_store`](file:///home/user/workspace/repo/railties/lib/rails/application/finisher.rb#L49-L53) runs for every app, API-only included, and installs `:cookie_store` unless `@session_store` is already set. By the time `build_stack` runs, default API-only apps already have a truthy `config.session_store` even though session middleware is omitted.

## Case-by-case

**Default full-stack.** `!config.api_only` is true, so Cookies stay. No change.

**Default API-only.** Today: no Cookies, no session, no Flash ([`middleware_test.rb` api stack](file:///home/user/workspace/repo/railties/test/commands/middleware_test.rb#L93-L114)). After the patch: `!true || CookieStore` inserts Cookies after Callbacks, still no session/Flash. That is a behavior change for every `config.api_only = true` app, including the generated template that only sets `config.api_only` ([`application.rb.tt`](file:///home/user/workspace/repo/railties/lib/rails/generators/rails/app/templates/config/application.rb.tt#L29-L35)).

**Explicit `config.session_store :cookie_store` in an API app.** Cookies would appear in the default position. Session still would not: insertion remains `if !config.api_only && config.session_store`. Sessions still need `config.middleware.use config.session_store, config.session_options`. The claim is only half-implemented, and the half that lands is the wrong half for default apps.

**Manual `ActionDispatch::Cookies` / session / Flash.** `config.middleware.use` is appended after the default stack ([`MiddlewareStackProxy#use`](file:///home/user/workspace/repo/railties/lib/rails/configuration.rb#L66-L68), [`Engine#app`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L526-L528)). The guide and tests do exactly that:

```451:456:guides/source/api_app.md
config.session_store :cookie_store, key: "_your_app_session"

# Required for all session management (regardless of session_store)
config.middleware.use ActionDispatch::Cookies

config.middleware.use config.session_store, config.session_options
```

Same pattern in [`session_test.rb`](file:///home/user/workspace/repo/railties/test/application/middleware/session_test.rb#L450-L459). After the patch those apps get Cookies twice. `MiddlewareStack#use` does not dedupe. Inner Cookies writes `Set-Cookie` and does not `commit!` the jar ([`Cookies#call`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/cookies.rb#L713-L727)), so the outer copy can write again.

`ActionDispatch::Flash.new` is a passthrough (`def self.new(app) app; end`). Adding Flash still does not persist flash without a session.

**Disabled sessions.** Getter is `nil`. Full-stack still gets Cookies (`unless api_only`). API-only does not. That case is fine.

**Initialization order.** The default-store initializer is `before: :build_middleware_stack`, so a session store set in `application.rb` is visible. Setting it in an initializer after the stack is built is already too late for default middleware; the patch does not change that. The real order bug is the opposite: the default initializer makes “configured” true before the user has opted in.

## Observable request effects

Session stores persist via `request.cookie_jar` ([`AbstractStore#set_cookie`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/session/abstract_store.rb#L90-L92), [`CookieStore`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/middleware/session/cookie_store.rb#L117-L125)). Cookies middleware is what turns that jar into `Set-Cookie`. Without it, jar mutations do not hit the response.

With the patch on a default API app you get an extra Rack hop on every request. `Cookies#call` only writes if `have_cookie_jar?`, so idle JSON endpoints would not sprout cookies. Anything that touches `request.cookie_jar` (or a `ActionController::Base` descendant, e.g. Active Storage’s custom-session API test) would start emitting `Set-Cookie`. Session cookies still would not, because session middleware is still absent.

`ActionController::API` still does not include `ActionController::Cookies`, so the `cookies` helper remains missing until the app includes it.

## Test gaps

No test asserts “API + `config.session_store` ⇒ Cookies in the default stack.” Existing coverage says the opposite:

- API stack is an exact list without Cookies.
- API + sessions is the documented manual `middleware.use` pair.
- Disabled store is a full-stack request test, not an API stack test.
- Duplicate Cookies / `Set-Cookie` is untested.

`test "api middleware stack"` would fail if this landed without test updates, and updating that list to always include Cookies would encode the accidental default-API change.

## Compatibility

- Default API apps pick up cookie middleware they did not ask for.
- Apps that followed [`api_app.md`](file:///home/user/workspace/repo/guides/source/api_app.md) get duplicate Cookies.
- Session options / SSL `:secure` cookie forcing still do not apply to API apps, because that block stays behind `!config.api_only`.
- Full-stack and `:disabled` stay compatible.

## Narrower alternative

Do not key off `config.session_store` while the default initializer still assigns CookieStore for API apps.

If the product goal is “API apps that opt into sessions get a working cookie+session pair in the right order”:

1. Skip `setup_default_session_store` when `config.api_only` (so a truthy store means the user set it).
2. Then, when `config.session_store` is present, insert Cookies and the session store for API apps in the existing Callbacks → Cookies → session position, including the SSL secure-cookie options.
3. Do not insert Flash/CSP as a side effect.
4. Update [`api_app.md`](file:///home/user/workspace/repo/guides/source/api_app.md) so `middleware.use ActionDispatch::Cookies` is no longer required, and add tests for: default API (still no Cookies), API + explicit store (Cookies then session, no Flash), API + `:disabled` (no Cookies), and no duplicate Cookies when the old `middleware.use` lines remain.

If the goal is only “don’t forget Cookies when someone manually adds a session store,” a stack check/insert-before-session is more honest than changing the API-only default. The documented two-line opt-in already works; this patch is not a safe substitute.
