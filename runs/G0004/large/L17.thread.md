## Assistant

`#strict_loading!` is per-record state: a boolean plus a mode. `:all` treats every lazy association load on that record as a violation. `:n_plus_one_only` lets the record load associations, then turns the flag on only for `has_many` children so the next hop is what raises.

### What the method stores

```736:754:activerecord/lib/active_record/core.rb
    def strict_loading!(value = true, mode: :all)
      unless [:all, :n_plus_one_only].include?(mode)
        raise ArgumentError, "The :mode option must be one of [:all, :n_plus_one_only] but #{mode.inspect} was provided."
      end

      @strict_loading_mode = mode
      @strict_loading = value
    end

    attr_reader :strict_loading_mode

    def strict_loading_n_plus_one_only?

    end

    def strict_loading_all?
      @strict_loading_mode == :all
    end
```

New records copy class defaults in `init_internals`: `@strict_loading = klass.strict_loading_by_default`, `@strict_loading_mode = klass.strict_loading_mode` (`:all`). Relation `#strict_loading` later calls `record.strict_loading!(strict_loading_value)` and therefore also defaults to `:all`.

Invalid mode is rejected immediately. There is no test for that path in [`strict_loading_test.rb`](file:///home/user/workspace/repo/activerecord/test/cases/strict_loading_test.rb); the `ArgumentError` lives only in this method.

### Two modes, two different questions

Violation is decided on the **association owner**, just before a DB load:

```235:244:activerecord/lib/active_record/associations/association.rb
      def violates_strict_loading?
        return unless find_target?

        return if @skip_strict_loading

        return unless owner.validation_context.nil?

        return reflection.strict_loading? if reflection.options.key?(:strict_loading)

        owner.strict_loading? && !owner.strict_loading_n_plus_one_only?
      end
```

| Mode on owner | `violates_strict_loading?` for that owner’s own lazy load |
|---|---|
| `:all` | true if `strict_loading?` |
| `:n_plus_one_only` | false — the owner may lazy-load |

`:n_plus_one_only` does its work later, when records are materialized, via `set_strict_loading`:

```123:128:activerecord/lib/active_record/associations/association.rb
      def set_strict_loading(record)
        if owner.strict_loading_n_plus_one_only? && reflection.macro == :has_many
          record.strict_loading!
        else
          record.strict_loading!(false, mode: owner.strict_loading_mode)
        end
      end
```

Mode is copied even when the flag is turned off. `strict_loading_n_plus_one_only?` looks only at `@strict_loading_mode`, not at `@strict_loading`. HABTM is implemented as `has_many :through`, so `reflection.macro` is `:has_many` and HABTM children are treated like `has_many` children.

```diagram
:all
  owner.strict_loading!                 # flag on, mode :all
    lazy has_many / belongs_to / has_one
      violates_strict_loading? → true   # raises/logs here

:n_plus_one_only
  owner.strict_loading!(mode: :n_plus_one_only)
    lazy belongs_to/has_one child
      no violation on owner
      child.strict_loading!(false, mode: :n_plus_one_only)
    lazy has_many child
      no violation on owner
      child.strict_loading!             # flag on, mode defaults to :all
        child.anything_lazy
          violates_strict_loading? → true
```

### Where the error (or log) is raised

`find_target` is the common load path for singular and collection associations:


`CollectionProxy#pluck` has a parallel check because it can hit SQL without `find_target`.

```254:264:activerecord/lib/active_record/core.rb
      def self.strict_loading_violation!(owner:, reflection:)
        case ActiveRecord.action_on_strict_loading_violation
        when :raise

          raise ActiveRecord::StrictLoadingViolationError.new(message)

        end
      end
```

Default is `:raise`. `:log` instruments `strict_loading_violation.active_record`; the log subscriber prints the same message at debug. The message is built from the **owner class** and reflection, not the instance:

```347:351:activerecord/lib/active_record/reflection.rb
      def strict_loading_violation_message(owner)
        message = +"`#{owner}` is marked for strict_loading."

      end
```

Guards that skip the check:

- association already loaded (`find_target?` is false)
- `@skip_strict_loading` (concat / replace / some writers)
- `owner.validation_context` is set
- association option `strict_loading:` present — that boolean wins over the owner’s flag

### How state reaches association objects and child records

```text
record.strict_loading!(...)
  @strict_loading, @strict_loading_mode on the record

record.audit_logs / record.mentor
  association.reader
    not loaded → load_target → find_target
      violates_strict_loading?  → raise/log
      else load rows
        set_strict_loading(child) on each materialized record

record.audit_logs.to_a
  CollectionProxy#records → load_target → same find_target

AssociationRelation#exec_queries (LIMIT / scoped collection queries)
  also calls set_strict_loading(record)

includes / preload with parent Relation#strict_loading
  StrictLoadingScope → cascade_strict_loading
  children instantiated with record.strict_loading!(true)

eager_load / joins
  JoinDependency#construct_model
    model.strict_loading! if parent relation or association scope is strict
```

Preload does **not** call `set_strict_loading`. Children get the flag because the preload scope was marked `strict_loading`, or because the child class has `strict_loading_by_default`.

`:all` also changes collection **read** behavior. `find_from_target?` is true when the owner is strict-loading in `:all`, so `first` / `take` load the whole collection instead of issuing a `LIMIT` query — avoiding a second SQL round-trip that would itself be a violation.
