`retry_on` is a `rescue_from` wrapper. On a matching error it either reenqueues the same job or treats the job as exhausted. I ran `AJ_ADAPTER=test bundle exec ruby -Itest test/cases/exceptions_test.rb test/cases/instrumentation_test.rb` from `activejob/`: 38 runs, 0 failures.

```text
perform_now
  executions += 1
  _perform_job → perform callbacks → perform
rescue Exception
  rescue_with_handler(exception)          # Rescuable, bottom-to-top
    retry_on handler
      executions_for(exceptions) += 1     # per retry_on declaration
      if unlimited or count < attempts
        report if report: true
        retry_job(wait, queue, priority, error)
          instrument enqueue_retry
            enqueue → enqueue callbacks → adapter
      else
        instrument retry_stopped
        yield job, error  if block given
        run_after_discard_procs
        raise error       unless block given
  if unhandled
    run_after_discard_procs
    raise
```

## Matching: bottom-to-top, then ancestors

`retry_on` registers through `rescue_from`. Each exception class becomes one handler entry; later declarations append.

```75:92:activejob/lib/active_job/exceptions.rb
        rescue_from(*exceptions) do |error|
          executions = executions_for(exceptions)
          if attempts == :unlimited || executions < attempts
            # ...
            retry_job ...
          else
            # exhaustion
          end
        end
```

Lookup is last-declared first (`rescue_handlers.reverse_each`), then `klass === exception`. That is `is_a?` for Exception classes, and also honors a custom `===`.

```123:137:activesupport/lib/active_support/rescuable.rb
        def find_rescue_handler(exception)
          if exception
            _, handler = rescue_handlers.reverse_each.detect do |class_or_name, _|
              if klass = constantize_rescue_handler_class(class_or_name)
                klass === exception
              end
            end
```

Subclass handlers sit after inherited ones because `rescue_handlers` is a `class_attribute`: a child copies the parent array and appends. Reverse search therefore tries the child first, then the parent. That is the “bottom to top, and up the class hierarchy” rule in the `retry_on` docs.

Only one handler runs. `AfterDiscardRetryJob` declares `retry_on AfterDiscardError` then `retry_on ChildAfterDiscardError`. A child error matches the child handler, so `after_discard` runs once, not twice ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L423-L428), [after_discard_retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/after_discard_retry_job.rb#L18-L19)). Active Support’s own tests show later declarations overwrite earlier ones for the same class, and children append ([rescuable_test.rb](file:///home/user/workspace/repo/activesupport/test/rescuable_test.rb#L153-L163)).

If nothing matches the exception, `rescue_with_handler` walks `exception.cause` (with a cycle guard). That is Rescuable, not Active Job–specific.

## Shared vs separate attempt counters

`attempts` counts the original execution plus retries (`executions < attempts` after incrementing). Default is 5.

The counter is per `retry_on` declaration, not per exception class. `executions_for` keys `exception_executions` with `exceptions.to_s` — the whole list from that call:

```207:213:activejob/lib/active_job/exceptions.rb
      def executions_for(exceptions)
        if exception_executions
          exception_executions[exceptions.to_s] = (exception_executions[exceptions.to_s] || 0) + 1
        else
          executions
        end
      end
```

One declaration, several classes, one counter. `retry_on FirstRetryableErrorOfTwo, SecondRetryableErrorOfTwo, attempts: 4` dies on the 4th combined failure ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L42-L56)). Separate `retry_on` lines get separate keys, so `DefaultsError` (5 attempts) then `FirstRetryableErrorOfTwo` (4) can both retry on the same job ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L58-L76)). Delay math uses that same per-declaration counter, not `job.executions` ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L346-L372)).

`exception_executions` is serialized with the job ([core.rb](file:///home/user/workspace/repo/activejob/lib/active_job/core.rb#L40-L44)). Pre–per-declaration jobs with `exception_executions = nil` fall back to the global `executions` counter ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L392-L410)).

`attempts: :unlimited` skips the comparison and never takes the exhaustion branch. The fixture retries `UnlimitedRetryError` nine times and succeeds on the 10th ([retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L45), [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L385-L390)).

## Wait: proc arity, polynomial backoff, jitter

`wait` is validated when `retry_on` is declared: Integer, Float, Duration, Proc, or `:polynomially_longer` ([exceptions.rb](file:///home/user/workspace/repo/activejob/lib/active_job/exceptions.rb#L67-L73), [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L447-L465)).

```181:204:activejob/lib/active_job/exceptions.rb
      def determine_delay(...)
        jitter = jitter == JITTER_DEFAULT ? self.class.retry_jitter : (jitter || 0.0)
        case seconds_or_duration_or_algorithm
        when :polynomially_longer
          delay = executions**4
          delay + determine_jitter_for_delay(delay, jitter) + 2
        when ActiveSupport::Duration, Integer, Float
          delay = seconds_or_duration_or_algorithm.to_f
          delay + determine_jitter_for_delay(delay, jitter)
        when Proc
          algorithm.arity == 2 || algorithm.arity < -1 ? algorithm.call(executions, error) : algorithm.call(executions)
```

- One-arg proc (`arity` 1 or `-1`): `(executions)` only. `->(executions) { executions * 2 }` waits 2, 4, 6, 8. `->(executions = 0)` is arity `-1`, same path ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L308-L337)).
- Two-arg proc (`arity` 2 or `< -1`): `(executions, error)`. `->(executions, error) { error.retry_after + executions }` waits 11 then 12 ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L332-L344)).
- Proc results are not jittered.

`:polynomially_longer` is `(executions**4) + (Kernel.rand * executions**4 * jitter) + 2`: ~3s, ~18s, ~83s, ~258s ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L175-L200)). Jitter is applied to `executions**4` only, not to the `+ 2`.

`JITTER_DEFAULT` means `self.class.retry_jitter` (0.0 on `ActiveJob::Base`; Rails 6.1+ `load_defaults` sets 0.15). Explicit `jitter: nil` or `0.0` disables jitter ([retry_job.rb](file:///home/user/workspace/repo/activejob/test/jobs/retry_job.rb#L33-L34), [exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L280-L306)). `jitter.zero?` skips `Kernel.rand`.

## `report: true` and the exhaustion block

`report: true` calls `ActiveSupport.error_reporter.report(error, source: "application.active_job")` only on the retry path, before `retry_job`. Exhaustion does not report. The exception test covers the retry case: `ReportedError` with 2 executions reports once ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L418-L421)).

On exhaustion:

| | block given | no block |
|---|---|---|
| `retry_stopped` | around `yield self, error` | fired with no inner block |
| `after_discard` | always | always |
| original error | swallowed | `raise error` after `after_discard` |

`CustomCatchError` with a block: 6th failure is handled, nothing bubbles ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L117-L120)). `DefaultsError` without a block: after 5 attempts the same `DefaultsError` instance is re-raised ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L78-L83)). If an `after_discard` proc raises, that error replaces the original (`run_after_discard_procs` raises `exceptions.last` before `raise error`).

## Instrumentation, queue/priority, callbacks, escape

`retry_job` instruments `enqueue_retry.active_job` with `:error` and `:wait`, then `enqueue`. The in-memory job’s `scheduled_at` / `queue_name` / `priority` are restored in `ensure`; the adapter sees the overridden copy.

```168:174:activejob/lib/active_job/exceptions.rb
    def retry_job(options = {})
      instrument :enqueue_retry, options.slice(:error, :wait) do
        scheduled_at, queue_name, priority = self.scheduled_at, self.queue_name, self.priority
        enqueue options
      ensure
        self.scheduled_at, self.queue_name, self.priority = scheduled_at, queue_name, priority
```

`set` applies `queue` / `priority` only when those options are truthy, so the defaults `queue: nil, priority: nil` leave the job’s current values. `retry_on HeavyError, queue: :low` performs first from `default`, then from `low` ([logging_test.rb](file:///home/user/workspace/repo/activejob/test/cases/logging_test.rb#L299-L306)). There is no exception-test coverage for `priority:`; that path is the same `set` call.

Notifications (verified in [instrumentation_test.rb](file:///home/user/workspace/repo/activejob/test/cases/instrumentation_test.rb#L26-L32)):

- retry → `enqueue_retry.active_job` → structured `active_job.retry_scheduled` (wait as `wait_seconds: wait.to_i`, `executions` is `job.executions`, not the declaration counter)
- exhaustion → `retry_stopped.active_job` → `active_job.retry_stopped`, including when a custom block swallows the error

Logs: “Retrying … after N attempts in W seconds, due to a …” and “Stopped retrying … which reoccurred on N attempts.”

Callbacks:

- Failed `perform` runs `before`/`around_perform` until the raise; `after_perform` is skipped (`skip_after_callbacks_if_terminated: true`).
- A retry runs the full enqueue callback chain (`before`/`around`/`after_enqueue`). `RetriesJob` retries `BeforeEnqueueError` on the same job instance ([exceptions_test.rb](file:///home/user/workspace/repo/activejob/test/cases/exceptions_test.rb#L412-L416)).
- Exhaustion and unhandled errors run `after_discard`.

Does the original exception escape?

- Retry: no. `rescue_with_handler` returns the exception; `perform_now` returns it and does not re-raise.
- Exhaustion with a block: no.
- Exhaustion without a block: yes, after `after_discard`, unless `after_discard` raises first.
- No matching handler: yes, after `after_discard`.
