## Assistant

Discovery used the helper’s public calling forms, the navigation-helper tests (39 `button_to` cases, all passing), `url_helper` tests for `url_for` only, forgery-protection rendering, the Action View guides, and live probes of untested edges. `button_to` now lives on `NavigationHelper`, not `UrlHelper`. This is a draft for correction, not a confirmed spec.

**Kind of work:** behavior change. Authors already have a one-control submit helper; the work is to make its supported calling forms more predictable and more usable with keyboard and assistive tech. Several current surprises may also be defects against documented intent; that is not settled.

**Problem frame:** A Rails view author needs a labeled control that submits to a URL with a chosen HTTP method, extra fields, and CSRF protection, without building a full form. People using the page need to recognize the control, know whether it is available, and activate it. Today the same helper changes meaning with argument order, block vs string, model persistence, method spelling, nested form options, and app defaults, so authors cannot reliably predict destination, method, token, or control. Some of those differences also change what a keyboard or screen-reader user can perceive or operate.

## Actors

- View authors choosing a label, destination, method, remote submit, disabled state, extra form attributes, or an explicit authenticity token.
- People using the generated control with pointer, keyboard, or assistive technology, including when the control is disabled or submits remotely.
- App maintainers upgrading Rails or copying documented examples.
- Security reviewers who need mutating actions to stay bot-resistant and token-protected.

## Current observable baseline

Supported author-facing forms today:

- String label plus destination: `button_to("Hello", url)`.
- Block as label: first argument is the destination, not the label: `button_to(url) { ... }`.
- Destination may be a string, path, routing hash, model, nested model array, or `false`.
- Options authors treat as special: `method`, `remote`, `disabled`, `form`, `form_class`, `params`, `authenticity_token`, plus attributes passed through to the control.

**URL conversion.** A string destination is used as-is. A routing hash, path helper, model, or nested array is converted through `url_for`. `false` omits the form destination. `nil`, no destination, or a lone options hash raises `ActionController::UrlGenerationError: No route matches {}`. An empty string destination yields an empty action. Query characters in the destination are escaped in the generated action (including when the URL was already marked HTML-safe). `url_helper` tests cover `url_for` itself (no extra escaping there, `:back`, arrays) and no longer cover `button_to`; those examples live in the navigation-helper tests after the extraction.

**Method selection.** Default with a string URL is POST. A new record infers POST; a persisted record infers PATCH, including when the destination is a nested array whose last object is persisted. Explicit `method: :post` on a persisted record stays POST and does not add an override field. `:delete`, `:put`, and `:patch` keep a POST form and add a `_method` field. `:get` uses a GET form and no `_method` field. `method: "post"` matches POST. `method: "GET"` and `method: ""` still produce POST. Nested `form: { method: ... }` does not win; DELETE still produced a POST form with `_method=delete`. Nested `form: { action: ... }` does not win; the converted URL overwrote it.

**Authenticity token.** A token field is emitted only when the form method is POST (including DELETE/PATCH/PUT that use POST plus `_method`) and forgery protection is on. GET never emits a token, even with `authenticity_token: "token"`. With protection on: omitted/`true` uses the generated token; a string uses that string; `false` omits the token. `remote: true` still includes a token on POST. Protection off, or no `protect_against_forgery?`, omits the token. Controller tests show a POST `button_to` token is accepted as POST, and a DELETE `button_to` token is bound to DELETE.

**Generated form attributes.** The form’s class defaults to `button_to`. `form_class` sets that class when `form` has no class. `form:` attributes appear on the form (`class`, `id`, `data-type`). If `form` already has `class`, extra `form_class` is not applied to the form and is left on the submit control (`form_class="..."`), which is an observed leak. `remote: true` and `remote: "true"` add `data-remote="true"` on the form; `remote: false` adds nothing. Control `data:` (confirm, disable-with, turbo-confirm) lands on the submit control; `form: { data: { turbo_confirm: ... } }` lands on the form. Rails’ JavaScript guide tells authors that Turbo confirmation for `button_to` must be on the form, not the control.

**String label vs block.** A string becomes the control’s text. A block becomes the control’s inner content and always uses a button control, even when the app is configured to emit a legacy submit input for string labels. Passing both a string label and a block (`button_to("Ignored", url) { ... }`) raises `NoMethodError` (`stringify_keys` on a String). A block plus a routing hash and HTML options works: destination from the hash, options on the control, block as content.

**Disabled.** `disabled: true` marks the control disabled. `disabled: false` omits that mark. The surrounding form remains submittable in markup; only the control is disabled.

**Labels and unsafe HTML.** Ordinary string labels escape markup (`<script>` becomes text). HTML-safe strings are not escaped inside a button. Block content is escaped unless the block returns HTML-safe content. On the legacy submit input, an HTML-safe label is placed in the `value` attribute, so tags show as attribute text rather than structure. Form class values are escaped. Missing string labels fall back to the URL as the visible name.

**Config split.** New apps default to a button control for string labels. Older apps default to `<input type="submit">`. Docs still disagree: the helper guide shows a submit input; the upgrade guide still names `UrlHelper#button_to`.

## User problems and desired outcomes

These outcomes are hypotheses from the request plus the baseline. They describe what authors and people using the page should be able to count on, not how to build it.

**String label versus block.** Problem: the first argument changes meaning, a block cannot take a string name, and the control type can differ from the string form. Desired: the same destination, method, token policy, disabled state, and remote behavior for both; the visible name comes from the string or the block without silent argument shuffling; a mistaken mix fails in a way authors can understand.

**GET versus POST versus DELETE.** Problem: inferred PATCH on persisted models, case-sensitive method values, and POST-plus-override for DELETE are easy to misread. Desired: the submitted method matches the author’s stated method when one is given; when none is given, the inferred method is stable and documented for new vs persisted records; GET does not carry POST-only token behavior; DELETE remains a non-GET mutating submit, not a crawlable link.

**`remote: true`.** Problem: remote is a form flag, while confirm/disable data often land on the control, so remote and confirmation do not travel together. Desired: a remote submit is recognizable as the same action as the non-remote form, including method and token policy; authors can tell which attributes apply to the form versus the control.

**Disabled buttons.** Problem: only the control is marked disabled; the form and any hidden fields remain in the page. Desired: a disabled control cannot be activated by pointer or keyboard; assistive tech can perceive that it is unavailable; enabling/disabling does not change destination or method.

**Nested `form:` options.** Problem: some nested attributes apply, but method and action are overwritten, and `form_class` can leak onto the control. Desired: attributes meant for the form stay on the form; authors can predict which nested keys are honored; nothing intended for the form appears as a mystery attribute on the control.

**Explicit `authenticity_token`.** Problem: a provided token is ignored on GET and omitted when protection is off or the value is `false`. Desired: authors can require, replace, or suppress a token on submits that actually use token-protected methods; GET stays without a token; suppressing a token is explicit and does not silently affect other fields.

**Nil URLs.** Problem: `false` means “no destination,” `nil` and missing destination raise a routing error, `""` yields an empty destination. Desired: a missing destination is either clearly “no action” or a clear author error, consistently, including with a block.

**Labels containing unsafe HTML.** Problem: escaping depends on string vs block vs HTML-safe vs legacy input. Desired: untrusted label text never becomes executable markup; authors who intentionally supply trusted structured content get that structure only when the control can expose it to assistive tech as content, not as raw attribute text; the rule does not change with GET/POST/DELETE.

## Constraints

- Existing calling forms (string, block, model, nested array, `false`, `params`, `remote`, `disabled`, `form`, `authenticity_token`) remain usable; any break needs an explicit compatibility decision.
- Mutating actions must stay form-based rather than becoming ordinary GET links, so crawlers and prefetchers do not trigger them.
- Token behavior must stay compatible with Rails request forgery protection, including per-method tokens.
- Untrusted labels and attributes must not introduce executable markup.
- Older apps that still generate a submit input, and newer apps that generate a button, are both in the installed base.
- Accessibility improvements must not make the control inoperable with keyboard only.

## Non-goals

- Prescribing particular markup, new helper options, JavaScript behavior, internal helper structure, or test implementation.
- Redesigning `link_to` or general form builders.
- Changing the CSRF protocol itself.
- Making `button_to` a general-purpose form DSL (arbitrary nested fields, multipart, file uploads) beyond today’s `params` and form attributes.
- Inventing numeric a11y scores or traffic metrics.

## Behavioral examples

Required unless marked illustrative.

1. **Core, string POST.** An author writes a labeled submit to a URL with no method. A person activates it and a POST goes to that URL. With forgery protection on, a token is included; with it off, none is.

2. **Core, block.** The same destination and method with a block label. A person sees/hears the block’s content as the control name and the submit matches example 1 for destination, method, token, and disabled/remote flags.

3. **GET.** Explicit GET submits as GET to the destination, with no authenticity token even if a token value was passed.

4. **DELETE.** Explicit DELETE does not become a GET link. Activating it performs the delete-style submit; with protection on, the token matches DELETE, not an implicit POST.

5. **Inferred record method.** A new record without `method` submits as create/POST. A persisted record without `method` submits as update/PATCH. Passing explicit POST on a persisted record submits as POST.

6. **Remote.** `remote: true` keeps destination and method of the non-remote form and marks the submit as remote on the form. Confirmation intended for that submit is not silently left on a different element than the one the app’s JS listens to. *(Boundary: today’s split between control `data:` and form `data:` is the pain; the outcome is that authors can place confirmation where it actually runs.)*

7. **Disabled.** `disabled: true` is announced/shown as unavailable and cannot be activated. `disabled: false` matches an enabled control. Hidden destination/method/token fields do not provide an alternate activation path for that person.

8. **Nested form options.** Extra form attributes the author set (class, id, custom data) appear on the form. Form class does not appear on the control. Destination and method remain the helper’s destination and method unless product later decides nested overrides are supported (open question).

9. **Explicit token.** On POST/DELETE, a string token is the token used; `true` uses the generated token; `false` omits it. On GET, no token field appears.

10. **Nil vs false destination.** `false` produces a submit with no destination. `nil` is an author error today. Empty string currently produces an empty destination. Product must pick one rule (open question).

11. **Unsafe vs trusted label.** `"<script>alert(1)</script>"` is shown as text, not executed, for both string and block. A trusted HTML-safe string or HTML-safe block may expose structure in the button form; the legacy input form still cannot expose that structure as content.

12. **Counterexample: block plus string name.** `button_to("Ignored", url) { "From block" }` is not a supported form today (it raises). It should not silently treat `"Ignored"` as the URL.

13. **Counterexample: `method: "GET"`.** Today this still POSTs. Either GET-by-spelling is supported or it remains invalid/POST, but it must be one predictable rule.

## Compatibility risks

- Apps that rely on inferred PATCH for persisted models (Rails 7+). Forcing POST would revive the upgrade hazard already documented.
- Apps still on the legacy submit-input default versus apps on the button default; docs that still show the input.
- Call sites that pass `form:` expecting method/action overrides (they do not work) versus call sites that pass `form_class` plus `form: { class: }` (class leak on the control).
- UJS `data-remote` / `data-confirm` versus Turbo confirmation on the form.
- HTML-safe labels that currently inject markup into buttons; tightening escaping would change visible content.
- GET with extra `params` currently still emits hidden fields; changing that would change query vs body behavior.
- Treating `nil` like `false` would stop a routing error that some apps may use as a fail-fast.
- The public constant path is now `ActionView::Helpers::NavigationHelper#button_to`; remaining `UrlHelper#button_to` references are stale.

## Steering evidence and success signals

Qualitative only; no numeric targets were supplied.

**Success.** Authors can move between string and block forms without changing destination, method, or token policy. A keyboard user can tab to an enabled control and activate it, and cannot activate a disabled one. A screen-reader user gets a control name from either a string or a block and hears that a disabled control is unavailable. Untrusted labels do not execute. GET/POST/DELETE match the author’s stated or clearly inferred method. Reviewers comparing generated pages for the examples above see one rule per case, including `remote`, nested form attributes, and explicit tokens. Upgrade notes and the helper guide describe the same module and the same control default the app actually uses.

**Investigate / not yet successful.** The same destination is encoded differently for string vs block. `method: "GET"` and `method: :get` still disagree. Disabled controls are still reachable. Confirmation for remote/delete runs only if the author guessed form vs control. `form_class` still appears on the button. `nil` and `false` remain easy to confuse without a documented rule.

**Framing is wrong if.** Authors actually need a full form builder, not a single-control submit; accessibility issues come from app CSS/JS rather than the helper’s calling forms; or the real pain is documentation drift only, with behavior already acceptable once described.

## Open product questions

1. Is `nil` a synonym for “no destination” (`false`), a hard author error, or distinct from `""`?
2. Must string and block calling forms accept the same argument order, or is “block shifts arguments” acceptable if it is fail-loud for mixed use?
3. Should method values be case-insensitive (`"GET"` vs `:get`)?
4. Are nested `form` method/action author overrides, or always owned by the helper?
5. When both `form: { class: }` and `form_class` are passed, which is the single source of form class?
6. Is `remote: true` still a current product surface (UJS-style), or only compatibility with existing apps?
7. For HTML-safe labels, is structured content inside the control in scope for accessibility, or should labels stay plain text in every form?
8. Should inferred PATCH on persisted models stay the default, given the Rails 7 compatibility story?
9. What accessibility bar is in scope: keyboard operability and name/disabled state only, or also name/role/value expectations for remote and delete?

Please correct anything that is the wrong problem, the wrong actor, or a calling form that should stay frozen. I will not treat this draft as the agreed spec until you do.
