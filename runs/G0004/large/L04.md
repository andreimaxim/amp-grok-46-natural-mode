`Array#extract_options!` peels a trailing options hash off an argument list. It never scans the rest of the array.

```ruby
# activesupport/lib/active_support/core_ext/array/extract_options.rb
class Hash
  def extractable_options?
    instance_of?(Hash)
  end
end

class Array
  def extract_options!
    if last.is_a?(Hash) && last.extractable_options?
      pop
    else
      {}
    end
  end
end
```

That is the whole contract. Methods that take `*args` call it so a trailing keyword-style hash can be options without being a real keyword rest.

## Trailing-only

The predicate is `last`. Nothing else is inspected, popped, or merged.

```text
[1, { a: :b }].extract_options!  # => { a: :b }, receiver [1]
[{ a: :b }].extract_options!     # => { a: :b }, receiver []
[1].extract_options!             # => {},       receiver [1]
[].extract_options!              # => {},       receiver []
```

`last` on an empty array is `nil`, `nil.is_a?(Hash)` is false, so the empty array is the same as a non-hash last element.

## `Hash` vs subclasses

`is_a?(Hash)` is the type gate. `extractable_options?` is the extractability gate.

`Hash#extractable_options?` is `instance_of?(Hash)`, not `is_a?(Hash)`. A plain `Hash` passes. A `Hash` subclass fails unless it overrides.

```text
last.is_a?(Hash)                  last.extractable_options?         extracted?
──────────────────────────────    ──────────────────────────────    ──────────
Hash                              true (instance_of?(Hash))         yes
Hash subclass (no override)       false                             no
Hash subclass that returns true   true                              yes
not a Hash                        (not called)                      no
```

The tests pin that: `HashSubclass` stays in the array; `ExtractableHashSubclass` is popped. Framework hashes that should count as options opt in the same way: `HashWithIndifferentAccess`, `ActiveSupport::OrderedOptions`, and `ActiveSupport::OrderedHash` all define `extractable_options?` as `true`.

Opt-in is on the object’s class, not on the array. `extract_options!` does not special-case those types.

## Mutation and the empty-hash return

On a hit, the method `pop`s. The receiver loses its last element; the return value is that same object, not a copy.

On a miss, the receiver is left alone and the method returns a new `{}`. That empty hash is not the last element. Callers can mutate the return as options without touching a leftover positional hash.

```text
array = [hash_subclass]
array.extract_options!  # => {}
array                   # => [hash_subclass]   # unchanged
```

The bang is only justified on the success path.

## Why an earlier hash stays positional

Because only `last` is eligible, an earlier hash is just another argument:

```text
[{ a: 1 }, { b: 2 }].extract_options!
# => { b: 2 }
# receiver: [{ a: 1 }]
```

That is the `*args` convention this exists for. `foo(record_hash, page: 2)` can treat `record_hash` as data and `{ page: 2 }` as options. If extraction walked the array, every hash argument would be options, and APIs that take hashes as positional values (`validates`, `form_for`, route components, cache names, etc.) would collapse.

The two-check order matters for that same reason: a trailing `Hash` subclass that did not opt in is still positional, even though `is_a?(Hash)` is true. Extraction is “trailing extractable options,” not “trailing hash.”
