`stream_from` does not send messages. It registers a named pubsub listener on the channel. `broadcast` is the producer: it stringifies the name, optionally encodes the payload, and publishes. The two APIs only meet on that string name.

```diagram
Client subscribe
      │
      ▼
Connection::Subscriptions#add
      │
      ▼
Channel#subscribe_to_channel
      │  subscribed
      ▼
stream_from("comments_for_45")
      │  String(name)
      │  defer confirmation
      │  build handler
      ▼
pubsub.subscribe(name, handler, on_success)
      │
      │  on_success → confirm_subscription
      │
      ●  ──── later ────
      │
ActionCable.server.broadcast(name, hash)
      │  String(name)
      │  coder.encode (default JSON)
      ▼
pubsub.broadcast(name, encoded)
      │
      ▼
handler.call(encoded)
      │  default: JSON.decode → transmit
      │  user callback: optional decode → worker pool
      ▼
Socket#transmit → WebSocket JSON envelope
```

The pairing is name-based and online-only. If no one is streaming that name at publish time, the update is gone. That is stated at [actioncable/lib/action_cable/channel/streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L8-L16).

## Subscribe: `stream_from` registers, then waits

`ActionCable::Channel::Base` includes `Streams` ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L112)). A client `subscribe` command becomes `Subscriptions#add` → `subscribe_to_channel` ([subscriptions.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/connection/subscriptions.rb#L64-L77), [base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L197-L206)):

```text
subscribe_to_channel
  run_callbacks :subscribe
    subscribed                    # app calls stream_from here
  reject_subscription if rejected?
  ensure_confirmation_sent        # trailing decrement
```

`stream_from` itself ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L90-L107)):

1. Return immediately if `unsubscribed?` is already true. After `unsubscribe_from_channel` sets `@unsubscribed` ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L211-L221)), further `stream_from` calls are no-ops.
2. Coerce the broadcasting with `String(broadcasting)`.
3. `defer_subscription_confirmation!` so the client does not get `confirm_subscription` until pubsub subscribe succeeds.
4. Build a handler via `worker_pool_stream_handler`.
5. Store it in `streams[broadcasting]` (one handler per name; a second `stream_from` of the same name overwrites the hash entry).
6. `pubsub.subscribe(broadcasting, handler, success_lambda)` where success calls `ensure_confirmation_sent` and logs `is streaming from …`.

`stream_for` is only `stream_from(broadcasting_for(...))` ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L117-L119)). The name is then `channel_name:gid_or_param` ([channel/broadcasting.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/broadcasting.rb#L24-L38)). ## Deferred subscription confirmation

The counter starts at 1 in `initialize` because subscribe itself is one outstanding wait ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L168-L172)). Each `stream_from` increments it ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L94-L96), [base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L259-L264)).

`ensure_confirmation_sent` ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L253-L257)):

- no-ops if the subscription was rejected
- decrements
- transmits `confirm_subscription` only when the counter is 0

`transmit_subscription_confirmation` also guards with `@subscription_confirmation_sent` so the wire message is sent at most once ([base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L322-L330)). The type string is `"confirm_subscription"` ([action_cable.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable.rb#L61-L67)).

Observed in tests:

- One `stream_from` in `subscribed` still yields a single confirmation ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L139-L146)).
- Two `stream_from` calls still yield one confirmation ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L394-L402)).
- Calling `transmit_subscription_confirmation` twice still leaves one transmission ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L148-L159)).

With a sync adapter (`SuccessAdapter#subscribe` calls the success callback immediately, [test_adapter.rb](file:///home/user/workspace/repo/actioncable/test/stubs/test_adapter.rb#L14-L19)), the pubsub success decrement happens *during* `subscribed`, while the counter is still 2. Confirmation is actually emitted by the trailing `ensure_confirmation_sent` in `subscribe_to_channel`. With an async adapter, pubsub success can fire after that trailing decrement; confirmation then waits on the last success callback, which is the comment at [streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L94-L96).

## Default handler vs user callback

Handler assembly ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L163-L226)):

```text
worker_pool_stream_handler(name, user_handler, coder:)
  inner = stream_handler(...)
  if user_handler
    -> msg { connection.perform_work inner, :call, msg }   # worker pool
  else
    inner                                                  # pubsub thread
  end

stream_handler
  user_handler → stream_decoder(user_handler, coder:)
  no handler   → default_stream_handler
                   coder ||= ActiveSupport::JSON
                   stream_transmitter(stream_decoder(coder:), broadcasting:)
```

**Default (no callback, no block).** The handler always decodes, then `transmit`s. `coder: nil` at the `stream_from` keyword is *not* “raw” here: `default_stream_handler` replaces it with `ActiveSupport::JSON` ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L195-L198)). The transmitter always sends; the client sees `{ identifier, message: decoded }` with `via: "streamed from <name>"` ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L214-L225), [base.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/base.rb#L237-L250)).

The default-handler test broadcasts `{ foo: "bar" }` (JSON-encoded on the way in) and asserts the socket message is `{ "foo" => "bar" }`, with `perform_work` never called ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L380-L390)).

**User callback.** There is no auto-`transmit`. `stream_decoder` either calls `coder.decode` then the callback, or passes the raw pubsub payload when `coder` is falsy ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L200-L212)). The docs example therefore calls `transmit message` itself ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L56-L73)).

`UserCallbackChannel` uses a block and no coder, so the raw payload goes to the block ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L330-L336)).

## `coder: nil` vs `ActiveSupport::JSON` vs server-side custom encoding

These are two independent coder arguments. They do not have to match.

| Path | `coder: nil` | `coder: ActiveSupport::JSON` (or omitted where that is the default) |
|---|---|---|
| `broadcast` / `broadcaster_for` | publish `message` unchanged | `coder.encode(message)` before pubsub |
| `stream_from` **with** callback | no decode; callback gets the pubsub bytes/object | `coder.decode` then callback |
| `stream_from` **without** callback | still JSON-decode (`coder \|\|= ActiveSupport::JSON`) then transmit | decode with that coder then transmit |

Server-side custom encoding is the broadcast-side coder. The only test of that in this revision is `DummyEncoder` ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L38-L42), [stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L356-L365)):

```ruby
def encode(*) '{ "foo": "encoded" }' end
def decode(*) { foo: "decoded" } end
```

`subscribe_to` uses `ChatChannel` with `params[:coder]` unset, so the *stream* decoder is JSON ([stream_test.rb](file:///home/user/workspace/repo/actioncable/test/channel/stream_test.rb#L14-L35)). Broadcast uses `coder: DummyEncoder`, which ignores the hash and publishes the string `'{ "foo": "encoded" }'`. The default stream handler JSON-decodes that string. Observable client message: `{ "foo" => "encoded" }`. `DummyEncoder#decode` is never used in that test.

`ChatChannel#pick_coder` can select `"none"` → `nil` and `"custom"` → `DummyEncoder` on the stream side, but no test in this file passes those params. The `coder: nil` “raw messages” contract is documented and implemented for **user callbacks only**.

The comment at [streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L192-L194) notes the default path always decode-then-re-encode through `transmit` even when pubsub and the socket are both JSON.

## Decode / encode failures

This revision has **no test** that raises from `coder.encode` or `coder.decode`. Behavior is only what the call sites do:

**Encode on broadcast.** `Broadcaster#broadcast` has no rescue. A failing `coder.encode` raises into the `broadcast` caller and never reaches pubsub ([server/broadcasting.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/broadcasting.rb#L54-L61)). `coder: nil` cannot fail at encode; it publishes the object unchanged.

**Decode on the default handler.** `coder.decode` runs on the pubsub/executor thread, unrescued ([streams.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/channel/streams.rb#L200-L205)). Invalid JSON (or a custom decoder raising) aborts that callback. Other subscribers on the same broadcasting still run (`SubscriberMap#broadcast` iterates `list.each`). There is no client `transmit` for the failed handler.

**Decode on a user callback.** Decode is inside the handler that `perform_work` invokes. `Worker#invoke` rescues `Exception`, logs `There was an exception - …`, and calls `receiver.handle_exception` only if the receiver defines it ([worker.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/worker.rb#L58-L66)). The receiver is the handler Proc, which does not, so the failure is logged and swallowed. The callback never sees the message.

**Encode on the socket.** `transmit` JSON-encodes the cable envelope ([socket.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L45-L50), [socket.rb](file:///home/user/workspace/repo/actioncable/lib/action_cable/server/socket.rb#L116-L118)). A non-JSON-serializable object that survived stream decode would raise there, also unrescued.

Mismatch is enough to fail decode: `broadcast(..., coder: nil)` of a Hash plus a default stream handler (`JSON.decode`) will raise, because the published object is not a JSON string. The custom-encoder test only works because `DummyEncoder#encode` happens to return JSON text the default decoder can parse.
