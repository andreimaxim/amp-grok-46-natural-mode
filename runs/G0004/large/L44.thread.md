I found **no upstream Rails PR or issue specifically about `Rails::Command::RunnerCommand#perform` leaking/restoring `ARGV` when called directly or embedded**. Current `main` still performs an unguarded replacement:

```ruby
ARGV.replace(command_argv)
```

It never restores the prior value within `RunnerCommand#perform` ([`runner_command.rb` lines 24–65](https://github.com/rails/rails/blob/main/railties/lib/rails/commands/runner/runner_command.rb#L24-L65)).

Therefore, the proposed `old_argv = ARGV.dup` plus `ensure { ARGV.replace(old_argv) }` is **not already implemented in upstream runner code**.

## Intended command-level isolation

Normal Rails dispatch goes through `Rails::Command.invoke`, which wraps the entire command execution in `with_argv(args)` ([`command.rb` lines 55–69](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L55-L69)). `with_argv`:

1. Duplicates the caller’s `ARGV`.
2. Replaces it with the invocation arguments.
3. Executes the command.
4. Restores the original contents in an `ensure` block.

See [`command.rb` lines 140–146](https://github.com/rails/rails/blob/main/railties/lib/rails/command.rb#L140-L146).

For a normal invocation, the nesting is effectively:

```ruby
with_argv(all_runner_args) do
  RunnerCommand#perform
  # RunnerCommand replaces ARGV with only command_argv
end
# with_argv restores the pre-invocation ARGV
```

Thus:

- **Through `Rails::Command.invoke`:** runner arguments do not escape the invocation.
- **Directly calling `RunnerCommand#perform`:** its `ARGV.replace(command_argv)` persists afterward.
- Adding local restoration to `perform` would close that direct/embedded-call gap without changing what runner code sees during execution.

## Relevant upstream design history

The closest upstream discussion is about isolation at the **`Command.invoke` boundary**, not specifically `RunnerCommand`:

- [PR #38495, “Isolate ARGV in Rails::Command.invoke”](https://github.com/rails/rails/pull/38495) explicitly says commands should not depend on previous `ARGV` and command mutations must not affect code after `invoke`.
- [PR #41611, “Populate ARGV with Rails::Command.invoke args”](https://github.com/rails/rails/pull/41611) refined that contract: invoked code should see the supplied arguments, while `ARGV` remains isolated between invocations.
- [Issue #40945](https://github.com/rails/rails/issues/40945) and [PR #40994](https://github.com/rails/rails/pull/40994) document why merely clearing `ARGV` was insufficient: templates and application initialization had historically expected invocation arguments to be visible.

- Commit [`5aea095`](https://github.com/rails/rails/commit/5aea0952e7cb445e614652e3cd9aba71a836eed0): pass extra runner arguments to the loaded script.
- Commit [`a06a643`](https://github.com/rails/rails/commit/a06a643e0572b8c983738c068ae637d020188c97): ensure the code/file operand itself is excluded from `ARGV`.

**Conclusion:** upstream’s documented model is “populate `ARGV` for the command, but isolate and restore it at `Rails::Command.invoke`.” `RunnerCommand#perform` assumes that outer boundary and does not independently isolate direct calls.

### Compatibility and tests

On the CLI path the extra restore is mostly harmless: `with_argv` already clobbers post-run ARGV, including in-script `ARGV <<` / `ARGV.replace` mutations.

It is still the wrong contract to copy into `#perform`:

- `at_exit` / `exit` inside a script already observe `with_argv`’s restored vector, not `command_argv`. A second restore does not fix a CLI bug.
- Direct `#perform` callers that *want* ARGV left as the script’s args would change.
- `$0` stays leaked after file runs, so embedding is still unclean.

[`railties/test/commands/runner_test.rb`](file:///home/user/workspace/repo/railties/test/commands/runner_test.rb) never inspects ARGV. Application tests only print ARGV **inside** a forked `bin/rails` ([`abstract_unit.rb`](file:///home/user/workspace/repo/railties/test/isolation/abstract_unit.rb#L408-L456) replaces ARGV in the child and exits). Nothing would fail today, and nothing would prove the claimed embed leak unless a test calls `#perform` in-process and asserts ARGV (and `$0`) after return, including `SystemExit` from syntax/missing-file.

### More precise change

Do not add `old_argv = ARGV.dup` / `ensure ARGV.replace(old_argv)` to `#perform`. Leave runner ARGV assignment as the script-visible contract; keep isolation at `Rails::Command.invoke`.

If the product goal is “`#perform` is embeddable without `invoke`”:

1. Restore **both** `ARGV` and `$0` around only the eval/load/`-` branches (not around `help; exit 1`, and after `boot_application!`).
2. Add in-process tests that do not use `rails "runner"`: original ARGV/`$0` after success, after `SyntaxError`, after missing `*.rb`, after `-`, and that dashed extras are still visible **during** the run.
3. Say why generate/console are different, or isolate there too.

Until that is the actual API and those tests exist, this PR should not land.
