`isolate_namespace` is class-body setup. It does not mount anything, draw routes, or dispatch a request. It stamps an engine as isolated, rewrites that engine’s name and default route scope, and (once) hangs lookup hooks on the namespace module. ### `engine_name`

`engine_name` is an alias of [`railtie_name`](file:///home/user/workspace/repo/railties/lib/rails/railtie.rb#L178-L181). Without isolation, the default is the engine *class* name: `MyEngine::Engine` → `"my_engine_engine"`. Isolation overwrites it from the *namespace* name: `isolate_namespace MyEngine` → `"my_engine"`.

```250:252:railties/lib/rails/railtie.rb

          ActiveSupport::Inflector.underscore(string).tr("/", "_")
        end
```

So `Bukkits::Awesome` becomes `"bukkits_awesome"`. The isolation integration test asserts exactly that for the simple case: `Bukkits::Engine.engine_name == "bukkits"` ([engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L951-L953)).

That string is reused as:

- the default `:as` for `mount` ([`Mapper#app_name`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L694-L701) returns `app.railtie_name` for a Railtie)
- the rake namespace for `*:install:migrations`
- the captured `name` inside `table_name_prefix` (see below)

**Explicit `engine_name`:** `engine_name "my_engine"` is `railtie_name=` ([documented on Engine](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L184-L191)). There is no dedicated test for assigning it. Order matters in the implementation:

- `engine_name` **before** `isolate_namespace` is overwritten; isolation always calls `engine_name(generate_railtie_name(mod.name))`.
- `engine_name` **after** isolation changes later `railtie_name` consumers (`mount` `:as`, rake tasks). It does **not** change `default_scope` (that used `mod.name`) or `table_name_prefix` (that closed over `name` at isolation time).

**Anonymous / unnamed namespace:** both `engine_name` and `default_scope` use `mod.name`. [`Inflector.underscore`](file:///home/user/workspace/repo/activesupport/lib/active_support/inflector/methods.rb#L113-L121) returns `camel_cased_word.to_s.dup` when `/[A-Z-]|::/` does not match, so `nil` becomes `""`. Then `generate_railtie_name(nil)` is `""`, `engine_name` is `""`, `default_scope` is `{ module: "" }`, and `table_name_prefix` is `"_"`. There is no engine/integration test for `isolate_namespace(Module.new)` or an anonymous engine class; this is only what those two methods do with a nil name. An anonymous `Class.new(Rails::Engine)` without isolation gets the same empty `engine_name`, because `railtie_name` falls through to `generate_railtie_name(self.name)`.

[`add_routing_paths`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L621-L631) then does `if routes? || routing_paths.any?` and registers that (possibly empty) set on `app.routes_reloader`. Missing `config/routes.rb` means no file is loaded into that set; the set still exists and is still the default endpoint.

**Custom endpoint.** `endpoint lambda { |env| ... }` makes `#app` wrap that lambda instead of the route set. `#call` still runs `build_request`, which assigns `req.routes = routes` and therefore still instantiates the route set ([engine.rb](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L779-L785)). The [“it passes router in env”](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L806-L832) test mounts such an engine at `/engine` and asserts `env["action_dispatch.routes"]` is `Bukkits::Engine.routes` inside the engine and `Rails.application.routes` on an app route.

### Externally visible routing: controller lookup

This is the isolation effect you see on a request.

`scope(module: "bukkits")` flows into mapping as `scope[:module]`. [`add_controller_module`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L329-L338) prefixes the controller unless the route used a leading slash (`"foo#index"` → `"bukkits/foo"`; `"/foo#index"` stays `"foo"`). Nested isolation uses `underscore("Bukkits::Awesome")` → `"bukkits/awesome"`, so `get "/foo" => "foo#index"` dispatches to `Bukkits::Awesome::FooController`. That is tested: mount at `/bukkits`, request `/bukkits/foo`, body `"ok"` ([engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1033-L1069)).

Request-time lookup does not consult `isolated?`. The Dispatcher asks the request for a constant:

```85:91:actionpack/lib/action_dispatch/http/request.rb
    def controller_class
      params = path_parameters
      params[:action] ||= "index"
      controller_class_for(params[:controller])
    end
```

`controller_class_for` camelizes `"bukkits/foo"` to `Bukkits::FooController`. Isolation’s contribution was already baked into `path_parameters[:controller]` when the engine’s routes were drawn.

```diagram
GET /bukkits/foo
      │
      ▼
Application RouteSet ── mount Bukkits::Engine, at: "/bukkits"
      │                   SCRIPT_NAME=/bukkits  PATH_INFO=/foo
      ▼
Engine#call → build_request (req.routes = engine.routes)
      │
      ▼
Engine RouteSet (default_scope module: "bukkits")
      │  get "/foo" => "foo#index"
      │  defaults[:controller] = "bukkits/foo"
      ▼
Dispatcher → Bukkits::FooController#index
```

A non-isolated engine drawing the same `get "/foo" => "foo#index"` would look up `FooController`, not `Bukkits::FooController`. Isolation is the module prefix, not a different dispatcher.

### `railtie_routes_url_helpers` and which helpers a controller gets

Isolation defines:

```415:417:railties/lib/rails/engine.rb
            unless mod.respond_to?(:railtie_routes_url_helpers)
              define_method(:railtie_routes_url_helpers) { |include_path_helpers = true| railtie.routes.url_helpers(include_path_helpers) }
            end
```

Action Controller, at load, does two class-level things ([action_controller/railtie.rb](file:///home/user/workspace/repo/actionpack/lib/action_controller/railtie.rb#L80-L82)):

1. `include app.routes.mounted_helpers` — every controller sees `main_app` and mount proxies.
2. `extend AbstractController::Railties::RoutesHelpers.with(app.routes)` — each subclass includes URL helpers.

[`RoutesHelpers`](file:///home/user/workspace/repo/actionpack/lib/abstract_controller/railties/routes_helpers.rb#L11-L22) is the isolation branch: if a module parent has `railtie_routes_url_helpers`, include **the engine’s** helpers; otherwise include **the application’s**. Mailers use the same hook with `include_path_helpers = false` ([action_mailer/railtie.rb](file:///home/user/workspace/repo/actionmailer/lib/action_mailer/railtie.rb#L41-L42)).

That is why, after boot, `Bukkits::MyMailer` responds to `foo_url` and not `bar_url`, and why `Bukkits::FooController#from_app` reports that neither `bar_path` nor the app helper `something` exist ([engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L951-L965)). Helper *files* follow the same parent walk via [`railtie_helpers_paths`](file:///home/user/workspace/repo/actionpack/lib/action_controller/railties/helpers.rb#L12-L16); isolated engine controllers get the engine’s `app/helpers`, not `ActionController::Helpers.helpers_path`.

This wiring is class definition time (`inherited`). Generating `/bukkits/foo` from `foo_path` inside that controller is request/view time, using the already-included module.

### Mount helpers and `main_app`

Two different helpers, installed at two different times.

**`main_app`** is always defined on the application route set during finish:

```61:63:railties/lib/rails/application/finisher.rb
      initializer :define_main_app_helper do |app|
        app.routes.define_mounted_helper(:main_app)
      end
```

[`define_mounted_helper`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/route_set.rb#L520-L535) defines a method on the shared `RouteSet::MountedHelpers` module that returns a [`RoutesProxy`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/routes_proxy.rb#L9-L48) around that route set. `main_app.bar_path` is therefore application routes, from anywhere that included `mounted_helpers`.

**Engine mount helpers** are created when `mount` is evaluated (route-draw time, not `isolate_namespace` time). [`Mapper#mount`](file:///home/user/workspace/repo/actionpack/lib/action_dispatch/routing/mapper.rb#L605-L663) defaults `:as` to `engine_name` / `railtie_name`, builds a normal named route, then `define_generate_prefix` for Railties:

```699:717:actionpack/lib/action_dispatch/routing/mapper.rb
            script_namer = ->(options) do
              prefix_options = options.slice(*_route.segment_keys)
              ...
              _url_helpers.public_send("#{name}_path", prefix_options)
            end

            app.routes.define_mounted_helper(name, script_namer)
```

The script namer is why `foo_path` inside the engine is `/bukkits/foo` rather than `/foo`, and why a mount under `scope "/:user"` produces `/anonymous/blog/posts` ([mounted_engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/mounted_engine_test.rb#L221-L237)). `MountedHelpers` is one shared module on `RouteSet`, so `blog.posts_path` works from the application and from another isolated engine (`Metrics`). Those helpers are not copied onto a `RoutesProxy`: `metrics.respond_to?(:weblogs_path)` is false even after `weblog.weblogs_path` has been used ([mounted_engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/mounted_engine_test.rb#L303-L306)).

Inside an isolated engine the usual pair is:

- short helpers (`foo_path`, `posts_path`) → engine RouteSet, with mount SCRIPT_NAME
- `main_app.bar_path` → application RouteSet

The isolation test renders exactly `"/bukkits/foo, /bar"` from `<%= foo_path %>, <%= main_app.bar_path %>` ([engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L906-L966)). With a sub-path `SCRIPT_NAME`, both sides preserve it: engine `main_app.bar_path` → `/foo/bar`, app `bukkits.bukkit_path` → `/foo/bukkits/bukkit` ([engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/engine_test.rb#L1656-L1694)).

Polymorphic URLs follow the same split: inside the engine, `polymorphic_path(Post.new)` uses relative naming + engine prefix (`/someone/blog/posts/44`); in the application, the same call without the engine proxy is `/posts/44` unless you pass `[blog, post]` ([mounted_engine_test.rb](file:///home/user/workspace/repo/railties/test/railties/mounted_engine_test.rb#L273-L282)).

### Lazy vs eager route loading

[`make_routes_lazy`](file:///home/user/workspace/repo/railties/lib/rails/engine.rb#L616-L619) runs on every engine, including the application, before `bootstrap_hook`:

```ruby
config.route_set_class = LazyRouteSet if Rails.env.local?
routes
```

`Rails.env.local?` is development or test ([environment_inquirer.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/environment_inquirer.rb#L13-L39)). In those envs the object you get from `Engine#routes` is [`Rails::Engine::LazyRouteSet`](file:///home/user/workspace/repo/railties/lib/rails/engine/lazy_route_set.rb), a RouteSet that calls `Rails.application.reload_routes_unless_loaded` on `call`, `draw`, `recognize_path`, `url_for`, `_path`/`_url` `method_missing`, and so on.

The finisher decides whether to load immediately:

```177:177:railties/lib/rails/application/finisher.rb
        reloader.execute_unless_loaded if !app.routes.is_a?(Engine::LazyRouteSet) || app.config.eager_load
```

So:

- **Eager (production, or `config.eager_load`)**: `RoutesReloader#execute_unless_loaded` runs at boot; `reload!` loads every registered `config/routes.rb` into every registered route set and `eager_load!`s them.
- **Lazy (development/test without eager load)**: route files are not loaded until the first request, `recognize_path`, or `_path`/`_url` helper. [`reload_routes_unless_loaded`](file:///home/user/workspace/repo/railties/lib/rails/application.rb#L168-L169) is `initialized? && routes_reloader.execute_unless_loaded`.

[`LazyRouteSet` tests](file:///home/user/workspace/repo/railties/test/engine/lazy_route_set_test.rb) pin the external behavior: after `require environment`, `root_path` is not yet in `url_helpers.methods`; calling it returns `"/"` for the app and `"/plugin/"` for the engine; a GET `/` or `/plugin/` also loads; `mounted_helpers` does not yet define `:plugin_engine` until used; `main_app.root_path` still works. `_path`/`_url` are the only suffixes that trigger load from `method_missing`, so including `url_helpers` into `Object` does not load routes on `to_ary`.

Mounted helpers on the lazy set are a second module ([`LazyRouteSet::MountedHelpers`](file:///home/user/workspace/repo/railties/lib/rails/engine/lazy_route_set.rb#L48-L74)) that copies methods from the shared `RouteSet::MountedHelpers` when `define_mounted_helper` runs — which, under lazy load, is during that first draw, not at `isolate_namespace` time.

### What is class-level vs request-time

| Happens when | What |
|---|---|
| Engine class body (`isolate_namespace`) | `isolated = true`; `engine_name` from `mod.name`; `config.default_scope`; first-time methods on `mod` (`railtie_namespace`, `table_name_prefix`, `use_relative_model_naming?`, `railtie_helpers_paths`, `railtie_routes_url_helpers`) |
| Controller/mailer class definition | Include engine or app `url_helpers` via `railtie_routes_url_helpers`; set `helpers_path` via `railtie_helpers_paths`; include `mounted_helpers` (methods may still be missing under lazy load) |
| Boot, `make_routes_lazy` | Choose `LazyRouteSet` in local env; instantiate `@routes` (even with no routes file) |
| Boot, `add_routing_paths` | Register route files and the route set with `RoutesReloader` |
| Boot, finisher | Define `main_app`; load routes now if not lazy / if `eager_load` |
| `routes.draw` / first lazy load | Apply `default_scope` module prefix; `mount` defines named route + mounted helper + SCRIPT_NAME namer |
| Request | App matches `mount`; `Engine#call` / `build_request`; engine RouteSet matches; `controller_class_for` constantizes the already-prefixed controller name |
| URL helper / view | Engine helpers (`foo_path`) vs `main_app` vs mount proxy (`bukkits`, `blog`); relative `param_key` for forms/polymorphic routes |

Isolation never changes the URL path by itself. The externally visible routing effects are: engine routes resolve to namespaced controllers without writing `namespace` in the engine’s router; engine controllers/mailers see only that engine’s named routes plus `mounted_helpers`; the application does not absorb the engine’s helpers; models drop the namespace from form/param/route keys and gain a table-name prefix; `mount`’s default helper name is the isolated `engine_name`.
