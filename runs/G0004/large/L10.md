**Block.** The claim is false. `Hash#compact_blank!` is defined as in-place `Object#blank?` removal, not as Ruby `Hash#compact`. Switching the predicate to `value.nil?` keeps the bang method’s `self` return (because `delete_if` still always returns the receiver) and still fails the public contract.

## Claim vs contract

Ruby `Hash#compact` / `compact!` drop only `nil`. Active Support’s method is a different API:

```265:276:activesupport/lib/active_support/core_ext/enumerable.rb
  # Removes all blank values from the `Hash` in place and returns self.
  # Uses Object#blank? for determining if a value is blank.
  #
  # ```
  # h = { a: "", b: 1, c: nil, d: [], e: false, f: true }
  # h.compact_blank!
  # # => { b: 1, f: true }
  # ```
  def compact_blank!
    # use delete_if rather than reject! because it always returns self even if nothing changed
    delete_if { |_k, v| v.blank? }
  end
```

That docstring is the same example as the existing test. `blank?` is documented as true for `nil`, `false`, empty, and whitespace-only strings ([`blank.rb`](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb#L7-L8)). Equivalence to Ruby `compact` is true of `nil?` and false of this API.

The non-bang Hash override uses the same predicate (`reject { |_k, v| v.blank? }` at [enumerable.rb:261-263](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/enumerable.rb#L261-L263)). `Enumerable#compact_blank` and `Array#compact_blank!` do too. A Hash-only `nil?` change would also split Hash from those siblings.

## Destructive return / identity

The implementation comment is the contract: `delete_if` rather than `reject!` so the method **always returns `self`**, even when nothing is removed.

Executed on this revision:

- `compact_blank!` on `{ a: 1, b: nil }` → same object, `{ a: 1 }`
- `compact_blank!` on `{ a: 1, b: 2 }` → same object, not `nil`
- Ruby `Hash#compact!` on an unchanged hash → `nil`
- `Hash#reject!` on an unchanged hash → `nil`
- `Hash#delete_if` on an unchanged hash → `self`

So `nil?` vs `blank?` does **not** change identity: both predicates still sit inside `delete_if`. What it does change is *which keys are deleted*. Copying Ruby `compact!` wholesale (including `nil` when unchanged) would also break the bang return that `delete_if` was chosen to preserve. Current tests only `assert_equal` contents after mutation; they never `assert_same` the return value.

`ActionController::Parameters#compact_blank!` is a separate method ([strong_parameters.rb:1051-1053](file:///home/user/workspace/repo/actionpack/lib/action_controller/metal/strong_parameters.rb#L1051-L1053)) that also uses `v.blank?`, via `reject!`. It is not `Hash#compact_blank!`.
