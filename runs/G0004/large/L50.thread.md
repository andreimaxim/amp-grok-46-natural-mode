## Assistant

**Problem frame:** App and engine authors run `bin/rails generate` and `bin/rails destroy` against a path that already exists. Help advertises the same `--force` / `--skip` contract for both, but the CLI does not always treat that existing file the same way across generate vs destroy, ordinary files vs migrations, interactive vs piped stdin, or app vs engine roots. People cannot tell whether the file will stay, be replaced, be removed, or abort the command. This is framed as **maintenance of one public collision contract**, not a new generator feature. If the differences are the long-standing contract, user-visible behavior stays as-is. If they contradict the documented flags, they are defects against that contract.

Grounding is from the generate/destroy CLI entry, `Rails::Generators` lookup/fallbacks/help, Thor file actions and the overwrite menu, engine destination roots, and Railties generator tests. I did not run live `bin/rails generate` / `destroy` against an app. Interactive answers, EOF stdin, and destroy-after-skip for ordinary files are inferred from that surface and are **not** asserted by Railties tests.

**Users:** Application developers generating or reversing code in an app. Engine authors doing the same from an engine root, including mountable and nested-name engines.

**Pain:** An existing target file is a common, expected situation (re-run, hand-edited file, previous skip). Today the same flags can mean overwrite, skip, prompt, hard error, or silent remove depending on command, file kind, and whether stdin is a TTY. Destroy after a skipped generate is especially unclear: the file may still be deleted even though generate declined to write it.

## Desired observable CLI behavior

One contract, visible from the command line, for both `generate` and `destroy`, in apps and engines:

- The same generator name resolves the same way on both commands (short names, `namespace:name`, fallbacks).
- A missing generator fails the same way on both commands: message, optional suggestion, non-zero exit, no files changed.
- Files are created or removed under the command’s destination root (app root, or the engine root when run inside an engine), including nested engine directories.
- When the target path already exists:
  - **Identical content:** generate does not change the file and reports it as identical. Destroy still treats the path as owned by the generator name (see open question).
  - **`--force`:** generate replaces differing content. Destroy removes the path. No prompt.
  - **`--skip`:** neither command changes that existing file.
  - **Interactive differing content (generate):** prompt before changing the file; yes / no / all / quit behave as below.
  - **Non-interactive stdin:** a single documented default, the same for app and engine generators (default itself is still open).
- Status lines (`identical`, `skip`, `force`/`conflict`, `remove`) match what happened to the file.
- Class-name reservation errors (“name already used or reserved”) are a separate check from file collisions. They appear on generate, not destroy, and `--force` / `--skip-collision-check` bypass them. Out of scope unless they are later judged part of this contract.

## Non-goals

- New generators, templates, or flags.
- Changing what a successful first-time generate writes.
- Redesigning help, coloring, or `--pretend` / `--quiet`.
- Merge/diff tooling beyond the existing overwrite menu.
- Implementation, architecture, or new test machinery.
- Deciding a new product policy where the current contract is confirmed intentional.

## Acceptance examples

Required cases, not an exhaustive catalog. “The user” is whoever runs `bin/rails generate` or `bin/rails destroy`.

**Identical content, generate.** A controller (or other ordinary file) already exists and matches what the generator would write. `bin/rails generate controller Topics` reports identical and leaves the file unchanged.

**Differing content, generate, no flags, interactive.** The same path exists with different content. The CLI asks `Overwrite <path>? (enter "h" for help) [Ynaqdhm]` and waits.

- **yes** (or empty): that file is replaced; the command continues.
- **no:** that file is unchanged; the command continues; later files can still be created or prompted.
- **all:** that file is replaced, and later collisions in this run are replaced without asking.
- **quit:** the CLI prints `Aborting...` and stops; that file is unchanged; no further files are written after the abort.

**`--force`, generate.** Differing existing file, `bin/rails generate … --force`. No prompt. File is replaced. Status shows force/replace, not skip.

**`--skip`, generate.** Differing existing file, `bin/rails generate … --skip`. No prompt. File is unchanged. Status shows skip. Other new paths may still be created.

**Non-interactive stdin, generate.** Differing existing file, stdin is not a TTY (EOF / piped empty). The command does not hang. Outcome is whatever the confirmed default is (overwrite, skip, or error)—same in apps and engines. **Default is unconfirmed.**

**Nested engine destination root.** From a mountable engine (including a nested name such as `bukkits-admin`), generate writes under that engine’s tree and namespace (`app/models/bukkits/admin/…`), not the dummy app or an unnamespaced app path. Destroy with the same generator name and arguments removes those same engine-rooted files and does not leave them in the dummy app.

**Namespaced generator resolution.** `model`, `rails:model`, and a configured fallback name (for example a test-framework alias that falls back to `test_unit`) resolve to the same generator on generate and on destroy. A nested name such as `my:awesome:namespace` resolves the same way on both. Rails’ own short name wins over a same-named generator on the load path.

**Missing generator.** `bin/rails generate unknownz` and `bin/rails destroy unknownz` both print that the generator could not be found, suggest a close name when there is one, point at generator help, exit non-zero, and change no files. **Open:** destroy’s help line currently names `generate --help`; whether that is the contract is unconfirmed.

**Destroy after a skipped collision.** An existing differing file was left in place by generate `--skip` (or interactive **no**). Then `bin/rails destroy` with the same generator and arguments. **Open:** either (a) destroy leaves that file (generate never wrote it), or (b) destroy removes it anyway (destroy is path-based reversal). The rest of a normal destroy (files generate did create) still comes out.

**Migration collision (boundary, already tested).** A migration with the same name already exists. Identical content: generate reports identical. Differing content without flags: generate errors and does not prompt (`Use --force to replace … or --skip to ignore`). `--skip` leaves it; `--force` replaces. Destroy removes the existing migration and does not show that conflict error. Whether ordinary files should keep prompting while migrations error is a contract question, not assumed to be a bug.

## Ambiguities — evidence needed before treating differences as accidental

These change the outcome. They stay open until someone watches the real CLI (or an existing public guarantee).

1. **Are generate and destroy supposed to share file-collision policy?** Help lists `--force` / `--skip` for both, but destroy removes an existing path without comparing content or prompting. Path-based destroy vs content-aware generate may be intentional.
2. **Destroy after skip / interactive no.** No Railties example shows whether destroy may delete a file generate refused to overwrite. That single outcome decides whether skip means “this file is not ours.”
3. **Ordinary file prompt vs migration hard error.** Same user-facing situation (target already exists, content differs, no flags). Two different CLI behaviors. Need a stated reason, or a decision that one of them is wrong.
4. **Non-interactive stdin.** Thor’s overwrite menu treats EOF as yes (overwrite). Rails tests do not pin this. CI and scripts may be overwriting files without a flag. Need to know if that is the contract.
5. **Interactive menu completeness.** yes / no / all / quit are in scope. `d` (diff), `m` (merge), and `h` (help) exist on the menu but were not requested; in or out?
6. **`--force` on destroy** and **`--skip` on destroy.** Help advertises both. Observed destroy is “remove if present.” Need to see whether `--skip` on destroy is supposed to refuse deletion of existing files.
7. **Missing-generator help on destroy** always telling the user to run `bin/rails generate --help`.
8. **Class-name collisions vs file collisions.** Generate can abort for a reserved/existing constant before files are considered; destroy does not. Same word “collision,” different meaning. Keep separate unless product intent says otherwise.
9. **App vs engine.** File placement and namespacing differ by design. Collision prompts, `--force`, `--skip`, missing-generator, and destroy-after-skip should not. If any of those already differ by engine root, that needs a captured transcript.

Cheapest evidence: one app and one nested mountable engine; ordinary file plus migration; identical vs differing; `--force`, `--skip`, TTY yes/no/all/quit, piped EOF; then destroy after skip. Record stdout/stderr, exit status, and whether the file bytes changed. That is enough to mark each difference as contract or accident.

## Steering evidence

**Success:** For the confirmed cases above, a person can predict the file and the message from the command, flags, and (when asked) the yes/no/all/quit answer, in both an app and an engine, without surprises between generate and destroy except differences that were explicitly kept.

**Investigate / do not “fix”:** A difference that matches documented help and a long-standing transcript (especially migration error vs ordinary-file prompt, or destroy removing by path).

**Wrong framing:** Users were actually blocked by class-name reservation, generator lookup, or engine namespacing—not by an existing file. Or they needed a new prompt/flag rather than a single contract. Stop and reshape.

---

This is a working brief, not a confirmed spec. The largest unconfirmed calls are destroy-after-skip, EOF-means-overwrite, and whether generate/destroy are supposed to be symmetric on existing files. Correct those and the examples change; the rest can stay.
