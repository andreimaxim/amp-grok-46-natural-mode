### Security invariants vs String compatibility

**Security (must not change):**

1. A **safe** receiver escaping-inserts untrusted text (`concat`/`<<`/`+`/`%`/`insert`/`prepend`/`replace`/`[]=`). Trusted (`html_safe`) text is inserted raw.
2. `safe_concat` never escapes. It is legal only while `html_safe?`. On a dirty receiver it raises `SafeConcatError` and must not mutate.
3. Once dirty, later `concat`/`%`/`*` must **not** re-escape and must **not** report `html_safe?`.
4. `[]` / `slice` / `slice!` on a dirty buffer must not return an `html_safe?` object (current code returns a plain `String` via `to_str`).
5. Bang transforms set `@html_unsafe = true` even when the match fails / content is unchanged.

**String compatibility (preserve unless the refactor’s stated contract drops it):**

- `concat`/`<<` mutate and return `self`; `nil` is a no-op ([L80–86](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/string/output_safety.rb#L80-L86)).
- `+`, `%`, `*` allocate; they do not mutate the receiver or `%` args.
- Integer `concat` is `String#concat`’s codepoint append (`13` → `"\r"`), still `html_safe?`.
- `slice` miss returns `nil`.
- `gsub!` with no match still returns `nil` (MRI), after marking dirty.
