**Problem frame:** Rails maintainers and app authors who write tests or diagnostic snippets need to watch notifications only while a piece of work runs. Today that window exists, but it is a second-class, callback-first path beside long-running `subscribe`. **Hypothesis:** the pain is ceremony, leak risk, and easy-to-miss scoping rules—not missing match types.

This is a draft for correction. Pain and “what better looks like” are inferred from the request plus current documented/tested behavior; they are not a reported incident.

## Current state (this revision)

Temporary observation is a documented companion to long-running subscription. The framework is described as designed for long-running subscribers; temporary use is warned as something to use sparingly because it wipes internal caches and hurts performance ([notifications.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/notifications.rb#L156-L161)).

## Maintainer / user pain

**Who:** people writing Rails tests, assertion helpers, and short diagnostic scripts who need “what fired during this work?”

**What happens today:** they must supply the observer as a separate callback from the work block, choose wall-clock vs monotonic themselves, and know that overlapping nested windows and raising work follow the rules above. After the block they rely on automatic unsubscription; leaking a long-running subscriber would keep collecting process-wide.

**Why it matters:** temporary observation is the natural shape for tests and diagnostics, but the documented happy path is long-running `subscribe`. Helpers hide some friction; anyone extending or bypassing them repeats the awkward split. Nested and raising work can surprise if “during the block” is read as “any finish inside the block.”

**Hypothesis, not a measured complaint:** no ticket or user quote was in this request. If the real pain is performance of subscribe/unsubscribe in tests, missing regexp docs, or assertion helpers rather than `subscribed` itself, the outcomes below should change.

## Desired observable outcomes

1. A test or diagnostic author can observe matching events **only while a given piece of work runs**, then see no further deliveries from that observation, without a manual unsubscribe.
2. That window still matches **exact name, regexp, and all events**, with the same inclusion/exclusion as today.
3. The author can still choose **wall-clock `Time` vs monotonic `Float`** timestamps; the default remains wall-clock.
4. **Nested windows stay independent:** an inner window does not receive an event that started before it opened; an outer window still can.
5. If the **instrumented work raises**, matching observers still see the published event (with exception payload), the error still surfaces to the caller, and the temporary observer does **not** remain subscribed afterward.
6. **Long-running `subscribe` / `unsubscribe` and both callback arities behave as they do now.** Existing one-argument Event callbacks and five-argument callbacks keep working, including those passed into temporary observation.

Usability here means less ceremony and less chance of a leftover subscriber for the scoped-observation job—not new match types, not new event fields.

## Non-goals

- Changing production, always-on subscription, or making temporary observation the default app-lifetime listener.
- Changing Event contents, exception payload keys, or the fact that instrumentation publishes on error then re-raises.
- Changing exact / regexp / all matching rules, invalid-pattern errors, or nested start/finish delivery.
- Changing callback arities or adding a third undocumented arity.
- Broadening assertion helpers (`assert_notification`, etc.) except as a natural consequence of easier temporary observation.
- Treating the cache-wipe performance warning as a problem this brief solves.
- Selecting types, classes, algorithms, or a new method shape.

## Compatibility constraints

- `subscribe`, `monotonic_subscribe`, and `unsubscribe` (by subscriber and by name, including regexp remainder behavior) stay the long-running path.
- One-argument Event vs five-argument `(name, start, finish, id, payload)` stay valid for both long-running and temporary observation.
- Default timestamps stay wall-clock `Time`; `monotonic: true` stays monotonic `Float`.
- Callers who already pass a callback plus a work block keep a supported path.
- Documented “use temporary subscription sparingly” in production remains in force; this work targets tests and diagnostics.

## Acceptance signals

**Success looks like:** authors of tests and diagnostic helpers can scope observation to a block of work with less setup than building a collector callback by hand; the examples above still hold; existing `subscribe` / `unsubscribe` callers and both arities need no change.

**Investigate (implementation or docs, not necessarily the goal):** a temporary observer still receiving after the window; a regexp or all-event window missing matches that long-running `subscribe` would see; monotonic timestamps becoming `Time` or wall-clock becoming `Float`; an inner window receiving an event started outside it; a raising block skipping the notification or leaving the observer attached.

**Reconsider the framing if:** people still reach for `subscribe` + manual `unsubscribe` in tests because the temporary path is unclear or costly; the real ask was assertion-helper gaps (`capture_notifications` has no monotonic switch) rather than `subscribed` itself; or production cache-wipe cost is the actual complaint.

**Stop if:** “usability” is resolved by documenting the existing callback-plus-block path, or if any change would require altering long-running subscription or callback arities.
