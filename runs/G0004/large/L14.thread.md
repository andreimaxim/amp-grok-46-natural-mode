## Assistant

**Problem frame:** A Rails developer (or plugin author) uses `ActiveSupport::OrderedOptions` as a Hash-like config object with attribute-style reads, including bang reads that must fail when a required value is missing or blank. Today those failures are hard to tell apart and hard to trace through inherited config, so diagnosis is slow even though the successful path already works.

This is a **behavior change** on the required-read failure experience, with a hard compatibility constraint: successful reads, writers, lookup, and Hash-like ordering stay as they are.

Evidence for current behavior: [ordered_options.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb), [ordered_options_test.rb](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb), [blank.rb](file:///home/user/workspace/repo/activesupport/lib/active_support/core_ext/object/blank.rb), plus a runtime probe for bang cases the tests do not cover (`false`, whitespace, empty collections, unset vs present-blank, inherited bang). Docs: [security.md](file:///home/user/workspace/repo/guides/source/security.md#L1745-L1751), [5.0 release notes](file:///home/user/workspace/repo/guides/source/5_0_release_notes.md#L1045-L1047).

## Current behavior is already a stable successful-read contract

**Symbol and string assignment and lookup** store one symbolized name. Assigning with a symbol or a string is the same entry; reading with `[]`, a string, a symbol, or a dynamic reader returns that same value. Mixed writes increase size by distinct names, not by key type. Insertion order of those symbolized names is preserved when enumerating. Tests: [test_usage](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L11-L27), [test_looping](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L29-L41), [test_string_dig](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L43-L51), [test_ordered_options_to_h](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L160-L168). Probe: `a["str"] = "from-str"` then `a[:str]` and `a.str` both return `"from-str"`; keys are `[:sym, :str]`.

**Dynamic writers and readers** do the same as `[]=` / `[]`. An unset reader returns `nil` and does not raise. A writer of `false` is stored and the non-bang reader returns `false`. Tests: [test_method_access](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L61-L77). Source: [method_missing](file:///home/user/workspace/repo/activesupport/lib/active_support/ordered_options.rb#L49-L57).

**`respond_to?`** is true for names that have never been set, including writers and bang readers. `method` can be taken for those names. Tests: [test_introspection](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L105-L111), [test_raises_with_bang](file:///home/user/workspace/repo/activesupport/test/ordered_options_test.rb#L113-L116). They raise `KeyError` with message `":name is blank"` when the resolved value is blank. Documented examples use that same exception and message. ## User pain

The optional read path already answers “what is stored?” The required read path only answers “present enough, or not.” When it is not, every failure looks the same: `KeyError` saying the name is blank.

That hurts in the situations this object is for: boot/config and credentials-style required reads ([security guide](file:///home/user/workspace/repo/guides/source/security.md#L1745-L1751)), and inherited config where the value may come from a parent or from a child override.

A developer cannot tell from the failure alone:

- the name was never set, versus set to `nil`, `false`, or whitespace
- the failing value is the child’s override versus an inherited parent value
- a boolean flag that is intentionally `false` is “blank” in the required-read sense

Non-bang reads, `dig`, and `respond_to?` do not compensate: a missing name still looks callable and still returns `nil`, same as an explicit `nil`.

**Hypothesis (not supplied by you, easy to veto):** the work is about making required-read *failures* understandable, not about changing which values successfully return.

## Desired outcomes

A person performing a required configuration read can still get the current successful value when that value is already treated as present.

When the required read cannot return a value, they can tell *why* it failed well enough to fix the config: at least unset versus present-but-unusable, without running a second manual inspection of writers, parents, and blank variants.

When the options object inherits, they can tell whether the required read used an inherited value or a child override, including when the child overrode a good parent value with a blank.

Optional reads, writers, `dig`, `respond_to?`, successful return values, and Hash-like ordering remain as they are today.

## Non-goals

- Changing successful return values of `[]`, dynamic readers, `dig`, or bang reads that currently succeed
- Changing Hash-like insertion order, symbolized storage of mixed string/symbol writes, or the fact that string and symbol reads hit the same name
- Making a missing non-bang reader raise
- Making `respond_to?` report only assigned names
- Changing Rails `blank?` for the rest of the framework
- Broader config, credentials, or railtie redesign
- New names, types, or storage (out of scope for this brief)

## Compatibility boundaries

Must remain:

- Successful bang and non-bang results above, including `false` and `nil` on non-bang reads
- `KeyError` as the failure class for required reads that cannot return a value (tests and docs)
- String/symbol assignment and lookup equivalence for `[]`, readers, writers, and `dig`
- Child inherits parent values; child override wins for the child; parent unchanged
- Enumeration order of symbolized names

Treat as compatibility risk / open:

- Exact message `":name is blank"` is in comments and the security guide, but tests only assert `KeyError`
- Whether `false` remaining a required-read failure is part of the contract (5.0 notes: bang raises if the value is `.blank?`) or part of the diagnosis pain

## Example journeys

These are required cases for agreement, not an exhaustive catalog.

**1. Required present value (core success)**  
Config has `api_key = "secret"`. The developer requires it. They receive `"secret"`, same as the non-bang read.

**2. Required unset name (core failure)**  
`api_key` was never set. Non-bang read is `nil`. Required read fails with `KeyError`. After the change, the failure is recognizably “this name was not set,” not only “blank.”

**3. Required explicit `nil` (boundary)**  
Someone set `api_key = nil`. Non-bang read is `nil`. Required read still fails. After the change, this is distinguishable from never set.

**4. Required `false` (boundary / open)**  
`enabled = false`. Non-bang read is `false`. Required read currently fails with the same blank `KeyError`. After the change, either that remains a failure but is recognizably “this is false,” or product later decides `false` is a successful required boolean. Do not silently flip that without an explicit decision.

**5. Required whitespace-only string (boundary)**  
`host = "   "` (also `""`, tabs, non-breaking space). Non-bang read returns that string. Required read fails. After the change, the failure is recognizably “present but blank text,” not “missing.”

**6. Optional missing read (counterexample)**  
`config.missing` and `config[:missing]` stay `nil` and do not raise. `dig(:missing)` stays `nil`. `respond_to?(:missing)` stays true.

**7. Inherited required value**  
Parent has `foo = :bar`. Child does not set `foo`. Child required read returns `:bar`.

**8. Child blank override of a good parent (inheritance diagnosis)**  
Parent has `keep = "parent"`. Child sets `keep = ""` or `nil`. Child required read fails; parent required read still returns `"parent"`. After the change, the child’s failure is recognizably from the child’s override, not from a missing parent.

**9. Ordering unchanged (counterexample)**  
Writes `one`, then `[:two]`, then `["three"]`. Enumeration remains `[:one, :two, :three]` with those values.

## Acceptance evidence

Success looks like:

- Existing successful required and optional reads still return the same objects/values
- Enumeration order of mixed string/symbol writes is unchanged
- A developer who only sees the required-read failure can say whether the name was unset, explicitly `nil`, `false`, or blank text, without dumping the whole object
- On inheritable config, they can say whether the failing or succeeding required value came from the child override or the parent
- Inherited present values still satisfy required reads; child blank overrides still fail required reads

We would investigate or reconsider the framing if:

- Callers start failing because they matched the exact string `":name is blank"` (message-as-API)
- Boolean config required-reads change from fail to succeed, or the reverse, without an explicit product decision
- Optional missing reads begin to raise, or `respond_to?` / `dig` / ordering change
- Developers still cannot tell unset from blank after the failure output is “improved”

**Open questions**

1. Must the `KeyError` message stay exactly `":name is blank"`, or may the failure text change if the class stays `KeyError`?
2. Is `false` a required-read failure that only needs a clearer explanation, or should a required boolean `false` succeed?
3. Is “unset vs present-but-unusable” enough, or must each blank-ish case (`nil`, `false`, whitespace, empty collection) be distinguishable?
4. For inheritable config, is “this value is the child’s override” required on success as well as failure, or only when the required read fails?

This is the shaping brief as specified: current behavior from source, tests, and probe; pain and outcomes; no classes, methods, storage, or mechanics. Correct the `false` decision and the exact-message constraint if those should be locked before any later design.
